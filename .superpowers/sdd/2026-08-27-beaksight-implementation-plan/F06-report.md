## Blocker（項目2）と、設計者の判断

- 状況: 凍結は、初期描画の後に auditor が有効にする。候補を探し直して handle を解決するのは、凍結の後である。そのため、凍結の前にスクロールしようとしても、そのための handle がない。
- 判断: 選択肢 A を採る。設計書 4.4 を再改訂し、F06b で実装する。
  - 手順: 凍結の前、Passive フェーズで下準備を行う。候補を探し直し、handle を解決する。その handle で `scrollIntoViewIfNeeded` を期限付きで実行してから、handle を破棄する。ページが落ち着くのを待ってから凍結し、その後はこれまでと同じ流れで進める。
  - 利点: 凍結の後の受け入れの判定と、安全の判定の順序を変えずに済む。
  - B を採らない理由: 安全の判定の順序が大きく変わるため。
  - 凍結の後にスクロールする案を採らない理由: スクロールで起きた遅延読み込みの通信が凍結によって遮断され、普通のボタンが BLOCKED になってしまうため。
- 補足:
  - DOM の作業量は、1回の audit の中で、これまでどおり共有する。下準備の探索で使う作業量も、同じ上限から差し引く。上限に近いページでは NOT_VERIFIABLE が増えるが、結果は正直である。
  - ページ座標への補正は残す。スクロールが起きなくなるので害はなく、既存のテスト（`:4376`）も直さずに済む。

## 発見事項と、設計者の判断

1. 期限切れの経路では、handle の破棄の失敗が遅れて届いた場合、結果の `safety` に入らないことがある。失敗は Ledger には残る。→ 許容する。既存の扱いと同じである。
2. N4 の回帰テストは、`Date.now` を呼ぶ回数に依存している。→ 許容する。観測ループを変えるときは、このテストも見直すこと。
