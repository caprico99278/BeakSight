## 指摘と、設計者の判断

1. **Important**: 環境の読み取りで、Context の終了の期限切れが記録されず、Run が `COMPLETE` になる（`environment.ts:165`）。
   - → **直す**（P18e）。閉じる処理の期限切れを、Run の理由（`UNHANDLED_FAILURE`、`environment-context-close:…` など）にする。`COMPLETE` にならないことを、テストで固定する。
   - 補足の問い（作成の期限切れの場合も、Run は `COMPLETE` になる）→ **今のまま（4.4 の表のとおり）とする。**
     - 環境の事実（User-Agent）は、監査の必須の部分ではない。作成の期限切れでは、User-Agent を未観測にするだけで、今の作成の失敗と同じである。
     - 一方、閉じる処理の期限切れでは、Context が閉じたことを確かめられていない。これは後始末の未完了なので、`COMPLETE` にしない。
     - この区別を、設計書 4.2 に書いた。
2. **Minor**: Run 全体のテストがない。Run Coordinator に、期限を注入する口もない（`run-coordinator.ts:93`）。
   - → **直す**（P18e）。`deadlines` を、Run Coordinator から下へ渡せるようにする。終わらない偽の Browser で、Run が期限の中で確定することのテストを、1件以上加える。
3. **Minor**: 幅の走査で、`getSafetyLedger` が投げた場合に、Context を閉じずに投げる（`stress-session.ts:89`）。
   - → **直す**（P18e）。ほかの呼び出し元と同じく、閉じてから投げる。
4. **Minor**: 凍結の期限のテストが、実際の閉じる処理の合流を再現していない（`isolated-interaction.test.ts:8046`）。
   - → **Task 18 の Safety の Gate（T18b）で、本物の Guard を使って確かめる。**
5. **Minor（推測）**: 遅れて届いた Context の違反が、ページの Safety の集計に入らない。
   - → **受け入れる。**
     - Run の集計は、Ledger の登録から行うので、遅れて届いた Context の違反も入る。Run Status の判定は保たれる。
     - Run とページの違反の件数が食い違うことがある。このことを、設計書 4.2 に書いた。
