# RDEF4 DEF-004（Guard の変更）の独立レビューの結果（2026-09-24）

総合判定: 承認（Critical 0 / Important 0 / Minor 2）

## 確かめられた点

- 違反から外す新しい条件は、既存の `ALLOW && isNavigationRequest && isMainFrame` のブロックの中にある。
  - GET 以外は BLOCK になるので、この経路に入らない。
  - 1274行目の違反と、`ERR_ABORTED` の例外は、変わっていない。
- Guard 自身が中断する経路は、すべて `ERR_BLOCKED_BY_CLIENT` である。
  - route の中断が6か所、`Fetch.failRequest` が6か所、予期した失敗の登録が固定されている。
  - そのため、Guard の中断が、一覧のコードに化ける経路はない。
- 一覧の14のコードは、どれも接続、名前解決、TLS の層の失敗である。接頭辞は、完全一致で照合している。
- 書き換えた9件のテストは、どれも条件を弱めていない。3785行目のテストは、条件が強くなった。

## Minor と、設計者の判断

1. 違反から外す条件に、Guard の状態の確認がない。そのため、Interaction の凍結中も、違反から外れる。
   - 判断: DEF-004b で直す。違反から外すのは、凍結中でない場合（`!isFrozenPhase(guardState.phase)`）に限る。
     - 凍結中は、これまでどおり違反とする（fail-closed）。
     - 閉じている途中と、無効化の途中は、違反から外す。どちらも、許可した GET のネットワークの失敗は、Guard の不具合ではないためである。
     - Interaction の隔離した Context での最初の読み込みは、凍結の前に行われるので、違反から外れる。
2. 一覧にないネットワークの層の失敗がある。例えば、HTTP/2 と QUIC のプロトコルのエラー、proxy、途中で切れた応答である。
   - 判断: fail-closed の扱いのまま、変えない。観察の対象として、不具合台帳の DEF-004 に記録した。実際のサイトで起きた場合に、一覧を広げるかを判断する。
