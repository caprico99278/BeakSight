# BeakSight API の登録の本文の一覧の形の値（DEF-226）設計書

- 日付: 2026-11-08
- 状態: ユーザー承認済み（2026-11-08。方向は下の 2）
- 関係する文書: `2026-10-17-beaksight-task-38-api-scenario-approval-design.md`（T38R-fix の I-2）、`2026-10-17-beaksight-task-39-api-write-guard-design.md`、`2026-10-17-beaksight-task-40-api-create-design.md`、`2026-10-18-beaksight-task-41-api-update-design.md`、`2026-11-08-beaksight-same-origin-api-and-spa-routes-design.md`
- 調査: INV-ARRAY（2026-11-08。127.0.0.1 の仮のサイトで、2 つの Chromium で再現）。

## 1. 目的

ユーザーの localhost の管理画面の新規登録の画面は、保存のときに JSON の本文に一覧の形の値（array）を 3 つ含める。今は、ページが決める鍵を scalar に限る規則（`SCENARIO_API_PAGE_KEY_NOT_SCALAR`。T38R-fix の I-2）で、画面の一覧に「この画面の入力のしかたを扱えないため、試せません。」と出る。調査で次が分かった。

- 型の記録は array の鍵に `type: 'array'` しか持たない。要素の型・数・印は残らない（`src/core/api-request-shape.ts:216-219`、`:609`）。
- 文字の欄の値が一覧に入る形（例: 札の欄の文字が `labels: ["<値>"]`）では、印が一覧の中にあっても記録されず、欄が鍵に対応づかない。
- 書き込みの段は、期待の確かめ（`EXPECTATION_INVALID`）と本文の読み取り（`BODY_VALUE_NOT_SCALAR`）の 2 か所で止まる（届いた数 0）。

## 2. ユーザーの判断（言葉どおり）

- 「一覧の値も扱えるよう広げる」（2026-11-08）。

## 3. 採用する設計（調査の案 C）

### 3.1 受ける一覧の形

1. 入れ子のない scalar の一覧だけを受ける。要素は文字・数・真偽・null。要素が object・array のものは今のまま拒む（理由を分ける: 入れ子 `SCENARIO_API_ARRAY_NESTED` など。名前は実装で決め、理由の一覧・schema・表示のカタログに登録する）。
2. 要素の数と、要素の文字の長さに上限を置く（定数は 1 か所。目安: 要素 20、文字 200）。上限を超える形は拒む。
3. 範囲は登録（CREATE）だけ。更新（UPDATE）の一覧の鍵は、前の値を画面から読めないので、今のまま拒む（限界として表示の理由は今のまま「入力のしかたを扱えない」）。

### 3.2 型の記録（操作さがし）

1. array の鍵に、要素の型の集合、要素の数、入れ子の有無を任意の項目として足す。値は残さない（I22 のまま）。
2. 要素の文字に印が含まれたら、その鍵を印の鍵の一覧に入れ、一覧の中で見つかった印だと分かる印を付ける。
3. 型の digest に要素の情報を入れる。一覧の鍵のない型の digest は今と同じ値にする（今の承認を無効にしない）。一覧の鍵のある型は digest が変わるので、操作さがしをやり直すと新しい型になる。古い発見の結果は要素の情報を持たないので、今のまま拒む。

### 3.3 鍵と欄の対応と承認

1. 印が一覧の中に入った欄は、欄の鍵（型 array）として対応づける。文字の欄 × 文字の一覧の組を、欄の型と JSON の型の対応（`SCENARIO_API_FIELD_JSON_TYPES`）に足す。
2. 欄に対応しない一覧の鍵は、ページが決める鍵として受ける。名前が秘密に見えない・状態の語でないことを今のとおり求める。要素の型の集合と数を承認の内容に入れる（承認の digest の計算に入れる。一覧のないシナリオの digest は変えない）。

### 3.4 書き込みの段の照合（送る前）

1. 欄に対応づけた一覧の鍵: 本文の値が `[生成した値]` と完全に一致することを求める。
2. ページが決める一覧の鍵: 入れ子がない、要素が scalar、要素の型の集合と数が承認と同じ、文字の長さが上限の中。違えば送らない。
3. 承認していない一覧の鍵、入れ子は今のまま止める。
4. 結果の記録に、一覧の値を文字の形で上限つきで残す（人が見る。値を照らさない鍵の中身を隠さない）。

## 4. 変えないもの

- 安全の守り（DELETE・PUT・upsert・論理削除・手続きの呼び出しの拒否、危険な語・資格情報・承認の外の Origin、1 回だけの送信、送る前の照合）。
- 承認の流れ（画面の一覧でチェックした画面だけ）。
- 更新の一覧の鍵の扱い。
- 欄の入力のしかた（文字の欄に文字を 1 つ入れる）。

## 5. サイトへの負荷

- 要求の数・読み込みの回数は変わらない（照合の規則が広がるだけ）。

## 6. 限界（安全のレビューで確かめる残る経路）

1. ページが決める一覧の要素の値そのもの（例: 権利を持つ人として入れた ID）は照らさない。今の scalar のページが決める鍵と同じ扱い。数と型を固定し、値を記録に残す。
2. 「追加」を押して一覧に入れる形（チップの形）の欄は試されない。その鍵は空の一覧のページが決める鍵として通る。
3. 要素の数がページの状態で変わるサイトは、送らずに止まる（安全の側）。
4. 古い発見の結果は、操作さがしをやり直すまで今のまま拒む。

## 7. テスト

- 仮のサイト（一般の文言）: 新規登録のフォーム、保存で JSON を POST、本文に scalar の鍵と一覧の鍵（空の一覧、選択肢から入る一覧、文字の欄から入る一覧）。
  - 操作さがしで型に要素の情報と一覧の中の印が記録され、下書きが通り、承認して書き込みの段で POST が 1 回届く（サーバの記録）。
  - 照合で止まる形: 入れ子、要素の型の違い、数の違い、上限の超過、欄の一覧が `[生成した値]` でない、承認していない一覧の鍵。届いた数 0。
  - 一覧の鍵のない型の digest と、一覧のないシナリオの承認の digest が変わらない。
  - UPDATE の一覧の鍵は今のまま拒む。
- 2 つの Chromium。既存の API の承認・書き込みのテストが通る。

## 8. 実装の分け方

1. **ARR-1:** 3.2 と 3.3 の 1（型の記録・digest・鍵と欄の対応）。
2. **ARR-2:** 3.3 の 2 と 3.4（承認・書き込みの照合・記録・表示の理由）。
3. **安全のレビュー SREV-ARR。**
4. ユーザーが localhost の管理画面で確かめる。
