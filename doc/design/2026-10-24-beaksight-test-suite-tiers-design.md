# 設計書 — テストの組を分け、実行時間と揺らぎを減らす

状態: ユーザーの指示と判断（2026-10-24）による。実装の前。
作成: 2026-10-24（設計者）

## 1. 経緯

ユーザーの指示（2026-10-24）は「テストの肥大化とテスト実行時間の増大への対処」です。実環境の確かめの前に行います。

測りは `.superpowers/sdd/2026-08-27-beaksight-implementation-plan/PRE42-test-metrics-brief.md` の報告によります。元の出力は scratchpad の `pre42-test\` にあります。

- 全体で約 58 分かかります。
  - ルート（単体・component・architecture・結合）: 1,830 秒。596 ファイル・16,679 件、15 並列。
  - 画面: 1,620 秒。75 ファイル・642 件、直列。
- 時間の 98% は結合です。上位は次の 3 ファイルです。
  - `stage-chain-fork` 1,121 秒
  - `stale-lock-takeover-processes` 1,118 秒（20 回 × 2）
  - `read-check-run` 830 秒
- 最後に `isolated-interaction`（414 秒）が 1 ファイルだけで走る部分が、約 7 分あります。
- CLI の Chromium の 2 回目（安全の 31 ファイル）は、約 12〜19 分の見込みです。
  - そのうち 22 ファイルは、1 回目の中で、既定と CLI の両方をもう流しています。
  - `stage-chain-fork` は、環境変数を読みません。
  - 2 回目で新しく確かめる分が大きいのは、5 ファイルだけです（`safety-gates`・`context-factory`・`gate-fixtures`・`passive-request-guard`・`beaksight-block-relation`）。
- 揺らぎの共通の原因は 5 つあります。
  - 15 並列の混雑（1.5〜1.7 倍）
  - 壁時計の時間の検査（約 60 ファイル）
  - 壁時計の決まった待ちで「起きた・起きない」を判定する場面
  - 既定の 30 秒の期限
  - Guard の作業の上限

ユーザーの判断（2026-10-24）は、次の 3 つです。

- 組を分ける（推奨）
- 回数を重ねる安全のテストは、ふだんは減らす（推奨）
- 画面のテストを並列で流せるか試す（推奨）

## 2. 守ること

- 安全の確かめの強さを、全部の組で落としません。
  - ふだんの組で弱めるのは、回数を重ねるテストの回数だけです。
  - 全部の組では、今の回数のままにします。
- テストを消しません。重なった対照のテストは、1 か所にまとめて残します。
- 依存を足しません（Vitest の今の機能の内で行う）。
- 組の一覧は、1 か所に置きます。どのファイルがどの組かを、scripts やほかの場所に書き写しません。

## 3. 設計

### 3.1 組（TS-a）

| 組 | 中身 | 流す時 |
| --- | --- | --- |
| `test:fast` | unit・component・architecture | いつも（実装者と設計者） |
| `test:safety` | 安全の一覧のファイル（今の `bn-verify.sh` の 31 ファイルとブラウザ自身の通信の検査）を既定の回で流す。続けて、CLI の回の一覧（新しく確かめる 5 ファイル）を `BEAKSIGHT_TEST_DEFAULT_CHROMIUM=cli` で流す | 安全に関わる変更のとき |
| `test:integration` | 結合のうち、重い組でないもの | 変えた所に関係するものを、ファイルを指定して流す |
| `test:heavy` | 結合のうち、重い組（目安: 混雑の下で 60 秒以上。一覧は 1 か所） | 全部の組で |
| `test:ui` | 画面のテスト（3.5 で並列を試す） | 全部の組で。画面を変えたときは関係するファイルだけ |
| `test:full` | `test:fast`・結合の全部・`test:safety`・`test:ui`。回数は全部の回数 | Task の区切り（承認の後の 1 回） |

- 組の一覧（安全の一覧、CLI の回の一覧、重い組の一覧）は、`tests/suites.ts` などの 1 つのファイルに置きます。Vitest の設定と scripts は、そこから読みます。
- `verify` と `verify:all` は、全部の組（`test:full` と build と typecheck）を指します。今の意味を保ちます。
- unit 系と integration は、Vitest の projects で分けます。integration の並列の数を下げ（例: 6〜8）、単体の時間の検査と、ブラウザを使う結合が CPU を取り合わないようにします。値は、測ってから決めます。
- 実装者の指示書と、設計者の確かめの手順は、この組を使う形に改めます。設計者の記憶にも残します。

### 3.2 回数（TS-b）

- 回数を重ねるテストの回数を、名前つきの値の 1 か所に置きます。
  - 対象: `stale-lock-takeover-processes`、`guard-popup-close-race`、`isolated-interaction` の `FROZEN_*_ROUNDS`、`safety-gates` と `gate-harness` の回数、`control-profile-processes` など。
  - ふだんの組の値と、全部の組の値を持ちます。全部の組の値は、今の回数です。
- どちらの値を使うかは、1 つの環境変数で決めます（例: `BEAKSIGHT_TEST_TIER=full`）。既定はふだんの組です。
- ふだんの組の値は、1 以上で、競合の場面を少なくとも 1 回は通る数にします（例: 20 → 3、40 → 5）。
- 止める経路が働いた証拠の確かめ（記録が残る回が 1 回以上）は、ふだんの組でも残します。

### 3.3 並び（TS-c）

- `isolated-interaction`（466 件）を、describe の単位で 3〜4 ファイルに分けます。
- `stage-chain-fork` を、Chromium ごとに 2 ファイルに分けます。
- `page-navigation-limit` の落ち着きの期限を、名前つきの値でテストから注入できるようにします。期限そのものの確かめは、別のテストに残します。
- 分けた後も、件数とテストの名前が保たれることを確かめます。

### 3.4 時間の検査（TS-d）

- 純粋な計算の速さの要件（architecture の 1 秒の上限 8 ファイル、単体の上限）は、壁時計ではなく CPU の時間（`process.cpuUsage` か `threadCpuUsage`）で測ります。測りの始まりは、検査の本体の直前にします（DEF-153）。
- 結合の「期限の内に返る」の確かめは、注入した時計か、名前つきの混雑の倍率（`cli-site-unavailable` の `LOADED_DEADLINE_FACTOR` の形）にします。
- 約 60 ファイルのうち、先に architecture の 8 ファイルと単体の上限を行います。結合は、揺らぎの記録（DEF の台帳）があるものから行います。

### 3.5 画面のテストの並列（TS-e）

- 直列にしている理由を確かめます（`apps/local-ui/vitest.config.ts` の `fileParallelism: false`）。
- 共有しているもの（リポジトリの `node_modules/.vite` の様子の検査、process の残りの検査、一時の root、port）を、ファイルごとに分けられるかを確かめます。
- 分けられれば、2〜3 並列にします。揺らぎが増えるなら、直列に戻し、理由を設定のコメントに書きます。

### 3.6 対照のテストのまとめ（TS-f）

- `gate-fixtures` の守りのない対照と、`safety-gates` の「control: without the Guard」の重なりを、1 か所にまとめます（同じ fixture・同じ確かめ）。
- 守りのない対照は、CLI の回の一覧に入れません（DEF-126 の 24 件が出なくなる）。
  - ブラウザ自身の要求（favicon など）を除く補助は、`tests/helpers/chromium.ts` の今の補助を使います。

#### 3.7.1 管理データを版 17 で直接作る（LG-2）

- 基準の版 17 の文を 1 つのモジュール（例: `src/control/store/control-schema-v17.ts`）に置く。中身は、今の版 1→17 で作った DB の `sqlite_schema.sql` をそのまま写した凍結の文にする（列の順と引用符が利用者の DB と一致するため）。
- 走らせる側:
  - 版 0 で表がない: 基準の文と seed を 1 つのトランザクションで流し、`application_id` と `user_version = 17` を書く。
  - 版 0 で表がある: 今のまま `NOT_A_BEAKSIGHT_DATABASE`。
  - 版 1〜16: 新しい閉じた理由 `DATABASE_FROM_OLDER_VERSION` で、何も書かないうちに止める（WAL にもしない）。利用者のファイルは変えない。
  - 版 17〜最新: 版 18 から後の段だけを流す（今は該当なし）。
  - より新しい版: 今のまま `DATABASE_FROM_NEWER_VERSION`。
- 版 18 から後の口（1 版 1 トランザクション、中での版の読み直し、失敗で戻す、公開した版の文を写しで固定する決まり）は残す。
- 捨てる: 版 1〜16 の文、写しの定数 `VERSION_<N>_…`、作り直しの列の定数、版 13〜17 の列の確かめ、テストのためだけの export、前の版の DB を作る補助と、前の版に関わるテスト。
- 足すテスト: 新しく作った DB と、写し取った fixture の形が同じこと（`pragma_table_info` の列の順、索引、外部キー）。fixture は、古い段を消す前に、今の版 1→17 で作った DB から写し取る。版 1〜16 の DB で止まり何も書かないこと。基準の文の SHA の固定。今の名前つきの一覧が基準の CHECK の値と等しいこと。
- `ControlStoreStatus.createdSchemaVersion`・`createdAt` は残す（診断用。費用がない）。

#### 3.7.4 意味の重なるテスト（TS-f を広げる）

## 5. 受け入れ条件

1. `test:fast` が、混雑のない状態で 3 分以内に終わる。
2. `test:full` の件数とテストの名前が、組み直しの前と同じ（分けたファイルを含む）。ただし、3.7 で捨てる・まとめるテストは、消したテストの名前と、その確かめを含む残す側のテストの名前を一覧にして報告する（一覧にないテストが消えていない）。
3. 全部の組の回数が、今の回数と同じ。
4. CLI の回が、新しく確かめる 5 ファイルだけを流し、DEF-126 の 24 件が出ない。
5. 時間の検査を直したファイルで、混雑の下の揺らぎが出ない（測りの 1 回で確かめる）。
6. 全体の時間（`test:full`）を測り、組み直しの前の 58 分と比べて報告する。
