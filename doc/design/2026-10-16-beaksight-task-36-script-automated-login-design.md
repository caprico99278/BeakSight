## 1. 目的

スクリプトが別のホストの認証のサービスへ token を取りに行くログインで、**自動ログイン**（BeakSight が保存した資格情報を入れて送信を押す）を使えるようにする。手動のログイン（Task 34）と同じ Guard の決まりに、自動ログインだけの守り（資格情報が登録の外の送信に乗らないこと、応答の状態での結果の区分）を足す。

## 2. 前提

- 今の自動ログイン（Task 26）は、form の送信（main frame のページの移動の POST）と文書の応答を前提にしている（入力の確かめ `login-form-submitter.ts`、送信の観測、結果の区分 `statusOutcome`・`observeDocuments`）。上限（同じプロファイルで 5 分以上あける、24 時間に 10 回）、止める決まり（成功でない終わり方の後は人が解くまで止める）、資格情報の扱い（DPAPI、平文を持つ時間）は変えない。
- Task 34 の T34R-fix-b（M-3）で、自動ログインのプロファイルの `SCRIPT_REQUEST` を検証で拒んでいる。Task 36 で外す。
- 自動ログインの `maxLoginAttempts` は 1 に固定（今のまま）。

## 3. 設計

### 3.1 検証と契約

- 自動ログインのプロファイルでも `SCRIPT_REQUEST` を受ける（`AUTH_SETUP_SCRIPT_LOGIN_AUTOMATED_NOT_SUPPORTED` を外す。理由コードは一覧に残すかを、使われなくなった閉じた一覧の扱いの前例に合わせて決める）。
- 自動ログインの 3 つのセレクタ（ユーザー名、パスワード、送信のボタン）は今どおり標準の CSS だけ。

### 3.2 入力の前の確かめ（`login-form-submitter.ts`）

- `SCRIPT_REQUEST` では、form の `action` と `method` を確かめない（スクリプトが送るため）。3 つの要素がちょうど 1 つずつあること、見えること、同じ form の中にあること、パスワードの欄の種類、などは今どおり確かめる。
- ~~設計者の既定: form の要素がない画面は止める~~ → **ユーザーの判断（2026-10-16「ログインの画面に form の要素がなければ止めるのでは監査が開始できない。」）により変更**: `SCRIPT_REQUEST` では、form の要素がない画面でも入力して押す。決まりは次のとおり。
  - 3 つの要素（ユーザー名、パスワード、送信のボタン）は、今どおり、それぞれちょうど 1 つ、見える、編集できる（押せる）、main frame の文書の中、パスワードの欄の種類。
  - 3 つとも form の外にあるか、3 つとも同じ form の中にあること。一部だけが form の中にある、別々の form にある、は止める（今の `NOT_SAME_FORM`）。
  - 送信のボタンは、`button`・`input[type=submit|button]`・`role=button` の要素。`href` を持つ `a` は止める（ページの移動を起こすため）。
  - `FORM_NAVIGATION` の確かめは変えない（form が要る）。
  - 押した後の送信は、Guard の決まり（token の送信 1 回と登録した送信だけ）と資格情報の守りが受け持つ（form のある画面と同じ）。

### 3.3 Guard: 資格情報が登録の外の送信に乗らないこと（自動ログインだけ）

- 自動ログインのログインの段で、Guard が通す読み取りでない送信のうち、token の送信のほか（登録したログインに伴う送信）について、要求の本文（`postData`）と URL に、入れた資格情報（ユーザー名、パスワード）の値が含まれていれば止めて記録する（理由を新しく足す）。値の比べは、そのまま、URL の符号化、JSON の文字列の符号化の 3 つの形で行う（ほかの形は限界として文書に書く）。
- 値は Guard の中だけで持ち、記録・IPC・管理データには値も長さも残さない。比べの部品は `src/safety/` の 1 か所。
- token の送信そのもの（承認した送信先）は、資格情報を運ぶのが目的なので比べない。

### 3.4 送信の観測と結果の区分

- token の送信を Guard が通したら、その要求の応答の**状態だけ**を CDP の Network の出来事で読む（本文は読まない。成功の応答の本文は token を含む）。`Retry-After` のヘッダは今の部品で読む。
- 区分（**設計者の既定（ユーザーの確認待ち）**）: 2xx の後は今の成功の確かめ（成功の画面、成功の鍵の名前、token を 1 回以上通した）で `SUCCESS` か `UNKNOWN_RESULT`、400 と 401 は `INVALID_CREDENTIALS`（止める）、429 は `RATE_LIMITED`（`Retry-After` を守る）、423 はアカウントのロック、5xx と応答なし（送ったかが分からない）は `UNKNOWN_RESULT`（止める）。form の送信の自動ログインの区分の表と同じ名前を使う。
- token の送信を通さないまま時間が来たら、今どおり（送っていない区分）。

### 3.5 そのほか

- 監査の段（Task 35）は、手動のログインと同じものを使う。
- 画面: 自動ログインのプロファイルでも「ログインの送り方」を選べるようにする（T34d で固定していた所）。
- 文書: `automated-login.md` のスクリプトの送信の節、結果の区分の表、限界。

## 4. 安全

- 新しく通す送信はない（Task 34 の決まりと同じ）。足すのは、自動ログインのときに登録の送信への資格情報の持ち出しを止める守りと、応答の状態の観測（本文は読まない）。
- 資格情報の値は、Guard と入力の部品の中だけで持ち、平文を持つ時間を今より延ばさない。目印の検査で確かめる。

## 5. 受け入れ条件（G36）

1. fixture（`startSpaAuthSite`）で、本物のワーカーのスクリプトの自動ログインが、ログインの確かめと監査で通る（両方の Chromium）。届いた読み取りでない要求は token の送信 1 回と登録した送信だけ。
2. 誤ったパスワード（400）で `INVALID_CREDENTIALS` と自動ログインの停止、429 で `RATE_LIMITED` と `Retry-After`、5xx と応答なしで `UNKNOWN_RESULT` と停止。上限（5 分、24 時間に 10 回）は今どおり。
3. 登録したログインに伴う送信に、ページの JS が資格情報を入れると止まる（3 つの形。届かない）。
4. 資格情報の目印が、管理データ（WAL を含む）、IPC、ワーカーの出力、成果物、画面に出ない。
5. 回帰: form の送信の自動ログイン（`automated-login*`、`audit-worker-automated-login-fork`、`credential-*`）、手動のスクリプトのログイン（Task 34）、監査の段（Task 35）。
6. 独立レビュー（Critical 0、Important 0）と `verify:all` を 1 回。
