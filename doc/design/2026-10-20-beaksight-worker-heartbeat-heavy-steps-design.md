# 設計書 — 長い Run の重い処理で、ワーカーの知らせが途絶えて止められる（DEF-143）

状態: 設計者の判断（実テスト環境の結果による）。調査と実装。
作成: 2026-10-20（設計者）

## 1. 経緯（実テスト環境の事実）

管理画面の全ページの監査（ページの上限 150、時間の上限 3 時間、読み込みの間隔 10 秒）で、次のことが起きた。

- 1 回目: 76 ページで利用者が止めた。止める処理の間に知らせ（`HEARTBEAT`）が途絶え、`WORKER_UNRESPONSIVE` で終わった。
- 2 回目（1 回目の続きから再開）: 139 ページの監査を終えた。その直後（139 ページ目の保存の約 20 秒後）に `WORKER_UNRESPONSIVE` で止められた。残りは 1 ページ。
- 3 回目（もう一度再開）: 始めてから 1 秒後に最後の知らせがあり、20 秒後に `WORKER_UNRESPONSIVE` で止められた。どのページも読んでいない。

数字の手がかり:

- ページの保存（`checkpoint/pages/`）は 139 ファイル、合計 168 MB（1 ファイル最大 1.7 MB）。
- 1 ページあたりの時間は、最初から最後まで 53〜56 秒でほぼ一定。ページごとの処理が伸びているのではない。
- 知らせの間隔は 2 秒、途絶えの上限は 20 秒（`AUDIT_JOB_HEARTBEAT_TIMEOUT_MS`）。

見立て（確かめが要る）: 再開のときのページの保存の読み込み（168 MB の JSON の解析と schema の確かめ）や、Run の終わりの集計（全ページの読み直し、報告、バンドル）が、ワーカーの main thread を 20 秒以上占める。その間は知らせを送れず、親が止める。2 回目は、76 ページ分の読み込みが 20 秒の内に収まったので再開できた。

## 2. 設計

- **調査を先に行う**（実装者）: fixture で、139〜150 ページ分の大きなページの保存を作る（1 ファイル 1〜2 MB）。次の 3 つの段で、main thread を占める最も長い時間を測る。
  - 再開の読み込み
  - 1 ページの後の保存
  - Run の終わりの集計・報告・バンドル
  
  20 秒を超える段と、その中の処理を特定する。2 回目の「139 ページの後」に当たる段も特定する。
- **直し**: 特定した重い処理を、ページの単位で区切って event loop に戻す（`await` で間を空ける）。どの段でも、知らせが途絶えないようにする（目安: main thread を 1 回に占めるのは 2 秒未満）。
  - 処理の中身と結果は変えない。
  - 同期の読み書き（`readFileSync` などの大きな塊）は、非同期にするか区切る。
- **途絶えの上限は今のまま**（20 秒）。本当に止まったワーカーを見つける守りなので、緩めない。区切っても足りない段がある場合だけ、その段の間だけ親に段を知らせて上限を延ばす案を、止まって設計者に諮る。
- **止める処理**: 利用者が止めたときも、片付けの重い処理の間に知らせが途絶えないようにする（1 回目）。

## 3. 受け入れ条件

1. fixture の大きな Run（150 ページ分、合計 150 MB 以上のページの保存）で、再開・1 ページの後の保存・Run の終わりのどの段でも、main thread を占める最も長い時間が 2 秒未満になる（測った値を報告する）。直す前は 20 秒を超えるか、それに近いこと（RED）。
2. 本物のワーカーの fork で、大きな保存からの再開が `WORKER_UNRESPONSIVE` にならず、最後まで終わる（headless）。
3. 成果物（`run.json`・`audit.json`・報告・バンドル）が、直す前と同じ中身になる（今の golden や比べのテスト）。
