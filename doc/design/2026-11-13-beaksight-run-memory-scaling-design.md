# 大きな Run でワーカーのメモリを抑える設計（DEF-266）

- 日付: 2026-11-13
- 状態: 設計者の案。ユーザーの「進めて」（2026-11-13）を受け、ロードマップの中の不具合の修正として進める。成果物の形を変える段（4 章）は、着手の前にユーザーに諮る。
- 上位の文書との関係: `2026-11-09-beaksight-remove-limits-design.md`（上限を外す設計）の後始末です。ページ数の上限を外したので、Run の大きさに比例してメモリを使う所を、ページごとに流す形に替えます。成果物（page.json・audit.json・report.html・バンドル）のバイト列は、1〜3 章の段では変えません。

## 1. 背景と問題
- 149 ページ・約 450MB の保存から再開すると、ワーカーが約 20 秒で 2GB を超えた（FINAL-RUN と INV-FINAL の e264）。
- 調べ（INV-266）で分かったこと:
  - 新しい Run でも再開でも、全ページの `PageAuditResult` を Run の終わりまでメモリに持つ（`run-coordinator.ts` の `results`）。
  - 成果物の書き出し（`ArtifactWriter.writeRun`）は、全体を `structuredClone` で写し、伏せ字の処理でさらに 2〜3 回写す。最大で全体の約 3 倍を同時に持つ。2GB を超えた主な所とみられる。
  - `audit.json` を 1 つの文字列にして書くので、1 ページ 3MB なら約 170 ページで、Node の文字列の長さの上限（約 5.4 億字）に当たり `RangeError` になる見込み。
  - バンドルは、全ファイルを読んで、全部の部の ZIP を作ってから書く。
  - 画面のサーバは `audit.json` を 256MB までしか読まない（`apps/local-ui/src/server/artifact-files.ts:407`）。超えると、ページのファイルを画面から渡せなくなる見込み。
- 1 ページの記録が大きい（簡単な表のページで 3MB・指摘 682 件）ことも、合わせて効いている（4 章）。

## 2. 方針
- **件数・大きさの上限は足さない。** サイトの構造に合わせて、どれだけ大きくても終われる形にする（ユーザーの方針「BeakSight 内で上限を定めないで」）。
- **ページごとに読んで、処理して、捨てる。** Run 全体で持つのは、ページ数に比例しても小さいもの（要約・索引・照らす表）だけにする。
- **成果物のバイト列と digest は変えない**（1〜3 章の段）。前の記録・保存はそのまま読める。
- **秘密をディスクに出さない。** 生の値（伏せ字の前）を一時のファイルに書かない。
- **安全の判定・伏せ字の結果を変えない。** 伏せ字の照らす表は、今と同じく Run 全体から作る。

## 3. 段の分け方
### MEM-1: 書き出しを流す形にする（案 A＋B）
- `writeRun` の `structuredClone` を外す（入力は凍結済みで、`#outgoing` は新しい木を返す）。
- 伏せ字（`src/safety/redact.ts`）を 2 つの段に分ける。
  - 1 回目: 全ページを順に見て、Run 全体の照らす表を作る（今の `matchTableOf` と同じ中身）。
  - 2 回目: ページごとに、表で置き換えて、確かめて、書く。
- `audit.json` は、先頭の部分、ページごとの JSON（`,` で区切る）、最後の部分を、順にファイルへ書き足す。バイト列は今と同じにする。schema の確かめは、run・各ページ・findings に分けて行い、誤りの path（`/pages/i/...`）を今と同じにする。
- run.json の確かめは 1 回にする。参照のファイルがあるかの確かめ（`artifact-references.ts:227-236`）は、読むのをやめて stat にする。
- 受け入れ条件:
  - 今の成果物のテストが、バイト列ごと同じまま通る。
  - 伏せ字の秘密の目印のテスト（T44R など）が通る。
  - 大きな Run を合成した単体か結合で、`audit.json` が文字列の上限を超える大きさでも書ける。
  - 書き出しで同時に持つのは、ページ 1 つ分と表だけ。

### MEM-2: バンドルを部ごとに作る（案 D）
- 部の割り当ては、ファイルの大きさ（stat）で決める。manifest の sha256 は、先に少しずつ読んで計算する。
- 部ごとに読んで、`zipSync` で作って、書いて、捨てる。fflate の流す形の `Zip` は使わない（data descriptor が付いてバイト列が変わるため）。
- 受け入れ条件: ZIP のバイト列と manifest が今と同じ。

### MEM-3: ページの結果を圧縮して持つ（案 C1）と、Run の終わりの集計をページごとに足す（案 E）
- `results` には要約だけを生で持つ。要約は、状態・理由・finalUrl・構造の鍵・数え上げ・Cross-page の索引の項目・findings。本体は JSON を `node:zlib` で圧縮してメモリに持ち、使うときに 1 ページずつ戻す。
- 再開のとき（`readCheckpoint`）は、保存のページを 1 ページずつ確かめて、要約と圧縮した本体を返す。
- Run の終わりの集計（Safety・数え上げ・Cross-page の索引・止めた理由）は、ページごとに足し込む。
- 保存のページそのものを置き場所にする案（C2）は、成果物が変わりうるので採らない。C1 で足りないことが測って分かったら、改めて諮る。

### MEM-4: 表示用モデルと HTML（案 F）、画面のサーバ
- 表示用モデルの索引をページごとに積む。HTML はファイルへ少しずつ書く。
- 画面のサーバ（`artifact-files.ts`）は、`audit.json` を丸ごと読まず、ページのファイルから参照を集める。256MB の読み込みの上限もなくす。

## 4. 1 ページの記録の大きさ（ユーザーに諮る段）
- 簡単な表のページで 3MB の内訳は、layout 50%、accessibility 17%、指摘 15% など。確かめ直し（AUD-2e）で、layout と accessibility を 2 回分持つ。
- 案:
  - 同じ構造の繰り返しは、構造ごとに 1 件だけ書き、違う値だけを全部書く。
  - 重なりは、要素の表を 1 つ持って番号で指す。
  - 確かめ直しは、1 回目との違いだけを書く。
  - `audit.json` は全ページの写しを持たず、目録にする。
- どれも成果物の形と schema の版が変わる。前の版も読めるようにする（LG-4）。MEM-1〜3 の後に、測った結果と合わせて、ユーザーに諮る。
- 重なりの指摘 378 件が、多く見つけすぎかどうかも、同じ時に調べる。

## 5. 速さと負荷
- サイトへの要求は変わらない（書き出しとメモリの持ち方だけの変更）。
- 圧縮と 2 回の読みで CPU は増える。Run の終わりの心拍（DEF-143）を止めないよう、ページごとに event loop を返す。

## 6. 受け入れの測り方
- `tests/integration/worker-finalizing-heartbeat-fork.test.ts` の 150MB 以上の保存から再開する場面で、ワーカーの node の最大を記録する。MEM-1〜3 の後に、同じ場面を約 450MB（今の雛形の大きさ）でも一度だけ測り、報告に書く。テストの既定の大きさは 150MB 以上のまま。
- テストで本番の長さを待たない。大きな Run は合成した記録で作り、ブラウザで 149 ページを監査し直さない。
