# 入力を極限まで減らす画面の作り直し（MI）— 設計書と実装計画

状態: ユーザーの承認済み（2026-10-26「進めて」）
関係: Task 42（実テスト環境の確かめ）を段 C の前で止めて行う。不具合 DEF-175。

## 1. 目的

利用者が画面で入れる・選ぶ・押すものを、極限まで減らします。

- 利用者が入れるのは、利用者が知っている値（開始の URL、テスト用のアカウント）だけにする。
- BeakSight が観察で分かる値（入口の確かめ、手動のログインの観察、設定のファイル、発見、台帳）は、BeakSight が埋める。利用者には見せず、「詳しい設定」を開いたときだけ見せて直せるようにする。
- 決まった値でよいもの（回数の上限、間隔、期限）は、既定のまま隠す。
- 安全のために人が決めることは、1 回の押下（確認のダイアログ）にまとめる。

見積もり（UX-0 の調査）: Task 42 の流れ（プロファイルの作成 → 手動のログイン → 自動ログイン → 監査 → 発見 → API の登録 1 件 → 更新 1 件）の入力・選択・押下は、約 100＋N_p（N_p はページが決める鍵の数）から約 33 になる。

## 2. 背景

- 2026-10-26、Task 42 で、利用者は自動ログインのプロファイルを別に作ろうとして止まった。「承認したサービスの Origin」（token の送信先の Origin）は通信を見なければ分からないのに、手で入れさせた。認証の設定の画面は、利用者が知りえない欄（token の送信先のパス、必須の query、ログインに伴う送信、成功のローカル ストレージの鍵）ばかりだった。
- ユーザーの言葉: 「事前にユーザーが知りえない情報を入力させようとするのは NG」「無駄な UI が多すぎる。不便過ぎて使えない」「入力項目は極限まで減らして。ほとんどいらない」。
- 調査（UX-0）で分かったこと:
  - 同じプロファイルで手動のログインから自動ログインへ切り替える操作（FM2e。`setUpAutomatedLogin`）は、すでにある。認証の設定と承認したサービスの Origin を引き継ぎ、利用者が入れるのは資格情報だけ。手順書（`real-test-environment.md` の 3 章・6.1・10.1）が、別のプロファイルを作って同じ値を手で写す形に書いていた。
  - 読み取りと書き込みでプロファイルを分けているのは、操作の表（`PROFILE_OPERATION_POLICY`）が書き込みのモードの `AUDIT` を許していないためで、安全の理由は設計書に書かれていない。ワーカー（`src/worker`、`src/orchestration`、`src/safety`、`src/browser`）は監査モードを見ていない（送信の扱いはジョブの種類で決まる）。
  - 守りの穴: 表の 1 行の「登録する」（`login-stage-registration-functions.ts` の `buildOf`）は、ジョブが自動ログインか、プロファイルの方式が自動ログインかを見ない。自動ログインのジョブの止めた行から、まだ手動のログインで観察していない token の送信先と承認したサービスの Origin を、確認 1 回で足せる。足した後の自動ログインでは、資格情報がその送信先へ送られる。

### 4.2 プロファイル（MI-1・MI-2）

**作成の画面**（`ProfileForm.tsx` の新しく作るときの見え方。`routes/profiles/new.tsx`）に出すのは次だけにします。

1. 開始の URL（必須）。
2. 使い方の 2 択: 「ログインして読む（テスト環境）」（`TEST`・`TEST_AUTH_PASSIVE`・`MANUAL_SESSION`）、「公開の画面だけ」（`PUBLIC`・`PUBLIC_PASSIVE`・`NONE`）。
3. テスト環境のときだけ、隔離の扱いの 2 択: 「隔離はまだ確かめていない（読み取りだけ）」を選ぶと、参照を `isolation-unverified-<YYYYMMDD>`（保存した日）で作る。「確かめた記録がある」を選んだときだけ、参照の文字の欄を出す。
4. 「保存して入口を確かめる」（公開の画面だけなら「保存」）。

隠す値（案のまま保存する。「詳しい設定」で直せる）:

| 値 | 決め方 |
| --- | --- |
| 名前（`profileId`） | 開始の URL のホスト名からの今の案。重なれば `-2`、`-3` を付ける。既存の設定のファイルを使うときも案を出す |
| 設定のファイル | 開始の URL の Origin を `site.allowedOrigins` に含み、かつファイルの開始の URL が入れた開始の URL と同じ（監査の開始と同じ正規化）ファイルが `config/targets`・`local/targets` にちょうど 1 つあれば、それを使う（2026-10-26 MI-1 の報告による設計者の判断。Origin だけで選ぶと、入れた開始の URL がプロファイルに残らず、読む画面が変わるため）。同じ Origin のファイルがないときは今どおり新しく作る（負荷はページの上限 3・間隔 10 秒）。同じ Origin のファイルが 2 つ以上ある、または開始の URL が違うときは、作成を止め、理由と候補を出して詳しい設定で選ばせる |
| 許可 Origin | 開始の URL の Origin |
| テスト環境の Origin | 許可 Origin を写す（既存のファイルを使うときも写す。今は空） |
| 環境・監査モード・認証の方式 | 2 択から決まる。自動ログインは、作成では選ばせない（4.4 の切り替えだけ） |
| 承認したサービスの Origin | 作成の画面から消す。手動のログインの観察だけが足す（今の自動の登録）。プロファイルの詳細では読むだけにし、消す操作だけ置く |

**詳しい設定**: 今の `ProfileForm` の全部の欄は、プロファイルの詳細の「詳しい設定」（たたんだ見出し）から開く編集の画面に残します。新しい部品「たたんだ詳しい設定」（`AdvancedSettings`。共通部品台帳に載せる）を作り、4.3 の認証の設定と、4.6 のシナリオでも使います。

**保存して入口を確かめる**: 保存に成功したら、同じ押下で入口の確かめのジョブを 1 回始めます（今の入口の確かめと同じ。ログインしないで開始の URL を 1 回 `GET`）。押す前に、ボタンの下の文で「保存すると、開始の URL を 1 回だけ読みます（ログインしません）」と示します。送る要求は今と同じで、増えません。

### 4.3 認証の設定（MI-3）

- **案で保存する**: 入口の確かめのジョブが「読んだ」（`READ`）で終わり、ログインの画面に見え（`facts.loginPage`）、そのプロファイルに認証の設定がまだないとき、ジョブの管理が、入口の確かめの案（`proposal`）と今の案の作り方（`authSetupDraftOf`）から認証の設定を作って保存します。読まないパスは空、読む範囲のパスは今の既定です。手動のログインの観察の自動の登録（T43d・T44e）は、そのまま、token の送信先などを足します。
  - 認証の設定がすでにあるときは、上書きしません（案と違う所は、今どおりジョブの画面の「入口の確かめの結果」に出す）。
  - ログインの画面に見えないとき、「読んだ」でないときは、保存しません。プロファイルの詳細の「次にすること」に、理由と「詳しい設定で認証の設定を作る」を出します。
  - 保存の検証（`validateAuthSetup`）は変えません。案が検証を通らないときは保存せず、上と同じく理由を出します。
  - 案で保存するのは、認証の方式が手動のログイン（`MANUAL_SESSION`）のプロファイルだけ（2026-10-26 MI-R の Minor 3 による）。自動ログインのプロファイルは、資格情報の送信先（フォームの送信先、セレクタ）を人の確かめなしに保存しないため、自動保存しない。
  - 「設定がないときだけ保存する」の確かめは、保存のトランザクションの中で行う（MI-R の Minor 4）。
- **画面をなくす**: 認証の設定の画面（`routes/auth-setup/$profileId.tsx`）は、ふだんの流れ（「次にすること」「次の手順」の進む先）からは外し、プロファイルの詳細の「詳しい設定」から開きます。直す道（設定が古い・自動保存できなかったときの「直す」、監査の開始の画面のログインの欄、手動のログインから登録した設定の「見直す」）のリンクは残します（2026-10-26 MI-3 の報告による設計者の判断）。画面の中も、今の欄を全部「詳しい設定」の部品でたたみ、上に「どこから来た値か」の要約（`DraftValueMark` の印）だけを出します。
- **空の欄の赤い文を出さない**: 承認したサービスの Origin が 0 件のときの赤い文（`noServiceOriginsNotice`）は、自動ログインのプロファイルで、まだ手動のログインの登録が済んでいないときだけ出る事態です。4.4 で自動ログインへ入る道を切り替えだけにするので、ふだんは出ません。出る場面では、赤い誤りでなく「手動のログインで 1 回ログインすると、自動で入ります」の知らせにします。
- **読まないパスを監査の開始の画面に出す**: 監査の開始の画面（`routes/start/$profileId.tsx`）に、「読まないパス（任意。1 行に 1 つ）」の欄を出します。今の値（認証の設定の `excludedPaths`）を初めから入れ、既定の語（`DEFAULT_EXCLUDED_URL_WORDS`）で止める語を説明に出します。値を変えて監査を始めると、認証の設定を保存してから始めます（変えなければ保存しません）。保存の検証と改訂の扱いは、今の認証の設定の保存と同じ部品を使います。

### 4.4 自動ログイン（MI-4）

- 自動ログインへは、今の切り替え（FM2e。`setUpAutomatedLogin`、`AutomatedLoginSetupForm.tsx`）だけで入ります。作成の画面で自動ログインを選ばせません（4.2）。今ある自動ログインのプロファイル（方式が `AUTOMATED_LOGIN`）は、そのまま動きます。
- プロファイルの詳細の「次にすること」で、手動のログインの登録が済んだ（token の送信先と成功の鍵がそろった）プロファイルに「次から自動でログインする」を出します。
- 切り替えの画面では、3 つのセレクタの案がそろっているときは、セレクタを「詳しい設定」にたたみます。見える欄は資格情報の 3 欄だけです。

### 4.5 書き込みにも使う（MI-5）

- `PROFILE_OPERATION_POLICY.AUDIT` に `TEST_APPROVED_WRITE: LOGIN_STRATEGIES` を足します（ユーザーの判断 1）。監査のジョブは、プロファイルのモードにかかわらず、今と同じ Passive の扱い（GET・HEAD だけ、読み取りでない要求を止める）です。これを安全のテストで確かめます（受け入れ条件 4）。
- プロファイルの詳細に「書き込みにも使う」を出します（`TEST_AUTH_PASSIVE` で、認証の設定があるプロファイル）。確認のダイアログに、次を出します: 書き込みの段に進めるようになること（書き込みそのものは、シナリオの承認と開始の押下がない限り送らない）、隔離の扱い（`environmentEvidenceRef` が未確認の参照なら、そのことを目立たせる）、プロファイルの改訂が 1 つ進み、承認済みのシナリオと発見・READ の確かめの結果のうち、改訂に結びつくものはやり直しになること。確認すると、モードを `TEST_APPROVED_WRITE` にした改訂を保存します（今のプロファイルの保存の部品を使う。認証の設定・資格情報・承認したサービスの Origin は同じプロファイルなので、そのまま）。
- 書き込みのモードから戻す操作は作りません（詳しい設定の編集で戻せる）。
- 監査の開始の確かめ、表示の設定（「削除のほかを通す」など、モードで変わる表示）を、書き込みのモードで監査を始めたときにどう見せるかは、MI-5 の実装者が今のコードを読んで報告し、設計者が決めます（調査で読み切れていない。7 章）。

### 4.6 書き込みのシナリオ（MI-6・MI-7）

- 1 つの値しか通らない欄（送る鍵の「全部オン」、1 回の上限 1、filter の名前など）は、表示だけにします。
- ページが決める鍵の既定を「全部オン」にします（今の新規の画面は既定のままだと拒まれる。自動の下書きは全部オン）。
- 累積の上限、期限は「詳しい設定」にたたみます。
- **副作用の確認 4 項目**（ユーザーの判断 2）: シナリオの画面からチェックを外し、承認のダイアログに 4 つの副作用の中身を並べて示します。「承認する」の 1 回の押下で、4 項目を確認したことにして、承認します。記録の形（シナリオの版と digest に副作用の確認が入る、承認がその digest を縛る）は変えません。どう 1 回の操作で「確認を入れた版を作り、その版を承認する」を行うか（1 つのトランザクションか、版を作ってから承認か）は、MI-6 の実装者が今のシナリオの保存と承認の部品を読んで報告し、設計者が決めます。
- 入力の規則で、副作用の確認がまだの間、メール・電話の欄が「推せなかった」に見える表示（`EXTERNAL_DELIVERY_BLOCKED`）は、確認が承認の時になることに合わせて直します（MI-6 で扱い方を報告させる）。
- **更新の照合の READ**: 更新のシナリオの下書きで、照合の READ を、台帳の登録のシナリオの照合の READ の定義と、変える欄から自動で埋めます（MI-7）。変える欄・保つ欄は、ユーザーの判断（2026-10-22「人が必ず選ぶ」）のとおり、人が選びます。

### 4.7 守りの穴をふさぐ（MI-G。最初に行う）

- 表の 1 行の「登録する」（案と保存の両方。`loginStageRowProposalFn` と保存の Server Function の `buildOf`）で、次のときは、token の送信先と承認したサービスの Origin を足す登録を拒みます（新しい拒否の理由。カタログに文言を足す）:
  - ジョブが自動ログインの試し（`autoLoginAttempt` がある、またはジョブの種類がログインの確かめ）。
  - プロファイルの認証の方式が `AUTOMATED_LOGIN`。
- ログインに伴う送信の登録は、送信先の Origin がすでに承認したサービスの Origin か許可 Origin の中にあるときだけ、上のときでも許します（新しい送信先を増やさない）。ただし、プロファイルが自動ログインのときは、4.7.1 の 3 により、ログインに伴う送信を足すことも拒みます（2026-10-26 MI-F1 の報告による。手動のログインのプロファイルで、自動ログインの記録のあるジョブの行は、この例外のとおり通る）。
- 足すのは、手動のログインの観察（自動の登録と、手動のログインのジョブの行の「登録する」）だけになります。

### 4.7.1 資格情報の送信先の不変条件（MI-R の Critical C-1・Important I-1 による。2026-10-26）

レビューで、認証の方式を手動と自動の間で往復させると、観察していない Origin を承認したサービスの Origin と token の送信先にできる道が見つかった（画面のサーバの Server Function を、手で作った要求か URL で呼ぶ必要がある）。また、自動ログインのプロファイルで、詳しい設定から token の送信先の path・query・ログインに伴う送信・フォームの送信先・テスト環境の Origin・設定のファイルを変えられた。次の不変条件を置く。

1. **承認したサービスの Origin を足すのは、観察からだけ。** 足す口は、手動のログインの後の自動の登録と、表の 1 行の「登録する」と、認証の設定の画面の下書きからの保存だけにする。どれも、サーバがジョブの記録と行から組み立て直した値だけを足す（ブラウザが送った `addServiceOrigins` を信用しない）。プロファイルの編集（`updateProfileFn`）は、方式によらず、承認したサービスの Origin を消すことだけを受け、足すことを拒む。作成は、承認したサービスの Origin を受けない。
2. **自動ログインへは切り替え（`setUpAutomatedLogin`）だけで入る。** プロファイルの作成と編集で、認証の方式を `AUTOMATED_LOGIN` にする保存を、サーバで拒む（今ある自動ログインのプロファイルを、方式を変えずに保存するのは受ける）。編集で手動のログインへ戻すことは受ける。
3. **自動ログインのプロファイルでは、資格情報の送信先を変えない。** 認証の方式が `AUTOMATED_LOGIN` のプロファイルの保存（認証の設定とプロファイル）で、次が変わるものを拒む: ログインの画面の URL、ログインの送り方、token の送信先（Origin・path・必須の query）、ログインに伴う送信の送信先、フォームの送信先、自動ログインのセレクタ、承認したサービスの Origin（足すこと）、テスト環境の Origin（足すこと）、設定のファイル。変えたいときは、手動のログインへ戻し、手動のログインで観察し直してから、切り替え直す。読まないパス、読む範囲のパス、成功の条件、セッションの切れの条件、失敗の条件、上限など、送信先でない欄の変更は受ける。
4. **守りの置き場所。** 判定は `src/control/` の純粋な関数 1 か所に置く。
   - 3 は、管理データの保存の部品（プロファイルと認証の設定の保存、`saveProfileAndAuthSetup`）の層に置き、トランザクションの中で「今保存してある値」と「保存の後の値」を比べて拒む（保存の前も後も `AUTOMATED_LOGIN` のとき）。今後の新しい口も覆うため。
   - 1 と 2 は、画面のサーバの口（作成・編集・下書きからの保存の Server Function）に置く。保存の部品の層は、観察からの登録（ジョブの管理の自動の登録、行の「登録する」）と、切り替え（`setUpAutomatedLogin`）と、テストの準備も使うため、その層で一律に拒むと、正しい口まで止まる。
   - Server Function は理由を画面に写すだけにする（判定を書き直さない）。
5. **実行の許可の発行と書き込みの開始は、副作用の確認を直接見る**（MI-R の Minor 7。承認の不変条件に頼らない多重の守り）。承認の前の前提（`PRE_APPROVAL_EVALUATION_PREMISE`）が、承認の前の画面のほかで使われないことを構造のテストで固定する。

6. **ログインの送信先は、観察からだけ入る（方式によらない）**（2026-10-26 再レビュー MI-R2 の Critical C-A による）。手動のログインのプロファイルのうちに、詳しい設定で送信先（3 の項目のうち、認証の設定のもの）を手で変え、そのまま切り替えると、観察していない送信先が自動ログインに入った。ユーザーの方針（知りえない値を手で入れさせない、自動化を厳守）にも合わせ、次にする。
   - 認証の設定の画面の保存（`saveAuthSetupFn`。詳しい設定）は、方式によらず、認証の設定がすでにあるときは、3 の送信先の項目を変える保存を拒む。送信先でない欄は今どおり受ける。
   - 認証の設定がまだないときの最初の保存（自動保存できなかったときの詳しい設定）は、送信先の項目が、そのプロファイルの最後の入口の確かめの案（ログインの画面の URL、送り方、フォームの送信先、セレクタ）と同じときだけ受ける。入口の確かめがなければ、送信先の項目を空のまま（スクリプトの送信の token の送信先などは、手動のログインの観察が入れる）にしたときだけ受ける。
   - token の送信先とログインに伴う送信は、観察の口（手動のログインの後の自動の登録、表の行の「登録する」、行から開いた下書きの保存）だけが入れる。下書きの保存は、Origin だけでなく、行の path と必須の query も照らし、行の観察と同じときだけ受ける。
   - 送信先を変えたいとき（サイトのログインが変わったなど）は、今は、プロファイルを作り直す（作成は入力 4 つ）。既知の制限として記録する。
   - 補足（2026-10-26 再々レビュー MI-R3 の Minor による。実装に合わせた）:
     - 最初の保存は、入口の確かめの案があっても、送信先のない形（ログインの画面の URL だけを人が入れ、token の送信先・ログインに伴う送信・フォームの送信先・セレクタがない形）を受ける。案の画面がログインの画面でなかったときの逃げ道のため。手動のログインは、その画面を開き、token の送信先などは観察から入る。資格情報は、切り替えの時のログインの画面の Origin に結びつき、実行時に照らされ、切り替えの後はログインの画面の URL を変えられない（3）。
     - 自動ログインのセレクタは、切り替えの時に人が確かめる値（案が既定）で、観察と照らさない。資格情報の送り先は、実行時の確かめ（フォームの送信: パスワードの欄、同じ form、POST、許した送信先。スクリプトの送信: token のほかの資格情報を含む要求を止める）が絞る。
     - プロファイルの項目（設定のファイル、テスト環境の Origin）は、手動のログインのうちに変えられ、切り替えで持ち越す。手動のログインで観察し直すことは前提で、強制しない（認証の設定の送信先は 6 のとおり変わらない）。
7. **口の判定はトランザクションの中で**（MI-R2 の Important I-A・Minor M-1）。作成・編集・下書きの保存の口の判定（1・2）は、画面が読んだ改訂と今の改訂の照合を先に行い、保存の部品のトランザクションの中で読んだ値に対して判定する（判定の関数は 1 か所のまま、保存の部品へ渡す）。

手動のログインへ戻して観察し直す道は、人が手動のログインで送信先を観察する前提なので、許す（設計どおり）。

認証の設定がまだない自動ログインのプロファイルへの最初の保存は、3 の比べる値がないので受ける（2026-10-26 MI-F1 の報告による設計者の判断）。画面の道では、この形のプロファイルはもう作れない（作成と編集は 2 で拒み、切り替えには設定が要る）。残るのは、MI より前に作った、設定のない自動ログインのプロファイルだけで、利用者に取り消しを勧める（Task 42 の当日の手順）。資格情報のメタデータに token の送信先を結ぶ多重の守り（MI-R の C-1 の案 d）は、1〜4 で道が閉じるので、今回は入れない（既知の追加の案として記録する）。

### 4.8 READ の確かめ（MI-7 に含める）

ユーザーの判断がない、確かめを緩める変更（期待の既定を「少なくとも 1 行」にする）はしません。緩めない変更だけ行います: 対象の種類を、来たリンク（候補か画面か）で決めて radio を出さない。画面の path の select の先頭を既定にする。

## 5. 安全への影響

- 監査のジョブの送信の扱いは、プロファイルのモードでなくジョブの種類で決まる（調査の事実）。書き込みのモードで監査を許しても、監査は読み取りだけのまま。受け入れ条件 4 で確かめる。
- 書き込みの守り（シナリオの承認、実行の許可、1 件の予約、照合、環境の証跡の参照）は、シナリオと許可の単位なので変わらない。「書き込みにも使う」の 1 回の確認が、今の「書き込みのプロファイルを別に作る」に代わる。
- 承認したサービスの Origin と token の送信先は、手動のログインの観察からだけ入る。MI-G で、自動ログインの記録から入る口を閉じる（今より強くなる）。
- 副作用の確認は、4 回の押下が 1 回になる（ユーザーの判断 2）。記録の形は変わらない。
- 認証の設定の案での保存は、検証を通ったものだけ。読まないパスは監査の開始の画面で見える。既定の語の一覧は今どおり効く。
- 「保存して入口を確かめる」は、利用者が押したときだけ、今と同じ 1 回の `GET` を送る。サイトへの負荷は増えない。
- 「判定できない」は増えない見込み（発見と READ を 2 つ目のプロファイルで設定の足りないまま走らせることがなくなる）。

## 6. 受け入れ条件

1. 新しく作る画面で、テスト環境のプロファイルを、入力 1（開始の URL）、選択 2、押下 1 で保存し、入口の確かめが走る。既存の設定のファイルが 1 つ当たるときは、それを使い、テスト環境の Origin が埋まる。
2. 入口の確かめがログインの画面を見つけたとき、認証の設定が案で保存される。すでにあるときは上書きしない。ログインの画面に見えないときは保存せず、理由が出る。
3. 手動のログインの監査 → 自動の登録 → 「次から自動でログインする」（資格情報 3 欄と確認）→ ログインの確かめ、が、認証の設定の画面を開かずに通る（fixture のサイト）。
4. 書き込みのモードのプロファイルで監査を始められ、その監査で読み取りでない要求がサーバに届かない（既定と CLI の Chromium の両方。今の Passive の安全のテストと同じ条件）。
5. 「書き込みにも使う」で、同じプロファイルが `TEST_APPROVED_WRITE` になり、発見 → シナリオの下書き → 承認（副作用の確認はダイアログの 1 回）→ 書き込み、が通る（fixture）。
6. MI-G: 自動ログインのジョブの行と、自動ログインのプロファイルでは、token の送信先と承認したサービスの Origin を足す登録が拒まれる（RED を先に確かめる）。手動のログインのジョブの行からは、今どおり登録できる。
7. 更新のシナリオの下書きで、照合の READ が台帳から埋まる。
8. 表示の SSOT（UI Gate、カタログ）を守る。新しい文言はカタログに置く。
9. 関係するテストが PASS（実装者は関係するテストだけ。全体の検証は最後に 1 回）。

## 8. 分からないこと（実装者に確かめさせる）

- 書き込みのモードで監査を始めたときの、開始の確かめと表示の設定（「削除のほかを通す」など）の扱い（MI-5）。
- 副作用の確認を承認の 1 回にするときの、シナリオの版の作り方と承認の順（MI-6）。
- 読む範囲のパスの既定（開始の URL の path そのもの）が、監査で読む範囲を狭くしすぎないか（MI-3 で今の案のまま。気づいたことを報告させる）。
- 切り替え（FM2e）の後に手動のログインへ戻す道が画面で通るか（MI-4 で確かめる）。
