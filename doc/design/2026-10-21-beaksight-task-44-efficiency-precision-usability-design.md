## 1. 目的と経緯

ユーザーの問いと指示（2026-10-18）による。

- 「監査効率、監査精度、ユーザビリティは重視されているか？」
- 「安全性を高めた結果、最初の画面から『判定できない』を連発するようでは困る」

2026-10-19〜21 の実テスト環境の確かめで、読み取りの段は通った。その途中で、次の方針が加わった。

- ユーザーの方針（2026-10-19）: ページが自分で出す送信は止めない。不自然な遮断は、サイトの検知を招く。BeakSight 自身の操作は、意図して制御する。
- 実テスト環境では、次の種類の問題が多く見つかった（DEF-136〜147 で直した。残りは 3 章）。
  - 使いにくさ
  - 判定を捨てる作り
  - 大きな Run での重さ

Task 44 では、fixture の代表のサイトで数を測り、残りの問題を優先度の順に直す。

## 2. 測ること（fixture の代表のサイト）

- 代表のサイト: 静的なサイト（公開の監査）と、スクリプトでログインする SPA の管理画面（今の `spa-auth-site-fixture`。手動のログインと、送信の扱い `PASS_EXCEPT_DELETE`）の 2 つ。
- 測りの部品を 1 つ作る（`tests/helpers/` と `tools/` のどちらかに置く）。測りの結果は、表の形で `doc/spec/real-test-environment.md` の記録の表と同じ項目にする。実テスト環境でも、同じ項目を手で記録できるようにする。

| 観点 | 測る項目 |
| --- | --- |
| 精度 | 段ごと（入口の確かめ、読み取りの監査、発見、READ の確かめ、書き込みの照合の READ）の「判定できない」（`UNDETERMINED`・`PARTIAL`・`UNKNOWN`・読めなかった画面）の数と割合と、理由ごとの内訳。発見できた画面・form・API の候補の数と、fixture の正解との差 |
| 使いやすさ | 開始の URL を入れてから最初の監査の結果が出るまでの、画面の操作の数と入力の数。理由の表示のない止まり方の数 |
| 効率 | 監査 1 回の所要時間を段ごとに（読み込みの間隔の待ち、落ち着きの待ち、probe の押下、Context の作り直し、仕上げ）。成果物の大きさ |

## 4. 目標（Exit Gate G44。ユーザーの承認が要る）

1. fixture の代表のサイトの最初の画面（入口の確かめと最初の読み取りの監査）で、「判定できない」のページが 1 割以下。残るものは、すべて理由と次にできることが画面と報告に出る。
2. 優先度 1 と優先度 2 をすべて直す。優先度 3 は P3-1・P3-3 を直し、ほかは測って効果が大きいものだけ直す。優先度 4 は、P4-1（秘密の扱い）を直し、ほかは時間の内で直す（残りは Task 42 の後の課題として記録）。
3. サイトへの負荷の上限（ロードマップの 7 章。読み込みの間隔、読み込み直しの回数）は変えない。
4. 安全の回帰（両方の Chromium）と、独立レビュー（Critical 0、Important 0）。
