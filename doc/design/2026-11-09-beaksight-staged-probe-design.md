# BeakSight 何段もの操作で入力の枠を開く登録の画面を、操作さがしでたどる（DEF-238）設計書

- 日付: 2026-11-09
- 状態: ユーザー承認済み（下の 2）
- 関係する文書: `2026-10-20-beaksight-probe-press-priority-design.md`（1 画面 3 回の上限。この設計書で置き換える）、`2026-11-08-beaksight-same-origin-api-and-spa-routes-design.md`（DEF-221）、`2026-11-02-beaksight-list-row-update-design.md`（N2・LU-10）
- 調査: INV-238（2026-11-09。仮の予約の画面、2 つの Chromium で 12 回）

## 1. 今の動き（INV-238 の事実）

- 操作さがしは、1 回の読み込みで欄を埋めてボタンを 1 つ押し、観察する。1 画面 3 回まで（`submission-probe-contracts.ts:52`）。
- 押して URL が変わると、その押下と残りを `PAGE_CHANGED` にして、観察した送信の形を捨てる（`submission-probe.ts:1146-1151`）。
- query だけ変わる移動は、正規化（許した名前の query だけ残す。既定は空）で押した画面と同じ URL になり、読まない（`discovery-run.ts:247`）。
- 窓（`role="dialog"`）でない区画に後から出る「作成」は、押す候補に足されない（`submission-probe.ts:983-1009`）。
- radio は触らない。検索して選ぶ欄は、目印の文字では候補が出ない。
- 調べた案のうち、別のページとして読む案（B）と、開く操作を先に押す案（C）だけでは、予約の作成の送信の形が取れない。段をたどる案（A）に、下の足しを入れた試作で `API_CREATE` が取れた（届いた読み取りでない要求は 0）。

## 2. ユーザーの判断（言葉どおり。2026-11-09）

- 押す数の上限について: 「BeakSight内で上限を定めないで。サイトの構造に合わせて。」
- 書き込みの段の途中の送信について: 「削除以外は全て通すという基本方針に従って」

## 3. 採用する設計（INV-238 の案 A ＋ 足し）

### 3.1 段をたどる

1. 押して画面が変わったとき（同じ文書の中の URL の変化・query の変化・欄や区画が出た）、打ち切らずに、その状態を新しい「段」として候補を読み直し、続けて押す。
2. 段ごとの観察は別にする（押下ごとに begin と end）。どの段の押下の送信かを記録に残す（段の番号と、前の段の押下の並び）。
3. 段を移った押下で観察した送信の形も、捨てずに記録する。
4. 押せなかった「作成」（押せない送信ボタン・後から出た候補）は、欄が開いた後にもう一度押す（段の中の押し直し）。窓でない区画に後から出た確定の語のボタンも、候補に足す。
5. radio は、組ごとに最初の選択肢を選ぶ（既にある値を選ぶ形）。select は今どおり空でない最初の選択肢。
6. 検索して選ぶ欄は選べないので、「新しい〜を入力」の開く操作を先に押す（知りえない値を利用者に入れさせない）。

### 3.2 終わりの決め方（BeakSight の数の上限を置かない）

1. 押す数・段の数に、固定の数の上限を置かない。1 画面 3 回の上限（`MAX_SUBMISSION_PROBE_PRESSES` など）と、入れたのに押せなかった回の上限は外す。
2. 終わりはサイトの構造で決める。
   - 同じ状態（候補の識別の集合と URL の正規の形）に戻ったら、その道は終える。
   - 新しい候補が出ない段では、それ以上進まない。
   - 1 つの状態の中で、同じ候補（識別の digest と順番）は 1 回だけ押す。
   - 今ある構造の決まり（ほかの画面と共通の部分は押さない、同じ識別・同じ語は押さない、削除の語・危険な語は押さない）は、そのまま使う。
3. 時間の決まり（ジョブの全体の時間の上限、静まるまでの待ち）は今のまま。

### 3.3 query の段

query の付いた URL への移動は、段の印として記録に残す（画面の場所に query を持たせる）。書き込みの段は、段を押してたどるので、query の URL を直に開かない（日付の query が古くなるため）。

### 3.4 書き込みの段

1. 承認の内容に、段の並び（段ごとに押した候補の識別の digest・同じ digest の中の順番・移り方）を入れる。LU-10（一覧の行の開き手を押してから書き込む）を先例にする。承認の画面には技術の情報を出さない。
2. 書き込みの段は、画面を 1 回読み、段を押してたどり、承認した送信を 1 回だけ届ける。
3. 段をたどる間の送信は、「削除のほかは通す」の基本の方針（`PASS_EXCEPT_DELETE`）に従う。削除・危険な語・資格情報は止める。承認した送信の照合（1 回だけ、本文の照合）は今のまま。

## 4. 変えないもの

- 操作さがしで押した送信は届けない（凍結の決まり）。
- 読み込みの間隔、要求の上限（承認したサービスの Origin の 1 分 600 件など）。
- 承認の流れ（画面の一覧でチェックした画面だけ）。

## 5. サイトへの負荷

- ページの読み込みの回数は増えない。
- 増えるのは、同じ画面の中で押す回数と、押して出る読み取り（検索の GET など）。上限を外すので、候補の多い画面で操作さがしの時間が延びる。実装で、実テスト環境に近い候補の数（1 画面 70〜250）の仮の画面で、時間と要求の数を測り、設計書に書き足す。
- 承認したサービスの Origin への要求の上限は今のまま効く。

## 6. 限界

1. 段を移る送信の応答を待ってから画面を移す SPA は、操作さがしでは先へ進めない（押した送信は届けないため）。
2. 時間の枠を選ぶ段は、今回の試作では押していない。
3. object の中の目印は、DEF-234 の段 C の範囲（行の object）のほかは数えない。

## 7. テスト

- 仮のサイト（INV-238 の `inv238/site.ts` を一般の文言で写す）で、操作さがしが予約の作成の送信の形（`API_CREATE`）を取れる。途中の送信（拠点の選択の保存）は届かない（サーバの記録）。
- 書き込みの段で、段をたどり、承認した送信が 1 回だけ届く。途中の送信は「削除のほかは通す」で届き、削除は止まる。
- 状態が繰り返す画面・新しい候補が出ない画面で、終わる。
- 2 つの Chromium で確かめる。
- 既存の操作さがし・押す順（DEF-142）・DEF-221・LU-10 のテストが通る（上限の期待は、外したことに合わせて直し、理由を報告に書く）。
