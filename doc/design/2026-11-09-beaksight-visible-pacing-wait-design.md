# BeakSight 読み込みの間隔の待ちを、前の画面を見せたまま行う（DEF-236）設計書

## 1. 目的

DEF-209 の直しで空の窓は出なくなった。しかし監査は、どの読み込みの境目（Desktop → 幅の走査 320・768・1024 → Mobile → 次のページ）でも、前の Context を閉じてから最小 10 秒を待つ。待つ間は窓が出ない。操作さがし・READ の確かめは、新しい空の page を作ってから待つ（`worker-run-session.ts:296` → `:338`）。

## 2. ユーザーの判断（言葉どおり）

- 「監査中、ブランクページでの待機は無くなったが、ページが閉じてから待機するようになった。ページを閉じずに画面を表示状態で10秒待機が望ましい」
- 待つ間の要求の増え（仮のサイトで 2 ページ 30 → 104 件）を示したうえで: 「サイトが自然に出す通信であれば許容する」（2026-11-09）

## 3. 採用する設計（INV-PACE の案 A 改）

### 3.1 監査

1. 証拠を集め終えたら、前のセッションを閉じずに、読み込みの間隔の目標の時刻まで待つ。待ち終えてから閉じ、次のセッションを作る。同時に 2 つの Context は生きない（DEF-191 の決まりを保つ）。
2. **待ちの印。** 待ちの始まりに、Guard へ印を付ける新しい口を作る（`announcePageLeave` は流用しない。要求の上限と移動の止めが違うため）。印の後の要求と止めた事象は、次のとおり扱う。
   - そのビューポートの数（`subresourceRequests`、DEF-129・DEF-130 の数）に入れない。
   - 止めた事象は記録に残すが、Finding の入力から外す。
   - 安全の判定（DELETE・危険な語・資格情報などの止め）は今のまま当てる。印は数と Finding の扱いだけを変える。
3. **待ちの記録。** pacer に「目標の時刻まで待つだけ」の口を足し、待った時間を `pacingWaitMs` に入れる（包む部品 `navigation-pacer.ts:217`、`run-coordinator.ts`、`audit-stage-run.ts:121`、site-metadata の hooks にも通す）。待ちの後の `beforeNavigation` は 0 秒近くになる。間隔の長さは変えない。
4. **待たない時。** 次の読み込みがない時は待たずに閉じる。対象は、違反・不調・セッションの切れ・ダウンロードで次のビューポートを始めない時と、Run の最後のページ。
5. **待ちの場所。**
   - Desktop と Mobile: collector を外した後、閉じる処理（`page-auditor.ts:936`）の前に置く。
   - 幅の走査: collector の閉じる処理（`layout-collector.ts:1657`）の前に口を足す。
   - 待ちは閉じる処理の期限（`CONTEXT_CLOSE_TIMEOUT_MS`）の外に置く。
6. **待つ間のセッションの切れ。** 待つ間にサイトがログインの画面へ移った時は、今の閉じた後の確かめでセッションの切れとして扱う。そのページの結果は、Run Coordinator の今の扱いのとおり採らない（FIX-236 の実装の後の判断。採るには Run Coordinator の変更が要るため）。

### 3.2 操作さがし・READ の確かめ・書き込みの段（`visitGuardedPage` の 5 か所）

監査と同じ決まりにそろえる（共通化）。新しい空の page を見せたまま待つのをやめ、前の画面を閉じずに待つ。待ちの印の扱いは 3.1 の 2 と同じ。押す処理（Interaction）の Context は対象外で、今のまま。

## 4. 変えないもの

- 読み込みの間隔の長さ（最小 10 秒など）と、読み込みの回数。
- 安全の判定（PASS_EXCEPT_DELETE でも DELETE・危険な語・資格情報は止める）。
- 閉じる手順（状態を読む → about:blank へ離れる → 1 秒 → 閉じる）。

## 5. サイトへの負荷

- BeakSight 自身が出す要求と、読み込みの回数は増えない。
- 待つ間も、サイトの画面が自分で出す通信（定期の読み取り、token の更新、WebSocket の繋ぎ直しなど）は続く。量は画面の作りによる（仮のサイトでは 1 回の待ちで数件、約 0.8 件/秒）。ユーザーはこれを許容した。
- 承認したサービスの Origin への要求の上限（1 分 600 件で待つ、1 回の Run 10,000 件で止める）は、待つ間の要求も数える。上限は変えない。

## 6. 限界

1. headed では、待つ間に人が画面を操作できる（操作で出た要求も、Guard の判定と待ちの印の扱いを受ける）。
2. 待つ間にサイトが自分で移動・ダウンロードをすると、記録には残るが、そのビューポートの結果には入らない。

## 7. テスト

- 仮のサイト（一般の文言。2 秒ごとの読み取り、鍵を回す token、WebSocket、pagehide の beacon、任意で定期の DELETE。INV-PACE の `invpace/site.ts` を写す）。
  - 待つ間に page が開いている（headless の page の数）。
  - `subresourceRequests` と Finding が今と同じ（待つ間の要求が混ざらない）。
  - 待つ間の DELETE は届かない。それが Finding にならず、記録に残る。
  - `pacingWaitMs` が待ちの長さを含む。
  - token の受け継ぎで使い回しが 0。
  - 最後のページの後に待たない。
- 操作さがし・READ の確かめで、空の page を見せない。前の画面を見せたまま待つ。
- 2 つの Chromium。DEF-027・DEF-225・DEF-191・navigation-pacing の既存のテストが通る。
