## 2. 第 1 段（今すぐ）

### 2.1 「登録する」をその場で保存する（不具合）

- 今の作り（Task 43）は、「登録する」で認証の設定の画面へ案を入れて移り、その画面で保存する。そのため、押しても登録されず、画面が移る。案には成功の鍵が入らず、保存で `AUTH_SETUP_STORAGE_KEY_INVALID` になった。
- 直し: 表の「登録する」は、その行を足した設定の案を、確認のダイアログ（足すもの: token の送信先、またはログインに伴う送信と回数、足す承認したサービスの Origin）に出し、確認したらその場で保存する。画面は移らない。
- 案の組み立ては、自動の登録（`src/control/manual-login-registration.ts`）と同じ部品を使う。成功の鍵は、ジョブのログインの観察（`loginObservation.storageKeys`）から入れる。今の設定が版 3 なら、その行だけを足す。
- 保存はプロファイルの改訂を進める（自動の登録と同じ。画面に出す）。
- 自動の登録が登録しない行（token の後の送信など）も、利用者がこの「登録する」で足せる。危険な語・読まないパスの行は、今どおり登録できない（理由を出す）。

### 2.2 ジョブのブラウザを表示する

- 監査・発見・READ の確かめ・書き込みのジョブのブラウザ（今は headless）を、表示（headed）で起動できるようにする。ログインの段のブラウザは今どおり表示。
- 表示するかは、プロファイルごとの表示の設定（既定は表示）。表示の設定は、承認に結ばれるプロファイルの文書・改訂とは別に持つ（切り替えても承認・発見のやり直しを起こさない）。置き場所は管理データの別の表か列（版 15 が要るなら、版 14 の写しを固定してから）。
- 表示しても、Guard・Context・中継・上限は変わらない。表示したブラウザを利用者が操作すると結果が乱れるので、ジョブの画面に「見るだけ。操作しない」の注意を出す。利用者がブラウザを閉じたら、今の Browser が切れたときの扱い（失敗として記録）になる。
- ワーカーは `START` で表示するかを受け取る（IPC の項目）。テストは今どおり headless。

### 2.3 ログインを自動にする

- 手動のログインの成功の後（自動の登録が SAVED のとき）、ジョブの画面とプロファイルの画面に「次から自動でログインする」を出す。押すと、資格情報の登録の画面（今の Task 26 の画面）へ進み、登録したら、そのプロファイルの次のジョブから自動ログインになる（今の自動ログインの設定と資格情報の作り。自動ログインの上限と厳しさは今のまま）。
- 自動ログインが失敗したとき（`AUTH_SETUP_REQUIRED` など）に、手動のログインで続ける案内を出す（今の作りに合わせる）。

## 3. 第 2 段（実テスト環境の確かめの後に詳細を書いて諮る）

- 3.1 まとめて実行: 「まとめて監査する」1 回で、監査 → 発見 → READ の確かめ（定義があるものだけ）を続けて行う。ログインは 1 回だけ（ログインの状態をジョブの間で引き継ぐか、1 つのジョブの中で段を続けるか、を詳細で決める）。
- 3.2 下書きの自動作成: 発見の後に、API の登録・更新のシナリオ（変える欄・保つ欄の既定、台帳の結び付け）と、照合の READ の定義（`{id}` の型、生成した値と比べる期待）の下書きを作る。利用者は確かめて承認するだけ。
- 3.3 入力の規則の自動作成: 欄の型と名前から、実行のたびに変わる値の規則（メール・氏名・番号など）を作る。

## 3A. 第 2 段の詳細（2026-10-22 案。ユーザーに諮る）

調べの控え: `.superpowers/sdd/2026-08-27-beaksight-implementation-plan/FM2S-research-{A,B,C}-summary.md`。

共通の決まり:

- 書き込み（登録・更新）は、今どおり人の承認を経てだけ行う。自動で作るのは下書き（`DRAFT`）と、承認の前の規則だけ。承認・副作用の確認・実行の許可の発行・書き込みの開始は、自動にしない。副作用の確認の 4 項目は、必ず偽で作る。
- サイトへの負荷の上限（読み込みの間隔、読み込み直しの回数）は変えない。下書きと規則は、成果物と管理データだけから作り、サイトを読まない。
- 推測で決めた項目は、項目ごとに「推測」の印と根拠を画面に出す。印は承認に結ばない（表示のときに同じ純粋な部品で求め直す）。

### 3A.1 まとめて実行（3.1）

- **形（案 b'）**: 1 つのワーカーが、ログイン 1 回の後に段を続ける。段ごとに、今のジョブの行と Run を 1 つずつ作る（記録・画面・再開は今の作りのまま）。ログインの状態はワーカーのメモリから出さない（仕様の「状態を保存しない・通信に載せない」と I22 を守る）。
- **段の並び**: モードが `TEST_AUTH_PASSIVE` なら、監査 → 発見 → READ の確かめ。`TEST_APPROVED_WRITE` なら、発見 → READ の確かめ（監査はこのモードで動かない）。READ は、定義が 1 件以上あるときだけ行う。0 件なら「行わなかった」として終える（失敗にしない）。
- **段の間で持ち越すもの**:
  - factory の最新のログインの状態（token の更新の後のもの）。メモリの中だけで、取り出す口を新しく作る。
  - 読み込みの間隔の部品（pacer）。
  - サービスの Origin への要求の 1 分の窓。
  - 1 回の Run あたりの上限は、今どおり段ごとに数える。
- **次の段へ進むかの表**（純粋な判定の 1 か所。書き込みの連鎖 `write-chain-policy.ts` と同じ形）:
  - 進む: `COMPLETE`、またはページ・時間の上限で止まった `PARTIAL`。
  - 止める: 利用者の停止、Safety の違反、サイトの不調、セッションの切れ、`FAILED`、サービスの要求の上限で止まった `PARTIAL`（負荷の側に倒す）。
- **ロックと停止**:
  - 連鎖の間、ワーカーは生きたまま次の段のジョブの行を受けるので、段の間に空きはない（ほかのジョブは始まらない）。
  - 画面の「やめる」は、連鎖の全体を止める（今の段は今の止め方で止め、次の段を始めない）。
- **改訂**: 連鎖は、始めた時のプロファイルの改訂に結ぶ。手動のログインの自動の登録（改訂を進める）は、連鎖の最後に 1 回だけ行う。
- **再開**: 連鎖そのものは再開しない。中断した監査の段は、今どおり監査のジョブとして再開できる。
- **画面**: 開始の画面に「まとめて実行する」を置く。ジョブの詳細に、連鎖の段の一覧と、止まった理由と次にできることを出す。

### 3A.2 下書きの自動の作成（3.2）

- **作る時**: 発見のジョブの詳細と発見の画面に、「シナリオの下書きを作る」のボタンを置く（利用者が 1 回押す）。発見の時の改訂が今の改訂と同じときだけ押せる。
- **作るもの**: API の型（`API_CREATE`・`API_UPDATE`）の行ごとに、下書きを 1 つずつ作る。form のシナリオは、推測が大半なので作らない（今の画面のまま）。
  - **登録**:
    - 送る鍵は、欄に対応する鍵のすべて。ページが決める鍵は、欄に対応しない鍵のすべて。
    - 上限と期限は既定。
    - `recordId.key` は、同じ表の更新の filter の名前から推す（推測の印）。なければ空にして、人に入れさせる。
  - **更新**:
    - 台帳は、結び付く登録が 1 つのときだけ決める。0 なら、同じボタンで先に登録の下書きを作る。2 つ以上なら人が選ぶ。
    - 更新の画面の型は、今の案の先頭。
    - 変える鍵は、人が必ず選ぶ（ユーザーの判断 2026-10-22）。下書きでは、どの鍵も「保つ」にしておく。そのままでは保存の確かめ（`SCENARIO_UPDATE_NO_CHANGED_FIELD`）を通らないので、更新の下書きは「変える欄を選んでください」の状態で作り、画面に案内を出す。保存の確かめを通らない下書きを残す口が要るかは、FM2b で確かめる（要るなら Blocker として止まる）。
  - **照合の READ**:
    - `{id}` の画面の型の定義を、読めた画面の path から推して作る（推測の印）。
    - 期待の欄は、入力の規則（3A.3）を付けた後に、変わる値の欄から推す。
- **共通化**: `apiProbeDraftOf`・`apiFormOf`（`apps/local-ui/src/server/scenario-functions.ts`）を `src/control/` の純粋な部品へ移す。画面の案と自動の下書きは、同じ部品を使う。
- **発見のやり直し**: 既にあるシナリオ（とくに承認済み）は書き換えない。同じ型の下書きがあれば作らず、「既にある」と示す。

### 3A.3 入力の規則の自動の作成（3.3）

- **作る時**: 3A.2 の下書きを作るときに、規則の集まりを作って付ける。承認の前だけ作り、承認の後には作らない。
- **推した規則を固定する**: 推した規則（`TEMPLATE`・`GENERIC`）を、保存した規則として固定し、承認の digest で結ぶ。コードの変更で、承認を外さずに送る値が変わることをなくすためである。出どころの印（推した・人）を残すため、規則の Schema と digest の形の版を上げる。
- **推せない欄**: `RANGE_MISSING`・`SEMANTIC_KIND_UNDECIDED` などの欄は、一覧にして人に入れさせる（今の規則の画面）。
  - 範囲のない日付と数には、既定の幅を入れる（ユーザーの判断 2026-10-22。Task 29 の設計書 10 章の 3「基準日から推さない」を、この場面について改める）。
    - 日付・日時: 基準日から 30 日後までの幅。
    - 数: 1〜100 の整数。
    - 名前つきの定数にする（`src/core/limits.ts` か規則の置き場所の 1 か所）。
    - 推測の印を付ける。
    - form の欄に min・max があるときは、今どおりその範囲を使う（既定の幅は、範囲の手がかりがないときだけ）。
    - サイトの検証で拒まれたとき（4xx）は、今どおり `INPUT_ERROR` → `FAILED` になる。人が直せるよう、規則の画面に既定の幅を使った欄を出す。
- **手がかりを足す**:
  - API の鍵の制約を、form の中の候補の欄から name で結んで補う。
  - 「番号・コード」の意味の種類を足す。単純な pattern（数字だけの桁数など）から作る。
  - label と placeholder は発見の記録に足さない（サイトの語と秘密が残る範囲が広がるため）。

### 3A.4 1 回の操作で自動ログイン（P2-6）

- **形**: 手動のログインが成功した後の「次から自動でログインする」から、1 つの画面へ進む。その画面で、次の 3 つを見せ、確認 1 回で保存する。
  - 認証の方式の変更
  - ログインの 3 つのセレクタ（案つき）
  - 資格情報の入力（人が入れる）
- **資格情報**: パスワードは人が画面で入れる（Task 26 の決まりのまま。平文は保存の要求の処理の間だけ持つ。画面に出さない）。
- **セレクタの出どころ**: 手動のログインの段の始めの観察に、ユーザー名・パスワード・送信のボタンの欄の検出を足す（値は読まない）。各欄の候補がちょうど 1 つのときだけ、案にする（推測の印）。
- **保存の順**:
  1. 全部を確かめる。
  2. 資格情報のファイルを書く。
  3. 管理データ（方式とセレクタ）を 1 つのトランザクションで書く。管理データで失敗したら、資格情報のファイルを消す。
- **その後**: 「ログインを確かめる」は自動で始めない。画面にボタンを出す（自動ログインの 5 分の間隔と、24 時間に 10 回の上限に数えるため）。

### 3A.5 ユーザーに諮った点（2026-10-22 の判断）

判断は、次のとおり。

1. 「状態はメモリだけ（推奨）」。案 b' を採る。
2. 「ボタン 1 回で作る（推奨）」。
3. 「人が必ず選ぶ（推奨）」。
4. 「既定の幅を入れる」。

問いは、次のとおり。

1. まとめて実行の形: 案 b'（状態はメモリだけ）でよいか。案 a（ジョブの間で状態を引き継ぐ）は、仕様と I22 を緩めることになる。
2. 下書きを作る時: ボタン 1 回か、発見の終わりに自動で作るか。
3. 更新の変える鍵: 人が必ず選ぶか、BeakSight が案を選んでおくか。
4. 範囲のない日付と数: 人が入れるか（Task 29 の判断のまま）、既定の幅を入れるか。

## 4. 受け入れ条件（第 1 段）

1. 「登録する」を押すと、確認の後にその場で保存され、画面は移らない。成功の鍵が入る。保存の誤りは出ない（fixture の記録で）。
2. 表示の設定が既定で表示で、監査・発見・READ・書き込みのジョブのブラウザが表示で起動する。切り替えても、プロファイルの改訂と承認は変わらない。表示しても、Guard の回帰（両方の Chromium）が通る。
3. 手動のログインの成功の後に「次から自動でログインする」が出て、資格情報を登録すると、次のジョブが自動ログインで始まる（偽のワーカーと、自動ログインの今の結合）。
