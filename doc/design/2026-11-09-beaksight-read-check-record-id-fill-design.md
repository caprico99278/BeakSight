# BeakSight 番号の入る画面の READ の確かめで、番号を自動で埋める（DEF-235）設計書

- 日付: 2026-11-09
- 状態: ユーザーの方向の判断済み（下の 2）。細部は設計者の既定
- 関係する文書: `2026-10-17-beaksight-task-38-api-scenario-approval-design.md`、`2026-10-20-beaksight-service-request-pacing-design.md`、`2026-11-04-beaksight-login-session-design.md`
- 調査: INV-235（2026-11-09。コードを読んで特定した）

## 1. 目的

書き込みの画面でチェックを入れると、自動の下書きは「登録した後に開く画面の型」（番号の入る path。例 `/<一覧>/{id}`）の READ の確かめを作る。この型の定義が、続けての点検の READ の確かめの段にも入り、番号がないため毎回 `URL_NOT_BUILT`（「見る前に止めた」）で終わる。

原因（INV-235）:
- 単独の READ の確かめで読む定義を選ぶ所（`audit-job-manager.ts` の `standaloneReadChecksOf`）は、`verificationOnly` の印の定義だけを外す。型の定義には印が付かない。
- 番号を埋めるのは、書き込みの段の照合だけ。

## 2. ユーザーの判断（言葉どおり）

- 「DEF-234、DEF-235も修正対象として。」
- 「DEF-235の番号が足らない場面も普通にある。断らないで」（2026-11-09）。断る・外す案は採らない。利用者に番号を入れさせない。

## 3. 採用する設計

### 3.1 番号の元（近い順。親が選ぶ）

1. **同じ連鎖の操作さがしで読み切れた、同じ型の画面**（`discovery_jobs.read_page_paths` の最新。`recordIdOfPathPattern`・`isUsableRecordId` で型に当てる）。
2. **同じ連鎖の点検の段のリンク**（`readAuditStageLinks`。例外を投げない部品で読む）。
3. **書き込みで作った登録の ID**（この定義に結んだ CREATE のシナリオの `write_results.record_id`。VERIFIED、新しい順）。

同じ元の中では、前の回に使った番号が今回の元にもあればそれを使い、なければ見つけた順の先頭を使う（比べる結果を安定させるため）。番号の形は `isUsableRecordId` と `isRecordIdLikePathSegment` で確かめる。

### 3.2 どれからも取れないとき（ワーカー）

1. 型の `{id}` の前までの path（一覧の画面）を 1 回読み、凍結の後にリンクを取り（`discoverLinks`）、型に当たる最初の番号の画面を読む。
2. 同じ一覧の画面は、定義が複数あっても 1 回にまとめる。
3. 一覧の画面がない・番号のリンクがないときは、断らずに新しい理由 `RECORD_ID_NOT_AVAILABLE` を残す。結果の区分は「判定できない」。画面の文は 1 文だけ（例:「見る登録がまだないため、見ていません。」）。利用者に手を求めない。

### 3.3 読む範囲と安全

- 埋めた URL は、照合の READ と同じ部品 `recordPageReadTargetOf` で確かめ直す（正規の形、Origin と型の一致、読まないパス、`isReadUrlAllowed`）。外れたら読まない（`REQUEST_POLICY`）。
- 読み込みは GET だけ。一覧の画面の読み込みも、同じ判定・pacer・Guard・監査の段の要求の上限と時間の上限を通す。

### 3.4 型の定義の期待

自動の下書きが型の定義に入れた期待（`ROW_COUNT_AT_LEAST 1`）は仮の値で、詳細の画面には表がないことが多く、`STRUCTURE_NOT_FOUND`（判定できない）が続く。

- **設計者の既定:** READ の確かめの段で読む型の定義（自動の下書きが作ったもの）は、「画面が開けて（2xx、ログインの切れでない、エラーの画面でない）」を一致とする。行の数の期待は、書き込みの段の照合（送った値が出ているか）で今のとおり使う。
- 利用者が手で書いた期待は、今のまま照らす。

### 3.5 書き込みの段

書き込みの段の照合（作った番号を入れて読む）は変えない。

## 4. サイトへの負荷

- 1 つの型の定義につき、読み込みは最大 2 回（一覧の画面 1 回 + 詳細の画面 1 回）。元 1〜3 で埋まれば 1 回で、今と同じ。
- 間隔は今の pacer のまま（最小の間隔はプロファイルの `crawl.minNavigationIntervalMs`。既定 5 秒、作成の下書きは 10 秒）。サイトの不調の確かめ直し（DEF-136）が付くと、最悪 1 定義 4 回。
- 1 回の段の全体の上限は `MAX_WORKER_READ_CHECKS` × 2 回の読み込み。

## 5. 限界

1. データが 1 件もないサイトは、`RECORD_ID_NOT_AVAILABLE` で「判定できない」（次の書き込みで登録ができれば、元 3 で埋まる）。
2. 選んだ番号の登録が、読む前に消されたときは、今の読み込みの結果（404 など）のまま。

## 6. テスト

- 単体: 元の選び方（1 → 2 → 3、前の回の番号の優先、形の確かめ）、型の定義の一致の決まり、`RECORD_ID_NOT_AVAILABLE`。
- 結合（2 つの Chromium）: 仮のサイト（一般の文言）で、続けての点検の READ の確かめの段が、型の定義を番号を埋めて読み「一致」になる。元がないときに一覧を 1 回読んで埋める。一覧に番号がないとき `RECORD_ID_NOT_AVAILABLE`。読み込みの数（サーバの記録）が上の上限の中。GET だけ。
- 既存の READ の確かめ・書き込みの照合のテストが通る。
