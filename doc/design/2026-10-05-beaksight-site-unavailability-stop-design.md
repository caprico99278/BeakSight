# BeakSight サイトが応答しないときに Run を止める 設計書

- 状態: ユーザーの判断（2026-10-05）を反映した設計。実装の後に独立レビューを受ける。
- 関係する設計書: サイトへの負荷の制御の設計書（`2026-10-01-beaksight-site-load-control-design.md`）、中断した Run の再開の設計書（`2026-10-01-beaksight-resumable-run-design.md`）、Task 14〜17 の設計書（Page Auditor と Run Coordinator。再試行は 5.6.4）

## 1. 目的

### 1.1 起きたこと

- Task 21 の2回目（2026-10-05）で、監査の対象のサイトがメンテナンスに入り、応答しなくなった。BeakSight は、12ページ目でモバイルの読み込みが時間切れになった後も、13ページ目の読み込みを続けた（13ページ目のデスクトップも時間切れ、モバイルは取り消し）。応答できないサイトに、読み込みを送り続けた。

### 1.2 ユーザーの指示と判断（2026-10-05）

- 指示: 「タイムアウト後にページ読み込みが中断された場合もrun自体が終了せず、続行したことも問題と考える」
- 判断（AskUserQuestion）:
  - 止める時点: 「最初の1回で止める」。サイトの不調による失敗が1回でも起きたら、そのページの残りの読み込みも、新しいページも始めずに止める。
  - 止めた後: 「再開できる状態で止める」。確認できた範囲の結果を書き出して止め、同じコマンドで続きから再開する。応答がなくて失敗したページは、再開のときに監査し直す。

### 1.3 解決すること

- サイトの不調を検知したら、それ以上の読み込みを送らない（サイトへの負荷の方針。メモリの「監査対象のサイトに過負荷を与えない」）。
- 不調で止めた Run を、サイトが戻った後に、同じコマンドで続きから再開できるようにする。

## 2. 判定（サイトの不調とみなす失敗）

- 対象: BeakSight が自分で始める、main frame の読み込み（Passive の各ビューポート、幅の走査の各幅、Interaction の各候補の読み込み、robots.txt と sitemap.xml の取得）。ページの部品（画像など）の要求や、許可 Origin の外への要求は、対象にしない。
- 次のどれかに当たれば、サイトの不調とみなす（閉じた一覧）:
  1. 読み込みの時間切れで、main frame の最後の文書の要求に、応答（ヘッダ）を1つも受けていないもの（2.1 の観測の `httpStatus` が `null`）。応答を受けた後の時間切れ（本文や部品が遅い。`domcontentloaded` は同期の外部のスクリプトで、`load` は遅い部品で遅れる）は含めない（2.2。2026-10-05 改訂）。
  2. ネットワークの層の失敗（`navigationOutcome` が `FAILED` で、失敗の詳細が、既存の閉じた一覧 `isNetworkLayerFailure`（`src/safety/network-layer-failure.ts`）に当たるもの。接続の拒否・リセット・失敗、名前解決の失敗、証明書の失敗など）。
  3. main frame の最後の文書の応答の HTTP の status が 429（要求が多すぎる）、502、503、504（読み込みが終わった場合も、時間切れの場合も）。名前付きの定数の閉じた一覧にする（`SITE_UNAVAILABLE_HTTP_STATUSES`）。500 は、そのページだけの不具合のことが多いので含めない。
- 含めないもの: `net::ERR_ABORTED`（ブラウザやページの都合でも起きる。DEF-027 で別に扱う）、`BLOCKED_EXTERNAL_REDIRECT`、4xx（429 を除く）、500。
- 判定の owner: 新しいファイル `src/orchestration/site-availability.ts`（例: `siteUnavailabilityOf(observation)`。入力は 2.1 の観測。不調なら、種類と詳細（例: `TIMEOUT`、`FAILED:net::ERR_CONNECTION_RESET`、`HTTP 503`）を返し、そうでなければ `null`）。ほかの場所に同じ判定を書かない。

### 2.1 main frame の読み込みの観測（2026-10-05 追補）

- 4か所の読み込み（Passive の `navigatePage`、幅の走査の `collectStressLayout`、Interaction の `loadInteractionTarget`、robots.txt と sitemap.xml の `fetchMetadata`）は、待ち方（`domcontentloaded`、`load`、期限の競争）が違う。判定に使う観測を、同じ形にそろえる。
- 観測の型（例: `MainFrameLoadObservation`）: `navigationOutcome`（`OK`、`TIMEOUT`、`FAILED`）、`httpStatus`（main frame の最後の文書の要求の応答の status。応答を受けていなければ `null`。時間切れと失敗の場合も、受けていれば入れる）、`failureDetail`（失敗の上限付きのメッセージ。`OK` なら `null`）。
  - 時間切れ: Playwright の期限切れ（`isPlaywrightTimeoutError`）と、期限の競争（`awaitBeforeDeadline` の `DEADLINE_EXCEEDED`）。
  - 失敗: それ以外の `goto` の失敗。Guard が遮断した外部へのリダイレクト（`BLOCKED_EXTERNAL_REDIRECT`）も、観測では `FAILED` になる（`net::ERR_BLOCKED_BY_CLIENT` なので、不調ではない）。
- 「最後の文書の要求の応答」は、page の要求と応答の事象で、main frame のナビゲーションの要求を追って知る（リダイレクトでは、新しい要求が来たら、前の応答を忘れる）。追う部品と観測の型の置き場所は `src/browser/main-frame-load.ts`（新設。collector と Interaction から使うので、`src/orchestration/` には置かない）。
- 観測を作るのは、この部品だけにする。4か所の読み込みは、この部品で観測を作り、Passive は結果に持たせ、ほかの3か所は、注入された受け口（例: `afterNavigation(observation)`）に渡す。判定は、受け取った Page Auditor と Run Coordinator が、`siteUnavailabilityOf` で行う。

### 2.2 判定を限る理由（2026-10-05 追補）

- 1回の不調で Run を止めるので、判定が広すぎると、動いているサイトでも止まる。止まったページは再開で監査し直すので、そのページで毎回止まり、Run が先へ進めなくなる。
- 応答を受けた後の時間切れは、そのページの重さ（同期の外部のスクリプト、遅い部品）で毎回起きうる。サイトのメンテナンスでは、応答が来ないか、503 などが返る（Task 21 の2回目の記録でも、時間切れの要求は、時刻がすべて -1 で、応答がなかった）。
- 応答を受けた後の時間切れは、今までどおり、そのページの失敗（`NAVIGATION_FAILED:TIMEOUT`、幅の走査や Interaction の理由）として記録し、Run を続ける。
- 既知の限界（SU2a の実装者と SUR のレビュー担当の事実。2026-10-05 改訂）: Playwright の応答の事象は、ヘッダではなく、本文の最初の部分を受けてから出る（`text/html` では、本文の始まりから約 0.5 秒後。`Content-Type` がなければ数 ms）。そのため、観測の「応答を受けた」は、実際には「本文の始まりを受けた」である。
  - ヘッダだけを送り、本文を期限まで1バイトも送らないページは、受けた時刻によらず、応答のない時間切れ（不調）と判定される（503 でも、status は `null` のまま）。
  - 本文の始まりが期限の直前の約 0.5 秒に届いた場合も、不調と判定されうる。
  - どちらも、サーバが本文を返せていない状態なので、止めることは負荷の方針に合う。そのページで止まり続けることは、3.2.1 の決まりで防ぐ（そのページにつき、起動が最大2回余分にかかる）。
  - テストで、本文の後の時間切れを確かめるときは、本文の始まりを送り、期限を 2 秒以上にする。

## 3. 止め方

### 3.1 ページの中（Page Auditor）

- 読み込みのたびに、2章の判定を行う。不調なら、そのページの残りの読み込み（次のビューポート、幅の走査の次の幅、Interaction の次の候補）を始めない。
  - 幅の走査は、次の幅のセッションを作る前に確かめ、不調なら作らずに段階を止める（違反で止めるのと同じ形。理由は `stress-layout:SITE_UNAVAILABLE`）。
  - Interaction は、次の候補の前に確かめ、不調なら止める（理由は `interaction:SITE_UNAVAILABLE:remaining=<件数>`）。
  - 次のビューポートは始めず、理由 `SITE_UNAVAILABLE`（`detail` は `null`）の SKIPPED にする（違反で始めなかったビューポートと同じ形）。違反と両方なら、違反の SKIPPED を優先する。
  - 不調を検知したビューポートには、理由 `SITE_UNAVAILABLE`（`detail` は `<段階>:<判定の詳細>`。例: `passive:TIMEOUT`、`stress-layout:HTTP 503`）を1件加える。
  - Passive の読み込みで不調を検知したら（503 などで読み込みが `OK` の場合も）、そのビューポートの収集（DOM の準備の待ち、controlled scroll、各 collector）を行わず、ビューポートを FAILED にする（2026-10-05 改訂。scroll などで、ページの部品の読み込みがさらに起きるのを避ける。中身はメンテナンスのページで、監査の意味がない）。network と console の Evidence と、Safety の Evidence は、今までどおり記録する。
  - 幅の走査か Interaction で不調を検知したら、その段階の残りを止め、新しい読み込みをしない残りの段階（配色、スクリーンショットなど）は、今までどおり行う。
  - 幅の走査か Interaction の読み込みが `OK` で 429・502・503・504 だった場合、その幅のレイアウトの収集や、その候補の下準備（scroll、hover、候補の探し直し）は、今までどおり行う（SUR の指摘 M3 への判断。2026-10-05）。新しい main frame の読み込みではなく、増える要求は、その1ページの部品に限られる（Interaction の凍結の後は送られない）。Passive では収集を止めるのと一貫しないが、受け口から止める合図を返す仕組みを足すほどの効果はないので、受け入れる。
  - ページの結果（`PageAuditOutcome`）に、最初に検知した不調の詳細（例: `siteUnavailableDetail`。形は `<ビューポート>:<段階>:<判定の詳細>`。例: `desktop:passive:TIMEOUT`。不調がなければ `null`）を持たせる。Run Coordinator は、これを Run の理由ときっかけのページの `detail` に使う。詳細の組み立ては、`site-availability.ts` の1か所で行う。
  - Desktop で不調を検知したら、再試行の判断（`precedesRetry`）を呼ばない（次のビューポートを始めないため）。
- そのページの結果に、不調で止めたこと（どの段階・どのビューポートで、どの失敗か）を持たせる。
- robots.txt と sitemap.xml の取得で不調なら、Run Coordinator は、ページの監査を始めない。robots.txt で不調なら、sitemap.xml を読み込まない（読み込みの前の待ちの受け口で止める。読み込まずに `FAILED`）。不調で止めた場合は、取得の結果を保存しない（再開のときに、取得し直す）。

### 3.2 Run（Run Coordinator）

- ページの結果に不調の印があれば、そのページは「終わったページ」にしない。巡回の記録で、理由 `SITE_UNAVAILABLE` の SKIPPED にする（再開のときに待ち行列に戻す。`RESUME_REQUEUE_SKIP_REASON_CODES` に加える）。`detail` は、最初に検知した失敗（Run の理由と同じ形）にする。始めなかったページの `detail` は `null` なので、`detail` のあるものが、止まるきっかけのページである（3.2.1 で使う）。ページの保存（`savePage`）もしない。
  - そのページで作った Safety Ledger の snapshot は、捨てない。ページの外の Ledger の snapshot と同じく、状態の保存に入れ、最後の処理の Safety の集計に含める（再試行の前の試行の Ledger と同じ考え方）。
  - そのページは、ページ数の上限（`maxPages`）の数え方（`pagesStarted`）から外す（再開で監査し直すときに、二重に数えないため）。
  - そのページの結果からは、Link を拾わない（再開で監査し直すときに拾う）。そのページの再試行の記録（`retries` と、再試行の前の試行の Evidence）も消す（ページの結果がないので、記録の `evidenceIds` の行き先がなくなるため）。
  - そのページで違反も検出していた場合（ページの Ledger の違反。`#detectSafetyViolation` の今のページの確かめ）は、ページを捨てずに、今のとおり普通の結果として保存し、違反で止める（違反の Evidence をページに残すため。違反の優先）。
  - 捨てたページの、スクリーンショットのファイル（幅の走査や Interaction で検知した場合は、撮った後のことがある）は、消さなくてよい。再開で同じ `pageId` で監査し直すと、同じパスに書き直される。再開しない場合も、Evidence から参照されないファイルが残るだけである（成果物の確かめは、参照されたファイルがあることを確かめる）。
  - 捨てた後に、状態を保存する（理由と `detail` のある SKIPPED を、途中で止まった場合にも残すため）。
- 残りの URL も、理由 `SITE_UNAVAILABLE` の SKIPPED にし、新しいページを始めない（止める理由の確かめの順は、違反、保存の失敗、サイトの不調、ページ数、実行時間、止める印）。
- Run の理由に、`SITE_UNAVAILABLE` を1件加える。`detail` は、最初に検知した失敗（例: `desktop:passive:TIMEOUT`、`mobile:passive:HTTP 503`、`site-metadata:TIMEOUT`）。この理由は、この実行で検知した不調から、最後の処理で作る（実行時間の上限や止める印の理由と同じく、保存の理由（`progress.reasons`）には入れない）。再開した実行で不調を検知しなければ、この理由は残らない（2026-10-05 追補）。
- Run Status は、SKIPPED のページがあるので `PARTIAL`（`deriveRunStatus` は変えない）。
- 実行の終わり方に `STOPPED_BY_SITE_UNAVAILABLE` を加える（`RUN_EXECUTION_END_REASONS`、両方のスキーマ、表示カタログ）。終わり方の決め方の順は、違反、サイトの不調、実行時間の上限、止める印。保存の状態は `STOPPED`（再開できる）。規則は `run-checkpoint.ts` の `decideRunExecutionEndReason` と `decideRunCheckpointConclusion` の1か所に加える。
- 違反が同じ実行で起きていれば、今のとおり違反を優先する（`FINISHED`。再開しない）。 不調を検知したページで違反も検出した場合は、Run の理由に `SITE_UNAVAILABLE` を入れない（違反の Run は再開しないので、「再開します」の表示を出さないため。SU3a の実装者の判断を設計者が受け入れた）。

#### 3.2.1 同じページで止まり続けないための決まり（2026-10-05 追補）

- 1つのページだけが、いつも応答しない（そのページの生成が遅く、期限までにヘッダが来ないなど）場合、そのページで止まり、再開でそのページから監査し直して、また止まる。Run が先へ進めない。
- そのため、前の実行で止まるきっかけになったページ（再開の前の保存で、理由 `SITE_UNAVAILABLE` の `detail` のある SKIPPED）が、この実行で、また止まるきっかけになった場合は、そのページを普通の結果（`NAVIGATION_FAILED` などの FAILED か PARTIAL）として保存し、`pagesStarted` にも数える。Run は、今までどおり止める（最初の1回で止める決まりは変えない）。次の再開では、そのページを監査し直さずに、次のページへ進む。
- 代償: サイトが戻る前に再開すると、そのページは、2回目の失敗で FAILED として残る。この決まりを README に書く（再開は、サイトが戻ってから行う）。
- robots.txt と sitemap.xml の段階も、同じ考え方にする。前の実行の終わり方が `STOPPED_BY_SITE_UNAVAILABLE` で、保存に取得の結果がない（その段階で止まった）場合に、この実行の取得で、また不調を検知したら、取得の結果（`FAILED` の記録）を保存して止める。次の再開では取得し直さずに、ページの監査へ進む（2026-10-05 追補）。
- 前の実行のきっかけのページは、再開の入力の保存（巡回の記録）から、Run Coordinator が実行の初めに1回だけ読み取る。保存の形（スキーマ）は変えない。

### 3.3 再試行との関係

- 今の再試行（Desktop の読み込みの時間切れと、一時的な接続の失敗のとき、同じページを1回だけ読み込み直す。Task 14〜17 の設計書 5.6.4）は、どれも2章のサイトの不調に当たる。ユーザーの判断（最初の1回で止める）により、これらの失敗では再試行せずに止める。
- そのため、今の再試行の対象の失敗のうち、接続の一時的な失敗（`CONNECTION_RESET`、`CONNECTION_CLOSED`、`EMPTY_RESPONSE`、`NETWORK_CHANGED`。どれもネットワークの層の失敗）と、応答のない時間切れは、止める側に入り、再試行しない。
- 応答を受けた後の Desktop の時間切れ（2.2）は、サイトの不調ではないので、今までどおり1回だけ再試行する（2026-10-05 改訂）。Run Coordinator は、ページの結果に不調の印があれば、再試行の判断より先に止める。
- 再試行の仕組み（`run.json` の `retries` を含む）は、この設計では消さない。

### 3.4 表示と README

- 理由 `SITE_UNAVAILABLE` の説明と、終わり方 `STOPPED_BY_SITE_UNAVAILABLE` のラベルと説明を、`messages.ts` と表示カタログに加える。
- CLI の結果に、不調で止めたときの1行を加える（例: `サイトが応答しないため、監査を止めました（<詳細>）。サイトが戻ったら、同じコマンドで続きから再開します。`）。出す条件は、この実行の終わり方が `STOPPED_BY_SITE_UNAVAILABLE` であること（Run の理由ではなく終わり方で決める。きっかけのページが最後の URL で、また不調だった場合は、Run を終えるので出さない）。
- README の「中断と再開」に、サイトの不調で止まる場合を加える（判定の一覧、止め方、再開）。「サイトへの負荷」にも、不調のときに読み込みを止めることを書く。
- README の「中断と再開」に、headed の Run では、ブラウザの画面を閉じたり、停止・再読み込みしたりしないこと、止めるときは端末で Ctrl+C を使うことを書く（DEF-027 のユーザーの判断。2026-10-05）。

### 3.5 1 回だけ確かめ直す（2026-10-07 追補。ユーザーの判断）

#### 3.5.1 起きたこと

- 2026-10-07 の Task 21 の再開で、60 ページ目の Interaction の候補の読み込みが、要求のヘッダを送った後、30 秒応答を受けずに止まった（拡張した観察で確かめた。分類 B）。同じ時刻に、利用者の普段のブラウザではサイトを閲覧でき、同じページの直前 5 回の読み込みは正常だった。サイト全体の停止ではなく、個々の要求がサーバ側で応答されない形である。
- 最初の 1 回で止める決まりでは、このたびに起動し直すことになる。ユーザーの判断（2026-10-07）: 「応答がないときは 1 分待って 1 回だけ確かめ直す」。

#### 3.5.2 決めたこと

- ページの段階（3.2）で、ページの結果に不調の印があり、違反がない場合:
  1. 今までどおり、そのページを捨てる（SKIPPED、保存しない、Link を拾わない、`pagesStarted` から外す、Ledger の snapshot を残す、再試行の記録を消す、状態を保存する）。捨てた試行の診断のファイルを書く（2.3。ファイル名に試行の番号を加える）。
  2. **その実行で、このページがまだ確かめ直されていなければ**、`SITE_UNAVAILABLE_RECHECK_DELAY_MS`（60,000。定数。設定にしない。設定の項目を増やすと、今の途中の Run を続きから再開できなくなるため）だけ待つ。待っている間は、サイトへ何も送らない。待ちは、止める印（Ctrl+C）で打ち切る。待った時間は、実行時間の上限に含める。
  3. 待った後、止める印がなく、実行時間の上限に達していなければ、同じページ（同じ `pageId`）を、もう 1 回だけ監査する（通常の監査と同じ。pacer の待ちも通る）。
  4. 2 回目に不調の印がなければ、通常どおり結果を保存して先へ進む。Run の理由には何も残さない（確かめ直したことは、捨てた試行の診断のファイルに残る）。
  5. 2 回目も不調なら、今までどおり止める（`siteUnavailableDetail` は 2 回目のもの。2 回目の診断のファイルも書く）。
- 巡回の記録（`CrawlFrontier`）は、`QUEUED → AUDITING` の遷移しか受け付けないので、確かめ直しのための専用の操作（例: `requeueForRecheck(url)`。理由のコードが `SITE_UNAVAILABLE` で `detail` のある `SKIPPED` を、待ち行列を通さずに `AUDITING` に戻す）を加える。`snapshot`・`restore`・保存の形は変えない（SU5 の Blocker への判断。2026-10-07）。
- 前の実行のきっかけのページ（3.2.1）の扱いは変えない（また不調なら、確かめ直さずに普通の結果として保存して止める）。
- robots.txt と sitemap.xml の段階（SU3b）は、確かめ直さない（今までどおり止める）。
- 確かめ直しは、1 つの実行の中で、ページごとに 1 回まで。確かめ直しで通ったページが、その実行の後のページで不調になった場合は、そのページで改めて 1 回確かめ直す。

#### 3.5.3 代償と安全

- 増える要求は、不調のページの監査 1 回分（最大で読み込み 25 回）だけで、60 秒の間をおく。サイトが止まっている場合は、2 回目もすぐ（最初の読み込みの時間切れで）止まる。
- 安全の不変条件は変えない（Guard、違反の優先）。

#### 3.5.4 表示と README

- CLI の進み具合に、確かめ直しを知らせる 1 行（例: `サイトが応答しないため、60 秒待ってから同じページを 1 回だけ確かめ直します（<ページの URL>）。`）を出す。文言は `messages.ts`。
- README の「サイトが応答しないとき」に、確かめ直しの決まりを書く。

## 5. テスト設計

- 判定（単体）: 一覧のそれぞれ（応答のない `TIMEOUT`、ネットワークの層の失敗の代表、429・502・503・504。時間切れで 503 を受けていた場合も）で不調。`OK` の 200・404・500、応答を受けた後の `TIMEOUT`、`ERR_ABORTED`、`ERR_BLOCKED_BY_CLIENT` で不調でない。
- 観測（実際の Chromium とローカルのサーバ）: 応答しないサーバで、時間切れ、`httpStatus` が `null`。ヘッダの後に本文を止めるサーバで、時間切れ、`httpStatus` が 200。503 で `OK`、503。接続を拒むと `FAILED`、`net::ERR_CONNECTION_REFUSED`。リダイレクトの後の文書が応答しないと、`httpStatus` が `null`（リダイレクトの 3xx を残さない）。
- Page Auditor（単体と結合）: デスクトップの Passive が不調なら、モバイルの読み込みを始めない。幅の走査の途中、Interaction の途中で不調なら、次を始めない。
- Run Coordinator（単体）: 不調のページが SKIPPED（`SITE_UNAVAILABLE`、`detail` は最初の失敗）になり、保存されず、`pagesStarted` に数えられない。残りも SKIPPED（`detail` は `null`）。Run の理由、`PARTIAL`、終わり方 `STOPPED_BY_SITE_UNAVAILABLE`、保存の `STOPPED`。robots.txt と sitemap.xml の不調で、ページを始めず、取得の結果を保存しない。違反と同時なら違反が優先。不調のページで再試行が起きない。応答を受けた後の時間切れは、今までどおり再試行する。前の実行のきっかけのページが、また不調になったら、普通の結果として保存して止め、次の再開でそのページを監査しない（3.2.1）。
- 結合（ローカルの fixture）: 監査の途中で、サーバが応答しなくなる（または 503 を返す）と、そのページの残りと次のページの読み込みがサーバに届かない。サーバを戻して同じ設定で再開すると、不調だったページから監査し直し、最後まで終える。中断しなかった Run と、ページの一覧と状態が同じ。
- 既存のテスト: 再試行のテストは、新しい決まり（止める）に合わせて直す（決まりの変更による直し）。

## 6. 対象外

- 不調の後に、自動で待って再開する仕組み（再開は、利用者が同じコマンドを実行したときに行う）。
- `net::ERR_ABORTED` の扱い（DEF-027）。
