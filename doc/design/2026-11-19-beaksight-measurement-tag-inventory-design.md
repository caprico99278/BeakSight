# 計測タグの一覧と、根拠・限界の印（改善提案 BS-01・BS-05。追補設計書、2026-11-19）

## 1. 目的
- ユーザーの改善提案書（2026-11-19。外の文書。サイトの名前・識別子は伏せる）: 取得済みの通信の証拠に複数の計測タグ（タグの管理の入れ物・広告・分析）の読み込みが記録されていたが、計測の構成の確認が要る候補として表に出なかった。
- ユーザーの判断（2026-11-19）: BeakSight は事実の一覧だけを作り、束とレポートに入れる。候補の文章は後段の意味の監査（ChatGPT）で作る。事業の目的の設定（BS-04）と外の行動データの照合（BS-06）は今回は入れない。順は AUD-1〜6 の後に BS-01・BS-05、次に BS-02・BS-03。
- 設計の決まり（実装タスク指示）: Collector は Finding を作らない。意味や良し悪しを Finding にしない。この一覧は Finding でなく、Run の事実の集計にする。

## 2. 決まり
### 2.1 計測サービスの閉じた一覧（1 か所）
- `src/core/` の 1 つのファイルに、計測サービスの一覧を閉じた表で置く。行ごとに: サービスの種類の ID（例 `TAG_MANAGER`・`GOOGLE_TAG`・`ANALYTICS_COLLECT`・`ADS_CONVERSION`・`META_PIXEL`・`CLARITY` など）、ホストと path の型、識別子を取る query の名前か path の位置、識別子の形（例 `GTM-` で始まる英数字）。
- 一覧にない外部のスクリプトは数えない（推測で計測と決めない）。一覧は汎用の外部サービスで、点検の対象のサイトの名前は書かない。
- 識別子は公開のページの通信に出る値なので、成果物（page.json と同じ扱い）に残す。Git の管理の対象のファイル（テストの fixture を含む）には、実在のサイトの識別子を書かない（作り物の値を使う）。

### 2.2 一覧の作り方（表示用モデルで 1 回だけ）
- 確定した Run から、表示用モデル（`src/report/view-model.ts`）を組み立てるときに 1 回だけ集計する。HTML・CLI・束は描くだけ（数え直さない）。
- 元: 各ページの各ビューポートの通信の Evidence の `requests`（と `repeatedReads` の最初の 1 件の URL・数）。応答の状態・失敗は、同じ requestId の `responses`・`failures` から。
- 1 行 = （サービスの種類, 識別子）。持つもの:
  - 観測したページの ID の一覧（点検の順）と数、ビューポートごと（desktop・mobile）の観測の有無。
  - 要求の種類（メソッド・resourceType）ごとの数と、結果（応答の状態の番号の分け方: 2xx・3xx・4xx・5xx・失敗・BeakSight が止めた）の数。止めたかは Safety の記録（止めた要求の記録）と照らす。
  - 根拠の参照: 代表の Evidence の ID と page.json の場所（最初に観測したページ・ビューポート）。
  - 検出元: `NETWORK_REQUEST`（1 版目はこれだけ。DOM の中の記述からの検出は行わない＝限界）。
- サイト全体で同じ構成が繰り返されるときは、1 行が全ページをまとめる（ページごとに行を作らない）。
- 「構成の要約」: 種類ごとの識別子の数（例: タグの管理の入れ物 4、広告 1、分析 1）。複数の入れ物があるかは数の事実として出すだけで、良し悪しや「二重計測」は書かない。

### 2.3 根拠と限界の印（BS-05）
- 一覧に、Run の限界を事実で付ける（表示用モデルの今の値を使う。新しく数え直さない）:
  - Run の状態（`PARTIAL` なら、点検できなかったページの数・理由の数。AUD-1 の `failedPageCount`・`uncollectedPageCount`）。
  - 監査の送信の扱い（`READ_ONLY` なら「計測の送信は BeakSight が止めたので、送信の成否は分からない」。`PASS_EXCEPT_DELETE` なら「通したが、送り先で受け付けられたか・計上されたかは分からない」）。
  - 計測サービスのホストへの、BeakSight が止めた要求の数。
- いつも付ける文（messages の 1 か所。技術の語を避ける）: 「読み込みを観測した事実です。設置した人・設定の中身・成果の計上（重なり・漏れ）は確かめていません。」
- 束の README に、この一覧の読み方（事実と確かめていないことの区別、候補にするときに断定しないこと）を足す。

### 2.4 出す所
- ChatGPT 用の束: 新しいファイル（例 `measurement-tags.json`。第 1 部の要約の JSON と同じ部に入れる）。`bundleSchemaVersion` の扱いは、ファイルを足すので上げるか、今の前例（項目の追加は上げない）で足りるかを実装者が確かめて報告する。
- HTML レポート: 短い節「計測のタグ（読み込みを観測したもの）」。種類・識別子・ページの数・パソコンとスマホの観測・限界の文。
- CLI の結果: 1 行（例「計測のタグ: 6 種類（読み込みを観測。詳しくはレポート）」）。0 件なら出さない。
- ローカルの画面: 出さない（利用者に技術の情報を出さない決まり）。

## 3. 負荷
- 新しい読み込み・要求はない（記録済みの Evidence の集計だけ）。

## 4. 版
- page.json は変えない。束はファイルを 1 つ足す。

## 5. 限界
- DOM の中の記述（埋め込みのスクリプトの設定）からの検出はしない。タグの管理の入れ物の中から読み込まれたか、直接の埋め込みかは区別しない。
- 送り先での計上・重なり・漏れ・設定の中身は分からない（BeakSight の責務の外）。

## 6. BS-1 の Blocker の判断（2026-11-19）
- Blocker: 成果物の書き手（`artifact-writer.ts` の `#outgoing`）が、記録した要求の URL の query の値をすべて伏せる（`redactRecordedRequestUrlsInValue`。T44g）。表示用モデルは伏せた後の Run から作るので、query で識別子を持つサービス（タグの管理の入れ物 `gtm.js?id=`・`gtag/js?id=`・分析の送信・広告の画素の `tr?id=`）の識別子が取れない（実際の公開の Run でも `gtm.js?id=[REDACTED]`）。
- ユーザーの判断（2026-11-19）: 識別子を残す（狭い例外）。
- 決まり:
  1. 伏せ字（`src/safety/redact.ts`）に狭い例外を 1 つ足す。query の値を伏せずに残すのは、次の全部に当たるときだけ: ホストと path が計測サービスの閉じた一覧（2.1。1 か所の owner）の行に合う、query の名前がその行の識別子の欄の名前、値がその行の識別子の形（例 `GTM-` の後の英数字だけ、`G-` の後の英数字だけ、`AW-` の後の数字だけ。長さの上限つき）に全部合う。どれかが合わなければ今どおり伏せる。
  2. 同じ URL のほかの query の値（`cx`・`gtm`・`random`・`dl` など）は今どおり伏せる。path の値に見える区切りの伏せ方も今のまま（一覧の行が path で識別子を持つときは、その位置と形に合うものだけ残す）。
  3. 例外は計測サービスの一覧の行だけに効く。認証つきの Run でも同じ（識別子はページに公開で書かれる値で、秘密でない）。承認したサービスの Origin の URL は、今の決まりのまま全部伏せる（例外を効かせない）。
  4. 一覧は 2.1 の閉じた表の 1 か所で、伏せ字の部品と表示用モデルの両方がそれを使う。
- 束の版: ファイルを 1 つ足すので `chatgpt-bundle/2.1` に上げる（`links.json` を足したときの前例）。
- 伏せ字の守りを変えるので、独立レビュー（実機と単体の両方で、トークン・利用者の ID・メールなどの値が例外で漏れないか）を受ける。
