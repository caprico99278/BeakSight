# BeakSight DEF-052 取り消しの証拠の待ちを、Node の処理の停止に強くし、証拠がなかった理由を記録する 設計書

- 状態: 設計者の判断（2026-10-09）。不具合の修正で、仕様の範囲は変えない。DEF-026 の設計書（`2026-10-05-beaksight-def-026-guard-canceled-document-design.md`）の 2 章を追補する。
- 対象: `src/safety/passive-request-guard.ts`（`CanceledDocumentRegistry`、`settlePausedDocumentCommand`、`CDP_CONTINUE_REQUEST_FAILED` と `CDP_FAIL_REQUEST_FAILED` の文書の要求の記録の箇所）
- 不具合台帳: 作業記録置き場の `defects.md` の DEF-052。調査: `DEF-052-fix-brief.md` とその報告（`progress.md`）

## 1. 起きたこと

- 混雑の下の全体の並行の実行で、iframe の `src` を 1 ms ごとに変えるページの Interaction の場面が、20 回中 1 回、`CDP_CONTINUE_REQUEST_FAILED`（`Invalid InterceptionId`）の違反 3 件で止まった。サーバに届いた POST は 0 件。
- 元のログの分析（事実）: 違反の 1 件目は、閉じる処理が始まる前（`goto` の途中、`PASSIVE_ACTIVE`）に記録された。つまり、文書の要求への命令の失敗に対し、取り消しの証拠が 500 ms の待ちの中で見つからなかった（または覚えられていなかった）。
- 再現の試み（事実）: 混雑の下で、Interaction の場面を headless shell で約 5,000 ラウンド、CLI の Chromium で約 1,000 ラウンド。再現 0 回。`Invalid InterceptionId` の失敗 約 71,600 件のすべてで、失敗の応答を受けた時点で証拠はもう届いていた。1 つの session の証拠の数の最大は 146（上限 256）。
- 原因の候補（どれも推測）:
  - (a) Node の処理が、待ちの間に 500 ms を超えて止まった（CPU の取り合い、GC）。止まりが解けると、Node は受信の処理より先にタイマーを動かすので、届いていた証拠を読む前に待ちが終わる。3 件がまとめて出たことと両立する。
  - (b) 証拠の数の上限 256 に届き、証拠を覚えられなかった。
  - (c) その要求の `Network.loadingFailed`（`canceled`、`Document`）が来なかった。

## 2. 方針

### 2.1 待ちの終わりに、届いている事象を読んでから決める（候補 (a) への対策）

- 証拠の待ちのタイマーが切れたとき、すぐに偽で決めない。Node がすでに受け取っている CDP の事象（session の事象の処理）を処理し終えてから、もう一度だけ証拠を見て決める。
- 実現の手段（`setImmediate` で何回譲るか、Playwright の中の事象の受け渡しの段数など）は、実装者が実験で確かめて選ぶ。条件は次のとおり。
  - 待ちの全体に上限がある（名前つきの定数。500 ms に足す時間は、Node の処理の数回分にとどめ、時間の長さでは決めない）。
  - 偽の harness で、「待ちの間に Node の処理を同期的に 500 ms を超えて止め、その間に証拠を受信の待ち行列に積む」順序を作ると、修正の前は違反、修正の後は違反にならない（RED と GREEN）。
  - 待ちの時間 500 ms、証拠の上限（256 件、5 秒）は変えない。
- これは決まりの緩和ではない。違反にしない条件（文言の一致、`networkId`、その要求の取り消しの証拠）は変えない。変わるのは「待ちの時間の中に届いた証拠を、Node の止まりのせいで読み落とさない」ことだけである。

### 2.2 証拠がなかった理由を、違反の文に付ける（候補 (b)・(c) の切り分け）

- `settlePausedDocumentCommand` が、`Invalid InterceptionId` の形の失敗を違反として投げ直すとき、違反の文の後ろに、決まった語だけで組み立てた診断を付ける。元の文言は変えずに先頭に残す。
- 診断の内容（閉じた語彙。値は数と決まった語だけで、URL やページの文字は入れない）:
  - 理由: `network-id-missing`（通知に `networkId` がない）、`closing-not-waited`（閉じる途中で待たなかった）、`session-cleared`（待つ間に session を閉じた）、`evidence-not-received`（待っても届かなかった）、`evidence-dropped-at-capacity`（その要求の証拠を、上限のために覚えなかった）
  - 待った時間（ms）と、実際に経った時間（ms）。両者の差が大きければ、Node の止まりがあったと分かる。
  - その session の、上限のために覚えなかった証拠の数の累計。
- 上限のために覚えなかった要求の ID は、上限つき（名前つきの定数）で覚えておき、`evidence-dropped-at-capacity` の判定に使う。覚えきれない場合は `evidence-not-received` に倒す（判定には使わず、診断だけに使う）。
- 違反の文の長さの上限（Safety Ledger の `#boundedText`）に収まる長さにする。違反の `code` は変えない。Safety Ledger のスキーマは変えない。
- 違反の文の文言に依存する処理（完全一致の照合など）がないことを、実装者が確かめる。あれば Blocker として止まる。

### 2.3 変えないもの

- 証拠なしで違反にしない案（文言だけで違反にしない）は、今回も採らない（DEF-026 の 2 章）。
- 閉じる処理が始まった後の `Invalid InterceptionId` の扱いも変えない。元のログでは、1 件目が閉じる前に記録されており、閉じた後の扱いを変えても直らないため。
- Document でない要求の扱い（DEF-042）、`failRequest` の閉じた失敗の扱い（DEF-045、DEF-050）。

## 3. 安全への影響

- 違反にしない条件は変わらない。2.1 は、すでに Node が受け取っている事象を読むだけで、待ちの全体には上限がある。2.2 は、違反の文に診断を足すだけである。
- 待ちの間も、その要求は Guard の作業の中で止まったまま（命令は失敗済み）で、ほかの要求の判定は今のとおり進む。

## 4. テスト設計

- 偽の harness（`tests/integration/passive-request-guard.test.ts` の既存の偽の CDP の仕組み）:
  - 2.1 の RED と GREEN（Node の処理を止める順序）。待ちの全体に上限があること（証拠が来ない場合は、今のとおり違反になり、上限の時間の中で決まること）。
  - 2.2: 各理由の文が付くこと。元の文言が先頭に残ること。URL などが入らないこと。
- 実機（127.0.0.1、両方の Chromium）: 既存の DEF-026、DEF-027、DEF-042、DEF-050 のテストが、変えずに PASS すること。混雑の下で DEF-050 の場面を繰り返して、違反 0（再現しないことは分かっているので、悪くしていないことの確かめ）。

## 5. 残ること

- 原因は確定していない。2.1 は候補 (a) にだけ効く。次に同じ違反が出たら、2.2 の診断で (b)、(c) と区別し、改めて設計する。DEF-052 は「対策と診断を入れた、原因は未確定」として台帳に残す。
