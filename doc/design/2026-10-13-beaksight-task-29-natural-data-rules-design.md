# BeakSight Task 29 LLM なしの自然な業務データの生成 設計書

作成日: 2026-10-13
状態: ユーザー承認済み（2026-10-13。10 章の 5 点と、電話番号の修正を含む）。G29 承認済み（2026-10-13）
対象範囲: シナリオ（Task 28）の送る欄に入れる値の規則（入力の規則）を作り、保存し、承認に縛る。規則から、欄の型と制約と小さな辞書と業務テンプレートに従う、自然で決定的な合成データを作る。**この Task でも書き込みは一切しない**（作ったデータを送るのは Task 30）

## 1. 目的

Task 30 の CREATE で送る値を、LLM を使わずに、型・選択肢・業務の決まり・欄どうしの関係に従って作る。同じ入力（seed）なら同じデータ、別の Run なら別のデータになる。作れない欄は推し量らずに `NEEDS_RULE_INPUT` で止め、決まりがぶつかれば `RULE_CONFLICT` で止める。メールや SMS が実際に届く値は作らない。

## 2. 根拠となる文書と、ロードマップからの読み替え

- 従う文書: ロードマップ `2026-10-09-beaksight-task-22-32-roadmap.md` の Task 29、7 章（合成テストデータの決定論的生成仕様）、1.2・1.3、3 章（I07・I09・I10・I13・I14）、5.1、6.3・6.5・6.6、8 章、9 章、13.4、ADR-008。Task 28 の設計書（入力の規則の参照の枠、承認の digest、再承認の判定）。
- 調査: 作業記録 `progress.md` の「T29 の調査」の行。
- ユーザーの判断（2026-10-13）:
  1. メールアドレスの欄は、配送されない予約のドメイン（`example.invalid`）の宛先だけを作る。電話番号の欄は、`090-0XXX-XXXX` の形（`090` の直後が `0`。通常の携帯電話番号として割り当てられていない形）だけを作る（2026-10-13 ユーザーの指示で改めた。初めは「電話番号は自動では作らない」）。
  2. BeakSight の登録を見分ける印（`BS-…` など）は付けない。一意性は値の組み合わせで作る。
  3. 小さな辞書（姓・名とフリガナ、架空の備考の文例、商品名）と、3 つの業務テンプレート（顧客・予約・商品）をリポジトリに置く。依存は増やさない。住所は初版では扱わない（人が値を入れる）。
- 読み替え:
  - ロードマップの seed の式 `stableHash(profileId, scenarioRevision, runId)` を、`stableHash(profileId, scenarioId, scenarioRevision, ruleSetDigest, executionGrantId)` と読む（シナリオの id と規則の digest がないと、別のシナリオや規則の変更で同じ値になりうるため。Run の id は書き込みのジョブの前には決まらないので、実行の許可の id を使う。許可は 1 回だけ使えるので、Run ごとに別の seed になる）。
  - 「READ から参照する選択値」は、この Task では発見した選択肢の値（候補の写し）と読む。READ の結果の値を使う生成は対象外（7 章の営業時間など）。

## 3. 採用する設計

- **規則の集まり（RuleSet）はシナリオごとに 1 つ**。欄ごとの規則（意味の種類、作り方、範囲、固定の値の一覧）と、欄どうしの関係（終了 > 開始、合計 = 単価 × 数量 など）を持ち、版を重ねる（追記だけ）。規則の集まりの digest を、シナリオの入力の規則の参照（Task 28）に付ける。規則の最新の版がシナリオの参照と違えば、`INPUT_RULES_CHANGED` で再承認（Task 28 の `currentFactsIn` が、規則の集まりの表から最新の版を読むように変える）。
- **規則の優先順位**（7 章）: 汎用の規則（型と制約から作れるもの）→ 業務テンプレート（顧客・予約・商品）→ 人の上書き。人の上書きが最も強い。テンプレートにサイト固有の値を書かない。
- **欄ごとの判定**（純粋な関数）: 送る欄すべてに規則が決まっていることを求める。required なのに送る欄に選ばれていない欄も `NEEDS_RULE_INPUT`。
  - 型と制約で決まる: number・range（min・max・step があるとき）、date・time 系（min・max があるとき）、color、select・radio・checkbox（発見した選択肢の値から。空の値と危険な語の値は除く）。
  - テンプレートか人の規則が要る: text・search・textarea（意味の種類が決まれば作る。決まらなければ `NEEDS_RULE_INPUT`）、pattern のある欄（単純な形（数字の桁数、英数字の長さ）以外は `NEEDS_RULE_INPUT`）、min・max のない number・date。
  - 作らない: password・file（送る欄にできない。DEF-094 で Task 28 の確かめに足す）、url（`NEEDS_RULE_INPUT`）、住所（autocomplete の住所系、名前の語。人の値だけ）。
  - メール（type `email`、autocomplete `email`、名前の語 mail・メール）: `<合成の局所部>@example.invalid` だけ。シナリオの副作用の確認 `NO_EXTERNAL_NOTIFICATION` が済んでいるときだけ作る。
  - 電話（type `tel`、autocomplete `tel*`、名前の語 tel・phone・fax・mobile・電話・携帯 など。2026-10-13 ユーザーの指示）: `090-0XXX-XXXX` の形だけを作る（`XXX-XXXX` の 7 桁を決定的に作る。欄の pattern・maxlength がハイフンを許さなければ `0900XXXXXXX` の 11 桁）。どちらの形も欄の制約に合わなければ、ほかの形（実在しそうな番号）に切り替えずに `NEEDS_RULE_INPUT`。CREATE ごとに、すでに作った番号（生成の履歴。Task 30 が送った記録から渡す）と重ならない番号を選ぶ（一意にする欄の組と同じ作り直し）。シナリオの副作用の確認 `NO_EXTERNAL_NOTIFICATION`（SMS や自動発信などの外部への通知が送られない設定であること）が済んでいるときだけ作る。人が値の一覧を入れた場合は、その一覧を優先する。注意（手順書に書く）: この形は公式に架空の番号として保証された番号帯ではなく、将来の割り当ての変更がありうる。電話番号を厳しく確かめるシステムでは登録に失敗しうる。そのときは別の形に切り替えず、入力の規則の確かめ（テスト環境で許される専用の番号、管理下のテスト用の回線の番号を人が入れる）を求める。電話を掛ける操作がなくても、顧客の登録を契機に SMS を送るシステムがありうるので、外部への通知の遮断は副作用の確認と Task 30 の設計で別に扱う。UPDATE で電話番号をどう扱うか（登録の時の番号を保つか、承認した新しい番号に変えるか）は Task 31。
  - 外部到達の欄（通知・SMS・メールの送信を求める checkbox など。名前の語 notify・sms・通知・配信 など）: 「送らない」側の値が選べれば選び、選べなければ `RULE_CONFLICT`。
  - 状態の欄（Task 27 の `hasStateField`）と、危険な語に当たる選択肢の値は使わない。
  - 既定の値がある欄（hasValue）: CREATE では規則の値で上書きする（UPDATE は Task 31）。
- **決定的な生成**（純粋な関数）: seed（2 章の式。SHA-256）から、カウンタつきの SHA-256 で整数の列を取り出し、辞書とテンプレートと範囲から値を選ぶ。`Math.random` を使わない。日時の基準日は実行の許可の発行日（Asia/Tokyo）で、seed と一緒に記録する。
- **一意性**（ユーザーの判断 2。印を付けない）: 規則の集まりに「一意にする欄の組」（テンプレートの既定: 顧客は氏名とフリガナ、商品は名前、予約は日付と開始と選択肢。人が変えられる）を持つ。生成の関数は、すでに使った値の組の集まり（Task 30 が送った記録から渡す）を受け取り、ぶつかればカウンタを進めて決定的に作り直す。名前つきの回数（`MAX_UNIQUE_RETRIES`）で作れなければ `RULE_CONFLICT`（組み合わせの数が足りない）。
- **辞書**（ユーザーの判断 3）: 姓・名とそのフリガナ（各 30〜50 件、ありふれたもの）、架空の備考の文例（短い文、10〜20 件）、商品名（10〜20 件）を、JSON のデータとしてリポジトリ（`src/control/data-rules/dictionaries/`）に置く。実在の人や会社を指さないありふれた語だけにし、危険な語・秘密に見える語・外部到達の語に当たらないことをテストで固定する。
- **補完の画面**: シナリオの詳細から開く。欄ごとに、当てた規則、状態（決まった・`NEEDS_RULE_INPUT`・`RULE_CONFLICT`・外部到達で止めた）、意味の種類の選択、固定の値の一覧、範囲、欄どうしの関係、一意にする欄の組を出して編集する。データの例は、いくつかの決まった seed で作って出すが、送らない。保存すると規則の集まりの新しい版ができ、シナリオに付け直して `DRAFT` に戻る（再承認）。人が入れた固定の値は管理データに平文で残る（READ の定義と同じ扱い。秘密に見える名前の欄は拒む）。
- **LLM の依存 0**: 依存（`package.json`）と import に LLM の SDK がないことを Gate で確かめる。

採らなかった案:
- 印を付けて一意にする案（ユーザーの判断で採らない）。
- 汎用の型だけでテンプレートを持たない案（人の手間が増える）。
- 実在の住所を使う案、実在しうる電話番号の範囲を使う案（実在の宛先に届くおそれ）。

## 4. 詳細設計

### 4.1 契約（`src/control/data-rules/` と `schemas/control/data-rule.schema.json`）

- 規則の集まり（id、シナリオの id、版、欄ごとの規則、欄どうしの関係、一意にする欄の組、作成の時刻）。
- 欄の規則: 欄の名前、意味の種類（閉じた一覧: 汎用（数値・日時・選択・色）、氏名（姓・名・フルネーム・フリガナの各種）、メール、備考、商品名、単価、数量、合計、日付、開始・終了の時刻、人数、固定の一覧、テンプレートの外）、作り方（型から・テンプレートから・人の固定の一覧から）、範囲、固定の値の一覧（上限つき）。
- 欄どうしの関係の閉じた一覧: 終了 > 開始（日時）、合計 = 単価 × 数量、フリガナは氏名と同じ人。
- 判定の理由の閉じた一覧: `NEEDS_RULE_INPUT`（細分の理由つき）、`RULE_CONFLICT`（細分の理由つき）、`EXTERNAL_DELIVERY_BLOCKED`。
- 規則の集まりの digest（決まった順の JSON の `createSha256Fingerprint`）。

### 4.2 生成と判定（純粋。`src/control/data-rules/`）

- `evaluateRuleSet(ruleSet, scenario, candidateSnapshot)`: 欄ごとの状態と、実行してよいか（すべて決まった）を返す。
- `generateScenarioData(ruleSet, scenario, seedInput, usedUniqueKeys)`: 送る値の一覧（欄の名前 → 値）と、使った seed の記録を返す。外れたら理由で拒む。
- 値を取り出す部品（`deterministic-stream.ts`）: seed とカウンタから整数を取り出し、範囲の中の一様な値に変える（偏りを避ける）。

### 4.3 管理データの版 7

- 先に、版 6 の文と、版 6 の CHECK が参照する一覧を写しで固定する（G28 で版 6 が公開になるため）。
- 新しい表: `rule_sets`（シナリオごと）、`rule_set_revisions`（版ごとの変えられない写し。追記だけ）。書くのは規則の保存の部品だけ（Gate）。シナリオに参照を付けるのは Task 28 の `attachInputRuleReference`（同じ部品から呼ぶ形は Gate (g) の決まりに合わせて設計する。規則を保存してから付ける 2 段の手順でよい）。
- `currentFactsIn`（Task 28）を、規則の集まりの最新の版を読むように変える。実行の許可の発行で、送る欄すべてに規則が決まっていることを確かめる（決まっていなければ `NEEDS_RULE_INPUT`）。

### 4.4 画面

3 章の「補完の画面」。文言はカタログと文言の owner を通す。画面は `src/control/data-rules/` の内部を直接 import しない（公開し直しの部品を通す）。

## 10. ユーザーの承認が要る点

1. **seed の式**: ロードマップの `stableHash(profileId, scenarioRevision, runId)` を、`stableHash(profileId, scenarioId, scenarioRevision, ruleSetDigest, executionGrantId)` に変える（2 章の理由）。

4. **人が入れた固定の値は管理データに平文で残る**（READ の定義と同じ扱い。秘密に見える名前の欄は拒む）。
5. **送る欄すべてに規則を求める**（required なのに送る欄にない欄も止める）。既定の値がある欄は CREATE では上書きする。
