# 仕様を簡単にし、テストを細くする設計

- 日付: 2026-11-14
- 状態: ユーザーの判断（2026-11-13）を受けた設計者の案。
- 上位の文書との関係:
  - 追補設計書の書き換えにあたる段（SPEC-2〜SPEC-5、REC）は、元の追補設計書の該当の節を、この設計書が置き換えます。置き換える節は、各段の指示書に書きます。
  - 安全の不変条件（実装タスク指示の Safety Invariants）は変えません。

## 1. 背景
- 修正に関係する結合をまとめて流したら、流した時間の合計が約 6.8 時間（446 回）でした（FINAL-RUN-2）。
- 調べ（INV-SLIM、scratchpad の `inv-slim/plan.md`）で分かったことは次の 3 つです。
  - 選び方が広すぎました。src を 1 行でも変えると、fork のテストの全部と画面のテストの全部が選ばれます。
  - 120 秒以上の 65 回で約 4 時間でした。元は次のとおりです。
    - 本物のジョブや Run の回数が多い。
    - 撤廃した上限の名残の、大きな数と掛け算がある。
    - 固定の待ちがある。
    - 落ち着きの窓の待ちがある。
    - Chromium を何度も起こし直している。
  - 仕様の過剰が見つかりました。種類は次の 4 つです。
    - 撤廃した上限と期限の名残。
    - 同じ守りの二重、三重の作り。
    - レビューの回ごとの場当たりの直しの積み重ね。
    - 利用者が求めていない細かさ。
- ユーザーの指摘（2026-11-13）: 「要件に対して重すぎるテストは、過剰な仕様の印」。
- 1 ページの記録も大きすぎます。簡単な表のページで 3MB あります。150 ページでは、ChatGPT 用のバンドルの中に 170MB のファイルができます（DEF-266 の続き）。

## 2. ユーザーの判断（2026-11-13）
- 仕様を簡単にする 4 案は、全部を採ります。
  1. 監査中の印（CLI のロック）を 1 つにします。古いかどうかは、その process がまだ生きているかだけで決めます。
  2. サイトの不調のときの診断の記録（D2・D3）をやめます。不調で止める仕組みは残します。
  3. 手で作る書き込みの道を外します。外すのは、作成・変更・規則の画面と、承認のダイアログです。書き込みは、画面の一覧のチェックだけにします。
  4. 押した後の確かめ（isolated Interaction の F10〜F20 の積み重ね）を、押した後の 1 回の観察で決める形にします。
- 1 ページの記録は、必要な分だけに絞ります。形の版を上げ、前の版の記録も読めるようにします。
- テストは「速い組」と「遅い組」に分けます。**遅い組の 3 時間は遅すぎます。**

## 3. 目標
| 項目 | 目標 |
| --- | --- |
| 速い組（直すたびに流す） | 関係するものの合計を 10 分以内にする。同時 2 本なら、壁の時計で 5 分程度 |
| 遅い組（区切りに流す） | 全部の合計を 1 時間以内にする。同時 2 本なら、壁の時計で 30〜40 分 |
| 1 ファイル | 2 分以内にする。超えるファイルは分けるか、細くする |
| 安全の確かめ | 弱めない（4 章） |

- 遅い組の 1 時間は、テストを細くするだけでは届きません。仕様を簡単にして、作りそのものとテストを消すことが前提です。
- 各段の終わりに、遅い組の合計の時間を測り、進み具合を `progress.md` に書きます。

## 4. 守ること
- 5 つの守りと、秘密を残さない守りは弱めません。5 つの守りは次のとおりです。
  - 削除を止める。
  - 押した後に凍結する。
  - 資格情報を守る。
  - 自分の移動の間隔を守る。
  - 自動ログインの間隔と回数を守る。
- 安全の受け入れ条件の場面は消しません。届いた数 0・secret-markers・伏せ字・資格情報・Guard の場面です。
  - 消すのは、制御の場面と、単体で確かめ済みの判定の写しだけです。
  - 消す場面ごとに、同じことを確かめている「別の所」を指示書と報告に書きます。
- 両方の Chromium で確かめるのは、安全の不具合の場面に限ります。safety-gates の CLI の回は残します。DEF-247・250 は CLI の回でだけ出たからです。
- テストで本番の長さを待ちません。TEST-TIME-B の 3 つの条件を守ります。
- 差し込みの口は、部品の引数か、テストだけの入口に限ります。

## 5.1 範囲の判断（2026-11-14、INV-SPEC の調べを受けて。案の全文は scratchpad の inv-spec/）
- 段の順: SPEC-1 → SPEC-3 と REC-0 → SPEC-2（A1・A2・レビュー）→ SPEC-4（4a・4b・4c）→ SPEC-5（5-1・5-2・レビュー）→ REC-1〜4 → SLIM-1〜6。
- SPEC-2: 端末の再起動の後は古いとみなす（`bootedAtMs`）。PID の使い回しは、持ち主の process の起動の時刻がロックを取った時刻より後なら古いとみなす（利用者に手で消させない）。画面のサーバの管理のロック（管理データの版が変わる）は、この段に入れない。
- SPEC-3: D1 と中継の上流のアドレスの表も消す。3.2.1 を 3.6 にまとめる案は採らない（減るのは約 40〜50 行で、長い停止のあいだにページが FAILED で残り、使える度合いが下がるため）。
- SPEC-4: 画面の書き込みの単独の道（`write.tsx`）も外す。「4 つの約束」の表示と撤回のボタンは外す。手で保存した規則の固定の値は、画面で見えないまま使い続けない（その規則は使わず、一覧でもう一度チェックする扱いにする）。人に直させる文は書き換える。保存の形と承認の digest の版は変えない。`maxCumulativeCreates` を消す段は別にする（digest の版が上がるため）。
- SPEC-5: 凍結の前の下準備は案 B（scroll と hover を残す）。属性の根拠はタブの決まりにそろえ、style を根拠から外す。区分が 1 段緩むことと、「効いた」とする向きの変化 3 つは、ユーザーの判断（判定の細かさが下がる）の範囲として受ける。ただし守り（凍結・Guard・Ledger）は弱めず、独立のレビューで実機で確かめる。

## 5.2 SPEC-2 の作り直し（2026-11-15、REV-SPEC2 の DEF-269〜271 を受けて）
- ファイルのロックと古さの判定（PID・起動の時刻・端末の起動の時刻）は、死んだロックの取り直しで 2 つが持てる（DEF-269、再現）・時計の飛びで生きている持ち主のロックを取る（DEF-270）・SYSTEM の PID の使い回しで止まり続ける（DEF-271）の 3 つの穴があった。どれも「古さを推し量る」作りから来る。
- 新しい形: OS が持ち主の終わりと同時に必ず放す排他を使う。
  - Windows: 名前つきのパイプ（`node:net` の `createServer().listen('\\\\.\\pipe\\beaksight-run-<出力先の正規化したパスの sha256 の先頭>')`）。2 つ目の listen は `EADDRINUSE`、持ち主の process が強制終了しても OS がすぐ放す。設計者の実験（2026-11-15、scratchpad pipe-exp）で、順の取り合い・強制終了の後の取り直し・8 つ同時 × 5 回（毎回 1 つだけ）を確かめた。
  - Linux: 抽象の名前空間の Unix socket（ファイルを残さない）。macOS: 一時のフォルダの Unix socket。`EADDRINUSE` は「持たれている」とみなす（止まる側。macOS は対象の外として報告に書く）。
  - 排他の名前の元は、出力先のディレクトリの `dev` と `ino`（出力先を作ってから取る。パスの綴りは使わない。REV-SPEC2 第 2 回の C-3）。`dev` か `ino` が 0 なら止まる側。取るために作った空の出力先は、Run を始めずに終われば消す（DEF-081）。
- 消すもの: `.beaksight-run.lock` のファイル、古さの判定、取り直し、`process-start-time.ts` と、ロックのための子 process。子 process の起動の部品は資格情報のフォルダへ戻す（`windows-child-process.ts` をなくす。REV-SPEC2 第 2 回の M-7）。
- 前の版との同時の実行は対象の外（配る前のため）。
- 限界: 同じ名前のパイプを BeakSight の外の process が先に listen すると、閉じるまで始められない（止まる側）。
- 限界（REV-SPEC2 第 3 回、どれも利用者の道と CLI のふつうの使い方からは届かない）: 持っている間に外から空の出力先を消して作り直すと別の起動も取れる。listen が EADDRINUSE 以外で失敗すると取るために作った空の出力先が残る。まだない同じ親の下に別々の出力先を CLI で同時に指定すると、片方が UNAVAILABLE になりうる（もう一度起動すれば通る）。
- REV-SPEC2 第 3 回（2026-11-15）で Critical 0・Important 0。SPEC-2 を閉じる。
- 画面のサーバの管理のロックは、この段では変えない。同じ出力先で 2 つの Run が同時に動かない守りは、この排他と、画面のジョブの管理（同時に 1 つ）の 2 つで足りる。
