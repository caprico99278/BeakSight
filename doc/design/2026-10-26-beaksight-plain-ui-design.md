## 1. 目的

IT に詳しくない利用者（中学生レベルと仮定する）が、最低限の情報だけで点検（監査）を始め、結果を読めるようにする。余計な認知の負荷をかけない。

ユーザーの言葉（2026-10-26）:
- 「人間が関心を持たない入力の規則や Origin 情報、送り方の形、READ の定義など、も画面上、表示しなくていい。非 IT 技術者のユーザー（中学生レベルと仮定していい）でも、最低限の情報だけで監査を開始でき、余計な認知負荷にさらされないようにして」
- 「フォームやボタンは増やさない。基本的に自動化を厳守する」
- 「事前にユーザーが知りえない情報を入力させようとするのは NG」
- 「手順が必要ということはまだ効率化が十分でない」
- 画面の無駄 1〜7 は提案どおり直す（UI-W の撮影で見つかったもの。下の 4 章）。

## 3. 画面の決まり（すべての画面に当てる）

1. **画面の形**: どの画面も、上から次の 3 つだけ。
   - **要点**: 今の状態を、やさしい言葉で 2〜3 行（例:「ログインの画面が見つかりました。次は、手でログインして点検します。」）。
   - **次に押すボタン 1 つ**: その段で次にすることのボタンを 1 つだけ（主のボタン）。押せないときは、ボタンを出さずに、理由と「いつ押せるようになるか」を要点に書く。
   - **詳しい内容 1 つ**: たたんだ区画（`AdvancedSettings` を使い回す。新しい部品を作らない）を 1 つだけ。中に、直すための欄と、調べるための情報を入れる。開かなくても流れは進む。
2. **出さないもの**（ふだんの画面にも、詳しい内容にも、原則出さない。成果物の JSON とジョブの記録には残す）: Origin、許可 Origin、承認したサービスの Origin、送り方・enctype、HTTP の言葉（GET・POST、状態の番号）、CSS セレクタ、path の型・必須の query、digest、ID（Run・ジョブ・規則・READ の定義・シナリオ）、版と承認の履歴、要求の形、検証の指定の中身、入力の規則の中身、発見の候補の種類・送信先・ドリフト・分類の理由、日時の細かい行、終了コード、英大文字の識別子（理由のコードは日本語の文に変える）。
   - ただし、ジョブの記録にしかない情報（ログインの段の要約など）は、消さずに「詳しい内容」に入れる（後で調べる道を残す）。
3. **消すもの**: 済んだ操作、押せないボタン、同じ行き先の重なり、自動化で要らなくなった操作、出しても保存で拒まれる欄（MI 4.7.1 で変えられない送信先の欄）。
4. **言葉**（5 章の表）: 画面の文は日常の言葉にそろえる。専門用語、英字、カタカナの技術語を使わない。1 つの文に 1 つのこと。
5. **自動で次へ**: ジョブ（作業）が成功で終わったら、次の段の画面へ自動で移る。失敗、安全の違反、書き込みの結果が分からない（UNKNOWN）、点検で送信を通したときは移さず、その画面で要点と次にすることを出す。
6. **安全のために人が決めること**は、隠さずに、やさしい 1〜2 行で必ず見せる（7 章）。
7. **ボタンを増やさない**: 新しいボタン・欄・区画を足さない。足したくなったら、自動化で解けないかを先に考える。足すしかないときは、設計者がユーザーに諮る。

## 6. 流れ（MI 4.1 を置き換える）

| 段 | 画面 | 利用者がすること |
| --- | --- | --- |
| 1 サイトを足す | 作成 | 開始のアドレスを入れる。「ログインして点検」か「公開の画面だけ」を選ぶ（既定はログインして点検）。「保存して入口を確かめる」を押す（2〜3）。隔離の扱いは、ここでは聞かない（7 の段へ移す） |
| 2 入口の確かめ | 作業の画面 → 自動でサイトの画面へ | なし（ログインの設定を BeakSight が保存する） |
| 3 点検（1 回目） | サイトの画面の主のボタン「点検を始める」→ 開始の画面 | 「点検を始める」（点検 → 操作さがし → 見るだけの確かめ をまとめて進める。判断 3）。開いたブラウザで手でログインする |
| 4 自動ログインにする | 点検の後、サイトの画面の主のボタン「次から自動でログインする」 | ID・パスワード・パスワードをもう一度、確定（4〜5）。確定で点検の開始の画面へ |
| 5 点検（2 回目から） | 主のボタン「点検を始める」 | 押すだけ。最初の自動ログインが、ログインの確かめを兼ねる（判断 1）。ログインに失敗したら、点検は止まり、作業の画面に理由が出る |
| 6 書き込みにも使う | 点検が 1 回終わった後、主のボタン「書き込みも試す」 | 確認のダイアログで、隔離の扱いを選び（「本番から切り離されているか、まだ確かめていない」が既定）、確定（2） |
| 7 書き込み（登録） | 操作さがしの結果から、BeakSight が書き込みの手順の下書きを作り、入れる値の決まりを付ける | 「書き込みの OK」（ダイアログで 4 つの約束を読んで確定）、「書き込みを始める」（ダイアログで確定）（4） |
| 8 書き込み（更新） | 作ったデータの一覧から、BeakSight が更新の下書きを作る | 書き換える欄を選ぶ（人が必ず選ぶ。2026-10-22 の判断）、保存、OK、始める（5〜6） |

- ログインの確かめの画面は、自動ログインが止まった（停止の hold）ときに、解く入口としてだけ残す（ふだんの流れからは行かない）。
- 自動ログインのセレクタ（ID・パスワードの欄、送信ボタン）は、観察の案を使い、人が直す欄を出さない（PL-4 の報告による設計者の判断）。案が 3 つそろわないときは「このサイトでは自動ログインを使えません。手でログインして点検してください」と出す。案が誤っていたときは、手でログインし直して観察し直す。
- 自動ログインの 5 分・24 時間 10 回の決まりは変えない。点検をすぐ始められないときは、主のボタンを出さずに「◯時◯分から始められます」と出す。
- 「まとめて実行」を既定にしても、ページの上限と読み込みの間隔（10 秒）は変えない。

## 8. 書き込みの段の自動化（判断 4）

- **入れる値の決まり（入力の規則）**: 書き込みの手順を保存したら、BeakSight が推して自動で付ける（今の自動は API の下書きの道だけ）。推せない欄があるときだけ、その欄だけを人に聞く（画面は「入れる値の決まり」の画面でなく、書き込みの手順の画面の要点に 1 行と、詳しい内容の欄）。
- **見るだけの確かめ（READ の定義）**: 書き込みの流れからは外す。答え合わせの定義は、BeakSight が操作さがしの候補から作る（API の形は今の自動の下書き、フォームの形は FV-0 の調べの結果で決める）。READ の確かめの画面は、読み取りの点検の任意の画面として残す（ふだんの流れからは行かない）。
- **更新の案内**: 自動の下書きの更新の案内を保存し、画面を移っても消えないようにする（下書きの押し直しをなくす）。
- **フォームの形の検証の指定**（成功の条件、入力の誤りの条件、登録の ID の取り方、答え合わせ）: 観察から自動で決める。決められないときは、書き込みの手順を作った時点で理由を一言出し、書き込みの後に初めて「判定できない」を出さない。期待は緩めない。

### 8.1 フォームの形の判定（調査 FV-0 の実験による。2026-10-26）

実験（127.0.0.1 の 45 場面。記録は作業記録 `fv-0/`）の結果、今の判定（人が入れる path の前方一致と CSS セレクタ）は、利用者が事前に知りえない値を要るので、判定の形を変える。案を 5 つ比べ、**案 (b2)** を採る。

| 案 | 正しく決めた | 誤って成功 | 誤って失敗 | 判定できない |
| --- | --- | --- | --- | --- |
| (a) URL の型と同じフォームの再表示 | 17 | 1 | 6 | 21 |
| (b) 照合を先に、同じフォームなら誤り | 28 | 1 | 1 | 15 |
| **(b2)** (b) の誤りを「送った値を保った同じフォーム」か 4xx に狭める | 26 | 1 | **0** | 18 |
| (c) URL の型と欄の値 | 18 | 1 | 0 | 26 |

「誤って成功」の 1 件（検索が問い合わせの文字を画面に返すサイトで、登録せずに既存の詳細へ移る）は、下の「事前の確かめ」で 0 件にする。誤って失敗を 0 にすることを、判定できないが少し増えることより優先する（誤った失敗は、利用者に誤った直しをさせるため）。

**判定の順（登録・更新とも）**:
1. 応答が 4xx なら、入力の誤り。5xx・応答なし・時間切れは、今どおり結果が分からない（止める）。
2. 2xx・3xx なら、成否によらず照合（登録は答え合わせの READ、更新は今の更新の後の照合）を行い、一致すれば成功。登録の ID は、送った後の URL を ID の型（発見の更新の候補から作る。数字か UUID の形の区切りだけを ID とみなす。core の `isRecordIdLikePathSegment`）に当てて取る。ID があり照合が一致すれば `VERIFIED`、ID がなければ `PARTIAL`。
3. 照合が一致しないときは、送った値を保った同じ「フォームの形」がもう一度出たときだけ入力の誤り。ほかは判定できない。
4. 「フォームの形」の鍵は、送信先・method・欄の名前の集まり・送信ボタンの語で作り、画面の path と hidden の値（CSRF の token など）を含めない。今の識別の digest とは別の鍵として、発見の部品に 1 か所で作る。

**事前の確かめ（設計者の判断）**: 登録を送る前に、同じ値で答え合わせの READ を 1 回読む。値がもう見えていれば、照合に使えないので、送らずに止める（理由を「この値はもうサイトにあるので、書き込みの結果を確かめられません」の形で出す）。安全の側に倒す判断（実験では、これがないと、登録していないのに `VERIFIED` になった）。

**自動で決める項目**:
| 項目 | 決め方 | 決められないとき |
| --- | --- | --- |
| 登録の ID の取り方 | 発見の更新の候補から、送信先の型（例 `/members/{id}`）と画面の型（例 `/members/{id}/edit`）の 2 つ | レコードがまだない、ID が数字・UUID の形でない → ID なし（`PARTIAL`）。作成の時点で「作ったデータを後で探せません（更新は試せません）」と出す |
| 答え合わせ（登録） | 発見の検索・一覧の候補を、照合の専用の定義にする。変わる欄（実行のたびに変わる値）に結び、期待は「作った値を含む」 | 候補がない、送れる文字の欄がない、変わる欄がない → 作成の時点で理由を出す |
| 更新の検証 | 台帳の登録の ID の型と答え合わせを写し、変える欄の値に結び直す（MI-7 を API とフォームの両方に一般にする） | 変える欄に変わる文字の欄がない → 理由を出す（更新の後の照合はできる） |

**サイトへの負荷（設計書に書く決まり）**: 登録 1 件あたり、事前の確かめの GET を 1〜2 回足す。失敗の場面でも照合の GET 2 回を読む。更新は、成功でない場面でも更新の後の照合の GET を 1 回読む。どれも `crawl.minNavigationIntervalMs`（10 秒）の間隔を守り、読み込み直しはしない。送り直しはしない（1 件の予約と、結果が分からないときに止める決まりは変えない）。

**契約の変更**: フォームの成否の条件（今の `inputErrorCondition`・成功の条件のセレクタ）を、構造の判定の印に置き換える。ID の型は 2 つまで。READ の定義に「照合の専用」の印（単独の READ の作業では読まない）。承認の digest の版を上げる（承認済みのフォームの書き込みの手順は、承認し直しになる）。ファイルの見込み: ソースとスキーマで 22〜30、テスト約 30。

**既知の制限**: 誤りがフォームのない別の画面で返るサイト、誤りの画面で値を消すサイト、後から索引に入る検索は、判定できないになる（今の手入力なら決められた場面がある）。本物の書き込みの段の Context（Guard、凍結 1 回）で送った後の画面を読む所は、実装の時に確かめる。
- **書き込みの手順の画面**: 主のボタンは状態で 1 つ（「書き込みの OK」か「書き込みを始める」）。OK と開始の確認は、それぞれ 1 回残す（2 段の守りを崩さない）。

## 9. 先にふさぐ安全の表示の穴（UX-1 の D 章）

1. 隔離が未確認でも、書き込みの開始の画面に緑の「証跡の参照があります」が出る → 未確認の形なら注意として出す。承認と開始のダイアログにも出す。
2. 自動ログインの確定のダイアログに、パスワードを送る先が出ない → 出す。
3. フォームの書き込みの OK のダイアログに、何を・どこへが出ない → 出す。
4. 副作用の 4 つの約束の文が過去形（「確かめました」）→ 現在形で、確かめてから押す形に。
5. 「削除のほかを通す」がオンの間の印。

## 14.1 流れの穴の直し（PL-U。PL-TD の文書の担当の発見による。2026-10-27）

ユーザーの方針（「手順が必要ということはまだ効率化が十分でない」「フォームやボタンは増やさない。自動化を厳守」）に反する穴を、画面の確認の前にふさぐ。ボタン・欄・区画は増やさない（主のボタンの文と行き先を変えるだけ）。

| 順 | 今 | 後 |
| --- | --- | --- |
| U1 | 一部未完了（`AUDIT_PARTIAL`）の点検は、自動で次の画面へ移らない | 完了と同じく、サイトの画面へ自動で移る。要点の 1 行目は「点検が終わりました。一部のページは見られませんでした。」の形 |
| U2 | 点検の後に自動でサイトの画面へ移るので、結果への主のボタンがない（13 章の 13 とずれる） | 点検を終えたばかりで移ったとき（`arrived=auto`）と、最新の点検の結果があって次の段の操作がまだないときは、サイトの画面の主のボタンを「結果を見る」にする。結果の 1 行（問題の件数）は要点に。次の段（書き込みも試すなど）は、そのときは二次のボタン |
| U3 | 書き込みの手順の下書きは、2 回押して作る（「書き込みの手順を作る」→「下書きを作る」） | 1 回の押下で作る。確認のダイアログが要るなら、ダイアログの確定を最初の押下の続きとして数え、間の画面を挟まない |
| U4 | 書き込みの手順が 0 件の一覧が行き止まり | 主のボタン「書き込みの手順を作る」（操作さがしの結果があれば下書き、なければ操作さがしを始める） |
| U5 | 「書き込みも試す」の後に、操作さがしのやり直しが要る（`DISCOVERY_STALE`） | 操作さがしの結果の古さの判定から、書き込みのモードの切り替えだけで変わる値（モード、隔離の参照）を外す。外すと安全が下がる理由が見つかったら止まって報告。外せないときは、切り替えの確定の後に操作さがしを自動で始める |
| U6 | 自動の登録（入口の確かめの後の認証の設定）と、まとめて実行の、どちらが先かを確かめていない | 端から端のテストで順を固定する（認証の設定が保存されてから、まとめて実行の点検が始まる） |
| U7 | サイトの作成で、設定のファイルの名前が Windows の予約名に当たると「別の名前にしてから」と出るが、名前の欄がない | 名前は自動で作るので、予約名に当たるときは自動で別の名前（末尾に番号など）にする。拒否は残さない |

8.1 より広く止める事前の確かめ（`VERIFICATION_READ_UNAVAILABLE`）は、独立レビューで安全の側から確かめる（直さない）。

PL-U の調べの後の判断（2026-10-27）:
- U1: 利用者が「止める」で止めた点検は、作業の画面に残す（自動で移らない）。押した人が、止まったことをその場で見られるようにするため。
- U3: 下書きを作る前の確認のダイアログはなくす（1 回の押下）。下書きは何も送らず、書き込みの OK の前に中身を見られるため、安全のための確認ではない。作ったものは、結果の 1 行（「書き込みの手順を N 個作りました」）で知らせる。
- U5: 案 (A) を採る。PL-U の調べで、次の 2 つが確かめられた。
  - 操作さがしは読み取りだけで、ワーカーはモードも隔離の参照も読まない。
  - 書き込みの OK と書き込みのときに、`approval-validity.ts` がモード・改訂・認証の設定・設定のファイルを照らし直す。

  そこで、操作さがしの結果の古さを決める判定を 1 つの関数にまとめる（SSOT）。この関数は、「書き込みも試す」の切り替えだけで進んだ改訂を、同じ改訂とみなす。今 4 か所にある比べ方（`isAutoDraftDiscoveryStale`、`apiProfileRevisionErrorsOf`、`scenario-store.ts` の改訂の読み方、`approval-validity.ts` の `API_DISCOVERY_PROFILE_STALE`）は、どれもこの関数を使う。

  変えないものは次の 2 つ。
  - 書き込みの OK と今の改訂を比べる判定（`PROFILE_REVISION_CHANGED` など）は、今のまま厳しく保つ。
  - 承認したサービスのアドレスの一覧が変わった改訂は、同じとみなさない。

  同じとみなすのは、「書き込みも試す」の切り替えで変わる値（モード、隔離の参照、認証の設定がどの改訂に結びつくか）のほかに違いがない改訂だけ。それを、保存してある記録から確かめられるときに限る。確かめられないときは、古いとみなす（安全の側に倒す）。

  補足（PL-REV の Minor 1 による。2026-10-27）: 認証の設定の中身（読まないパスなど、送信先でない欄）の変更は、操作さがしの古さには数えない。U5 の前から、同じ改訂のままの認証の設定の変更は数えていなかった。書き込みの OK は、OK を出した時の認証の設定の digest で縛る（`AUTH_SETUP_CHANGED`）。送信先の欄は MI 4.7.1-6 で変えられない。そのため、書き込みの迂回にはならない。
