## 3. 採用する設計

- **UPDATE の指定**（シナリオの内容に足す。承認の digest の項目になる）:
  - 台帳の参照: どの CREATE のシナリオで登録したレコードを対象にするか（同じプロファイルの CREATE のシナリオ 1 つ。複数の段のシナリオではなく、台帳を読む先の指定）。
  - path の型: 更新の画面の path と送信先の path を、ID の位置を `{id}` にした型で持つ（それぞれ `{id}` はちょうど 1 つ）。型に、発見で見た候補の ID の区切りを入れると、候補の具体的な path に戻ること（同じ値で両方）を確かめる。
  - 欄の役割: 見えていて編集できる欄は、すべて「変える欄」か「保つ欄」のどちらかにする（既定は保つ）。変える欄が 1 つもない指定は受けない。
  - 保つ欄の期待の値: 更新の前に読んだ値（前の値）。人が期待の値を決める必要はない。
- **型にした識別の digest**: 候補の識別の digest（画面の path と送信先の path を含む）を、ID の区切りを `{id}` にした形で求める純粋な関数を、候補の識別の owner（`src/discovery/fingerprint.ts`）に足す。UPDATE のシナリオの承認と有効性の判定はこの digest で行う。実行の時は、対象の ID の画面で読んだ候補から同じ digest を求めて照らす。
- **レコードの ID の形（Task 30 と共用する SSOT）**: path の 1 区切りに入れて安全な閉じた形（英数字・`_`・`-`、1〜64 文字。名前つきの定数）。Task 30 の ID の取り出し（T30f）も同じ部品で受ける（外れる ID は `PARTIAL` の `RECORD_ID_UNSAFE`）。Task 30 の設計変更履歴にも書く。
- **対象の選び方**（ユーザーの判断 4）: 実行の許可の発行の中で、対象にできるレコードのうち、登録の時刻が最も新しい 1 件を自動で選ぶ。開始の画面にその ID を「更新の予定のレコード」として出し、開始の要求はその ID を持つ。発行の時に選び直した結果が違えば止める（`TARGET_SELECTION_CHANGED`）。人は ID を入力しない。選んだ ID は実行の許可と予約に結び、ワーカーは親から受け取る ID だけを使う。
- **対象にできるレコード**（ユーザーの判断 5）: 参照した CREATE のシナリオの登録で `VERIFIED` のもの（BeakSight が登録して照合した管理レコード）。外すレコードは設けない。レコードごとの更新の回数は数えない。前の UPDATE の結果（`UNKNOWN` を含む）によらず、同じレコードを何度でも更新できる。二重の更新は、1 回の Run で 1 件、ジョブの管理の「同時に 1 つの枠」、実行の許可の 1 回だけの消費、通信の断の後に再試行しないこと、で防ぐ。
- **値の照らし方**: 完全な一致。改行は CRLF と LF を同じと見なすだけで、ほかの正規化はしない。サーバが値を整形して食い違う場合は止めて報告し、必要なら後で正規化の閉じた一覧を足す。
- **変える欄の値**: Task 29 の生成で作る。使った値（`UNKNOWN` を含む履歴）と重なる値は作らない（BeakSight が作った値は履歴にあるので、前の値とも重ならない）。メールと電話は既定で保つ（ユーザーの判断 3）。変える欄に選んだときだけ合成の値（`example.invalid`、`090-0XXX-XXXX`）にし、`NO_EXTERNAL_NOTIFICATION` の確認を求める（Task 29 のとおり）。
- **削除にあたる変更の遮断**:
  - 状態の欄（`DISCOVERY_STATE_FIELD_WORDS` に当たる名前）は変える欄にできない（保つだけ。`STATE_FIELD_NOT_CHANGEABLE`）。
  - 状態の欄の語に `hidden`・`show`・`display`・`flag`・`closed`・`cancel`・`表示`・`非表示`・`ステータス`・`停止` などを足す（閉じた一覧。語の単位の比べ）。
  - 変える select・radio の選択肢から、危険な語に加えて無効化の語（`inactive`・`hidden`・`closed`・`非表示`・`無効`・`停止`・`取消` など）の値と文言を除く。
  - 送る中身の照合で、保つ欄の値・`_method` の値（承認した候補の上書きの値と完全に一致。DEF-096）・状態の名前の hidden の欄の値（更新の前に読んだ値と同じ）を照らす（「値を照らす passthrough」。照合の owner は `src/safety/write-payload-policy.ts` のまま）。
  - 秘密に見える名前（`state`・`code` など）の見える欄がある画面は、値を読めないので UPDATE を実行しない（`SECRET_LIKE_FIELD_IN_UPDATE_FORM`）。
- **同じ名前の hidden と checkbox の組**（Rails 型）: 同じ form で、checkbox の直前にある同じ名前の hidden 1 つは、checkbox の「外した値」として組で扱う。hidden の値は更新の前に読み（秘密でない閉じた値）、送る中身では値を照らす。checkbox が保つ欄なら、チェックの状態も照らす。照合の owner の部品なので、CREATE でも使えるようになる（今は止めている形が受けられる）。
- **更新の前の読み取り**（Task 30 の画面の確かめと同じ 1 回の GET）: 凍結した Context で対象の ID の更新の画面を開き、isolated world で候補を読み直して型にした識別の digest を照らす。変える欄と保つ欄の今の値、状態の名前の hidden の欄の値、組の hidden の値を、prototype の getter で読む（`write-form-submitter.ts` の読み取りの部品を広げる）。読んだ値を「前の値」とする（台帳の値とは比べない。ユーザーの判断 5）。前の値はワーカーの中だけで使い、送る中身の照合の期待（保つ欄・状態の hidden・組の hidden は前の値と同じ）と、後の照合の期待を作る。書き込みの段の Context で開き直した画面の値が前の値と違えば、入力の前の確かめか送る中身の照合で止める（送らずに `BLOCKED`、予約は `RELEASED`）。
- **送信**: Task 30 の書き込みの段をそのまま使う（承認の形の POST を 1 回だけ。送信先は型に対象の ID を入れた具体的な path。`_method` の PUT・PATCH はページのまま送り、値を照らす）。送る直前の確かめ直し（IPC の往復）も同じ。
- **結果の判定**: Task 30 の判定（成功・入力の誤り・429・5xx・どれにも当たらない・2 つ以上・セッションの切れ・307/308）に加えて、成功の後に取れた ID が対象の ID と同じであること（違えば `UNKNOWN` の `RECORD_ID_MISMATCH`）。
- **更新の後の照合**: 書き込みの段を閉じた後、凍結した Context で対象の更新の画面を開き直し（GET 1 回）、変えた欄が新しい値、保つ欄が期待の値、状態の名前の hidden の欄と組の hidden が前と同じであることを欄ごとに照らす。続けて、シナリオの検証の指定の READ（Task 30。結び付けた値は新しい値）で照らす。
  - すべて一致 → `VERIFIED`。
  - 変えた欄が新しい値でない、保つ欄・状態の欄が変わった → `UNKNOWN`（`UNEXPECTED_FIELD_CHANGE`。副作用の疑いがあり、成功と偽らない）。
  - 画面が開けない・digest が違う・欄がない → `PARTIAL`（照合できない）。
- **証拠と記録**: 欄ごとに、欄の名前、役割、後の照合で一致したかの真偽を持つ。変える欄は、前の値と新しい値を持つ（前後の差分を画面に出すため。BeakSight が登録したテストのレコードの値なので、平文の扱いは Task 30 の送った値と同じ）。保つ欄の値、hidden の値、CSRF のトークンは記録しない（一致の真偽だけ）。成果物は Task 30 の `action-run.json` を UPDATE に広げる（スキーマの版を上げる）。
- **上限**: 1 回の Run で 1 件、累積はシナリオの上限（Task 28 の既定 20 件）、同じシナリオの連続は Task 30 の定数（5 分以上の間隔、24 時間に 5 件）。レコードごとの上限は設けない（ユーザーの判断 5）。`UNKNOWN` は件数を使ったものとして数え、シナリオは止めない（Task 30 のユーザーの判断 2 と同じ）。通信の断の後に自動で再試行しない。
- **記録**: 管理データの版 9（G30 の後。版 8 の写しを先に固定）。ジョブの種類 `WRITE_UPDATE`、UPDATE の結果（対象の ID、変えた欄の前の値と新しい値、後の照合の結果、結果の理由）、対象の ID と実行の許可・予約の結び付き。対象の選択は、発行と同じトランザクションで行う（2 つの process の競争でも 1 件だけ）。

採らなかった案:
- 変える欄だけのフォームに限る案、保つ欄を名前だけで照らす案（ユーザーの判断 1。名前だけでは状態の欄を守れない）。
- 開始の時に人が台帳から選ぶ案（ユーザーの判断 4。代わりに、選んだ ID を開始の画面に出し、開始の要求と発行の選び直しで照らす）。
- 版の値を BeakSight が読んで送る案（hidden の値は読まない決まりを保ち、ページのまま送る）。
- 前の値を台帳と比べて止める案、結果が分からなかったレコード・値が台帳と違うレコードを外す案、レコードごとの回数の上限（ユーザーの判断 5。監査を繰り返すと対象がなくなり、ほかの更新者を気にしなくてよいので要らない）。

## 4. 詳細設計の要点

- **契約**（`src/control/approval/scenario-contracts.ts`）: UPDATE の指定（台帳の参照、path の型 2 つ、欄の役割）。下書きの確かめ（`validateScenarioDraft`）で、path の型が候補に戻ること、見える編集できる欄がすべて役割を持つこと、変える欄が 1 つ以上、状態の欄・秘密に見える名前・危険な語の扱い、参照した CREATE のシナリオが同じプロファイルにあること、を確かめる。承認の digest の版 3（今の承認はすべて再承認）。
- **型にした識別の digest**（`src/discovery/fingerprint.ts`）: 発見の索引の候補から求め直せること（T31b で確かめる。求め直せなければ Blocker として止まる）。
- **照合**（`src/safety/write-payload-policy.ts`）: 期待に「値を照らす passthrough」（DEF-096 で足す形）を使い、保つ欄・状態の hidden・組の hidden を足す。名前の重なりは組の形だけ受ける。
- **生成**（`src/control/data-rules/`）: 変える欄の新しい値を、シナリオの指定と使った値の履歴から決める（Task 29 の生成を使う）。保つ欄の期待はワーカーが前の値から作る。
- **台帳の読み出し**（`src/control/actions/write-result-facts.ts`）: 参照した CREATE のシナリオの `VERIFIED` の登録の ID の一覧（登録の時刻の新しい順）、使った値の集まり（UPDATE で送った値を含む）。
- **IPC**: START に UPDATE の指定（対象の ID、path の型、欄の役割、変える欄の新しい値）。ワーカーは管理データを読まない。
- **読み込みの回数と間隔**: ログイン、更新の前の読み取り（GET 1 回）、書き込みの画面（GET 1 回）、POST 1 回、結果の画面（redirect の GET）、更新の後の読み取り（GET 1 回）、照合の READ（GET を定義の数だけ）。1 回の Run で 7〜8 回程度。どの読み込みも `crawl.minNavigationIntervalMs` を守る。読み込み直しはしない。

## 5. SSOT と安全性への影響

## 6. テスト設計

- 契約: path の型（`{id}` の数、候補に戻らない型、ID の形）、欄の役割の網羅、状態の欄を変える欄にできない、秘密に見える名前、参照の確かめ、digest の版 3。
- 型にした識別の digest: ID だけが違う 2 つの画面で同じ、構造が違えば違う。
- 照合: 保つ欄の値の違い、`_method=DELETE`、状態の hidden の値の書き換え（ページの JS で `active=0`）、組の hidden、名前の重なり（組でない形は止める）。両方の Chromium で、届かないことをサーバの記録で数える。
- 生成: 変える値が履歴（UPDATE で送った値を含む）と重ならない、メールと電話は既定で保つ、無効化の語の選択肢を選ばない、多くの seed。
- 対象の選択: `VERIFIED` の登録の最新の 1 件、`UNKNOWN` の後も同じレコードを選ぶ、選び直しの違いで止まる、2 つの process の競争で 1 件だけ。
- 前の読み取り: 前の読み取りと書き込みの段の画面の間で値が変わる fixture で、送らない。
- 後の照合: サーバが保つ欄を変える fixture、状態を変える fixture、変えた欄を受けない fixture で `UNKNOWN`。
- 結果: ID の不一致、通信の断の後に再試行しない、二重の更新 0。
- test-only の永続化する fixture（127.0.0.1。`lock_version`、状態の欄、Rails 型の checkbox、`_method`）で、指定した差分だけが変わる。
- 目印の検査（資格情報・Cookie・CSRF のトークン・hidden の値・保つ欄の値が、成果物・管理データ・ログ・IPC・画面に出ない）。
- 回帰: 公開監査・認証つきの監査・自動ログイン・発見・READ・シナリオ・入力の規則・CREATE。
- Gate: 入力と読み取りの owner、照合の owner、版 9 の表に書くファイル。

## 10. ユーザーの承認が要る点

1. **ユーザーの判断 4 の具体化**: 対象は、参照した CREATE のシナリオの `VERIFIED` の登録のうち、登録の時刻が最も新しい 1 件。開始の画面にその ID を出し、発行の時に選び直して違えば止める。外すレコードはないので、毎回同じレコードを更新する（新しい登録があればそれに移る）。
2. **前の値の扱い**（ユーザーの判断 5）: 更新の前に読んだ値を前の値とし、台帳とは比べない。保つ欄は前の値のまま送られ、後も前の値のままであることを確かめる。値の比べ方は完全な一致（改行だけ同じと見なす）。
3. **削除にあたる変更の遮断の追加**: 状態の欄は保つだけ、語の一覧の追加（発見の印と生成の判定が変わり、承認の再判定が起きうる）、秘密に見える名前の見える欄がある画面は実行しない。
4. **Rails 型の checkbox の組を受ける**: CREATE でも受けられるようになる。
5. **記録する値**: 変える欄は前の値と新しい値を記録し、画面に差分を出す。保つ欄・hidden の値は記録しない（一致の真偽だけ）。
6. **読み込みの回数**: 1 回の Run で 7〜8 回程度（更新の前と後の読み取りで、Task 30 より GET が 1 回多い）。どれも設定の間隔を守る。
