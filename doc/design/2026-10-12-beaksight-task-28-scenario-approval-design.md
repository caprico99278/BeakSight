# BeakSight Task 28 シナリオの承認・保存・再承認 設計書

作成日: 2026-10-12
状態: ユーザー承認済み（2026-10-12。10 章の 5 点を含む）。G28 承認済み（2026-10-13）
対象範囲: テスト環境の書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルで、発見した CREATE・UPDATE の候補を「シナリオ」として、人が画面で確かめて承認し、保存・撤回・再承認できるようにする。実行の許可（ExecutionGrant）と件数の予約の仕組みを作るが、**この Task では書き込みは一切しない**（書き込みの実行は Task 30・31）

## 1. 目的

Task 30（承認された CREATE）と Task 31（承認された UPDATE）の前に、「何を、どの条件で、何件まで書いてよいか」を人が明示的に承認し、その承認を書き換えられない記録として残す。承認の対象が変わったら（フォーム、送信先、プロファイル、上限、期限、入力の規則）、承認は自動では引き継がず、再承認を求める。

- 承認だけでは書き込みは始まらない。書き込みのジョブ（Task 30 以降）は、承認が今も有効であることを、期限つきで 1 回だけ使える実行の許可（ExecutionGrant）と、件数の予約（WriteReservation）で確かめてから始める。
- G28: 「承認なし・版の違い・撤回済み・期限切れ・許可の再利用」による実行は、すべて拒まれる。承認の保存はできるが、実サイトへの書き込みはまだできない。

## 3. 採用する設計

- **シナリオ = 書き込みの候補 1 つ**: 最後の発見のジョブで見つかった、分類が `CREATE` か `UPDATE` の候補 1 つ（要求の形 1 つ）と、結果を照らす READ の確かめの定義の参照 0〜n 件。複数の段のシナリオ（登録してから更新する、など）は扱わない。`NEEDS_BINDING`・`NOT_EXECUTABLE`・`UNSUPPORTED_READ_TRANSPORT`・`BLOCKED_EXTERNAL`・`DISPLAY_ONLY`・`READ` の候補からは作れない。
- **シナリオの版**: どの編集でも版が上がる。承認は「シナリオのある版」に対して行い、その版の承認の内容の digest（承認の digest）を、書き換えられない承認の記録（receipt）に固定する。版が上がると、それまでの承認は引き継がない（状態は `DRAFT` に戻る）。
- **承認を縛るもの（どれかが変われば再承認）**: シナリオの版、プロファイルの改訂（`profile_revisions`。どの編集でも）、認証の設定の digest、ターゲットの設定の digest、候補の識別の digest と規則の digest（Task 27）、要求の形（method、Origin、path、送る欄の名前の一覧、enctype）、副作用の確認、上限（1 回の Run と累積）、期限、入力の規則の参照（版と digest）、照らす READ の定義の参照（id と版）。承認の digest は、これらを決まった順で並べた JSON の SHA-256（`createSha256Fingerprint`）。
- **有効かの判定は 1 つの純粋な関数**（`src/control/approval/approval-validity.ts`）: 今のシナリオ・今の事実（プロファイルの改訂、各 digest、最後の発見の候補とドリフト、時計）・最後の承認の記録から、`APPROVED` か、または再承認が要る理由の閉じた一覧（`SCENARIO_REVISION_CHANGED`、`PROFILE_REVISION_CHANGED`、`AUTH_SETUP_CHANGED`、`TARGET_CONFIG_CHANGED`、`CANDIDATE_CHANGED`、`CANDIDATE_MISSING`、`INPUT_RULES_CHANGED`、`READ_CHECK_CHANGED`、`EXPIRED`、`REVOKED`、`NOT_APPROVED`、`PROFILE_RETIRED`、`MODE_NOT_WRITE`）を返す。画面の表示、実行の許可の発行、書き込みの前の確かめ直し（Task 30）は、すべてこの関数を通す（SSOT）。
- **実行の許可（ExecutionGrant）**: 有効な承認のシナリオに対して、管理データのトランザクションの中で、承認の判定をやり直してから発行する。許可は 1 つのジョブに結び付き、期限（`EXECUTION_GRANT_TTL_MS`。5 分。ジョブの開始までに使う）つきで、1 回だけ消費できる（消費の時刻を記録し、2 回目は拒む）。偽造（存在しない id、別のシナリオ・別のジョブ・別のプロファイルへの流用）と期限切れは拒む。この Task では、書き込みのジョブの種類とワーカーは作らない。発行・消費・確かめ直しの口と、ジョブの開始の guard（`createStartingJob` の同じトランザクションの確かめの形）を作り、テストで直接呼んで G28 を確かめる。
- **件数の予約（WriteReservation）**: 実行の許可の発行と同じトランザクションで、1 回の Run の上限と累積の上限の残りから件数を予約する。累積の数は、予約中・送信済み・結果が分からない（`UNKNOWN`）を数え、返したものは数えない。撤回・許可の期限切れ・送る前の中止では、送っていない予約を返す。状態は `RESERVED`・`RELEASED`・`COMMITTED`・`UNKNOWN` の閉じた一覧（`COMMITTED` と `UNKNOWN` に変える口は Task 30 が使う。表の CHECK はこの Task で作る）。
- **入力の規則の枠**: シナリオに、入力の規則の参照（規則の集まりの id、版、digest。どれも空でよい）を持たせる。参照が空のシナリオは承認はできるが、実行の許可は `NEEDS_RULE_INPUT` で拒む。参照を付ける口（`attachInputRuleReference`）はこの Task で作り、画面は作らない（Task 29 が規則を作って付ける）。参照が変われば再承認。
- **承認の操作は画面だけ**: 承認と撤回は、確認のダイアログの後の POST の Server Function だけで行う。Server Function は、画面に出した承認の digest とシナリオの版を受け取り、サーバで求め直した値と一致しなければ拒む（古い画面のまま承認しない）。承認者は、利用者の ID がない（単独の利用者）ので、固定の値 `LOCAL_OPERATOR` を記録する。
- **発見の根拠の写し**: シナリオを作るとき、最後の発見のジョブの `discovery.json` から、その候補の詳しい内容（値を持たない形。Task 27 の候補の契約のまま）を管理データに写す（成果物が消されても根拠と差分を出せるように）。ページが書いた値（送信先の path、欄の名前、制約、選択肢の値）を含む点は `discovery.json` と同じ（手順書に書く）。
- **モードの拡張**: `TEST_APPROVED_WRITE` のプロファイルでも、認証の設定、`DISCOVERY`、`READ_CHECK` を許す（ユーザーの判断 1）。認証つきの監査（`AUDIT`）は、この Task では許さない（判断の範囲の外）。書き込みのジョブはまだない。

採らなかった案:
- 承認の状態だけを保存し、承認の内容を記録しない案（承認の後に何が変わったか示せない）。
- 承認の期限切れを保存する案（時計とのずれ）。
- 予約を Task 30 で作る案（G28 の予約の競合のテストができない）。

## 4. 詳細設計

### 4.1 契約（`src/control/approval/` と `schemas/control/`）

- `scenario.schema.json`: シナリオの版 1 つ（id、profileId、版、kind（`CREATE`・`UPDATE`）、候補の識別の digest と規則の digest、要求の形、送る欄の名前の一覧（候補の送れる欄の中から選ぶ。秘密に見える名前と危険な語は Task 27 の判定で拒む）、照らす READ の定義の参照、副作用の確認（閉じた一覧の各項目を人が確かめたか）、上限（1 回の Run、累積）、期限の日数、入力の規則の参照、作成と更新の時刻）。
- `approval-receipt.schema.json`: 承認の記録（receipt の id、シナリオの id と版、承認の digest、縛った事実の値（プロファイルの改訂、各 digest）、承認の時刻、期限の時刻、承認者 `LOCAL_OPERATOR`）と、撤回の記録（receipt の id、対象の承認の receipt の id、撤回の時刻、理由の閉じた値）。追記だけ。
- 副作用の確認の閉じた一覧（承認の前に人がすべて確かめる）: 登録・更新されるのはテスト環境のレコードだけ、メール・SMS・外部の通知が送られない設定であること、決済や外部のサービスに及ばないこと、削除・無効化・取り消しに当たらないこと。どれかが未確認なら承認できない。
- 既定の上限と期限は名前つきの定数（`APPROVAL_TTL_DAYS = 30`、`DEFAULT_MAX_CREATES_PER_RUN = 1`、`DEFAULT_MAX_CUMULATIVE_CREATES = 20`、`WRITE_JOB_CONCURRENCY = 1`、`EXECUTION_GRANT_TTL_MS = 5 分`）。シナリオで既定より小さくはできるが、大きくはできない（大きくするのはユーザーの判断で既定値を変えるとき）。UPDATE の上限は CREATE と同じ値を使う（Task 31 で見直す）。

### 4.2 管理データの版 6（`src/control/store/migrations.ts`）

- 先に、版 5 の文と、版 5 の CHECK が参照する一覧を写しで固定する（Task 27 の決まり。G27 で版 5 が公開になるため）。
- 新しい表（どれも STRICT、プロファイルへの外部キー、ジョブへの外部キーは持たない）:
  - `scenarios`（今の版の行。版、状態 `DRAFT`・`APPROVED`・`REVOKED`、最後の承認の receipt の id）
  - `scenario_revisions`（版ごとの変えられない写し。発見の根拠の写しを含む）
  - `approval_receipts`（承認と撤回の追記だけ。UPDATE と DELETE をしない）
  - `execution_grants`（シナリオ、版、承認の receipt、ジョブの id（一意）、発行と期限と消費の時刻。「消費していない有効な許可は 1 シナリオに 1 つまで」の部分一意の索引）
  - `write_reservations`（許可、シナリオ、件数、状態、時刻。状態と時刻の組み合わせの CHECK）
- 版 1〜5 のデータベースから版 6 へ上がること、版 1〜6 の文の SHA-256 の固定をテストする。

### 4.3 再承認の判定（`approval-validity.ts`。純粋。時計を注入）

3 章の理由の一覧を、決まった順で求める（複数あれば全部返す）。候補の判定は、最後の発見のジョブの索引のドリフト（`UNCHANGED` 以外、`MISSING`、`NOT_REVISITED` は再承認か実行不可）と、識別と規則の 2 つの digest の一致で行う。

### 4.4 実行の許可と予約（決まりは `execution-grant.ts`、書き込みは `scenario-store.ts`、読み出しは `scenario-facts.ts`）

- 発行: 1 つのトランザクションの中で、(1) 承認の判定（4.3）、(2) 入力の規則の参照があること、(3) 消費していない有効な許可がないこと、(4) 予約の残り（1 回の Run と累積）、(5) 書き込みの同時実行の枠（全体の、消費していない有効な許可と、消費済みで予約が `RESERVED` のままの許可の数を `WRITE_JOB_CONCURRENCY` と比べる。2026-10-13 T28d）を確かめてから、許可と予約を書く。どれかが外れたら何も書かずに理由のコードで拒む。
- 消費: 1 つのトランザクションの中で、許可の id・シナリオ・版・ジョブ・期限・未消費を確かめ、承認の判定をやり直してから、消費の時刻を書く。
- 確かめ直し（Task 30 が書き込みの要求の前に呼ぶ）: 許可が消費済みで、承認が今も有効（撤回されていない、期限内、版と縛った事実が同じ）か。
- 撤回: 撤回の receipt を追記し、シナリオを `REVOKED` にし、消費していない許可を無効にし、`RESERVED` の予約を `RELEASED` にする（同じトランザクション）。
- 競合: 2 つの発行が同時に来ても、予約の合計が上限を超えない。撤回と発行が同時に来ても、撤回の後に有効な許可が残らない（SQLite の `BEGIN IMMEDIATE`。テストで確かめる）。

### 4.5 モードの拡張

`src/control/execution-policy.ts`、`src/control/auth/auth-setup-policy.ts`、ジョブの管理の開始の判定で、`TEST_APPROVED_WRITE` を認証の設定・`DISCOVERY`・`READ_CHECK` に加える。書き込みのモードで `AUDIT` は今のまま始められない。

### 4.6 画面（`apps/local-ui/`）

- プロファイルの詳細（`TEST_APPROVED_WRITE` のとき）から「シナリオ」の一覧へ。
- 一覧: シナリオごとの kind、画面と送信先、状態（下書き・承認済み・要再承認（理由）・期限切れ・撤回済み）、期限、上限と使った件数。
- 作成: 候補の画面（Task 27）の CREATE・UPDATE の候補から「シナリオを作る」。送る欄の選択、照らす READ の定義の選択、上限（既定以下）、期限（既定以下）、副作用の確認。
- 詳細: 発見の根拠（写し）、要求の形、欄の型と制約（値の例は出さない。Task 29 まで）、承認の状態と理由、承認と撤回の履歴、最後の承認との差分（項目ごとの機械の読める差分と、日本語の説明）。
- 承認: 差分と副作用の確認を出した確認のダイアログの後に POST。撤回: 確認のダイアログの後に POST。どちらも CSRF、版と承認の digest の照合。
- 文言はカタログと文言の owner を通す。画面は `src/control/approval/` の内部を直接 import せず、画面向けの公開し直し（`src/control/approval-view.ts`）を使う。

### 4.7 秘密と個人情報

シナリオと承認の記録に、入力の値、CSRF のトークン、hidden の値、選択肢の label、資格情報を持たない。ページが書いた値（path、欄の名前、制約、選択肢の値）は持つ（`discovery.json` と同じ。手順書に書く）。

## 5. SSOT と安全性への影響

| 項目 | owner | この設計での扱い |
| --- | --- | --- |
| 承認が有効かの判定 | `src/control/approval/approval-validity.ts` | 新設（画面・許可・Task 30 の確かめ直しが使う唯一の判定） |
| 承認の digest | `src/control/approval/`（`createSha256Fingerprint` を使う） | 新設 |
| 候補の契約・digest・ドリフト | `src/discovery/`、`src/control/job/discovery-index-store.ts` | 利用のみ |
| 送れる欄・秘密に見える名前・危険な語 | `src/discovery/read-check-contracts.ts`、`classify.ts`、秘密の名前の方針 | 利用のみ（送る欄の選択に使う） |
| プロファイルの改訂、認証の設定、ターゲットの設定の digest | Task 22〜26 の owner | 利用のみ |
| ジョブの同時実行の枠 | `jobs_single_active` | 利用のみ |

- 公開監査・認証つきの監査・自動ログイン・発見・READ の振る舞いと出力は変えない（モードの拡張で、書き込みのモードのプロファイルでも認証の設定・発見・READ ができるようになるだけ）。
- この Task のどのコードも、サイトへ書き込みの要求を送らない（書き込みのジョブ・ワーカーを作らない。Gate で確かめる）。

## 6. テスト設計

- 再承認の判定の表（理由ごと、組み合わせ、時計の境）。
- 承認の digest の安定（同じ内容は同じ、各項目の変化で変わる）。
- 版 6 の移行と、版 1〜5 の文の固定。
- G28: 承認なし・版の違い・撤回済み・期限切れ・許可の再利用・偽造・別のジョブへの流用・規則の未設定の、許可の発行と消費がすべて拒まれる。正しい承認なら 1 回だけ発行・消費できる。
- 予約の競合（同時の発行、撤回と発行）、上限の境、返した予約を数えない。
- 画面: 一覧・作成・詳細・承認・撤回、確認のダイアログ、CSRF（cross-site の POST は 403）、古い画面の承認の拒否、文言の書き漏れ、キーボードの操作、CSP。
- 目印の検査（シナリオの写しと承認の記録と画面に、秘密の目印が出ない）。
- 回帰: 公開監査と認証つきの監査と自動ログインと発見と READ（golden、`cli-output-parity`、`safety-gates`、`authenticated-*`、`automated-login*`、`discovery-*`、`read-check-*`）。
- Gate: 承認の判定の owner の外に同じ判定を書かない。`src/control/approval/` から書き込みの要求を送る部品（ブラウザ、ワーカー）を import しない。

## 9. 実装計画の分け方（概要。承認の後に実装計画を書く）

T28a 契約・スキーマ・理由のコード・承認の digest・再承認の判定（純粋）→ T28b モードの拡張（T28c と並行）→ T28c 管理データの版 6（版 5 の固定を先に）とシナリオ・記録の保存 → T28d 実行の許可と予約（競合のテスト）→ T28e 画面（一覧・作成・詳細・承認・撤回・差分）と文言 → T28f 目印の検査・回帰・手順書 → T28R 独立レビュー。

## 10. ユーザーの承認が要る点

1. **承認を縛る範囲**: プロファイルのどの編集でも再承認にする（意味の違いを区別しない。止める側に寄せる）。加えて、認証の設定とターゲットの設定の digest が変わっても再承認にする。
2. **実行の許可の期限**: 5 分（許可を発行してから書き込みのジョブを始めるまで。1 回だけ使える）。
3. **承認者の記録**: 利用者の ID がないので、固定の値 `LOCAL_OPERATOR` を記録する（OS のユーザー名などは記録しない）。
4. **発見の根拠の写し**: シナリオを作るときに、候補の詳しい内容（値を持たない形。ページが書いた path・欄の名前・制約・選択肢の値を含む）を管理データに写す。
5. **書き込みのモードで許すもの**: 認証の設定・発見・READ だけ。認証つきの監査（`AUDIT`）は書き込みのモードでは今までどおり始められない。
