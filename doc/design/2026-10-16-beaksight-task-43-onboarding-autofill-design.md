## 1. 目的とユーザーの要望

ユーザーが画面で動作を確かめた所感（2026-10-16、言葉どおり。サイトの名前は伏せる）:

1. 「local\targets\<サイト名>.jsonは起動前に作成する必然性はなく、プロファイル作成時点で新規作成可能に見えた」
2. 「プロファイル作成時点で入力すべきサイト項目は監査対象のURL程度に留めるべきで、可能な限り監査時に他項目は自動的に判別すべき」
3. 「プロファイル作成後に監査が可能になるUIへの導線が悪い。初期設定⇒監査の流れをスムーズにすべき」

その後の指示: 「サイトのURLを入力した時点で、自動補完し、変更したい場合だけ入力させるUIにすることは可能なはずだ」「その形で進めて」。

目的: 利用者は**開始の URL を入れるだけ**で始められ、ほかの欄は BeakSight が埋めた案を確かめて保存する。変えたい欄だけを書き直す。プロファイルの作成から監査の開始まで、画面の中で迷わずに進める。

## 2. 前提（読み取り専用の調査で確かめた事実）

- 対象の設定のファイル（`site.startUrl`、`site.allowedOrigins`、負荷、出力）を読むのは `src/config/load-config.ts` の `loadConfig` だけ。画面の起動は読まない。起動の前に要る理由はコードになく、要るのは「プロファイルを作る前に、選択肢にファイルがあること」だけ。
- プロファイルは `targetConfigPath` で参照し、ワーカー・ジョブの管理・承認はファイルの SHA-256 を確かめる。SSOT はファイル側。`local/` は Git の管理の外で、`isAcceptedTargetConfigPath` は `local/targets/` を受ける。
- 欄の多くは、開始の URL から決められる（許可 Origin、テスト環境の Origin、監査の path、成功の画面の path）。ログインの画面の path・欄・送り方は、開始の URL を 1 回読めば分かる。token の送信先・ログインに伴う送信・承認した API の Origin・成功の鍵の名前は、手動のログインを 1 回試して観察しないと分からない。
- 「監査を始める」は一覧の「最後の Run」の列にしかなく、プロファイルの詳細・認証の設定の保存・ログインの確かめの成功のどこからも進めない。書き込みのモードではボタンが黙って消える。プロファイルを直すと認証の設定が「古い」になるが、開始の画面に入るまで分からない。文書の「左のメニューの『新しいプロファイル』」は実装と違う。

## 3. 決まり（安全）

- **埋めた値は、保存されていない案**。保存は利用者が押す。保存したものだけが通る（I14「推定値で通さない」、前のロードマップ 1.3「勝手な登録はしない」は、「案を埋めて利用者が確かめて保存する」と読み替える。ユーザーの判断。ロードマップ 12 章に記録）。
- **推定しない欄**: 環境（`PUBLIC`・`TEST`）、監査モード、確かめた記録の参照（I03: URL の文字列だけでテスト環境と見なさない）、失敗の条件（わざと失敗させない。I05）。成功の画面のセレクタは、ユーザーの判断（「ログインの後の画面から提案する」）で、4.4 の観察から案を出す。
- **負荷**: 生成する対象の設定のファイルの負荷の値は既定値（`src/config/defaults.ts`）。画面から負荷を変えない決まり（Task 24）は保つ。変えたい利用者はファイルを直す。
- **入口の確かめ**（3 段の 2）は、Guard の付いた読み取りだけの Context で、開始の URL を 1 回だけ読む（読み込み直しなし。ほかのジョブと同じ間隔を守る）。許可 Origin の外へ移るなら、移ろうとした Origin を示すだけで読まない。
- **観察した要求の登録**（3 段の 3）は、登録するまで今どおり止めたまま（I17・I19）。値を持つ path の区切り（伏せた区切り）と、query の値は登録の案に入れない。例外は、プロトコルの決まった名前の閉じた一覧（今は `grant_type`）の値だけ。ローカル ストレージは鍵の名前だけを読み、値は読まない（I22）。

## 4. 設計

### 4.1 導線（案 1）

- プロファイルの詳細に「次にすること」の欄を置く。認証の設定、資格情報、ログインの確かめ、監査の開始の 4 つを、済み・要る・要らない・古い（直す画面へのリンクつき）で並べる。判定は今の部品（`isExecutableProfile`、開始の確かめの理由）を使い、第二の判定を作らない。
- プロファイルの詳細に「監査を始める」を置く（一覧の列は残す）。書き込みのモードなど監査を始められないときは、ボタンを消さずに理由を出す（文言は表示のカタログに）。
- 認証の設定の保存、資格情報の保存、ログインの確かめの成功の後に、次の手順へのリンクを出す。
- プロファイルの作成で、監査モードを選ぶと環境と認証の方式の初めの値を組み合わせの表（`profile-policy.ts`）に合わせる。公開のモードでは、テスト環境の欄と確かめた記録の欄を隠す。
- 左のメニューに「新しいプロファイル」を足すか、文書を実装に合わせる（設計者の既定: メニューに足す）。

### 4.2 対象の設定のファイルの生成と URL からの自動補完（案 2）

- プロファイルの作成の最初の欄を「開始の URL」にする。今の「設定のファイルを選ぶ」は「すでにあるファイルを使う」として残す（CLI と前の使い方のため）。
- URL を入れると、画面がその場で埋める（区分 a）: プロファイルの ID の案（ホスト名から、規則に合う形に直す）、許可 Origin（開始の URL の Origin）、テスト環境の Origin（TEST のモードを選んだとき、許可 Origin を写す）。
- 保存のとき、サーバが `local/targets/<profileId>.json` を作る（`target.id` は profileId、`site.startUrl`、`site.allowedOrigins`、負荷と出力は既定値）。`validateConfig` を通してから書く。同じ名前のファイルがあれば上書きしない（誤りにする）。パスは固定の形だけ（任意のパスに書かない）。書く根の場所は設定で差し替えられるようにし、テストは一時のディレクトリに書く（実際の `local/` に書かない）。
- 許可 Origin を足したい利用者のため、作成の画面で許可 Origin の一覧を直せるようにする（案を埋めた欄）。
- 認証の設定の画面も、開始の URL から埋める（区分 a）: 監査の path（開始の URL の path）、成功の画面の path（開始の URL の path）、除外の path（既定の `/logout` など今の既定）。

### 4.3 入口の確かめ（区分 b。案 3 の前半）

- 新しいジョブの種類「入口の確かめ」（`ENTRY_CHECK`）。プロファイルの詳細と認証の設定の画面から始める。ログインは要らない。
- ワーカーは、Guard の付いた読み取りだけの Context で開始の URL を 1 回読み、落ち着いたら凍結し、isolated world で読む: 移った先の URL（許可 Origin の中ならその path、外なら Origin だけ）、ログインの画面に見えるか（パスワードの欄があるか）、ユーザー名・パスワード・送信のボタンの要素（それぞれちょうど 1 つの候補）と、それを指す一意な CSS（`#id`、`input[name=…]`、`[type=password]` など。一意であることを確かめる）、form の有無と form の action・method。
- 結果は、認証の設定の画面に「案」として埋める: ログインの開始の URL、セッションの切れの path、送り方（form の送信の action が許可 Origin の中で POST なら「フォームの送信」とその送信先、form がない・action がないなら「スクリプトで送る」）、自動ログインの 3 つのセレクタ。
- 負荷: 1 回のジョブで読み込み 1 回。同じプロファイルの入口の確かめは、ほかのジョブと同じ最小の間隔を守る。
- 成果物: 読んだ事実だけ（URL は伏せる部品を通す。欄の値は読まない）。管理データに結果を残し、画面が読む。

### 4.4 観察した要求の登録（区分 c。案 3 の後半）

- 手動のログインの確かめ（今のジョブ）で、ログインの段が止めた要求の一覧（ジョブの詳細の画面）の各行に「登録する」のボタンを置く。行の種類で、登録先を分ける:
  - token の送信の形（読み取りでない、別の Origin、`grant_type` の query）→ 認証の設定の送り方「スクリプトで送る」、token の送信先（Origin、path、必須の query）。
  - 認証の Origin や API の Origin → プロファイルの承認したサービスの Origin。
  - ログインの前後の手続きの呼び出し → ログインに伴う送信（Origin、path、method、回数の上限は既定 1）。
- 「登録する」は、その場では保存しない。認証の設定の画面（とプロファイル）の下書きに入れて開き、利用者が確かめて保存する。プロファイルと認証の設定の両方が変わるときは、1 回の保存で両方を書く（プロファイルの改訂で認証の設定が「古い」にならない形）。
- 記録に足すもの: 止めた要求の行に、query の名前の一覧（値なし）と、閉じた一覧の名前（`grant_type`）の値。伏せた path の区切りがある行は、ボタンを出さず、手で入れるよう案内する。
- 成功の鍵の名前: ログインの段の終わりに、ログインの画面の Origin のローカル ストレージの鍵の名前を、ログインの前と後で比べ、新しく出た名前を記録する（値は読まない）。認証の設定の成功の鍵の名前の案にする。
- 成功の画面のセレクタ（ユーザーの判断「ログインの後の画面から提案する」2026-10-16）: ログインの確かめでログインの段が終わった画面（ログインの後の画面）を、凍結の後に isolated world で読み、ログインの後にだけあると見られる要素の案を出す。設計者の既定: 候補は、ログアウトの語（閉じた一覧。除外の path の語 `logout` などと同じ owner を使う）に当たる見えるリンクやボタン、ログインの画面になかった見える `nav`・`header` の中の要素。入口の確かめ（4.3）で読んだログインの画面にもある要素は外す。案は一意な CSS（4.3 と同じ組み立ての部品）にし、ログインの後の画面でちょうど 1 つに当たることを確かめる。見つからなければ案を出さず、人が入れるよう案内する。要素の文字は案の説明に短く出すが、管理データには CSS だけを残す（画面の文字に個人の情報が入りうるため）。押さない、値を読まない。
- 利用者は「観察のためのログイン → 登録 → もう一度ログインの確かめ」を、止められる要求がなくなるまで繰り返す（毎回、利用者が押す。ログインの上限は今どおり）。

### 4.5 文書

`doc/spec/getting-started.md`、`end-to-end-usage.md`、`profiles.md`、`authenticated-audit.md`、`local-ui.md`、`real-test-environment.md`: 起動の前にファイルを作る手順を「URL を入れて作る」に直す（前の使い方も残す）。入口の確かめと、観察した要求の登録の手順。「左のメニュー」の記述の誤り。

## 5. 受け入れ条件（G43）

1. 開始の URL だけを入れて、プロファイルの作成から（公開のモードの）監査の開始まで、画面の中のリンクだけで進める（画面のテスト）。
2. 生成したファイルが `validateConfig` を通り、CLI の `--config` でも読める。同じ名前があれば上書きしない。テストは実際の `local/` に書かない。
3. 入口の確かめで、fixture（form のあるログイン、form のないログイン、許可 Origin の外へ移るログイン）の案が正しく埋まる。読み込みは 1 回、読み取りでない要求は 0（両方の Chromium）。
4. 手動のログインの観察で止めた token の送信・手続きの呼び出し・API の Origin を「登録する」で下書きに入れ、保存した後のログインの確かめで通る（`startSpaAuthSite`）。保存の前は止まったまま。伏せた path の行にはボタンがない。
5. 成功の鍵の名前の案が出て、値は管理データ・成果物・画面に出ない（目印の検査）。
6. 回帰: 今のプロファイル・認証の設定・開始の確かめ・CLI のテスト。独立レビュー（Critical 0、Important 0）。`verify:all` は GD の前の 1 回にまとめる。
