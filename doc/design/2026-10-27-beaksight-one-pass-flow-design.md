## 2. 新しい流れ（案）

| 段 | 画面 | 利用者がすること |
| --- | --- | --- |
| 1 サイトを足す | 作成 | テスト環境のアドレスを入れる。「ログインが必要なサイト」か「ログインしなくても見られるサイト」を選ぶ。必要なら ID とパスワードを入れる。「点検を始める」を押す |
| 2 下調べと点検 | 作業の画面（自動で進む） | なし。サイトの下調べ（今の入口の確かめ）→ 自動ログイン → 点検 → 操作さがし を、まとめて進める。ログインが済んだかは BeakSight が判定する |
| 3 結果 | サイトの画面 | 結果の要点と「結果を見る」。下に「登録・更新を試せる画面」の一覧（チェックの欄）と「チェックした画面で試す」の 1 つのボタン |
| 4 書き込み | 同じサイトの画面（移らない） | なし。BeakSight が、チェックした画面ごとに登録 →（あれば）更新を行い、行ごとに結果を出す |

- 手動ログインは、サイトの設定（詳しい内容）で切り替えるときだけ使う。
- 本番からの切り離しは、聞かない・出さない（責務の外）。テスト環境のアドレスは、利用者が入れたものを使う。

## 3. 守るもの（変えない）
- 読み取りの点検で、GET・HEAD のほかを送らない。
- 書き込みは、チェックして OK を押した画面だけ。1 つの画面につき、登録 1 件と更新 1 件まで。送り直さない。間隔は 10 秒。
- 自動ログインの 5 分・24 時間 10 回の決まり。
- 資格情報は、BeakSight が観察した送り先にだけ送る（MI 4.7.1）。最初の自動ログインの扱いは 4 章で決める。
- 結果の正直さ。番号が取れないときは「一部だけ確かめた」と出す。

## 4. 決めること（調べ FV-1 の後に確定）
1. 最初の自動ログインを、手でのログインの観察なしに行えるか。
   - ID・パスワードの欄と送信のボタンの案を、下調べだけで出せるか。
   - 最初の自動ログインで観察した送り先を、MI 4.7.1 の「観察」として扱ってよいか。
2. 「ログインを終えた」をなくしたとき、ログインが済んだことを判定する手がかりがいつも取れるか。
3. 画面の一覧でまとめて OK にするとき、今の承認と許可の仕組み（digest、許可、上限）をそのまま中で使えるか。OK の 1 回の押下が「承認」と「開始」を兼ねる形にできるか。
4. 更新の欄を BeakSight が決める規則。登録で入れた、ふつうの文字の欄から選ぶ。
5. 書き込みのモードの切り替えをなくし、一覧の OK で内側で切り替える形にしたとき、操作さがしの古さ（U5）の扱い。自動の登録の後の改訂の進みも含める。

### 4.1.1 ユーザーの指示による置き換え（2026-10-27）

ユーザーの言葉: 「登録・更新が発生していても、それは監査の流れの一部に過ぎない。読み取りの監査の流れの中で、許可した（一覧でチェックした）画面については登録・更新も実施するというだけ。わざわざ処理フローを分ける必要もない。」

これで、D7〜D9 を次の D7'〜D9' に置き換える。

| # | 決めたこと |
| --- | --- |
| D7' | 書き込みは、別の作業にしない。点検（まとめて実行）の 1 つの作業の中で、一覧でチェックした画面だけ、登録 →（あれば）更新も行う。チェックは、サイトの画面の「登録・更新を試せる画面」の一覧で行い、保存しておく（次の点検から効く）。チェックの保存が、その画面への書き込みの許可（今の承認に当たる）を兼ねる。確認のダイアログは置かない。何が起きるかは、一覧の上の 1 行で出す（「チェックした画面では、点検のときに、テスト用のデータを 1 件登録し、1 回更新します。作ったデータは消しません。」）。チェックを外すと、次の点検から書き込まない |
| D8' | 1 回の点検の中で、チェックした画面を順に試す。送るのは、1 つの画面につき登録 1 件と更新 1 件までで、送り直さない。読み込みの間隔（10 秒）は、読み取りと同じに守る。結果が分からない画面や、安全の違反があった画面の後は、残りの書き込みを止める（読み取りの点検は続けてよいか、止めるかは FV-2 で決める） |
| D9' | ログインは、点検の 1 回だけで、書き込みにもそのまま使う。作業の外へログインの状態を持ち出さない。そのため、ログインを使い回すための仕組みは作らない |

まだ決まっていないこと（FV-2 で、作り方と安全の境目を調べる）:
1. 1 つの作業の中で読み取りと書き込みを行うときの、文脈の分け方。今は、読み取りの文脈（Passive）と、操作の文脈（Isolated Interaction）を分けている。
2. 今の承認の記録・digest・許可・上限（5 分・24 時間）を、作業の中の画面ごとの書き込みに、どう当てるか。
3. 読み取りの点検の「GET・HEAD のほかは送らない」の保証と報告を、どう分けて書くか。
4. 書き込みのモード（`TEST_APPROVED_WRITE`）の切り替えを、チェックの保存の中で行う形。

### 4.1.2 書き込みの段の作り（FV-2 の結果による。2026-10-27）

**作り（案 C）**
- 書き込みは、今の「まとめて実行」の連鎖（監査 → 発見 → READ の確かめ）の最後に、段を足して行う。足す段は、チェックした画面ごとの登録 →（あれば）更新。
- ログインは連鎖の 1 回だけ。ログインの状態・pacer・1 分の窓は、今の `RunStageCarry` でワーカーのメモリの中だけで渡す。IPC・ディスクには出さない。
- 書き込みの段は、今の書き込みの流れをそのまま使う。凍結した Passive の文脈で確かめ、Isolated の書き込みの段の文脈で送る。文脈は段ごとに分ける。
- 親は、書き込みの段の前ごとに次を行い、`NEXT_STAGE` に書き込みの指定を載せる。段の終わりに締める（`#settleWrite`）。
  - 許可の発行（`issueExecutionGrant`）
  - 書き込みの準備（`#prepareWrite`）
- 書き込みの段の Run と報告は、段ごとに分ける。監査・発見・READ の報告は今のまま「読み取りだけ」。点検の要点に「チェックした画面では登録・更新も行った」の 1 行を足す。

**チェックの保存**: 次の 2 つを行う。
- 今の承認（`approveScenario`。承認の記録と digest）
- 書き込みのモードへの切り替え

点検の途中で切り替えると、連鎖は改訂の変化で止まるため、切り替えは保存のときに済ませる。

**FV-2 の実験**: 127.0.0.1 の fixture、2 つの Chromium で行った。結果は次のとおり。
- ログインは 1 回。
- 登録・更新・登録の 3 件が VERIFIED で、POST はどれも 1 件。違反は 0。
- 境目を含め、読み込みの間隔を守った。
- 3 件で約 30 秒かかった。

**残っていた 4 点の判断**

| # | 判断 |
| --- | --- |
| R1 更新の画面の候補 | （2026-10-28 に改めた）更新の画面は、データがあるときにしか見つからない。データのないサイトでは、チェックした画面の 1 回目の点検は登録だけにし、行に「更新は、次の点検で試します。」と出す。次の点検の操作さがしで、その画面の更新の候補が見つかったら、BeakSight がチェックの範囲の中で、自動で更新の下書きと承認を行い、同じ点検で更新する。人は何もしない。前の案（登録の後の小さな発見）は採らない。小さな発見が最後の発見を書き換え、ほかの承認を `CANDIDATE_MISSING` にするため（OP-2 の Blocker） |
| R2 書き込みの途中でログインが切れた | ログインし直さない。残りの書き込みを止め、行に「ログインが切れたため試せませんでした」と出す（D9'） |
| R3 認証の設定が変わって、チェック（承認）が無効になった | 自動で承認し直さない（守りを弱めない）。無効の行は、チェックを外した形で出し、「もう一度チェックしてください」の 1 行を出す。チェックは、1 回目の点検の後（D4 の自動の登録の後）に行うので、ふだんは起きない |
| R4 送らずに止まった回の値 | 生成の履歴に入るので、値の候補が少ない規則では、やり直しが `WRITE_DATA_NOT_GENERATED` になる。規則 F と汎用の作り物の文字で当たらないことを、OP-2 のテストで確かめる |

### 4.1.3 ログインの側の作り（OP-1 の Blocker への判断。2026-10-27）

1. **値の保存と、D4 の登録**: 同じワーカーの中で行う。
   - 親は、`START` に受け取りを許す印を入れる。ワーカーは、値のない受け取りのメタデータを `AUTH_STATE` に載せる。
   - 書く順は、次のとおり。
     1. 親が登録を組み立て、検証で通ることを確かめる。
     2. 親がワーカーに許しを返す。
     3. ワーカーが資格情報のファイルを書く。
     4. 親が、登録と自動ログインへの切り替えを 1 回で保存する（`saveProfileAndAuthSetup`）。
     5. 4 が失敗したら、親が資格情報のファイルを消す。
   - 親からワーカーへ、新しい設定（`LOGIN_REGISTERED`）か、飛ばしたこと（`SKIPPED`）を送る。プロトコルの版を上げる。
   - 連鎖は、親が自分で進めた改訂だけを基準として受け入れる。
   - 受け取るのは、資格情報のファイルがないときだけ。
   - 3 つのセレクタがそろわないときは、手動のまま続け、受け取った値は捨てる。
   - 自動ログインへの切り替えの中身は、`src/control/auth/` の 1 か所に移す。
2. **D5 の設定**: プロファイルに任意の項目 `loginPreference`（`AUTOMATIC`・`MANUAL_EVERY_TIME`）を足す。省けば `AUTOMATIC`。今のプロファイルは、そのまま読める。
3. **作成の画面のボタン 1 つ**: 下調べの後に点検を始める判定は、ジョブの管理の 1 か所で行う。
4. **「ログインを終えた」**: BeakSight がログインの終わりを判定できるときは出さない。判定できるかの印は `AWAITING_LOGIN` に載せる。
5. **DEF-181**: 手動と自動の両方のログインの段で、空の成功の条件をそれだけでは成功にしない。
