# 設計書 — 手動のログインの間は、ページの送信を止めずに通す

状態: ユーザー承認済み（2026-10-19「今すぐ直す（推奨）」）
作成: 2026-10-19（設計者）

## 1. 目的と経緯

実テスト環境の確かめで、手動のログインの画面のログインの送信（外部の認証のサービスへの token の送信）と、ページが読み込みで出す手続きの呼び出し（テナントを決める呼び出し）を、ログインの段の Guard が止め、ログインできなかった（`ERR_BLOCKED_BY_CLIENT`。サイトには届いていない）。原因は、プロファイルの認証の設定が版 2（フォームの送信）のままで、ログインの段の Guard が「登録した送信先だけを通す」決まりを、人が操作する手動のログインにも当てていたこと。

ユーザーの指摘: 「手動ログインの手間を許容しているにも関わらず、ログインまでブロックされるのは意味が分からない」。ユーザーの判断: 手動のログインの間は、ページの送信を止めずに通し（形だけ記録）、利用者が「ログインを終えた」を押したら状態を保存して監査に進む形に、今すぐ直す。

## 2. 設計

### 2.1 手動のログインの段の Guard（通して記録する）

- 手動のログイン（人が headed の Browser で操作する段。`authenticated-login.ts`）の Context では、ページが出す読み取りでない要求を止めずに通す。対象は、ログインの送信、手続きの呼び出し、事前確認（`OPTIONS`）などで、普通のブラウザと同じ振る舞いにする。
- 通した要求の形を記録する。項目は Origin・path・method・資源の種類・query の名前と数で、今の「ログインの段で止めた送信」の表と同じ形・同じ上限にする。値（本文、query の値、ヘッダの値、Cookie、token）は記録しない。query の値を記録しない決まりは、今の記録の部品（秘密に見える名前の扱いを含む）に合わせる。
- 次の守りは今のまま残す: ダウンロード、外部のアプリの起動（`tel:` など）、Guard が閉じた後の要求、資格情報の目印の確かめ（自動ログインの段のもの）、WebRTC の止め方、出口の中継。
- 認証の設定の版 3 の「登録した送信先だけ通す」決まりと回数の上限は、自動ログインの段だけに当てる（自動ログインは人が見ていないため、厳しさを変えない）。
- 監査・発見・READ の確かめ・書き込みの段の Guard は変えない（読み取りだけ）。

### 2.2 ログインの終わり

- 今の成功の条件（成功の path、セレクタ、成功のローカル ストレージの鍵）に当たれば、今どおり成功とする。
- 加えて、利用者が画面のジョブの「ログインを終えた」を押したら、成功とする。親からワーカーへ、ログインを終えた知らせ（IPC の新しい形）を送る。ワーカーはそれを受けたら、今の成功の後の手順（状態の取り出し、許可 Origin への絞り込み、空なら `UNSUPPORTED_AUTH_STATE`）に進む。
  - 状態の絞り込みでは、許可 Origin に加えて、プロファイルの承認したサービスの Origin の Cookie と localStorage も残す（今の決まりに合わせる。広げない）。
- 知らせは、ジョブが `AWAITING_LOGIN` のときだけ受ける。ほかの状態では、親が拒む。
- 時間の上限（`LOGIN_WAIT_TIMEOUT_MS`）と止める印は今のまま。

### 2.3 手動のログインの成功から、Guard を通るための設定を自動で登録する（ユーザーの指示 2026-10-19「一度、手動ログインに成功したら、その情報を元にガードを通るための必要な情報は登録するにようにして」）

- 手動のログインが成功したら（成功の条件に当たった、または「ログインを終えた」）、親は、通した送信の記録とログインの後の状態の鍵の名前から、認証の設定の版 3（スクリプトで送るログイン）と、プロファイルの承認したサービスの Origin を組み立て、利用者の追加の操作なしで保存する。保存した中身は、ジョブの画面とプロファイルの画面に「自動で登録した設定」として出し、利用者が見直して直せるようにする。
- 組み立ての決まり（今の「登録する」の案の部品（Task 43 の `login-observation-draft.ts` など）を使い、複製しない）:
  - token の送信先: ログインの段で通した読み取りでない送信のうち、ログインの送信の形（今の案の部品が token の送信と見分けるもの。例: query `grant_type`）のもの。Origin・path・必須の query（名前と、今の設計で写してよい値。秘密に見える名前の値は写さない）。
  - ログインに伴う送信: 成功の前に通した、token の送信のほかの読み取りでない送信。回数の上限は、見えた回数（上限は今の閉じた上限の中）。path に危険な語（削除・ログアウトなど、今の閉じた一覧）があるものは入れない。
  - 承認したサービスの Origin: 上の送信の送り先の Origin。プロファイルの許可 Origin（監査の対象）は入れない。
  - 成功のローカル ストレージの鍵: ログインの後に、許可 Origin に現れた鍵の名前から、今の提案の部品（一般の語の終わりだけ。Task 43）で選ぶ。値は読まない。選べなければ、成功の条件は今の path の条件のまま。
- 自動ログインの段は、この登録した設定で、今の厳しさ（登録した送信だけ、回数の上限）のまま動く。
- 保存すると、プロファイルの改訂が進む。承認済みのシナリオや発見の結果は、今の決まりどおり、やり直しが要ることがある（画面に出す）。
- 通した送信の記録は、ジョブの画面の表（今の「ログインの段で止めた送信」の表を「ログインの段の送信」として、止めた・通したを分けて出す）にも出す。

### 2.4 画面

- ジョブの画面で `AWAITING_LOGIN` のとき、「ログインを終えた」のボタンと説明を出す。説明の中身: ログインの間の操作はサイトへ送られる。ログインが済んだら押す。
- 手動のログインの説明（`doc/spec/authenticated-audit.md` など）を直す。

## 3. 安全と影響

- 手動のログインの間に、ページが出す読み取りでない要求は、サイトへ届く。これは人が普通のブラウザで操作するのと同じで、利用者の操作の結果として扱う。この決まりは、手動のログインの段だけに当てる。
- 資格情報と token の値は、記録・IPC・成果物に出さない（今の決まり）。
- 自動ログインと、監査の段の安全の不変条件は変えない。
- 「判定できない」への影響: 減る（設定がなくても、手動のログインで先へ進める）。

## 4. 受け入れ条件

1. fixture（スクリプトで token を取りに行く SPA）で、認証の設定が版 2 のままでも、手動のログインで token の送信と手続きの呼び出しが届き、「ログインを終えた」で監査に進める。
2. 成功の条件に当たる場合は、ボタンを押さなくても今どおり進む。
3. 通した送信の形が記録され、値（パスワード、token、query の値）は、管理データ（WAL を含む）・成果物・IPC・画面に出ない。
4. 自動ログインの段は、今どおり登録した送信だけを通す（回帰）。
5. 監査の段は、今どおり読み取りだけ（回帰。両方の Chromium）。
6. 独立レビューで Critical 0・Important 0。
7. 手動のログインの成功の後、認証の設定の版 3 と承認したサービスの Origin が自動で保存され、次の自動ログインがその設定で通る（fixture。登録した送信だけが通り、回数の上限が効く）。危険な語の path は登録されない。値（パスワード、token）は保存されない。
