# BeakSight 操作さがしで、サイトの token の更新を止めて後半の画面が 401 になる（DEF-233）設計書

- 日付: 2026-11-09
- 状態: ユーザーの指示「DEF-233を直して」（2026-11-09）。方式は設計者の判断（調査の推奨）
- 関係する文書: `2026-11-04-beaksight-login-session-design.md`（DEF-191・193・200）、`2026-10-17-beaksight-task-37-*`（T37R-fix-B の受け継ぎの決まり）、`2026-10-20-beaksight-service-request-pacing-design.md`
- 調査: INV-233（2026-11-09。仮のサイト、2 つの Chromium、試作の写しで A・B を確かめた）

## 1. 原因（実験で確かめた事実）

1. 操作さがしは、各画面で候補を読んだ直後に Interaction の凍結を始める（`src/discovery/discover-page.ts:238`）。凍結の間は、読み取りでない要求を全部 `BLOCK_FROZEN` で止める（`passive-request-guard.ts:4568-4594`）。中継も、凍結の後は GET・HEAD だけ通す（`egress-proxy.ts:707`、`context-factory.ts:653`）。サイトのスクリプトの token の更新が、凍結の間に来ると届かない。
2. 凍結で止めた更新は `tokenRefreshBlocked` に数えない（記録の抜け）。
3. 次の画面へ渡す状態は、押す前に読んだもので固定する（`context-factory.ts:2238`・`:2269`）。凍結の間に更新できても、次へ渡らない。
4. 401 は数えるだけで、セッションの切れとみなさない。DEF-200 のログインし直しが働かない。
5. 実環境の `otherNonReadBlocked`・`allowedOriginDataRequestsBlocked` の 15 は、401 を受けたサイトのログアウトの送信を止めたもの（結果であって原因ではない）。

推測（未確認）: 本来のサイトのスクリプトは、読み込みの時ではなくタイマーで更新する。

## 2. 採用する設計（A1 + A2 + B）

### 2.1 A1: 凍結の段でも、サイトの token の更新を通す

1. 通す対象は次の全部を満たす要求だけ。
   - 監査の段の判定で `TOKEN_REFRESH` になる形（登録の token の送り先、必須の query の値が違う POST）。
   - 監査の送信の扱いが `PASS_EXCEPT_DELETE`。
   - 危険な語がない。資格情報を含まない（今の `credentialCheckedDecision`）。
   - 本文に、押すときに欄へ入れた目印（marker）を含まない。
2. 当てる所は 3 か所すべて: Guard の凍結の判定、凍結の段の CORS の事前確認（`frozenPreflight`）、中継の凍結の受け入れ（`egress-proxy.ts:707`、`context-factory.ts:653`）。部品は 1 つにし、3 か所で共用する（判定を複製しない）。
3. 通した数と止めた数を記録する。凍結で止めた更新も `tokenRefreshBlocked` に数える（記録の抜けを直す）。
4. 通した更新は、押下の観察（送信の形の記録）に混ぜない。混ざると候補が `MULTIPLE_REQUESTS` になる（INV-233 の追加の発見）。

### 2.2 A2: 押した後に更新された、ログインの鍵だけを次の画面へ渡す

1. 次の画面へ渡す状態は、今のとおり押す前に読んだものを基にする（T37R-fix-B。押下でページが書いたほかの storage は渡さない）。
2. その上に、閉じる前の状態から、プロファイルのログインの成功の鍵（接頭と接尾の決まり）に当たる値だけを重ねる。決まりは今の成功の判定の部品を共用する。

### 2.3 B: 承認したサービスの Origin の 401 が続いたら、セッションの切れとして扱う

1. 操作さがし・READ の確かめ・監査の段で、ある画面の読み込みで、承認したサービスの Origin から 401 を受け、その画面が `SERVICE_READ_REFUSED` になったら、セッションの切れ（新しい詳しい理由 `SERVICE_UNAUTHORIZED`）として扱い、DEF-200 のログインし直しへ回す（K = 1 画面）。
2. 切れた画面の結果は採らず、ログインし直した後に読み直す（DEF-200 と同じ）。
3. 回数の上限は DEF-200 のまま（段ごとに 2 回、自動ログインの間隔 5 分・24 時間 10 回）。上限に当たったら今の止まり方。
4. 手動のログインのプロファイルは、今のとおりログインし直さない。
5. 書き込みの段では行わない（今のとおり）。

## 3. 変えないもの

- 押した送信は届けない（凍結の判定の、更新の形のほかの要求は今のまま止める）。
- 監査の段の判定、ログインの段の守り、受け継ぎの「最後に閉じた Context」の決まり。

## 4. サイトへの負荷

- A: 増えるのは、サイトのスクリプト自身の token の更新だけ（期限ごとに数回）。
- B: ログインの送信が、切れたときだけ 1 回（実環境なら約 1 時間に 1 回、段ごとに最大 2 回）。読み直しが 1 画面。

## 5. 限界

1. 権限などで本当に 401 を返す画面では、B が空振りのログインし直しをする（段ごとの上限 2 回で止まる）。
2. 更新の形が登録の token の送り先と違うサイトは、A では救えない（B が受ける）。

3. 凍結の段で更新を通すのは、凍結の前に「Guard が通し、2xx を返し、応答で成功の鍵が実際に更新された」と確かめた更新と、本文の形・header・query の値が同じものだけ（SREV-233 の 3 回のレビューの後の決まり）。凍結の前に確かめた更新がない Run では通さず、B のログインし直しが受ける。
4. 本物の形の更新を、ページがいつ・何回送るかで情報を運ぶ通り道は残る。本物の更新を通す限り塞げない。戻すにはサーバの記録が要る（SREV-233 の M-2）。
5. 監査の段の B は、承認したサービスの Origin の 401 が 1 件でもあればセッションの切れとみなす（SREV-233 の M-4）。権限で 401 を返す画面があると、ログインし直しを上限まで行ってから止まる。

## 6. テスト

- 仮のサイト（INV-233 の `inv233/site.ts` を一般の文言で写す。token の期限はテストの値（数秒。操作さがしの長さが期限を越えることを期待で確かめる）、鍵を回し使い回しで取り消す、タイマーで更新、401 でログアウトの POST）。
  - M1（凍結中にタイマーが当たる）: 401 が 0、更新は今の鍵で回る、`API_CREATE` が取れる。
  - M2（更新の間隔が 1 画面より長い）: ログインし直して読み直し、残りの画面が 401 にならない。
  - 押した送信の到着は 0（サーバの記録。名前つきの時間待って数え直す）。目印を含む更新・危険な語・DELETE・資格情報は届かない。
- 2 つの Chromium。既存の操作さがし・凍結・ログイン・DEF-191・DEF-200 のテストが通る。
