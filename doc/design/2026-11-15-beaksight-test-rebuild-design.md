## 1. 背景
- 遅い組は 95 ファイルで、約 112 分かかります。速い組の全部は約 80 分です（SLIM-6、2026-11-15）。テストを細くするだけでは、目標に届きませんでした。
- 調べ（INV-SLIM7、scratchpad の `inv-slim7/design.md`）で、遅さの元は製品の作りにあると分かりました。元は次の 4 つです。
  - 判定とブラウザの操作が混ざっている。
  - 決め打ちの待ちがあり、テストから差し込めない。
  - 段ごとの入口がない。
  - Browser をそのつど起こし直している。
- ユーザーの指摘（2026-11-15）は次の 4 つです。
  - 「実測ではなく、設計的な問題点があるはずだ」
  - 「ブラウザを使うテストも、必ずしも全てのテストをブラウザで動作させる必要があるのか」
  - 「偽のブラウザが本物とずれる点をピンポイントでテストしているか。全てのテストの前提にチェックを入れているのでは無駄」
  - 今のテストは、どの場面でも本物のブラウザで「サーバに読み取り以外が届いていない」「遅れて届く分」を確かめ直しています。これが重さの大きな元です。

## 2. 決まり
1. **ブラウザに頼む口（port）を 1 つに決める。**
   - 判定と段の進め方は、Playwright を直に呼びません。口を通して頼みます。
   - 口が受け持つ操作は、次のとおりです。
     - 画面を開く
     - DOM・部品の位置・アクセシビリティを読む
     - 押す・入れる
     - 通信を観る
     - 送信を止める・通す
     - Context を作る・閉じる
   - 口の中身は 2 つ用意します。
     - 本物（Playwright の adapter）
     - 偽（メモリの中のページと通信の記録）
   - 口の型の唯一の owner を決めます（SSOT）。置き場所は、INV-REBUILD の後に決めます。
2. **ずれの確かめ（contract tests）を、狙いを絞って 1 か所に置く。**
   - 口の操作ごとに、本物の Chromium で確かめます。確かめるのは「本物の口が、偽の口と同じ答えを返す」ことです。
   - 通信の通り道ごとに、代表を 1 本ずつ置きます。通り道の例は、先読み、閉じるときの送信、beacon、ポップアップ、Worker、WebSocket、WebRTC、外のスキーム、移動、form の送信です。確かめるのは「口で止めたら、本物の Chromium でもサイトに届かない」ことです。
   - ここだけは、両方の Chromium で流します。対象は、テストの既定（headless shell）と CLI の起動の設定（本番）です。BeakSight では、両者の振る舞いの違いで漏れを見落としたことがあります（DEF-030）。
   - ブラウザ（Playwright）の版を上げるときは、ずれの確かめを必ず流します。
3. **ほかのテストは、口の答えを前提として信じ、確かめ直さない。**
   - 判定・段の進め方・書き出し・伏せ字・画面のサーバのテストは、偽の口で流します。
   - 「サーバに届いた数 0」「遅れて届く分の数え直し」は、ずれの確かめの中にだけ置きます。ほかのテストには入れません。
4. **待ちは、すべて差し込めるようにする。**
   - 落ち着き・静まり・観察・閉じる前・移動の間隔・ログインの間隔の待ちを、1 つの「観察の窓の一式」にまとめます（SSOT）。テストは、偽の時計か短い値を渡します。
   - 本番の入口が本番の値を使っていることは、Gate で守ります（TEST-TIME-B の 3 つの条件）。
   - 利用者が触れる口は作りません。
5. **段ごとの入口を作る。**
   - 点検の連鎖の各段（発見・READ・監査・書き込み）に、前の段の結果を与えて入れるようにします。テストだけが使う入口です。
   - 本番の順（承認を確かめ直すことなど）は変えません。
6. **Browser・画面のサーバは、ファイルごとに 1 回だけ起こす。**
   - 場面ごとには、Context か入れ物だけを新しくします。
   - 画面のサーバは、テストの中で依存を差し込んで直に起こせるようにします。対象の依存は、ジョブの管理・データの置き場所・資格情報の守りです。
7. **テスト用のサイトは、確かめたい画面に 1〜2 ページで届く最小にする。**
8. **時間の目標**
   - 1 場面（it 1 本）を 5 秒以内にします。
   - 例外は、名前を書いた一覧だけに限ります。対象は次の 4 種類で、合わせて 5〜10 本を目安にし、区切りに流す組に置きます。
     - 利用者の流れを、端から端まで本物で通すテスト
     - 秘密が全部の出口で残らないことを、端から端で確かめるテスト
     - Windows の本物の機能（DPAPI・process の強制終了）を使うテスト
     - ずれの確かめの両方の Chromium の回
   - 端から端の例外は、1 本が数分かかってよいとします（ユーザーの判断 2026-11-15）。ただし、同じ観点を何本もの端から端で繰り返しません。観点ごとに 1 本だけにし、観点の一覧と、それを確かめる 1 本を Gate で照らします。
   - 場面ごとの時間を見張る Gate を足します。ユーザーの判断（2026-11-15）で、次の作りにします。
     - 秒の値は、テストやコードに直に書きません。テスト用の設定ファイル（例: `tests/test-time-limits.json`）の 1 か所に持たせます（SSOT）。
       - 1 場面の上限（既定 5 秒）
       - 例外の一覧（ファイルと場面、それぞれの上限）
     - 見張りは、共通の処理 1 つで行います。例は vitest の setup か reporter です。各テストのファイルには書きません。
     - 設定ファイルの形と、例外の各行に理由があることは、Gate で確かめます。5 秒を超えたら落とし、例外の一覧にないものは通しません。
9. **送信を止める作りは、決まった守りだけにする**（ユーザーの方針「削除以外止めない」、2026-11-15 に確かめ直した）。
   - 残す守り:
     - 削除を止める（見せかけの削除を含む）。2026-11-16 から、BeakSight が削除に関する操作をしない（操作の前に判定する）形に変えた。サイト自身の通信は止めない（`2026-11-16-beaksight-action-based-delete-guard-design.md`）
     - 発見の probe で押した後の凍結
     - 資格情報の送り先の守り
     - 自分の移動の間隔
     - 自動ログインの間隔と回数
     - 秘密を記録に残さない守り
     - 人が選んだときの READ_ONLY
     - 外のアプリを起こさない（tel:・mailto: など。ユーザーの判断 2026-11-15）
   - これ以外の「止める」作りは、部品ごと外す。例は、Passive の GET・HEAD 以外の既定の止め、先読み・報告・WebRTC・Worker の止め、件数の上限。
   - 2 の通り道ごとの代表は、残す守りが要る通り道だけに置く。
10. **安全の受け入れは弱めない。**
   - 5 つの守りと、秘密を残さない守りの受け入れは、次の 2 つで確かめます。
     - 偽の口の判定のテスト（全部の組み合わせ）
     - ずれの確かめ（通り道ごとの本物の代表）
   - どちらかが欠ける守りは作りません。

### 3.2 送信を止める作り（2 章の 9 の 8 つの守り）
- Guard を「既定は通す。止めるのは削除・凍結・資格情報。READ_ONLY は判定 1 行」に裏返します。外す作りは X1〜X14 です（plan.md 3 章 A）。見込みは src 約 −3,000〜4,300 行です。
- ユーザーの判断（2026-11-15）:
  - **サイト自身が出す通信は止めない。** 書き込みの最中に、サイトが出す予定にない送信も止めません（削除は止めます）。BeakSight が送る書き込みの中身が、承認した中身と合っているかの照合は、BeakSight 自身の送信として残します。
  - **ログアウト・取り消しの語を持つボタンや移動は、止めたまま残します**（途中でログインが切れて、判定できないが増えるのを避けるため）。
  - **READ_ONLY は「読み取り以外の送信を止める」**にします。WebSocket・WebRTC などのリアルタイムの通信は止めません。
  - **ブラウザ自身の外への接続（Google など）は止めません。**
- 設計者の判断:
  - サイトに負荷をかけないための止め（ページが自分で読み込み直す輪など）は、「監査対象のサイトに過負荷を与えない」方針に当たるので残します。
  - Worker の中の WebSocket の CSP は、凍結（守り 2）に要る場合だけ残します。要るかどうかは、RB-4 の段で確かめてから決めます。
- 利用者に見える変わり目: ページの script が自分で送る form の POST は、通るようになります。
- RB-4a の後の設計者の判断（2026-11-15。外す前に読みで確かめたら、守りに要る作りがあったもの）:
  - X4（CORS の事前確認を Guard が返す作り）: 残します。凍結の段の事前確認の扱いに要ります。ほかの Origin への事前確認も、通す作りなので、今のままにします。
  - X6（WebRTC の止め）: 起動の引数（ブラウザ全体の UDP の止め）は外します。サイト自身の通信は止めない方針に合わせるためです。初期化のスクリプトは、凍結しうる Context（Interaction・probe）にだけ残し、凍結の迂回を防ぎます。RB-4b で行います。
  - X9（外のスキームの検出と記録）: 残します。守り 8（外のアプリを起こさない）の記録と指摘、probe の判定に使うためです。
  - X13（起動の引数）:
    - 先読みの止めは残します。守り 1 とログアウトの語の止めに要ります。
    - 報告の機能・FedCM の止めは残します。凍結の後に Guard を通らずに届くので、守り 2 に要ります。
    - ブラウザ自身の Google などへの接続は、ユーザーの判断どおり止めません。出口の中継と記録の扱い（中継が通す、止めた送信の指摘に数えない）は、RB-4b の X10 といっしょに直します。
  - `AUDIT_SEND_OVER_LIMIT` は、もう作られません。前の記録を読むために、理由の値の一覧には残します。
- REV-RB4 の後の判断（2026-11-15）:
  - DEF-275（Critical）: 凍結しうる Context では、Worker の WebSocket を止めます。submissionObservation は、凍結する PRIMARY（発見・READ の確かめ・入口の確かめ・書き込みのジョブの読み取り）にだけ付け、監査の Run の PRIMARY には付けません（factory の印 `pageAuditRun`）。監査の PRIMARY は、Worker のリアルタイムの通信を止めません。
  - REV-RB456 の後の判断（2026-11-15）:
    - DEF-276（Important）: DEF-275 の直しで、凍結しうる Context の文書の WebSocket が、凍結の前から CSP で止まるようになりました。サイト自身の通信は止めない方針に合わないので、次の 2 つで直しました（ユーザーの判断「基本方針は既に伝えた通り」）。
      - ws を止める CSP は、凍結の後に押す Context（操作さがしの PRIMARY。factory の印 `submissionProbeRun`）だけに当てます。READ の確かめ・入口の確かめ・書き込みのジョブの読み取りでは、WebSocket を止めません。印のない観察の口では、押す道と最初から凍結の道が開きません。
      - 操作さがしの PRIMARY では、文書の WebSocket を Node の側で出口の中継を通してつなぎ（`src/safety/websocket-relay.ts`）、凍結の前は届けます。凍結の時に切ります。
    - DEF-276 の限界（守りは破れない）:
      - 操作さがしの画面では、Worker の WebSocket は凍結の前から止まります。https で凍結の後に確実に止める手が、CSP しかないためです。止めたことは記録に残ります。
      - 中継した接続では、サーバの選んだ subprotocol をページに返せません。ページには申し出の最初のものが見えます。
      - 証明書の確かめは Node の側です（同梱と OS の置き場所の CA）。クライアント証明書は送れません。
      - Origin は、page の main frame の Origin です。宛先が別 Origin の iframe の 1 つとだけ同じ site なら、その Origin です。決まらないときは付けません。同じ site の判定は「同じ host か、後ろの 2 つの label が同じ」の近似で、2 段の接尾辞の国の domain では、別の site を同じ site とみなすことがあります。
      - Lax・Strict の Cookie は、Cookie の Domain が main frame の host にも当たるときだけ送ります。ブラウザより狭い扱いです。
      - 握手に失敗したとき、ページには close だけが届き、`error` の事象は出ません。`bufferedAmount` はいつも 0 です。送りの列は 16MiB を上限にし、超えたら閉じて記録します。
      - Accept-Language・client hints・圧縮の拡張のヘッダは送りません。
  - REV-RB13 の後の判断（2026-11-15）:
    - DEF-279: 押した後の落ち着きの待ちも、使えなくなった文書を見放す仕組みで囲みます。押下が外のスキームへ移ったなど、文書が使えないと分かった押下は、観察を最短の長さで打ち切ります。その候補の結果は外のスキームとして記録し、Context も閉じるので、記録の欠けにも漏れにもなりません（REV-RB13 の実機の実験で、両方の Chromium で確かめました）。
  - REV-RB14 の後の判断（2026-11-16）:
    - 見るだけの点検の、知らせの枠を閉じる押下の期間は、URL に資格情報がある読み取りでない送信だけを止めます（X11 を外した）。削除の止めは押す期間も効きます。移った画面は今どおり点検しません。
    - CORS の事前確認: 凍結しない Context で送信の扱いが PASS_EXCEPT_DELETE のときは、許可 Origin と承認したサービスの Origin への事前確認もサーバへ転送し、サーバの答えに従います（前は Guard が答え、サーバが拒む書き込みもブラウザが送っていた）。凍結の段・READ_ONLY・通さない要求は、今どおり Guard が答えます。
    - ログインの段の Context の WebSocket は止めたままにします。資格情報の送り先の守り（守り 3）は HTTP だけを照らすので、通すと照らされない道になるためです。
    - Passive のダウンロードの取り消しと、許可 Origin の外への main frame の移動の止めは残します。サイトの通信の止めではなく、端末にファイルを残さないことと、点検の範囲の境目です。
    - 段が Browser の貸し出しを返さずに終わったときは、次の段の準備が失敗します（本番の 5 か所は、どれも必ず返します）。
    - CLI の Chromium では、ほかの Origin の子の frame の Worker の WebSocket は、止めても記録されないことがあります。
  - 限界として残すもの（どれも利用者の道で守りが破れないため、Minor）:
    - CLI の Chromium では、同じページで外のスキームを 2 回目から開こうとしても記録されません。起動そのものは、どの回も止めます。
    - 承認した Origin の別名の host（例: localhost と 127.0.0.1）への POST は、照合で止めません。
    - `text/plain` の本文の `_method=DELETE` は止めません。主な枠組みが、この形を上書きとして読まないためです。
