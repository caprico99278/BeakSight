## 1. 出発点と確かめた事実

### 1.1 G32 の実テスト環境で分かったこと（2026-10-16）

- 本来の監査対象のサイトのテスト環境のログインは、フォームの送信ではない。画面の中のスクリプトが、**別のホスト**にある外部の認証のサービスの token の送信先（`/auth/v1/token?grant_type=password`）へ POST する（ユーザーが普段のブラウザの開発者ツールで確かめた）。
- ログインの後の状態は、スクリプトがブラウザの**ローカル ストレージ**に保存する（ユーザーが確かめた）。
- 今の BeakSight のログインの段は「登録した送信先へのフォームの送信（main frame のページの移動の POST）だけを通す」ので、Guard がこの送信を止め、ログインできなかった。サイトへ届いた読み取りでない要求はない。
- ログインの画面の表示、HTTPS の証明書（ブラウザが信頼した）、ジョブの止め方は確かめた。ログインが要る段は、すべて未検証。

### 1.3 ユーザーが決めたこと（2026-10-16）

- 範囲: **B（スクリプトで送るログインへの対応）と C（API で書き込むサイトの書き込み）の両方**。B の後に中間の Gate を置き、C に進むかをそこで改めて判断する。
- 送信先のホスト: ログインの画面と**別のホスト**。
- ログインの状態の保存先: **ローカル ストレージ**。

### 1.4 推測（Task 33 の観察で確かめる）

- 管理画面のデータは、ページのスクリプトが API の Origin へ GET で読む（`Authorization` と API の鍵のヘッダつき。事前確認がある）。
- 一部の読み取りが、POST の手続きの呼び出し（例 `/rest/v1/rpc/...`）で行われる可能性。
- token の更新（`grant_type=refresh_token` の POST）が、有効期限の前に自動で出る。
- 登録・更新は、API の Origin への `POST`・`PATCH`（JSON の本文、更新は query の filter で対象を指す形）で送られる。
- 画面の更新に WebSocket を使う可能性。

## 2. スコープと非スコープ

**スコープ**

- 登録した外部の認証の Origin の token の送信先への、スクリプトの POST によるログイン（手動のログインと自動ログイン）。
- そのログインの後の、読み取りだけの監査（SPA の管理画面）。
- スクリプトで送るフォームの、送らずに観察する候補の発見と READ の確かめ。
- 承認した API の登録（CREATE）と更新（UPDATE）。ページが組み立てた要求を、承認した型に照らして 1 回だけ通す。
- 127.0.0.1 の fixture での確かめと、実テスト環境での確かめ（起動とログインはユーザー）。

**非スコープ**

- 別の Origin へページが移るログイン（OAuth の redirect の IdP）、MFA、CAPTCHA。
- 削除、論理削除、手続きの呼び出し（RPC）による書き込み、まとめての書き込み（配列の本文、filter のない更新）、upsert、ファイルの送信、WebSocket での書き込み。
- BeakSight がページを通さずに API を直接呼ぶこと（ページの組み立てた要求だけを扱う。テストの外での API の鍵や token の利用はしない）。
- 監査の段での token の更新（既定で止める。D1）。

## 3. 安全の不変条件の追加

前のロードマップの I01〜I16 は変えない。次を足す。

| 番号 | 不変条件 |
| --- | --- |
| I17 | ログインの段で通すスクリプトの送信は、登録した認証の Origin、path、`POST`、必須の query（`grant_type=password`）に一致するものだけ。回数は、自動ログインで 1 回、手動のログインで認証の設定の上限まで。ほかの送信（token の更新、別の送信先、別の `grant_type`、許可していない Origin）は止めて記録する。 |
| I18 | CORS の事前確認は、どの段でもサーバへ送らない（今の作りを保つ）。 |
| I19 | API の Origin は、プロファイルの許可 Origin とは別の、テスト環境だけの閉じた一覧（承認した API の Origin）で持つ。読む範囲（クロールの対象）を広げない。監査の段で API の Origin へ送るのは、ページが出す読み取り（GET・HEAD）だけ。 |
| I20 | API の書き込みは、ページが組み立てた要求のうち、承認した型（method、Origin、path、filter の query、JSON の本文の欄と値、許したヘッダの名前）に一致する 1 回だけを、BeakSight の送り手が 1 回だけ送る。再送しない。 |
| I21 | `DELETE`、論理削除にあたる欄、RPC、upsert、まとめての書き込み、filter のない更新は、候補にも実行にもならない。 |
| I22 | token、API の鍵、`Authorization`、ローカル ストレージの認証の値は、秘密として扱い、管理データ、成果物、ログ、画面に出さない（今の秘密の扱いを広げる）。 |

## 4. 設計の要点（契約の変更）

- **認証の設定 v3**: ログインの送り方 `FORM_NAVIGATION | SCRIPT_REQUEST`。`SCRIPT_REQUEST` のときは、認証の Origin、token の path、必須の query、成功の条件（移った画面の path に加え、ローカル ストレージの決まった名前の鍵があること。値は読まない）。
- **プロファイル**: 承認した API の Origin の一覧（`TEST` の 2 つのモードだけ）。プロファイルの改訂になる。
- **Guard**: ログインの段の「スクリプトの送信の許可」（I17）、監査の段の API の Origin の扱い（I19）、書き込みの段の「承認した fetch の 1 回」（I20）。判定は今の `decideGuardRequest` に寄せ、段ごとの第二の判定を作らない。要求の種類（document・fetch・xhr など）を記録に足す。
- **候補の発見**: 送らずに観察する probe。凍結した Context で、合成の値を入れて送信を押し、Guard が止めた「送るはずだった要求」の型（method、Origin、path、query の名前、JSON の本文の欄の名前、ヘッダの名前）を記録する。値は記録しない。
- **承認の digest v4**: API の候補の型を結ぶ。
- **管理データ**: 新しい版（v11 以降）。前の版の写しを固定してから足す。
- **成果物**: 書き込みの報告（Task 32）に API の型を足す。

#### Task 44: 監査の効率・精度・使いやすさの評価と改善（2026-10-18 追加。Task 41 の後、Task 42 の前）

- ユーザーの問いと指示による（「監査効率、監査精度、ユーザビリティは重視されているか？」「Aで進めて。安全性を高めた結果、最初の画面から「判定できない」を連発するようでは困る」）。設計書は別に書き、ユーザーの承認を得てから実装する。
- 測ること（fixture の代表のサイト。静的なサイトと、スクリプトでログインする SPA の両方）:
  - **精度:** 入口の確かめ・読み取りの監査・発見・READ の確かめ・書き込みの照合の READ の各段で、「判定できない」（`UNDETERMINED`・`PARTIAL`・`UNKNOWN` と、読めなかった画面）の数と割合と、理由ごとの内訳。発見できた画面・form・API の候補の数と、見逃した数（fixture の正解と比べる）。
  - **使いやすさ:** 開始の URL を入れてから、最初の監査の結果が出るまで、と、最初の承認した書き込みが終わるまでの、画面の操作の数・入力の数・迷いうる所（理由の表示がない止まり方）。
  - **効率:** 監査 1 回の所要時間を段ごとに（読み込みの間隔の待ち、落ち着きの待ち、probe の押下、Context の作り直し）。
- 直すこと:
  - 「判定できない」の理由を 1 つずつ、(a) 本当に判定できない（サイトの側の事実）と、(b) 安全の決まりが広すぎて判定を捨てている、に分ける。(b) は、安全の不変条件（I01〜I22）を破らない範囲で、判定できる形に直す。不変条件を変える必要があるものは、ユーザーに諮る。
  - 判定できないときは、理由と、利用者が次にできること（設定の直し方など）を画面と報告に出す。
  - サイトへの負荷の上限（7 章）を変えずに、待ちを縮められる所を直す。
- Exit Gate G44:
  - fixture の代表のサイトで、最初の画面（入口の確かめと、最初の読み取りの監査）の結果が「判定できない」で埋まらない。理由ごとの数と割合の目標は、設計書で決めてユーザーの承認を得る。
  - 残る「判定できない」は、すべて理由と次にできることが画面と報告に出る。
  - 安全の回帰（両方の Chromium）と、独立レビュー（Critical 0、Important 0）。
- Task 42 の実テスト環境の確かめでも、同じ数を記録する。
