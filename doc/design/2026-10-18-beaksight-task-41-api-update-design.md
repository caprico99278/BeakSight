## 1. 目的

承認した API の更新のシナリオを、書き込みのジョブで 1 回だけ実行できるようにする。

- 対象は、台帳の「照合済み」のレコードだけ（filter の値で結ぶ）。
- 変える欄だけを新しい値にし、保つ欄は変えない。
- 送る前と後に、更新の画面を読み直して照らす（D4。BeakSight は API を直接呼ばない）。
- 結果が分からないときは、成功と偽らない。
- 2026-10-19 の実テスト環境の確かめで使う。

## 2. 前提（調査で確かめた事実）

- probe の分類は、filter がちょうど 1 つ（`eq`）で、その値が画面の path の最後の ID と同じ PATCH だけを `API_UPDATE` にする（`api-shape-classification.ts`・`api-request-shape.ts`）。path に ID を持つ REST の形は扱わない（T39a の限界）。
- 下書きは、filter の名前、台帳の参照（同じプロファイルの CREATE のシナリオ）、台帳の画面の path の型を確かめる。承認の digest v4 は、filter の名前と台帳の参照を結ぶ。
- Guard の照合は、UPDATE の filter の値が `eq.<台帳の ID>` と完全に一致すること、query の名前の集合が `select` と filter だけであることを確かめる（`api-write-payload-policy.ts`）。照合そのものは揃っている。
- 足りないもの:
  - 配線（許可・開始・IPC・ワーカーが UPDATE を拒んでいる）
  - 保つ欄の考え（probe が目印を入れた欄は、すべて送る鍵になる）
  - 型の `{id}` が画面の path の最後の ID であることの確かめ
  - 台帳の ID の意味と filter の列の結び付け
  - form のない画面の、path を型にした識別の digest
  - form の外の欄の値を読む部品
- form の更新（Task 31）の部品で使えるもの: 対象の選び方（`selectUpdateTargetRecordId`）、証拠の形と判定（`WriteUpdateEvidence`・`updateEvidenceOf`・`actionOutcomeOf` の UPDATE の分岐）、比べ方（完全一致。改行だけ同じとみなす）、上限と予約、台帳の版 14。

## 3. 設計

### 3.1 契約と承認（T41a）

- **保つ鍵**: `ScenarioApiSpec` に、保つ鍵の一覧（`keptKeys`）を足す。
  - probe が目印を入れた欄の鍵は、変える鍵か保つ鍵のどちらかにする。
  - 既定は保つ。メールと電話は、既定で保つ（Task 31 の判断 3）。
  - 変える鍵が 1 つもない指定は受けない。
  - 保つ鍵には、生成した値を作らない。
- **論理削除の鍵**: 本文に状態の語の鍵がある型は、今のまま型の全体を拒む（I21。調査の候補 5）。
- **`{id}` の位置**: 台帳の画面の path の型の `{id}` が、候補の画面の path の最後の ID の区切りであることを、保存の時に確かめる。
- **台帳の ID と filter の結び付け**:
  - 台帳が API の CREATE で、ID を応答の本文の鍵から取るときは、その鍵の名前と filter の名前が同じであることを求める。
  - 台帳が URL の型から ID を取るシナリオ（form の CREATE・API の CREATE）のときは、型の `{id}` の前後の区切りが、更新の画面の path の型と同じであることを求める（`isUpdatePathBoundToLedger` と同じ考え）。
- **画面の path を型にした識別の digest**（調査の候補 6）:
  - form のない API の候補について、画面の path の最後の ID を `{id}` にした識別の digest を、候補の識別の owner（`src/discovery/fingerprint.ts`）に足す。
  - 索引に入れる。今の型にした digest の一覧の列を印で分けて共用できるなら版 14 のまま、できなければ版 15。
  - API の UPDATE のシナリオの有効性は、この digest が最新の索引にあることで判定する（form の UPDATE と同じ）。probe したレコードの画面を、次の発見で読み直せなくても `CANDIDATE_MISSING` にならない。
  - ワーカーは、対象の ID の画面の候補からこの digest を求めて照らし、送信の要素を探す。
- **ページが決める鍵**（ユーザーの判断 2 による。3.3 を見る）。
- **承認の digest**: v4 の項目に、保つ鍵の一覧を足す（v4 は未公開なので、その場で足す）。
- **秘密に見える名前の語**:
  - 部分一致で足す語: `privkey`、`passwort`、`encryptionkey`、`licensekey`、`hmac`、`securitycode`、`秘密鍵`、`暗証`、`セッション`。
  - 語の単位で足す語: `pw`、`salt`、`ssn`。
  - 足さない語: `refresh`、`card_number`（正当な欄に当たる）。
  - 結合文字の形（NFD にして結合文字を除いた形）でも比べる。
  - 今ある誤り（`author`・`footprint` を拒む）は、Task 44 で直す候補として記録する。

### 3.2 許可・開始・IPC（T41b）

- `apiWriteRejectionOf` の UPDATE の拒否を外す。
- 対象の選び方: `api.ledger` の CREATE のシナリオの、照合済みの登録のうち、最新の 1 件を発行の中で自動で選ぶ（Task 31 の判断 4・5）。開始の画面に、更新の予定のレコードとして出す。
- 発行の時の台帳の結び付けの確かめ直しを、API の UPDATE にも当てる。
- `START` の API の書き込みの指定に、次を足す。
  - 対象の ID
  - 保つ鍵
  - 変える鍵の生成した値（保つ鍵の値は持たない）
- 照合の READ の `{id}` には、対象の ID を入れる。

### 3.3 Guard の照合（T41c）

- **保つ鍵:**
  - 本文にあるとき: ワーカーが送る前に読んだ値（前の値）と完全一致を求める。
  - 本文にないとき: 通す（ユーザーの判断 1「なくても通す」）。PATCH では送らない欄は変わらない扱いとし、保つ欄が変わっていないことは後の照合（3.4 の 4）で確かめる。
  - 前の値は、照合の期待としてワーカーのメモリの中だけで渡し、記録しない。
- **変える鍵:** 生成した値と完全一致を求める（今の照合）。
- **filter:** 値が `eq.<対象の ID>` であること（今の照合）。
- **ページが決める鍵**（ユーザーの判断 2「前の値と照らせるものだけ通す」）:
  - 更新の画面の欄として識別できる鍵（欄の識別を持つもの。select の欄など）だけを受け、前の読み取りで読んだ値と完全一致を求める。
  - 欄として識別できないページが決める鍵を持つ型は、更新のシナリオにできない（下書きで拒む。理由を画面に出す）。
  - 登録（Task 40）のページが決める鍵の扱いは変えない。
- **状態の語の鍵:** 承認の外で本文に現れたら止める。重ねの守りとして足す（今は鍵の集合の完全一致で止まる）。

### 3.4 ワーカーの流れ（T41d）

1. **前の読み取り:** 凍結した Context で、対象の ID の更新の画面を 1 回読む。
   - 画面の path を型にした識別の digest で、候補を照らす。
   - 欄の識別（`NAME`・`SELECTOR`）で、変える欄と保つ欄の今の値を読む。`api-write-submitter.ts` の値の読み取りを広げる。
   - SPA が値を入れる前に読まないよう、値が落ち着くまで待つ。間隔を置いて 2 回読み、同じになるまで待つ。上限は名前つきの定数にする。
   - 読めなければ送らない（`PRECHECK_FAILED`）。
2. **書き込みの段:**
   - 開き直した画面の値が前の値と違えば、送らない（`PRIOR_VALUE_CHANGED` と同じ扱い）。
   - 変える鍵の欄にだけ、生成した値を入れる。保つ欄には触れない。
   - 2 段の窓（観察の段 → `readyToPress` → 送信の段）で、承認した 1 回を送る。
3. **結果の判定:**
   - 応答の状態は `apiResponseJudgementOf` で決める。
   - 登録の ID は、対象の ID とする（Guard が filter で結んでいるため）。応答の本文に ID の鍵があり、対象の ID と違えば `RECORD_ID_MISMATCH`（`UNKNOWN`）。
   - 応答の本文の表現が空の一覧（`[]`）なら、更新された行がないとして `UNKNOWN` にする（成功と偽らない）。
4. **後の照合（ユーザーの判断 3「更新の画面を読み直す」）:** 書き込みの段を閉じた後、凍結した Context で更新の画面を開き直す。変えた欄が新しい値、保つ欄が前の値であることを、欄ごとに照らす。
   - すべて一致: 照合の READ（`{id}` に対象の ID）に進む。一致すれば `VERIFIED`。
   - 一致しない欄がある: `UNKNOWN`（`UNEXPECTED_FIELD_CHANGE`）。
   - 読めない: `PARTIAL`（`UPDATE_POSTCHECK_UNDETERMINED`）。
5. **証拠:** Task 31 の `WriteUpdateEvidence` を使う。変える欄は前の値と新しい値を持ち、保つ欄は一致の真偽だけを持つ。台帳の版 14 の「照合済みの UPDATE は `update_evidence` が必須」をそのまま満たす。

### 3.5 報告と画面（T41e）

- 報告と結果の画面に、API の要約と、更新の前後の差分（変える欄）を出す。
- シナリオの画面で、目印を入れた欄ごとに、変えるか保つかを選べるようにする（既定は保つ）。
- 開始の画面に、更新の予定のレコードを出す。

### 3.5.1 登録してから更新する（T41g。2026-10-18 ユーザーの判断「1で進めて。明日の検証に必要。」）

- 更新のシナリオの開始の画面に「登録してから更新する」を置く。更新の対象にできる照合済みのレコードがないとき（`TARGET_RECORD_UNAVAILABLE`）と、最新のレコードで止まったとき（台帳の値と違う、など）に、1 回の操作で、台帳の登録のシナリオの書き込み → 続けて更新のシナリオの書き込み、を行う。
- 確認のダイアログには、2 回の書き込み（登録 1 回、更新 1 回）を、それぞれの送り先・上限の残り・予定とともに出す。利用者が 1 回承認すると、2 つを続けて行う。
- 始める前に、登録のシナリオと更新のシナリオの両方が、対象のレコードのほかは始められる状態かを確かめる（承認、検証の指定、上限、間隔、許可の確かめ）。どちらかが始められなければ、何も始めない。
- 登録のジョブは今の口（許可の発行 → `startWriteCreate`）で始める。登録のジョブが終わり、結果が照合済み（`VERIFIED`）で、更新の予定の対象（`readPlannedUpdateTarget`）がその登録の ID と同じときだけ、更新の許可を今の口で発行し（予定の ID を渡す）、`startWriteUpdate` で始める。照合済みでない・ID が違う・更新が始められないときは、更新を始めず、理由を画面に出す。
- 2 つは別々の許可・予約・上限を使う（登録と更新は別のシナリオなので、同じシナリオの間隔には当たらない）。続けて始める決まりは画面のサーバ（`apps/local-ui/src/server/`）が持ち、ワーカーと Guard は変えない。続けて始める予定はメモリの中だけに持つ（画面のサーバが止まれば、更新は始めない。安全側）。
- form の更新のシナリオにも同じ部品で使える（台帳の参照が同じ作り）。
- （2026-10-18 T41R5 と RT-prep-5 の報告による設計者の判断）自動ログインのプロファイルでは、自動ログインどうしの最小の間隔（`AUTO_LOGIN_MIN_INTERVAL_MS` = 5 分、プロファイルごと）があるので、登録のすぐ後の更新は開始の前の確かめで `AUTO_LOGIN_RATE_LIMITED`（次に始められる時刻つき）になる。続けて始める部品は、この理由のときだけ、次に始められる時刻まで待ってから、開始の前の確かめと許可の発行をやり直して 1 回だけ更新を始める（待ちの上限は名前つきの定数。待つ間の状態を画面に出す）。間隔の決まりそのものは変えない。ほかの理由で始められないときは今のまま始めない。
- （T41R5 の M-1）続けて始める要求に、画面が読んだ登録のシナリオの版を足し、登録の許可の発行に渡す（違えば `GRANT_REVISION_CONFLICT` で何も始めない）。（M-2）続きの中で更新の許可を発行した後に開始が例外になったときに許可が開いたまま残る形は、ふつうの開始の口と同じ既存の形なので、限界として文書に書く。
- （2026-10-18 T41R6。Critical 0・Important 0・Minor 1）許可の発行の後に、ジョブの管理の開始が自動ログインの間隔で拒む時刻の境の競合では、許可が開いたまま残り、やり直しは `GRANT_ALREADY_OPEN` で止まる（書き込みは増えない。稀）。Task 44 で、やり直すのは許可を発行していない回だけにする。

## 4. 安全と「判定できない」の影響

**安全**
- 対象は台帳の照合済みのレコードだけで、filter の値は Guard が完全一致で照らす。
- 送るのは承認した 1 回だけ。2 段の窓と送り手を使い、再送しない。
- 削除にあたる作用（状態の鍵、filter のない更新、配列、upsert）は、下書き・Guard・分類の 3 か所で止める。
- 値と秘密は残さない（I22）。保つ欄の値は記録しない。

**「判定できない」の影響**（ロードマップ 12 章の 2026-10-18 の指示による）

| 場面 | この設計での扱い | 増え方 |
| --- | --- | --- |
| 応答が 204・空の本文で ID を返さない | ID は対象の ID にするので `RECORD_ID_NOT_FOUND` にならない | 増えない（応答の本文の ID を必須にした場合の毎回の `PARTIAL` を避ける） |
| probe したレコードの画面を、次の発見で読み直さない | 画面の path を型にした digest で判定 | 増えない（作らなければ、承認の後の `CANDIDATE_MISSING` が頻発する見込み） |
| SPA が値を遅れて入れる | 落ち着くまで 2 回読む | 待ちの上限を超えたときだけ `PRECHECK_FAILED` |
| 本文が変える欄だけ | 通す（ユーザーの判断 1） | 増えない |
| 欄として識別できないページが決める鍵を持つ型 | 更新のシナリオにできない（ユーザーの判断 2） | シナリオを作れない（理由を画面に出す） |
| 本文に状態の鍵を含むサイト | 型の全体を拒む | シナリオを作れない（意図した止まり方。理由を画面に出す） |
| サーバが値を整形する（空白、大文字など） | 完全一致なので `UNEXPECTED_FIELD_CHANGE` | 起きうる。Task 44 で、正規化の閉じた一覧を足すかを判断する |
| 0 行の更新 | `[]` は `UNKNOWN`、204 は後の照合で拾う | 成功とは偽らない |

## 5. 受け入れ条件（G41）

1. fixture の SPA の更新の画面で、次の流れが通る: 発見 → シナリオ（変える鍵と保つ鍵）→ 承認 → 許可（台帳の最新の照合済みのレコード）→ 書き込みのジョブ → 前の読み取り → 1 回の PATCH → 後の照合 → 照合の READ → `VERIFIED` → 台帳 → 報告。サーバに届いた書き込みは 1 回で、変えた欄だけが変わる（両方の Chromium）。
2. 承認の範囲外 0、対象の外のレコードの更新 0、削除にあたる作用 0、二重の更新 0、上限の超過 0。
3. サーバの副作用、0 行の更新、ID の不一致、応答なし、4xx・5xx、照合の READ の不一致・判定できない、のときに成功と偽らない。
4. 秘密の目印と保つ欄の値が、管理データ（WAL を含む）・成果物・画面・IPC に出ない。
5. form の更新（Task 31）と API の登録（Task 40）の主なテストが PASS する（関係するテストだけ。全体の回帰と `verify:all` はロードマップの最後）。
6. 独立レビューで Critical 0、Important 0。
