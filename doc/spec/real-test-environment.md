# 実テスト環境の手順（低負荷の確かめ）

本来の監査対象のサイトのテスト環境で、認証つきの監査、自動ログイン、操作の候補の発見と READ の確かめを、低い負荷で確かめる手順です。
書き込み（登録と更新）の前で止めて、続けるかを判断します。
この確かめは、テスト環境が本番から隔離されているかを観察することも目的に含みます。そのため、HTTPS の証明書と隔離は、事前に確かめられていなくても、読み取りの段を始めてよいことにしています（下の「1. 事前の確かめ」と「7. 読み取りの段で確かめること・確かめられないこと」）。

[README に戻る](../../README.md)・[仕様の索引](README.md)

## この手順の決まり

- **Run の起動と再開、ログインは、利用者（運用者）が行います。** 見張りと記録の担当は、画面と記録を見るだけで、Run の起動とログインをしません。
- **負荷の上限**: 設定のファイルの `crawl.maxPages` は `3`、`crawl.minNavigationIntervalMs` は `10000`（10 秒）にします。どのジョブも、この値で読みます。画面からは変えられません。
- **自動ログインの上限**: 同じプロファイルで 5 分以上あけ、24 時間に 10 回までです（「[ログインの送信の回数と上限](automated-login.md#ログインの送信の回数と上限)」）。
- **書き込みは、この手順では行いません。** 手順 8 で止めて、登録（CREATE）と更新（UPDATE）まで行うかを、利用者が改めて判断します。
- **名前を書かない**: 本来の監査対象のサイトの名前、ドメイン、URL、対象のサイトのプラットフォームの名前を、Git に載るファイルに書きません。設定のファイルと記録は、Git の管理の外（`local/`）に置きます。
- **行えなかった部分は「未検証」と区分します。** 「完成」「本番検証済み」とは書きません。

## 1. 事前の確かめ

始める前に、次を確かめます。「事前に確かめなくてよい」と書いた項目のほかは、1 つでも確かめられなければ、始めません。

| 項目 | 確かめること |
| --- | --- |
| Gate | テスト用のサイト（fixture）での確かめの承認が済んでいること（最後の判定 G32 のうち、実テスト環境を除く部分。2026-10-15 に承認済み）。 |
| ビルド | `npm run build` と `npm run build:ui` が通ること（`npm run ui` が両方を行います）。 |
| 設定のファイル | `local/targets/<名前>.json` に、テスト環境の `site.startUrl`（ログインの後の管理画面）と `site.allowedOrigins`、`crawl.maxPages: 3`、`crawl.minNavigationIntervalMs: 10000` を書く。`node dist/cli/index.js validate-config --config local/targets/<名前>.json` が「設定に、誤りはありません。」を出すこと。形は `config/targets/example-test-environment.json.example` の `targetConfig` と同じです。 |
| 隔離の証跡 | 読み取りの段（手動のログインの監査、自動ログイン、操作の候補の発見と READ の確かめ）は、隔離が未確認でも始めてよい。読み取りの段がサイトへ送るのは、ログインの送信（POST）のほかは読み取りだけで、サイトのデータも外部への通知も変えないためです。このとき、プロファイルの `environmentEvidenceRef` には、未確認であることが分かる参照（例 `isolation-unverified-20261016`。秘密を含まない）を入れます。隔離を確かめた記録（テスト環境の所有者の接続の許可、テスト専用の Origin であること、データベース・メール・SMS・決済・外部の API が本番と分かれていることなど）があれば、Git の管理の外に置き、その参照を入れます。BeakSight は参照の中身を読まず、形とあるかだけを確かめます（「[`environmentEvidenceRef`](profiles.md#environmentevidenceref)」）。 |
| ログインの方式 | ログインの画面と送信先と管理画面が、同じ Origin にあり、フォームの送信（ページの移動の POST）でログインすること。別の Origin のログインのサービス（IdP）、多要素認証（MFA）、画面の中のスクリプト（fetch）で送るログイン、CAPTCHA は、BeakSight が扱えません。当たるときは、その段を「未検証」とします。 |
| アカウント | テスト環境のテスト用のアカウントであること。本番の資格情報、ふだん使うパスワードは使いません。自動ログインは Windows だけです。 |
| HTTPS の証明書 | 事前に確かめなくてよい。最初の低負荷の Run で分かります（下の「7. 読み取りの段で確かめること・確かめられないこと」）。BeakSight は、証明書の誤りを無視して読み進める作りではありません。書き込みまで進む場合だけ、書き込みの送り手が同じ証明書を信頼できるかを、その時点で確かめます（送り手は、Node の同梱の証明書と OS の証明書で確かめます）。 |
| 読まないパス | ログアウトの画面と、開くだけで状態が変わる画面（承認、送信、取り消しなど）の path を、テスト環境の管理者と確かめておくこと。 |

## 2. 画面を起動する

利用者が起動します。

```powershell
npm run ui
```

コンソールに出た URL をブラウザで開きます。「環境の状態」の画面で、管理データの整合性の確かめと、資格情報の暗号化（自動ログインを使うとき）を確かめます。

## 3. テスト環境のプロファイルを作る

「新しいプロファイル」で、次のプロファイルを作ります。値の例は `config/targets/example-test-environment.json.example` の `profiles` にあります（「[テスト環境のプロファイルを作る](authenticated-audit.md#2-テスト環境のプロファイルを作る)」）。

| 用途 | 環境 | 監査モード | 認証の方式 |
| --- | --- | --- | --- |
| 手動のログインの監査 | `TEST` | `TEST_AUTH_PASSIVE` | `MANUAL_SESSION` |
| 自動ログイン（Windows） | `TEST` | `TEST_AUTH_PASSIVE` | `AUTOMATED_LOGIN` |

- 「テスト環境の Origin」は、設定のファイルの `site.allowedOrigins` に含まれるテスト環境の Origin です。
- 「テスト環境であることを確かめた記録の参照」は、手順 1 の隔離の証跡の参照です。隔離が未確認なら、未確認であることが分かる参照（例 `isolation-unverified-20261016`）にします。
- それぞれのプロファイルで「認証の設定を開く」から認証の設定を作ります。読まないパスに、ログアウトの画面を必ず入れます。読む範囲のパスで、管理画面の範囲に絞ります。

## 4. 手動のログインで認証つきの監査をする

1. 手動のログインのプロファイルの「監査を始める」を押し、開始の画面で、ページの上限が 3、ページの読み込みの間隔が 10 秒であることを確かめてから、「新しく始める」を選んで「監査を始める」を押します。
2. BeakSight が開いたブラウザで、利用者がログインします。ログインのほかの操作（別のタブ、アドレスバー、開発者ツール）はしません。
3. ジョブの画面で、ログインの状態、進み具合、終わり方を見ます。
4. 終わった後に、手順 9 の項目を記録します。

## 5. 自動ログインを確かめる

1. 自動ログインのプロファイルの「資格情報を開く」で、テスト用のアカウントを登録します。
2. 「ログインを確かめる」で、ログインだけを 1 回試します。結果が成功でなければ、「[結果ごとにすること](automated-login.md#6-結果ごとにすること)」に従います。止めた自動ログインを解く前に、テスト環境でアカウントの状態を確かめます。
3. 成功したら、間隔（5 分）をあけてから、手順 4 と同じく「監査を始める」で監査します。ブラウザは開きません。

## 6. 操作の候補の発見と READ の確かめ

`TEST_AUTH_PASSIVE` のプロファイルで行えます（書き込みのモードのプロファイルを作らなくても行えます）。

1. 「操作の候補を開く」で「操作の候補を探す」を押します。ページの上限（3）と間隔（10 秒）で読むだけです。
2. 候補の分類と、読まなかった画面の理由を記録します。
3. READ の確かめをするときは、「READ の確かめを開く」で、テスト用の値だけを送る定義を作り、「READ を確かめる」を押します。1 回のジョブで読む定義の数だけ、GET が増えます（「[サイトへの読み込み](discovery-and-read-check.md#サイトへの読み込み)」）。

## 7. 読み取りの段で確かめること・確かめられないこと

### 確かめられること

- **テスト環境の画面がつながる外部のサービス**: 監査の段では、ページ自身が読み込む許可 Origin の外の部品（画像、スクリプト、fetch など）への `GET` は送られます（「[認証つきの監査の監査の段](authenticated-audit.md#監査の段)」）。読み取りでない要求（`POST` など）、許可 Origin の外へのページの移動、ポップアップは、Guard が止めます。次の記録から、テスト環境の画面がつながる外部のサービス（アクセス解析、外部の API、外部の決済や通知のスクリプトなど）を観察できます。
  - `pages/<pageId>/page.json` のネットワークの Evidence（`type` が `network`）の `requests` の `url` と `method`: 送った要求（許可 Origin の外への `GET` を含む）。記録の数には上限があり、超えた分は `omittedRequestCount` に数えます。
  - `pages/<pageId>/page.json` の安全の Evidence（`type` が `safety`）: `blockedRequests`（Guard が止めた読み取りでない要求。`method`、`url`、理由 `NON_READ_METHOD`）、`blockedNavigations`（許可 Origin の外へのページの移動。理由 `EXTERNAL_MAIN_FRAME_NAVIGATION`）、`blockedPopups`、`blockedWebSockets`、`blockedInteractionRequests`（理由 `GUARD_BYPASS_EGRESS` など）。
  - `run.json` の `safety`（`blockedActions`、`blockedRequestsByMethod`）と、`run.json` の `load.requests.otherOrigins`（許可 Origin の外へ送った要求の数と 1 分あたりの最大）。
  - 許可 Origin の外への `GET` は、実際にその外部のサービスへ届きます（アクセス解析の数字に入ることがあります）。ログインの段では、許可 Origin の外への要求はすべて止めますが、その記録は URL を持たず、保存もしないので、この観察には使えません（「[ログインの段の通信の制限](automated-login.md#ログインの段の通信の制限)」）。操作の候補の発見の `discovery.json` は、画面ごとの止めた数だけを持ちます。
- **HTTPS の証明書がブラウザに信頼されるか**: ブラウザが信頼しない証明書では、ページの読み込みが、ネットワークの層の失敗（`net::ERR_CERT_` で始まるコード）になります。監査の Run は、これをサイトの不調として扱い、確かめ直してから、再開できる状態で止まります（`PARTIAL`。`run.json` の `incompleteReasons` に `SITE_UNAVAILABLE`、`diagnostics/` に診断の記録。「[サイトが応答しないとき](site-unavailability.md)」）。手動のログインでは、ログインの画面を先に開きます。その画面での証明書の誤りの表れ方と、そのときのジョブの終わり方は、確かめていません。

### 確かめられないこと

- **サーバの裏側の隔離**: データベースが本番と別か、登録や更新のときにメール・SMS・外部の API への通知が出るか。BeakSight は、画面とブラウザの通信からしか観察できないので、これらは「未検証」と区分します。

## 8. ここで止めて判断する

書き込み（登録と更新）は、この手順では行いません。ここまでの記録を見て、利用者が次を判断します。

- 手順 7 で観察した外部のつながりを材料にして、サーバの裏側の隔離をどう扱うか（テスト環境の管理者に確かめる、など）。
- 書き込みまで行うか。行う場合は、`TEST_APPROVED_WRITE` のプロファイル、シナリオ、入力の規則、検証の指定、承認が要ります（「[通しの使い方](end-to-end-usage.md)」の 4〜9）。累積の上限を小さくし、テスト環境の管理者と、登録されるレコード、通知、片付けの方法を確かめてから始めます。
- 書き込みまで進むときは、その時点で、書き込みの送り手が、テスト環境の証明書を信頼できるかを確かめます（「[登録の要求の送り方](approved-create.md#登録の要求の送り方)」）。プロファイルの `environmentEvidenceRef` を、隔離を確かめた記録の参照に直すかも判断します（BeakSight は参照の中身を読まないので、未確認の参照のままでも書き込みの許可を拒みません）。
- 行わない場合は、書き込みの段を「未検証」と記録します。

## 9. 記録の取り方

記録は、Git の管理の外（例 `local/` の下）に置きます。本来の監査対象のサイトの名前と URL を、Git に載るファイルに書きません。

| 記録すること | 見る場所 |
| --- | --- |
| 日時、BeakSight の版（Git のコミット）、Node.js・Playwright・Chromium の版 | Git のコミットは `git log -1` で見る。版は `run.json` の `environment`（監査の Run だけ） |
| プロファイルの ID と改訂、ジョブの ID、Run の ID、ジョブの状態、Run の状態、終わり方 | 実行履歴、ジョブの画面 |
| サイトへの負荷: ページの読み込みの回数、許可 Origin への要求の数と 1 分あたりの最大、許可 Origin の外への要求 | `run.json` の `load`、HTML レポートの「サイトへの負荷」（「[実績の確かめ方](site-load.md#実績の確かめ方)」） |
| 安全: 遮断した操作の件数、安全の不変条件の違反の件数と内容 | `run.json` の `safety`、HTML レポートの「安全」（「[Safety Ledger の読み方](safety.md#safety-ledger-の読み方)」） |
| ログイン: 自動ログインの結果、送信したか、止めた理由 | ジョブの画面の「自動ログイン」 |
| 発見と READ: 読んだ画面と読まなかった画面の数、分類ごとの候補の数、READ の結果 | 画面「操作の候補」と「READ の確かめ」、`discovery.json`、`read-evidence.json` |
| 起きた問題と、その回の扱い | 手で記録する |
| 外部のつながり: 許可 Origin の外の Origin ごとに、送った `GET` の有無、Guard が止めた要求の method と理由、どの画面か | `page.json` のネットワークの Evidence と安全の Evidence、`run.json` の `safety` と `load.requests.otherOrigins`（手順 7）。記録に写すのは Origin と件数までにし、URL の query は写しません |
| HTTPS の証明書: ブラウザが信頼したか（証明書の失敗のコードがあれば、そのコード） | `run.json` の `incompleteReasons`、`diagnostics/` |
| 確かめられなかった段と理由（「未検証」）。サーバの裏側の隔離は、手順 7 のとおり「未検証」 | 手で記録する |

- 成果物（スクリーンショット、可視テキスト）には、テスト環境の管理画面のデータが入ります。記録に写すのは件数と状態だけにし、外へ渡すときは「[成果物を外へ渡す前の確かめ](anonymization.md)」に従います。
- 資格情報、Cookie、トークンを、記録に書きません。

## 「未検証」と区分するもの

次に当たる段は、「未検証」と記録し、確かめた段と分けます。

- 対応しないログイン（別の Origin の IdP、MFA、画面の中のスクリプトで送るログイン、CAPTCHA）のため、行えなかった段。
- ブラウザが HTTPS の証明書を信頼せず、行えなかった段。
- サーバの裏側の隔離（データベース、登録・更新のときのメール・SMS・外部の API への通知）。BeakSight では観察できません。
- 手順 8 で行わないと決めた書き込み（登録と更新）。
- 時間や負荷の都合で、途中で止めた段。
