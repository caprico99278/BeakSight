# 実テスト環境の手順（低負荷の確かめ）

本来の監査対象のサイトのテスト環境で、読み取りの段（入口の確かめ、ログイン、認証つきの監査、操作の候補の発見、READ の確かめ）と、書き込みの段（プロファイルの詳細の一覧でチェックした画面での、API の登録と更新）を、低い負荷で確かめる手順です。
書き込みの段の前で必ず止まり、続けるかを利用者が判断します（下の「[書き込みの前に止めて判断する](#書き込みの前に止めて判断する)」）。
この確かめは、テスト環境が本番から隔離されているかを観察することも目的に含みます。そのため、HTTPS の証明書と隔離は、事前に確かめられていなくても、読み取りの段を始めてよいことにしています（下の「1. 事前の確かめ」と「[読み取りの段で確かめられること・確かめられないこと](#読み取りの段で確かめられること確かめられないこと)」）。BeakSight の画面は、隔離の扱いを聞きません（責務の外です。テスト環境のアドレスは、利用者が入れたものを使います）。

[README に戻る](../../README.md)・[仕様の索引](README.md)

この手順書の言葉は、これまでの言葉（監査、プロファイル、ジョブ、発見、READ、シナリオ、承認など）のままです。画面は日常の言葉で出ます（たとえば「監査を始める」は、画面では「点検を始める」、入口の確かめは「サイトの下調べ」と出ます）。対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」の表にあります。ボタンの名前は、画面に出る語で「」に入れて書きます。

画面はどれも、上から「要点のパネル（今の様子）」「次に押す主のボタン 1 つ」「たたんだ『詳しい内容』1 つ」の形です。直す欄と調べる情報は「詳しい内容」の中にあり、開かなくても流れは進みます。ジョブが成功で終わると、次の画面へ自動で移ります（入口の確かめ → 続けて始めた点検、まとめて実行の段 → 次の段 → 最後はプロファイルの詳細。監査は、一部のページを見られなかったときも移ります）。失敗、安全の違反、結果が分からない（`UNKNOWN`）、利用者が止めたときは移らず、その画面に要点と次にすることが出ます。点検を終えて移ったプロファイルの詳細の主のボタンは「結果を見る」（HTML レポート）で、「点検を始める」は二次のボタンです。書き込む画面は、その下の一覧「登録・更新を試せる画面」でチェックします。

## この手順の決まり

- **Run とジョブの起動と再開、ログインは、利用者（運用者）が行います。** 見張りと記録の担当は、画面と記録を見るだけで、起動とログインをしません。
- **負荷の上限**: 設定のファイルの `crawl.maxPages` は `3`、`crawl.minNavigationIntervalMs` は `10000`（10 秒）にします。作成の画面（手順 3）が新しく作ったファイルは、最初からこの値です。どのジョブも、この値で読みます（まとめて実行の発見の段だけは、登録の画面とその 1 つ上の一覧の画面を合わせて最大 10 ページ、続けてページの上限まで読みます。手順 8）。プロファイルの詳細の「詳しい内容」の「点検の負荷」で変えられますが、実テスト環境では、サイトの運営者と決めた値の外にしないでください（間隔は今の下限より短くできません）。
- **読み込み直しはしません。** 発見、READ の確かめ、書き込みのジョブは、読めなかった画面を読み直しません。サイトが応答しないときだけ、監査は待ってから同じページを確かめ直し（最大 4 回）、発見と READ の確かめは 60 秒待って 1 回だけ確かめ直します（下の「[サイトが応答しなくなったとき](#サイトが応答しなくなったとき)」）。
- **自動ログインの上限**: 同じプロファイルで 5 分以上あけ、24 時間に 10 回までです（「[ログインの送信の回数と上限](automated-login.md#ログインの送信の回数と上限)」）。1 回目の点検は、開いたブラウザで人が手でログインします。そのときに入れた ID とパスワードを BeakSight が受け取って保存し、プロファイルを自動ログインに切り替えます（手順 5）。その後は、点検（まとめて実行。監査 → 発見 → READ の確かめ →（チェックした画面があれば）書き込み）ごとに、最初に自動ログインを 1 回だけ行います（「[まとめて実行](stage-chain.md)」）。書き込みも、同じ点検のログインのまま行い、ログインし直しません。ログインの確かめ（`LOGIN_CHECK`）は、ふだんの流れにありません（点検の最初の自動ログインが兼ねます）。1 日の段取りは、この数に収まるように組みます。
- **書き込みの上限**: 書き込みは、プロファイルの詳細の一覧「登録・更新を試せる画面」でチェックした画面だけ、点検の最後に行います（手順 10・11）。1 回の点検で、1 つの画面につき登録 1 件と更新 1 件までを送り、送り直しません。書き込みの読み込みも、読み取りと同じく、ページの読み込みの間隔（10 秒）を守ります。同じシナリオ（画面ごとの登録・更新の手順）の書き込みは 5 分以上あけ、24 時間に 5 件までです（「[承認された登録の上限](approved-create.md#上限)」）。結果が分からない画面や安全の違反があった画面の後は、残りの画面の書き込みを止めます。
- **名前を書かない**: 本来の監査対象のサイトの名前、ドメイン、URL、対象のサイトのプラットフォームの名前、外部の認証のサービスの名前を、Git に載るファイルに書きません。設定のファイルと記録は、Git の管理の外（`local/`）に置きます。
- **行えなかった部分は「未検証」と区分します。** 「完成」「本番検証済み」とは書きません（下の「[「未検証」と区分するもの](#未検証と区分するもの)」）。

## 手順の一覧

「読み取りでない要求」は、BeakSight がサイトへ通す `GET`・`HEAD` のほかの要求です。ページ自身が読み込む画像・スクリプト・fetch の `GET` は、どの段でも届きます。表の列は、BeakSight が自分から送るものです。ほかに、手順 7〜9 と書き込みの段の一部では、ページが自動でする送信のうち削除と危険な語のほかが、送信の扱い（既定は「削除のほかを通す」）のとおりに届きます（手順 7）。

| 段 | 利用者がすること | 読み取りでない要求 | 止まるところ |
| --- | --- | --- | --- |
| 1. 事前の確かめ | 下の表を確かめる | 0（BeakSight を使いません） | 確かめられない項目がある |
| 2. 画面の起動 | `npm run ui` | 0（サイトへ送りません） | ビルドの失敗、port の使用中 |
| 3. プロファイルの作成 | 開始の URL を入れ、使い方が「ログインが必要なサイト」（既定）であることを確かめ、「点検を始める」を押す | 0（保存はサイトへ送りません。続けて手順 4・5 が走ります） | 使う設定のファイルが決まらない（同じ開始の URL のファイルが 2 つ以上ある、同じサイトのファイルが別の開始の URL のものだけ）、置き場所のリンク |
| 4. 入口の確かめ（画面では「サイトの下調べ」） | なし（保存に続けて走ります。ログインの画面が見つかり、認証の設定を案で保存できると、続けて手順 5 の点検を始めます） | 0（開始の URL の読み込み 1 回だけ） | 許可 Origin の外へ移ろうとした、読めなかった、ログインの画面に見えない |
| 5. 1 回目の点検（手でログイン）と、自動ログインへの切り替え | 開いたブラウザで 1 回ログインする（BeakSight がログインの終わりを判定できないときだけ「ログインを終えた」を押す）。ログインの直後に、BeakSight がログインの設定の自動の登録と、入れた ID とパスワードの保存と、自動ログインへの切り替えを行い、続けて監査 → 発見 → READ の確かめが走ります（手順 7〜9） | 利用者のログインの操作で、ページが出す送信（止めずに通し、形だけ記録） | ログインの時間切れ、扱えないログインの形、自動ログインへ切り替えられなかった |
| 6. 自動ログイン | なし（手順 5 の切り替えで入ります。BeakSight の画面で ID とパスワードを入れる手順は、ふだんの流れにありません） | 0 | — |
| 7. 読み取りの監査（2 回目からは自動ログイン） | 2 回目からは、プロファイルの詳細の「点検を始める」→ 開始の画面の「点検を始める」（まとめて実行。最初の自動ログインがログインの確かめを兼ねます） | ログインの送信 1 回（スクリプトで送る形は token の送信 1 回と、登録したログインに伴う送信）のほかは、登録した読み取りの手続きの呼び出しだけ | 成功でない自動ログイン、資格情報を含む要求、セッションの切れ、要求の上限、サイトの不調 |
| 8. 発見（probe） | なし（まとめて実行の 2 つ目のステップ。1 つだけ行うときは、プロファイルの詳細の「詳しい内容」の「操作さがしの結果を見る」から） | ログインの送信のほかは、登録した読み取りの手続きの呼び出しだけ（probe の押下は何も送りません） | 要求の上限、成功の鍵の消失 |
| 9. READ の確かめ | なし（まとめて実行の 3 つ目のステップ。定義がなければ行いません） | 8 と同じ | 要求の上限、成功の鍵の消失 |
| 判断の点 | 書き込み（登録と更新）まで進むかと、どの画面で試すかを決める | — | ここで必ず止まる |
| 10. 書き込む画面のチェック | 点検の後のプロファイルの詳細の一覧「登録・更新を試せる画面」で、試す画面にチェックを入れる（その場で保存します。確認のダイアログはありません。書き込みの手順と承認は BeakSight が作ります） | 0（チェックの保存はサイトへ送りません） | 「この画面では試せません」の行、チェックの保存が拒まれた |
| 11. 次の点検での登録と更新 | 「点検を始める」→「点検を始める」（手順 7 と同じ。チェックした画面では、点検の最後に登録 →（あれば）更新を行います。データのないサイトでは、1 回目は登録だけで、更新は次の点検で行います） | 手順 7〜9 の要求のほかは、チェックした画面ごとに、承認した登録の要求 1 回と更新の要求（`PATCH`）1 回だけ | 送る前の確かめ、自動保存、照合の不一致、結果が分からない・安全の違反（残りの書き込みを止める）、ログインの切れ |

## 1. 事前の確かめ

始める前に、次を確かめます。「事前に確かめなくてよい」と書いた項目のほかは、1 つでも確かめられなければ、始めません。

| 項目 | 確かめること |
| --- | --- |
| Gate | テスト用のサイト（fixture）での確かめの承認が済んでいること（G40 まで承認済み。2026-10-18）。 |
| ビルド | `npm run build` と `npm run build:ui` が通ること（`npm run ui` が両方を行います）。 |
| 設定のファイル | 前もって作らなくてかまいません（手順 3 で画面が作ります。同じ開始の URL の設定のファイルがすでに 1 つあれば、それを使います）。画面が作るファイルは、最初から `crawl.maxPages` が `3`、`crawl.minNavigationIntervalMs` が `10000` です（手で作るときは、この値にします）。どの作り方でも、最初の読み込みの前に、`node dist/cli/index.js validate-config --config local/targets/<名前>.json` が「設定に、誤りはありません。」を出すことを確かめます。前の使い方（ファイルを手で作る）では、`site.startUrl`（ログインの後の管理画面）と `site.allowedOrigins` も書きます。形は `config/targets/example-test-environment.json.example` の `targetConfig` と同じです。 |
| 隔離の証跡 | 事前に確かめなくてよい。BeakSight の画面は、隔離の扱いを聞きません（責務の外）。読み取りの段がサイトへ送るのは、ログインの送信（POST）と、利用者が登録した読み取りの手続きの呼び出しのほかは読み取りだけで、サイトのデータも外部への通知も変えません。プロファイルの `environmentEvidenceRef` には、BeakSight が内部で「確かめていない」の固定の形の参照（`isolation-unverified-<YYYYMMDD>`。秘密を含まない）を入れます。画面には出さず、書き込みの許可も、この参照で拒みません（「[`environmentEvidenceRef`](profiles.md#environmentevidenceref)」）。隔離を確かめた記録（テスト環境の所有者の接続の許可、テスト専用の Origin であること、データベース・メール・SMS・決済・外部の API が本番と分かれていることなど）は、利用者が Git の管理の外で扱います。書き込みの段に進むかは、判断の点で決めます。 |
| ログインの方式 | ログインの送り方が、フォームの送信（ページの移動の POST）か、画面の中のスクリプト（fetch・XHR）で token を取りに行く形か。スクリプトの形は、「スクリプトで送るログイン」の設定のときだけ扱います（手動のログインと自動ログイン）。別の Origin のログインのサービス（IdP）へ画面が移るログイン、多要素認証（MFA）、CAPTCHA は、BeakSight が扱えません。扱えないときは、ログインが要る段を「未検証」とします。確かめ方は、下の「[ログインの方式の確かめ方](#ログインの方式の確かめ方)」にあります。 |
| アカウント | テスト環境のテスト用のアカウントであること。本番の資格情報、ふだん使うパスワードは使いません。自動ログインは Windows だけです。資格情報は 4 文字以上の値にします。 |
| HTTPS の証明書 | 事前に確かめなくてよい。最初の低負荷の Run で分かります（下の「[読み取りの段で確かめられること・確かめられないこと](#読み取りの段で確かめられること確かめられないこと)」）。BeakSight は、証明書の誤りを無視して読み進める作りではありません。書き込みまで進む場合だけ、書き込みの送り手が同じ証明書を信頼できるかを、その時点で確かめます（送り手は、Node の同梱の証明書と OS の証明書で確かめます）。 |
| 読まないパス | ログアウトの画面と、開くだけで状態が変わる画面（承認、送信、取り消しなど）の path を、テスト環境の管理者と確かめておくこと。 |
| 書き込みの相談（書き込みまで進むとき） | テスト環境の管理者と、登録・更新されるレコード、通知、片付けの方法を確かめておくこと。決まっていなければ、書き込みの段は行いません。 |
| 前に作ったシナリオと承認（書き込みまで進むとき） | Task 41 で、承認を縛る項目に「保つ鍵」を足しました。そのため、今までに承認したシナリオは、すべて承認し直しが要ります（画面での見え方は、この手順のために確かめていません）。Task 41 より前に保存した API の更新のシナリオ（保つ鍵などの指定を持たない形）は、読みません（管理データの誤り `DATABASE_INTEGRITY_FAILED` で止まります。利用者のデータには残っていません）。 |
| 書き込む画面のチェックと発見（書き込みまで進むとき） | 一覧「登録・更新を試せる画面」の行は、プロファイルの最後の発見の結果から作ります。最初のチェックの保存で、監査モードが書き込みのモード（`TEST_APPROVED_WRITE`）になり、プロファイルの改訂が進みますが、この切り替えだけの改訂は、発見の結果の古さの判定では同じ改訂とみなすので、発見のやり直しは要りません。切り替えのほかにプロファイルを変えたときは、行が「サイトの設定が変わったため、まだ試せません。もう一度点検すると、試せるようになります。」になるので、もう一度点検します。 |

### ログインの方式の確かめ方

BeakSight を使う前に、普段のブラウザで確かめます。

1. テスト環境のログインの画面を開き、開発者ツールの「ネットワーク」タブを開きます。
2. 「ログを保持」（Preserve log）にチェックを入れます。ページが移っても、記録が消えないようにするためです。
3. ログインします。
4. ログインを押した直後の `POST` の行の「種類」（Type）と、送り先のホストを見ます。
   - 「種類」が `document` なら、フォームの送信（ページの移動）です。送り先のホストがログインの画面と同じ Origin なら、BeakSight のログインの段が扱える形です。入口の確かめ（手順 4）が、ログインの画面の form から「ログインの送信先」の案を作り、認証の設定に保存します。案の Origin と path が、見た送り先と合うかを確かめます（違えば、プロファイルの詳細の「詳しい内容」の「ログインの設定を開く」で直します）。
   - 「種類」が `fetch` か `xhr` なら、画面の中のスクリプトで送る形です。外部の認証のサービスへ token を送るものなども、この形です。入口の確かめの案は、送り方「スクリプトで送る」になります。token の送信先と承認したサービスの Origin は、手動のログインで 1 回ログインすると、BeakSight が自動で登録します（手順 5。下の「[スクリプトで送るログインの設定の値](#スクリプトで送るログインの設定の値)」）。「フォームの送信」の設定のままでは、自動ログインのログインの段の Guard が、ページの移動でない `POST` と、許可 Origin の外への要求を止めるので、ログインできません（「[ログインの段](authenticated-audit.md#ログインの段)」。ログインの画面がその失敗をどう表示するかは、画面の作りによります）。

ログインの送り方の設定が画面と合わずにログインできないときは、左のメニューの「作業の履歴」からそのジョブの画面を開き、止めるボタン（画面では「点検を止める」）で止めます。止めても、ジョブの画面の「詳しい内容」の、ログインの段で止めた送信の表と数は残るので、時間切れ（10 分）を待つ必要はありません。設定を直せないときは、ログインが要る段を「未検証」と記録します。

### スクリプトで送るログインの設定の値

**ふだんは、値を手で写しません。** 手動のログインで 1 回ログインすると、BeakSight が、通した送信の形から、token の送信先・ログインに伴う送信・成功のローカル ストレージの鍵と、承認したサービスの Origin を自動で登録します（手順 5）。下の表は、開発者ツールで見た形（「[スクリプトで送るログインの観察の手順](script-login-observation.md)」の O1〜O4）と、自動の登録が埋めた欄を照らすときと、プロファイルの詳細の「詳しい内容」の「ログインの設定を開く」（認証の設定の画面）で直すときの対応です。値は、BeakSight の設定（Git の管理の外の管理データ）にだけ置きます。記録やほかの文書には、形だけを書きます。欄の決まりは「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」にあります。自動の登録が足りないときは、手動のログインのジョブの画面の「詳しい内容」の、通した送信の表の「登録する」で足します（行の登録が要るときは、要点のパネルにそう出ます）。

| 見たもの | 対応する欄 |
| --- | --- |
| token の `POST` の「リクエスト URL」の Origin（O1）と、管理画面が読む API の Origin（O4） | プロファイルの「承認したサービスの Origin」。**画面からは足せません**（読むだけと「消す」だけ）。手動のログインの観察（自動の登録と、手動のログインのジョブの行の「登録する」）だけが足します。自動ログインの記録と、自動ログインのプロファイルからは足せません（新しい送信先を足す登録を拒みます）。監査の対象の Origin は入りません。 |
| token の `POST` の「リクエスト URL」の Origin とパス（O1） | 認証の設定の「token の送信先の Origin」（承認したサービスの Origin から選ぶ）と「token の送信先のパス」。 |
| token の `POST` の query の名前と値（O1。例: 名前 `grant_type`、値 `password`） | 「必須の query」（「query の組を足す」）。要求の query と組がちょうど同じときだけ通すので、見えた組をすべて写します。秘密に見える名前の query は書けません。 |
| ログインの後のローカル ストレージの鍵の名前の形と、そのホスト（O3） | 「成功のローカル ストレージの鍵」の「鍵の Origin」（テスト環境の Origin）、「鍵の名前の接頭辞」、「鍵の名前の接尾辞」（例: `-auth-token`）。値は写しません。どちらか一方が空でもかまいません。 |
| token のほかにログインの前後に出る `POST`（O1・O4） | 「ログインに伴う送信」は、まず空で試します。止めた記録を見て、要るものだけを登録します（手順 5）。登録するかは、その送信が読み取りか、ログインに要る処理かを、利用者が判断します（BeakSight は、その送信の query と本文を照らしません）。 |
| 管理画面の 1 画面を開いたときに出る、API への要求（O4。1 画面で数十の要求、テナントの手続きの呼び出しなど） | 監査の段の欄（「[スクリプトで送るログインの後の監査](authenticated-audit.md#スクリプトで送るログインの後の監査)」）。読み取りの手続きの呼び出し（`POST`）は「監査で通す読み取りの手続きの呼び出し」に、まず空で試し、監査の成果物の `page.json` の安全の記録（止めた要求）を見て、データを読むだけの呼び出しだけを登録します（読むだけかどうかは、利用者が判断します）。「サービスの Origin への要求の上限」は、空のまま（1 分あたり 600 件、1 回の Run の全体（再開をまたぐ）で 10,000 件か、ページの上限 × 200 件の大きいほう。1 分あたりの上限に届いても止めず、次の画面の読み込みの前に待ってから続けます。「[承認したサービスの Origin への要求の上限](site-load.md#承認したサービスの-origin-への要求の上限)」）か、より小さい値にします。 |

- **保存済みの設定を変えずに使う場合**: 認証の設定は版 3 の形だけを読みます（前の版の形（版 2）の設定は、管理データの誤り `DATABASE_INTEGRITY_FAILED` で止まります。利用者のデータには残っていません）。「スクリプトの送信」に変えて保存すると、認証の設定の digest が変わるので、書き込みのシナリオは承認のし直しが要ります。
- **全セッションを無効にするログアウトに注意**: テスト環境のログアウトが、そのアカウントのすべてのセッションを無効にする作りのことがあります（観察の O8）。確かめの間は、普段のブラウザで、同じアカウントからログアウトしません。BeakSight のログインの状態も無効になります（そのときにジョブの途中でどう見えるかは、確かめていません）。

## 2. 画面を起動する

- **すること**: 利用者が起動します。

  ```powershell
  npm run ui
  ```

  コンソールに出た URL をブラウザで開きます。「環境の状態」の画面で、管理データの整合性の確かめと、資格情報の暗号化（自動ログインを使うとき）を確かめます。
- **送るもの**: サイトへは何も送りません。画面が 2 秒ごとに読み直すのは、画面のサーバの管理データだけです。
- **止まるところ**: 同じ管理データで画面のサーバがすでに動いている、port が使用中、のときは、理由と取るべき手順を出して止まります（「[画面の起動](local-ui.md#画面の起動)」）。
- **終わり方**: 管理画面のブラウザ（すべてのタブ）を閉じると、15 秒の猶予の後に、画面のサーバも止まります（コンソールに「管理画面が閉じられたので、画面のサーバを止めました。」が出ます）。読み込み直しでは止まりません。監査のジョブが動いている間は止まらず、ジョブが終わった後に止まります。コードを変えた後は、古いサーバが止まったことをコンソールで確かめてから、`npm run ui` で起動し直します。
- **結果の見方**: 起動の時刻と、Git のコミット（`git log -1`）を記録します。

## 3. URL からプロファイルを作る

- **すること**: 左のメニューの「サイトを足す」（新しいプロファイル）で、次の 3 つだけを行います（「[管理画面でのプロファイルの作り方](profiles.md#管理画面でのプロファイルの作り方)」）。
  1. 「開始のアドレス」（開始の URL）に、ログインの後の管理画面の URL を入れます。
  2. 「使い方」が「ログインが必要なサイト」であることを確かめます（既定。もう 1 つは「ログインしなくても見られるサイト」）。
  3. 「点検を始める」を押します（ボタンの下に「押すと、サイトを下調べしてから点検を始めます。ログインの画面が開いたら、いつもどおりログインしてください。次からは BeakSight がログインします。」が出ます）。
- 作成の画面には、隔離の扱いの選択も、ID とパスワードの欄も、たたんだ詳しい設定の欄もありません。
- **作るプロファイルは 1 つです。** 自動ログイン（手順 5・6）と書き込み（手順 10・11）にも、同じプロファイルを使います。別のプロファイルを作って、同じ値を写すことはしません。
- **BeakSight が決める値**（作成の画面には出ません。保存の後に、プロファイルの詳細の「詳しい内容」の「サイトの設定」（プロファイルの編集）で見られて、直せます）:

  | 値 | 決め方 |
  | --- | --- |
  | 名前（`profileId`） | 開始の URL のホスト名から作ります。同じ名前があれば `-2`、`-3` を付けます。 |
  | 設定のファイル | 同じ開始の URL の設定のファイルが `config/targets/`・`local/targets/` にちょうど 1 つあれば、それを使います（中身は変えません）。同じサイト（同じ Origin）のファイルがなければ、`local/targets/<名前>.json` を新しく作ります。新しいファイルの負荷は、最初からページの上限 3、読み込みの間隔 10 秒です。 |
  | 許可 Origin・テスト環境の Origin | 開始の URL の Origin。 |
  | 環境・監査モード・認証の方式 | テスト環境（`TEST`）、テスト環境の監査（ログインあり・読むだけ）（`TEST_AUTH_PASSIVE`。画面では「ログインして見るだけの点検」）、手でログインする（`MANUAL_SESSION`）。1 回目の点検の手でのログインの後に、BeakSight が自動ログインへ切り替えます（手順 5）。手でのログインを続けるときだけ、「サイトの設定」の「毎回手でログインする」を入れます |
  | テスト環境であることを確かめた記録の参照 | 保存した日付の `isolation-unverified-<YYYYMMDD>`（「確かめていない」の固定の形。画面には出ません）。 |
  | 承認したサービスの Origin | 空です。作成の画面にはありません。1 回目の点検の手でのログイン（手順 5）の観察が、ログインのサーバの Origin を自動で足します。 |

- **送るもの**: 保存は、サイトへ何も送りません。保存に続けて、手順 4 の入口の確かめ（開始の URL の読み込み 1 回）と、手順 5 の点検が走ります。
- **止まるところ**（設定のファイルもプロファイルも作りません）:
  - 使う設定のファイルが決まらない（同じ開始の URL の設定のファイルが 2 つ以上ある、同じサイトの設定のファイルが別の開始の URL のものだけ）。拒否の知らせの中に「どれを使いますか」の選択（候補のファイルか「開始のアドレスから新しく作る」）が出るので、選んでからもう一度保存します。
  - 置き場所（`local`・`local/targets`）がリンクか、フォルダでない（`TARGET_CONFIG_LOCATION_UNSAFE`）。
- **名前**: 名前はホスト名から作ります（作成の画面に名前の欄はありません）。Windows の予約名（`con` など）に当たるときは、止まらずに、末尾に番号を付けた名前（`con-2` など）で作ります。
- **結果の見方**: 保存すると、入口の確かめのジョブの画面へ移ります。入口の確かめを始められなかったときは、プロファイルの詳細に移り、「サイトは保存しましたが、サイトの下調べを始められませんでした」と理由が出ます（主のボタン「サイトの下調べをやり直す」で、もう一度始めます。このボタンは入口の確かめだけを行い、点検は続けて始めません。点検は「点検を始める」で始めます）。記録の表の「操作の数」は、この画面を開いた時から数えます（下の「[記録の取り方](#記録の取り方)」）。

## 4. 入口の確かめ

- **すること**: ありません。手順 3 の保存に続けて走ります（画面では「サイトの下調べ」）。ログインの画面が見つかり、認証の設定を保存できた（か、すでにある）ときは、続けて手順 5 の点検（まとめて実行）を始め、その作業の画面へ移ります。点検を続けて始めなかったとき（ログインの画面に見えない、案を保存できない、開始の URL を読めなかった、利用者が止めた、など）は、プロファイルの詳細へ移り、要点に理由が出ます。もう一度確かめるときは、プロファイルの詳細の「詳しい内容」の「サイトの下調べをやり直す」を押します（入口の確かめだけで、点検は続けて始めません）。
- **送るもの**: ログインしないで、開始の URL を 1 回だけ読みます（`GET`）。読み取りでない要求は 0 です。欄の値は読まず、入力・押下・送信はしません。ページ自身の読み込み直しや移動は、frame ごとに 2 回までです（「[ページ自身の読み込み直しの上限](site-load.md#ページ自身の読み込み直しの上限)」）。
- **認証の設定の自動の保存**: 入口の確かめが「読んだ」で終わり、開始の URL がログインの画面に見え（見えるパスワードの欄がある）、プロファイルに認証の設定がまだないときは、BeakSight が入口の確かめの案から認証の設定を作り、保存の確かめ（手で保存するときと同じ）を通ったものだけを保存します。読まないパスは空、読む範囲のパスは開始の URL の path です。プロファイルの改訂は進みません。自動の保存は、認証の方式が手動のログインのプロファイルだけです（自動ログインに切り替えた後に入口を確かめ直しても、保存しません。資格情報の送信先を、人の確かめなしに保存しないためです）。
  - 認証の設定がすでにあるときは、上書きしません（案と違う所は、ジョブの画面の「詳しい内容」の入口の確かめの結果で見られます）。
  - 次のときは保存しません。プロファイルの詳細の要点のパネルに理由が出て、主のボタン「ログインの設定を開く」（認証の設定の画面）から作ります。
    - 開始の URL を読めなかった、許可 Origin の外へ移ろうとした。
    - 開始の URL がログインの画面に見えない（見えるパスワードの欄がない）。
    - 案が保存の確かめを通らない。たとえば、開始の URL の path がログインの画面の path の前方に当たるとき（開始の URL が `/` や `/admin/` で、ログインの画面が `/admin/login` など）は、ログインが済んだと判定するパスを開始の URL から決められないので、保存しません（既知の制限）。
- **止まるところ**: 終わり方は「読んだ」「許可 Origin の外へ移ろうとした」「読めなかった」です。開始の URL が別の Origin のログインのサービスへ移る作りなら、「許可 Origin の外へ移ろうとした」になります（その場合は、ログインの方式を確かめ直します）。成功でない終わり方では、点検を続けて始めません。
- **結果の見方**: ジョブの画面の「詳しい内容」の入口の確かめの結果（移った先、ログインの画面に見えるか、欄の候補、form、認証の設定の案）と、成果物 `entry-check.json`（「[入口の確かめの成果物](output.md#入口の確かめの成果物)」）。「読めなかった」とその理由を、記録の表の「判定できない」に数えます。

## 5. 1 回目の点検（手でログイン）と、自動ログインへの切り替え

`TEST_AUTH_PASSIVE`（と `TEST_APPROVED_WRITE`）のプロファイルの点検は、まとめて実行（監査 → 操作の候補の発見 → READ の確かめ。チェックした画面があれば、最後に書き込み）です。ログインは最初に 1 回だけで、監査の段は手順 7、発見の段は手順 8、READ の確かめの段は手順 9 と同じものを送ります（「[まとめて実行](stage-chain.md)」）。1 回目の点検だけ、ログインを人が手で行い、その後に BeakSight が自動ログインへ切り替えます。

- **すること**:
  1. 手順 3 から来たときは、することはありません（点検は自動で始まります）。前に作ったプロファイル（手でログインのもの）で始めるときは、プロファイルの詳細の主のボタン「点検を始める」で開始の画面を開き、「詳しい内容」で、ページの上限が 3、ページの読み込みの間隔が 10 秒であることと、行うステップ（この順）を確かめ、「読まないパス」（画面では「読まないページ」）に、ログアウトの画面と、開くだけで状態が変わる画面（承認、送信、取り消しなど）の path を入れてから、主のボタン「点検を始める」を押します（手順 1 の「読まないパス」。説明に出る既定の語を含む URL は、書かなくても読みません）。読まないパスを変えたときは、認証の設定を保存してから始めます。前回の監査が最後まで終わっていないときだけ、「詳しい内容」に「始め方」の選択が出ます（既定は「前回の続きから再開する」。途中の Run を捨てて最初から読むときだけ「新しく始める」）。
     - 手順 3 から続けて始まる点検では、前もって読まないパスを入れられません（既定の語を含む URL は読みません）。既定の語を含まない、開くだけで状態が変わる画面があるサイトでは、前もって設定のファイルとプロファイルを用意し、プロファイルの詳細の「点検を始める」から始めます。
  2. BeakSight が開いたブラウザで、利用者がログインします。ログインのほかの操作（別のタブ、アドレスバー、開発者ツール）はしません。手動のログインの間は、ページの送信を止めません（認証の設定が「フォームの送信」のままでも、ログインは止まりません）。
  3. ログインが済むと、BeakSight がログインの終わりを判定して、先へ進みます（ログインの画面を離れたこと（パスワードの欄が消え、セッションの切れの path の外へ移った）と、新しいログインの状態の名前（Cookie・ストレージの鍵）が増えたことで判定します）。判定できないサイトのときだけ、ジョブの画面の要点（「開いたブラウザで、ログインしてください。」）に主のボタン「ログインを終えた」が出るので、ログインが済んでから押します（受け付けるのは「ログイン待ち」の間の 1 回だけです。受け付けられないときは、理由が出ます）。
  4. ログインの直後、監査の前に、BeakSight が次を 1 回の保存で行います（利用者がすることはありません）。
     - **ログインの設定の自動の登録**: Guard を通るための設定（認証の設定の「スクリプトの送信」の token の送信先・ログインに伴う送信・成功のローカル ストレージの鍵と、プロファイルの承認したサービスの Origin）。登録するログインに伴う送信は、token の送信より前に通した、token の送信先と同じ Origin の、書き込みの語を含まない、符号化していない手続きの呼び出し（`/rpc/`）だけです。承認したサービスの Origin に足すのは、token の送信先の Origin だけです。token の送信先が 2 つ以上あって 1 つに決まらないときは、登録しません（ジョブの画面の「詳しい内容」の、通した表の token の行から「登録する」で、正しい送信先を選びます。要点のパネルに、行の登録が要ることが出ます）。
     - **自動ログインへの切り替え**: ログインの画面で入れた ID とパスワードを BeakSight が受け取り、資格情報として保存し、認証の方式を自動ログインにします（プロファイルの改訂が進みます）。受け取るのは、ログインに成功し、かつ受け取った値が観察したログインの送信先への送信の本文に入っていたときだけです。値はページから見えない所で読み、画面・記録・ログに出しません（「[1 回目の手でのログインから切り替える](automated-login.md#1-回目の手でのログインから切り替える)」）。
     - **切り替えないとき**（手でログインのまま。受け取った値は捨てます。次の点検も手でログインします）: ログインの欄・パスワードの欄・送信のボタンの 3 つの案がそろわない、このプロファイルの資格情報のファイルがすでにある、Windows でない・資格情報の暗号化を使えない、サイトの設定で「毎回手でログインする」を入れている。
     - 登録と切り替えの結果は、ジョブの画面の「詳しい内容」に出ます（切り替えたときは「次の点検から、BeakSight が自動でログインします。」）。この点検（まとめて実行）は、この保存で進んだ改訂を基準として、そのまま次の段へ進みます（途中でプロファイルが変わったとして止まりません）。中身が違っていれば、プロファイルの詳細の「詳しい内容」の「ログインの設定を開く」から直します。
  5. 続けて、読み取りだけの監査（手順 7）、発見（手順 8）、READ の確かめ（手順 9）が走ります。
- **送るもの**: 手動のログインの間は、ページが出す読み取りでない送信（ログインの送信、外部の認証のサービスへの token の送信、ページの手続きの呼び出し、事前確認など）を止めずに通し、サイトに届きます（普通のブラウザで人が操作するのと同じ）。BeakSight は、通した送信の形（Origin・パス・method・種類・query の名前と数）だけを記録し、値は記録しません。読み取り（GET と HEAD）の決まりは変わらず、**許可 Origin の外への読み取りは止めます**（人が入れた値を、ページのスクリプトが別の Origin への読み取りに載せて運ぶことを防ぐため）。ダウンロード、外部のアプリの起動、WebSocket、許可 Origin の外への画面の移動も、今までどおり止めます。ログインの後の各段で送るものは、手順 7〜9 と同じです。
- **止まるところ**: ログインの時間切れ（10 分）。ログインの後に、許可した Origin の Cookie も localStorage もないとき（「扱えないログインの形」）。各段は手順 7〜9 と同じです。
- **自動で次へ移るか**: 監査の段が最後まで終わり（`COMPLETE`）、次の段が始まれば、次の段のジョブの画面へ、最後の段が終われば、プロファイルの詳細へ移ります。送信の扱い（既定は「削除のほかを通す」）によらず、同じように移ります（ジョブの画面には、通したことの知らせを出しません。通した数は HTML レポートと `run.json` に出ます）。ページの上限（3）で止まった監査は一部未完了（`PARTIAL`）ですが、最後まで終えた監査と同じく移ります（まとめて実行は、止める理由でなければ次の段へ進みます）。最後の段の後に移ったプロファイルの詳細の主のボタンは「結果を見る」、二次のボタンは「点検を始める」で、その下に一覧「登録・更新を試せる画面」が出ます。「点検を止める」で利用者が止めたときは、ジョブの画面に残ります。
- **結果の見方**: ジョブの画面の「詳しい内容」の、ログインの段で止めた送信の表と、手動のログインの間に通した送信の表（Origin・パス・種類・回数・query の名前。通した行からも「登録する」を使えます）と、手動のログインから登録した設定と、自動ログインへ切り替えたか。各段の結果は手順 7〜9 と同じ所で見ます。

## 6. 自動ログイン

手順 5 の切り替えで、同じプロファイルが自動ログインになります（自動ログインのプロファイルを別に作りません）。認証の設定と承認したサービスの Origin は、手順 5 の自動の登録のものを、そのまま使います。BeakSight の画面で ID とパスワードを入れる手順（前の「次から自動でログインする」の画面）は、ふだんの流れにありません。

- **確かめること**: プロファイルの詳細の「詳しい内容」の「ログインのしかた」が自動ログインになったこと（サイトの一覧の行は「次は点検です（自動でログインします）」）。次の点検（手順 7）の最初の自動ログインが、ログインの確かめを兼ねます（ログインだけを 1 回試すジョブは行いません）。
- **切り替わらなかったとき**: 理由を手順 5 のジョブの画面の「詳しい内容」で見て、記録します。次の点検も手でログインします（自動ログインの段を「未検証」とするかを判断します）。プロファイルの詳細の「詳しい内容」の「ID とパスワードの画面を開く」から自動ログインにする道も残っていますが、ふだんの流れではありません（同じ ID とパスワードを 2 回入れることになるため）。
- **手でログインを続けたいとき**: 「詳しい内容」の「サイトの設定」（プロファイルの編集）の「毎回手でログインする」を入れて保存します。外すと、BeakSight が自動でログインします（保存した ID とパスワードは消しません）。
  - 自動ログインへは、1 回目の点検の手でのログインの後の切り替えで入ります。プロファイルの作成でも、「詳しい内容」のプロファイルの編集でも、認証の方式を自動ログインにはできません（手動のログインへ戻すことはできます）。
  - 自動ログインに切り替えた後は、ログインの送信先（ログインの画面の URL、ログインの送り方、token の送信先の Origin・パス・必須の query、ログインに伴う送信の送信先、フォームの送信先、自動ログインのセレクタ、設定のファイル）を変える保存と、承認したサービスの Origin・テスト環境の Origin を足す保存を拒みます。変えたいときは、手動のログインへ戻し、手動のログインで観察し直してから、切り替え直します（手動のログインに戻したプロファイルは、資格情報のファイルが残っていると、次の手でのログインで切り替えません。下の行）。読まないパス、読む範囲のパス、成功・セッションの切れ・失敗の条件、上限などは、自動ログインのままでも直せます。
  - このプロファイルに、前に保存した資格情報のファイルが残っているとき（自動ログインから手動のログインに戻したプロファイルなど）は、手でのログインの後に切り替えません。先に ID とパスワードの画面の「詳しい内容」の削除で消します（「[手動のログインへ戻す](automated-login.md#手動のログインへ戻す)」）。
- **送るもの**: 切り替えは、サイトへ何も送りません（手順 5 のログインの送信のほかに、ログインを試しません）。

## 7. 読み取りの監査

- **すること**: 2 回目からの点検は、プロファイルの詳細の「点検を始める」（点検を終えて移ってきた直後は二次のボタン）から開始の画面を開き、「詳しい内容」でページの上限が 3、間隔が 10 秒であることと、「読まないパス」を確かめてから、主のボタン「点検を始める」を押します（まとめて実行。手順 5 と同じく、発見と READ の確かめが続けて走ります）。自動ログインなら、ブラウザは開きません（表示の設定で作業中のブラウザを出すときは、開始の画面に「作業中のブラウザが画面に出ます」と書かれます）。手順 5 で自動ログインに切り替えた後は、この点検の最初の自動ログインで、自動ログインを確かめます。
  - 自動ログインの間隔（5 分）の中では、主のボタンが出ず、要点に「自動ログインは続けては行えないため（サイトとアカウントを守る決まりです）、<日時> から始められます。」が出ます（最新の点検の報告があれば、主のボタンは「結果を見る」です）。その時刻の後に、もう一度開きます。
  - 一覧でチェックした画面があるときは、点検の最後に書き込みの段を行います（手順 11）。チェックがないときは、点検は読み取りだけで、開始の画面の要点にもそう出ます。監査の段そのものの送るもの・止めるものは、チェックの有無と監査モードで変わりません（監査の段で BeakSight は書き込みません）。
- **送信の扱い（既定は「削除のほかを通す」）**: サイトが自動でする通信は、削除と危険な語のほかは止めずに通します（2026-10-29 から、新しいサイトの既定。「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」）。止めると画面の部品が動かず、点検や答え合わせが「判定できない」になるためです。すべて止める（読み取りだけ）ときだけ、始める前に、プロファイルの詳細の「詳しい内容」の「表示の設定」で「ページが出す送信のうち、削除のほかを通す」のチェックを外します（通す側に戻すときは、確認のダイアログで「通す」を押します）。前に読み取りだけのまま保存したサイトは、読み取りだけのままなので、通すときはチェックを入れます。通した数は、HTML レポートと `run.json` の `safety.auditSend` に出ます（ジョブの画面には出しません）。送信を通した監査のジョブも、成功で終われば、次の画面へ自動で移ります。
- **送るもの**:
  - ログインの送信（自動ログインなら 1 回だけ。フォームの送信は 1 回の `POST`。スクリプトで送る形は token の送信 1 回と、登録したログインに伴う送信）。入れた資格情報を含む、ほかの要求は止めます（「[資格情報の持ち出しの守り](automated-login.md#資格情報の持ち出しの守り)」）。
  - 読み込み: 1 ページにつき、デスクトップとモバイルの 2 回と、幅の走査の幅ごとに 1 回（既定 3 幅）です（「[1つのページの読み込みの回数](site-load.md#1つのページの読み込みの回数)」）。認証つきの監査では、クリックによる操作の確かめ（Interaction）を行いません。ページ自身の読み込み直しは frame ごとに 2 回までです。
  - 読み取りでない要求: ログインの送信のほかは、スクリプトで送るログインの設定で、利用者が登録した読み取りの手続きの呼び出し（`POST`。1 回の読み込みでの回数の中）だけです。承認したサービスの Origin への要求は、1 分あたりと Run の全体の上限の中です（「[スクリプトで送るログインの後の監査](authenticated-audit.md#スクリプトで送るログインの後の監査)」）。送信の扱いが「削除のほかを通す」（既定）のときは、ページが自分で出す送信のうち、削除と危険な語のほかを、送り先の Origin を問わず、1 回の読み込みで 60 件まで通します（token の更新も通し、入れ替わった状態を次の読み込みに引き継ぎます）。
- **止まるところ**:
  - 自動ログインが成功でない結果（資格情報の誤り、回数の制限、アカウントのロック、結果が分からない）。監査は止まり、ジョブの画面に理由が出ます。人が確かめて解くまで、そのプロファイルの自動ログインを止めます（プロファイルの詳細の要点に「前の自動ログインがうまくいかなかったため、自動ログインを止めています。…」と、二次のボタン「自動ログインの停止を解く」が出ます）。結果が「結果が分からない」で、ジョブの画面の「詳しい内容」の「資格情報を含む要求を止めた数」が 1 以上のときは、ログインの画面が入力の値を token の送信のほかの要求に載せた可能性があります。止めた自動ログインを解く前に、テスト環境でアカウントの状態を確かめます（「[結果ごとにすること](automated-login.md#6-結果ごとにすること)」）。解くのは、「自動ログインの停止を解く」で開く画面「自動ログインの再開」の「確かめたので再開する」と、確認のダイアログの「再開する」です（ログインの確かめの画面は、この入口としてだけ残っています）。
  - 自動ログインの記録（監査の止めた行）と、自動ログインのプロファイルからは、新しいログインの送信先（token の送信先と、承認したサービスの Origin）を足せません（「登録する」が理由を出して拒みます）。足りないときは、手動のログインに戻してから、手動のログインで 1 回ログインします（「[手動のログインへ戻す](automated-login.md#手動のログインへ戻す)」）。送信先の Origin がすでに承認したサービスの Origin か許可 Origin の中にある、ログインに伴う送信は登録できます。
  - セッションの切れ（`STOPPED_BY_AUTH_SESSION_LOST`。成功の鍵の消失は場所の印 `session-key`）、承認したサービスの Origin への要求の上限（`STOPPED_BY_SERVICE_REQUEST_LIMIT`）、サイトの不調（`STOPPED_BY_SITE_UNAVAILABLE`）、安全の不変条件の違反。どれも、まとめて実行は次の段へ進みません。
- **結果の見方**: ジョブの画面（要点の結果の 1 行。最後まで終われば「点検が終わりました。問題が N 件見つかりました。」の形。「詳しい内容」に Run の状態、終わり方、自動ログインの結果、ログインを送信したか、止めた理由）、主のボタン「結果を見る」（移ったプロファイルの詳細の主のボタンも同じ）で開く HTML レポート（冒頭の「まとめ」と、末尾の記録の段のサイトへの負荷、安全）、`run.json`（`load`、`safety`、`authentication`、`incompleteReasons`）、ページごとの `page.json`（状態、`documentRequests`）。一部未完了・失敗のページと理由を、記録の表の「判定できない」に数えます。自動ログインが成功したら、次の自動ログインまで 5 分あけます。

## 8. 操作の候補の発見（probe）

- **すること**: ふだんは、手順 5・7 のまとめて実行の 2 つ目の段として走ります（することはありません）。発見だけを行うときは、プロファイルの詳細の「詳しい内容」の「操作さがしの結果を見る」で画面「操作の候補」（画面の題は「操作さがし」）を開き、主のボタン（初めは「操作さがしを始める」、前の結果があれば「もう一度さがす」）を押します。`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` のプロファイルで行えます。発見だけのジョブは、終わっても自動で移りません。ジョブの画面の主のボタン「操作さがしの結果を見る」で開きます。
- **送るもの**:
  - 読み込み: ログインの段の画面と、読む範囲の画面を 1 画面につき 1 回。まとめて実行の発見の段は、監査の段が見つけた登録の画面らしいページと、その 1 つ上の一覧の画面（監査の段のリンクにあるもの）を、合わせて最大 10 ページ先に読み、続けて入口からページの上限 3 まで読みます（最大 13 ページ。すでに読んだ画面は読み直しません。「[まとめて実行](stage-chain.md)」）。一覧の画面は、登録の答え合わせに使い、更新の候補も探します。発見だけのジョブは、ページの上限 3 までです（登録の画面らしいリンクを先に読む順だけが変わります）。
  - 送らずに観察する押下（probe）: 1 画面 3 回まで、1 回のたびに 2 秒待ちます。押す順は、保存・登録など登録・更新の語のボタンが先で、文字のないボタン（アイコンのボタン）は最後です（見えないボタンは、回数を使わずに飛ばします）。押下は凍結の中で行い、サーバへは何も送りません。承認した API の Origin への CORS の事前確認は、Guard が代わりに答えます（「[送らずに観察する押下（probe）](discovery-and-read-check.md#送らずに観察する押下probe)」）。
  - 読み取りでない要求: BeakSight が送るのは、ログインの送信のほかは、登録した読み取りの手続きの呼び出しだけです（ページが自動でする送信は、手順 7 の送信の扱いのとおり）。
- **止まるところ**: 承認したサービスの Origin への要求の上限（残りの画面を読まずに `PARTIAL`）、成功の鍵の消失（セッションの切れ、場所の印 `session-key`）。読めなかった画面は、不完全の理由を付けて残ります。
  - **サイトの不調**（応答しない、接続できない、429・502・503・504）: その画面の結果を捨て、60 秒待って同じ画面を 1 回だけ確かめ直します（待つ間は、ジョブの画面に知らせが出ます）。通ったら続け、その後の読み込みの間隔を 2 倍にします。まだ不調なら、ジョブを止めます（終わり方 `SITE_UNAVAILABLE`「サイトが応答しないため止めました」、結果 `PARTIAL`、残りの画面は読みません）。サイトが戻ってから、ジョブを始め直します（「[サイトが応答しないときの発見と READ の確かめのジョブ](site-unavailability.md#発見と-read-の確かめのジョブ)」）。
  - **4xx・5xx の画面**（上の 4 つを除く）: その画面から候補もリンクも拾わず、読まなかった画面（理由 `HTTP_ERROR_STATUS`）にして、次の画面へ進みます。
- **結果の見方**: 画面「操作の候補」の要点（書き込める操作の数）と、「詳しい内容」（読んだ画面の数、読まなかった理由、読み切れなかった画面、画面ごとの見つかった操作と分類）。画面には、型の分類（`API_CREATE`・`API_UPDATE`・`NOT_EXECUTABLE` とその理由など）、送り方、送信先は出ません。型の分類は、成果物 `discovery.json` の候補の `submissionProbe` で見ます（「[型の分類](discovery-and-read-check.md#型の分類)」）。見つかった登録の画面は、プロファイルの詳細の一覧「登録・更新を試せる画面」の行になります（手順 10）。

## 9. READ の確かめ

- **すること**: ふだんは、まとめて実行の 3 つ目の段として、取り消していない定義が 1 件以上あるときだけ走ります（定義がなければ「行わなかった」で終わり、失敗にはしません）。READ の確かめは、書き込みの流れからは外れています（照合に使う定義は、手順 10 のチェックの保存で BeakSight が作ります）。読み取りの確かめを自分で決めて行いたいときだけ、プロファイルの詳細の「詳しい内容」の「見るだけの確かめを開く」で定義を作ります。読み取りの候補の行の「この候補で作る」なら「候補を読む」（読み取りの候補に、テスト用の値だけを送る）、「画面の読み方を決める」なら「画面を読む」（画面の path を読む）です（「[画面を読む READ](discovery-and-read-check.md#画面を読む-read)」）。照合の専用の定義と、`{id}` の型の画面の定義は、READ の確かめとしては単独で読みません（手順 11 の照合に使います）。
- **送るもの**: ログインの段の画面と、対象の画面を 1 回、定義ごとに READ の URL を 1 回（1 回のジョブで 20 定義まで）。読み取りでない要求は、手順 8 と同じです。
- **止まるところ**: 手順 8 と同じです（サイトの不調では、その定義の結果を捨て、60 秒待って 1 回だけ確かめ直し、まだ不調ならジョブを止めて、その定義と残りの定義を確かめません）。読む前の確かめ（読まないパス、危険な語など）で止めた定義は、読みません（`READ_BLOCKED_BY_POLICY`）。4xx・5xx の画面の定義は、今どおり `UNDETERMINED`（詳しい理由 `HTTP_ERROR_STATUS`）です。
  - 限界: 最初の定義の画面で止まったジョブは、画面「READ の確かめ」の結果の一覧には並びません。ジョブの画面に、知らせと `PARTIAL` が出ます。
- **結果の見方**: 画面「READ の確かめ」（画面の題は「見るだけの確かめ」）の定義ごとの結果と詳しい理由。成果物は `read-evidence.json` です（`MATCHED`・`NOT_MATCHED`・`UNDETERMINED` などの値）。`UNDETERMINED` の数と理由を、記録の表に書きます（「[描けなかった画面](discovery-and-read-check.md#描けなかった画面)」）。

## 読み取りの段で確かめられること・確かめられないこと

### 確かめられること

- **テスト環境の画面がつながる外部のサービス**: 監査の段では、ページ自身が読み込む許可 Origin の外の部品（画像、スクリプト、fetch など）への `GET` は送られます（「[認証つきの監査の監査の段](authenticated-audit.md#監査の段)」）。読み取りでない要求（`POST` など）、許可 Origin の外へのページの移動、ポップアップは、Guard が止めます。次の記録から、テスト環境の画面がつながる外部のサービス（アクセス解析、外部の API、外部の決済や通知のスクリプトなど）を観察できます。
  - `pages/<pageId>/page.json` のネットワークの Evidence（`type` が `network`）の `requests` の `url` と `method`: 送った要求（許可 Origin の外への `GET` を含む）。記録の数には上限があり、超えた分は `omittedRequestCount` に数えます。
  - `pages/<pageId>/page.json` の安全の Evidence（`type` が `safety`）: `blockedRequests`（Guard が止めた読み取りでない要求。`method`、`url`、理由）、`blockedNavigations`（許可 Origin の外へのページの移動。理由 `EXTERNAL_MAIN_FRAME_NAVIGATION`）、`blockedPopups`、`blockedWebSockets`、`blockedInteractionRequests`（理由 `GUARD_BYPASS_EGRESS` など）。
  - `run.json` の `safety`（`blockedActions`、`blockedRequestsByMethod`）と、`run.json` の `load.requests.otherOrigins`（許可 Origin の外へ送った要求の数と 1 分あたりの最大）。
  - 許可 Origin の外への `GET` は、実際にその外部のサービスへ届きます（アクセス解析の数字に入ることがあります）。ログインの段では、許可 Origin の外への要求はすべて止めますが、その記録は URL を持たず、保存もしないので、この観察には使えません（「[ログインの段の通信の制限](automated-login.md#ログインの段の通信の制限)」）。操作の候補の発見の `discovery.json` は、画面ごとの止めた数だけを持ちます。
- **HTTPS の証明書がブラウザに信頼されるか**: ブラウザが信頼しない証明書では、ページの読み込みが、ネットワークの層の失敗（`net::ERR_CERT_` で始まるコード）になります。監査の Run は、これをサイトの不調として扱い、確かめ直してから、再開できる状態で止まります（`PARTIAL`。`run.json` の `incompleteReasons` に `SITE_UNAVAILABLE`、`diagnostics/` に診断の記録。「[サイトが応答しないとき](site-unavailability.md)」）。手動のログインでは、ログインの画面を先に開きます。その画面での証明書の誤りの表れ方と、そのときのジョブの終わり方は、確かめていません。

### 確かめられないこと

- **サーバの裏側の隔離**: データベースが本番と別か、登録や更新のときにメール・SMS・外部の API への通知が出るか。BeakSight は、画面とブラウザの通信からしか観察できないので、これらは「未検証」と区分します。

## 書き込みの前に止めて判断する

手順 9 の後で、必ず止まります。ここまでの記録を見て、利用者が次を判断します。決めるまで、手順 10 のチェックを入れません（チェックを入れると、次の点検で書き込みます）。

- 読み取りの段で観察した外部のつながりを材料にして、サーバの裏側の隔離をどう扱うか（テスト環境の管理者に確かめる、など）。BeakSight の画面は、隔離の扱いを聞きません。
- 書き込み（API の登録と更新）まで行うか。行う場合は、テスト環境の管理者と、登録・更新されるレコード、通知、片付けの方法を確かめてから、チェックを入れます。チェックは、その画面の登録 1 件と更新 1 件の両方を許します（登録だけにする選び方はありません）。チェックしたままの画面では、点検のたびに登録を 1 件行います。
- どの画面で試すか（一覧「登録・更新を試せる画面」の行）。メールや電話への知らせを送ることがある画面の行には、その 1 行が出ます。だれにも届かない設定のテスト用のサイトのときだけ、チェックします。
- 書き込みの送り手が、テスト環境の証明書を信頼できるか（「[登録の要求の送り方](approved-create.md#登録の要求の送り方)」）。確かめられなければ、送る前に止まります（`BLOCKED`、`PRECHECK_FAILED`）。
- 手順 8 で、登録の画面のボタンの型が `API_CREATE` だったか（画面には出ないので、`discovery.json` の候補の `submissionProbe` で見ます）。`API_CREATE` でなければ、その画面の行は「この画面では試せません」になります（その理由を記録して、書き込みの段を「未検証」とします）。
- 更新について、次も決めます。
  - 更新してよいレコードか（対象は、BeakSight がその画面で登録して照合した最も新しい 1 件です）。
  - 更新で変える欄は、BeakSight が決めます（規則 F。登録で送った欄 → 登録の画面にある欄 → ほかの欄の順に、値が決まり毎回変わる欄から選びます。メールアドレスと電話番号は保ちます）。選べない画面は、行に「更新する欄を決められないため、登録だけを試します。」が出ます。
  - filter の名前が、更新の行を選ぶ列を指しているか（テスト環境の API の定義で確かめる）。
  - 更新の画面のボタンの型が `API_UPDATE` か（同じく `discovery.json` で見ます）。更新の画面は、作ったデータがあるときにしか見つかりません。データのないサイトでは、1 回目の点検は登録だけで、行に「更新は、次の点検で試します。」が出ます。更新は、次の点検の発見で更新の候補が見つかったときに、BeakSight がチェックの範囲の中で下書きと承認を行い、同じ点検で行います。その次の点検の前にも、同じように止まって判断します。
- 行わない場合は、チェックを入れず、書き込みの段を「未検証」と記録します。

## 10. 書き込む画面のチェック

書き込みは、別の作業にしません。点検（まとめて実行）の中で、プロファイルの詳細の一覧「登録・更新を試せる画面」でチェックした画面だけ、最後に登録 →（あれば）更新を行います（手順 11）。チェックの保存が、その画面への書き込みの承認を兼ねます。中では、今の承認の記録・digest・実行の許可・上限（「[書き込みのシナリオの承認の手順](scenario-approval.md)」「[承認された登録の手順](approved-create.md)」「[承認された更新の手順](approved-update.md)」）を、そのまま使います。書き込みの手順の画面、書き込みの OK と書き込みを始める確認のダイアログ、作ったデータの一覧の「更新を試す」は、ふだんの流れにありません（直すときと調べるときの道として、「詳しい内容」の中に残っています）。

### 10.1 一覧を見る

- **見る所**: 点検の後のプロファイルの詳細の、要点のパネルの下の一覧「登録・更新を試せる画面」。最後の発見で見つかった登録の画面（API の形とフォームの形）ごとに 1 行です。一覧の上に「チェックした画面では、点検のときに、テスト用のデータを 1 件登録し、1 回更新します。作ったデータは消しません。」が出ます。見つかっていなければ「登録・更新を試せる画面は、まだ見つかっていません。点検をすると、見つかった画面がここに出ます。」です。
- **行に出るもの**: 画面の名前（発見が記録した見出しか題。取れなければ「「◯◯」の登録の画面」「登録の画面（N）」の形。英字の path は出ません）、状態（「チェックしています」「チェックできます」「サイトの設定が変わったので、チェックが外れました。もう一度チェックしてください。」「この画面では試せません」）、試せない理由（秘密に見える欄がある、消す・取り消すなどの操作に当たる欄がある、答え合わせのしかたを決められない、サイトの設定が変わった、入力のしかたを扱えない）、更新の 1 行、知らせを送ることがある画面の 1 行、前の点検の結果。
- **送るもの**: 一覧を見るだけでは、サイトへ何も送りません。

### 10.2 チェックを入れる

- **すること**: 判断の点で決めた画面の行にだけ、チェックを入れます。チェックを入れると、その場で保存します（「保存しています…」。確認のダイアログはありません）。チェックを外すと、その画面の登録と更新の承認を取り消し、次の点検から書き込みません。
- **保存で BeakSight が行うこと**（1 回で行います）:
  1. 書き込みのモードへの切り替え（まだなら。監査モードを `TEST_APPROVED_WRITE` にした次の改訂。認証の設定、資格情報、承認したサービスの Origin は、同じプロファイルのものをそのまま使います）。この切り替えだけの改訂は、発見の結果の古さの判定では同じ改訂とみなします。
  2. その画面の書き込みの手順の自動の下書き: 登録（`CREATE`）のシナリオと、更新の候補があれば更新（`UPDATE`）のシナリオ。入力の規則、検証の指定（登録の ID の取り方と照合の READ）、更新で変える欄（規則 F）を、BeakSight が決めます（サイトには接続しません）。
  3. 承認（承認の記録と digest。副作用の確認の 4 項目は、チェックがその確認を兼ねます）。実行の許可は、ここでは出しません（点検の書き込みの段の前ごとに、ジョブの管理が出します）。
  - 前にチェックした画面のチェックを外して入れ直したときも、最後の発見の結果と今の作り方で、登録の手順を作り直します（同じなら承認だけ、違えば新しい版を作って承認します）。BeakSight を直した後に、答え合わせのしかたなどを新しくするのは、このチェックの入れ直しか、次の点検の始めの確かめ（手順 11.2）です。
- **送るもの**: サイトへは何も送りません。
- **止まるところ**（保存せず、行に理由が出ます）: 書き込みのモードにできなかった（ログインの設定を確かめる）、その画面の手順を作れなかった・承認を有効にできなかった（もう一度点検してからチェックする）、サイトの設定を読めなかった（読み込み直す）。
- **答え合わせのしかたが決まる所**（データのないサイトを含む）:
  - 登録の ID の取り方: API の形は、応答の本文の、登録の ID の鍵を勧めます。応答の本文の最上位の object（か、要素が 1 つだけの array のその object）の鍵の値を、ID として読みます。値は文字列か 0 以上の整数で、英数字・`_`・`-` だけの 1〜64 文字のときだけ使います。更新の候補がない（データのない）サイトでは、よくある番号の鍵（`id` など、名前つきの短い一覧）を推します。フォームの形で更新の候補がないときは、登録の送信先の型から番号の型（`<送信先の path>/{id}`）を推し、送った後の URL から取ります。
  - 照合の READ: 登録で送った毎回変わる値と比べる期待を、1 つ以上持たせます（行の数だけの期待では作りません）。API の形では、答え合わせの画面を次の順に選びます（OP-R の R1）。
    1. 発見で見つけた一覧・検索の READ の候補。
    2. 一覧の画面（登録の画面の 1 つ上の path で、監査の段のリンクにあるもの。手順 8 で読みます）。期待は「作った値を含む」で、比べるのは毎回違う作り方の欄（メールアドレス、電話番号、数字の番号、文字）だけです（前の登録の名前などで一致しないようにするため）。
    3. どちらもないときだけ、詳細の画面の型（登録の画面の 1 つ上の path に `{id}` を付けたもの）を推します。
    - 期待は緩めず、読むのは `GET` 1 回だけです。
  - 推しが外れて番号が取れなかったときは、その回は一部だけ確かめた（`PARTIAL`）として「確かめられませんでした」を出し、更新はしません。確かめの指定がそろわない画面は、送りません（行は「この画面では試せません」）。
  - API の要求の型（method、送り先の Origin、path の型、query の名前、本文の鍵と欄、ページが決める鍵、ページが付けるヘッダの名前）は、画面には出ません（承認が縛る型として管理データに残り、書き込みの結果の記録に出ます）。
- **中身を確かめたいとき**（ふだんは開きません）: プロファイルの詳細の「詳しい内容」の「書き込みの手順へ」で、書き込みの手順の画面を開くと、推測した項目（「推測した項目（確かめてください）」）、入れる値の決まり、書き込みの履歴を見られます。そこで直すと、版が進んで承認が外れるので、一覧の行が「もう一度チェックしてください」になります。

## 11. 次の点検での登録と更新

チェックした画面で、次の点検の最後に、登録 1 件と（あれば）更新 1 件を送り、照合の READ で確かめます。全体の決まりは「[承認された登録の手順の API の登録](approved-create.md#api-の登録)」と「[承認された更新の手順の API の更新](approved-update.md#api-の更新)」にあります。

### 11.1 前提

- 手順 10 で、1 つ以上の画面の行が「チェックしています」になっていること。
- 更新は、同じ点検の登録の段で BeakSight が作り、照合まで済んで番号が取れたレコードだけが対象です（BeakSight が作っていないレコードは更新しません）。登録の ID が取れずに一部だけ確かめた（`PARTIAL`）ときは、その点検では更新しません。
- チェックしたままの画面では、点検のたびに登録を 1 件行います（登録をせずに更新だけを行う選び方はありません）。テスト環境の管理者と決めた件数を超えないように、続けて書き込まない画面はチェックを外します。
- 更新の画面の候補は、発見で、登録したレコードの更新の画面を読んだときだけ出ます。`API_UPDATE` になるのは、`PATCH` で、filter がちょうど 1 つ（`eq`）で、その値が画面の path の最後の ID と同じ要求だけです（「[型の分類](discovery-and-read-check.md#型の分類)」）。発見はページの上限（3）までしか読まないので、更新の画面が読む範囲の 3 ページに入らなければ、候補は出ず、更新はしません。
- 対象のレコードの保つ欄の値が、BeakSight の外（テスト環境の画面で人が変えるなど）で変わっていないこと。保つ欄は台帳が知る値と比べるので、外で変わったレコードは更新できません（下の 11.4）。

### 11.2 始める

- **すること**:
  1. 判断の点に戻り、続けることを決めてから進みます。
  2. プロファイルの詳細の「点検を始める」から開始の画面を開きます。要点に「サイトのページを見て回り、操作できる所を探します。チェックした画面では、テスト用のデータを登録・更新します。そのほかは見るだけです。」が出ることを確かめ、主のボタン「点検を始める」を押します（手順 7 と同じ）。
- **始めの確かめ**（サイトへは何も送りません）: 点検を始めるときに、BeakSight が、チェックした画面の登録の手順を、最後の発見の結果（前回までの点検のもの）と今の作り方で作り直して比べます。答え合わせのしかただけが違えば、新しい手順を自動で承認します。送る中身が違えば、承認を外し、行を「もう一度チェックしてください」にします（その画面には書き込みません）。一覧のどの行にも結び付かない承認は取り消します。この確かめを終えられないときは、点検を始めません（見るだけの段も始まりません。「[まとめて実行](stage-chain.md#書き込みの段)」）。
- **流れ**: 自動ログイン 1 回 → 監査（BeakSight は書き込まない） → 発見 → READ の確かめ → チェックした画面ごとに、登録の段 →（あれば）更新の段。書き込みの段の前ごとに、ジョブの管理が承認と上限を確かめ直して実行の許可（5 分の期限、1 回だけ）を出し、件数を 1 件予約します。ログインは点検の 1 回だけで、書き込みにもそのまま使います（ログインの状態を作業の外へ持ち出しません）。
- 監査・発見・READ の確かめの報告は、今までどおり「読み取りだけ」です。チェックした画面があるときは、監査の報告（HTML）のまとめに「この点検では、この後に、チェックした画面でテスト用のデータを登録・更新します。結果はサイトの画面に出ます。」の 1 行が出ます。書き込みの段の Run と報告は、段ごとに分かれます（「[書き込みの報告](output.md#書き込みの報告)」）。
- 更新の候補が、この点検の発見で初めて見つかったときは、BeakSight がチェックの範囲の中で、更新の下書きと承認を自動で行い、同じ点検で更新します（人がすることはありません）。ただし、更新の画面がメールや電話への知らせを送ることがあるときは、自動では承認せず、行に「更新の画面は、メールや電話への知らせを送ることがあります。もう一度チェックすると、更新も試します。」が出ます。

### 11.3 登録の段で送るもの

- **送るもの**（成功の 1 回。どの読み込みも、設定の間隔を守ります）:
  - 画面の確かめ（`GET`）と、書き込みの画面（`GET`）。書き込みの画面では、承認したサービスの Origin への `GET`・`HEAD` を上限の中で通します。
  - サイトが自動でする通信（送信の扱いが「削除のほかを通す」のとき）: 画面の確かめ・書き込みの画面の値を入れる前・照合の READ の画面では、ページが自動で出す読み取りでない要求のうち、削除と危険な語のほかで、送り先が許可 Origin か承認したサービスの Origin のものを通します（データを読む手続きの呼び出しなど）。承認した送信先とその下のアドレス、WebSocket、許可の外は通しません。値を入れた後と押した後には当てません（「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」の書き込みのジョブの項）。読み取りだけのサイトでは、今どおりすべて止めます。
  - 値を入れて押すと、ページのスクリプトが組み立てた登録の要求を Guard が止め、承認した型と生成した値に照らします。一致した 1 回だけを、BeakSight の送り手が送ります（再送しません）。応答はページに返します。**BeakSight が書き込みとして送る要求は、この 1 回だけです。**
  - 照合の READ: 答え合わせの画面（手順 10.2 の順。一覧の画面なら `{id}` を入れずに、詳細の画面の型なら取れた ID を `{id}` に入れて）の path に、保存の時と同じ確かめをかけ直してから、1 回読みます（`GET`）。詳細の画面の型で ID がなければ読みません。
- **止まるところ**（送らずに止まれば、結果は `BLOCKED`、件数の予約は返します）:
  - 送る前の確かめ（承認と許可が今も有効か、送信の要素と鍵の欄があるか、成功の鍵の消失、要求の上限、書き込みの送り手の証明書）。
  - **入力の途中で自動保存するページ**: 値を入れた後に、ページが読み取りでない要求か、入れた値（目印）を含む要求を出すと、押さずに止まります（意図した止まり方。承認した形の要求でも止めます）。このときは、書き込みのジョブはそのページでは使えません。値を入れた後に出た読み取り（`GET`・`HEAD`）と WebSocket の張り直しで、目印を含まないものは、止めたまま、書き込みは続けます。止めた要求の数は、書き込みの報告の Guard の要約に出ます。
  - 照合で止めた要求（型・値・ヘッダの名前・query が承認と違う）は送りません（`PAYLOAD_MISMATCH`）。
- **結果の判定**:
  - 結果の判定は、応答の HTTP の状態（2xx は成功、429 は要求が多すぎる、ほかの 4xx は入力の誤り、5xx はサーバの誤り）と、取れた登録の ID で決めます。
  - `VERIFIED`: 2xx で、ID が取れ、照合の READ が一致した。`PARTIAL`: 2xx だが、ID が取れない・使えない形、照合の READ を判定できない。`UNKNOWN`: 送ったが、登録されたか分からない（応答がない、5xx、照合の READ が一致しない、など）。`FAILED`: 送ったが、サイトが登録しなかったと判定できる（ほかの 4xx、429）。
  - `UNKNOWN` のときは、テスト環境で登録があるかを確かめます（「[UNKNOWN の後にすること](approved-create.md#unknown-の後にすること)」）。自動の再試行はしません。
  - BeakSight は、作ったデータを消しません。

### 11.4 更新の段で送るもの

- 対象は、同じ点検の登録の段で作り、照合まで済んで番号が取れたレコードです（BeakSight が自動で選びます。人は ID を入れません）。
- **送るもの**（成功の 1 回。どの読み込みも、設定の間隔を守ります）:
  1. **前の読み取り**（`GET`）: 凍結した環境で、対象の ID の更新の画面を 1 回読みます。画面の path を型にした識別で承認した候補がちょうど 1 つあり、その path の最後の ID が対象の ID であることを確かめます。変える欄・保つ欄・ページが決める鍵の欄の今の値（前の値）を、落ち着くまで待って読みます（下の「値の落ち着きの待ち」）。値はメモリの中だけで扱います。
  2. **書き込みの画面**（`GET`）: 更新の画面を開き直し、欄の値が前の値と同じかを確かめます（違えば送りません）。変える欄にだけ値を入れます。保つ欄には触りません。押す直前（送る直前の確かめ直しの前）に欄を読み直し、保つ欄とページが決める鍵の欄が前の値のまま、変える欄が入れた値のままでなければ押しません。
  3. **更新の要求**（`PATCH` 1 回）: 2 段の窓（観察の段 → 押す直前の確かめ直し → 送信の段）で、Guard が承認した型と照らし、一致した 1 回だけを BeakSight の送り手が送ります。照らすのは、filter の値が `eq.<対象の ID>` と完全に一致すること、変える鍵が生成した値と一致すること、本文にある保つ鍵とページが決める鍵が前の値と一致すること（保つ鍵が本文になければ通します）、承認の外の状態の鍵がないこと、などです。
  4. **後の照合**（`GET`）: 書き込みの段を閉じた後、凍結した環境で更新の画面を 1 回読み直し、変えた欄が新しい値、保つ欄とページが決める鍵の欄が前の値であることを、欄ごとに照らします。
  5. **照合の READ**（`GET`）: 後の照合で一致しない欄がなければ、`{id}` に対象の ID を入れた画面を 1 回読みます。
  - **更新の段の読み取りでない要求は、`PATCH` の 1 回だけです。** 送らずに止めた回のサイトへの読み込みは、前の読み取りと書き込みの画面の 2 回以下です。
- **値の落ち着きの待ち**: SPA の画面が値を後から入れる前に読まないよう、前の読み取り・書き込みの画面・押す直前の読み直し・後の照合のどれでも、次の順に待ってから値を読みます。
  - ページの要求が止んで（読み込み中の要求がなく、500 ミリ秒静か）、欄の値が続けて 2 回同じになるまで待ちます。
  - 要求が止むのを待つのは最大 3 秒（`API_WRITE_VALUE_QUIET_TIMEOUT_MS`）です。開いたままの要求があるページは、3 秒の後に、欄の値を 0.5 秒おきに読み、続けて 2 回同じになったら進みます（最大 10 回。落ち着かなければ送りません）。同じ Run の残りの読み取りでは、この 3 秒の待ちを省きます。テスト用のサイトでは、開いたままの要求がある画面の更新は、1 回に約 14 秒かかりました。
  - 前の読み取りで、目印を入れた欄（変える欄と保つ欄）の値がすべて空なら、値が入る前の画面とみなして送りません（`PRECHECK_FAILED`）。
  - **保つ欄は、台帳が知る値と比べます。** 台帳が知る値は、BeakSight がそのレコードの登録と、照合済みの更新で送った値です。前の読み取りか押す直前の読み直しで、保つ欄の値が台帳が知る値と違えば送りません（`PRECHECK_FAILED`）。後の照合で違えば、照合できない（`PARTIAL`、`UPDATE_POSTCHECK_UNDETERMINED`）です。そのため、次の画面とレコードでは止まります。
    - 値が入る前に仮の値（「読み込み中」など）を出す画面。
    - BeakSight の外（テスト環境の画面で人が変えるなど）で、保つ欄の値が変わったレコード。新しく登録してから更新します。
  - 限界: 台帳が知らない保つ欄（登録で送らなかった欄）は、台帳の値と比べられません。その欄だけをページのタイマーで遅れて入れる画面は、見分けられないことがあります。
- **止まるところ**（送らずに止まれば、結果は `BLOCKED`、件数の予約は返します）:
  - 前の読み取りで、承認した候補がちょうど 1 つない、path の最後の ID が対象の ID でない、欄が読めない、値が落ち着かない、目印を入れた欄の値がすべて空、保つ欄の値が台帳が知る値と違う、変える欄の前の値が長すぎる（8,192 文字を超える）（`PRECHECK_FAILED`）。
  - 書き込みの画面の値が前の値と違う、押す直前の読み直しで値が変わっていた（`PRECHECK_FAILED`）。
  - ページのスクリプトが、保つ欄の値や filter の値を書き換えて送ろうとした（Guard が照合で止めます。`PATCH` はサイトに届きません）。
  - 入力の途中で自動保存するページ、送る直前の確かめ直し、成功の鍵の消失、要求の上限（登録と同じ）。
- **結果の見方**: ジョブの画面の「書き込みの結果」（結果、理由、送信、応答、「更新の対象のレコード」、前後の差分（変えた欄の前の値・新しい値・後の照合、保つ欄の照合）、照合の READ、予約の締め）と、書き込みの報告、台帳。ページが決める鍵の値は、更新では残しません（「更新では値を残しません（送る前の画面の値と同じであることを照らしました）」）。

  | 場面 | 結果 | 理由 |
  | --- | --- | --- |
  | 2xx で、後の照合で変えた欄が新しい値・保つ欄が前の値、照合の READ が一致（本文が変える鍵だけの場合、応答が 204 の場合を含む） | `VERIFIED` | `READ_VERIFICATION_MATCHED` |
  | 後の照合で一致しない欄がある（サーバが保つ欄を変えた副作用、204 で何も変わっていない、など） | `UNKNOWN` | `UNEXPECTED_FIELD_CHANGE` |
  | 2xx で、応答の本文が空の一覧 `[]`（更新した行がない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
  | 2xx で、応答の本文が 2 行以上の一覧（どの行が変わったか分からない） | `UNKNOWN` | `MULTIPLE_CONDITIONS_MATCHED` |
  | 2xx で、応答の本文が空でなく、1 MiB を超えるか JSON として読めない（行の数が分からない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
  | 応答の本文の ID の鍵の値が、対象の ID と違う | `UNKNOWN` | `RECORD_ID_MISMATCH` |
  | 後の照合を読めない | `PARTIAL` | `UPDATE_POSTCHECK_UNDETERMINED` |
  | 照合の READ を判定できない／一致しない | `PARTIAL`／`UNKNOWN` | `READ_VERIFICATION_UNDETERMINED`／`READ_VERIFICATION_NOT_MATCHED` |
  | 400（ほかの 4xx）・429 | `FAILED` | `INPUT_ERROR`・`RATE_LIMITED` |
  | 503（5xx） | `UNKNOWN` | `SERVER_ERROR` |
  | 応答がない | `UNKNOWN` | `NO_RESPONSE` |
  | ページが保つ値や filter を書き換えた | `BLOCKED` | 送る中身の照合で止めた（`PATCH` は届かない） |

  - 値の比べ方は完全な一致です（改行だけ同じと見なします）。サーバが値を整形する（前後の空白を除く、大文字にするなど）と、`UNEXPECTED_FIELD_CHANGE` になります（正規化を足すかは Task 44 で判断します）。
  - `UNKNOWN` のときは、テスト環境でレコードの状態を確かめます。自動の再試行はしません。
  - 同じシナリオで続けて更新するときは、5 分以上あけます（24 時間に 5 件まで）。2 回目も、台帳の最も新しい照合済みの登録が対象です（同じレコードを何度でも更新できます）。

### 11.5 結果の見方

- **プロファイルの詳細**: 点検を終えて移ってきた要点の 1 行目の点検の結果の次に、書き込みの 1 行が出ます（「チェックした画面では登録・更新も行いました。」「チェックした画面では登録も行いました。」（更新の画面がまだない）「チェックした画面の登録・更新に、確かめられなかったものか、試せなかったものがあります。」「チェックした画面の登録・更新は、試せませんでした（何も送っていません）。」）。一覧の行の「前の点検の結果」に、登録と更新の結果（「登録しました」「登録は確かめられませんでした。」「更新しました」「更新は確かめられませんでした」「更新は試せませんでした」、送らずに締めた回は「前回は試せませんでした。…」）が出ます。
- **ジョブの画面**: 書き込みの段のジョブの画面の「詳しい内容」の「書き込みの結果」（結果、理由、送信、応答の HTTP の状態と判定、登録の ID、照合の READ、予約の締め、ページが決める鍵とその値。更新は「更新の対象のレコード」と前後の差分）。書き込みの報告（`action-report.html` とバンドル）。プロファイルの詳細の「詳しい内容」の「作ったデータの一覧を開く」（監査済みデータの台帳）。
- **まとめて実行が止まるとき**: 結果が分からない画面（`UNKNOWN`）の後は、残りの画面の登録・更新をしません（止めた理由「テスト環境の画面で、データが作られたかを確かめてください。残りの画面の登録・更新はしていません。」）。試せなかった画面には何も送っていません（一覧で、その画面の様子を確かめます）。書き込みの途中でログインが切れたときは、ログインし直さず、残りの書き込みを止めます（行に「ログインが切れたため試せませんでした」）。
- `UNKNOWN` のときは、テスト環境で登録や更新があるかを確かめます（「[UNKNOWN の後にすること](approved-create.md#unknown-の後にすること)」）。自動の再試行はしません。
- 次の点検で同じ画面にもう一度書き込むときは、同じシナリオの 5 分の間隔と 24 時間に 5 件の上限を守ります（自動ログインの 5 分の間隔もあるので、ふつうは収まります）。チェックしたままなら、次の点検でも登録を 1 件行います。続けて書き込まないときは、チェックを外します。

### 11.6 更新の画面について観察すること

テスト環境の更新の画面が、次の作りかどうかは、まだ分かっていません（未確認）。どれも、送らずに止まるかと、かかる時間に効きます。普段のブラウザの開発者ツールと、書き込みの結果の止まった所から観察し、記録の表に書きます。

- 値を遅れて入れるか（画面を開いた直後は欄が空で、後から値が入る）。
- 値が入る前に、仮の値（「読み込み中」など）を出すか。
- 開いたままの要求があるか（開発者ツールの「ネットワーク」で、終わらない要求が残る。リアルタイムの更新など）。

## 記録の取り方

記録は、Git の管理の外（例 `local/` の下）に置きます。本来の監査対象のサイトの名前と URL を、Git に載るファイルに書きません。成果物の中身を記録に写すときは、Origin・path・名前を「テスト環境の Origin」「管理画面の path 1」のように伏せ、件数と状態だけを写します。外へ渡すときは「[成果物を外へ渡す前の確かめ](anonymization.md)」に従います。資格情報、Cookie、トークン、ページが決める鍵の値は、記録に書きません。

## サイトが応答しなくなったとき

サイトが応答しなくなったら、まず BeakSight がその時に接続していたかを、次の順に確かめます。確かめた事実を、時刻とともに記録します。

1. **ジョブの状態**: 左のメニューの「作業の履歴」で、動いているジョブがあるかを見ます。監査は画面全体で同時に 1 つ、書き込みも同時に 1 つだけです。動いているジョブがあれば、ジョブの画面の止めるボタン（画面では「点検を止める」など、ジョブの種類の名前。まとめて実行も「点検を止める」）で止めます（30 秒たっても止まらなければ「強制的に止める」。「[止める・強制的に止める](local-ui.md#止める強制的に止める)」）。
2. **Run の状態と終わり方**: 監査の Run なら、ジョブの画面の Run の状態と終わり方、`run.json` の `executions` の最後の `endReason`（`STOPPED_BY_SITE_UNAVAILABLE` なら BeakSight がサイトの不調を検知して止まった）、`incompleteReasons` の `SITE_UNAVAILABLE` と、`diagnostics/` の診断の記録を見ます。監査は、サイトの不調を検知すると、そのページを捨てて待ち（60 秒・2 分・4 分・8 分）、同じページを確かめ直します（1 ページにつき最大 4 回）。待っている間は、サイトへ何も送りません（「[サイトが応答しないとき](site-unavailability.md)」）。発見と READ の確かめは、60 秒待って 1 回だけ確かめ直し、まだ不調ならジョブを止めます（終わり方 `SITE_UNAVAILABLE`）。書き込みは、読み直しをしません。
3. **Run のロック**: 監査の Run のディレクトリの `checkpoint/run.lock` は、実行中は 1 分ごとに更新されます。最後の更新から 5 分より長く経っているか、作ったプロセスが動いていなければ、その Run は動いていません（「[中断と再開](resume.md#中断と再開)」）。
4. **Chromium のプロセス**: タスク マネージャーの「詳細」で、BeakSight のワーカーが動かす Chromium（Playwright に同梱の通常の Chromium）のプロセスが残っていないかを見ます。画面のサーバを止めると、ワーカーと、ワーカーが動かしていた Chromium も止まります（「[画面のサーバが落ちたとき](local-ui.md#画面のサーバが落ちたとき)」）。プロセスの名前とパスの見え方は、この手順のために確かめていません。
5. **時刻の照らし合わせ**: サイトが応答しなくなった時刻と、ジョブの開始・終わりの日時、`run.json` の `load`（1 分あたりの最大）を照らします。書き込みのジョブが動いていたなら、「書き込みの結果」の送信の時刻と結果も照らします。

- 再開は、サイトが戻ってから行います。サイトが戻る前に再開すると、止まるきっかけになったページは失敗として残ります。
- サイトの不調が BeakSight の負荷によるものかは、BeakSight の記録だけでは決められません。テスト環境の管理者のサーバの記録と照らします。

### 点検の始めの確かめとチェックの、まれな場合の見え方（既知の点）

どれも、テスト用のサイトとコードの読みで分かったことで、直していません。サイトへ余計に送ることはありません。

- 始めの確かめは、前回までの点検の発見の結果で行います。その点検の発見の段の結果では、確かめ直しません（次の点検で反映されます）。
- 始めの確かめを終えられずに点検を始めないとき、出る文は「書き込みの OK を使えませんでした」です（今の画面のチェックの言葉と合いません）。見るだけの段も始まりません。
- 送る中身が変わってチェックが外れたときも、行には「サイトの設定が変わったので、チェックが外れました。…」が出ます（原因ごとの文はありません）。
- 管理データの取り消しの口が拒んだときに、チェックを外しても外れたように見え、承認が残って、次の点検の開始を拒み続けることがあります。
- 発見の結果がない・読めないときは、チェックした画面の承認をすべて取り消します（一覧も出ないので、もう一度点検してからチェックします）。
- 作成の画面から続けて始まる 1 回目の点検は、始めの確かめを通りません（その時点では書き込みの手順がないので、書き込みはしません）。

## 「未検証」と区分するもの

次に当たる段は、「未検証」と記録し、確かめた段と分けます。

- 対応しないログイン（別の Origin の IdP へ画面が移るログイン、MFA、CAPTCHA）のため、行えなかった段。
- ブラウザが HTTPS の証明書を信頼せず、行えなかった段。書き込みの送り手が証明書を信頼できず、送らずに止まった書き込み。
- サーバの裏側の隔離（データベース、登録・更新のときのメール・SMS・外部の API への通知）。BeakSight では観察できません。
- 判断の点で行わないと決めた書き込み（登録と更新）。
- 手順 8 で `API_CREATE` の型が観察できず、シナリオを作れなかった書き込み。
- 入力の途中で自動保存するページのため、押さずに止まった書き込み（意図した止まり方。次にできることの表示は Task 44 で扱います）。
- 書き込みの画面が、登録した読み取りの手続きの呼び出しがないと描けないために、送る前の確かめで止まった書き込み（送信の扱いが読み取りだけのサイトでは、書き込みのジョブは、その呼び出しを通しません。「削除のほかを通す」のサイトでは、値を入れる前に通します）。
- 一覧の画面から開く入力（「編集」のボタンで開く画面の中の入力など）で行う更新。BeakSight は、まだ扱いません（更新の候補になりません）。
- 手順 8 で `API_UPDATE` の型が観察できず、または更新の画面が読む範囲の 3 ページに入らず、更新のシナリオを作れなかった更新。
- 欄として識別できないページが決める鍵を持つ型のため、作れなかった更新のシナリオ（`SCENARIO_API_PAGE_KEY_NOT_IDENTIFIABLE`）。
- 台帳の ID と filter が結び付かず、作れなかった更新のシナリオ。
- データのないサイトで、番号の型や鍵の推しが外れ、番号が取れずに一部だけ確かめた（`PARTIAL`）登録と、そのために行わなかった更新。
- 一覧の行が「この画面では試せません」になり、チェックできなかった画面。
- 時間や負荷の都合で、途中で止めた段。

API の書き込みの限界（Task 38〜40 の設計書の履歴による。テスト用のサイトでは確かめた範囲の外です）:

- 応答をページに返せなかった印（`RESPONSE_NOT_DELIVERED`）は、取り消しの時刻とブラウザによって付かないことがあります。成功とは偽りません（最後の守りは、毎回変わる値と比べる照合の READ です）。
- ページが決める鍵の値は照らしません（承認で名前と JSON の型を結び、値は書き込みの結果の記録に残します）。
- ヘッダの値は、`Content-Type` と `Prefer` のほかは照らしません。`select` の query の値も照らしません。
- form のない画面（ボタンの候補）の欄は、制約（必須、長さ、形、選択肢）を持たないので、欄の制約に基づく値の確かめは効きません。
- 本文が 64 KiB を超える型は、実行できないものになります。
- 書き込みの報告の API の判定の説明は、「成功の条件と入力の誤りの条件を使いません」の形のままです（フォームの書き込みも、今は成否の条件を使わず、応答の状態と照合で決めます）。
- 値が 2 つだけの固定の一覧も「実行のたびに変わる値」とみなします（境目は Task 44 で判断します）。
- 書き込みの送り手が HTTP/2 だけを話すサイトに送れるかは、API の書き込みでは確かめていません（form の書き込みでは送れません）。
- API の更新の filter の値と query の名前は、URL の percent-encode を戻した後で比べます（`eq%2E<ID>` のような書き方も、同じ値として通します）。
- API の更新の filter の列の名前は、BeakSight では確かめられません（人がテスト環境の API の定義で確かめます）。
- API の更新の変えた欄の前の値は、平文で記録されます。登録の後に人がそのレコードを編集していれば、その人の値も記録と画面に出ます（「[承認された更新の証拠と記録](approved-update.md#証拠と記録)」と同じ）。
