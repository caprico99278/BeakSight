# 実テスト環境の手順（低負荷の確かめ）

本来の監査対象のサイトのテスト環境で、読み取りの段（入口の確かめ、ログイン、認証つきの監査、操作の候補の発見、READ の確かめ）と、API の登録と、API の更新を、低い負荷で確かめる手順です。
書き込みの段の前で必ず止まり、続けるかを利用者が判断します（下の「[書き込みの前に止めて判断する](#書き込みの前に止めて判断する)」）。
この確かめは、テスト環境が本番から隔離されているかを観察することも目的に含みます。そのため、HTTPS の証明書と隔離は、事前に確かめられていなくても、読み取りの段を始めてよいことにしています（下の「1. 事前の確かめ」と「[読み取りの段で確かめられること・確かめられないこと](#読み取りの段で確かめられること確かめられないこと)」）。

[README に戻る](../../README.md)・[仕様の索引](README.md)

## この手順の決まり

- **Run とジョブの起動と再開、ログインは、利用者（運用者）が行います。** 見張りと記録の担当は、画面と記録を見るだけで、起動とログインをしません。
- **負荷の上限**: 設定のファイルの `crawl.maxPages` は `3`、`crawl.minNavigationIntervalMs` は `10000`（10 秒）にします。画面の「開始の URL から新しく作る」で作ったファイルは、最初からこの値です。どのジョブも、この値で読みます。プロファイルの詳細の「監査の負荷」で変えられますが、実テスト環境では、サイトの運営者と決めた値の外にしないでください（間隔は今の下限より短くできません）。
- **読み込み直しはしません。** 発見、READ の確かめ、書き込みのジョブは、読めなかった画面を読み直しません。サイトが応答しないときだけ、監査は待ってから同じページを確かめ直し（最大 4 回）、発見と READ の確かめは 60 秒待って 1 回だけ確かめ直します（下の「[サイトが応答しなくなったとき](#サイトが応答しなくなったとき)」）。
- **自動ログインの上限**: 同じプロファイルで 5 分以上あけ、24 時間に 10 回までです（「[ログインの送信の回数と上限](automated-login.md#ログインの送信の回数と上限)」）。自動ログインのプロファイルでは、ログインのあるジョブ（ログインの確かめ、監査、発見、READ の確かめ、書き込み）ごとに、自動ログインを 1 回行います。1 日の段取りは、この数に収まるように組みます。
- **書き込みの上限**: 書き込みのジョブは 1 回に 1 件だけ送ります。同じシナリオの書き込みは 5 分以上あけ、24 時間に 5 件までです（「[承認された登録の上限](approved-create.md#上限)」）。
- **名前を書かない**: 本来の監査対象のサイトの名前、ドメイン、URL、対象のサイトのプラットフォームの名前、外部の認証のサービスの名前を、Git に載るファイルに書きません。設定のファイルと記録は、Git の管理の外（`local/`）に置きます。
- **行えなかった部分は「未検証」と区分します。** 「完成」「本番検証済み」とは書きません（下の「[「未検証」と区分するもの](#未検証と区分するもの)」）。

## 手順の一覧

「読み取りでない要求」は、BeakSight がサイトへ通す `GET`・`HEAD` のほかの要求です。ページ自身が読み込む画像・スクリプト・fetch の `GET` は、どの段でも届きます。

| 段 | 利用者がすること | 読み取りでない要求 | 止まるところ |
| --- | --- | --- | --- |
| 1. 事前の確かめ | 下の表を確かめる | 0（BeakSight を使いません） | 確かめられない項目がある |
| 2. 画面の起動 | `npm run ui` | 0（サイトへ送りません） | ビルドの失敗、port の使用中 |
| 3. プロファイルの作成 | 開始の URL を入れて保存 | 0（サイトへ送りません） | 名前の重なり、予約名、置き場所のリンク |
| 4. 入口の確かめ | 「入口を確かめる」 | 0（開始の URL の読み込み 1 回だけ） | 許可 Origin の外へ移ろうとした、読めなかった |
| 5. 手動のログインと自動の登録 | ログインし、「ログインを終えた」を押す | 利用者のログインの操作で、ページが出す送信（止めずに通し、形だけ記録） | ログインの時間切れ、扱えないログインの形 |
| 6. 自動ログイン | 「ログインを確かめる」 | ログインの送信 1 回（スクリプトで送る形は token の送信 1 回と、登録したログインに伴う送信） | 成功でない結果、資格情報を含む要求 |
| 7. 読み取りの監査 | 「監査を始める」 | ログインの送信のほかは、登録した読み取りの手続きの呼び出しだけ | セッションの切れ、要求の上限、サイトの不調 |
| 8. 発見（probe） | 「操作の候補を探す」 | ログインの送信のほかは、登録した読み取りの手続きの呼び出しだけ（probe の押下は何も送りません） | 要求の上限、成功の鍵の消失 |
| 9. READ の確かめ | 定義を作り「READ を確かめる」 | 8 と同じ | 要求の上限、成功の鍵の消失 |
| 判断の点 | 書き込みまで進むかを決める | — | ここで必ず止まる |
| 10. API の登録 | シナリオ → 入力の規則 → 承認 → 「書き込みを始める」 | ログインの送信と、承認した登録の要求 1 回だけ | 送る前の確かめ、自動保存、照合の不一致 |
| 判断の点 | 更新まで進むかを決める | — | ここで必ず止まる |
| 11. API の更新 | 更新のシナリオ → 入力の規則 → 承認 → 「書き込みを始める」（照合済みの登録がなければ「登録してから更新する」） | ログインの送信と、承認した更新の要求（`PATCH`）1 回だけ（「登録してから更新する」は、登録の要求 1 回と `PATCH` 1 回） | 前の読み取り、値の落ち着き、ページの書き換え、後の照合の不一致、登録が照合済みにならない |

## 1. 事前の確かめ

始める前に、次を確かめます。「事前に確かめなくてよい」と書いた項目のほかは、1 つでも確かめられなければ、始めません。

| 項目 | 確かめること |
| --- | --- |
| Gate | テスト用のサイト（fixture）での確かめの承認が済んでいること（G40 まで承認済み。2026-10-18）。 |
| ビルド | `npm run build` と `npm run build:ui` が通ること（`npm run ui` が両方を行います）。 |
| 設定のファイル | 前もって作らなくてかまいません（手順 3 で画面が作ります）。画面が作るファイルは、最初から `crawl.maxPages` が `3`、`crawl.minNavigationIntervalMs` が `10000` です（手で作るときは、この値にします）。どの作り方でも、最初の読み込みの前に、`node dist/cli/index.js validate-config --config local/targets/<名前>.json` が「設定に、誤りはありません。」を出すことを確かめます。前の使い方（ファイルを手で作る）では、`site.startUrl`（ログインの後の管理画面）と `site.allowedOrigins` も書きます。形は `config/targets/example-test-environment.json.example` の `targetConfig` と同じです。 |
| 隔離の証跡 | 読み取りの段は、隔離が未確認でも始めてよい。読み取りの段がサイトへ送るのは、ログインの送信（POST）と、利用者が登録した読み取りの手続きの呼び出しのほかは読み取りだけで、サイトのデータも外部への通知も変えないためです。このとき、プロファイルの `environmentEvidenceRef` には、未確認であることが分かる参照（例 `isolation-unverified-20261019`。秘密を含まない）を入れます。隔離を確かめた記録（テスト環境の所有者の接続の許可、テスト専用の Origin であること、データベース・メール・SMS・決済・外部の API が本番と分かれていることなど）があれば、Git の管理の外に置き、その参照を入れます。BeakSight は参照の中身を読まず、形とあるかだけを確かめます（「[`environmentEvidenceRef`](profiles.md#environmentevidenceref)」）。書き込みの段に進むかは、判断の点で決めます。 |
| ログインの方式 | ログインの送り方が、フォームの送信（ページの移動の POST）か、画面の中のスクリプト（fetch・XHR）で token を取りに行く形か。スクリプトの形は、「スクリプトで送るログイン」の設定のときだけ扱います（手動のログインと自動ログイン）。別の Origin のログインのサービス（IdP）へ画面が移るログイン、多要素認証（MFA）、CAPTCHA は、BeakSight が扱えません。扱えないときは、ログインが要る段を「未検証」とします。確かめ方は、下の「[ログインの方式の確かめ方](#ログインの方式の確かめ方)」にあります。 |
| アカウント | テスト環境のテスト用のアカウントであること。本番の資格情報、ふだん使うパスワードは使いません。自動ログインは Windows だけです。資格情報は 4 文字以上の値にします。 |
| HTTPS の証明書 | 事前に確かめなくてよい。最初の低負荷の Run で分かります（下の「[読み取りの段で確かめられること・確かめられないこと](#読み取りの段で確かめられること確かめられないこと)」）。BeakSight は、証明書の誤りを無視して読み進める作りではありません。書き込みまで進む場合だけ、書き込みの送り手が同じ証明書を信頼できるかを、その時点で確かめます（送り手は、Node の同梱の証明書と OS の証明書で確かめます）。 |
| 読まないパス | ログアウトの画面と、開くだけで状態が変わる画面（承認、送信、取り消しなど）の path を、テスト環境の管理者と確かめておくこと。 |
| 書き込みの相談（書き込みまで進むとき） | テスト環境の管理者と、登録・更新されるレコード、通知、片付けの方法を確かめておくこと。決まっていなければ、書き込みの段は行いません。 |
| 前に作ったシナリオと承認（書き込みまで進むとき） | Task 41 で、承認を縛る項目に「保つ鍵」を足しました。そのため、今までに承認したシナリオは、すべて承認し直しが要ります（画面での見え方は、この手順のために確かめていません）。Task 41 より前に保存した API の更新のシナリオ（保つ鍵などの指定を持たない形）は、読みません（管理データの誤り `DATABASE_INTEGRITY_FAILED` で止まります。利用者のデータには残っていません）。 |
| 書き込みのプロファイルの発見（書き込みまで進むとき） | API のシナリオは、書き込みのプロファイル（`TEST_APPROVED_WRITE`）で、プロファイルを最後に編集した後に行った発見の候補からだけ作れます。前に行った発見の結果は、型の記録が足りないことがあるので、書き込みのプロファイルで「操作の候補を探す」をやり直します（手順 10.2）。 |

### ログインの方式の確かめ方

BeakSight を使う前に、普段のブラウザで確かめます。

1. テスト環境のログインの画面を開き、開発者ツールの「ネットワーク」タブを開きます。
2. 「ログを保持」（Preserve log）にチェックを入れます。ページが移っても、記録が消えないようにするためです。
3. ログインします。
4. ログインを押した直後の `POST` の行の「種類」（Type）と、送り先のホストを見ます。
   - 「種類」が `document` なら、フォームの送信（ページの移動）です。送り先のホストがログインの画面と同じ Origin なら、BeakSight のログインの段が扱える形です。認証の設定の「ログインの送信先」に、その Origin と path を入れます。
   - 「種類」が `fetch` か `xhr` なら、画面の中のスクリプトで送る形です。外部の認証のサービスへ token を送るものなども、この形です。認証の設定の「ログインの送り方」を「スクリプトの送信」にして扱います（下の「[スクリプトで送るログインの設定の値](#スクリプトで送るログインの設定の値)」）。「フォームの送信」の設定のままでは、ログインの段の Guard が、ページの移動でない `POST` と、許可 Origin の外への要求を止めるので、ログインできません（「[ログインの段](authenticated-audit.md#ログインの段)」。ログインの画面がその失敗をどう表示するかは、画面の作りによります）。

ログインの送り方の設定が画面と合わずにログインできないときは、左のメニューの「実行履歴」からそのジョブの画面を開き、「監査を止める」で止めます。止めても、パネル「ログインの段で止めた送信」の表と数は残るので、時間切れ（10 分）を待つ必要はありません。設定を直せないときは、ログインが要る段を「未検証」と記録します。

### スクリプトで送るログインの設定の値

開発者ツールで見た形（「[スクリプトで送るログインの観察の手順](script-login-observation.md)」の O1〜O4）を、次の欄に写します。値を写すのは、BeakSight の設定（Git の管理の外の管理データ）だけです。記録やほかの文書には、形だけを書きます。欄の決まりは「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」にあります。手順 5 の「登録する」と「案を認証の設定に入れる」でも、同じ欄に案を入れられます。

| 見たもの | 写す欄 |
| --- | --- |
| token の `POST` の「リクエスト URL」の Origin（O1）と、管理画面が読む API の Origin（O4） | プロファイルの「承認したサービスの Origin（1 行に 1 つ）」。監査の対象の Origin は書きません。 |
| token の `POST` の「リクエスト URL」の Origin とパス（O1） | 認証の設定の「token の送信先の Origin」（承認したサービスの Origin から選ぶ）と「token の送信先のパス」。 |
| token の `POST` の query の名前と値（O1。例: 名前 `grant_type`、値 `password`） | 「必須の query」（「query の組を足す」）。要求の query と組がちょうど同じときだけ通すので、見えた組をすべて写します。秘密に見える名前の query は書けません。 |
| ログインの後のローカル ストレージの鍵の名前の形と、そのホスト（O3） | 「成功のローカル ストレージの鍵」の「鍵の Origin」（テスト環境の Origin）、「鍵の名前の接頭辞」、「鍵の名前の接尾辞」（例: `-auth-token`）。値は写しません。どちらか一方が空でもかまいません。 |
| token のほかにログインの前後に出る `POST`（O1・O4） | 「ログインに伴う送信」は、まず空で試します。止めた記録を見て、要るものだけを登録します（手順 5）。登録するかは、その送信が読み取りか、ログインに要る処理かを、利用者が判断します（BeakSight は、その送信の query と本文を照らしません）。 |
| 管理画面の 1 画面を開いたときに出る、API への要求（O4。1 画面で数十の要求、テナントの手続きの呼び出しなど） | 監査の段の欄（「[スクリプトで送るログインの後の監査](authenticated-audit.md#スクリプトで送るログインの後の監査)」）。読み取りの手続きの呼び出し（`POST`）は「監査で通す読み取りの手続きの呼び出し」に、まず空で試し、監査の成果物の `page.json` の安全の記録（止めた要求）を見て、データを読むだけの呼び出しだけを登録します（読むだけかどうかは、利用者が判断します）。「サービスの Origin への要求の上限」は、空のまま（1 分あたり 600 件、1 回の Run の全体（再開をまたぐ）で 10,000 件か、ページの上限 × 200 件の大きいほう。1 分あたりの上限に届いても止めず、次の画面の読み込みの前に待ってから続けます。「[承認したサービスの Origin への要求の上限](site-load.md#承認したサービスの-origin-への要求の上限)」）か、より小さい値にします。 |

- **保存済みの設定を変えずに使う場合**: 認証の設定は版 3 の形だけを読みます（前の版の形（版 2）の設定は、管理データの誤り `DATABASE_INTEGRITY_FAILED` で止まります。利用者のデータには残っていません）。「スクリプトの送信」に変えて保存すると、認証の設定の digest が変わるので、書き込みのシナリオは承認のし直しが要ります。
- **全セッションを無効にするログアウトに注意**: テスト環境のログアウトが、そのアカウントのすべてのセッションを無効にする作りのことがあります（観察の O8）。確かめの間は、普段のブラウザで、同じアカウントからログアウトしません。BeakSight のログインの状態も無効になります（そのときにジョブの途中でどう見えるかは、確かめていません）。

## 2. 画面を起動する

- **すること**: 利用者が起動します。

  ```powershell
  npm run ui
  ```

  コンソールに出た URL をブラウザで開きます。「環境の状態」の画面で、管理データの整合性の確かめと、資格情報の暗号化（自動ログインを使うとき）を確かめます。
- **送るもの**: サイトへは何も送りません。画面が 2 秒ごとに読み直すのは、画面のサーバの管理データだけです。
- **止まるところ**: 同じ管理データで画面のサーバがすでに動いている、port が使用中、のときは、理由と取るべき手順を出して止まります（「[画面の起動](local-ui.md#画面の起動)」）。
- **終わり方**: 管理画面のブラウザ（すべてのタブ）を閉じると、15 秒の猶予の後に、画面のサーバも止まります（コンソールに「管理画面が閉じられたので、画面のサーバを止めました。」が出ます）。読み込み直しでは止まりません。監査のジョブが動いている間は止まらず、ジョブが終わった後に止まります。コードを変えた後は、古いサーバが止まったことをコンソールで確かめてから、`npm run ui` で起動し直します。
- **結果の見方**: 起動の時刻と、Git のコミット（`git log -1`）を記録します。

## 3. URL からプロファイルを作る

- **すること**: 左のメニューの「新しいプロファイル」で、「対象のサイトの設定」の「開始の URL から新しく作る」を選び、「開始の URL」（ログインの後の管理画面の URL）を入れます。名前・許可 Origin・テスト環境の Origin の案が埋まります（「[管理画面でのプロファイルの作り方](profiles.md#管理画面でのプロファイルの作り方)」）。案は、変えたい欄だけ直します。保存すると `local/targets/<名前>.json` を作ります。
  - このファイルの負荷は、最初からページの上限 3、読み込みの間隔 10 秒です（画面の「保存すると作る設定のファイル」にも出ます）。直さずに次の手順へ進めます。
  - 2 つ目からのプロファイルは、「すでにある設定のファイルを使う」で同じファイルを選びます。
  - 画面の選択肢には日本語の名前だけが出ます（括弧の中はコードの値です）。
- **作るプロファイル**（読み取りの段）:

  | 用途 | 環境 | 監査モード | 認証の方式 |
  | --- | --- | --- | --- |
  | 手動のログイン | テスト環境（`TEST`） | テスト環境の監査（ログインあり・読むだけ）（`TEST_AUTH_PASSIVE`） | 手でログインする（`MANUAL_SESSION`） |
  | 自動ログイン（Windows） | テスト環境（`TEST`） | テスト環境の監査（ログインあり・読むだけ）（`TEST_AUTH_PASSIVE`） | 自動でログインする（`AUTOMATED_LOGIN`） |

  - 書き込みのプロファイル（`TEST_APPROVED_WRITE`）は、判断の点の後に、手順 10 で作ります。このモードでは監査（読み取りの監査）を始められません。
  - 「テスト環境の Origin」は、設定のファイルの `site.allowedOrigins` に含まれるテスト環境の Origin です。
  - ログインがスクリプトで送る形のときは、「承認したサービスの Origin（1 行に 1 つ）」に、外部の認証のサービスと API の Origin を書きます。この欄は案が埋まりません。
  - 「テスト環境であることを確かめた記録の参照」は、手順 1 の隔離の証跡の参照です。
- **送るもの**: サイトへは何も送りません。案は、画面の中で URL の文字から作ります。
- **止まるところ**（設定のファイルもプロファイルも作りません）:
  - 同じ名前のファイルがある（`TARGET_CONFIG_EXISTS`）。
  - 名前が Windows の予約名（`TARGET_CONFIG_NAME_RESERVED`。名前を入れた時点で理由が出ます）。
  - 置き場所（`local`・`local/targets`）がリンクか、フォルダでない（`TARGET_CONFIG_LOCATION_UNSAFE`）。
- **結果の見方**: プロファイルの詳細の「次にすること」と「次の手順」のリンクで、残りの手順をたどれます。記録の表の「操作の数」は、この画面を開いた時から数えます（下の「[記録の取り方](#記録の取り方)」）。

## 4. 入口の確かめ

- **すること**: それぞれのプロファイルの詳細で、「入口を確かめる」を押します。終わったら「認証の設定の画面で案を確かめる」から認証の設定を開き、案を確かめて保存します。読まないパスに、ログアウトの画面を必ず入れます。読む範囲のパスで、管理画面の範囲に絞ります。
- **送るもの**: ログインしないで、開始の URL を 1 回だけ読みます（`GET`）。読み取りでない要求は 0 です。欄の値は読まず、入力・押下・送信はしません。ページ自身の読み込み直しや移動は、frame ごとに 2 回までです（「[ページ自身の読み込み直しの上限](site-load.md#ページ自身の読み込み直しの上限)」）。
- **止まるところ**: 終わり方は「読んだ」「許可 Origin の外へ移ろうとした」「読めなかった」です。開始の URL が別の Origin のログインのサービスへ移る作りなら、「許可 Origin の外へ移ろうとした」になります（その場合は、ログインの方式を確かめ直します）。
- **結果の見方**: ジョブの詳細の「入口の確かめの結果」（移った先、ログインの画面に見えるか、欄の候補、form、認証の設定の案）と、成果物 `entry-check.json`（「[入口の確かめの成果物](output.md#入口の確かめの成果物)」）。「読めなかった」とその理由を、記録の表の「判定できない」に数えます。

## 5. 手動のログインと、設定の自動の登録

- **すること**:
  1. 手動のログインのプロファイルの行の「監査を始める」を押し、開始の画面で、ページの上限が 3、ページの読み込みの間隔が 10 秒であることを確かめてから、「新しく始める」を選んで「監査を始める」を押します。
  2. BeakSight が開いたブラウザで、利用者がログインします。ログインのほかの操作（別のタブ、アドレスバー、開発者ツール）はしません。手動のログインの間は、ページの送信を止めません（認証の設定が「フォームの送信」のままでも、ログインは止まりません）。
  3. ログインが済んだら、ジョブの画面の欄「手動のログイン」の「ログインを終えた」を押します（受け付けるのは「ログイン待ち」の間の 1 回だけです。受け付けられないときは、欄に理由が出ます）。成功の条件に当たれば、押さなくても先へ進みます。そのまま手順 7 の監査になります。
  4. ログインが成功し、その間に送信を通したジョブは、ジョブが終わった後に、BeakSight が Guard を通るための設定（認証の設定の「スクリプトの送信」の token の送信先・ログインに伴う送信・成功のローカル ストレージの鍵と、プロファイルの承認したサービスの Origin）を自動で保存します。登録するログインに伴う送信は、token の送信より前に通した、token の送信先と同じ Origin の、書き込みの語を含まない、符号化していない手続きの呼び出し（`/rpc/`）だけです。承認したサービスの Origin に足すのは、token の送信先の Origin だけです。token の送信先が 2 つ以上あって 1 つに決まらないときは、登録しません（通した表の token の行から「登録する」で、正しい送信先を選びます）。ジョブの画面の欄「手動のログインから登録した設定」に、登録したこと（保存したプロファイルの改訂と、足した Origin）か、登録しなかった理由と次にすることが出ます（終わったジョブの画面は、結果が出るまで短い間だけ読み直します）。ジョブの画面とプロファイルの画面の同じ欄で中身を見直し、違っていれば「認証の設定の画面で見直す」から直します。保存でプロファイルの改訂が進むので、承認済みのシナリオや、発見・READ の確かめの結果は、やり直しが要ることがあります（手順 6 の自動ログイン、手順 8 からの発見と書き込みは、この保存の後に行います）。
- **送るもの**: 手動のログインの間は、ページが出す読み取りでない送信（ログインの送信、外部の認証のサービスへの token の送信、ページの手続きの呼び出し、事前確認など）を止めずに通し、サイトに届きます（普通のブラウザで人が操作するのと同じ）。BeakSight は、通した送信の形（Origin・パス・method・種類・query の名前と数）だけを記録し、値は記録しません。読み取り（GET と HEAD）の決まりは変わらず、**許可 Origin の外への読み取りは止めます**（人が入れた値を、ページのスクリプトが別の Origin への読み取りに載せて運ぶことを防ぐため）。ダウンロード、外部のアプリの起動、WebSocket、許可 Origin の外への画面の移動も、今までどおり止めます。
- **止まるところ**: ログインの時間切れ（10 分）。ログインの後に、許可した Origin の Cookie も localStorage もないとき（「扱えないログインの形」）。
- **結果の見方**: パネル「ログインの段で止めた送信」の、止めた送信の表と、手動のログインの間に通した送信の表（Origin・パス・種類・回数・query の名前。通した行からも「登録する」を使えます）。欄「手動のログインから登録した設定」（このジョブからの登録の結果と、保存してある中身）。

## 6. 自動ログイン

- **すること**:
  1. 手順 5 で決めた認証の設定と同じ値を、自動ログインのプロファイルの認証の設定に作ります（「[スクリプトで送るログインの自動ログイン](automated-login.md#スクリプトで送るログインの自動ログイン)」）。
  2. 「資格情報を開く」で、テスト用のアカウントを登録します。
  3. 「ログインを確かめる」で、ログインだけを 1 回試します。
- **送るもの**: ログインの送信を 1 回だけ通します（フォームの送信は 1 回の `POST`。スクリプトで送る形は token の送信 1 回と、登録したログインに伴う送信）。入れた資格情報を含む、ほかの要求は止めます（「[資格情報の持ち出しの守り](automated-login.md#資格情報の持ち出しの守り)」）。
- **止まるところ**: 成功でない結果（資格情報の誤り、回数の制限、アカウントのロック、結果が分からない）では、人が確かめて解くまで、そのプロファイルの自動ログインを止めます。結果が「結果が分からない」で、パネル「ログインの段で止めた送信」の「資格情報を含む要求を止めた数」が 1 以上のときは、ログインの画面が入力の値を token の送信のほかの要求に載せた可能性があります。止めた自動ログインを解く前に、テスト環境でアカウントの状態を確かめます（「[結果ごとにすること](automated-login.md#6-結果ごとにすること)」）。
- **結果の見方**: ジョブの画面の「自動ログイン」（結果、ログインを送信したか、止めた理由）。成功したら、5 分あけてから手順 7 に進みます。

## 7. 読み取りの監査

- **すること**: プロファイルの行の「監査を始める」を押し、開始の画面でページの上限が 3、間隔が 10 秒であることを確かめてから、「新しく始める」を選んで「監査を始める」を押します。手動のログインなら、開いたブラウザでログインします（自動ログインなら、ブラウザは開きません）。
- **送信の扱いの切り替え（選ぶとき）**: ページが出す送信のうち削除のほかを通して監査するときは、始める前に、プロファイルの画面の「表示の設定」で「ページが出す送信のうち、削除のほかを通す」を選び、確認のダイアログで「通す」を押して保存します（既定は読み取りだけ。「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」）。通した数は、ジョブの画面と HTML レポートと `run.json` の `safety.auditSend` に出ます。
- **送るもの**:
  - 読み込み: 1 ページにつき、デスクトップとモバイルの 2 回と、幅の走査の幅ごとに 1 回（既定 3 幅）です（「[1つのページの読み込みの回数](site-load.md#1つのページの読み込みの回数)」）。認証つきの監査では、クリックによる操作の確かめ（Interaction）を行いません。ページ自身の読み込み直しは frame ごとに 2 回までです。
  - 読み取りでない要求: ログインの送信のほかは、スクリプトで送るログインの設定で、利用者が登録した読み取りの手続きの呼び出し（`POST`。1 回の読み込みでの回数の中）だけです。承認したサービスの Origin への要求は、1 分あたりと Run の全体の上限の中です（「[スクリプトで送るログインの後の監査](authenticated-audit.md#スクリプトで送るログインの後の監査)」）。送信の扱いを「削除のほかを通す」にしたときは、ページが自分で出す送信のうち、削除と危険な語のほかを、送り先の Origin を問わず、1 回の読み込みで 60 件まで通します（token の更新も通し、入れ替わった状態を次の読み込みに引き継ぎます）。
- **止まるところ**: セッションの切れ（`STOPPED_BY_AUTH_SESSION_LOST`。成功の鍵の消失は場所の印 `session-key`）、承認したサービスの Origin への要求の上限（`STOPPED_BY_SERVICE_REQUEST_LIMIT`）、サイトの不調（`STOPPED_BY_SITE_UNAVAILABLE`）、安全の不変条件の違反。
- **結果の見方**: ジョブの画面（Run の状態、終わり方）、HTML レポート（サイトへの負荷、安全）、`run.json`（`load`、`safety`、`authentication`、`incompleteReasons`）、ページごとの `page.json`（状態、`documentRequests`）。一部未完了・失敗のページと理由を、記録の表の「判定できない」に数えます。

## 8. 操作の候補の発見（probe）

- **すること**: プロファイルの詳細の「操作の候補と READ の確かめ」から画面「操作の候補」を開き、「操作の候補を探す」を押します。`TEST_AUTH_PASSIVE` のプロファイルで行えます。
- **送るもの**:
  - 読み込み: ログインの段の画面と、読む範囲の画面を 1 画面につき 1 回（ページの上限 3 まで）。
  - 送らずに観察する押下（probe）: 1 画面 3 回まで、1 回のたびに 2 秒待ちます。押す順は、保存・登録など登録・更新の語のボタンが先で、文字のないボタン（アイコンのボタン）は最後です（見えないボタンは、回数を使わずに飛ばします）。押下は凍結の中で行い、サーバへは何も送りません。承認した API の Origin への CORS の事前確認は、Guard が代わりに答えます（「[送らずに観察する押下（probe）](discovery-and-read-check.md#送らずに観察する押下probe)」）。
  - 読み取りでない要求: ログインの送信のほかは、登録した読み取りの手続きの呼び出しだけです。
- **止まるところ**: 承認したサービスの Origin への要求の上限（残りの画面を読まずに `PARTIAL`）、成功の鍵の消失（セッションの切れ、場所の印 `session-key`）。読めなかった画面は、不完全の理由を付けて残ります。
  - **サイトの不調**（応答しない、接続できない、429・502・503・504）: その画面の結果を捨て、60 秒待って同じ画面を 1 回だけ確かめ直します（待つ間は、ジョブの画面に知らせが出ます）。通ったら続け、その後の読み込みの間隔を 2 倍にします。まだ不調なら、ジョブを止めます（終わり方 `SITE_UNAVAILABLE`「サイトが応答しないため止めました」、結果 `PARTIAL`、残りの画面は読みません）。サイトが戻ってから、ジョブを始め直します（「[サイトが応答しないときの発見と READ の確かめのジョブ](site-unavailability.md#発見と-read-の確かめのジョブ)」）。
  - **4xx・5xx の画面**（上の 4 つを除く）: その画面から候補もリンクも拾わず、読まなかった画面（理由 `HTTP_ERROR_STATUS`）にして、次の画面へ進みます。
- **結果の見方**: 画面「操作の候補」（画面ごとの候補、分類、読み切れなかった理由）。候補の「詳しい内容」の「送らずに観察した送り方」に、型の分類（`API_CREATE`・`API_UPDATE`・`NOT_EXECUTABLE` とその理由など。「[型の分類](discovery-and-read-check.md#型の分類)」）が出ます。成果物は `discovery.json` です。

## 9. READ の確かめ

- **すること**: 「READ の確かめを開く」で、定義を作ります。「候補を読む」（読み取りの候補に、テスト用の値だけを送る）か、「画面を読む」（画面の path を読む）を選び、「READ を確かめる」を押します（「[画面を読む READ](discovery-and-read-check.md#画面を読む-read)」）。`{id}` の型の画面の定義は、READ の確かめとしては単独で読みません（手順 10 の照合に使います）。
- **送るもの**: ログインの段の画面と、対象の画面を 1 回、定義ごとに READ の URL を 1 回（1 回のジョブで 20 定義まで）。読み取りでない要求は、手順 8 と同じです。
- **止まるところ**: 手順 8 と同じです（サイトの不調では、その定義の結果を捨て、60 秒待って 1 回だけ確かめ直し、まだ不調ならジョブを止めて、その定義と残りの定義を確かめません）。読む前の確かめ（読まないパス、危険な語など）で止めた定義は、読みません（`READ_BLOCKED_BY_POLICY`）。4xx・5xx の画面の定義は、今どおり `UNDETERMINED`（詳しい理由 `HTTP_ERROR_STATUS`）です。
  - 限界: 最初の定義の画面で止まったジョブは、画面「READ の確かめ」の結果の一覧には並びません。ジョブの画面に、知らせと `PARTIAL` が出ます。
- **結果の見方**: 画面「READ の確かめ」の定義ごとの結果（`MATCHED`・`NOT_MATCHED`・`UNDETERMINED` など）と詳しい理由。成果物は `read-evidence.json` です。`UNDETERMINED` の数と理由を、記録の表に書きます（「[描けなかった画面](discovery-and-read-check.md#描けなかった画面)」）。

## 読み取りの段で確かめられること・確かめられないこと

### 確かめられること

- **テスト環境の画面がつながる外部のサービス**: 監査の段では、ページ自身が読み込む許可 Origin の外の部品（画像、スクリプト、fetch など）への `GET` は送られます（「[認証つきの監査の監査の段](authenticated-audit.md#監査の段)」）。読み取りでない要求（`POST` など）、許可 Origin の外へのページの移動、ポップアップは、Guard が止めます。次の記録から、テスト環境の画面がつながる外部のサービス（アクセス解析、外部の API、外部の決済や通知のスクリプトなど）を観察できます。
  - `pages/<pageId>/page.json` のネットワークの Evidence（`type` が `network`）の `requests` の `url` と `method`: 送った要求（許可 Origin の外への `GET` を含む）。記録の数には上限があり、超えた分は `omittedRequestCount` に数えます。
  - `pages/<pageId>/page.json` の安全の Evidence（`type` が `safety`）: `blockedRequests`（Guard が止めた読み取りでない要求。`method`、`url`、理由）、`blockedNavigations`（許可 Origin の外へのページの移動。理由 `EXTERNAL_MAIN_FRAME_NAVIGATION`）、`blockedPopups`、`blockedWebSockets`、`blockedInteractionRequests`（理由 `GUARD_BYPASS_EGRESS` など）。
  - `run.json` の `safety`（`blockedActions`、`blockedRequestsByMethod`）と、`run.json` の `load.requests.otherOrigins`（許可 Origin の外へ送った要求の数と 1 分あたりの最大）。
  - 許可 Origin の外への `GET` は、実際にその外部のサービスへ届きます（アクセス解析の数字に入ることがあります）。ログインの段では、許可 Origin の外への要求はすべて止めますが、その記録は URL を持たず、保存もしないので、この観察には使えません（「[ログインの段の通信の制限](automated-login.md#ログインの段の通信の制限)」）。操作の候補の発見の `discovery.json` は、画面ごとの止めた数だけを持ちます。
- **HTTPS の証明書がブラウザに信頼されるか**: ブラウザが信頼しない証明書では、ページの読み込みが、ネットワークの層の失敗（`net::ERR_CERT_` で始まるコード）になります。監査の Run は、これをサイトの不調として扱い、確かめ直してから、再開できる状態で止まります（`PARTIAL`。`run.json` の `incompleteReasons` に `SITE_UNAVAILABLE`、`diagnostics/` に診断の記録。「[サイトが応答しないとき](site-unavailability.md)」）。手動のログインでは、ログインの画面を先に開きます。その画面での証明書の誤りの表れ方と、そのときのジョブの終わり方は、確かめていません。

### 確かめられないこと

- **サーバの裏側の隔離**: データベースが本番と別か、登録や更新のときにメール・SMS・外部の API への通知が出るか。BeakSight は、画面とブラウザの通信からしか観察できないので、これらは「未検証」と区分します。

## 書き込みの前に止めて判断する

手順 9 の後で、必ず止まります。ここまでの記録を見て、利用者が次を判断します。決めるまで、手順 10 を始めません。

- 読み取りの段で観察した外部のつながりを材料にして、サーバの裏側の隔離をどう扱うか（テスト環境の管理者に確かめる、など）。
- 書き込み（API の登録）まで行うか。行う場合は、テスト環境の管理者と、登録されるレコード、通知、片付けの方法を確かめてから始めます。累積の上限を小さくします（例: 1〜2 件）。
- 書き込みの送り手が、テスト環境の証明書を信頼できるか（「[登録の要求の送り方](approved-create.md#登録の要求の送り方)」）。確かめられなければ、送る前に止まります（`BLOCKED`、`PRECHECK_FAILED`）。
- プロファイルの `environmentEvidenceRef` を、隔離を確かめた記録の参照に直すか（BeakSight は参照の中身を読まないので、未確認の参照のままでも、空でなければ書き込みの許可を拒みません）。
- 手順 8 で、登録の画面のボタンの「送らずに観察した送り方」が `API_CREATE` だったか。`API_CREATE` でなければ、API のシナリオは作れません（その理由を記録して、書き込みの段を「未検証」とします）。
- 行わない場合は、書き込みの段を「未検証」と記録します。
- API の更新（手順 11）の前にも、同じように止まって判断します。更新では、次も決めます。
  - 更新してよいレコードか（対象は、手順 10 で BeakSight が登録して照合した最も新しい 1 件です）。
  - 変える欄と保つ欄。メールアドレスと電話番号は、保つのを既定にします。
  - filter の名前が、更新の行を選ぶ列を指しているか（テスト環境の API の定義で確かめる）。
  - 手順 8 の発見で、更新の画面のボタンの型が `API_UPDATE` だったか。`API_UPDATE` でなければ、API の更新のシナリオは作れません（その理由を記録して、更新の段を「未検証」とします）。

## 10. API の登録

API の登録のシナリオを作り、承認し、1 件だけ送って、照合の READ で確かめます。書き込みの機能の全体は「[書き込みのシナリオの承認の手順](scenario-approval.md)」と「[承認された登録の手順](approved-create.md)」にあります（API のシナリオの決まりは、それぞれの「[API のシナリオ](scenario-approval.md#api-のシナリオ)」と「[API の登録](approved-create.md#api-の登録)」の節にあります）。

### 10.1 書き込みのプロファイルを用意する

- **すること**: 「新しいプロファイル」で、監査モード「テスト環境の監査（承認した書き込みあり）」（`TEST_APPROVED_WRITE`）、環境「テスト環境（`TEST`）」のプロファイルを作ります。「すでにある設定のファイルを使う」で、手順 3 のファイルを選びます。「承認したサービスの Origin」と「テスト環境であることを確かめた記録の参照」を入れます（参照が空なら、実行の許可は出ません。`GRANT_ENVIRONMENT_EVIDENCE_MISSING`）。認証の設定（と、自動ログインなら資格情報）を、手順 5・6 と同じ値で作ります。
- **送るもの**: サイトへは何も送りません。

### 10.2 このプロファイルで発見をする

- **すること**: 書き込みのプロファイルで「操作の候補を探す」を押します（手順 8 と同じ）。シナリオは、そのプロファイルの最後の発見の候補からだけ作れます。発見の後にプロファイルを編集すると、API のシナリオは保存できません（`SCENARIO_API_DISCOVERY_PROFILE_STALE`。発見をやり直します）。
- **送るもの・止まるところ**: 手順 8 と同じです。
- **結果の見方**: 登録の画面のボタンの候補の「詳しい内容」で、「送らずに観察した送り方」が `API_CREATE` であることを確かめます。

### 10.3 照合の READ の定義を作る

- **すること**: 「READ の確かめを開く」の「画面を読む定義を作る」で、登録したレコードの詳細の画面の path の型を入れます。path の区切りの 1 つの全体を `{id}` にします（1 つだけ。前に固定の区切りが 1 つ以上要ります。例: `/admin/members/{id}`）。この定義は、手順 10.4 の照合の READ に使います。単独では読みません。
- **送るもの**: サイトへは何も送りません（保存の確かめは、代わりの値で行います）。
- **止まるところ**: 読まないパス、読む範囲の外、ログインの画面、危険な語に当たる path は保存しません（「[画面を読む READ](discovery-and-read-check.md#画面を読む-read)」）。

### 10.4 API のシナリオを作る

- **すること**: 画面「操作の候補」の登録の候補の「API のシナリオを作る（<method> <path の型>）」を押します。次を確かめて「保存する」を押します。
  - 「API の要求の型と、送る鍵」: 「本文の鍵と欄」（欄に値を入れて送る鍵。すべて送ります）、「ページが決める鍵」（欄に対応しない鍵のうち、許すものだけを選ぶ。値は照らさず、実行のときの値を記録に残します）、「ページが付けるヘッダの名前」（承認に結びます）。
  - 「登録の ID を読む応答の鍵（任意）」: 応答の本文の、登録の ID の鍵の名前です。**この形を勧めます。** 応答の本文の最上位の object（か、要素が 1 つだけの array のその object）の鍵の値を、ID として読みます。値は文字列か 0 以上の整数で、英数字・`_`・`-` だけの 1〜64 文字のときだけ使います。応答の本文が空か JSON でなければ、ID は取れません（結果は `PARTIAL`、`RECORD_ID_NOT_FOUND`）。
  - 上限（累積の上限を小さく）、承認の期限、副作用の確認の 4 項目。
  - 「検証の指定」: API のシナリオで要るのは、**登録の ID の取り方**と**照合の READ** の 2 つだけです。成功の条件と入力の誤りの条件は使わず、欄も出ません。登録の ID は、上の応答の鍵か、検証の指定の取り方（保存の後の画面の URL か要素）のどちらかで決めます。画面から取る ID の型が、書き込みの画面（登録の画面）の path にも当たるときは、注意（「…登録の ID は応答の本文の鍵から取る形を勧めます。」）が出ます。保存はできます。
  - 照合の READ: 手順 10.3 の定義を選びます。期待には、**実行のたびに変わる値（生成した値）と比べる期待を 1 つ以上**入れます（「本文が含む」か「詳細の項目の値」で、比べる値に送る欄を選ぶ）。行の数だけの期待では保存できません（`SCENARIO_API_READ_VERIFICATION_NOT_BOUND`）。
- **送るもの**: サイトへは何も送りません（シナリオの作成・変更・承認は、管理データの中だけで行います）。
- **止まるところ**: 型が `API_CREATE` でない（`SCENARIO_API_CANDIDATE_NOT_API`）、論理削除にあたる鍵や method の上書きがある、送る欄と鍵が対応しない、秘密に見える名前のページが決める鍵や ID の鍵、などは保存しません（理由が項目ごとに出ます）。
- **結果の見方**: シナリオの詳細の「API の要求の型（承認が縛る型）」（method、送り先の Origin、path の型、query の名前、本文の鍵と欄、ページが決める鍵、ページが付けるヘッダの名前）。

### 10.5 入力の規則を決める

- **すること**: シナリオの詳細の「入力の規則を開く」から、送る鍵の欄すべての作り方を決め、確認のダイアログの「保存する」で保存します（「[入力の規則とデータの生成](data-rules.md)」）。照合の READ の期待で比べる欄は、実行のたびに値が変わる作り方にします（値が 1 つだけの固定の一覧にしない）。保存すると、シナリオは下書きに戻ります。
- **送るもの**: サイトへは何も送りません。「データの例（送りません）」は画面の中だけです。

### 10.6 承認する

- **すること**: シナリオの詳細の「承認する」を押し、確認のダイアログで、上限・期限・副作用の確認・API の要求の型を読んでから「承認する」を押します（「[承認する](scenario-approval.md#5-承認する)」）。
- **送るもの**: 何も送りません。承認しただけでは、書き込みは始まりません。
- **止まるところ**: 承認の後に、発見で型・Origin・path・鍵・欄・ヘッダの名前が変わるか、プロファイルを改訂すると、再承認が要ります（「[再承認が要る場合](scenario-approval.md#再承認が要る場合)」）。

### 10.7 書き込みを始める

- **すること**:
  1. 判断の点に戻り、続けることを決めてから進みます。
  2. シナリオの詳細の「書き込みを始める画面を開く」を押します。画面「書き込みを始める」で、送り方「API の要求」、API の要求の型、累積の上限、連続の上限（5 分の間隔・24 時間に 5 件）、次に実行できる時刻、承認の状態を確かめます。始められないときは「実行できない理由」が出ます（例: 照合の READ の期待が毎回同じ値の欄とだけ比べている `READ_VERIFICATION_NOT_VARYING`）。
  3. 「書き込みを始める」を押し、確認のダイアログの「書き込みを始める」を押します。このときだけ、実行の許可（5 分の期限、1 回だけ）を出し、件数を 1 件予約して、ジョブを始めます。
  4. 手動のログインなら、開いたブラウザでログインします。
- **送るもの**（成功の 1 回）:
  - ログインの送信（手順 5・6 と同じ）。
  - 画面の確かめ（`GET`）と、書き込みの画面（`GET`）。書き込みの画面では、承認したサービスの Origin への `GET`・`HEAD` を上限の中で通します。登録した読み取りの手続きの呼び出しは、書き込みのジョブでは通しません。
  - 値を入れて押すと、ページのスクリプトが組み立てた登録の要求を Guard が止め、承認した型と生成した値に照らします。一致した 1 回だけを、BeakSight の送り手が送ります（再送しません）。応答はページに返します。**読み取りでない要求は、ログインの送信のほかは、この 1 回だけです。**
  - 照合の READ: 取れた ID を `{id}` に入れた画面の path に、保存の時と同じ確かめをかけ直してから、1 回読みます（`GET`）。ID がなければ読みません。
- **止まるところ**（送らずに止まれば、結果は `BLOCKED`、件数の予約は返します）:
  - 送る前の確かめ（承認と許可が今も有効か、送信の要素と鍵の欄があるか、成功の鍵の消失、要求の上限、書き込みの送り手の証明書）。
  - **入力の途中で自動保存するページ**: 値を入れる間に、ページが読み取りでない要求を出すと、押さずに止まります（意図した止まり方。承認した形の要求でも止めます）。このときは、書き込みのジョブはそのページでは使えません。止めた要求の数は、書き込みの報告の Guard の要約に出ます。
  - 照合で止めた要求（型・値・ヘッダの名前・query が承認と違う）は送りません（`PAYLOAD_MISMATCH`）。
- **結果の見方**: ジョブの画面の「書き込みの結果」（結果、理由、送信、応答の HTTP の状態と判定、登録の ID、照合の READ、予約の締め、ページが決める鍵とその値）、シナリオの詳細の「書き込みの履歴」、「書き込みの報告」（`action-report.html` とバンドル）、プロファイルの詳細の「監査済みデータの台帳を開く」。
  - 結果の判定は、応答の HTTP の状態（2xx は成功、429 は要求が多すぎる、ほかの 4xx は入力の誤り、5xx はサーバの誤り）と、取れた登録の ID で決めます。
  - `VERIFIED`: 2xx で、ID が取れ、照合の READ が一致した。`PARTIAL`: 2xx だが、ID が取れない・使えない形、照合の READ を判定できない。`UNKNOWN`: 送ったが、登録されたか分からない（応答がない、5xx、照合の READ が一致しない、など）。`FAILED`: 送ったが、サイトが登録しなかったと判定できる（ほかの 4xx、429）。
  - `UNKNOWN` のときは、テスト環境で登録があるかを確かめます（「[UNKNOWN の後にすること](approved-create.md#unknown-の後にすること)」）。自動の再試行はしません。
  - 2 件目を送るときは、5 分以上あけます。

## 11. API の更新

手順 10 で BeakSight が登録して照合したレコード 1 件を、API の更新（`PATCH`）で 1 回だけ更新し、更新の画面の読み直しと照合の READ で確かめます。全体の決まりは「[承認された更新の手順の API の更新](approved-update.md#api-の更新)」にあります。始める前に、「[書き込みの前に止めて判断する](#書き込みの前に止めて判断する)」と同じく止まって判断します。

### 11.1 前提

- 同じ書き込みのプロファイルで、手順 10 の API の登録のシナリオの結果が「照合済み」（`VERIFIED`）の登録が 1 件以上あること。なければ、実行の許可は出ません（`TARGET_RECORD_UNAVAILABLE`）。BeakSight が作っていないレコードは更新しません。照合済みの登録がないときは、11.5 の「登録してから更新する」で、登録と更新を続けて行えます。
- 照合の READ が比べる欄の入力の規則は、登録のシナリオでも更新のシナリオでも、実行のたびに値が変わる作り方にしておきます。1 つの固定の値だと、実行の許可が出ません（`READ_VERIFICATION_NOT_VARYING`）。「登録してから更新する」では、どちらかのシナリオが始められなければ何も始めません。
- 対象のレコードの保つ欄の値が、BeakSight の外（テスト環境の画面で人が変えるなど）で変わっていないこと。保つ欄は台帳が知る値と比べるので、外で変わったレコードは更新できません（下の 11.4）。そのときは、手順 10 で新しく登録してから更新します。
- 書き込みのプロファイルの最後の発見で、登録したレコードの更新の画面を読み、更新のボタンの「送らずに観察した送り方」が `API_UPDATE` であること。`API_UPDATE` になるのは、`PATCH` で、filter がちょうど 1 つ（`eq`）で、その値が画面の path の最後の ID と同じ要求だけです（「[型の分類](discovery-and-read-check.md#型の分類)」）。発見はページの上限（3）までしか読まないので、更新の画面が読む範囲の 3 ページに入らなければ、候補は出ません。

### 11.2 更新のシナリオを作る

- **すること**: 画面「操作の候補」の更新の候補の「API のシナリオを作る（PATCH <path の型>）」を押し、次を決めて「保存する」を押します。
  - **欄の役割**: 目印を入れた欄の鍵ごとに、「変える」か「保つ」を選びます。既定は保つです。メールアドレスと電話番号の欄も、既定で保ちます（変える欄にすると、合成の値（`example.invalid`、`090-0XXX-XXXX`）を送り、外部への通知がないことの確認が要ります）。変える欄は 1 つ以上要ります。保つ欄には値を作らず、送る前の画面の値のままにします。
  - **ページが決める鍵**: 更新では、更新の画面の欄として識別できる鍵（選択の欄など）だけを許し、送る前の画面の値と照らします。欄として識別できないページが決める鍵を持つ型は、更新のシナリオにできません（`SCENARIO_API_PAGE_KEY_NOT_IDENTIFIABLE`）。
  - **更新の filter の名前**: 要求の型の filter の名前と同じにします。filter の列の名前は、発見では確かめていません。別の列を指していないかを、テスト環境の API の定義で確かめてから承認します（画面に注意が出ます）。
  - **台帳**: 「台帳（更新するレコードを登録したシナリオ）」に、手順 10 の API の登録のシナリオを選びます。台帳にできるのは、同じ送り先（API の Origin と path の型が同じ。同じ表）の API の登録のシナリオで、下の結び付けに合うものだけです。画面の選択肢も、それだけに絞られます。
  - **更新の画面の path の型**: 候補の画面の path の、レコードの ID の区切り（path の最後の ID）を `{id}` にした型です。
  - **台帳の ID と filter の結び付け**: 台帳のレコードの ID で更新の行を選べることを、保存と実行の許可の発行で確かめます。
    - **確実な形**: 台帳の登録のシナリオで、登録の ID を応答の本文の鍵から取り、その鍵の名前を filter の名前と同じにします（違えば `SCENARIO_API_FILTER_NOT_BOUND_TO_LEDGER_ID`）。
    - 台帳が URL の型から ID を取るときは、台帳の型と更新の画面の型で、`{id}` の位置（区切りの番号）と、`{id}` より前の区切りがすべて同じであることを求めます（後ろの区切りは違ってよい。例: `/admin/members/{id}` と `/admin/members/{id}/edit` は結び付きます）。台帳が画面の要素から ID を取るときは、更新の画面の `{id}` が最後の ID の区切りであることを求めます。合わなければ `SCENARIO_UPDATE_PATH_NOT_BOUND_TO_LEDGER_ID` です。
  - **検証の指定**: API の更新で要るのは、照合の READ だけです（登録の ID は、許可が台帳から選ぶ対象の ID です）。`{id}` の型の画面の READ の定義を選び、期待には、変える欄の生成した値と比べる期待を 1 つ以上入れます（決まりは登録と同じ。「[API の検証の指定](approved-create.md#api-の検証の指定)」）。
  - 上限（累積の上限を小さく）、承認の期限、副作用の確認の 4 項目。
- **送るもの**: サイトへは何も送りません。
- **止まるところ**: 上の理由のほか、論理削除にあたる鍵を持つ型は作れません（`SCENARIO_API_STATE_KEY`）。
- **結果の見方**: シナリオの詳細の「API の要求の型（承認が縛る型）」（変える鍵と欄、「保つ鍵と欄」、ページが決める鍵と欄、filter の名前、台帳）。

### 11.3 入力の規則を決めて、承認する

- **すること**: 「入力の規則を開く」で、変える欄の作り方だけを決めて保存します（保つ欄の値は作りません）。照合の READ の期待で比べる欄は、実行のたびに値が変わる作り方にします。次に「承認する」を押し、確認のダイアログで、変える鍵・保つ鍵・filter の名前・台帳を読んでから承認します。
- **送るもの**: 何も送りません。

### 11.4 書き込みを始める

- **すること**:
  1. 判断の点に戻り、更新まで続けることを決めてから進みます。
  2. シナリオの詳細の「書き込みを始める画面を開く」を押します。画面「書き込みを始める」の「更新の予定のレコード」に、台帳の照合済みの登録のうち、登録の時刻が最も新しい 1 件の ID が出ます（BeakSight が自動で選びます。人は ID を入れません）。
  3. 「書き込みを始める」を押し、確認のダイアログの「書き込みを始める」を押します。画面が見せた予定のレコードと、許可の発行の時に選び直したレコードが違えば、始めません（`TARGET_SELECTION_CHANGED`。画面を読み込み直します）。
  4. 手動のログインなら、開いたブラウザでログインします。
- **送るもの**（成功の 1 回。どの読み込みも、設定の間隔を守ります）:
  1. ログインの送信（手順 5・6 と同じ）。
  2. **前の読み取り**（`GET`）: 凍結した環境で、対象の ID の更新の画面を 1 回読みます。画面の path を型にした識別で承認した候補がちょうど 1 つあり、その path の最後の ID が対象の ID であることを確かめます。変える欄・保つ欄・ページが決める鍵の欄の今の値（前の値）を、落ち着くまで待って読みます（下の「値の落ち着きの待ち」）。値はメモリの中だけで扱います。
  3. **書き込みの画面**（`GET`）: 更新の画面を開き直し、欄の値が前の値と同じかを確かめます（違えば送りません）。変える欄にだけ値を入れます。保つ欄には触りません。押す直前（送る直前の確かめ直しの前）に欄を読み直し、保つ欄とページが決める鍵の欄が前の値のまま、変える欄が入れた値のままでなければ押しません。
  4. **更新の要求**（`PATCH` 1 回）: 2 段の窓（観察の段 → 押す直前の確かめ直し → 送信の段）で、Guard が承認した型と照らし、一致した 1 回だけを BeakSight の送り手が送ります。照らすのは、filter の値が `eq.<対象の ID>` と完全に一致すること、変える鍵が生成した値と一致すること、本文にある保つ鍵とページが決める鍵が前の値と一致すること（保つ鍵が本文になければ通します）、承認の外の状態の鍵がないこと、などです。
  5. **後の照合**（`GET`）: 書き込みの段を閉じた後、凍結した環境で更新の画面を 1 回読み直し、変えた欄が新しい値、保つ欄とページが決める鍵の欄が前の値であることを、欄ごとに照らします。
  6. **照合の READ**（`GET`）: 後の照合で一致しない欄がなければ、`{id}` に対象の ID を入れた画面を 1 回読みます。
  - **読み取りでない要求は、ログインの送信のほかは、`PATCH` の 1 回だけです。** 送らずに止めた回のサイトへの読み込みは、前の読み取りと書き込みの画面の 2 回以下です。
- **値の落ち着きの待ち**: SPA の画面が値を後から入れる前に読まないよう、前の読み取り・書き込みの画面・押す直前の読み直し・後の照合のどれでも、次の順に待ってから値を読みます。
  - ページの要求が止んで（読み込み中の要求がなく、500 ミリ秒静か）、欄の値が続けて 2 回同じになるまで待ちます。
  - 要求が止むのを待つのは最大 3 秒（`API_WRITE_VALUE_QUIET_TIMEOUT_MS`）です。開いたままの要求があるページは、3 秒の後に、欄の値を 0.5 秒おきに読み、続けて 2 回同じになったら進みます（最大 10 回。落ち着かなければ送りません）。同じ Run の残りの読み取りでは、この 3 秒の待ちを省きます。テスト用のサイトでは、開いたままの要求がある画面の更新は、1 回に約 14 秒かかりました。
  - 前の読み取りで、目印を入れた欄（変える欄と保つ欄）の値がすべて空なら、値が入る前の画面とみなして送りません（`PRECHECK_FAILED`）。
  - **保つ欄は、台帳が知る値と比べます。** 台帳が知る値は、BeakSight がそのレコードの登録と、照合済みの更新で送った値です。前の読み取りか押す直前の読み直しで、保つ欄の値が台帳が知る値と違えば送りません（`PRECHECK_FAILED`）。後の照合で違えば、照合できない（`PARTIAL`、`UPDATE_POSTCHECK_UNDETERMINED`）です。そのため、次の画面とレコードでは止まります。
    - 値が入る前に仮の値（「読み込み中」など）を出す画面。
    - BeakSight の外（テスト環境の画面で人が変えるなど）で、保つ欄の値が変わったレコード。新しく登録してから更新します。
  - 限界: 台帳が知らない保つ欄（登録で送らなかった欄）は、台帳の値と比べられません。その欄だけをページのタイマーで遅れて入れる画面は、見分けられないことがあります。
- **止まるところ**（送らずに止まれば、結果は `BLOCKED`、件数の予約は返します）:
  - 前の読み取りで、承認した候補がちょうど 1 つない、path の最後の ID が対象の ID でない、欄が読めない、値が落ち着かない、目印を入れた欄の値がすべて空、保つ欄の値が台帳が知る値と違う、変える欄の前の値が長すぎる（8,192 文字を超える）（`PRECHECK_FAILED`）。
  - 書き込みの画面の値が前の値と違う、押す直前の読み直しで値が変わっていた（`PRECHECK_FAILED`）。
  - ページのスクリプトが、保つ欄の値や filter の値を書き換えて送ろうとした（Guard が照合で止めます。`PATCH` はサイトに届きません）。
  - 入力の途中で自動保存するページ、送る直前の確かめ直し、成功の鍵の消失、要求の上限（登録と同じ）。
- **結果の見方**: ジョブの画面の「書き込みの結果」（結果、理由、送信、応答、「更新の対象のレコード」、前後の差分（変えた欄の前の値・新しい値・後の照合、保つ欄の照合）、照合の READ、予約の締め）と、書き込みの報告、台帳。ページが決める鍵の値は、更新では残しません（「更新では値を残しません（送る前の画面の値と同じであることを照らしました）」）。

  | 場面 | 結果 | 理由 |
  | --- | --- | --- |
  | 2xx で、後の照合で変えた欄が新しい値・保つ欄が前の値、照合の READ が一致（本文が変える鍵だけの場合、応答が 204 の場合を含む） | `VERIFIED` | `READ_VERIFICATION_MATCHED` |
  | 後の照合で一致しない欄がある（サーバが保つ欄を変えた副作用、204 で何も変わっていない、など） | `UNKNOWN` | `UNEXPECTED_FIELD_CHANGE` |
  | 2xx で、応答の本文が空の一覧 `[]`（更新した行がない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
  | 2xx で、応答の本文が 2 行以上の一覧（どの行が変わったか分からない） | `UNKNOWN` | `MULTIPLE_CONDITIONS_MATCHED` |
  | 2xx で、応答の本文が空でなく、1 MiB を超えるか JSON として読めない（行の数が分からない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
  | 応答の本文の ID の鍵の値が、対象の ID と違う | `UNKNOWN` | `RECORD_ID_MISMATCH` |
  | 後の照合を読めない | `PARTIAL` | `UPDATE_POSTCHECK_UNDETERMINED` |
  | 照合の READ を判定できない／一致しない | `PARTIAL`／`UNKNOWN` | `READ_VERIFICATION_UNDETERMINED`／`READ_VERIFICATION_NOT_MATCHED` |
  | 400（ほかの 4xx）・429 | `FAILED` | `INPUT_ERROR`・`RATE_LIMITED` |
  | 503（5xx） | `UNKNOWN` | `SERVER_ERROR` |
  | 応答がない | `UNKNOWN` | `NO_RESPONSE` |
  | ページが保つ値や filter を書き換えた | `BLOCKED` | 送る中身の照合で止めた（`PATCH` は届かない） |

  - 値の比べ方は完全な一致です（改行だけ同じと見なします）。サーバが値を整形する（前後の空白を除く、大文字にするなど）と、`UNEXPECTED_FIELD_CHANGE` になります（正規化を足すかは Task 44 で判断します）。
  - `UNKNOWN` のときは、テスト環境でレコードの状態を確かめます。自動の再試行はしません。
  - 同じシナリオで続けて更新するときは、5 分以上あけます（24 時間に 5 件まで）。2 回目も、台帳の最も新しい照合済みの登録が対象です（同じレコードを何度でも更新できます）。

### 11.5 登録してから更新する

照合済みの登録がないとき（または最新のレコードで前の更新が止まったとき）に、1 回の操作で、台帳の登録のシナリオの書き込みと、続けて更新のシナリオの書き込みを行います。**明日の手順では、照合済みの登録がなければ、これを使うことを勧めます。** form の更新のシナリオでも同じ作りです。

- **ボタンが出るとき**: 更新のシナリオの画面「書き込みを始める」に、注意「登録してから更新する」と、同じ名前のボタンが出ます。出るのは次のときです。
  - 更新の対象にできる照合済みのレコードがない（「更新できる照合済みのレコードがありません。…」）。
  - 最新のレコードで、前の更新が照合済みにならずに止まった（「最新のレコードでは、前の更新が照合済みにならずに止まりました。…」。台帳の値と違う、など）。
- **ボタンが出ないとき**: 更新の予定のレコードがあり、前の更新が止まっていないとき（「書き込みを始める」を使います）。注意が出ても、台帳の登録のシナリオか更新のシナリオのどちらかが今は始められないときは、ボタンの代わりに「台帳の登録のシナリオか、この更新のシナリオが、今は始められません。それぞれの開始の画面で理由を確かめてください。」が出ます（承認、検証の指定、上限、間隔、許可の確かめ。更新のシナリオは、対象のレコードのほかの確かめで見ます）。
- **確認のダイアログ**（「登録してから更新しますか」）: 2 回の書き込みを、それぞれ出します。
  - 「1 回目: 登録（シナリオ <id>）」: 送り先と、累積の残り（上限）。
  - 「2 回目: 更新（シナリオ <id>）」: 送り先と、累積の残り（上限）、更新するレコード「1 回目で登録して照合済みになったレコード」。
  - 「登録してから更新する」を押したときだけ始めます。始めた後は、送る直前の確かめで止まらない限り、送信を取り消せません。
- **何も始めずに拒むとき**: 使う場面でない（`CHAIN_NOT_OFFERED`。更新の予定のレコードがある）、台帳の登録のシナリオが始められない（`CREATE_NOT_STARTABLE`）、更新のシナリオが始められない・画面の版が古い（`UPDATE_NOT_STARTABLE`）。
- **続けて更新を始める条件**: 登録のジョブが終わり、その結果が照合済み（`VERIFIED`）で、登録の ID が記録にあり、更新の予定の対象（台帳の照合済みの登録の最新の 1 件）がその ID と同じときだけ、更新の実行の許可を出し、更新のジョブを始めます。始めないときの理由は次のとおりです（ジョブの画面の「続けて更新する予定」の「更新を始めなかった理由」に出ます）。

  | 理由 | 画面の表示 |
  | --- | --- |
  | `CREATE_NOT_VERIFIED` | 登録が照合済みになりませんでした（結果がない、照合できていない、分からない、止めた、など） |
  | `CREATE_RECORD_ID_MISSING` | 登録の ID が記録にありません |
  | `PLANNED_TARGET_MISMATCH` | 更新の予定の対象が、登録したレコードと違います |
  | `UPDATE_START_REJECTED` | 更新を始められませんでした（更新の許可の発行か、ジョブの開始が拒んだ。理由は更新のシナリオの開始の画面で確かめる） |
  | `CREATE_WAIT_TIMEOUT` | 登録のジョブが待つ時間（60 分）の中で終わりませんでした |

- **予定はメモリの中だけ**: 続けて始める予定と状態は、画面のサーバのメモリの中だけに持ちます（管理データに書きません）。画面のサーバが止まれば、予定は消え、更新は始めません。
- **別々の許可と上限**: 登録と更新は別のシナリオなので、別々の実行の許可・件数の予約・上限を使います（同じシナリオの 5 分の間隔には当たりません）。書き込みの同時実行は 1 つのままなので、更新は登録のジョブが終わってから始めます。
- **送るもの**: 登録（手順 10.7）と更新（11.4）を、この順に 1 回ずつです。ログインは、それぞれのジョブで行います。
  - **手動のログインのプロファイル**: 待ちはありません。登録のジョブと更新のジョブのそれぞれで、開いたブラウザでログインします（2 回）。
  - **自動ログインのプロファイル**: 自動ログインどうしには 5 分の間隔があるので、登録のすぐ後の更新は、開始の前の確かめで止まります（`AUTO_LOGIN_RATE_LIMITED`）。このときだけ、更新は「自動ログインの間隔を待っています（待った後に続けて更新します）」の状態になり、次に始められる時刻（ふつうは約 5 分後）まで待ちます。待った後に、開始の前の確かめと実行の許可の発行をやり直し、更新を 1 回だけ始めます（許可は待った後にだけ出します）。次に始められる時刻が 10 分（`WRITE_CHAIN_LOGIN_WAIT_LIMIT_MS`）より先なら待たず、更新は始めません（`UPDATE_START_REJECTED`）。間隔の決まりそのものは変わりません。
  - 待つ間に別のジョブを始めると、やり直しの確かめで止まり、更新は始まりません（`UPDATE_START_REJECTED`。やり直しは 1 回だけです）。待つ間に画面のサーバを止めると、予定が消え、更新は始まりません。
- **結果の見方**: 登録のジョブの画面の「続けて更新する予定」（状態: 「登録中（終わったら続けて更新します）」「自動ログインの間隔を待っています（待った後に続けて更新します）」「続けて更新を始めました」「更新は始めませんでした」、理由、「更新のジョブを開く」）。待つ間は「更新を始め直す時刻」が出て、画面は 2 秒ごとに読み直し続けます（読み込み直しの操作は要りません）。更新を始めたら、更新のジョブの画面で 11.4 と同じく見ます。

### 11.6 更新の画面について観察すること

テスト環境の更新の画面が、次の作りかどうかは、まだ分かっていません（未確認）。どれも、送らずに止まるかと、かかる時間に効きます。普段のブラウザの開発者ツールと、書き込みの結果の止まった所から観察し、記録の表に書きます。

- 値を遅れて入れるか（画面を開いた直後は欄が空で、後から値が入る）。
- 値が入る前に、仮の値（「読み込み中」など）を出すか。
- 開いたままの要求があるか（開発者ツールの「ネットワーク」で、終わらない要求が残る。リアルタイムの更新など）。

## 記録の取り方

記録は、Git の管理の外（例 `local/` の下）に置きます。本来の監査対象のサイトの名前と URL を、Git に載るファイルに書きません。成果物の中身を記録に写すときは、Origin・path・名前を「テスト環境の Origin」「管理画面の path 1」のように伏せ、件数と状態だけを写します。外へ渡すときは「[成果物を外へ渡す前の確かめ](anonymization.md)」に従います。資格情報、Cookie、トークン、ページが決める鍵の値は、記録に書きません。

セッションの切れ（`AUTH_SESSION_LOST`）で止まったときは、その原因を調べる材料として、セッションの切れの記録（頼んだページ、行き着いた先、読み込みの経路、止めた要求、ログインの状態の名前の違い）を、ジョブの画面と `run.json` の `authentication.sessionLoss`（発見と READ の確かめは成果物の `sessionLoss`）で見ます（「[セッションの切れの記録](authenticated-audit.md#セッションの切れの記録)」）。記録に写すときは、パスを「管理画面の path 1」のように伏せ、名前の違いは数と一般の語の形だけを写します。ログインの後にどの Cookie・ローカル ストレージの鍵・IndexedDB のデータベースを監査に引き継いだか（外したか）は、ジョブの画面の「ログインの段」の欄の「ログインの後のブラウザの状態の名前」で見て、ドメインと Origin を伏せ、件数と結果と一般の語の形だけを写します（「[監査の段](authenticated-audit.md#監査の段)」）。

## サイトが応答しなくなったとき

サイトが応答しなくなったら、まず BeakSight がその時に接続していたかを、次の順に確かめます。確かめた事実を、時刻とともに記録します。

1. **ジョブの状態**: 左のメニューの「実行履歴」で、動いているジョブがあるかを見ます。監査は画面全体で同時に 1 つ、書き込みも同時に 1 つだけです。動いているジョブがあれば、ジョブの画面の「監査を止める」で止めます（30 秒たっても止まらなければ「強制的に止める」。「[止める・強制的に止める](local-ui.md#止める強制的に止める)」）。
2. **Run の状態と終わり方**: 監査の Run なら、ジョブの画面の Run の状態と終わり方、`run.json` の `executions` の最後の `endReason`（`STOPPED_BY_SITE_UNAVAILABLE` なら BeakSight がサイトの不調を検知して止まった）、`incompleteReasons` の `SITE_UNAVAILABLE` と、`diagnostics/` の診断の記録を見ます。監査は、サイトの不調を検知すると、そのページを捨てて待ち（60 秒・2 分・4 分・8 分）、同じページを確かめ直します（1 ページにつき最大 4 回）。待っている間は、サイトへ何も送りません（「[サイトが応答しないとき](site-unavailability.md)」）。発見と READ の確かめは、60 秒待って 1 回だけ確かめ直し、まだ不調ならジョブを止めます（終わり方 `SITE_UNAVAILABLE`）。書き込みは、読み直しをしません。
3. **Run のロック**: 監査の Run のディレクトリの `checkpoint/run.lock` は、実行中は 1 分ごとに更新されます。最後の更新から 5 分より長く経っているか、作ったプロセスが動いていなければ、その Run は動いていません（「[中断と再開](resume.md#中断と再開)」）。
4. **Chromium のプロセス**: タスク マネージャーの「詳細」で、BeakSight のワーカーが動かす Chromium（Playwright に同梱の通常の Chromium）のプロセスが残っていないかを見ます。画面のサーバを止めると、ワーカーと、ワーカーが動かしていた Chromium も止まります（「[画面のサーバが落ちたとき](local-ui.md#画面のサーバが落ちたとき)」）。プロセスの名前とパスの見え方は、この手順のために確かめていません。
5. **時刻の照らし合わせ**: サイトが応答しなくなった時刻と、ジョブの開始・終わりの日時、`run.json` の `load`（1 分あたりの最大）を照らします。書き込みのジョブが動いていたなら、「書き込みの結果」の送信の時刻と結果も照らします。

- 再開は、サイトが戻ってから行います。サイトが戻る前に再開すると、止まるきっかけになったページは失敗として残ります。
- サイトの不調が BeakSight の負荷によるものかは、BeakSight の記録だけでは決められません。テスト環境の管理者のサーバの記録と照らします。

## 「未検証」と区分するもの

次に当たる段は、「未検証」と記録し、確かめた段と分けます。

- 対応しないログイン（別の Origin の IdP へ画面が移るログイン、MFA、CAPTCHA）のため、行えなかった段。
- ブラウザが HTTPS の証明書を信頼せず、行えなかった段。書き込みの送り手が証明書を信頼できず、送らずに止まった書き込み。
- サーバの裏側の隔離（データベース、登録・更新のときのメール・SMS・外部の API への通知）。BeakSight では観察できません。
- 判断の点で行わないと決めた書き込み（登録と更新）。
- 手順 8 で `API_CREATE` の型が観察できず、シナリオを作れなかった書き込み。
- 入力の途中で自動保存するページのため、押さずに止まった書き込み（意図した止まり方。次にできることの表示は Task 44 で扱います）。
- 書き込みの画面が、登録した読み取りの手続きの呼び出しがないと描けないために、送る前の確かめで止まった書き込み（書き込みのジョブは、その呼び出しを通しません）。
- 手順 8 で `API_UPDATE` の型が観察できず、または更新の画面が読む範囲の 3 ページに入らず、更新のシナリオを作れなかった更新。
- 欄として識別できないページが決める鍵を持つ型のため、作れなかった更新のシナリオ（`SCENARIO_API_PAGE_KEY_NOT_IDENTIFIABLE`）。
- 台帳の ID と filter が結び付かず、作れなかった更新のシナリオ。
- 時間や負荷の都合で、途中で止めた段。

API の書き込みの限界（Task 38〜40 の設計書の履歴による。テスト用のサイトでは確かめた範囲の外です）:

- 応答をページに返せなかった印（`RESPONSE_NOT_DELIVERED`）は、取り消しの時刻とブラウザによって付かないことがあります。成功とは偽りません（最後の守りは、毎回変わる値と比べる照合の READ です）。
- ページが決める鍵の値は照らしません（承認で名前と JSON の型を結び、値は書き込みの結果の記録に残します）。
- ヘッダの値は、`Content-Type` と `Prefer` のほかは照らしません。`select` の query の値も照らしません。
- form のない画面（ボタンの候補）の欄は、制約（必須、長さ、形、選択肢）を持たないので、欄の制約に基づく値の確かめは効きません。
- 本文が 64 KiB を超える型は、実行できないものになります。
- 応答の判定のラベル（「成功の条件に当たった」など）は、API の書き込みでは言い方がずれます（報告の判定の説明で補っています）。
- 値が 2 つだけの固定の一覧も「実行のたびに変わる値」とみなします（境目は Task 44 で判断します）。
- 書き込みの送り手が HTTP/2 だけを話すサイトに送れるかは、API の書き込みでは確かめていません（form の書き込みでは送れません）。
- API の更新の filter の値と query の名前は、URL の percent-encode を戻した後で比べます（`eq%2E<ID>` のような書き方も、同じ値として通します）。
- API の更新の filter の列の名前は、BeakSight では確かめられません（人がテスト環境の API の定義で確かめます）。
- API の更新の変えた欄の前の値は、平文で記録されます。登録の後に人がそのレコードを編集していれば、その人の値も記録と画面に出ます（「[承認された更新の証拠と記録](approved-update.md#証拠と記録)」と同じ）。
