# 承認された登録（CREATE）の手順（テスト環境だけ）

テスト環境で、承認したシナリオ（「[書き込みのシナリオの承認](scenario-approval.md)」）と入力の規則（「[入力の規則とデータの生成](data-rules.md)」）に従って、登録（CREATE）を 1 件だけ実際に送り、結果を判定し、登録した内容を READ で読み直して照合する手順です。結果の種類と、結果が分からないときにすること、上限、サイトへの読み込み、守りの範囲、確かめていないことも書きます。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> BeakSight がサイトへ書き込みの要求を送る機能です。テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません（「[実テスト環境の手順](real-test-environment.md)」）。

## 使ってよい場合（前提）

- **テスト環境だけに使います。本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします（「[認証つきの監査の使ってよい場合](authenticated-audit.md#使ってよい場合)」と同じです）。
- 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）、環境が `TEST` のプロファイルだけで使えます（「[監査プロファイル](profiles.md)」）。
- **環境の証跡**: プロファイルの環境の証跡の参照（`environmentEvidenceRef`。テスト環境であることの証跡の参照）が空なら、実行の許可を出しません（`GRANT_ENVIRONMENT_EVIDENCE_MISSING`）。
- **副作用の確認**: シナリオの 4 つの副作用の確認（テスト環境のレコードだけ、`NO_EXTERNAL_NOTIFICATION`（メール・SMS・外部の通知が送られない設定）、決済や外部のサービスに及ばない、削除・無効化・取り消しに当たらない）をすべて確かめて、承認していることが要ります（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）。サーバの側の通知は BeakSight からは確かめられないので、この確認と環境の証跡に頼ります。
- **入力の規則**: 送る欄すべての作り方が決まっていることが要ります（決まっていなければ `NEEDS_RULE_INPUT`）。
- **検証の指定**: 下の 4 項目がすべて決まっていることが要ります（どれかが未指定なら `VERIFICATION_SPEC_MISSING`）。

## 検証の指定

シナリオの内容に持たせる、登録の結果を確かめる指定です。承認の digest の項目なので、変えると再承認が要ります。どれかが未指定でも下書きの保存と承認はできますが、実行の許可は出せません。

| 項目 | 内容 |
| --- | --- |
| 成功の条件（`successCondition`） | 送信の後の画面が登録の成功に当たる条件。`{ pathPrefix, selector }`（path の前方一致と、CSS セレクタ。自動ログインの結果の条件と同じ形）。 |
| 入力の誤りの条件（`inputErrorCondition`） | 送信の後の画面が入力の誤り（サイトが登録しなかった）に当たる条件。同じ形。 |
| 登録の ID の取り方（`recordId`） | 成功の後の URL の path を型（例 `/items/{id}`。`{id}` をちょうど 1 つ、path の 1 つの区切りの全体に）に当てて取る（`URL_PATH_PATTERN`）か、成功の画面の要素（CSS セレクタ）の文字から取る（`ELEMENT`）。 |
| 照合の READ（`readVerification`） | READ の確かめの定義（「[READ の確かめの定義を作る](discovery-and-read-check.md#4-read-の確かめの定義を作る)」）の参照（id と版）、定義の送る値の一部を生成した値（送る欄）に結び付ける指定（1 件以上）、期待（1 件以上）。 |

- **登録の ID の形**: 使えるのは、英数字・`_`・`-` だけの、1〜64 文字の値です（path の 1 つの区切りに入れて安全な閉じた形。後の更新（UPDATE）と同じ決まり）。外れる値は ID として使わず、結果は `PARTIAL`（`RECORD_ID_UNSAFE`）になります。取れなければ `PARTIAL`（`RECORD_ID_NOT_FOUND`）です。
- **照合の READ の期待**: 行の数がちょうど N（`ROW_COUNT_EQUALS`。N は 1 以上）、本文が生成した値を含む（`TEXT_CONTAINS`）、詳細の項目が生成した値と一致（`DETAIL_FIELD_EQUALS`）、の 3 種類です。比べる値は、生成した値を送る欄の名前で指します。行の数が「N 以上」（`ROW_COUNT_AT_LEAST`）は、二重の登録を見分けられないので使えません。
- 例: 検索の READ の `q` を生成した氏名に結び付け、行の数がちょうど 1、本文が生成した氏名を含む、を期待にします。

## 画面の手順

管理画面（「[管理画面（ローカル）](local-ui.md)」）で、次の順に行います。前の段（プロファイル、認証の設定、操作の候補の発見、READ の確かめの定義）は「[通しの使い方](end-to-end-usage.md)」にあります。

1. **シナリオを作る**: 画面「操作の候補」で、登録（CREATE）の候補の「シナリオを作る」を押します。送る欄、照らす READ の定義（任意）、上限、承認の期限、副作用の確認の 4 項目、検証の指定（成功の条件、入力の誤りの条件、登録の ID の取り方、照合の READ）を入れて「保存する」を押します（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）。
2. **入力の規則を決める**: シナリオの詳細の「入力の規則を開く」から、送る欄すべての作り方を決め、確認のダイアログの「保存する」で保存します（「[入力の規則とデータの生成](data-rules.md)」）。保存すると、シナリオは下書きに戻ります。
3. **承認する**: シナリオの詳細の「承認する」を押し、確認のダイアログで上限・期限・副作用の確認・差分を読んでから「承認する」を押します（「[承認する](scenario-approval.md#5-承認する)」）。
4. **書き込みを始める画面を開く**: シナリオの詳細の「書き込みを始める画面を開く」を押します。画面「書き込みを始める」に、シナリオと版、送る欄、送り先、1 回の Run で 1 件、累積の上限（使った件数と残り）、連続の上限（最後の書き込みから 5 分あける・24 時間に 5 件まで。残り）、次に実行できる時刻、外部への通知、テスト環境の証跡、承認の状態が出ます。検証の指定に決めていない項目があれば「実行できない理由」が出ます。
5. **始める**: 内容を確かめて「書き込みを始める」を押します。確認のダイアログ（「書き込みを始めますか」。「テスト環境に、登録を 1 件送ります。」）の「書き込みを始める」を押したときだけ、実行の許可を出し、書き込みのジョブを始めて、ジョブの画面へ移ります。始められないときは、ボタンを出さず「今は書き込みを始められません」と出します。拒まれたときは「書き込みを始められませんでした」と理由と手順を出します。
6. **手動のログインのときは、開いたブラウザでログインします**（認証つきの監査と同じです。「[開いたブラウザでログインする](authenticated-audit.md#5-開いたブラウザでログインする)」）。自動ログインのときは、BeakSight がログインします。
7. **結果を見る**: ジョブの画面の「書き込みの結果」に、結果、理由、送信、止めた理由、応答、登録の ID、照合の READ、予約の締め、日時、送った値が出ます。`UNKNOWN` は目立つお知らせで出ます（下の「[UNKNOWN の後にすること](#unknown-の後にすること)」）。シナリオの詳細の「書き込みの履歴」にも、1 行ずつ残ります。
8. **報告を見る**: ジョブの画面の「書き込みの報告」から、報告（`action-report.html`）を開き、書き込みのバンドル（ZIP）を落とせます。報告を配らないときは、その理由が出ます（「[書き込みの報告](output.md#書き込みの報告)」）。外へ渡す前に「[成果物を外へ渡す前の確かめ](anonymization.md)」を読んでください。
9. **台帳を見る**: プロファイルの詳細の「監査済みデータの台帳を開く」で、登録した ID と照合の状態を確かめます（「[監査済みデータの台帳](local-ui.md#監査済みデータの台帳)」）。

## 実行の流れ

1 回の書き込みのジョブ（`WRITE_CREATE`）は、次の順に進みます。どの段で止まっても、送っていなければ件数の予約を返します（`RELEASED`）。

1. **確かめ**: 承認が今も有効か（「[再承認が要る場合](scenario-approval.md#再承認が要る場合)」）、入力の規則、検証の指定、環境の証跡、上限と連続の上限（下の「上限」）、書き込みの同時実行の枠を確かめます。
2. **実行の許可**: 1 つのジョブに結び付いた、期限つき（5 分）で 1 回だけ使える許可を出し、同じ手続きの中で件数を 1 件予約します（`RESERVED`）。許可を出してから 5 分の間にジョブを始めないと、許可は使えません。
3. **値の生成**: 入力の規則から、送る値を決まった形で作ります（「[入力の規則とデータの生成](data-rules.md)」）。基準日は、実行の許可を出した日（Asia/Tokyo）です。前に送った値（結果が分からなかったものを含む）とは重ならない値を作ります。
4. **ログイン**: 認証の設定のとおりにログインします（手動のログイン、または自動ログイン。ほかの認証つきのジョブと同じです）。
5. **画面の確かめ**: 書き込みの画面を、凍結した別の Context で 1 回読み（GET）、操作の候補を読み直します。承認に縛った候補（識別と規則の 2 つの digest）と同じ候補がちょうど 1 つなければ、送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。
6. **書き込みの画面と入力**: 書き込みの段の Context で書き込みの画面をもう一度読み（GET）、フォームを確かめて（POST、送信先の `action` と `formaction`、enctype、target、送る欄が同じ form にあること）、生成した値を入れます。
7. **送る直前の確かめ直し**: 押す前の読み込みの間隔を待った後、押す直前に、ワーカーが親（画面のサーバ）に確かめを頼み、親が、承認と許可が今も有効かを求め直します（撤回、シナリオやプロファイルの変更、許可の期限切れなど）。外れれば送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。確かめ直しの答えを受けてから押すまでの間には、待ちと読み込みを入れません。
8. **送信**: ブラウザで押します。送る中身は、ブラウザの内部の層で照合します（下の「守りの範囲」）。照合で止めたら送らずに `BLOCKED`（`PAYLOAD_MISMATCH`）です。照合が通った登録の要求は、ブラウザには送らせず、BeakSight の送り手が 1 回だけ送り、応答をブラウザに返します（「[登録の要求の送り方](#登録の要求の送り方)」）。サーバの証明書を確かめられなかった回は送らず、`BLOCKED`（`PRECHECK_FAILED`）です。
9. **判定**: 送信の後の画面で結果を決めます（下の「結果の種類と意味」）。
10. **ID**: 成功のときだけ、検証の指定の取り方で登録の ID を取ります。
11. **照合**: 成功のときだけ、照合の READ（生成した値を結び付けた定義）を、READ の確かめと同じ部品で行います（凍結した Context で候補を確かめ、別の Context で READ の URL を読む）。
12. **記録と報告**: ワーカーが、Run のディレクトリに、書き込みの報告（`approval-summary.json`、`action-evidence.json`、`action-report.html`、書き込みのバンドル `beaksight-action-bundle_YYYYMMDDHHmmss.zip`）と `action-run.json`（スキーマ `schemas/action-run.schema.json`）を書きます（「[書き込みの報告](output.md#書き込みの報告)」）。親（画面のサーバ）は、管理データに書き込みの結果を記録し、件数の予約を締め（送って応答を受けた → `COMMITTED`、送ったか分からない → `UNKNOWN`、送らずに止めた → `RELEASED`）、報告のファイルを確かめます（報告の確かめ。通らなければ画面で配りません）。

## 登録の要求の送り方

- **フォームに値を入れて押すのはブラウザ、送るのは BeakSight の送り手が 1 回だけです。** ブラウザがフォームから組み立てた登録の POST を、ブラウザの内部の層で止めて照合し、照合が通ったら、ブラウザには送らせず、BeakSight の送り手が同じ要求を 1 回だけサイトへ送ります。送り手は BeakSight の中継（出口の中継）だけにつなぎ、送り直しはせず、redirect も追いません。サイトの応答（redirect の応答を含む）をブラウザに返し、ブラウザは、その応答を自分が受けた応答として結果の画面を表示します（redirect の先の画面は、ブラウザが読みます）。
- **理由**: ブラウザ（Chromium）は、サーバが登録の POST を受けた後、応答を返す前に接続が切れると、同じ POST を新しい接続で自動でもう一度送ることがあります（DEF-099。テスト用のサイトで、両方の Chromium と本物のワーカーで再現しました）。送り直しはブラウザの内部の層の下で起きるので、照合も送信の記録も 1 回分しか見られず、テスト環境に登録が 2 件できることがありました。BeakSight が自分で 1 回だけ送れば、応答がないときも送り直さず、結果を `UNKNOWN` として記録できます。
- **ブラウザが送る要求と違う点**: 本文（欄の名前と値。CSRF のトークンを含む）は、ブラウザが組み立てて照合が通ったものを、そのまま送ります（BeakSight は値を作り直しません。ページが作る値の名前の閉じた一覧（CSRF のトークンなど）に当たる欄の値は読みません。ほかの hidden・readonly・見えない欄の値は、照合のために読みますが、記録しません）。ほかは、次の点がブラウザが自分で送る要求と違います。サイトがこうした点で要求を見分けているときは、結果が変わることがあります。
  - `Sec-Fetch-Site`・`Sec-Fetch-Mode`・`Sec-Fetch-Dest`・`Sec-Fetch-User` は、同じ Origin のフォームの送信の決まった値にします（`Origin` が送信先と違えば、`Sec-Fetch-Site` は `cross-site`）。
  - `Accept-Encoding` は gzip・deflate・br だけです。
  - `Connection: close` を付けます（接続を使い回しません）。
  - `Accept-Language` は、ブラウザの Context の locale の値そのままです（ブラウザのような、重みの付いた言語の並びではありません）。
  - ヘッダの並びと、TLS の形（ALPN は http/1.1 だけ）は、ブラウザと違います。
- **サーバの証明書の確かめ**: https のサイトでは、サーバの証明書を、Node の同梱の証明書と OS の証明書の置き場所で確かめます（ブラウザの証明書の設定は使いません）。社内の CA の証明書で動くテスト環境では、その CA を OS に入れておく必要があります。確かめに失敗した回は送らず、結果は `BLOCKED`（`PRECHECK_FAILED`）です。
- **HTTP/2 だけを話すサイトには送れません**（送り手は http/1.1 で話します）。
- **応答の大きさと時間**: 応答が 16 MiB を超える場合は、結果は `UNKNOWN` です（送った後なので、件数は使ったものとして数えます）。時間の上限は 2 つあります。
  - **送り手の上限**: 送り手は、サイトの応答を 30 秒（`WRITE_SUBMISSION_TIMEOUT_MS`）まで待ちます。30 秒で応答が終わらなければ、待つのをやめます（送り直しません）。
  - **結果の判定の締め切り**: 押した後、結果の画面が決まるのを、設定の `crawl.navigationTimeoutMs` まで待ちます。
  - このため、押してから `min(crawl.navigationTimeoutMs, 30 秒)` の間に結果が決まらなければ、結果は `UNKNOWN` です（`crawl.navigationTimeoutMs` が 30 秒より短ければ、その時間で `UNKNOWN` になります）。

## 結果の種類と意味

| 結果 | 意味 | 件数 |
| --- | --- | --- |
| `VERIFIED` | 成功の条件に当たり、登録の ID を取り、照合の READ が一致した。 | 使った |
| `PARTIAL` | 成功の条件に当たったが、照合できない（ID が取れない・使えない形、READ の照合を判定できない）。完了とは扱いません。 | 使った |
| `UNKNOWN` | 送ったが、登録されたか分からない（応答がない、応答が 16 MiB を超える、押してから `min(crawl.navigationTimeoutMs, 30 秒)` の間に結果が決まらない、5xx、どの条件にも当たらない、2 つ以上の条件に当たる、セッションが切れた、307・308 の再 POST を止めた、応答を画面に返せなかった、照合の READ が成功の条件と食い違う）。成功と偽りません。 | 使った |
| `BLOCKED` | 送らずに止めた（画面の確かめ、送る直前の確かめ直し、フォームの確かめ、送る中身の照合、サーバの証明書の確かめ）。 | 返した |
| `FAILED` | 送ったが、サイトが登録しなかったと判定できる（入力の誤りの条件に当たった、429）。 | 使った |

- 5xx は、サーバが 5xx を返す前に登録を済ませていることがあるので、失敗（`FAILED`）と言い切らず `UNKNOWN` にします。
- 「応答を画面に返せなかった」（理由のコード `RESPONSE_NOT_DELIVERED`）は、BeakSight の送り手は登録の応答を受けたが、ブラウザが登録の要求を取り消した（ページのスクリプトが別の画面へ移ったなど）ため、その応答を画面に返せなかった回です。今の画面は登録の応答ではないので、成功の条件と登録の ID を判定せず、`UNKNOWN` にします。
- 理由のコードは `action-run.json` の結果と、管理データの書き込みの結果に残します。

### UNKNOWN の後にすること

- **テスト環境で、登録があるかを確かめてください。** BeakSight は、結果が分からない登録を自動で確かめ直しません。
- 件数は使ったものとして数えます（累積の上限と、24 時間の件数に入ります）。
- シナリオは止めません。次の Run も実行できます（上限と間隔の中で）。
- 送った値は「使った値」として生成の履歴に入れます。BeakSight は同じ値を二度と作りません（一意にする欄の組と電話番号が、前の登録と重ならないようにするため）。
- **自動の再試行はしません。** 同じ値でもう一度送ることもしません。登録の要求は BeakSight の送り手が 1 回だけ送るので、ブラウザが自分で送り直すことも、送り手が送り直すこともありません（「[登録の要求の送り方](#登録の要求の送り方)」）。

## 上限

| 決まり | 値 | 意味 |
| --- | --- | --- |
| 1 回の Run の件数 | 1 件 | 1 回の書き込みのジョブで送る登録は 1 件だけ（`DEFAULT_MAX_CREATES_PER_RUN`。シナリオで小さくはできない）。 |
| 累積の件数 | 20 件（シナリオで小さくできる） | シナリオの累積で書き込める件数（`DEFAULT_MAX_CUMULATIVE_CREATES`）。予約中・送った・送ったか分からないを数えます。 |
| 同時に実行できる書き込み | 1 つ | シナリオとプロファイルをまたいで 1 つ（`WRITE_JOB_CONCURRENCY`）。 |
| 実行の許可の期限 | 5 分 | 許可を出してから、書き込みのジョブを始めるまで（`EXECUTION_GRANT_TTL_MS`）。 |
| 連続の間隔 | 5 分以上 | 同じシナリオの最後の書き込み（送った・送ったか分からない）から（`MIN_WRITE_INTERVAL_MS`。`GRANT_WRITE_INTERVAL_NOT_ELAPSED`）。ちょうど 5 分は受けます。 |
| 24 時間の件数 | 5 件まで | 同じシナリオの、判定の時刻より前の 24 時間の窓の中の書き込みが 5 件なら、許可を出しません（`MAX_WRITES_PER_DAY`。`GRANT_DAILY_WRITE_LIMIT_REACHED`）。ちょうど 24 時間前の書き込みは窓の外です。 |

- 既定値を変えるのは、利用者の判断です（名前つきの定数。`src/control/approval/scenario-contracts.ts`）。
- 2 つの許可の発行が同時に来ても、予約の合計は上限を超えません。

## サイトへの読み込み

- 成功の 1 回の書き込みで、ログインのほかにサイトへ送る読み込みと書き込みは、**5 回**です: 画面の確かめ（GET）、書き込みの画面（GET）、登録の POST（と、結果の画面への redirect の GET）、照合の READ の対象の画面（GET）、READ（GET）。
- 送らずに止めた回は、**2 回以下**です（画面の確かめと、書き込みの画面）。
- どの読み込みも、設定の間隔（`crawl.minNavigationIntervalMs`）を守ります（「[サイトへの負荷](site-load.md)」）。
- **読み込み直しはしません。** 結果が分からないときも、自動でもう一度送ったり読み直したりしません。登録の POST は BeakSight の送り手が 1 回だけ送り、redirect は追いません（「[登録の要求の送り方](#登録の要求の送り方)」）。

## 送る欄に選ばなかった欄

フォームの、見えていて編集できる欄のうち、シナリオの送る欄に選ばなかった欄は、次のとおりに扱います（ブラウザがそのまま送る中身と、照合の期待を合わせるため）。

- **text 系の欄**（text、search、email、url、tel、number、date など、textarea）: 空のまま送ります（照合の期待は空の値）。
- **checkbox・radio**: チェックしないまま（選ばないまま）にします（照合の期待は「送られない」）。同じ名前の hidden と checkbox の組（Rails 型）の checkbox は、hidden の値だけが送られます。
- **select（1 つ・複数）、range、color**: ブラウザがページの決めた既定の値で送るので、**送る欄に選ぶ必要があります**。選ばないシナリオは、下書きの保存で受けません（`SCENARIO_CREATE_DEFAULT_VALUE_FIELD_NOT_SENT`）。書き込みのときも送りません。
- hidden の欄、読み取り専用の欄、見えない欄（見えない checkbox・radio・select を含む）は、ページの値のまま送ります。
  - **名前だけを照らす欄は、ページが作る値の名前の閉じた一覧（CSRF のトークン、`nonce` など）に当たる欄だけ**です。値を読まず、記録しません。`token` の語に当たる名前（`auth_token`・`access_token`・`api_token` など）も、この一覧に当たるので名前だけを照らします（下の「確かめていないこと・使えないこと」の限界）。
  - **それ以外の欄**（`lock_version` など）は、書き込みの画面で値を読み、送る中身がその値と完全に一致するかを照らします（見えない checkbox・radio は、チェックの状態（送るか送らないか）と値を、見えない select は選んだ値を照らします）。読んだ値は記録しません。
  - **それ以外の秘密に見える名前**（`code`・`key`・`ticket` など）の hidden・readonly・見えない欄がある画面は、値を読めず照らせないので、実行しません（シナリオの下書きの確かめで受けません。`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`）。
  - **disabled の欄**は、ブラウザが送らないので、送られないことを照らします。
  - `_method` の欄は、承認した候補の上書きの値と同じかも照らします。

## 守りの範囲

- **書き込みの段の Guard**: 書き込みの段の Context では、承認された要求の形（method `POST`、Origin、path、enctype）に完全に一致する、main frame のナビゲーションの POST を 1 回だけ通します。送信の窓の間は、ほかのすべての要求を止めます。許可 Origin の外へは、段の全体で止めます。Service Worker・iframe・popup・WebSocket・beacon・Worker の fetch は届きません。307・308 の再 POST は止めます（結果は `UNKNOWN`）。2 回目の POST、別の path、別の Origin も届きません。
- **送る中身の照合**: 通す前に、POST の本文を照合します。欄の名前は送る欄・送る欄に選ばなかった見える欄（上の扱い）・承認した候補の hidden と readonly の欄だけ、送る欄の値は生成した値と完全に一致（改行は CR LF にそろえるだけ）、enctype は `application/x-www-form-urlencoded` と `multipart/form-data` だけ（`text/plain` は止める）、file の欄は空、文書の文字コードは UTF-8 だけ、`_method` の値は承認した候補の上書きと一致。外れたら送りません（`BLOCKED`）。**hidden・readonly・見えない欄の値（見えない checkbox・radio・select を含む）は、書き込みの画面で読んだ値と照らします**（読んだ値は記録しません）。disabled の欄は、送られないことを照らします。**ページが作る値の名前の閉じた一覧（CSRF のトークンなど）に当たる欄の値だけは、読まず、照らさず、記録しません**（名前だけを照らします。ページの JS がその値を書き換えても見つけられない限界があります）。それ以外の秘密に見える名前の hidden・readonly・見えない欄がある画面は実行しません（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`。上の「送る欄に選ばなかった欄」）。
- **送る直前の確かめ直し**: 押す直前（押す前の読み込みの間隔の待ちの後）に、親が承認と許可を求め直します。撤回などで外れれば送りません。撤回とシナリオの変更のときは、親（画面のサーバ）が、そのシナリオの動いている書き込みのジョブに止める合図を送ります。ワーカーは、押す前の最後の待ちの後と、確かめ直しの答えを受けた後に、止める合図を見ます。確かめ直しの答えを受けてから押すまでの短い間に撤回したときは、送ります（下の「確かめていないこと・使えないこと」）。
- **フォームの入力**: 入力の操作（値を入れる、選ぶ、チェックする）は、ログインと書き込みの 2 つの部品だけが持ちます（自動の検査で確かめます）。BeakSight は要求の本文を自分で組み立てません（ページのフォームに値を入れ、ブラウザが組み立てた要求を照合してから、BeakSight の送り手が 1 回だけ送ります）。
- **送り手の数え（重ねの守り）**: 送り手は BeakSight の中継だけにつなぎます。http のサイトでは、中継も、承認された登録の POST を 1 回に数え、2 回目を止めます（https では、中継から要求の中身は見えないので、送り手が 1 回だけ送ることと Guard で守ります）。
- **記録**: 資格情報、Cookie、CSRF のトークン、hidden の値は、管理データ・成果物・ログ・ワーカーとの通信に残しません。送った値は合成のテストデータなので、決まった場所（管理データの書き込みの結果、`action-run.json`）に平文で残します（READ の定義の送る値と同じ扱い）。
- **予約の締め**: ジョブの終わりで必ず締めます。画面のサーバを再起動したときは、締めていない予約を `UNKNOWN` で締めます。

## 確かめていないこと・使えないこと

- **ブラウザと完全には同じでない要求**: 登録の要求は BeakSight の送り手が送るので、一部のヘッダ、ヘッダの並び、TLS の形、証明書の確かめ方が、ブラウザが自分で送るときと違います（「[登録の要求の送り方](#登録の要求の送り方)」）。こうした違いでサイトの振る舞いが変わるかは、実際のテスト環境では確かめていません。
- **HTTP/2 だけを話すサイト**: 登録の要求を送れません。
- **読み込みのたびに値が変わる、秘密に見えない名前の hidden がある画面**（時刻や要求の番号など）: 画面の確かめのときに読んだ値と照らすので、登録は止まります（止める側）。ページが作る値の名前の閉じた一覧に当たる欄（`nonce`・CSRF のトークンなど）は名前だけを照らすので、値が変わっても止まりません。
- **値を照らす欄が同じ名前で 2 つ以上ある画面**: 止まります。**見えない checkbox・radio・select** も、値を照らします（checkbox・radio はチェックの状態と値、select は選んだ値）。
- **名前だけを照らす欄**（ページが作る値の名前の閉じた一覧。CSRF のトークンなど）: 値を照らさないので、ページの JS が値を書き換えても見つけられません（「[守りの範囲](#守りの範囲)」の送る中身の照合の限界）。`token` の語に当たる `auth_token`・`access_token`・`api_token` なども、ページが作る値かどうかによらず、この一覧に当たるので名前だけを照らします（同じ限界）。一覧の外の秘密に見える名前の hidden・readonly・見えない欄がある画面は、実行しません（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`）。
- **確かめ直しの後の撤回**: 送る直前の確かめ直しの答えを受けてから、登録の要求がサイトに届くまでの間（押す前のフォームの確かめ、押す、送る中身の照合、送り手の接続。テスト用のサイトで 0.07〜0.28 秒）に撤回やシナリオの変更をしたときは、登録を送ります（止める合図が届いても、押した後です）。結果は、その回の判定のとおりに記録します。
- **サーバの側の通知**: 登録を契機にしたメールや SMS は、自動では確かめません。副作用の確認 `NO_EXTERNAL_NOTIFICATION` と環境の証跡に頼ります。ブラウザから許可 Origin の外への要求は止めます。
- **更新（UPDATE）**: 「[承認された更新の手順](approved-update.md)」にあります。複数の段のシナリオ（登録してから更新する、など）と、READ の結果の値を使う生成は扱いません。
- **実際のテスト環境**: まだ接続して確かめていません。
- CLI からの書き込み。
