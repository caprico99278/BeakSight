# 承認された登録（CREATE）の手順（テスト環境だけ）

テスト環境で、承認したシナリオ（「[書き込みのシナリオの承認](scenario-approval.md)」）と入力の規則（「[入力の規則とデータの生成](data-rules.md)」）に従って、登録（CREATE）を 1 件だけ実際に送り、結果を判定し、登録した内容を READ で読み直して照合する手順です。結果の種類と、結果が分からないときにすること、上限、サイトへの読み込み、守りの範囲、確かめていないことも書きます。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 画面の言葉は、この文書の言葉と違います（シナリオは「書き込みの手順」、承認と実行の許可は「書き込みの OK」、入力の規則は「入れる値の決まり」、照合は「答え合わせ」、監査済みデータの台帳は「作ったデータの一覧」など）。対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」にあります。

> BeakSight がサイトへ書き込みの要求を送る機能です。テスト用の小さなサイトで確かめています。実際のテスト環境では、API の登録 1 件（一覧の画面での答え合わせで `VERIFIED`）を確かめました。フォームの送信の登録は、実際のテスト環境では確かめていません（「[実テスト環境で確かめたこと](real-test-environment.md#実テスト環境で確かめたこと2026-11-02-時点)」）。

## 使ってよい場合（前提）

- **テスト環境だけに使います。本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします（「[認証つきの監査の使ってよい場合](authenticated-audit.md#使ってよい場合)」と同じです）。
- 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）、環境が `TEST` のプロファイルだけで使えます。認証つきの読み取りの監査で使っているプロファイルで、点検の後のプロファイルの詳細の一覧「登録・更新を試せる画面」で画面に初めてチェックを入れると、その保存がこのモードにします（確認のダイアログと隔離の扱いの選択はありません。新しいプロファイルは作りません。「[監査プロファイル](profiles.md#保存の後)」）。
- **環境の証跡**: プロファイルの環境の証跡の参照（`environmentEvidenceRef`。テスト環境であることの証跡の参照）が空なら、実行の許可を出しません（`GRANT_ENVIRONMENT_EVIDENCE_MISSING`）。プロファイルを作ったときに、BeakSight が「確かめていない」の固定の形の参照を入れます。この参照で書き込みは止めず、画面にも注意を出しません（隔離の扱いは BeakSight の責務の外です。分からなければ、画面にチェックを入れないでください）。
- **副作用の確認**: シナリオの 4 つの副作用の確認（テスト環境のレコードだけ、`NO_EXTERNAL_NOTIFICATION`（メール・SMS・外部の通知が送られない設定）、決済や外部のサービスに及ばない、削除・無効化・取り消しに当たらない）をすべて確かめて、承認していることが要ります。確かめるのは、承認のダイアログ（画面では「書き込みの OK を出す」）の 1 回の押下です（「[承認する](scenario-approval.md#5-承認する)」）。サーバの側の通知は BeakSight からは確かめられないので、この確認と環境の証跡に頼ります。
- **入力の規則**: 送る欄すべての作り方が決まっていることが要ります（決まっていなければ `NEEDS_RULE_INPUT`）。ふだんは、シナリオを保存したときに BeakSight が推して付けます。推せない欄があるときだけ、人が決めます（「[入力の規則とデータの生成](data-rules.md)」）。
- **検証の指定**: 下の項目が決まっていることが要ります（決まっていなければ `VERIFICATION_SPEC_MISSING`）。フォームの送信のシナリオでは、BeakSight が操作さがしの結果から決めます。API のシナリオは 2 項目です（下の「[API の検証の指定](#api-の検証の指定)」）。

## 検証の指定

シナリオの内容に持たせる、登録の結果を確かめる指定です。承認の digest の項目なので、変えると再承認が要ります。決まっていない項目があっても下書きの保存と承認はできますが、実行の許可は出せません。フォームの送信のシナリオでは、どの項目も人が入れずに BeakSight が決めます（設計書 `doc/design/2026-10-26-beaksight-plain-ui-design.md` の 8.1）。

| 項目 | 内容 | 決め方（フォームの送信のシナリオ） |
| --- | --- | --- |
| 結果の判定のしかた（`resultJudgement`） | フォームの送信のシナリオでは、いつも構造の判定（`FORM_STRUCTURE`。下の「[結果の判定](#結果の判定)」）。API のシナリオでは使いません（null）。 | 下書きの確かめが付けます。人は入れません。 |
| 登録の ID の取り方（`recordId`） | 送った後の URL の path を、ID の型（例 `/members/{id}` と `/members/{id}/edit`。2 つまで。`URL_PATH_PATTERNS`）に順に当てて取ります。当てた区切りが数字か UUID の形で、押す前の URL の値と違い、URL が押す前から変わったときだけ ID にします。 | 発見の更新（UPDATE）の候補から、送信先の型と画面の型の 2 つを作ります。更新の候補がない、ID が数字・UUID の形でないときは、ID なし（null）のままです（下の「ID が取れないフォームの登録」）。 |
| 照合の READ（`readVerification`） | READ の確かめの定義の参照（id と版）、定義の送る値の一部を生成した値（送る欄）に結び付ける指定（1 件以上）、期待（1 件以上）。照合の専用の印（`verificationOnly`）を持てます。 | 発見の検索・一覧の候補（READ。同じ Origin。登録の送信先と同じ path の候補を先に選ぶ）を、照合の専用の定義にします。実行のたびに値が変わる文字の欄に結び、期待は「本文が作った値を含む」（`TEXT_CONTAINS`）です。 |

- **照合の専用の定義**: 照合の専用の印のある定義は、そのシナリオの照合だけに使い、単独の READ の確かめのジョブでは読みません。答え合わせのために、人が READ の定義を作る必要はありません（「[操作の候補の発見と READ の確かめ](discovery-and-read-check.md)」の READ の確かめは、読み取りの点検の任意の画面です）。
- **決められないとき**: シナリオの詳細（画面「書き込みの手順」）の要点に、理由を 1 行出します（書き込みの後に初めて「判定できない」を出すことはしません）。答え合わせを決められない（検索や一覧の候補がない、送れる文字の欄がない、変わる欄がない）ときは「答え合わせのしかたを決められなかったので、書き込みの結果を確かめられません。このままでは書き込みを始められません。」と出し、実行の許可を出しません。
- **ID が取れないフォームの登録**: 登録の ID の取り方を決められなかったフォームの送信のシナリオでも、答え合わせがあれば実行の許可を出します。結果は、照合が一致しても ID なしの `PARTIAL`（一部だけ確かめた）です。その登録からは、更新（UPDATE）を試せません。作成の時点で、画面に「作ったデータを後で探せないので、この登録で作ったデータの更新は試せません（登録は試せます）。」と出します。
- **登録の ID の形**: 使えるのは、英数字・`_`・`-` だけの、1〜64 文字の値です（path の 1 つの区切りに入れて安全な閉じた形。後の更新（UPDATE）と同じ決まり）。外れる値は ID として使わず、結果は `PARTIAL`（`RECORD_ID_UNSAFE`）になります。API のシナリオで取れなければ `PARTIAL`（`RECORD_ID_NOT_FOUND`）です。
- **照合の READ の期待**: 行の数がちょうど N（`ROW_COUNT_EQUALS`。N は 1 以上）、本文が生成した値を含む（`TEXT_CONTAINS`）、詳細の項目が生成した値と一致（`DETAIL_FIELD_EQUALS`）、の 3 種類です。比べる値は、生成した値を送る欄の名前で指します。行の数が「N 以上」（`ROW_COUNT_AT_LEAST`）は、二重の登録を見分けられないので使えません。
- **前の形の成否の条件**: 前に人が入れていた成功の条件（`successCondition`）と入力の誤りの条件（`inputErrorCondition`）、フォームの ID の要素の取り方（`ELEMENT`）は、もう使いません。前に保存したシナリオの文書は読めますが、読むときに成否の条件を捨てます。承認の digest の版が上がった（v5）ので、前に承認したフォームの送信のシナリオは、承認し直しになります。
- **手で直すとき**: 検証の指定の欄は、シナリオの作成と変更の画面のたたんだ「詳しい内容」の中にあります（ふだんは開きません）。

## 画面の手順

**ふだんの流れ**（設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` の 4.1.1・4.1.2・4.1.4）: 書き込みは別の作業にしません。点検の後のプロファイルの詳細の一覧「登録・更新を試せる画面」で画面にチェックを入れると、その保存が、書き込みのモードへの切り替え、その画面の登録と更新のシナリオの下書き（送る欄、検証の指定、照合の専用の定義、入力の規則）、承認（副作用の確認の 4 項目を確かめたことにする）を 1 回で行います（確認のダイアログはありません）。書き込みは、次の点検（まとめて実行）の最後に、チェックした画面ごとに、ジョブの管理が実行の許可を出して、登録 1 件 →（あれば）更新 1 件を送ります。ログインは点検の 1 回のまま使い、送り直しません。結果は一覧の行の「前の点検の結果」と、書き込みの段のジョブの画面に出ます（「[登録・更新を試せる画面](local-ui.md#登録更新を試せる画面)」「[まとめて実行](stage-chain.md)」）。下の手順の画面（シナリオの下書き・承認・書き込みの開始のダイアログ）は、中身を確かめる・直すときと、単独の書き込みのときだけ使います。どちらの道でも、許可・上限・送る直前の確かめ・照合は同じです。

- **データのないサイト**（4.1.4）: 更新の候補（同じ表のデータの画面）がないときは、登録の ID の取り方と照合を、よくある形から推します。フォームの形は、登録の送信先の型から番号の型（`<送信先の path>/{id}`。根拠の名前を付けます）を推し、送った後の URL から番号を取ります。API の形は、よくある番号の鍵（`id` など、名前つきの短い一覧）を推し、登録の返事の本文から番号を取ります。照合は、発見で見つけた一覧・検索の READ に「作った値を含む」で結びます。API の形で一覧・検索の READ の候補がないときは、一覧の画面（登録の画面の 1 つ上の path で、監査の段のリンクにあるもの。下の「[API の検証の指定](#api-の検証の指定)」）を使います。どちらもないサイト（SPA）では、データのないときに限って、詳細の画面の型（登録の画面の 1 つ上の path に `{id}` を付けたもの。根拠 `READ_PAGE_TEMPLATE_COMMON_SHAPE`）を推します。期待は緩めず、送るものは増えません（読むのは `GET` だけです）。確かめの指定がそろわない画面は送りません（`VERIFICATION_SPEC_MISSING`）。推しが外れて番号が取れなかったときは、`PARTIAL` と「確かめられませんでした」を出し、更新はしません。

単独の書き込みは、管理画面（「[管理画面（ローカル）](local-ui.md)」）で、次の順に行います。前の段（プロファイル、入口の確かめ、点検、書き込みのモードへの切り替え）は「[通しの使い方](end-to-end-usage.md)」にあります。どの画面も、要点（「今の様子」）と主のボタン 1 つと、たたんだ「詳しい内容」1 つの形です。

1. **発見する**: 操作さがしを使うプロファイルで「点検を始める」を押すと、監査 → 発見 → READ の確かめをまとめて行います（「[まとめて実行](stage-chain.md)」）。発見だけをやり直すときは、操作さがしの画面の「もう一度さがす」を押します。
2. **シナリオの下書きを作る**: シナリオが 0 件の一覧（プロファイルの詳細の主のボタン「書き込みの手順へ」）か、操作さがしの画面（プロファイルの詳細の「詳しい内容」の「操作さがしの結果を見る」）の主のボタン「書き込みの手順を作る」を 1 回押します（確認のダイアログはありません。作った数は「書き込みの手順を N 個作りました。」の 1 行で出ます）。書き込みのモードへの切り替えの前の発見の結果から作れます。BeakSight が、発見の登録（CREATE）の候補ごとに、シナリオの下書き（送る欄、検証の指定、照合の専用の定義）を作り、入力の規則を推して付けます。サイトには接続しません。承認・副作用の確認・書き込みは行いません。1 回の Run の上限は 1 件の決まった値で、累積の上限と承認の期限は既定のままです（変えるときは、変更の画面の「詳しい内容」）。
3. **推せなかったことを確かめる**: シナリオの詳細（画面「書き込みの手順」）の要点に、決められなかったことが 1 行ずつ出ます。入力の規則を推せない欄があるときは「入れる値を決められない欄があります。…」と出るので、「詳しい内容」の「入れる値の決まりを開く」で、その欄だけを決めます（「[入力の規則とデータの生成](data-rules.md)」）。推した項目は「詳しい内容」の「推測した項目（確かめてください）」に並びます。
4. **承認する**: シナリオの詳細の主のボタン「書き込みの OK」を押し、確認のダイアログで、何を・どこへ・何件（「◯◯の画面で、作り物のデータを 1 件登録します。送ったら取り消せません。」）、副作用の 4 つの約束を読んでから「書き込みの OK を出す」を押します。この 1 回の押下で、副作用の確認の 4 項目を確かめたことにします（「[承認する](scenario-approval.md#5-承認する)」）。
5. **書き込みを始める画面を開く**: 承認の後、シナリオの詳細の主のボタンが「書き込みを始める」に変わります。押すと画面「書き込みを始める」が開き、何を・どこへ・何件の文が出ます。累積の上限（使った件数と残り）、連続の上限（最後の書き込みから 5 分あける・24 時間に 5 件まで）、外部への通知、テスト環境の証跡などは「詳しい内容」の中です。今は始められないときは、主のボタンを出さず、理由（間隔の中なら「◯時◯分から始められます。」）を出します。
6. **始める**: 内容を確かめて「書き込みを始める」を押します。確認のダイアログ（「書き込みを始めますか」）の「書き込みを始める」を押したときだけ、実行の許可を出し、書き込みのジョブを始めて、ジョブの画面へ移ります。拒まれたときは「書き込みを始められませんでした」と理由と手順を出します。
7. **手動のログインのときは、開いたブラウザでログインします**（認証つきの監査と同じです。「[開いたブラウザでログインする](authenticated-audit.md#5-開いたブラウザでログインする)」）。自動ログインのときは、BeakSight がログインします。
8. **結果を見る**: ジョブの画面（画面では「作業の様子」）の要点に、結果の 1 行が出ます。`VERIFIED` で終わると、シナリオの詳細へ自動で移ります（続けて更新を始めたときは、その更新のジョブの画面へ移ります）。`PARTIAL`、`UNKNOWN`（「送ったかどうか分かりません。テスト用のサイトでデータがあるか確かめてください。」）、`FAILED`、送らずに止めた、安全の違反のときは移りません。結果の理由・送信・応答・登録の ID・照合などは、ジョブの画面の「詳しい内容」にあります（下の「[UNKNOWN の後にすること](#unknown-の後にすること)」）。シナリオの詳細の「詳しい内容」の「書き込みの履歴」にも、1 行ずつ残ります。
9. **報告を見る**: ジョブの画面の主のボタン「結果を見る」から、報告（`action-report.html`）を開けます。書き込みのバンドル（ZIP）は「詳しい内容」の中です。報告を配らないときは、その理由が出ます（「[書き込みの報告](output.md#書き込みの報告)」）。外へ渡す前に「[成果物を外へ渡す前の確かめ](anonymization.md)」を読んでください。
10. **台帳を見る**: プロファイルの詳細の「詳しい内容」の「作ったデータの一覧を開く」で、登録したデータと照合の結果を確かめます（「[監査済みデータの台帳](local-ui.md#監査済みデータの台帳)」）。BeakSight は登録したデータを消しません。片付けは、テスト環境の管理者に頼みます。

## 実行の流れ

1 回の書き込みのジョブ（`WRITE_CREATE`）は、次の順に進みます。どの段で止まっても、送っていなければ件数の予約を返します（`RELEASED`）。

1. **確かめ**: 承認が今も有効か（「[再承認が要る場合](scenario-approval.md#再承認が要る場合)」）、入力の規則、検証の指定、環境の証跡、上限と連続の上限（下の「上限」）、書き込みの同時実行の枠を確かめます。
2. **実行の許可**: 1 つのジョブに結び付いた、期限つき（5 分）で 1 回だけ使える許可を出し、同じ手続きの中で件数を 1 件予約します（`RESERVED`）。許可を出してから 5 分の間にジョブを始めないと、許可は使えません。
3. **値の生成**: 入力の規則から、送る値を決まった形で作ります（「[入力の規則とデータの生成](data-rules.md)」）。基準日は、実行の許可を出した日（Asia/Tokyo）です。前に送った値（結果が分からなかったものを含む）とは重ならない値を作ります。
4. **ログイン**: 認証の設定のとおりにログインします（手動のログイン、または自動ログイン。ほかの認証つきのジョブと同じです）。
5. **画面の確かめ**: 書き込みの画面を、凍結した別の Context で 1 回読み（GET）、操作の候補を読み直します。承認に縛った候補（識別と規則の 2 つの digest）と同じ候補がちょうど 1 つなければ、送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。
   - **送る前の答え合わせ**（フォームの送信のシナリオ）: 生成した値で照合の READ を 1 回読みます。値がもうサイトに見えていれば、照合に使えないので送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`、具体的な理由 `VALUE_ALREADY_PRESENT`。画面では「この値はもうサイトにあるので、書き込みの結果を確かめられません。」）。判定できなければ、送った後の照合もできないので、送らずに止めます（`VERIFICATION_READ_UNAVAILABLE`）。
6. **書き込みの画面と入力**: 書き込みの段の Context で書き込みの画面をもう一度読み（GET）、フォームを確かめて（POST、送信先の `action` と `formaction`、enctype、target、送る欄が同じ form にあること）、生成した値を入れます。
7. **送る直前の確かめ直し**: 押す前の読み込みの間隔を待った後、押す直前に、ワーカーが親（画面のサーバ）に確かめを頼み、親が、承認と許可が今も有効かを求め直します（撤回、シナリオやプロファイルの変更、許可の期限切れなど）。外れれば送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。確かめ直しの答えを受けてから押すまでの間には、待ちと読み込みを入れません。
8. **送信**: ブラウザで押します。送る中身は、ブラウザの内部の層で照合します（下の「守りの範囲」）。照合で止めたら送らずに `BLOCKED`（`PAYLOAD_MISMATCH`）です。照合が通った登録の要求は、ブラウザには送らせず、BeakSight の送り手が 1 回だけ送り、応答をブラウザに返します（「[登録の要求の送り方](#登録の要求の送り方)」）。サーバの証明書を確かめられなかった回は送らず、`BLOCKED`（`PRECHECK_FAILED`）です。
9. **ID**: 送った後の URL を、検証の指定の ID の型に当てて、登録の ID を取ります（取れなければ ID なし）。
10. **照合**: 送信の後の画面の状態が 2xx・3xx なら、成否によらず、照合の READ（生成した値を結び付けた定義）を、READ の確かめと同じ部品で行います（凍結した Context で候補を確かめ、別の Context で READ の URL を読む）。
11. **判定**: 応答の状態、照合の結果、送った後の画面のフォームの形で結果を決めます（下の「[結果の判定](#結果の判定)」）。
12. **記録と報告**: ワーカーが、Run のディレクトリに、書き込みの報告（`approval-summary.json`、`action-evidence.json`、`action-report.html`、書き込みのバンドル `beaksight-action-bundle_YYYYMMDDHHmmss.zip`）と `action-run.json`（スキーマ `schemas/action-run.schema.json`）を書きます（「[書き込みの報告](output.md#書き込みの報告)」）。親（画面のサーバ）は、管理データに書き込みの結果を記録し、件数の予約を締め（送って応答を受けた → `COMMITTED`、送ったか分からない → `UNKNOWN`、送らずに止めた → `RELEASED`）、報告のファイルを確かめます（報告の確かめ。通らなければ画面で配りません）。

## 登録の要求の送り方

- **フォームに値を入れて押すのはブラウザ、送るのは BeakSight の送り手が 1 回だけです。** ブラウザがフォームから組み立てた登録の POST を、ブラウザの内部の層で止めて照合し、照合が通ったら、ブラウザには送らせず、BeakSight の送り手が同じ要求を 1 回だけサイトへ送ります。送り手は BeakSight の中継（出口の中継）だけにつなぎ、送り直しはせず、redirect も追いません。サイトの応答（redirect の応答を含む）をブラウザに返し、ブラウザは、その応答を自分が受けた応答として結果の画面を表示します（redirect の先の画面は、ブラウザが読みます）。
- **理由**: ブラウザ（Chromium）は、サーバが登録の POST を受けた後、応答を返す前に接続が切れると、同じ POST を新しい接続で自動でもう一度送ることがあります（DEF-099。テスト用のサイトで、両方の Chromium と本物のワーカーで再現しました）。送り直しはブラウザの内部の層の下で起きるので、照合も送信の記録も 1 回分しか見られず、テスト環境に登録が 2 件できることがありました。BeakSight が自分で 1 回だけ送れば、応答がないときも送り直さず、結果を `UNKNOWN` として記録できます。
- **ブラウザが送る要求と違う点**: 本文（欄の名前と値。CSRF のトークンを含む）は、ブラウザが組み立てて照合が通ったものを、そのまま送ります（BeakSight は値を作り直しません。ページが作る値の名前の閉じた一覧（CSRF のトークンなど）に当たる欄の値は読みません。ほかの hidden・readonly・見えない欄の値は、照合のために読みますが、記録しません）。ほかは、次の点がブラウザが自分で送る要求と違います。サイトがこうした点で要求を見分けているときは、結果が変わることがあります。
  - `Sec-Fetch-Site`・`Sec-Fetch-Mode`・`Sec-Fetch-Dest`・`Sec-Fetch-User` は、同じ Origin のフォームの送信の決まった値にします（`Origin` が送信先と違えば、`Sec-Fetch-Site` は `cross-site`）。
  - `Accept-Encoding` は gzip・deflate・br だけです。
  - `Connection: close` を付けます（接続を使い回しません）。
  - `Accept-Language` は、ブラウザの Context の locale の値そのままです（ブラウザのような、重みの付いた言語の並びではありません）。
  - ヘッダの並びと、TLS の形（ALPN は http/1.1 だけ）は、ブラウザと違います。
- **サーバの証明書の確かめ**: https のサイトでは、サーバの証明書を、Node の同梱の証明書と OS の証明書の置き場所で確かめます（ブラウザの証明書の設定は使いません）。社内の CA の証明書で動くテスト環境では、その CA を OS に入れておく必要があります。確かめに失敗した回は送らず、結果は `BLOCKED`（`PRECHECK_FAILED`）です。
- **HTTP/2 だけを話すサイトには送れません**（送り手は http/1.1 で話します）。
- **応答の大きさと時間**: 応答が 16 MiB を超える場合は、結果は `UNKNOWN` です（送った後なので、件数は使ったものとして数えます）。時間の上限は 2 つあります。
  - **送り手の上限**: 送り手は、サイトの応答を 30 秒（`WRITE_SUBMISSION_TIMEOUT_MS`）まで待ちます。30 秒で応答が終わらなければ、待つのをやめます（送り直しません）。
  - **結果の判定の締め切り**: 押した後、結果の画面が決まるのを、設定の `crawl.navigationTimeoutMs` まで待ちます。
  - このため、押してから `min(crawl.navigationTimeoutMs, 30 秒)` の間に結果が決まらなければ、結果は `UNKNOWN` です（`crawl.navigationTimeoutMs` が 30 秒より短ければ、その時間で `UNKNOWN` になります）。

## 結果の種類と意味

| 結果 | 意味 | 件数 |
| --- | --- | --- |
| `VERIFIED` | 登録の ID を取り、照合の READ が一致した。 | 使った |
| `PARTIAL` | 成功と判定したが、照合しきれない（ID が取れない・使えない形、READ の照合を判定できない）。画面では「書き込みを送りましたが、入ったかを最後まで確かめられませんでした。」と出ます（一部だけ確かめた）。完了とは扱いません。ID のない登録からは更新できません。 | 使った |
| `UNKNOWN` | 送ったが、登録されたか分からない（応答がない、応答が 16 MiB を超える、押してから `min(crawl.navigationTimeoutMs, 30 秒)` の間に結果が決まらない、5xx、判定できない（フォームで照合が一致せず、送った値を保った同じフォームも出ない、など）、セッションが切れた、307・308 の再 POST を止めた、応答を画面に返せなかった、新しい ID が出たのに照合の READ が一致しない）。成功と偽りません。 | 使った |
| `BLOCKED` | 送らずに止めた（画面の確かめ、送る前の答え合わせ、送る直前の確かめ直し、フォームの確かめ、送る中身の照合、サーバの証明書の確かめ）。 | 返した |
| `FAILED` | 送ったが、サイトが登録しなかったと判定できる（4xx の入力の誤り、429、フォームで照合が一致せず、送った値を保った同じフォームがもう一度出た）。 | 使った |

- 5xx は、サーバが 5xx を返す前に登録を済ませていることがあるので、失敗（`FAILED`）と言い切らず `UNKNOWN` にします。
- 「応答を画面に返せなかった」（理由のコード `RESPONSE_NOT_DELIVERED`）は、BeakSight の送り手は登録の応答を受けたが、ブラウザが登録の要求を取り消した（ページのスクリプトが別の画面へ移ったなど）ため、その応答を画面に返せなかった回です。今の画面は登録の応答ではないので、結果と登録の ID を判定せず、`UNKNOWN` にします。
- 理由のコードは `action-run.json`（版 1.2。版 1.1 の記録も読めます）の結果と、管理データの書き込みの結果に残します。

### 結果の判定

フォームの送信のシナリオの判定は、構造の判定（`FORM_STRUCTURE`）です。人が入れる path の前方一致と CSS セレクタは使いません（利用者が前もって知りえない値が要るため。設計書 8.1 の案 (b2)）。

1. 応答が 4xx なら入力の誤り（`INPUT_ERROR`。429 は `RATE_LIMITED`）で `FAILED` です。5xx・応答なし・時間切れは `UNKNOWN` です。
2. 2xx・3xx なら、成否によらず照合の READ を読み、一致すれば成功です。登録の ID があれば `VERIFIED`、なければ `PARTIAL` です。
3. 照合が一致しないときは、送った値を保った同じ「フォームの形」（送信先・method・欄の名前の集まり・送信ボタンの語で作る鍵。画面の path と hidden の値（CSRF のトークンなど）は含めない）がもう一度出たときだけ、入力の誤り（`FAILED`）です。ほかは判定できない（`UNKNOWN`）です。送った後の URL に新しい ID が出ていれば `UNKNOWN`（`READ_VERIFICATION_NOT_MATCHED`）です（失敗とは言いません）。
4. 照合を判定できないときは、新しい ID があり同じフォームが出ていなければ `PARTIAL`（`READ_VERIFICATION_UNDETERMINED`）、ほかは `UNKNOWN` です。

- 既知の制限: 誤りをフォームのない別の画面で返すサイト、誤りの画面で入れた値を消すサイト、後から索引に入る検索は、判定できない（`UNKNOWN`）になります。

### UNKNOWN の後にすること

- **テスト環境で、登録があるかを確かめてください。** BeakSight は、結果が分からない登録を自動で確かめ直しません。
- 件数は使ったものとして数えます（累積の上限と、24 時間の件数に入ります）。
- シナリオは止めません。次の Run も実行できます（上限と間隔の中で）。
- 送った値は「使った値」として生成の履歴に入れます。BeakSight は同じ値を二度と作りません（一意にする欄の組と電話番号が、前の登録と重ならないようにするため）。
- **自動の再試行はしません。** 同じ値でもう一度送ることもしません。登録の要求は BeakSight の送り手が 1 回だけ送るので、ブラウザが自分で送り直すことも、送り手が送り直すこともありません（「[登録の要求の送り方](#登録の要求の送り方)」）。

## API の登録

ページのスクリプトが API の要求で登録する画面（form のない画面を含む）の、API のシナリオ（送り方「API の要求」。「[API のシナリオ](scenario-approval.md#api-のシナリオ)」）の書き込みです。上の画面の手順、上限、実行の許可、件数の予約、送る直前の確かめ直し、`UNKNOWN` の後にすることは、form のシナリオと同じです。違う点を次に書きます。

### API の検証の指定

API のシナリオの検証の指定で要るのは、次の 2 項目だけです（どれかがなければ `VERIFICATION_SPEC_MISSING`）。成功の条件と入力の誤りの条件は使わず、画面にも欄を出しません。

| 項目 | 内容 |
| --- | --- |
| 登録の ID の取り方 | シナリオの「登録の ID を読む応答の鍵」（応答の本文の鍵）か、検証の指定の登録の ID の取り方（保存の後の画面の URL の型か、要素）のどちらか。 |
| 照合の READ | 画面を読む READ の定義（「[画面を読む READ](discovery-and-read-check.md#画面を読む-read)」）と、期待。画面は、`{id}` の型の詳細の画面か、一覧の画面（下）です。 |

- **登録の ID は、応答の本文の鍵から取る形を勧めます。** 応答の本文（JSON）の最上位の object か、要素が 1 つだけの array のその object から、鍵の値を読みます。値は文字列か 0 以上の整数で、使える形（英数字・`_`・`-` だけの 1〜64 文字）のときだけ ID にします。応答の本文が空・JSON でない・1 MiB を超えるときは、ID は取れません。応答の本文は記録しません。
- **画面から取る ID の型の注意**: 画面から取る登録の ID の型が、書き込みの画面（登録の画面）の path にも当たるときは、保存の画面とシナリオの詳細に、注意（「…登録の ID は応答の本文の鍵から取る形を勧めます。」）を出します。保存はできます。押す前の画面から同じ取り方で取れた値と、URL が変わらないときの値は、ID として使いません。
- **照合の READ の期待の決まり**:
  - 生成した値と比べる期待（「本文が含む」か「詳細の項目の値」で、比べる値に送る欄を選ぶ）を 1 つ以上入れます。行の数だけの期待では、シナリオを保存しません（`SCENARIO_API_READ_VERIFICATION_NOT_BOUND`）。別の登録の画面を読んでも一致しうるためです。
  - 比べる欄は、実行のたびに値が変わる欄にします。毎回同じ値になる欄（値が 1 つだけの固定の一覧など）とだけ比べる期待では、実行の許可を出しません（`READ_VERIFICATION_NOT_VARYING`。画面「書き込みを始める」の「実行できない理由」に出ます）。入力の規則で、その欄を値が 2 つ以上になる作り方にします（「[入力の規則とデータの生成](data-rules.md)」）。
- **答え合わせの画面の選び方**（設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` の 4.1.9 の R1）: BeakSight が下書きで、次の順に選びます。
  1. 発見の READ の候補（一覧・検索）。
  2. 一覧の画面: 登録の画面の path の 1 つ上（例 `/admin/x/new` → `/admin/x`）で、監査の段のリンクにあるもの（まとめて実行の発見の段で読みます。「[まとめて実行](stage-chain.md)」）。`{id}` のない画面の path ですが、API の照合の READ に限って使えます。期待は「本文が作った値を含む」で、比べる欄は、毎回違う作り方の欄（メールアドレス、電話番号、数字の番号、文字）だけです（一覧には前の登録も並ぶので、人の名前や辞書の値では、前の登録で一致してしまうためです）。
  3. 推した詳細の画面（登録の画面の 1 つ上の path に `{id}` を付けたもの。根拠 `READ_PAGE_TEMPLATE_COMMON_SHAPE`）。
- 照合の READ は、`GET` で 1 回読みます。詳細の画面の型なら、取れた ID を `{id}` に入れた画面の path に、保存の時と同じ確かめをかけ直してから読みます（ID がなければ読みません）。一覧の画面なら、ID を入れずに、同じ確かめをかけ直してから読みます（「[画面を読む READ](discovery-and-read-check.md#画面を読む-read)」）。
- 限界（一覧の画面）: 一覧の並びやページ分けで、作ったデータが読んだ一覧の画面に出ないと、照合は一致せず `UNKNOWN`（`READ_VERIFICATION_NOT_MATCHED`）になります（成功と偽らない側です）。

### API の送り方

- 値は、ページの欄（シナリオの「本文の鍵と欄」）に入れ、ページのスクリプトが要求を組み立てます。BeakSight は本文を組み立てません。
- 値を入れる前は、プロファイルの送信の扱いが「削除のほかを通す」（管理画面の既定）なら、ページが自動で出す読み取りでない要求のうち、削除と危険な語のほかで、送り先が許可 Origin か承認したサービスの Origin のものを通します（承認した送信先とその下の path、WebSocket は通しません。「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」の書き込みのジョブの項）。送る前の確かめの画面と照合の READ の画面も同じです。
- 値を入れた後は、観察の段です。この間にページが出す読み取りでない要求と、入れた値（目印）を含む要求は、承認した形の要求も含めてすべて止めて数えます。1 つでもあれば、押さずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。読み取り（`GET`・`HEAD`）と WebSocket の張り直しで、目印を含まないものは、止めたまま数えず、押すのを止めません（設計書の 4.1.7 の N1）。
  - **入力の途中で自動保存するページでは、書き込みのジョブは押さずに止まります。** 意図した止まり方です。そのページでは、API の書き込みのジョブは使えません。
- 押す直前に、送信の段を開きます。送信の段の中で、承認した API の Origin と path への `POST` を Guard が止め、承認した型（method、Origin、path、query の名前、ページが付けるヘッダの名前、`Content-Type`、`Prefer`、本文の鍵と JSON の型）と生成した値に照らします。一致した 1 回だけを、BeakSight の送り手が送ります（再送しません）。応答はページに返します。合わない要求は送りません（`BLOCKED`、`PAYLOAD_MISMATCH`）。
- ページが決める鍵の値は照らさず、書き込みの結果の記録に残します。ヘッダの値は、`Content-Type` と `Prefer` のほかは照らしません。

### API の結果の判定

結果は、送り手が受けた応答の HTTP の状態と、取れた登録の ID で決めます（成功の条件と入力の誤りの条件は使いません）。

| 応答と ID | 応答の判定 | 結果 |
| --- | --- | --- |
| 2xx で、ID が取れ、照合の READ が一致した | `SUCCESS` | `VERIFIED` |
| 2xx で、ID が取れない（`RECORD_ID_NOT_FOUND`）か使えない形（`RECORD_ID_UNSAFE`） | `SUCCESS` | `PARTIAL` |
| 2xx で、照合の READ を判定できない | `SUCCESS` | `PARTIAL`（`READ_VERIFICATION_UNDETERMINED`） |
| 2xx で、照合の READ が一致しない | `SUCCESS` | `UNKNOWN`（`READ_VERIFICATION_NOT_MATCHED`） |
| 429 | `RATE_LIMITED` | `FAILED` |
| ほかの 4xx | `INPUT_ERROR` | `FAILED` |
| 5xx | `SERVER_ERROR` | `UNKNOWN`（5xx の前に登録を済ませていることがあるため） |
| 1xx・3xx | `NO_CONDITION_MATCHED` | `UNKNOWN` |
| 100〜599 の外の状態、応答がない | — | `UNKNOWN` |

- ジョブの画面の「詳しい内容」の書き込みの結果と、報告には、送り方「API の要求」、API の要求の型の要約、ページが決める鍵とその値を出します。報告には、判定の説明（応答の状態の番号と取れた登録の ID で結果を決めること）を添えます。人が入れる成功の条件と入力の誤りの条件は、今はフォームの送信のシナリオでも使いません（上の「[結果の判定](#結果の判定)」）。
- 画面から ID を取る形で、ブラウザが登録の要求を取り消して応答をページに返せなかった回は、`UNKNOWN`（`RESPONSE_NOT_DELIVERED`）です。この印は、取り消しの時刻とブラウザによって付かないことがあります（成功とは偽りません。最後の守りは、毎回変わる値と比べる照合の READ です）。

### API の書き込みのサイトへの読み込み

- 成功の 1 回の書き込みで、ログインのほかにサイトへ送る読み込みと書き込みは、**4 回**です: 画面の確かめ（`GET`）、書き込みの画面（`GET`）、登録の要求（1 回）、照合の READ の画面（`GET`）。ほかに、ページ自身が読み込む部品の `GET` と、承認したサービスの Origin への `GET`・`HEAD`（上限の中）が届きます。
- BeakSight が書き込みとして送る読み取りでない要求は、ログインの送信のほかは、登録の要求の 1 回だけです。ほかに、送信の扱いが「削除のほかを通す」のときは、ページが自動で出す要求が、上の決まりで届きます。

## 上限

| 決まり | 値 | 意味 |
| --- | --- | --- |
| 1 回の Run の件数 | 1 件 | 1 回の書き込みのジョブで送る登録は 1 件だけ（`DEFAULT_MAX_CREATES_PER_RUN`。シナリオで小さくはできない）。 |
| 累積の件数 | 20 件（シナリオで小さくできる） | シナリオの累積で書き込める件数（`DEFAULT_MAX_CUMULATIVE_CREATES`）。予約中・送った・送ったか分からないを数えます。 |
| 同時に実行できる書き込み | 1 つ | シナリオとプロファイルをまたいで 1 つ（`WRITE_JOB_CONCURRENCY`）。 |
| 実行の許可の期限 | 5 分 | 許可を出してから、書き込みのジョブを始めるまで（`EXECUTION_GRANT_TTL_MS`）。 |
| 連続の間隔 | 5 分以上 | 同じシナリオの最後の書き込み（送った・送ったか分からない）から（`MIN_WRITE_INTERVAL_MS`。`GRANT_WRITE_INTERVAL_NOT_ELAPSED`）。ちょうど 5 分は受けます。 |
| 24 時間の件数 | 5 件まで | 同じシナリオの、判定の時刻より前の 24 時間の窓の中の書き込みが 5 件なら、許可を出しません（`MAX_WRITES_PER_DAY`。`GRANT_DAILY_WRITE_LIMIT_REACHED`）。ちょうど 24 時間前の書き込みは窓の外です。 |

- 既定値を変えるのは、利用者の判断です（名前つきの定数。`src/control/approval/scenario-contracts.ts`）。
- 2 つの許可の発行が同時に来ても、予約の合計は上限を超えません。

## サイトへの読み込み

- 成功の 1 回の書き込み（フォームの送信のシナリオ）で、ログインのほかにサイトへ送る読み込みと書き込みは、**7 回**です: 画面の確かめ（GET）、送る前の答え合わせ（照合の READ の対象の画面と READ の GET の 2 回）、書き込みの画面（GET）、登録の POST（と、結果の画面への redirect の GET）、照合の READ の対象の画面（GET）、READ（GET）。
- **送る前の答え合わせ**（フォームの送信のシナリオの登録だけ）: 登録を送る前に、同じ値で照合の READ を 1 回読みます（GET 1〜2 回。対象の画面を読めずに決まれば 1 回）。値がもうサイトに見えていれば（照合に使えないので）送らずに止め（`BLOCKED`、`PRECHECK_FAILED`、具体的な理由 `VALUE_ALREADY_PRESENT`）、読めなければ（送った後の照合もできないので）送らずに止めます（同じく `VERIFICATION_READ_UNAVAILABLE`）。
- **送った後の照合は、成否によらず読みます**（フォームの送信のシナリオ）: 送信の後の画面の状態が 2xx・3xx なら、成功に見えない画面（同じフォームがもう一度出た、ID が取れないなど）でも、照合の READ（GET 2 回）を読んでから結果を決めます。4xx・5xx・応答がない回は読みません。送信の後の画面は、書き込みの段の画面のまま、落ち着くまで待って 1 回読むだけです（読み込みを足しません）。
- 送らずに止めた回は、**4 回以下**です（画面の確かめ、送る前の答え合わせの 2 回、書き込みの画面）。
- どの読み込みも、設定の間隔（`crawl.minNavigationIntervalMs`）を守ります（「[サイトへの負荷](site-load.md)」）。
- スクリプトで送るログインの設定のプロファイルでは、承認したサービスの Origin への `GET` と `HEAD` を、上限（1 分あたりと、1 回のジョブの全体）の中で通します。監査で通す読み取りの手続きの呼び出しは、書き込みのジョブでは通しません（「[スクリプトで送るログインの後の監査](authenticated-audit.md#スクリプトで送るログインの後の監査)」）。
- その設定のプロファイルでは、画面の確かめの後・書き込みの段を開く前と、押す直前に、成功の鍵が消えていたか、承認したサービスの Origin への要求の上限に届いていたら、送らずに止めます（`BLOCKED`、`PRECHECK_FAILED`）。
- 書き込みの段の Context の、承認したサービスの Origin への要求は、送り方で違います。
  - **フォームの送信のシナリオ**: 書き込みの段の Context は、承認したサービスの Origin へ送りません。
  - **API のシナリオ**: 書き込みの段の Context でも、承認したサービスの Origin への `GET`・`HEAD` を、監査の段と同じ判定と上限（1 分あたりと、1 回のジョブの全体）の中で通します（SPA の画面を描くため）。
  - どちらの送り方でも、登録した読み取りの手続きの呼び出しを、登録した呼び出しとしては通しません。送信の扱いが「削除のほかを通す」のときは、値を入れる前・送る前の確かめ・照合の READ の画面で、ページが自動で出す要求の 1 つとして通ります（上の「[API の送り方](#api-の送り方)」）。
- 限界: 書き込みの段の中で成功の鍵が消えても、押す前には見えません。フォームの送信のシナリオで、書き込みの段の画面が API のデータを要るなら、画面を描けないことがあります。API のシナリオでも、画面が登録した読み取りの手続きの呼び出しを要るなら、画面を描けないことがあります。
- **読み込み直しはしません。** 結果が分からないときも、自動でもう一度送ったり読み直したりしません。登録の POST は BeakSight の送り手が 1 回だけ送り、redirect は追いません（「[登録の要求の送り方](#登録の要求の送り方)」）。

## 送る欄に選ばなかった欄

フォームの、見えていて編集できる欄のうち、シナリオの送る欄に選ばなかった欄は、次のとおりに扱います（ブラウザがそのまま送る中身と、照合の期待を合わせるため）。

- **text 系の欄**（text、search、email、url、tel、number、date など、textarea）: 空のまま送ります（照合の期待は空の値）。
- **checkbox・radio**: チェックしないまま（選ばないまま）にします（照合の期待は「送られない」）。同じ名前の hidden と checkbox の組（Rails 型）の checkbox は、hidden の値だけが送られます。
- **select（1 つ・複数）、range、color**: ブラウザがページの決めた既定の値で送るので、**送る欄に選ぶ必要があります**。選ばないシナリオは、下書きの保存で受けません（`SCENARIO_CREATE_DEFAULT_VALUE_FIELD_NOT_SENT`）。書き込みのときも送りません。
- hidden の欄、読み取り専用の欄、見えない欄（見えない checkbox・radio・select を含む）は、ページの値のまま送ります。
  - **名前だけを照らす欄は、ページが作る値の名前の閉じた一覧（CSRF のトークン、`nonce` など）に当たる欄だけ**です。値を読まず、記録しません。`token` の語に当たる名前（`auth_token`・`access_token`・`api_token` など）も、この一覧に当たるので名前だけを照らします（下の「確かめていないこと・使えないこと」の限界）。
  - **それ以外の欄**（`lock_version` など）は、書き込みの画面で値を読み、送る中身がその値と完全に一致するかを照らします（見えない checkbox・radio は、チェックの状態（送るか送らないか）と値を、見えない select は選んだ値を照らします）。読んだ値は記録しません。
  - **それ以外の秘密に見える名前**（`code`・`key`・`ticket` など）の hidden・readonly・見えない欄がある画面は、値を読めず照らせないので、実行しません（シナリオの下書きの確かめで受けません。`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`）。
  - **disabled の欄**は、ブラウザが送らないので、送られないことを照らします。
  - `_method` の欄は、承認した候補の上書きの値と同じかも照らします。

## 守りの範囲

- **書き込みの段の Guard**: 書き込みの段の Context では、承認された要求の形（method `POST`、Origin、path、enctype）に完全に一致する、main frame のナビゲーションの POST を 1 回だけ通します。送信の窓の間は、ほかのすべての要求を止めます。許可 Origin の外へは、段の全体で止めます。Service Worker・iframe・popup・WebSocket・beacon・Worker の fetch は届きません。307・308 の再 POST は止めます（結果は `UNKNOWN`）。2 回目の POST、別の path、別の Origin も届きません。
- **送る中身の照合**: 通す前に、POST の本文を照合します。欄の名前は送る欄・送る欄に選ばなかった見える欄（上の扱い）・承認した候補の hidden と readonly の欄だけ、送る欄の値は生成した値と完全に一致（改行は CR LF にそろえるだけ）、enctype は `application/x-www-form-urlencoded` と `multipart/form-data` だけ（`text/plain` は止める）、file の欄は空、文書の文字コードは UTF-8 だけ、`_method` の値は承認した候補の上書きと一致。外れたら送りません（`BLOCKED`）。**hidden・readonly・見えない欄の値（見えない checkbox・radio・select を含む）は、書き込みの画面で読んだ値と照らします**（読んだ値は記録しません）。disabled の欄は、送られないことを照らします。**ページが作る値の名前の閉じた一覧（CSRF のトークンなど）に当たる欄の値だけは、読まず、照らさず、記録しません**（名前だけを照らします。ページの JS がその値を書き換えても見つけられない限界があります）。それ以外の秘密に見える名前の hidden・readonly・見えない欄がある画面は実行しません（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`。上の「送る欄に選ばなかった欄」）。
- **送る直前の確かめ直し**: 押す直前（押す前の読み込みの間隔の待ちの後）に、親が承認と許可を求め直します。撤回などで外れれば送りません。撤回とシナリオの変更のときは、親（画面のサーバ）が、そのシナリオの動いている書き込みのジョブに止める合図を送ります。ワーカーは、押す前の最後の待ちの後と、確かめ直しの答えを受けた後に、止める合図を見ます。確かめ直しの答えを受けてから押すまでの短い間に撤回したときは、送ります（下の「確かめていないこと・使えないこと」）。
- **フォームの入力**: 入力の操作（値を入れる、選ぶ、チェックする）は、ログインと書き込みの 2 つの部品だけが持ちます（自動の検査で確かめます）。BeakSight は要求の本文を自分で組み立てません（ページのフォームに値を入れ、ブラウザが組み立てた要求を照合してから、BeakSight の送り手が 1 回だけ送ります）。
- **送り手の数え（重ねの守り）**: 送り手は BeakSight の中継だけにつなぎます。http のサイトでは、中継も、承認された登録の POST を 1 回に数え、2 回目を止めます（https では、中継から要求の中身は見えないので、送り手が 1 回だけ送ることと Guard で守ります）。
- **記録**: 資格情報、Cookie、CSRF のトークン、hidden の値は、管理データ・成果物・ログ・ワーカーとの通信に残しません。送った値は合成のテストデータなので、決まった場所（管理データの書き込みの結果、`action-run.json`）に平文で残します（READ の定義の送る値と同じ扱い）。
- **予約の締め**: ジョブの終わりで必ず締めます。画面のサーバを再起動したときは、締めていない予約を `UNKNOWN` で締めます。

## 確かめていないこと・使えないこと

- **ブラウザと完全には同じでない要求**: 登録の要求は BeakSight の送り手が送るので、一部のヘッダ、ヘッダの並び、TLS の形、証明書の確かめ方が、ブラウザが自分で送るときと違います（「[登録の要求の送り方](#登録の要求の送り方)」）。こうした違いでサイトの振る舞いが変わるかは、実際のテスト環境では確かめていません。
- **HTTP/2 だけを話すサイト**: 登録の要求を送れません。
- **読み込みのたびに値が変わる、秘密に見えない名前の hidden がある画面**（時刻や要求の番号など）: 画面の確かめのときに読んだ値と照らすので、登録は止まります（止める側）。ページが作る値の名前の閉じた一覧に当たる欄（`nonce`・CSRF のトークンなど）は名前だけを照らすので、値が変わっても止まりません。
- **値を照らす欄が同じ名前で 2 つ以上ある画面**: 止まります。**見えない checkbox・radio・select** も、値を照らします（checkbox・radio はチェックの状態と値、select は選んだ値）。
- **名前だけを照らす欄**（ページが作る値の名前の閉じた一覧。CSRF のトークンなど）: 値を照らさないので、ページの JS が値を書き換えても見つけられません（「[守りの範囲](#守りの範囲)」の送る中身の照合の限界）。`token` の語に当たる `auth_token`・`access_token`・`api_token` なども、ページが作る値かどうかによらず、この一覧に当たるので名前だけを照らします（同じ限界）。一覧の外の秘密に見える名前の hidden・readonly・見えない欄がある画面は、実行しません（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`）。
- **確かめ直しの後の撤回**: 送る直前の確かめ直しの答えを受けてから、登録の要求がサイトに届くまでの間（押す前のフォームの確かめ、押す、送る中身の照合、送り手の接続。テスト用のサイトで 0.07〜0.28 秒）に撤回やシナリオの変更をしたときは、登録を送ります（止める合図が届いても、押した後です）。結果は、その回の判定のとおりに記録します。
- **サーバの側の通知**: 登録を契機にしたメールや SMS は、自動では確かめません。副作用の確認 `NO_EXTERNAL_NOTIFICATION` と環境の証跡に頼ります。ブラウザから許可 Origin の外への要求は止めます。
- **更新（UPDATE）**: 「[承認された更新の手順](approved-update.md)」にあります。複数の段のシナリオ（登録してから更新する、など）と、READ の結果の値を使う生成は扱いません。
- **実際のテスト環境**: API の登録 1 件は確かめました（「[実テスト環境で確かめたこと](real-test-environment.md#実テスト環境で確かめたこと2026-11-02-時点)」）。フォームの送信の登録は、確かめていません。
- CLI からの書き込み。
