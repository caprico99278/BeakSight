# 管理画面（ローカル）

このコンピュータの中だけで動く管理画面の、起動のしかた、画面と操作、守りの範囲、開発と検証のスクリプトです。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 管理画面では、監査プロファイルの登録・更新・取り消し、公開の監査（読むだけ）と認証つきの読み取りの監査（手動のログインと、Windows での自動ログイン）の開始・進み具合の表示・停止・結果の閲覧、自動ログインの資格情報の保存と、止めた自動ログインの再開、操作の候補の発見と READ の確かめ、書き込みのシナリオの承認と撤回、入力の規則、承認された登録（CREATE）と更新（UPDATE）の開始と結果と報告、監査済みデータの台帳、環境の状態を扱えます。ふだんの書き込みは、プロファイルの詳細の一覧「登録・更新を試せる画面」でチェックした画面だけを、次の点検（まとめて実行）の最後に行います（「[登録・更新を試せる画面](#登録更新を試せる画面)」）。CLI の監査（`run`、`validate-config`）は、管理画面とは別に、これまでどおり動きます。画面の語（「点検」「作業」など）と、この文書の語の対応は「[画面の語と文書の語](#画面の語と文書の語)」にあります。3 つのモードを通して使う順は「[通しの使い方](end-to-end-usage.md)」にあります。

## 画面の起動

管理データを準備してから（「[管理データの準備](local-setup.md)」）、画面を起動します。

```powershell
npm run setup:local
npm run ui
```

- `npm run ui` は、監査の本体（`npm run build`。画面から動かす監査のワーカーが使う `dist/`）と画面（`npm run build:ui`）をビルドしてから、画面のサーバを起動します。起動の初めに、`npm run setup:local` と同じ準備を行うので、`setup:local` を忘れても、正しく準備してから起動します。
- 起動のときに、前の画面のサーバで終わっていなかった監査を「中断」として記録し、コンソールに知らせます（「[画面のサーバが落ちたとき](#画面のサーバが落ちたとき)」）。
- 起動のときに、自動ログインの資格情報のフォルダに残った書きかけの一時のファイルを消し、資格情報の暗号化を使えるかを 1 回確かめます（結果は「環境の状態」の画面。「[自動ログイン](#自動ログイン資格情報とログインの確かめ)」）。
- 準備ができなかったときは、`npm run setup:local` と同じ説明と取るべき手順を表示し、画面のサーバを起動せずに止まります（終了コード 1。「[困ったとき](local-setup.md#困ったとき)」）。
- 起動すると、コンソールに次のような URL を表示します。この URL をブラウザで開きます。

```text
BeakSight 管理画面: http://127.0.0.1:4317/?token=…
この URL は、この起動のあいだだけ使えます。ほかの人に渡さないでください。
```

- URL の `token` は、起動のたびに変わる合言葉です。ほかの人に渡さないでください。ログやファイルには書きません。
- **画面のサーバは、同時に 1 つだけ動かせます。** 同じ管理データ（`local-data/`）で、すでに画面のサーバが動いていると、2 つ目は待ち受けずに、動いている画面のサーバのプロセスの ID と port、取るべき手順（動いている画面のサーバを使うか、止めてから起動する）を表示して止まります（終了コード 1）。`npm run ui` と開発のサーバ（`npm run ui:dev`）の組み合わせも、`--port` の違う 2 つの起動も、同じ扱いです。このとき、2 つ目は、前の画面のサーバのジョブの記録を書き換えません。監査を画面全体で同時に 1 つだけにするためです（「[サイトへの負荷の決まり](#サイトへの負荷の決まり)」）。
  - どちらが動いているかは、管理データの中の 1 行（動いている画面のサーバのプロセスの ID、OS の起動の時刻、ハートビートの時刻）で判断します。画面のサーバは、ハートビートを 1 分ごとに書き換えます。画面のサーバが落ちてこの行が残っても、そのプロセスが終わっている、OS を起動し直した、ハートビートが 5 分より古い、のどれかなら、次の画面のサーバが取り直して起動します（CLI の Run のロックと同じ決まり）。
  - 前の画面のサーバが止まって見えて、次の画面のサーバがロックを取り直した場合も、前の画面のサーバの監査のワーカーが動いている（最後の合図から 20 秒以内）間は、次の画面のサーバはそのジョブを中断に直さず、新しい監査を始めません。ロックを失った前の画面のサーバは、自分の監査に止める要求を送り、60 秒の後も終わらなければワーカーを止めます。
  - 開発のサーバは、待ち受けを始めてから確かめるので、止まる前に一瞬だけ待ち受けます（token の URL は表示しないので、画面は開けません）。
- 待ち受けの port の既定は `4317` です。使用中なら、別の port を選ばずに、理由と取るべき手順を表示して止まります（終了コード 1）。別の port を使うときは、`npm run ui -- --port 4400` のように指定します。番号でない値や範囲の外の値（1〜65535 の外）も、説明を表示して止まります。
- 止めるときは、コンソールで Ctrl+C を押します。動いている監査があれば、そのことを知らせて止める要求を送り、今のページの監査を終えるまで最大 10 秒待ってから、管理データを閉じて終わります（待つ時間は名前つきの定数 `AUDIT_JOB_SHUTDOWN_WAIT_MS`）。待つ間にもう一度 Ctrl+C を押すと、待たずにすぐに終わります（そのときの監査は「[画面のサーバが落ちたとき](#画面のサーバが落ちたとき)」と同じ扱いです）。
- **管理画面のブラウザを閉じると、画面のサーバも止まります。** 管理画面のページは、開いている間 5 秒ごとに、画面のサーバへ生きている知らせを送り、閉じるときに閉じたことを知らせます（どちらも、同じ Origin への token の cookie つきの要求です。別のサイトや token のない要求では受けません）。次の 3 つがそろうと、画面のサーバは Ctrl+C の 1 回目と同じ止め方で止まり、コンソールに「管理画面が閉じられたので、画面のサーバを止めました。もう一度使うときは、npm run ui を実行してください。」を出します。
  - 起動の後に、管理画面を一度は開いた（起動しただけで、まだ開いていないときは止まりません）。
  - どのページも開いていない。最後のページを閉じてから 15 秒の猶予があり、読み込み直しはこの中で戻るので止まりません。複数のタブで開いていれば、どれか 1 つが開いている間は止まりません。閉じたことを知らせずにページが消えたときは、知らせが 150 秒途絶えた後に閉じたと見なします（隠れたタブの知らせは、ブラウザが 1 分ごとに間引くことがあるため、長めにしてあります）。
  - 動いている監査のジョブがない。ジョブが動いている間は止めず、ジョブが終わった後に確かめ直して止まります（その間に管理画面を開き直せば止まりません）。
- 間隔と猶予は名前つきの定数です（`apps/local-ui/src/security/ui-presence.ts`）。ブラウザが長い間ページを止めた（凍結した）ときも、知らせが途絶えるので、画面のサーバは止まります。そのときは、もう一度 `npm run ui` で起動します。BeakSight がログインのために開くブラウザ（Chromium）は、管理画面のブラウザとは別で、閉じてもこの決まりに当たりません。
- 開発のサーバ（`npm run ui:dev`）は、ブラウザを閉じても止まりません（Ctrl+C で止めます）。

## 画面の語と文書の語

画面は、IT に詳しくない人にも読めるように、日常の言葉で書いてあります（設計書 `doc/design/2026-10-26-beaksight-plain-ui-design.md` の 5 章）。この文書と、ほかの手順書・成果物（JSON・報告の記録の段）は、これまでの言葉のままです。手順書の「監査を始める」は、画面では「点検を始める」と出ます。対応は次のとおりです。

| 文書の語 | 画面の語 |
| --- | --- |
| 監査 | 点検 |
| 監査プロファイル（プロファイル） | 点検するサイト（短く「サイト」）。左のメニューは「点検するサイト」「サイトを足す」 |
| Run・最後の Run | 点検の回・前回の点検 |
| ジョブ | 作業（一覧の画面は「作業の履歴」、1 つの画面は「作業の様子」） |
| 操作の候補の発見（発見） | 操作さがし |
| READ の確かめ（読み取り） | 見るだけの確かめ |
| シナリオ | 書き込みの手順 |
| 承認・実行の許可 | 書き込みの OK（ふだんの流れでは出しません。一覧「登録・更新を試せる画面」のチェックが承認を兼ねます） |
| 入力の規則 | 入れる値の決まり（ふだんは出しません） |
| 照合・照合の READ | 答え合わせ |
| 資格情報 | ログインの ID とパスワード（画面「ID とパスワード」） |
| 手動のログイン | 手でログイン（ログインのしかた「手でログインする」） |
| 自動ログイン | 自動ログイン（ログインのしかた「自動でログインする」） |
| 認証の方式 | ログインのしかた |
| 認証の設定 | ログインの設定 |
| 監査モード | 点検のしかた（`PUBLIC_PASSIVE` は「公開の画面の点検」、`TEST_AUTH_PASSIVE` は「ログインして見るだけの点検」、`TEST_APPROVED_WRITE` は「書き込みも試す点検」） |
| 環境（`PUBLIC`・`TEST`） | サイトの種類（「本番のサイト」「テスト用のサイト」） |
| テスト環境 | テスト用のサイト |
| 監査済みデータの台帳 | 作ったデータの一覧 |
| 隔離 | 本番から切り離されていること（画面では聞かず、出しません） |
| 改訂・版 | 何回目の変更か（ふだんは出しません） |
| 段 | ステップ |
| 読まないパス | 読まないページ |
| 監査の負荷 | 点検の負荷 |
| 副作用の確認（4 項目） | ほかへの影響の 4 つの約束 |
| 「次にすること」の欄 | 要点のパネル「今の様子」 |
| たたんだ「詳しい設定」 | たたんだ「詳しい内容」 |
| ログインの確かめ（`LOGIN_CHECK`）の画面 | 自動ログインの再開（ふだんの流れからは開きません） |
| 入口の確かめ | サイトの下調べ（ボタン「サイトの下調べをやり直す」） |
| 使い方の 2 択（テスト環境のログインあり・公開） | 「ログインが必要なサイト」「ログインしなくても見られるサイト」 |
| ログインの希望 `loginPreference`（`MANUAL_EVERY_TIME`） | 「毎回手でログインする」（サイトの設定の中。省けば自動ログイン） |
| 承認した書き込みのシナリオがある登録の画面（チェックした画面） | 一覧「登録・更新を試せる画面」の、チェックした行 |
| 登録（`CREATE`）・更新（`UPDATE`）の書き込み | 登録・更新（前の画面の語「書き換え」は「更新」になりました。作ったデータの一覧のボタンは「更新を試す」） |
| HTML レポート | 作業の様子の主のボタン「結果を見る」（点検を終えて移ったサイトの画面の主のボタンも「結果を見る」） |

- アドレスは、画面では「サイトのアドレス」（Origin）、「ページのアドレス」（URL）、「アドレスの後ろ」（path）と呼び分けます。どれも、ふだんの画面には出しません。
- 画面には、Origin、送り方、HTTP の言葉、CSS セレクタ、digest、各種の ID、版と承認の履歴、入力の規則の中身などを、原則として出しません（成果物の JSON とジョブの記録には残ります）。

## 画面と操作

左のメニューは 3 つです（画面では「点検するサイト」「サイトを足す」「作業の履歴」。環境に問題があるときだけ「環境に問題があります」が足されます）。キーボードだけでも操作できます。画面の語と、この文書の語の対応は「[画面の語と文書の語](#画面の語と文書の語)」にあります。

### どの画面にも共通の形

- **要点＋主のボタン 1 つ＋詳しい内容 1 つ**: どの画面も、上から、今の様子をやさしい言葉で書いた要点、次に押すボタン 1 つ（主のボタン。止めるなどの二次のボタンがあれば同じ行の右）、たたんだ「詳しい内容」1 つ、の形です。直すための欄と、調べるための情報（ジョブの記録にしかない情報を含む）は、「詳しい内容」の中にあります。開かなくても流れは進みます。押せないときは、ボタンを出さずに、理由といつ押せるようになるか（例: 「◯◯ から始められます。」）を要点に書きます。
- **今どこにいるか**: 題（h1）の上に「サイトの一覧 ＞ ◯◯ ＞ 点検」の形の 1 行があります。前の画面へは、この 1 行から戻ります。
- **自動で次へ**: ジョブが成功で終わると、次の画面へ自動で移ります。移った先の要点の 1 行目に、何が起きたか（例: 「サイトの下調べが終わりました。ログインの画面が見つかりました。」）を書きます。移る組は次のとおりです（判定は `apps/local-ui/src/server/audit-job-functions.ts` の `jobSummaryOf`）。
  - 作成の画面の「点検を始める」から始めた入口の確かめ → 続けて始めた点検（まとめて実行）の最初の段のジョブの画面。点検を続けて始めなかったときは、入口の確かめの結果によらず、プロファイルの詳細（要点に理由）。
  - 「サイトの下調べをやり直す」から始めた入口の確かめ（ログインの画面が見つかった・はじめのページを見られた）→ プロファイルの詳細。
  - 監査（最後まで見た `COMPLETE` と、一部のページを見られなかった `PARTIAL`）→ プロファイルの詳細。一部のページを見られなかったときは、要点の 1 行目が「点検が終わりました。一部のページは見られませんでした。」です。
  - まとめて実行の段 → 次の段のジョブの画面（チェックした画面の書き込みの段を含む）。最後の段まで済んだら、プロファイルの詳細。
  - 単独の書き込み（シナリオの画面から始めたもの。ふだんの流れではありません。照合済み `VERIFIED`）→ シナリオの詳細。登録に続けて更新を始めたときは、その更新のジョブの画面。
  - 点検（監査かまとめて実行）を終えたばかりで移ったプロファイルの詳細では、主のボタンが「結果を見る」（HTML レポート）になり、「点検を始める」などの元の主のボタンは二次のボタンになります（「[プロファイルの詳細の主のボタン](#プロファイルの詳細の主のボタン)」）。チェックした画面で書き込んだ点検では、要点の 2 行目に書き込みの 1 行が出ます（「[登録・更新を試せる画面](#登録更新を試せる画面)」）。
  - 失敗、安全の違反、ログインの切れ、書き込みの結果が分からない（`UNKNOWN`）・一部だけ確かめた（`PARTIAL`）、利用者が「点検を止める」などで止めたときは移らず、その画面に要点と次にすることを出します（止めたことを、押した人がその場で見られるようにするためです）。単独の発見・READ の確かめ・ログインの確かめのジョブも移りません。移るかどうかは、送信の扱い（下の「監査の段の送信の扱い」）によりません。

### 画面の一覧

| 画面 | できること |
| --- | --- |
| サイトとプロファイル（画面では「点検するサイト」） | 登録した監査プロファイルの一覧。何をする道具かの 1 行と、主のボタン「サイトを足す」。行ごとに、次にすることの短い文（プロファイルの詳細と同じ判定）と「続ける」（プロファイルの詳細へ）。 |
| 新しいプロファイル（画面では「サイトを足す」） | 入力は 3 つです: 「開始のアドレス」、「使い方」（「ログインが必要なサイト」か「ログインしなくても見られるサイト」）、ボタン「点検を始める」1 つ。名前・設定のファイル・許可 Origin・テスト環境の Origin・隔離の参照（「確かめていない」の固定の形）は BeakSight が決めます。隔離の扱い、ID とパスワード、詳しい設定の欄は、作成の画面にはありません。同じサイトの設定のファイルが決まらないときだけ、保存の拒否の知らせの中で「どれを使いますか」を選びます。押すと、保存 → 入口の確かめ（サイトの下調べ）→ 点検（まとめて実行）へ自動で進みます（ログインしなくても見られるサイトは、入口の確かめの後に公開の監査）。ログインが必要なサイトの 1 回目の点検は、開いたブラウザで手でログインし、その後は BeakSight が自動でログインします（「[管理画面でのプロファイルの作り方](profiles.md#管理画面でのプロファイルの作り方)」）。 |
| プロファイルの詳細（画面ではサイトの名前） | 要点のパネル「今の様子」と、段で決まる主のボタン 1 つ（下の表）。その下に、一覧「登録・更新を試せる画面」（操作さがしを使うプロファイルだけ。「[登録・更新を試せる画面](#登録更新を試せる画面)」）。「詳しい内容」の中に、点検のしかたとログインのしかた、「ほかの画面」（「サイトの下調べをやり直す」、「ログインの設定を開く」、「ID とパスワードの画面を開く」、「操作さがしの結果を見る」、「見るだけの確かめを開く」、「書き込みの手順へ」、「作ったデータの一覧を開く」のうち、そのプロファイルで使えるもの。どれも、ふだんの流れでは開きません）、「表示の設定」、「点検の負荷」（「[サイトへの負荷の決まり](#サイトへの負荷の決まり)」）、「サイトの設定」（プロファイルの編集）、「このサイトの登録を取り消す」があります。 |
| プロファイルの編集（画面では「サイトの設定」） | プロファイルの詳細の「詳しい内容」の中にあります。項目を直して保存すると、改訂が 1 つ進みます。承認したサービスの Origin は、読むだけの一覧と「消す」だけです（足す欄はありません。手動のログインの観察だけが足します）。認証の方式は、自動ログインにはできません（手動のログインへ戻すことはできます。自動ログインへは、1 回目の点検の手でのログインの後の切り替えで入ります）。「毎回手でログインする」を入れると、自動ログインのプロファイルでも、点検のたびに開いたブラウザで手でログインします（外すと自動ログインに戻ります。保存した ID とパスワードは消しません）。自動ログインのプロファイルでは、ログインの送信先（設定のファイルを含む）を変える保存と、承認したサービスの Origin・テスト環境の Origin を足す保存を拒みます（「[自動ログインへの入り方と、変えられない値](profiles.md#自動ログインへの入り方と変えられない値)」）。ほかの画面で先に保存された場合は、保存せずに知らせるので、読み込み直してからもう一度変更します。 |
| プロファイルの取り消し | プロファイルの詳細の「詳しい内容」の「このサイトの登録を取り消す」から、確認のダイアログの「取り消す」で取り消します。元に戻せません。同じ名前（profileId）は使い直せません。続けて使う場合は、もう一度「サイトを足す」で作ります（名前の欄はなく、BeakSight が末尾に番号を付けた別の名前にします）。保存した資格情報があれば、それも消します。 |

### 登録・更新を試せる画面

操作さがしを使うプロファイル（`TEST_AUTH_PASSIVE`・`TEST_APPROVED_WRITE`）のプロファイルの詳細の、要点のパネルの下の一覧です（設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` の 4.1.1・4.1.2・4.1.4）。書き込みは別の作業にせず、点検の中で、ここでチェックした画面だけ、最後に登録 →（あれば）更新を行います。

- **行**: 最後の発見で見つかった登録の画面（API の形とフォームの形）ごとに 1 行。画面の名前（発見が記録した見出しか題。取れなければ「「◯◯」の登録の画面」「登録の画面（N）」。英字の path は出しません）、状態（「チェックしています」「チェックできます」「サイトの設定が変わったので、チェックが外れました。もう一度チェックしてください。」「この画面では試せません」）、試せない理由、更新の 1 行（「更新は、次の点検で試します。」「更新する欄を決められないため、登録だけを試します。」など）、メールや電話への知らせを送ることがある画面の 1 行、前の点検の結果。一覧の上に「チェックした画面では、点検のときに、テスト用のデータを 1 件登録し、1 回更新します。作ったデータは消しません。」を出します。
- **チェックの保存**: チェックを入れると、その場で保存します（確認のダイアログはありません）。1 回の保存で、書き込みのモードへの切り替え（まだなら。改訂が 1 つ進みます。この切り替えだけの改訂は、発見の結果の古さの判定では同じ改訂とみなします）、その画面の登録と更新のシナリオの自動の下書き（更新で変える欄は BeakSight が決めます）、承認（今の承認の記録と digest。副作用の確認の 4 項目は、チェックが確かめたことにします）を行います。実行の許可は、ここでは出しません。チェックを外すと、その画面の登録と更新の承認を取り消します。サイトへは何も送りません。
  - 前にチェックした画面にチェックを入れ直したときも、最後の操作さがしの結果と今の作り方で、登録の手順を作り直します。前の手順と同じなら承認だけを行い、違えば新しい版を作って承認します（答え合わせのしかたなどの直しが、チェックの入れ直しで効きます）。
- **点検の始めの確かめ**: 点検（まとめて実行）を始めるときに、チェックした画面の登録の手順を、最後の操作さがしの結果で作り直して比べます（そのときの点検の操作さがしの結果ではなく、前回までの結果です）。
  - 答え合わせのしかただけが違うときは、新しい手順を自動で承認して、そのまま書き込みます。
  - 送る中身（送り先や送る欄の形）が違うときは、承認を外し、行を「サイトの設定が変わったので、チェックが外れました。もう一度チェックしてください。」にします（その画面には書き込みません。もう一度チェックすると戻ります）。
  - 一覧のどのチェックの行にも結び付かない承認（画面の形が変わって、一覧に行として出なくなったものなど）は、取り消します（チェックした画面だけに書き込むためです）。
  - この確かめを終えられないとき（管理データを読めない、など）は、点検を始めません。そのときは、見るだけの段も始まりません。
  - まれな場合の見え方（出る文が今の画面に合わない、など）は「[実テスト環境の手順の既知の点](real-test-environment.md#点検の始めの確かめとチェックのまれな場合の見え方既知の点)」にあります。
- **書き込み**: 次の点検（まとめて実行）の最後に、チェックした画面ごとに、ジョブの管理が実行の許可を出し、登録 1 件 →（同じ点検の登録で作り、照合して番号が取れたレコードの）更新 1 件を送ります。送り直しません。ログインは点検の 1 回のまま使い、読み込みの間隔も守ります。結果が分からない画面・安全の違反・ログインの切れの後は、残りの書き込みを止めます。チェックしたままなら、点検のたびに登録を 1 件行います（「[まとめて実行](stage-chain.md)」）。
- **データのないサイト**: 更新の画面は、作ったデータがあるときにしか見つかりません。チェックした後の最初の点検は登録だけで、次の点検の発見で更新の候補が見つかったら、BeakSight がチェックの範囲の中で更新の下書きと承認を行い、同じ点検で更新します（知らせを送ることがある更新の画面は、自動では承認しません）。番号の型・鍵は、よくある形から推します（「[承認された登録](approved-create.md)」）。
- **結果**: 点検を終えて移ったプロファイルの詳細の要点に、書き込みの 1 行（「チェックした画面では登録・更新も行いました。」など）を、行に「前の点検の結果」を出します。書き込みの段のジョブの画面と報告は、段ごとに分かれます。

- 保存できない値は、項目ごとに理由を日本語で表示します。
- 承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルでも、点検の監査の段で BeakSight が書き込むことはありません（ページが自動でする通信の扱いは、下の「[監査の段の送信の扱い](#認証つきの監査ログインあり読むだけ)」の項）。チェックした画面がないときは、開始の画面に「この点検は見るだけで行います（書き込みは送りません）。」が出ます。チェックした画面があるときは、要点に「…チェックした画面では、テスト用のデータを登録・更新します。そのほかは見るだけです。」が出ます。ほかに使えるのは、認証の設定、資格情報（自動ログイン）、操作の候補の発見、READ の確かめ、書き込みのシナリオの承認・撤回、入力の規則、承認された登録と更新、監査済みデータの台帳です（「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。
- 認証つきの読み取りの監査（`TEST_AUTH_PASSIVE`）と承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルは、認証の設定を使います。入口の確かめでログインの画面が見つかると、BeakSight が案で保存します。保存できなかったときだけ、プロファイルの詳細の主のボタン「ログインの設定を開く」から作ります。

## 監査の実行

画面から動かせるのは、公開の監査（読むだけ。`PUBLIC_PASSIVE`）と、認証つきの読み取りの監査（ログインあり・読むだけ。`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` で、認証の方式が手動のログインか、Windows での自動ログイン。書き込みのモードでも、監査の段で BeakSight は書き込みません。「[認証つきの監査](#認証つきの監査ログインあり読むだけ)」）です。CLI の `run` と同じ監査を、画面のサーバとは別の process（監査のワーカー。`dist/worker/audit-worker.js`）で行います。結果（`run.json`、`audit.json`、`report.html`、`report-summary.json`、ChatGPT 用のバンドル）の形は、CLI と同じです。画面では、監査は「点検」、ジョブは「作業」と出ます。

### 始める

- プロファイルの詳細の主のボタン「点検を始める」（一覧の行の「続ける」からプロファイルの詳細を開きます）で、開始の画面を開きます。始められないとき（取り消したプロファイル、認証の設定がない・古い・誤りがある、資格情報がない、自動ログインの間隔の中・止めている、など）は、主のボタンを出さずに、理由と次にすることを要点に書きます。
- 開始の画面の主のボタンは「点検を始める」1 つです。`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` のプロファイルでは、これで**まとめて実行**（監査 → 操作の候補の発見 → READ の確かめ →（チェックした画面があれば）書き込み）を始めます（既定。別のボタンはありません。「[まとめて実行](stage-chain.md)」）。`PUBLIC_PASSIVE` のプロファイルでは、監査だけを始めます。要点に、1 回押すと何が起きるか（例: 「サイトのページを見て回り、操作できる所を探します。読むだけで、書き込みはしません。」。チェックした画面があれば「…チェックした画面では、テスト用のデータを登録・更新します。そのほかは見るだけです。」）を書きます。
- **始め方**: 前回の監査が最後まで終わっていないときだけ、要点に一文が出て、「詳しい内容」の中に「始め方」（「前回の続きから再開する」が既定。「新しく始める」は CLI の `--new` と同じ）が出ます。選ばなければ、続きがあれば続きから、なければ新しく始めます。前回が最後まで終わっていれば、選択は出さず、新しく始めます。
- **詳しい内容**: 行う段（この順）、開始の URL、設定のファイルの要点（ページの上限、時間の上限、ページの読み込みの間隔。開始の画面では変えられません。プロファイルの詳細の「点検の負荷」で変えます）、認証つきの監査では読まないパスの欄（「[認証つきの監査](#認証つきの監査ログインあり読むだけ)」）があります。
- 画面を開いた後にプロファイルが変更された場合は、開始せずに知らせます。

### サイトへの負荷の決まり

- **間隔と上限は、プロファイルの詳細の「詳しい内容」の「点検の負荷」で変えます。** 監査は、設定のファイルの値のまま使います。まとめて実行を既定にしても、ページの上限と読み込みの間隔は変わりません。変えられるのは、ページの上限・時間の上限・ページの読み込みの間隔の 3 つだけで、プロファイルが指す設定のファイルが `local/targets/` の中の、名前と同じ `.json`（作成の画面で BeakSight が作ったファイルと同じ形）のときだけです。ほかの場所（`config/targets/` など）のファイルは、画面からは書きません。設定のファイルを直してください。
  - 値の範囲は、設定の検証と同じです（ページの上限と時間の上限は 1 以上の整数、間隔は 0 以上の整数のミリ秒）。**間隔は、今の下限より短くできません。** 許可 Origin にループバック（`127.0.0.1` など）でないものがあれば、下限は 1 秒です（「[サイトへの負荷](site-load.md)」の決まりと同じ）。範囲の外の値は、欄ごとに理由を表示して、書きません。今と同じ値も書きません。
  - 確定の前の確認のダイアログに、変える前と後の値（変えた項目だけ）を表示します。あわせて、書き込みのモードで承認したシナリオがあれば、承認が外れて再承認が要ること（件数）を、途中の Run があれば、再開されずに新しい Run が始まることを表示します。承認は設定のファイルの内容に結びつき（変えると「ターゲットの設定が変わった」で要再承認）、再開は設定が同じ Run だけを続けるためです（「[中断と再開](resume.md)」）。
  - 確定すると、設定のファイルの 3 つの値だけを書き換えます（ほかの項目は変えません。JSON は字下げ 2 の形で書き直します）。プロファイルの改訂は変わりません。画面を開いた後に設定のファイルが変わっていたら、上書きせずに知らせます。
- **監査は、画面全体で同時に 1 つだけです。** ほかの監査が動いている間に開始すると、理由を表示して開始しません。同じ出力先では、CLI の監査とも同時には始まりません（「[同じ出力先で、2つの監査を同時に始めない](cli.md#同じ出力先で2つの監査を同時に始めない)」）。
- 画面が 2 秒ごとに状態を読み直すのは、画面のサーバの管理データだけで、監査の対象のサイトには何も送りません（画面には「この画面は自動で新しくなります。閉じても点検は続きます。」とだけ出ます）。

### 進み具合と結果

- ジョブの画面（画面では「作業の様子」）は、動いている間、2 秒ごとに読み直します。要点には、結果の 1 行（「点検をしています。」など）と、監査の進み具合（「読んだページ 3 / 20。長くても あと 約 3 分」。ページの上限と読み込みの間隔から求めた上限の見積もり）を出します。CLI と同じ書式の細かい進み具合（発見したページ、ページの読み込みの回数、許可 Origin への要求と 1 分あたりの最大、許可 Origin の外への要求）と、知らせ（サイトの不調の確かめ直し、減速）は、「詳しい内容」の中です。
- 画面を閉じても監査は続きます。開き直すと、同じ状態を表示します。
- 終わった後は、要点に結果の 1 行を出します。最後まで終えた監査では、報告の小さなまとめ（`report-summary.json`。「[出力の構成](output.md#出力の構成)」）を読み、「点検が終わりました。問題が N 件見つかりました。」の形で問題の数を出します。主のボタンは「結果を見る」（HTML レポート）です。ただし、最後まで終えた監査と、一部のページを見られなかった監査は、自動でプロファイルの詳細へ移り、そこでも主のボタンが「結果を見る」になります（「[どの画面にも共通の形](#どの画面にも共通の形)」）。後から結果を見るときは、「作業の履歴」か、一覧の「前回の点検」の欄からジョブの画面を開きます。
- 「詳しい内容」の中に、ジョブの状態、Run の状態（完了、一部未完了など）、終わり方、日時と、成果物へのリンク（「HTML レポートを開く」、`run.json`・`audit.json`・ChatGPT 用のバンドルのダウンロード）があります。Run の ID や終了コードは、ふだんの画面には出しません（成果物とジョブの記録にあります）。失敗と中断では、理由と取るべき手順を、要点か「詳しい内容」に出します。
- **終わり方と理由**: `run.json` を読めた監査のジョブには、「詳しい内容」に「終わり方と理由」を表示します。最後の実行の終わり方（時間の上限で停止、サイトの不調で停止など）と、Run の理由（ページの上限、始める前の確認の失敗など）の説明に、次にできること（例: ページの上限で止まった → プロファイルの詳細の「点検の負荷」でページの上限を上げる。時間の上限で止まった → もう一度「点検を始める」を押すと、既定で続きから再開する）を添えます。この画面の文のない Run の理由（想定していない失敗 `UNHANDLED_FAILURE`、出力ファイルがスキーマに合わない `REQUIRED_ARTIFACT_INVALID` など）には、HTML レポートと同じ次にできることを、日本語の文で出します。「確かめきれなかったページの理由」も、どの理由にも次にできることを出します。確かめきれなかった所があるときは、要点に「確かめきれなかった所があります。くわしくは、下の「詳しい内容」を開いて見てください。」を出します。ページごとの理由は、HTML レポートの各ページにあります（この画面では `audit.json` を読みません）。発見と READ の確かめのジョブには、終わり方と次にできることを、入口の確かめのジョブには、案を作れなかった終わり方の次にできることを表示します。

### 止める・強制的に止める

- 要点の二次のボタン「点検を止める」は、確認のダイアログの後に、今のページの監査を終えてから止めます（CLI の 1 回目の Ctrl+C と同じ）。止めた Run は一部未完了になり、次に「点検を始める」を押すと、既定で続きから再開します。止めた監査のジョブの画面は、自動では移りません（止まったことを、その場で見られます）。
- 止める要求から 30 秒たっても止まらないときは、「強制的に止める」を表示します。今のページを待たずに、すぐに止めます（CLI の 2 回目の Ctrl+C と同じ）。再開のための保存は、最後に監査を終えたページまで残ります。強制的に止める要求の後も 10 秒止まらないときは、ワーカーを終わらせます。
- **ほかの種類のジョブ**: 止めるボタンと確認のダイアログの題・本文・確定のボタンは、ジョブの種類に合わせます（画面では「操作さがしを止める」「見るだけの確かめを止める」など）。まとめて実行の全体も、要点の「点検を止める」で止めます（今の段を止め、次の段を始めません）。続きから再開できるのは監査だけです。ほかの種類のジョブは、止めたら再開せず、もう一度始め直します。ダイアログの本文と、止める要求を送った後にジョブの画面に出す文は、止めたときに起きることを、種類ごとに書きます。
  - ログインの確かめ: ログインを送る前なら、送らずに止めます（画面から新しく始める道はありませんが、前から動いているジョブの扱いとして残ります）。
  - 操作の候補の発見: 次の画面を読まずに止めます。READ の確かめ: 次の定義を読まずに止めます。
  - 登録・更新の書き込み: 送る前なら、送らずに止めます。送る直前の確かめ直しの後に止めたときは、そのまま送り、その回の結果を記録します（「[承認された登録](approved-create.md)」の「確かめ直しの後の撤回」と同じ）。強制的に止めたときは、送ったか分からない（結果が分からない）として記録することがあります。そのときは、テスト環境でレコードの状態を確かめます。
  - 入口の確かめ: 開始の URL を読む前なら、読まずに止めます。

### 認証つきの監査（ログインあり・読むだけ）

テスト環境の管理画面などを、人がログインした状態で、読み取りだけで監査します。手動のログインでは、監査を始めたときに BeakSight が開くブラウザで、人がログインします。
始めから再開までの手順、守りの範囲、使えないこと、確かめていないことは「[認証つきの監査の手順](authenticated-audit.md)」にあります。

- **認証の設定**（画面では「ログインの設定」。ふだんは、入口の確かめの後に BeakSight が案で保存するので、開きません。案を作れなかったときは、プロファイルの詳細の主のボタン「ログインの設定を開く」から、直すときは「詳しい内容」の「ログインの設定を開く」から開きます。画面は、要点＋主のボタン＋詳しい内容の形で、欄は「詳しい内容」にたたんであります。保存していなければ、そう表示します）: ログインの送り方（「フォームの送信」か「スクリプトの送信」。スクリプトの送信の欄は「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」）、ログインの画面の URL、ログインの送信先（ログインの間だけ、ここへの送信（POST）を許します。入口の確かめと手動のログインの観察からだけ入り、画面では読むだけです）、ログインが済んだと判定するパス（と、任意で要素の CSS セレクタ）、セッションが切れたと判定するパス（空なら、ログインの画面のパス）、読まないパス（画面では「読まないページ」。ログアウトの画面を必ず入れます）、読む範囲のパス（空なら絞りません）、ログインの送信の回数の上限（1〜3 回）を設定します。パスか query にログアウトや削除などの語（`logout`、`signout`、`sign-out`、`log-out`、`delete`、`remove`、`destroy`、`cancel`）を含む URL は、設定にかかわらず読みません（画面では変えられません）。
- **秘密は書きません。** 認証の設定の画面には、パスワードや Cookie の値を入れる欄はありません。秘密に見える名前の query（`password`、`token`、`session` など）を含むログインの画面の URL も、保存しません。
- 保存の前に、サーバがプロファイルと設定のファイルで確かめ直し、誤りを項目ごとに日本語で表示します（1 行に 1 つの項目は、誤りのある行も示します）。
- 認証の設定は、保存したときのプロファイルの改訂に結びつきます。プロファイルを変更すると、認証の設定は「古い（保存し直しが必要）」になり、内容を見直して保存し直すまで、監査を始めません（プロファイルの詳細の主のボタンが「ログインの設定を開く」になります）。
- **始める**: 開始の画面の主のボタンは「点検を始める」です。手動のログインのプロファイルでは、開いたブラウザでログインすることを要点に書きます。読まないパスは、「詳しい内容」の欄（任意。1 行に 1 つ。今の値を入れて出し、既定で読まない語を説明に出します）で変えられます。値を変えて始めると、認証の設定を保存してから始めます。書き込みのモードのプロファイルでは、「この点検は見るだけで行います（書き込みは送りません）。」も表示します。認証の設定がない・古い・誤りがあるときは、理由と、認証の設定の画面へのボタンを表示して、開始のボタンを出しません。
- **ログイン**: 手動のログインでは、ジョブの画面の要点に「開いたブラウザで、ログインしてください。」と、二次のボタン「点検を止める」を出します。開いたブラウザでログインすると、BeakSight がログインの終わり（ログインの画面を離れた、新しいログインの状態の名前が増えた）を判定して先へ進みます。判定できないサイトのときだけ、主のボタン「ログインを終えた」を出すので、済んだら押します。ログインが済むと、まとめて実行では、ログインの設定の自動の登録と自動ログインへの切り替え（下の「1 回目の手でのログインから自動ログインへ」）をしてから、そのブラウザを閉じて、読み取りだけの監査を始めます。ログインの状態（Cookie など）は保存せず、画面にも出しません。再開するときも、もう一度ログインします。決められた時間の中にログインが済まない、送信の回数の上限を超える、などのときは、理由を表示して監査を始めません。認証の状態（ログイン待ち、ログイン済み、止まった理由）は、「詳しい内容」の「ログイン」の欄にあります。
- **セッションが切れたとき**: 監査の途中でログインの状態が切れたら、その Run を一部未完了で止め、要点に「◯◯ を見たときに、ログインが切れました。」と、止まったページを読まないパスに足す案内を出します（画面は移りません）。
- 認証つきの監査では、クリックによる操作の確かめ（Interaction）を行いません。速さの上限（ページの読み込みの間隔など）は、公開の監査と同じく設定のファイルの値のまま使います。

- **入口を確かめる**（画面では「サイトの下調べ」。作成の画面の「点検を始める」と、プロファイルの詳細の「サイトの下調べをやり直す」。入口を確かめていないときは主のボタン、ほかは「詳しい内容」の中）: ログインしないで開始の URL を 1 回だけ読み、ログインの画面の欄と送り方を調べて、認証の設定の案を作るジョブ（ジョブの種類「入口の確かめ」）です。ログインの画面が見つかり、認証の設定がまだなければ、その案で保存します（保存の確かめを通ったものだけ。すでにあれば上書きしません）。作成の画面から始めたときは、案を保存できた（か、すでにある）ら、続けて点検（まとめて実行）を始めます。「サイトの下調べをやり直す」から始めたときは、成功で終わると、プロファイルの詳細へ自動で移り、要点の 1 行目に結果を出します（点検は続けて始めません）。保存できなかったときは、プロファイルの詳細の主のボタンが「ログインの設定を開く」になります（「[入口の確かめ](authenticated-audit.md#入口の確かめ)」）。
- **観察した要求の登録**: 手動のログインの後は、BeakSight がログインの送信先などを自動で登録します（まとめて実行では、ログインの直後、監査の前に登録します。単独の監査では、ジョブが終わった後です。自動の登録が済んだら、行の「登録する」は出しません）。登録できる行が残ったときだけ、要点に「ログインの設定に足りない送信があります。下の「詳しい内容」の表で、行を選んで登録してください。」を出します。ジョブの画面の「詳しい内容」の、パネル「ログインの段で止めた送信」の表の「登録する」は、確認のダイアログの後に、その場で保存します（画面は移りません。成功の鍵は、ジョブのログインの観察から入れます）。行の「認証の設定の画面で直す」と、欄「ログインの段で観察した案」の「案を認証の設定に入れる」は、認証の設定の画面を下書きつきで開きます。保存は、その画面で利用者が行います（「[観察した要求の登録](authenticated-audit.md#観察した要求の登録)」）。
- **1 回目の手でのログインから自動ログインへ**: 手動のログインのプロファイルのまとめて実行で、開いたブラウザで手でログインすると、BeakSight がそのときに入れた ID とパスワードを受け取り、ログインの直後に、ログインの設定の自動の登録と、資格情報の保存と、自動ログインへの切り替えを 1 回で保存します（プロファイルの改訂が進みます。まとめて実行は、この改訂を基準として次の段へ進みます）。値はページから見えない所で読み、ログインに成功し、観察したログインの送信先への送信の本文に入っていたときだけ保存します。画面・記録・ログに値を出しません。ログインの欄・パスワードの欄・送信のボタンの 3 つの案がそろわない、資格情報のファイルがすでにある、暗号化を使えない、「毎回手でログインする」を入れている、のどれかのときは切り替えず、受け取った値を捨てます。切り替えたときは、ジョブの画面の「詳しい内容」に「次の点検から、BeakSight が自動でログインします。」を出します。前の「次から自動でログインする」の画面（ID とパスワードを BeakSight で入れ直す手順）は、ふだんの流れからなくしました（「[1 回目の手でのログインから切り替える](automated-login.md#1-回目の手でのログインから切り替える)」）。
- **表示の設定**: プロファイルの詳細の「詳しい内容」の「表示の設定」で、監査・発見・READ の確かめ・書き込みのジョブのブラウザを表示するかを選びます（画面では「作業中のブラウザを画面に出す」。既定は表示）。この欄の設定は、チェックを切り替えるとすぐ保存します。欄に専用の保存のボタンはなく、プロファイルの「保存する」のボタンとは別です（プロファイルを保存しても、この欄は変わりません）。保存の間はチェックを押せず、保存できたら欄の中に「表示の設定を保存しました。」を出します。保存できなかったとき（プロファイルが見つからないなどで拒まれたとき、入力の検証の誤りや通信の誤りのとき）は、チェックを切り替える前の値に戻し、理由を出します。切り替えても、プロファイルの改訂と承認は変わりません。表示する設定のとき、動いているジョブの画面に「見るだけにして、操作しないでください」の注意を出します。
- **監査の段の送信の扱い**: サイト（ページ）が自動でする通信のうち、読み取りでないものを、削除のほかは止めずに通すか（`PASS_EXCEPT_DELETE`）、すべて止めるか（`READ_ONLY`。読み取りだけ）です。**サイトの既定は「削除のほかを通す」です**（2026-10-29 から。新しいサイトと、表示の設定をまだ保存していないサイト。止めると、画面の部品が動かず、点検や答え合わせが「判定できない」になるためです）。前に「読み取りだけ」のまま保存してあったサイトは、そのままです（人が選んだのかを見分けられないためです）。
  - 変えるときは、同じ「表示の設定」の欄のチェック「ページが出す送信のうち、削除のほかを通す」で選びます。読み取りだけにするのは、人がこのチェックを外したときだけです。外すときは、ダイアログを出さず、切り替えた時点で保存します。もう一度通す側へ切り替えるときは、確認のダイアログ（「ページが出す書き込みの送信がサイトに届きます。削除と危険な語の送信は止めます。」）を出し、「通す」を選んだ時点で保存します（「やめる」なら切り替えず、保存もしません）。保存できなかったときは、チェックを元の値に戻します（表示の設定と同じ）。切り替えても、プロファイルの改訂と承認は変わらず、次に始めるジョブから使います（ジョブの開始のときに読み、ワーカーに渡します）。
  - 当てる作業: 監査・発見・READ の確かめと、書き込みの作業の中の、値を入れる前の画面・送る前の確かめの画面・答え合わせの画面です。書き込みの作業の中では、承認した送信先とその下のアドレスへの送信は通しません（登録が 2 件にならないためです）。値を入れた後と、押した後には当てません。ログインの確かめ・入口の確かめには当てません。
  - 既定なので、プロファイルの詳細の要点に「守りを緩めています」の印は出しません。ジョブの画面には、通したことの知らせを出さず、成功で終われば、読み取りだけのときと同じく次の画面へ移ります。通した数と内訳は、`run.json` の `safety.auditSend`（発見と READ の確かめは成果物の `auditSendPolicy`）と、HTML レポート・CLI の出力・ChatGPT 用のファイルに残ります。通すもの・止めるもの・限界は「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」を見てください。
- **認証の設定の画面の案**: 保存した設定がないときは、開始の URL の path（成功の画面の path と、読む範囲のパス）と、最後に成功した入口の確かめの案で欄を埋めます。観察した要求の下書きは、保存した設定があっても入れます。優先の順は「[観察した要求の登録](authenticated-audit.md#観察した要求の登録)」にあります。

### 自動ログイン（資格情報とログインの確かめ）

テスト環境のプロファイル（`TEST_AUTH_PASSIVE`）は、1 回目の点検で手でログインした後に、BeakSight が認証の方式を自動ログイン（`AUTOMATED_LOGIN`）に切り替え、そのとき入れたテスト用のアカウントの資格情報で、次から自動でログインします（BeakSight の画面では入れません）。自動ログインは Windows だけで使えます（Windows の暗号化（DPAPI）で資格情報を保存するため）。手順、結果ごとにすること、守りの範囲、残る危険は「[自動ログインの手順](automated-login.md)」にあります。

- **ログインの確かめは、ふだんの流れから外しました。** 自動ログインのプロファイルで「点検を始める」を押すと、点検の最初の自動ログインが、ログインできるかの確かめを兼ねます。ログインに失敗したら、点検は止まり、ジョブの画面に理由が出ます（画面は移りません）。画面からログインの確かめのジョブ（`LOGIN_CHECK`）を始める道はありません（ジョブの種類と、停止を解いた後の扱いは残ります）。
- **認証の設定**: 手動のログインの項目に加えて、自動ログインの項目があります。ユーザー名の欄・パスワードの欄・送信のボタンの CSS セレクタ（それぞれ、ちょうど 1 つの要素を指す、標準の CSS のもの。Playwright 独自の書き方は保存しません）と、ログインの失敗を見分ける 4 つの条件（資格情報の誤り、アカウントのロック、人の操作（MFA など）が必要、パスワードの期限切れ）です。セレクタは、切り替えのときに手でのログインの観察の案から入り、画面に出しません（人が直す欄はありません）。ログインの送信の回数は、自動ログインでは 1 回に固定です（画面では変えられません。アカウントのロックを避けるため）。誤りは、項目ごとに表示します。
- **資格情報の画面**（画面では「ID とパスワード」。自動ログインのプロファイルでは、プロファイルの詳細の「詳しい内容」の「ID とパスワードの画面を開く」から開きます）:
  - 要点に出すのは、保存してあるか、保存の場所、ログインする先（ホストだけ）、自動ログインを止めているか（理由と人がすることと回数の決まり）だけです。日時・改訂・Origin・暗号化の行は出しません。**ユーザー名を含めて、値は一度も画面に出しません。**
  - **新しく登録**: まだなければ、入力 3 つ（ID、パスワード、パスワードをもう一度）と主のボタン「登録する」を出します。パスワードは 2 回入れ、一致しなければ保存しません。どちらも 4 文字以上 256 文字までです（4 文字未満は、変更と入れ直しでも保存しません。前に保存した値は今どおり使えます。「[資格情報を登録する](automated-login.md#4-資格情報を登録する)」）。
  - **変更**（「詳しい内容」の中）: 「ユーザー名を変える」「パスワードを変える」を選び、選んだ方の欄だけを入れます（パスワードは 2 回）。選ばなかった方は、保存してある値をそのまま使います。どちらも選ばないときと、空の欄は、保存しません（空の欄は「消す」の意味になりません）。
  - **入れ直し**: 保存したログインの Origin が、今の認証の設定と違うときは、一部の変更はできないので、入れ直しの 3 欄で両方を入れ直します。
  - **自動ログインの停止も解く**: 自動ログインを止めているときだけ、変更の画面に出る明示の選択です。資格情報を変えただけでは、停止は解きません（ロックや回数の制限は、サーバの側で続いているかもしれないため）。
  - **削除**（「詳しい内容」の「保存した ID とパスワードを消す」）: 確かめのダイアログの後に削除します。削除すると、もう一度登録するまで、自動ログインは始められません。
  - そのプロファイルのジョブ（監査など）が動いている間は、変更と削除をしません（理由を表示します）。
  - **ここに本番のパスワードを書かないでください。** テスト環境のテスト用のアカウントだけを使います。ブラウザが、入れたパスワードの保存を勧めることがあります（BeakSight からは止められません）。保存しないでください。
  - 資格情報は、リポジトリの `local/secrets/<profileId>.credential.json`（Git の管理の外）に、ユーザー名とパスワードを別々に暗号化して保存します。フォルダの権限は、今の Windows の利用者だけに絞ります。復号するのは、ログインする監査のワーカーだけです。
- **ID とパスワードの画面から切り替えるとき**（ふだんの流れではありません。手でのログインの後に切り替わらなかったときだけ）: 確認のダイアログに、パスワードを入れる先（「手でログインしたときと同じ、◯◯ のログインの画面」。ホストだけ）、テスト用のアカウントだけを入れること、保存の場所（このパソコンの中、今のユーザーだけが開ける形）、回数の決まり（5 分に 1 回、1 日 10 回まで。うまくいかないと止まり、確かめるまで再開しない）を出します。
- **上限**: 自動ログイン（監査の前のログインを含む）は、1 回のジョブでログインの送信が 1 回だけ、同じプロファイルで 5 分以上あけ、24 時間に 10 回までです。サーバが回数の制限（HTTP 429）で示した待つ時間（`Retry-After`。上限 24 時間）も守ります。間隔の中は、プロファイルの詳細に主のボタンを出さず、「◯◯ から始められます。」と出します。
- **止めた状態**: ログインを送った後に成功以外で終わると（資格情報の誤り、ロック、MFA、期限切れ、429、結果が分からない、など）、アカウントのロックを避けるため、そのプロファイルの自動ログインを止めます。ログインを送る前に止まった場合（フォームの確かめで止めた、など）は止めません。止めているときは、プロファイルの詳細の要点に理由を出し、二次のボタン「自動ログインの停止を解く」で、ログインの確かめの画面（画面では「自動ログインの再開」）を開きます。その画面に止めた理由と人がすることを表示します。テスト環境のアカウントを確かめた後に、「確かめたので再開する」→ 確かめのダイアログの「再開する」で解きます。解いても、5 分の間隔と `Retry-After` は守ります。
- **ジョブの画面**: 「詳しい内容」の「自動ログイン」の欄に、結果、ログインを送信したか、サーバが示した次に試してよい日時（429 のとき）、フォームの確かめで止めた理由を表示します。結果ごとに、人がすること（資格情報を変更する、テスト環境の管理者にロックの解除を頼む、MFA のあるアカウントは使えない、手でログインして観察し直す、時間をおく、など）を表示します。
- **監査の開始**: 自動ログインのプロファイルの開始の画面の要点には、次の点検から BeakSight が自動でログインすることと、ログインに失敗したら点検が止まることを書きます。始められないとき（止めている、間隔の中など）は、理由と次に始められる日時を書きます。
- **環境の状態**: 「資格情報の暗号化（自動ログイン）」に、使える・使えない・この環境では使えない（Windows でない）を表示します。画面のサーバ（と `npm run setup:local`）は、起動のときに、資格情報のフォルダに残った書きかけの一時のファイルを消し、暗号化の往復を 1 回だけ確かめます（値は出しません）。使えなくても、画面のサーバは起動します（自動ログインを始められないだけです）。

### 操作の候補と READ の確かめ

認証つきの読み取りの監査（`TEST_AUTH_PASSIVE`）か、承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルで、ログインの後に、管理画面に「どんな操作があるか」を書き込みなしで洗い出し、読み取り（READ）の操作だけは実際に読んで確かめます。画面では「操作さがし」「見るだけの確かめ」と出ます。ふだんは、「点検を始める」のまとめて実行の 2 つ目・3 つ目の段として自動で行います（ログインは最初の 1 回だけ）。手順、候補と結果の見方、サイトへの読み込み、守りの範囲、確かめていないことは「[操作の候補の発見と READ の確かめの手順](discovery-and-read-check.md)」にあります。単独で行うときは、プロファイルの詳細の「詳しい内容」の「操作さがしの結果を見る」「見るだけの確かめを開く」から開きます。始めるには、監査と同じく、認証の設定（自動ログインなら資格情報も）が要ります。始められないときは、理由を表示して、開始のボタンを出しません。

- **発見**（画面「操作さがし」）: 要点に、書き込める操作（登録と更新の形）の数か、見つかった操作の数を出します。主のボタンは 1 つです（承認した書き込みのモードで、シナリオにできる登録の形があれば「書き込みの手順を作る」、もう作ってあれば「書き込みの手順を見る」、ほかは「もう一度さがす」。まだ一度もしていなければ「操作さがしを始める」）。単独の発見のジョブは、終わっても自動では移りません（ジョブの画面の主のボタン「操作さがしの結果を見る」で開きます）。BeakSight がログインしてから、認証の設定の読む範囲の管理画面を、設定のファイルの読み込みの間隔とページの上限で読み、フォームとボタンを集めて分類します。フォームの送信、入力、クリックはしません。
  - **詳しい内容**: 前回の発見の結果（読んだ画面の数、読まなかった理由ごとの数、読み切れなかった画面と理由）と、見つかった操作の、画面（アドレスの後ろ）ごとの分類だけです。
  - **画面に出さないもの**: 送り方（GET・POST と `_method`）、送信先、ドリフト、分類の理由、入力の欄の詳細、状態の欄の印は、画面に出しません。成果物の `discovery.json` に残ります（読み方は「[候補の見方](discovery-and-read-check.md#候補の見方)」）。**入力の値、CSRF のトークン、hidden の値、選択肢の label は、成果物にも画面にも出しません。**
  - **分類**: 読み取り（READ）だけが READ の確かめに使えます。登録（CREATE）の候補は、プロファイルの詳細の一覧「登録・更新を試せる画面」の行になり、チェックの保存でシナリオの下書きになります。承認した書き込みのモードのプロファイルでは、主のボタン「書き込みの手順を作る」でも下書きを作れます（ふだんの流れではありません。「[書き込みのシナリオ](#書き込みのシナリオ承認と撤回)」）。候補ごとにシナリオを作るボタンはありません。
- **READ の確かめ**（画面「見るだけの確かめ」）: ふだんの流れ（書き込みを含む）からは開かない、任意の画面です。書き込みの照合に使う定義（照合の専用の定義。`readVerification.verificationOnly`）は、BeakSight が発見の候補から作り、単独の READ の確かめのジョブでもまとめて実行でも読みません。
  - **定義を作る**: 「画面の読み方を決める」から、送る値と期待を決めます。送る値の入力の欄は、その候補の値を送れる欄（名前があり、見えていて、読み取り専用でも無効でもない欄。パスワードとファイルの欄は、名前にかかわらず除きます）だけです。値を入れた欄だけを送ります。期待は「行の数がちょうど」「行の数が少なくとも」「本文が文を含む」「詳細の項目の値が等しい」から選びます（1 件以上 10 件まで）。1 つのプロファイルの定義は 20 件までです。
  - **送る値は、テスト環境のテスト用の値だけにしてください。** 値は管理データにそのまま保存し、この画面に表示します。秘密に見える名前（token、session、code、state、key など）の欄に値を入れると、保存せずに、その欄に理由を表示します。送る値の名前か値に危険な語（削除、取り消し、一括、無効、delete、cancel など）があるときも、同じく保存せずに、その欄に理由を表示します。
  - **保存の確かめ**: 保存のときに、サーバが、最後の発見の結果の候補に照らして確かめ直します。拒んだときは、理由を項目ごとに表示します（秘密に見える名前、危険な語、送れない欄、READ でない候補、最後の発見の結果にない候補、件数の上限、形の誤り）。
  - **変える・削除する**: 定義の画面から行います。ほかの画面で先に変えられていたときは、保存せずに知らせます（読み込み直してから、もう一度変えます）。削除は、確かめのダイアログの後に、定義を一覧から外します（前の結果の記録は残ります）。取り消したプロファイルでは、定義を作ったり変えたりできません（削除はできます）。
  - **始める**: 「見るだけの確かめを始める」で、ジョブ（種類「READ の確かめ」）を始めます。定義が 1 件もなければ、理由を表示して、開始のボタンを出しません。BeakSight がログインしてから、定義ごとに、対象の候補がまだ同じ形で READ であることを確かめ、送る値で GET の URL を組み立てて読み（フォームの送信はしません）、結果を期待と照らします。
  - **結果**: 定義ごとの結果（一致、不一致、判定できない、読む前に止めた、画面が変わった、READ でなくなった）と、期待ごとの結果の要約は、「詳しい内容」の中です。HTTP の状態などの技術の値は、`read-evidence.json` に残ります。表の全体は写しません。
- **ジョブの画面**: スクリプトで送るログインの設定のプロファイルでは、「詳しい内容」に欄「ログインの後の読み取りの数」（通した登録した読み取りの手続きの呼び出し、止めた token の更新、止めたそのほかの読み取りでない送信、サービスがログインの状態を受け付けなかった応答（401）、サービスへの要求の上限に「届きました」か「届いていません」か）を出します（「[SPA の画面の発見と READ](discovery-and-read-check.md#spa-の画面の発見と-read)」）。操作の候補の発見と READ の確かめのジョブは、進み具合の知らせを送りません。成果物の `discovery.json` と `read-evidence.json` は、「詳しい内容」のダウンロードで取り出せます。どちらのジョブも、止まったら再開せず、もう一度始めます。

### 書き込みのシナリオ（承認と撤回）

承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルだけで使えます（画面では、シナリオは「書き込みの手順」、承認は「書き込みの OK」と出ます）。ほかのモードのプロファイルには、シナリオへの案内を出さず、サーバも作成を拒みます。シナリオは、最後の発見の結果の、登録（CREATE）か更新（UPDATE）の候補 1 つです。**承認しただけでは書き込みは始まりません。** 承認は、書き込みを許す条件（版、上限、期限、副作用の確認、検証の指定）を記録します。ふだんは、一覧「登録・更新を試せる画面」のチェックが、下書きと承認を 1 回で行い、書き込みは次の点検の最後の書き込みの段で行います（「[登録・更新を試せる画面](#登録更新を試せる画面)」）。この節の画面（下書き・承認・撤回のボタンとダイアログ）は、中身を確かめる・直すときの道です。単独の書き込みは、承認の後に、別の画面「書き込みを始める」から人が始めます（「[書き込みの実行](#書き込みの実行登録と更新)」）。手順、再承認が要る場合、上限と期限、守りの範囲、確かめていないことは「[書き込みのシナリオの承認の手順](scenario-approval.md)」にあります。

- **下書きを自動で作る**: 発見の画面の主のボタン「書き込みの手順を作る」を 1 回押すと、最後の発見の結果から、登録のシナリオの下書きをまとめて作ります（確認のダイアログはありません。下書きはサイトへ何も送らず、承認の前に中身を見られるためです）。作った結果は「書き込みの手順を N 個作りました。」の 1 行で知らせます。新しく作るものがなかったとき（ほかの画面で先に作ってあった、など）は「新しく作る書き込みの手順はありませんでした。」です。作るときに、BeakSight が次を自動で決めます（サイトには接続しません。承認・副作用の確認・書き込みは行いません）。
  - **0 件の一覧から作る**: シナリオが 0 件の一覧（画面「書き込みの手順」）にも、主のボタン「書き込みの手順を作る」があります。使える発見の結果があれば、発見の画面と同じく下書きを作ります。使える結果がない（まだ発見していない、発見の後にプロファイルを変えた、書き込める形がない）ときは、このボタンで発見を始めます。
  - **書き込みのモードへの切り替えの後**: 切り替えの前の発見の結果から作れます（チェックの保存の切り替えで進んだ改訂は、発見の結果の古さの判定では同じ改訂とみなします）。切り替えのほかにプロファイルを変えたときは、発見をやり直します。
  - **入力の規則**: シナリオを保存するたびに、BeakSight が推して付けます。推せない欄があるときだけ、シナリオの詳細の要点に 1 行（「入れる値を決められない欄があります。…」）が出て、「詳しい内容」の「入れる値の決まりを開く」で人が決めます（「[入力の規則とデータの生成](data-rules.md)」）。
  - **検証の指定**: 結果の判定（API は応答の状態の番号、フォームは構造の判定）、登録の ID の取り方、照合の READ（照合の専用の定義）を、観察から決めます。決められないときは、作った時点で、要点に理由を 1 行出します（例: 「作ったデータを後で探せないので、この登録で作ったデータの更新は試せません（登録は試せます）。」「答え合わせのしかたを決められなかったので、…書き込みを始められません。」）。書き込みの後に初めて「判定できない」を出すことはしません（「[検証の指定](approved-create.md#検証の指定)」）。
  - **READ の定義を人が作って選ぶ手順は、書き込みの流れから外しました。**
  - 更新のシナリオは、この下書きでは作りません。ふだんは、一覧のチェックの保存か、点検の中の自動の下書きで、BeakSight が変える欄を決めて作ります。手で作るときは、作ったデータの一覧の主のボタン「更新を試す」から、変える欄を人が選ぶ作成の画面へ進みます（「[監査済みデータの台帳](#監査済みデータの台帳)」）。
- **作成と変更の画面**: 自動の下書きの更新の案内か、作ったデータの一覧の「更新を試す」から、作成の画面を開きます。送る欄（候補の、見えていて、読み取り専用でも無効でもない欄だけ。秘密に見える名前の欄、危険な語の欄、パスワードとファイルの欄、`_method` の欄は選べず、理由を示します）と、更新なら欄ごとの役割（変える・保つ。人が必ず選びます）を決めます。手で決める欄（検証の指定、上限、承認の期限など）は、作成の画面の「詳しい内容」の中です。上限は、1 回の Run は 1 件の決まった値で表示だけ、累積は 20 件の既定以下、承認の期限は 30 日の既定以下です。**副作用の確認**（テスト環境のレコードだけ、メール・SMS・外部の通知が送られない、決済や外部のサービスに及ばない、削除・無効化・取り消しに当たらない、の 4 項目）は、この画面になく、承認のダイアログで確かめます。保存のときに、サーバが最後の発見の候補に照らして確かめ直し、拒んだときは理由を項目ごとに表示します。変えるときは、シナリオの詳細の「詳しい内容」の「変える」から開きます（候補は変えられません）。保存すると版が 1 つ進み、下書きに戻ります（前の承認は引き継ぎません）。
- **一覧**（画面「書き込みの手順」）: シナリオごとの種類、画面、状態（下書き・承認済み・要再承認・期限切れ・撤回済み）など。0 件のときは、主のボタン「書き込みの手順を作る」（上の「0 件の一覧から作る」）。
- **詳細**: 要点に、状態の文と、決められなかったこと・写したことの 1 行、主のボタン 1 つ（下書き・要再承認なら「書き込みの OK」、承認が有効なら「書き込みを始める」）。「詳しい内容」の中に、状態、「変える」「入れる値の決まりを開く」「書き込みの OK を取り消す」、画面と送る欄、推測した項目（「推測した項目（確かめてください）」）、書き込みの履歴があります。要求の形・digest・版と承認の履歴・入力の規則の中身は、画面に出しません（管理データと成果物に残ります）。
- **承認する**: 主のボタン「書き込みの OK」で確認のダイアログ（開くと取り消しにフォーカス）を開き、「書き込みの OK を出す」を押したときだけ承認します。ダイアログには、何を・どこへ・何件（「◯◯の画面で、作り物のデータを 1 件登録します。送ったら取り消せません。」の形）、ほかへの影響の 4 つの約束（現在形。4 つとも本当か確かめてから押し、1 つでも違えばやめる）、推測した項目が残っていればその印を出します。この 1 回の押下で、副作用の確認の 4 項目を確かめたことにします（まだ確かめていない版は、確かめた次の版を作って、その版を承認します）。画面に出した版と承認の digest をサーバが今の事実から求め直し、違えば「画面が古い」として承認しません（読み込み直してから、もう一度承認します）。承認者は `LOCAL_OPERATOR` と記録します。
- **再承認**: 承認の後に、シナリオの版、プロファイル（どの項目の編集でも）、認証の設定（自動ログインなら、資格情報の版と、資格情報の登録・変更・削除の記録も。削除して登録し直しても再承認になります）、ターゲットの設定のファイルの内容、候補（入力の規則か分類）、入力の規則の参照、照合の READ の定義のどれかが変わると、状態は「要再承認」になり、主のボタンが「書き込みの OK」に戻ります。期限を過ぎると「期限切れ」です。どれも、内容を確かめてから、もう一度承認します。承認の digest の版が上がったとき（フォームの判定を構造の判定にした v5）も、承認し直しになります。
- **承認を撤回する**: 承認済みのシナリオだけ。「詳しい内容」の「書き込みの OK を取り消す」から、確認のダイアログの後に撤回します。撤回すると、まだ消費していない実行の許可は無効になり、送っていない件数の予約は返ります。送った書き込みは取り消せません。撤回の記録は残ります。
- 取り消したプロファイルでは、シナリオを作る・変える・承認するはできません（記録は見られます。撤回はできます）。
- プロファイルが指す設定のファイルか、資格情報のメタデータ（版）を読めないときは、承認の状態を確かめられないことを表示し、承認しません。

### 入力の規則（送る値の作り方）

画面では「入れる値の決まり」と出ます。ふだんは、シナリオの保存のたびに BeakSight が推して付けるので、開きません。推せない欄があるときだけ、シナリオの詳細の「詳しい内容」の「入れる値の決まりを開く」から開きます。承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルのシナリオだけで、編集とデータの例を出します（ほかのモードでは出さず、サーバも保存を拒みます）。**この画面からは書き込みを実行しません。データの例もサイトに送りません。** 値は LLM を使わず、欄の型と制約、小さな辞書と業務テンプレート（顧客・予約・商品）、人が入れた値の一覧から、決まった手順で作ります。

- **状態**: 入力の規則の状態（未設定・すべて決まった・不足あり）。
- **送る欄の規則**: BeakSight が作り方を決められなかった欄を先に見せ、決められた欄はたたんだ区画に入れます。送る欄ごとに、状態（決まった・規則の入力が要る・決まりがぶつかる・外部到達で止めた）と、その理由の説明と手順を示します。送る欄でない必須の欄も、理由とともに並びます。
  - 「意味の種類」で、人の規則を決めます（「自動」は、業務テンプレートか汎用の規則で決めます。選べる種類は、欄の型に合うものだけです）。作り方（欄の型と制約から・業務テンプレートと辞書から・人が入れた値の一覧から）と、値の一覧（1 行に 1 つ）、範囲（最小・最大・刻み）を決めます。
  - 人が入れた値は、管理データにそのまま残ります。秘密に見える名前の欄には入れられません（保存を拒みます）。
  - メールアドレスは、配送されない予約のドメイン `example.invalid` の宛先だけ、電話番号は `090-0` で始まる形（ハイフンなしは `0900` で始まる 11 桁）だけを作ります。どちらも、副作用の確認「メール・SMS・外部の通知が送られない設定です」を確かめるまで作りません。この確認は、承認のダイアログの「書き込みの OK を出す」の 1 回の押下で入ります。そのため、承認の前のこの画面では、承認のときに確かめる印を付けて、作れる欄として出します。住所と URL の欄は、人が入れた値だけを使います。通知・配信を求める欄は、送らない側に固定します（送らない側が選べなければ止めます）。
- **欄どうしの関係**: 終了は開始より後、合計は単価 × 数量、フリガナは氏名と同じ人。人が決めた関係に、業務テンプレートの既定の関係を足して当てます。
- **一意にする欄の組**: 選ばなければ、業務テンプレートの既定の組を使います。
- **データの例（送りません）**: 送る欄すべての作り方が決まったときだけ、この画面のための決まった値で作った例を 3 つ示します。実際の書き込みでは、実行の許可ごとに別の値になります。
- **保存する**: 確認のダイアログ（開くと取り消しにフォーカス）で「保存する」を押したときだけ保存します。保存すると、入力の規則の新しい版ができ、シナリオに付け直します。シナリオの版が 1 つ上がって下書きに戻るので、承認していた場合は、もう一度承認が要ります。ほかの画面で先に変えられていたときは、保存せずに知らせます（読み込み直してから、もう一度保存します）。
- 送る欄すべての作り方が決まっていないシナリオには、実行の許可を出しません。

### 書き込みの実行（登録と更新）

承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルのシナリオだけで使えます。書き込みを始められるのは、承認が今も有効なシナリオだけです。ふだんの書き込みは、点検の最後の書き込みの段で、この節と同じ確かめ（実行の許可、上限、送る直前の確かめ、照合）を通して行います。この節の画面とダイアログは、単独の書き込みのときだけ使います。詳しい決まりは「[承認された登録の手順](approved-create.md)」と「[承認された更新の手順](approved-update.md)」にあります。

- **開く**: シナリオの詳細の主のボタン「書き込みを始める」から、画面「書き込みを始める」（`/scenarios/<profileId>/<scenarioId>/write`）を開きます。
- **始める前に確かめること**: 要点に、何を・どこへ・何件かの文と、始められないときの理由（次に始められる時刻を含む）を出します。送る欄（登録）か更新するレコード・変える欄・保つ欄（更新）、1 回の Run で 1 件、累積の上限（使った件数と残り）、連続の上限（最後の書き込みから 5 分あける・24 時間に 5 件まで）、外部への通知（副作用の確認）、承認の状態は、「詳しい内容」の中です。検証の指定に決めていない項目があるときは、始められない理由として出します。
- **始める**: 始められるときだけ、主のボタン「書き込みを始める」を出します。押すと確認のダイアログ（「書き込みを始めますか」）が開きます。ダイアログの「書き込みを始める」を押したときだけ、実行の許可を出し、書き込みのジョブを始めて、ジョブの画面へ移ります。「やめる」を押すと何もしません。始めた後は、送る直前の確かめで止まらない限り、送信を取り消せません。承認（「書き込みの OK を出す」）と開始の確認（「書き込みを始める」）は、それぞれ 1 回残ります。
- **拒まれたとき**: 理由と手順を出します。承認が無効になった理由があれば並べます。
- **結果**: ジョブの画面の要点に結果の 1 行（「書き込みが終わりました。サイトに入ったことを確かめました。」など）と、主のボタン「結果を見る」（書き込みの報告）を出します。照合済み（`VERIFIED`）で終わると、シナリオの詳細へ自動で移ります（登録に続けて更新を始めたときは、その更新のジョブの画面へ）。結果が分からない（`UNKNOWN`）ときは「送ったかどうか分かりません。テスト用のサイトでデータがあるか確かめてください。」を出し、画面を移しません。照合できていない（`PARTIAL`）ときも移しません。書き込みの後の要点には「作ったデータは消しません。片付けはテスト用のサイトの管理者に頼んでください。」も出します。「詳しい内容」の「書き込みの結果」に、結果（照合済み、照合できていない、結果が分からない、登録されなかった、送らずに止めた）、理由、送信の状態、止めた理由、応答の判定、登録の ID（更新は対象のレコードと取れた ID）、照合の READ、予約の締め、日時、送った値（合成のテストデータ）を出します。送る前の確かめで止めた（`PRECHECK_FAILED`）ときは、具体的な理由（台帳が知る保つ値と違う、前の値と違う、画面を読めない、同じ値がもうサイトにあるので結果を確かめられない、など。`action-run.json` の `precheckDetail`）と次にできることを出します。
- **書き込みの履歴**: シナリオの詳細の「詳しい内容」の「書き込みの履歴」に、新しい順に、記録した日時、結果、理由、更新の対象のレコード、報告（開くリンクか「配らない」）などを出します。
- **更新の前後の差分**: 更新のジョブでは、変えた欄の前の値と新しい値と、更新の後の照合の一致を出します。保つ欄は、一致したかだけを出します（値は記録しません）。
- **書き込みの報告**: 親の確かめに通った報告だけ、主のボタン「結果を見る」と、「詳しい内容」の報告（`action-report.html`）を開くリンクと ZIP のダウンロードを出します。通らない・確かめていないときは、報告を配らず、その理由を出します（「[書き込みの報告](output.md#書き込みの報告)」）。

### 監査済みデータの台帳

画面では「作ったデータの一覧」と出ます。プロファイルの詳細の「詳しい内容」の「作ったデータの一覧を開く」から、画面（`/ledger/<profileId>`）を開きます。承認した書き込みのモードのプロファイルだけで行を出します（ほかのモードでは理由を出します）。読み方は「[リスクと監査の記録](risks-and-audit-logs.md#監査済みデータの台帳の読み方)」にあります。

- **要点**: 作ったデータの数と、行（「何を作ったか」「いつ」「更新したか」）、主のボタン「更新を試す」（更新できるデータがあるとき。ふだんの流れでは使いません）。「更新を試す」は、台帳と更新の画面の型を前もって選んだ更新のシナリオの作成の画面を開きます。変える欄は人が選びます（「[承認された更新の手順](approved-update.md)」）。照合の READ と登録の ID の型は、台帳の登録のシナリオから写します。
- **ID の取れない登録**: フォームの登録で登録の ID を取れなかった回（`PARTIAL`）は、後でそのデータを探せないので、その登録からは更新を試せません。
- **詳しい内容**: データの ID と照合の結果、シナリオごとの累計の件数と上限。送らずに止めた回は入れません。送ったか分からない回は入れます。実行の許可の ID・digest・ジョブと Run の ID・シナリオの ID と版は、画面に出しません（管理データに残ります）。
- **BeakSight は、登録したデータを削除も復元もしません。** テスト環境のデータの片付けは、この台帳をもとに、テスト環境の管理者が行います。
- 台帳は画面だけです。ファイルへの書き出しはありません。

### 画面のサーバが落ちたとき

- 画面のサーバが落ちると（強制終了を含む）、ワーカーと、ワーカーが動かしていた Chromium も止まります。
- 次に画面のサーバを起動したときに、そのジョブを「中断」（理由: 画面のサーバが、監査の途中で終わった）として記録し、コンソールにも知らせます。
- 同じプロファイルで「点検を始める」を押すと、既定で同じ Run の続きから再開します（CLI で同じコマンドを実行したときと同じ再開の仕組みです。「[中断と再開](resume.md#中断と再開)」）。

## 守り

管理画面は、このコンピュータの中から、起動した本人だけが使う前提で、次のように守ります。

- **待ち受けは `127.0.0.1` だけです。** ほかのコンピュータ（LAN を含む）からは繋がりません。設定でも変えられません。さらに、要求を受けた接続の手元のアドレスが `127.0.0.1` でなければ、421 で拒否します（Host の値は送る側が偽れるため）。
- **Host の確かめ**: `http://127.0.0.1:<port>` 以外の名前で来た要求（`localhost` を含む）は、421 で拒否します（DNS rebinding の対策）。
- **合言葉と cookie**: コンソールの URL の `token` が正しければ、`HttpOnly`、`SameSite=Strict`、`Path=/` の cookie に替え、`token` を除いた URL へ移します（303）。cookie も `token` もない要求と、誤った `token` は 401 で拒否します（画面、Server Function、static のファイルのすべて）。
- **CSRF**: 画面の保存と監査の開始・停止の操作（資格情報の登録・変更・削除、自動ログインの停止の解除、操作の候補の発見と READ の確かめの開始、READ の確かめの定義の保存と削除、シナリオの作成・変更・承認・撤回、入力の規則の保存、書き込みの開始を含む。Server Function）は、同じ Origin からの要求だけを受けます（`Sec-Fetch-Site`、なければ `Origin` で確かめ、違えば 403）。管理データへの書き込みは POST の Server Function だけで行います。
- **入力の確かめ**: 画面からの入力は、サーバで JSON Schema（`schemas/control/`）とプロファイルの決まり（認証の設定は、その決まり）で確かめ直してから保存します。監査の開始は、開始の直前に、プロファイル（有効か、改訂が画面で読んだものと同じか、今実行できる監査モードと認証の方式か）と設定のファイルと、認証つきの監査では認証の設定を確かめ直します。
- **応答の header**: すべての応答に、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cross-Origin-Opener-Policy: same-origin`、`Content-Security-Policy`（`default-src 'self'`、script は要求ごとの nonce、`frame-ancestors 'none'` など。`'unsafe-inline'` と `'unsafe-eval'` は使いません）を付けます。

## 成果物の取り出し

ジョブの詳細のリンクは、`/artifacts/<ジョブの ID>/<Run のディレクトリの中の相対パス>` を開きます（GET だけ。ほかのメソッドは 405）。

- 配るのは、そのジョブの Run のディレクトリ（出力先は、プロファイルの設定のファイルの `output.directory`）の中の、許可の一覧のファイルだけです: `run.json`、`audit.json`、`report.html`、操作の候補の発見の `discovery.json`、READ の確かめの `read-evidence.json`、ChatGPT 用のバンドルの ZIP、`audit.json` が参照するもの（ページの `page.json` と `visible-text.txt`、スクリーンショット）。それ以外（`checkpoint/` の中、参照されていないファイル、`..` や符号化した区切り、Windows の別名やデバイス名など）は 404 です。
- 書き込みのジョブの報告の 4 つ（`action-report.html`、`action-evidence.json`、`approval-summary.json`、書き込みのバンドルの ZIP `beaksight-action-bundle_YYYYMMDDHHmmss.zip`）は、親の確かめ（報告の確かめ）が「確かめ済み」のジョブだけ配ります。ほかのジョブでは、ファイルがあっても 404 です。ZIP は、`action-run.json` の終わりの時刻から決まる名前の 1 つだけです。2 つの JSON は、配る前に、スキーマと、文書のジョブの ID がそのジョブであることを確かめ直します。`action-run.json` は配りません（画面の書き込みの結果で示します）。
- ファイルは、リンク（シンボリックリンク、junction）をたどらずに、Run のディレクトリの中にあることを確かめてから読みます。
- `report.html` と `action-report.html` は、script を動かさない CSP（`sandbox allow-same-origin`、`default-src 'none'`、`img-src 'self' data:`、レポートの `<style>` だけを SHA-256 の値で許す `style-src`）で返します。`allow-scripts` は付けないので、レポートの中に script があっても動きません。`allow-same-origin` は、レポートの中の相対のリンク（スクリーンショットなど）を開くときに、合言葉の cookie（`SameSite=Strict`）を送るために付けています（付けないと 401 になります）。
- `run.json`、`audit.json`、`discovery.json`、`read-evidence.json`、`action-evidence.json`、`approval-summary.json`、ZIP は、ダウンロード（`Content-Disposition: attachment`。ファイル名は ASCII の決まった形）で返します。
- Host、待ち受けのアドレス、合言葉の cookie の守りは、成果物にも同じように掛かります（cookie がなければ 401）。

## 受け入れる危険（守りの範囲の外）

- **同じコンピュータで動くほかのプログラム**は、管理データのファイル（`local-data/`）を直接読み書きできます。画面のサーバの守りは、画面のサーバへの要求を守るもので、ファイルの直接の読み書きは守りの範囲の外です。
- **cookie は port で分かれません。** 合言葉の cookie は、同じコンピュータの `127.0.0.1` のほかの port で動くサーバにも送られます。ほかの port の画面からの保存の操作は CSRF の確かめで拒否しますが、管理画面を使うあいだは、信頼できないローカルのサーバを動かさないでください。

## 開発のサーバ

画面を作る人のための、変更をすぐに反映する開発のサーバです。

```powershell
npm run ui:dev
```

- 本番の起動と同じ守り（`127.0.0.1` だけ、Host、合言葉と cookie、CSRF、応答の header）を掛けます。
- Vite の preview（`vite preview`）では起動できません（守りを通らないため。説明を表示して終了コード 1 で止まります）。画面は `npm run ui` で起動します。
- 待ち受けのアドレスは変えられません。`npm run ui:dev -- --host`（`0.0.0.0`、`::`、`localhost` などを含む）のように待ち受けのアドレスを指定すると、説明を表示して起動しません（終了コード 1）。実際に待ち受けたアドレスも確かめ、`127.0.0.1` でなければ止めます。port の使用中も、説明を表示して止まります。コンソールに `BeakSight 管理画面（開発）: http://127.0.0.1:<port>/?token=…` を表示します。
- 待ち受けを始めたときに、同じ管理データを準備し、前のサーバで終わっていなかった監査を「中断」として記録します。
- 画面から監査を動かすには、先に `npm run build` で監査の本体をビルドしておきます（開発のサーバは、監査の本体をビルドしません。ワーカーは `dist/worker/audit-worker.js` です）。
- 止めるとき（Ctrl+C）は、本番と同じく、動いている監査を止めてから終わります（2 回目の Ctrl+C で、待たずに終わります）。
- ブラウザに配るファイルは、画面が読み込む範囲（`apps/local-ui`、`src/presentation`、`src/core`、`src/control`、依存のパッケージ）に絞ります。`local/`、`artifacts/`、`local-data/`、`.git` などは配りません。

## 検証のスクリプト

| コマンド | 内容 |
| --- | --- |
| `npm run build:ui` | 画面をビルドします（`apps/local-ui/dist/`）。 |
| `npm run typecheck:ui` | 画面のコードの型チェックを行います（`build:ui` の後。生成の route の表を使うため）。 |
| `npm run test:ui` | 画面とサーバのテスト（`apps/local-ui/tests/`）を行います（`build:ui` と `build` の後。画面から動かす監査のテストは、監査の本体のビルドの出力 `dist/` を使います）。 |
| `npm run verify:ui` | `build:ui`、`typecheck:ui`、`test:ui` を順に行います。 |
| `npm run verify:all` | `verify`（CLI の型、テスト、ビルド）と `verify:ui` を順に行います。 |

- 画面のテストは、リポジトリの外の一時のフォルダに画面（と監査の本体のビルドの出力 `dist/`）を写して起動します。リポジトリの `local-data/` は作りません。監査は、テストの中で起動する 127.0.0.1 の小さなサイトだけを対象にします。ブラウザは headless の Chromium だけを使い、外部のサイトにはアクセスしません。
- `apps/local-ui/src/routeTree.gen.ts` は、ビルドと開発のサーバが作る生成のファイルで、Git の管理の外です。

## この画面でできないこと

- CLI で始めた Run の一覧（作業の履歴（実行履歴）には、画面から始めた作業だけを表示します）。
- 削除（DELETE）・初期化・復元の書き込み、1 回の Run で 2 件以上の書き込み、複数の段のシナリオ（登録してから更新する、など）。
- 一覧の画面の「編集」などから開く入力で行う更新（「[承認された更新の手順の API の更新](approved-update.md#api-の更新)」）。
- 監査済みデータの台帳の、ファイルへの書き出し。
- CLI からの認証つきの監査、操作の候補の発見、READ の確かめ、書き込み（どれも画面からだけ動かせます）。Windows 以外での自動ログイン。
- 管理データの消去、作り直し、バックアップと復元（手で名前を変えれば、次の準備で新しく作られます。「[管理データの扱い](local-setup.md#管理データの扱い)」）。
- ほかのコンピュータからの利用、複数の人の権限の管理。
