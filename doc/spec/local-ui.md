# 管理画面（ローカル）

このコンピュータの中だけで動く管理画面の、起動のしかた、画面と操作、守りの範囲、開発と検証のスクリプトです。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 管理画面では、監査プロファイルの登録・更新・取り消し、公開の監査（読むだけ）と認証つきの読み取りの監査（手動のログインと、Windows での自動ログイン）の開始・進み具合の表示・停止・結果の閲覧、自動ログインの資格情報の保存とログインの確かめ、操作の候補の発見と READ の確かめ、書き込みのシナリオの承認と撤回、入力の規則、承認された登録（CREATE）と更新（UPDATE）の開始と結果と報告、監査済みデータの台帳、環境の状態を扱えます。CLI の監査（`run`、`validate-config`）は、管理画面とは別に、これまでどおり動きます。3 つのモードを通して使う順は「[通しの使い方](end-to-end-usage.md)」にあります。

## 画面の起動

管理データを準備してから（「[管理データの準備](local-setup.md)」）、画面を起動します。

```powershell
npm run setup:local
npm run ui
```

- `npm run ui` は、監査の本体（`npm run build`。画面から動かす監査のワーカーが使う `dist/`）と画面（`npm run build:ui`）をビルドしてから、画面のサーバを起動します。起動の初めに、`npm run setup:local` と同じ準備を行うので、`setup:local` を忘れても、正しく準備してから起動します。
- 起動のときに、前の画面のサーバで終わっていなかった監査を「中断」として記録し、コンソールに知らせます（「[画面のサーバが落ちたとき](#画面のサーバが落ちたとき)」）。
- 起動のときに、自動ログインの資格情報のフォルダに残った書きかけの一時のファイルを消し、資格情報の暗号化を使えるかを 1 回確かめます（結果は「環境の状態」の画面。「[自動ログイン](#自動ログイン資格情報とログインの確かめ)」）。
- 準備ができなかったときは、`npm run setup:local` と同じ説明と取るべき手順を表示し、画面のサーバを起動せずに止まります（終了コード 1。「[困ったとき](local-setup.md#困ったとき)」）。
- 起動すると、コンソールに次のような URL を表示します。この URL をブラウザで開きます。

```text
BeakSight 管理画面: http://127.0.0.1:4317/?token=…
この URL は、この起動のあいだだけ使えます。ほかの人に渡さないでください。
```

- URL の `token` は、起動のたびに変わる合言葉です。ほかの人に渡さないでください。ログやファイルには書きません。
- **画面のサーバは、同時に 1 つだけ動かせます。** 同じ管理データ（`local-data/`）で、すでに画面のサーバが動いていると、2 つ目は待ち受けずに、動いている画面のサーバのプロセスの ID と port、取るべき手順（動いている画面のサーバを使うか、止めてから起動する）を表示して止まります（終了コード 1）。`npm run ui` と開発のサーバ（`npm run ui:dev`）の組み合わせも、`--port` の違う 2 つの起動も、同じ扱いです。このとき、2 つ目は、前の画面のサーバのジョブの記録を書き換えません。監査を画面全体で同時に 1 つだけにするためです（「[サイトへの負荷の決まり](#サイトへの負荷の決まり)」）。
  - どちらが動いているかは、管理データの中の 1 行（動いている画面のサーバのプロセスの ID、OS の起動の時刻、ハートビートの時刻）で判断します。画面のサーバは、ハートビートを 1 分ごとに書き換えます。画面のサーバが落ちてこの行が残っても、そのプロセスが終わっている、OS を起動し直した、ハートビートが 5 分より古い、のどれかなら、次の画面のサーバが取り直して起動します（CLI の Run のロックと同じ決まり）。
  - 前の画面のサーバが止まって見えて、次の画面のサーバがロックを取り直した場合も、前の画面のサーバの監査のワーカーが動いている（最後の合図から 20 秒以内）間は、次の画面のサーバはそのジョブを中断に直さず、新しい監査を始めません。ロックを失った前の画面のサーバは、自分の監査に止める要求を送り、60 秒の後も終わらなければワーカーを止めます。
  - 開発のサーバは、待ち受けを始めてから確かめるので、止まる前に一瞬だけ待ち受けます（token の URL は表示しないので、画面は開けません）。
- 待ち受けの port の既定は `4317` です。使用中なら、別の port を選ばずに、理由と取るべき手順を表示して止まります（終了コード 1）。別の port を使うときは、`npm run ui -- --port 4400` のように指定します。番号でない値や範囲の外の値（1〜65535 の外）も、説明を表示して止まります。
- 止めるときは、コンソールで Ctrl+C を押します。動いている監査があれば、そのことを知らせて止める要求を送り、今のページの監査を終えるまで最大 10 秒待ってから、管理データを閉じて終わります（待つ時間は名前つきの定数 `AUDIT_JOB_SHUTDOWN_WAIT_MS`）。待つ間にもう一度 Ctrl+C を押すと、待たずにすぐに終わります（そのときの監査は「[画面のサーバが落ちたとき](#画面のサーバが落ちたとき)」と同じ扱いです）。

## 画面と操作

左のメニューから、次の画面を選びます。キーボードだけでも操作できます。

| 画面 | できること |
| --- | --- |
| サイトとプロファイル | 登録した監査プロファイルの一覧（名前、環境、監査モード、認証の方式、状態、改訂、最後の更新、最後の Run）。「最後の Run」の欄には、最後の監査のジョブの状態と Run の状態（完了、一部未完了など）を表示します。今実行できるプロファイル（有効な、公開の監査のプロファイルと、認証の方式が手動のログインか自動ログインの認証つきの読み取りの監査のプロファイル）には「監査を始める」を、自動ログインのプロファイルには「ログインを確かめる」も置きます。 |
| 新しいプロファイル | プロファイルの登録。設定のファイル（`config/targets/` か `local/targets/` の JSON）を選ぶと、その場で設定の誤りを確かめて表示します。 |
| プロファイルの編集 | 項目を直して保存すると、改訂が 1 つ進みます。ほかの画面で先に保存された場合は、保存せずに知らせるので、読み込み直してからもう一度変更します。 |
| プロファイルの取り消し | 編集の画面の「このプロファイルを取り消す」から、確認のダイアログの後に取り消します。取り消しは元に戻せません。同じ名前（profileId）は使い直せないので、続けて使う場合は、別の名前で新しく作ります。 |
| 認証の設定 | 認証つきの読み取りの監査（ログインあり・読むだけ。`TEST_AUTH_PASSIVE`）か、承認した書き込みのモード（`TEST_APPROVED_WRITE`）で、認証の方式が手動のログインか自動ログインのプロファイルだけ。プロファイルの詳細の「認証の設定を開く」から開きます（「[認証つきの監査](#認証つきの監査ログインあり読むだけ)」）。 |
| 資格情報 | 自動ログインのプロファイルだけ（`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE`）。プロファイルの詳細の「資格情報を開く」から開き、テスト用のアカウントの資格情報を登録・変更・入れ直し・削除します（「[自動ログイン](#自動ログイン資格情報とログインの確かめ)」）。 |
| ログインを確かめる | 自動ログインのプロファイルだけ（`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE`。`TEST_APPROVED_WRITE` は、一覧ではなく、プロファイルの詳細から開きます）。保存した資格情報でログインだけを 1 回試します。止めた自動ログインを、確かめた後に再び許します。 |
| 操作の候補 | 認証つきの読み取りの監査か、承認した書き込みのモードのプロファイルだけ。プロファイルの詳細の「操作の候補を開く」から開き、管理画面のフォームとボタンを、読むだけで集めて分類します（「[操作の候補と READ の確かめ](#操作の候補と-read-の確かめ)」）。 |
| READ の確かめ | 認証つきの読み取りの監査か、承認した書き込みのモードのプロファイルだけ。読み取り（READ）の候補ごとに送る値と期待を決め、GET で読んで結果を照らします（「[操作の候補と READ の確かめ](#操作の候補と-read-の確かめ)」）。 |
| シナリオ | 承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルだけ。プロファイルの詳細の「シナリオを開く」から開き、登録（CREATE）・更新（UPDATE）の候補を「シナリオ」にして、内容を確かめて承認・撤回します。承認だけでは書き込みは始まりません（「[書き込みのシナリオ](#書き込みのシナリオ承認と撤回)」）。 |
| 書き込みを始める | 承認した書き込みのモードのプロファイルのシナリオだけ。シナリオの詳細の「書き込みを始める画面を開く」から開き、始める前に確かめる内容を見てから、登録（CREATE）か更新（UPDATE）を 1 件だけ始めます（「[書き込みの実行](#書き込みの実行登録と更新)」）。 |
| 監査済みデータの台帳 | 承認した書き込みのモードのプロファイルだけ。プロファイルの詳細の「監査済みデータの台帳を開く」から開き、BeakSight が登録したかもしれないデータの一覧と、シナリオごとの累計の件数を見ます（「[監査済みデータの台帳](#監査済みデータの台帳)」）。 |
| 監査を始める | プロファイルと設定のファイルの要点を確かめて、監査を始めます（「[監査の実行](#監査の実行)」）。 |
| 監査のジョブ | 1 つの監査の進み具合、停止、結果、成果物へのリンク（「[監査の実行](#監査の実行)」）。ジョブの種類（監査、ログインの確かめ、操作の候補の発見、READ の確かめ、登録の書き込み、更新の書き込み）と、自動ログインの結果、書き込みの結果と報告も表示します。 |
| 実行履歴 | 監査のジョブの一覧（新しい順。開始の要求の日時、プロファイル、ジョブの種類、ジョブの状態、Run の ID、Run の状態、終わり方、終わりの日時）。日時から、ジョブの詳細を開きます。 |
| 環境の状態 | Node.js の版、SQLite の版、管理データの場所と版、プロファイルの件数、整合性の確かめ（`quick_check`）、待ち受けのアドレス、資格情報の暗号化（自動ログイン）を使えるか。 |

- 保存できない値は、項目ごとに理由を日本語で表示します。
- 承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルでは、読み取りの監査（「監査を始める」）は実行できません。使えるのは、認証の設定、資格情報（自動ログイン）、ログインの確かめ、操作の候補の発見、READ の確かめ、書き込みのシナリオの承認・撤回、入力の規則、承認された登録と更新、監査済みデータの台帳です（「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。一覧に「監査を始める」を出しません。
- 認証つきの読み取りの監査（`TEST_AUTH_PASSIVE`）と承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルは、保存した後に、認証の設定を作ってから、監査や操作の候補の発見を始めます。モードを選ぶと、画面にもそう表示します。

## 監査の実行

画面から動かせるのは、公開の監査（読むだけ。`PUBLIC_PASSIVE`）と、認証つきの読み取りの監査（ログインあり・読むだけ。`TEST_AUTH_PASSIVE` で、認証の方式が手動のログインか、Windows での自動ログイン。「[認証つきの監査](#認証つきの監査ログインあり読むだけ)」）です。CLI の `run` と同じ監査を、画面のサーバとは別の process（監査のワーカー。`dist/worker/audit-worker.js`）で行います。結果（`run.json`、`audit.json`、`report.html`、ChatGPT 用のバンドル）の形は、CLI と同じです。

### 始める

- 一覧の「監査を始める」から、開始の画面を開きます。プロファイルと、設定のファイルの要点（開始の URL、ページの上限、時間の上限、ページの読み込みの間隔）を表示します。
- 始め方を選んで開始します: 「前回の続きから再開する」（既定。途中で止まった Run があれば続きから、なければ新しく）か、「新しく始める」（CLI の `--new` と同じ）。
- 取り消したプロファイル、今は実行できない監査モードと認証の方式、認証の設定がない・古い・誤りがある、読めない設定のファイル、今の設定で通らないプロファイルは、理由と取るべき手順を表示して、開始のボタンを出しません（開始できません）。画面を開いた後にプロファイルが変更された場合も、開始せずに知らせます。

### サイトへの負荷の決まり

- **画面から設定は変えられません。** 間隔と上限は、設定のファイルの値のまま使います。変えるときは、設定のファイルを直します。
- **監査は、画面全体で同時に 1 つだけです。** ほかの監査が動いている間に開始すると、理由を表示して開始しません。同じ出力先では、CLI の監査とも同時には始まりません（「[同じ出力先で、2つの監査を同時に始めない](cli.md#同じ出力先で2つの監査を同時に始めない)」）。
- 画面が 2 秒ごとに状態を読み直すのは、画面のサーバの管理データだけで、監査の対象のサイトには何も送りません。

### 進み具合と結果

- ジョブの画面は、動いている間、2 秒ごとに読み直して、進み具合（監査を終えたページ、発見したページ、ページの上限、経過の時間、ページの読み込みの回数、許可 Origin への要求と 1 分あたりの最大、許可 Origin の外への要求）と、知らせ（サイトの不調の確かめ直し、減速）を、CLI と同じ書式で表示します。
- 画面を閉じても監査は続きます。開き直すと、同じ状態を表示します。
- 終わった後は、ジョブの状態、Run の ID、Run の状態（完了、一部未完了など）、終わり方、終了コード（CLI と同じ値）、日時と、成果物へのリンク（HTML レポートを開く、`run.json`・`audit.json`・ChatGPT 用のバンドルのダウンロード）を表示します。失敗と中断では、理由と取るべき手順を表示します。

### 止める・強制的に止める

- 「監査を止める」は、確認のダイアログの後に、今のページの監査を終えてから止めます（CLI の 1 回目の Ctrl+C と同じ）。止めた Run は一部未完了になり、後で「前回の続きから再開する」で続きから再開できます。
- 止める要求から 30 秒たっても止まらないときは、「強制的に止める」を表示します。今のページを待たずに、すぐに止めます（CLI の 2 回目の Ctrl+C と同じ）。再開のための保存は、最後に監査を終えたページまで残ります。強制的に止める要求の後も 10 秒止まらないときは、ワーカーを終わらせます。

### 認証つきの監査（ログインあり・読むだけ）

テスト環境の管理画面などを、人がログインした状態で、読み取りだけで監査します。ログインは、監査を始めたときに BeakSight が開くブラウザで、人が行います。
始めから再開までの手順、守りの範囲、使えないこと、確かめていないことは「[認証つきの監査の手順](authenticated-audit.md)」にあります。

- **認証の設定**（プロファイルの詳細の「認証の設定を開く」）: ログインの画面の URL、ログインの送信先（ログインの間だけ、ここへの送信（POST）を許します）、ログインが済んだと判定するパス（と、任意で要素の CSS セレクタ）、セッションが切れたと判定するパス（空なら、ログインの画面のパス）、読まないパス（ログアウトの画面を必ず入れます）、読む範囲のパス（空なら絞りません）、ログインの送信の回数の上限（1〜3 回）を設定します。パスか query にログアウトや削除などの語（`logout`、`signout`、`sign-out`、`log-out`、`delete`、`remove`、`destroy`、`cancel`）を含む URL は、設定にかかわらず読みません（画面に一覧を表示します。画面では変えられません）。
- **秘密は書きません。** 認証の設定の画面には、パスワードや Cookie の値を入れる欄はありません。秘密に見える名前の query（`password`、`token`、`session` など）を含むログインの画面の URL も、保存しません。
- 保存の前に、サーバがプロファイルと設定のファイルで確かめ直し、誤りを項目ごとに日本語で表示します（1 行に 1 つの項目は、誤りのある行も示します）。
- 認証の設定は、保存したときのプロファイルの改訂に結びつきます。プロファイルを変更すると、認証の設定は「古い（保存し直しが必要）」になり、内容を見直して保存し直すまで、監査を始めません。
- **始める**: 開始の画面に「BeakSight が開くブラウザでログインしてください。ログインが済むと自動で監査が始まります」の案内と、ログインの画面の URL、読む範囲を表示します。認証の設定がない・古い・誤りがあるときは、理由と、認証の設定の画面へのリンクを表示して、開始のボタンを出しません。
- **ログイン**: ジョブの画面の「ログイン」に、認証の状態（ログイン待ち、ログイン済み、止まった理由）を表示します。ログイン待ちの間に、開いたブラウザでログインします。ログインが済むと、そのブラウザを閉じて、読み取りだけの監査を始めます。ログインの状態（Cookie など）は保存せず、画面にも出しません。再開するときも、もう一度ログインします。決められた時間の中にログインが済まない、送信の回数の上限を超える、などのときは、理由を表示して監査を始めません。
- **セッションが切れたとき**: 監査の途中でログインの状態が切れたら、その Run を一部未完了で止め、止まったページの URL と、「このページを読まないパスに足すと、次から読まない」案内と、認証の設定の画面へのリンクを表示します。
- 認証つきの監査では、クリックによる操作の確かめ（Interaction）を行いません。速さの上限（ページの読み込みの間隔など）は、公開の監査と同じく設定のファイルの値のまま使います。

### 自動ログイン（資格情報とログインの確かめ）

テスト環境のプロファイル（`TEST_AUTH_PASSIVE`）で、認証の方式を自動ログイン（`AUTOMATED_LOGIN`）にすると、画面で一度だけ入れたテスト用のアカウントの資格情報で、BeakSight が自動でログインします。自動ログインは Windows だけで使えます（Windows の暗号化（DPAPI）で資格情報を保存するため）。手順、結果ごとにすること、守りの範囲、残る危険は「[自動ログインの手順](automated-login.md)」にあります。

- **認証の設定**: 手動のログインの項目に加えて、自動ログインの項目を入れます。ユーザー名の欄・パスワードの欄・送信のボタンの CSS セレクタ（それぞれ、ちょうど 1 つの要素を指す、標準の CSS のもの。Playwright 独自の書き方は保存しません。「[認証の設定を作る](automated-login.md#3-認証の設定を作る)」）と、ログインの失敗を見分ける 4 つの条件（資格情報の誤り、アカウントのロック、人の操作（MFA など）が必要、パスワードの期限切れ。それぞれ、使わないか、画面のパスの前方一致と任意の要素のセレクタ）です。使わない条件は、パスとセレクタの両方を空にします。ログインの送信の回数は、自動ログインでは 1 回に固定です（画面では変えられません。アカウントのロックを避けるため）。同じパスの条件が 2 つ以上あるときは、どちらにもセレクタを指定します（同じパスで、片方にセレクタがない条件は、同時に当たりうるので保存しません）。誤りは、項目ごとに表示します。
- **資格情報の画面**（プロファイルの詳細の「資格情報を開く」）:
  - 表示するのは、保存の有無、登録した日時、最後に変えた日時と変更の種類、保存したログインの Origin、今の認証の設定のログインの Origin と合うか（合わなければ「入れ直しが必要」）、資格情報の暗号化の状態、自動ログインを止めているか（理由と日時）だけです。**ユーザー名を含めて、値は一度も画面に出しません。**
  - **新しく登録**: ユーザー名とパスワードの両方を入れます。パスワードは 2 回入れ、一致しなければ保存しません。
  - **変更**: 「ユーザー名を変える」「パスワードを変える」を選び、選んだ方の欄だけを入れます（パスワードは 2 回）。選ばなかった方は、保存してある値をそのまま使います。どちらも選ばないときと、空の欄は、保存しません（空の欄は「消す」の意味になりません）。
  - **入れ直し**: 保存したログインの Origin が、今の認証の設定と違うときは、一部の変更はできないので、ユーザー名とパスワードの両方を入れ直します。
  - **自動ログインの停止も解く**: 自動ログインを止めているときだけ、変更の画面に出る明示の選択です。資格情報を変えただけでは、停止は解きません（ロックや回数の制限は、サーバの側で続いているかもしれないため）。
  - **削除**: 確かめのダイアログの後に削除します。削除すると、もう一度登録するまで、自動ログインとログインの確かめは始められません。
  - そのプロファイルのジョブ（監査かログインの確かめ）が動いている間は、変更と削除をしません（理由を表示します）。
  - **ここに本番のパスワードを書かないでください。** テスト環境のテスト用のアカウントだけを使います。ブラウザが、入れたパスワードの保存を勧めることがあります（BeakSight からは止められません）。保存しないでください。
  - 資格情報は、リポジトリの `local/secrets/<profileId>.credential.json`（Git の管理の外）に、ユーザー名とパスワードを別々に暗号化して保存します。フォルダの権限は、今の Windows の利用者だけに絞ります。復号するのは、ログインする監査のワーカーだけです。
- **ログインを確かめる**（一覧とプロファイルの詳細の「ログインを確かめる」）: 保存した資格情報で、ログインだけを 1 回試し、結果を記録するジョブ（ジョブの種類「ログインの確かめ」）を始めます。監査は行わず、ブラウザも開きません。始められないとき（資格情報がない・入れ直しが必要・暗号化を使えない・自動ログインを止めている・間隔や回数の上限の中、など）は、理由と次に始められる日時を表示して、開始のボタンを出しません。
- **上限**: 自動ログイン（監査の前のログインを含む）は、1 回のジョブでログインの送信が 1 回だけ、同じプロファイルで 5 分以上あけ、24 時間に 10 回までです。サーバが回数の制限（HTTP 429）で示した待つ時間（`Retry-After`。上限 24 時間）も守ります。
- **止めた状態**: ログインを送った後に成功以外で終わると（資格情報の誤り、ロック、MFA、期限切れ、429、結果が分からない、など）、アカウントのロックを避けるため、そのプロファイルの自動ログインを止めます。ログインを送る前に止まった場合（フォームの確かめで止めた、など）は止めません。止めているときは、「ログインを確かめる」の画面に理由と人がすることを表示します。テスト環境のアカウントを確かめた後に、「確かめたので自動ログインを再び許す」（確かめのダイアログ）で解きます。解いても、5 分の間隔と `Retry-After` は守ります。
- **ジョブの画面**: ジョブの種類（監査、ログインの確かめ）と、「自動ログイン」の欄に、結果、ログインを送信したか、サーバが示した次に試してよい日時（429 のとき）、フォームの確かめで止めた理由を表示します。結果ごとに、人がすること（資格情報を変更する、テスト環境の管理者にロックの解除を頼む、MFA のあるアカウントは使えない、セレクタと失敗の条件を見直す、時間をおく、など）を表示します。
- **監査の開始**: 自動ログインのプロファイルの開始の画面には、「BeakSight が保存した資格情報で自動でログインします。ブラウザは開きません」の案内と、自動ログインの状態（今すぐ始められる、止めている、次に始められる日時）を表示します。
- **環境の状態**: 「資格情報の暗号化（自動ログイン）」に、使える・使えない・この環境では使えない（Windows でない）を表示します。画面のサーバ（と `npm run setup:local`）は、起動のときに、資格情報のフォルダに残った書きかけの一時のファイルを消し、暗号化の往復を 1 回だけ確かめます（値は出しません）。使えなくても、画面のサーバは起動します（自動ログインを始められないだけです）。

### 操作の候補と READ の確かめ

認証つきの読み取りの監査（`TEST_AUTH_PASSIVE`）か、承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルで、ログインの後に、管理画面に「どんな操作があるか」を書き込みなしで洗い出し、読み取り（READ）の操作だけは実際に読んで確かめます。手順、候補と結果の見方、サイトへの読み込み、守りの範囲、確かめていないことは「[操作の候補の発見と READ の確かめの手順](discovery-and-read-check.md)」にあります。どちらも、プロファイルの詳細の「操作の候補と READ の確かめ」から開きます。始めるには、監査と同じく、認証の設定（自動ログインなら資格情報も）が要ります。始められないときは、理由を表示して、開始のボタンを出しません。

- **操作の候補を探す**（画面「操作の候補」）: ジョブ（種類「操作の候補の発見」）を始めます。BeakSight がログインしてから、認証の設定の読む範囲の管理画面を、設定のファイルの読み込みの間隔とページの上限で読み、フォームとボタンを集めて分類します。フォームの送信、入力、クリックはしません。
  - **最後の発見**: 終わり方（読める画面をすべて読んだ、ページの上限、ログインの状態の切れ、など）、Run の状態、読んだ画面と読まなかった画面の数、読まなかった理由ごとの数、読み切れなかった画面と理由。
  - **候補の一覧**: 画面（path）ごとに、種類（フォーム、ボタン）、分類と分類の理由、ドリフト、送り方（GET・POST と `_method`）、送信先、状態の欄の印（`active`・`status`・`deleted` などの欄がある）、この画面から実行できるかを示します。許可 Origin が 2 つ以上のプロファイルでは、同じ path の候補を、画面の Origin で分けて示します。
  - **分類**: 読み取り（READ）だけが「READ の確かめに使える」です。登録（CREATE）・更新（UPDATE）・実行しない（削除など）・送り方が決まらない（JavaScript で送る）・扱えない読み取り（POST の検索、パスワードの欄のある GET など）・許可 Origin の外へ送る・分類できない（表示だけ）は、「この画面からは実行できない」と示します。登録と更新の候補は、承認した書き込みのモードのプロファイルでは「シナリオを作る」からシナリオにでき、承認の後に「[書き込みの実行](#書き込みの実行登録と更新)」で 1 件ずつ送れます。
  - **ドリフト**（最後の発見に対して）: 新しい、変わった（入力の規則・分類・理由・状態の欄の印のどれか）、変わらない、消えた（読み切れた画面にない。記録は残す）、読み直していない（その画面を読まなかった）。
  - **詳しい内容**（各候補の「詳しい内容」）: ボタンの分類の語（ボタンの文言そのものは出しません。文言に当たった分類の語だけを出し、当たる語がなければ「分類の語なし」）、enctype、target、送信先の query の名前、JavaScript の結び付き、入力の欄（名前、型、必須・読み取り専用・無効・見えない、制約、選択肢の値、値を送れるか）。候補を最後に見た発見のジョブの `discovery.json` から読みます。**入力の値、CSRF のトークン、hidden の値、選択肢の label は、成果物にも画面にも出しません。** 見えない欄と秘密に見える名前の欄は、選択肢の値も出しません。選択肢の値は、個人情報になりえます（「[候補の見方](discovery-and-read-check.md#候補の見方)」）。
- **READ の確かめ**（画面「READ の確かめ」）:
  - **定義を作る**: 「READ の候補」（最後の発見の結果で READ に分類された候補）の「この候補で作る」から、送る値と期待を決めます。送る値の入力の欄は、その候補の値を送れる欄（名前があり、見えていて、読み取り専用でも無効でもない欄。パスワードとファイルの欄は、名前にかかわらず除きます）だけです。値を入れた欄だけを送ります。期待は「行の数がちょうど」「行の数が少なくとも」「本文が文を含む」「詳細の項目の値が等しい」から選びます（1 件以上 10 件まで）。1 つのプロファイルの定義は 20 件までです。
  - **送る値は、テスト環境のテスト用の値だけにしてください。** 値は管理データにそのまま保存し、この画面に表示します。秘密に見える名前（token、session、code、state、key など）の欄に値を入れると、保存せずに、その欄に理由を表示します。送る値の名前か値に危険な語（削除、取り消し、一括、無効、delete、cancel など）があるときも、同じく保存せずに、その欄に理由を表示します。
  - **保存の確かめ**: 保存のときに、サーバが、最後の発見の結果の候補に照らして確かめ直します。拒んだときは、理由を項目ごとに表示します（秘密に見える名前、危険な語、送れない欄、READ でない候補、最後の発見の結果にない候補、件数の上限、形の誤り）。
  - **変える・削除する**: 定義の「変える」から開きます。ほかの画面で先に変えられていたときは、保存せずに知らせます（読み込み直してから、もう一度変えます）。削除は、確かめのダイアログの後に、定義を一覧から外します（前の結果の記録は残ります）。取り消したプロファイルでは、定義を作ったり変えたりできません（削除はできます）。
  - **READ を確かめる**: ジョブ（種類「READ の確かめ」）を始めます。定義が 1 件もなければ、理由を表示して、開始のボタンを出しません。BeakSight がログインしてから、定義ごとに、対象の候補がまだ同じ形で READ であることを確かめ、送る値で GET の URL を組み立てて読み（フォームの送信はしません）、結果を期待と照らします。
  - **結果**: ジョブごとに、定義ごとの結果（一致、不一致、判定できない、読む前に止めた、画面が変わった、READ でなくなった）、詳しい理由、HTTP の状態、期待ごとの結果の要約（数えた行の数、文を含んでいたか、詳細の項目の取れた値）、`read-evidence.json` のダウンロードのリンク。表の全体は写しません。
- **ジョブの画面**: 操作の候補の発見と READ の確かめのジョブは、進み具合の知らせを送りません。ジョブの画面には、種類と状態（と Run の状態）だけを示し、結果の画面（操作の候補、READ の確かめ）へのリンクを出します。成果物の `discovery.json` と `read-evidence.json` は、ダウンロードで取り出せます。どちらのジョブも、止まったら再開せず、もう一度始めます。

### 書き込みのシナリオ（承認と撤回）

承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルだけで使えます。ほかのモードのプロファイルには、シナリオへの案内も「シナリオを作る」も出さず、サーバも作成を拒みます。シナリオは、最後の「操作の候補を探す」の結果の、登録（CREATE）か更新（UPDATE）の候補 1 つです。**承認しただけでは書き込みは始まりません。** 承認は、書き込みを許す条件（版、上限、期限、副作用の確認、検証の指定）を記録します。書き込みは、承認の後に、別の画面「書き込みを始める」から人が始めます（「[書き込みの実行](#書き込みの実行登録と更新)」）。手順、再承認が要る場合、上限と期限、守りの範囲、確かめていないことは「[書き込みのシナリオの承認の手順](scenario-approval.md)」にあります。

- **作る**（画面「シナリオを作る」）: 「操作の候補」の画面の、登録・更新の候補の「シナリオを作る」から開きます（ほかの分類の候補には出ません）。次を決めて保存すると、版 1 の下書きになります。
  - **送る欄**: 候補の、見えていて、読み取り専用でも無効でもない欄だけを選べます。秘密に見える名前（token、session、code、state、key など）の欄、危険な語（削除、取り消し、一括、無効、delete、cancel など）の欄、パスワードとファイルの欄、`_method` の欄は選べず、理由を示します。送る値の作り方（入力の規則）は、シナリオを作った後に、下の「入力の規則」の画面で決めます（「[入力の規則とデータの生成](data-rules.md)」）。
  - **照らす READ の定義**（任意）、**上限**（1 回の Run は 1 件、累積は 20 件の既定以下）、**承認の期限**（30 日の既定以下）、**副作用の確認**（テスト環境のレコードだけ、メール・SMS・外部の通知が送られない、決済や外部のサービスに及ばない、削除・無効化・取り消しに当たらない、の 4 項目）。
  - **検証の指定**（成功の条件、入力の誤りの条件、登録の ID の取り方、照合の READ）。決めていない項目があっても保存と承認はできますが、書き込みは始められません（「[検証の指定](approved-create.md#検証の指定)」）。
  - **UPDATE の指定**（更新の候補だけ。送る欄の選択の代わりに出ます）: 台帳にする登録（CREATE）のシナリオ、path の型、欄ごとの役割（変える・保つ）（「[UPDATE の指定](approved-update.md#update-の指定)」）。
  - 保存のときに、サーバが最後の発見の候補に照らして確かめ直します。拒んだときは、理由を項目ごと（送る欄はその欄、照らす READ の定義はその定義）に表示します。
- **一覧**（画面「シナリオ」）: シナリオごとに、種類、画面と送信先、状態（下書き・承認済み・要再承認（理由の一覧）・期限切れ・撤回済み）、承認の期限、上限と使った件数（予約中・送った・送ったか分からない件数の合計。送る前に返した予約と、期限を過ぎてまだ無効にしていない許可の予約は数えません。実行の許可の発行と同じ数え方です）、入力の規則の状態（未設定・すべて決まった・不足あり）、版。
- **詳細**: 承認の状態と再承認が要る理由、要求の形（送り方、送信先の Origin と path、enctype、送る欄、照らす READ の定義）、入力の規則の状態と参照（なければ「未設定。入力の規則を決めるまで、実行の許可は出せません。」。「入力の規則を開く」から、下の「入力の規則」の画面を開きます）、副作用の確認、最後の承認との差分（項目ごとに「前の値 → 今の値」と説明）、発見の根拠の写し（シナリオを作ったときの候補。欄の名前・型・属性・制約だけで、値・選択肢・hidden の値・CSRF のトークンは出しません）、承認と撤回の履歴、版の履歴。
- **変える**: 詳細の「変える」から開きます（候補は変えられません）。保存すると版が 1 つ進み、下書きに戻ります（前の承認は引き継ぎません）。ほかの画面で先に変えられていたときは、保存せずに知らせます（読み込み直してから、もう一度変えます）。
- **承認する**: 副作用の確認の 4 項目をすべて確かめたシナリオだけ。確認のダイアログ（開くと「やめる」にフォーカス。上限、承認の期限、副作用の確認、最後の承認との差分を示す）で「承認する」を押したときだけ承認します。画面に出した版と承認の digest をサーバが今の事実から求め直し、違えば「画面が古い」として承認しません（読み込み直してから、もう一度承認します）。承認者は `LOCAL_OPERATOR` と記録します。
- **再承認**: 承認の後に、シナリオの版、プロファイル（どの項目の編集でも）、認証の設定（自動ログインなら、資格情報の版と、資格情報の登録・変更・削除の記録も。削除して登録し直しても再承認になります）、ターゲットの設定のファイルの内容、候補（入力の規則か分類）、入力の規則の参照、照らす READ の定義のどれかが変わると、状態は「要再承認」になり、理由を表示します。期限を過ぎると「期限切れ」です。どれも、内容を確かめてから、もう一度承認します。
- **承認を撤回する**: 承認済みのシナリオだけ。確認のダイアログの後に撤回します。撤回すると、まだ消費していない実行の許可は無効になり、送っていない件数の予約は返ります。送った書き込みは取り消せません。撤回の記録は残ります。
- 取り消したプロファイルでは、シナリオを作る・変える・承認するはできません（記録は見られます。撤回はできます）。
- プロファイルが指す設定のファイルか、資格情報のメタデータ（版）を読めないときは、承認の状態を確かめられないことを表示し、承認しません。

### 入力の規則（送る値の作り方）

シナリオの詳細の「入力の規則を開く」から開きます。承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルのシナリオだけで、編集とデータの例を出します（ほかのモードでは出さず、サーバも保存を拒みます）。**この画面からは書き込みを実行しません。データの例もサイトに送りません。** 値は LLM を使わず、欄の型と制約、小さな辞書と業務テンプレート（顧客・予約・商品）、人が入れた値の一覧から、決まった手順で作ります。

- **状態**: 入力の規則の状態（未設定・すべて決まった・不足あり）と、保存した版。
- **送る欄の規則**: 送る欄ごとに、状態（決まった・規則の入力が要る・決まりがぶつかる・外部到達で止めた）と、その理由の説明と手順、当てた規則の出どころ（人の規則・業務テンプレート・汎用の規則・送らない側に固定）、外部到達の種類（メール・電話・通知・配信・住所の欄）を示します。送る欄でない必須の欄も、理由とともに並びます。
  - 「意味の種類」で、人の規則を決めます（「自動」は、業務テンプレートか汎用の規則で決めます。選べる種類は、欄の型に合うものだけです）。作り方（欄の型と制約から・業務テンプレートと辞書から・人が入れた値の一覧から）と、値の一覧（1 行に 1 つ）、範囲（最小・最大・刻み）を決めます。
  - 人が入れた値は、管理データにそのまま残ります。秘密に見える名前の欄には入れられません（保存を拒みます）。
  - メールアドレスは、配送されない予約のドメイン `example.invalid` の宛先だけ、電話番号は `090-0` で始まる形（ハイフンなしは `0900` で始まる 11 桁）だけを作ります。どちらも、シナリオの副作用の確認「メール・SMS・外部の通知が送られない設定です」を確かめるまで作りません。住所と URL の欄は、人が入れた値だけを使います。通知・配信を求める欄は、送らない側に固定します（送らない側が選べなければ止めます）。
- **欄どうしの関係**: 終了は開始より後、合計は単価 × 数量、フリガナは氏名と同じ人。人が決めた関係に、業務テンプレートの既定の関係を足して当てます（当てる関係を示します）。
- **一意にする欄の組**: 選ばなければ、業務テンプレートの既定の組を使います（当てる組を示します）。
- **データの例（送りません）**: 送る欄すべての作り方が決まったときだけ、この画面のための決まった値で作った例を 3 つ示します。メールアドレスと電話番号には、合成の形であることを添えます。実際の書き込みでは、実行の許可ごとに別の値になります。
- **保存する**: 確認のダイアログ（開くと「やめる」にフォーカス）で「保存する」を押したときだけ保存します。保存すると、入力の規則の新しい版ができ、シナリオに付け直します。シナリオの版が 1 つ上がって下書きに戻るので、承認していた場合は、もう一度承認が要ります（再承認の理由に「入力の規則が変わった」が出ます）。ほかの画面で先に変えられていたときは、保存せずに知らせます（読み込み直してから、もう一度保存します）。規則は保存できたのにシナリオに付けられなかったときも、そのことを知らせます。
- 送る欄すべての作り方が決まっていないシナリオには、実行の許可を出しません。

### 書き込みの実行（登録と更新）

承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルのシナリオだけで使えます。書き込みを始められるのは、承認が今も有効なシナリオだけです。詳しい決まりは「[承認された登録の手順](approved-create.md)」と「[承認された更新の手順](approved-update.md)」にあります。

- **開く**: シナリオの詳細の「書き込みを始める画面を開く」から、画面「書き込みを始める」（`/scenarios/<profileId>/<scenarioId>/write`）を開きます。
- **始める前に確かめること**: シナリオと版、送る欄（登録）か更新するレコード・変える欄・保つ欄・更新の画面（更新）、送り先、1 回の Run で 1 件、累積の上限（使った件数と残り）、連続の上限（最後の書き込みから 5 分あける・24 時間に 5 件まで）、次に実行できる時刻、外部への通知（副作用の確認）、テスト環境の証跡、承認の状態を出します。検証の指定に決めていない項目があるときは「実行できない理由」を出します。
- **始める**: 始められるときだけ「書き込みを始める」のボタンを出します。押すと確認のダイアログ（「書き込みを始めますか」）が開きます。ダイアログの「書き込みを始める」を押したときだけ、実行の許可を出し、書き込みのジョブを始めて、ジョブの画面へ移ります。「やめる」を押すと何もしません。始めた後は、送る直前の確かめで止まらない限り、送信を取り消せません。
- **拒まれたとき**: 「書き込みを始められませんでした」と、理由と手順を出します。承認が無効になった理由があれば並べます。「読み込み直す」で画面を読み直します。
- **結果**: ジョブの画面の「書き込みの結果」に、結果（照合済み、照合できていない、結果が分からない、登録されなかった、送らずに止めた）、理由、送信の状態、止めた理由、応答の HTTP の状態、応答の判定、登録の ID（更新は対象のレコードと取れた ID）、照合の READ、予約の締め、日時、送った値（合成のテストデータ）を出します。結果が分からない（`UNKNOWN`）ときは目立つお知らせで、テスト環境で登録の有無を確かめるよう促します。照合できていない（`PARTIAL`）ときも、お知らせを出します。
- **書き込みの履歴**: シナリオの詳細の「書き込みの履歴」に、新しい順に、記録した日時、結果、理由、送信、更新の対象のレコード、登録の ID、予約の締め、報告（開くリンクか「配らない」）、ジョブを開くリンクを出します。
- **更新の前後の差分**: 更新のジョブでは、変えた欄の前の値と新しい値と、更新の後の照合の一致を出します。保つ欄は、一致したかだけを出します（値は記録しません）。
- **書き込みの報告**: 親の確かめに通った報告だけ、「報告を開く」（`action-report.html`）と「報告の ZIP をダウンロードする」のリンクを出します。通らない・確かめていないときは、報告を配らず、その理由を出します（「[書き込みの報告](output.md#書き込みの報告)」）。

### 監査済みデータの台帳

プロファイルの詳細の「監査済みデータの台帳を開く」から、画面「監査済みデータの台帳」（`/ledger/<profileId>`）を開きます。承認した書き込みのモードのプロファイルだけで行を出します（ほかのモードでは理由を出します）。読み方は「[リスクと監査の記録](risks-and-audit-logs.md#監査済みデータの台帳の読み方)」にあります。

- **登録（CREATE）の表**: 登録の ID（取れていなければ「取れていない」）、シナリオと版、seed の記録（実行の許可の ID と規則の digest）、ジョブと Run、照合の状態（送信の状態・結果・照合の READ）、その ID への UPDATE の回数と最後の結果、記録した日時。新しい順です。送らずに止めた回は入れません。送ったか分からない回は入れます。UPDATE の回数と最後の結果も、送らずに止めた回は数えません。
- **件数（シナリオごと）の表**: シナリオ、種類、版、累計の件数と上限（実行の許可の判定と同じ数え方）。
- **BeakSight は、登録したデータを削除も復元もしません。** テスト環境のデータの片付けは、この台帳をもとに、テスト環境の管理者が行います。
- 台帳は画面だけです。ファイルへの書き出しはありません。

### 画面のサーバが落ちたとき

- 画面のサーバが落ちると（強制終了を含む）、ワーカーと、ワーカーが動かしていた Chromium も止まります。
- 次に画面のサーバを起動したときに、そのジョブを「中断」（理由: 画面のサーバが、監査の途中で終わった）として記録し、コンソールにも知らせます。
- 同じプロファイルで「前回の続きから再開する」を選んで開始すると、同じ Run の続きから再開します（CLI で同じコマンドを実行したときと同じ再開の仕組みです。「[中断と再開](resume.md#中断と再開)」）。

## 守り

管理画面は、このコンピュータの中から、起動した本人だけが使う前提で、次のように守ります。

- **待ち受けは `127.0.0.1` だけです。** ほかのコンピュータ（LAN を含む）からは繋がりません。設定でも変えられません。さらに、要求を受けた接続の手元のアドレスが `127.0.0.1` でなければ、421 で拒否します（Host の値は送る側が偽れるため）。
- **Host の確かめ**: `http://127.0.0.1:<port>` 以外の名前で来た要求（`localhost` を含む）は、421 で拒否します（DNS rebinding の対策）。
- **合言葉と cookie**: コンソールの URL の `token` が正しければ、`HttpOnly`、`SameSite=Strict`、`Path=/` の cookie に替え、`token` を除いた URL へ移します（303）。cookie も `token` もない要求と、誤った `token` は 401 で拒否します（画面、Server Function、static のファイルのすべて）。
- **CSRF**: 画面の保存と監査の開始・停止の操作（資格情報の登録・変更・削除、ログインの確かめ、自動ログインの停止の解除、操作の候補の発見と READ の確かめの開始、READ の確かめの定義の保存と削除、シナリオの作成・変更・承認・撤回、入力の規則の保存、書き込みの開始を含む。Server Function）は、同じ Origin からの要求だけを受けます（`Sec-Fetch-Site`、なければ `Origin` で確かめ、違えば 403）。管理データへの書き込みは POST の Server Function だけで行います。
- **入力の確かめ**: 画面からの入力は、サーバで JSON Schema（`schemas/control/`）とプロファイルの決まり（認証の設定は、その決まり）で確かめ直してから保存します。監査の開始は、開始の直前に、プロファイル（有効か、改訂が画面で読んだものと同じか、今実行できる監査モードと認証の方式か）と設定のファイルと、認証つきの監査では認証の設定を確かめ直します。
- **応答の header**: すべての応答に、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cross-Origin-Opener-Policy: same-origin`、`Content-Security-Policy`（`default-src 'self'`、script は要求ごとの nonce、`frame-ancestors 'none'` など。`'unsafe-inline'` と `'unsafe-eval'` は使いません）を付けます。

## 成果物の取り出し

ジョブの詳細のリンクは、`/artifacts/<ジョブの ID>/<Run のディレクトリの中の相対パス>` を開きます（GET だけ。ほかのメソッドは 405）。

- 配るのは、そのジョブの Run のディレクトリ（出力先は、プロファイルの設定のファイルの `output.directory`）の中の、許可の一覧のファイルだけです: `run.json`、`audit.json`、`report.html`、操作の候補の発見の `discovery.json`、READ の確かめの `read-evidence.json`、ChatGPT 用のバンドルの ZIP、`audit.json` が参照するもの（ページの `page.json` と `visible-text.txt`、スクリーンショット）。それ以外（`checkpoint/` の中、参照されていないファイル、`..` や符号化した区切り、Windows の別名やデバイス名など）は 404 です。
- 書き込みのジョブの報告の 4 つ（`action-report.html`、`action-evidence.json`、`approval-summary.json`、書き込みのバンドルの ZIP `beaksight-action-bundle_YYYYMMDDHHmmss.zip`）は、親の確かめ（報告の確かめ）が「確かめ済み」のジョブだけ配ります。ほかのジョブでは、ファイルがあっても 404 です。ZIP は、`action-run.json` の終わりの時刻から決まる名前の 1 つだけです。2 つの JSON は、配る前に、スキーマと、文書のジョブの ID がそのジョブであることを確かめ直します。`action-run.json` は配りません（画面の書き込みの結果で示します）。
- ファイルは、リンク（シンボリックリンク、junction）をたどらずに、Run のディレクトリの中にあることを確かめてから読みます。
- `report.html` と `action-report.html` は、script を動かさない CSP（`sandbox allow-same-origin`、`default-src 'none'`、`img-src 'self' data:`、レポートの `<style>` だけを SHA-256 の値で許す `style-src`）で返します。`allow-scripts` は付けないので、レポートの中に script があっても動きません。`allow-same-origin` は、レポートの中の相対のリンク（スクリーンショットなど）を開くときに、合言葉の cookie（`SameSite=Strict`）を送るために付けています（付けないと 401 になります）。
- `run.json`、`audit.json`、`discovery.json`、`read-evidence.json`、`action-evidence.json`、`approval-summary.json`、ZIP は、ダウンロード（`Content-Disposition: attachment`。ファイル名は ASCII の決まった形）で返します。
- Host、待ち受けのアドレス、合言葉の cookie の守りは、成果物にも同じように掛かります（cookie がなければ 401）。

## 受け入れる危険（守りの範囲の外）

- **同じコンピュータで動くほかのプログラム**は、管理データのファイル（`local-data/`）を直接読み書きできます。画面のサーバの守りは、画面のサーバへの要求を守るもので、ファイルの直接の読み書きは守りの範囲の外です。
- **cookie は port で分かれません。** 合言葉の cookie は、同じコンピュータの `127.0.0.1` のほかの port で動くサーバにも送られます。ほかの port の画面からの保存の操作は CSRF の確かめで拒否しますが、管理画面を使うあいだは、信頼できないローカルのサーバを動かさないでください。

## 開発のサーバ

画面を作る人のための、変更をすぐに反映する開発のサーバです。

```powershell
npm run ui:dev
```

- 本番の起動と同じ守り（`127.0.0.1` だけ、Host、合言葉と cookie、CSRF、応答の header）を掛けます。
- Vite の preview（`vite preview`）では起動できません（守りを通らないため。説明を表示して終了コード 1 で止まります）。画面は `npm run ui` で起動します。
- 待ち受けのアドレスは変えられません。`npm run ui:dev -- --host`（`0.0.0.0`、`::`、`localhost` などを含む）のように待ち受けのアドレスを指定すると、説明を表示して起動しません（終了コード 1）。実際に待ち受けたアドレスも確かめ、`127.0.0.1` でなければ止めます。port の使用中も、説明を表示して止まります。コンソールに `BeakSight 管理画面（開発）: http://127.0.0.1:<port>/?token=…` を表示します。
- 待ち受けを始めたときに、同じ管理データを準備し、前のサーバで終わっていなかった監査を「中断」として記録します。
- 画面から監査を動かすには、先に `npm run build` で監査の本体をビルドしておきます（開発のサーバは、監査の本体をビルドしません。ワーカーは `dist/worker/audit-worker.js` です）。
- 止めるとき（Ctrl+C）は、本番と同じく、動いている監査を止めてから終わります（2 回目の Ctrl+C で、待たずに終わります）。
- ブラウザに配るファイルは、画面が読み込む範囲（`apps/local-ui`、`src/presentation`、`src/core`、`src/control`、依存のパッケージ）に絞ります。`local/`、`artifacts/`、`local-data/`、`.git` などは配りません。

## 検証のスクリプト

| コマンド | 内容 |
| --- | --- |
| `npm run build:ui` | 画面をビルドします（`apps/local-ui/dist/`）。 |
| `npm run typecheck:ui` | 画面のコードの型チェックを行います（`build:ui` の後。生成の route の表を使うため）。 |
| `npm run test:ui` | 画面とサーバのテスト（`apps/local-ui/tests/`）を行います（`build:ui` と `build` の後。画面から動かす監査のテストは、監査の本体のビルドの出力 `dist/` を使います）。 |
| `npm run verify:ui` | `build:ui`、`typecheck:ui`、`test:ui` を順に行います。 |
| `npm run verify:all` | `verify`（CLI の型、テスト、ビルド）と `verify:ui` を順に行います。 |

- 画面のテストは、リポジトリの外の一時のフォルダに画面（と監査の本体のビルドの出力 `dist/`）を写して起動します。リポジトリの `local-data/` は作りません。監査は、テストの中で起動する 127.0.0.1 の小さなサイトだけを対象にします。ブラウザは headless の Chromium だけを使い、外部のサイトにはアクセスしません。
- `apps/local-ui/src/routeTree.gen.ts` は、ビルドと開発のサーバが作る生成のファイルで、Git の管理の外です。

## この画面でできないこと

- CLI で始めた Run の一覧（実行履歴には、画面から始めた監査だけを表示します）。
- 承認した書き込みのモード（`TEST_APPROVED_WRITE`）のプロファイルでの読み取りの監査（`TEST_AUTH_PASSIVE` のプロファイルで行います）。
- 削除（DELETE）・初期化・復元の書き込み、1 回の Run で 2 件以上の書き込み、複数の段のシナリオ（登録してから更新する、など）。
- 監査済みデータの台帳の、ファイルへの書き出し。
- CLI からの認証つきの監査、操作の候補の発見、READ の確かめ、書き込み（どれも画面からだけ動かせます）。Windows 以外での自動ログイン。
- 管理データの消去、作り直し、バックアップと復元（手で名前を変えれば、次の準備で新しく作られます。「[管理データの扱い](local-setup.md#管理データの扱い)」）。
- ほかのコンピュータからの利用、複数の人の権限の管理。
