# まとめて実行（ログイン 1 回で、監査・発見・READ の確かめ・書き込みを続ける）

[仕様の索引に戻る](README.md)

ログインして読むプロファイル（`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE`）では、管理画面の開始の画面の主のボタン「点検を始める」が、まとめて実行を始めます（既定。設計書 `doc/design/2026-10-26-beaksight-plain-ui-design.md` の 2 章の判断 3）。ログインを 1 回だけ行い、その後に次の段を続けて行います。開始の画面に「まとめて実行」の別のボタンはありません。プロファイルの詳細の一覧「登録・更新を試せる画面」でチェックした画面があれば、最後に書き込みの段（登録 →（あれば）更新）を続けます（設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` の 4.1.1・4.1.2）。作成の画面の「点検を始める」は、入口の確かめの後に、まとめて実行を続けて始めます。
段ごとに、ジョブの記録と Run を 1 つずつ作ります。各段の成果物は、1 つずつ始めたときと同じです。

画面の言葉は文書と違います（監査は「点検」、発見は「操作さがし」、READ の確かめは「見るだけの確かめ」、段は「ステップ」、ジョブは「作業」）。対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」にあります。

## 使えるモードと段の並び

| プロファイルのモード | 段の並び（この順） |
| --- | --- |
| `TEST_AUTH_PASSIVE` | 監査 → 操作の候補の発見 → READ の確かめ |
| `TEST_APPROVED_WRITE` | 監査 → 操作の候補の発見 → READ の確かめ →（チェックした画面ごとに）登録 →（あれば）更新。チェックした画面がなければ、`TEST_AUTH_PASSIVE` と同じです。監査・発見・READ の確かめの段で、BeakSight は書き込みを送りません（ページが自動でする通信は、送信の扱いのとおり。「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」） |
| `PUBLIC_PASSIVE` | 使いません（ログインしないため。開始の画面の「点検を始める」は、監査だけを始めます） |

- 開始の確かめは、1 つずつ始めるときと同じです（プロファイルの改訂、認証の設定、自動ログインの上限など）。どの段の操作もそのモードで許されるときだけ始めます。
- 監査の段の始め方は、前回の続きから再開するのが既定です（途中で止まった Run があれば続きから、なければ新しく）。前回の監査が最後まで終わらなかったときだけ、開始の画面のたたんだ「詳しい内容」に「始め方」（「前回の続きから再開する」か「新しく始める」）が出ます。読まないパスの欄と、行う段の一覧（「行うステップ（この順）」）と、上限の値も「詳しい内容」の中です。「読まないパス」（画面では「読まないページ」）を変えて始めたときは、1 つずつ始めるときと同じく、認証の設定を保存してから始めます。発見と READ の確かめは、いつも新しい Run です。
- READ の確かめは、取り消していない定義のうち、シナリオの照合の専用の印（`verificationOnly`）で参照されていないものが 1 件以上あるときだけ行います。照合の専用の定義（書き込みの答え合わせのために BeakSight が作るもの）は、READ の確かめのジョブでは読みません。対象の定義がなければ、READ の確かめを行わずに終えます（失敗にはしません。ジョブの詳細の段の一覧に「行わなかった」と出ます）。定義の件数は、まとめて実行の開始の確かめに入れません（定義が 0 件でも始められます）。
- READ の確かめの対象の画面は、この連鎖の発見の段が候補の索引を記録した後に、1 つずつ始めるときと同じ決め方で決めます。
- 発見の段（画面では「操作さがし」）の読む先（OP-J の J1。設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` 4.1.6）: 直前の監査の段が見つけたリンクのうち、登録の画面らしいもの（リンクの文字・`aria-label`・`title`・path の語。危険な語・読まないパス・読む範囲の外は読みません）を先に読み、続けて今どおり入口からページの上限（`crawl.maxPages`）まで読みます。すでに読んだ画面は読み直しません。先に読んだ登録の画面のリンクはたどりません。
  - 一覧の画面も読みます（OP-R の R2。設計書の 4.1.9）: 先に読む登録の画面ごとに、アドレスの後ろ（path）の 1 つ上の一覧の画面（例 `/admin/x/new` → `/admin/x`）で、監査の段のリンクにあるものを、その登録の画面の直後に読みます。読む数は、上の 10 ページの中に数えます。この一覧の画面は、登録の答え合わせ（照合の READ）に使います（「[API の検証の指定](approved-create.md#api-の検証の指定)」）。
  - **サイトへの負荷の上限: 操作さがしの段は、登録の画面と一覧の画面を合わせて最大 10 ページ（名前つきの定数 `MAX_CHAINED_CREATE_PAGE_READS`）、続けてページの上限まで（最大 10 + `crawl.maxPages` ページ。どれも GET だけで、読み込みの間隔は変わりません）。**
  - 登録の画面らしいリンクがなければ、今どおりです。1 つだけ始める発見のジョブは、今どおり入口からページの上限までです（読む数は変わりません。見つけたリンクのうち、登録の画面らしいものを先に読む順だけが変わります。OP-I の I2）。

## 書き込みの段

- **対象**: 承認した登録のシナリオ（一覧でチェックした画面のもの。チェックの保存が承認を兼ねます）ごとに、登録の段 1 つと、その台帳に結ぶ承認した更新のシナリオがあれば更新の段 1 つです。1 つの画面につき、登録 1 件と更新 1 件までで、同じ段をもう一度行いません（送り直しません）。チェックしたままなら、点検のたびに登録を 1 件行います。
- **始めの確かめ**（OP-T。設計書の 4.1.9 の後の直し）: まとめて実行を始めるとき（最初の段を始める前）に、チェックした画面の登録の手順を、最後の操作さがしの結果（前回までの点検のもの）と今の作り方で作り直し、承認したものと比べます。
  - 答え合わせのしかただけが違う: 新しい手順を自動で承認し、そのまま書き込みます。
  - 送る中身が違う: 承認を外し、一覧の行を「もう一度チェックしてください」にします（その画面には書き込みません）。
  - 一覧のどのチェックの行にも結び付かない承認済みの登録（と、結ぶ更新）: 取り消します。
  - この確かめを終えられない（管理データを読めない、など）: まとめて実行を始めません（見るだけの段も始めません）。
  - チェックを入れたときにも、同じ作り直しを行います（「[登録・更新を試せる画面](local-ui.md#登録更新を試せる画面)」）。
- **更新の対象**: 同じ点検の登録の段で作り、照合まで済んで番号が取れたレコードです。番号が取れなかったときは、その画面の更新の段を行いません。
- **自動の更新の下書き**: この連鎖の発見の段で、チェックした画面の更新の候補が初めて見つかったときは、BeakSight がチェックの範囲の中で、更新のシナリオの下書きと承認を行い、同じ連鎖で更新します（知らせを送ることがある更新の画面は、自動では承認しません）。
- **段の前ごとに**: 画面のサーバ（親）が、実行の許可（`issueExecutionGrant`。期限つきで 1 回だけ）を出し、書き込みの準備（件数の予約など）をして、次の段の指示に書き込みの指定を載せます。段の終わりに結果を締めます。承認の有効さ（改訂・認証の設定・期限など）は、この許可の発行が確かめます（無効なら、その画面は送りません）。
- **文脈と記録**: 書き込みの段は、1 つずつ始める書き込みと同じ流れ（凍結した読み取りの文脈で確かめ、分けた書き込みの文脈で送る）を通ります。段ごとに、ジョブの記録・Run・書き込みの報告を作ります。監査・発見・READ の確かめの報告は、読み取りだけのままです（監査の報告のまとめに、この後に書き込むことの 1 行が出ます）。
- **ログイン**: 連鎖の最初の 1 回のログインのまま行います。ログインし直しません。ログインの状態と読み込みの間隔（pacer）と 1 分の窓は、ほかの段と同じく、監査の process のメモリの中だけで持ち越します（境目でも間隔を守ります）。
- **残りを止めるとき**: 止める要求、安全の違反、ログインの切れ、改訂の変化、結果が分からない（締めていない・`UNKNOWN`）ときは、残りの書き込みの段を行いません。照合できなかった・送らなかった・失敗した画面の後は、次の画面へ進みます（その画面の結果は、一覧の行に出ます）。

## ログインの状態の扱い

- ログインは連鎖の最初に 1 回だけです（自動ログインなら、自動ログインの間隔と 24 時間の回数に 1 回として数えます）。
- 段の間では、次のものを監査の process（ワーカー）のメモリの中だけで持ち越します。
  - ログインの状態（前の段のブラウザが受けた最新の状態。token の更新の後のものを含む）
  - 読み込みの間隔: 前の段の最後の読み込みの開始と、前の段の終わり（ブラウザを閉じた後）の遅い方から、設定の間隔以上空けて次の段を始めます。前の段がサイトの不調の確かめ直しで間隔を上げていれば、上げた間隔を引き継ぎます（下げません）。再開した監査の段の後も同じです。
  - 承認したサービスの Origin への要求の 1 分あたりの窓（段の境目で数え直しません）
- ログインの状態は、成果物、管理データ、画面、ログ、監査の process との間の通信のどこにも書きません（[認証つきの監査](authenticated-audit.md) の「秘密を出さないこと」と同じ決まりです）。
- 1 回の Run あたりの上限（ページの数、時間、サービスの Origin への要求の数）は、段ごとに数えます。

## 次の段へ進むか

段が終わるたびに、次の段へ進むかを決めます。

- **進む**: Run の状態が `COMPLETE`、または止める理由のない `PARTIAL`（ページの上限・深さの上限・時間の上限と、ページごとの理由: 読み込み・描画・測りの失敗など）。
- **止める**（次の段を始めません）。理由のコードは、すべて「進む」か止める理由のどちらかに分けてあります。Run 単位の理由（再開のための保存を書けなかった、安全の記録が上限で切れた、扱われない失敗、実行が欠けた、必須の作業の理由、必須の成果物の不正）は「段が失敗した」で止めます。一覧にない値は止める側に倒します。

| 止めた理由 | 起きること |
| --- | --- |
| 「点検を止める」で止めた | 今の段を今の止め方で止め、次の段を始めません。 |
| 安全の違反があった | 違反の中身を確かめてください。 |
| ログインが切れた | 止まった段のジョブの画面の、ログインの欄の案内に従ってください。 |
| サイトが応答しなかった | サイトが応答するようになってから、もう一度まとめて実行してください。 |
| サービスの Origin への要求の上限に届いた | 負荷の側に倒して止めます。認証の設定の上限を見直してください。 |
| 段が失敗した | Run の状態が `FAILED`、Run を実行しなかった、結果を読めなかったときです。 |
| 途中でプロファイルが変わった | 連鎖は、始めた時のプロファイルの改訂に結びます。途中で改訂が変わったら止めます。 |
| 次の段を始められなかった | 画面のサーバが終わる途中、または管理のロックを失ったときです。 |
| 書き込みの結果が分からない | 書き込みの段で、送ったか・照合できたかが分かりません。テスト環境の画面で、データが作られたかを確かめてください。残りの画面の書き込みはしていません。 |
| 試せなかった画面がある | チェックした画面のうち、試せなかった画面がありました（許可を出せない・値を作れない、など。何も送っていません）。ほかの画面は試しました。一覧の行で、その画面の様子を確かめてください。 |

- 最後の段でも、止める要求なら「点検を止める」で止めた、段が結果（`FINISHED`）なしに終わったなら「段が失敗した」とし、「最後まで行った」とは出しません。
- 連鎖が止まった段には、段の一覧で「この段で止まった」の印を付けます。

止まった理由と次にできることは、ジョブの詳細の「まとめて実行」の欄に出ます。詳しい理由は、止まった段のジョブの画面（終わり方と理由、次にできること）で確かめてください。止まった段のジョブの画面では、その画面の終わり方と同じ意味の理由（安全の違反、ログインの切れ、サイトの不調、サービスの要求の上限、段の失敗）の次にできることを繰り返さず、上の欄を見る案内だけを出します。

## 止める・再開

- 画面の「点検を止める」は、連鎖の全体を止めます。どの段のジョブの ID で押しても（終えた前の段の画面からでも）、今の段のジョブへ止めを回します。段の間（次の段へ進むかを決めている間、次の段を始めた直後）に押しても、次の段は始めません（始めていれば、その段を止めます）。
- 連鎖の全体を止めるボタンは、作業の画面の要点の「点検を止める」1 つです（前の「まとめて実行をやめる」のボタンは、なくしました）。
- 監査の process は、途中の段を終えた後、画面のサーバからの次の段の指示を最大 60 秒（`WORKER_NEXT_STAGE_TIMEOUT_MS`）待ちます。60 秒を過ぎたら、次の段を始めずに、終えた段の終了コードで終わります（連鎖は「段が失敗した」で止まった扱いになります。終えた段のジョブの記録は、そのまま残ります）。
- まとめて実行そのものは再開しません。止まった監査の段は、次に「点検を始める」を押すと、既定の「前回の続きから再開する」で続きから始めます（監査の段の後に、発見と READ の確かめも続けて行います）。

## 同時に動くジョブとプロファイルの改訂

- 連鎖の間、段の間に空きはありません。前の段のジョブの記録を締めることと、次の段のジョブの記録を作ることを続けて行うので、ほかのジョブは始まりません（全体で 1 つの決まりのまま）。
- 手動のログインの成功からの認証の設定の自動の登録と、自動ログインへの切り替え（プロファイルの改訂を進める）は、ログインの直後、監査の前に、1 回の保存で行います（「[1 回目の手でのログインから切り替える](automated-login.md#1-回目の手でのログインから切り替える)」）。連鎖は、画面のサーバ（親）が自分で進めたこの改訂だけを、新しい基準として受け入れます（ほかの保存で改訂が変わったら、「途中でプロファイルが変わった」で止めます）。結果は、最初の段（ログインを行った段）のジョブの画面に出ます。
- 書き込みのモードへの切り替え（一覧のチェックの保存）は、点検の前に済ませます（点検の途中に切り替えると、改訂の変化で連鎖が止まるためです）。

## 画面

- 開始の画面: 要点に「サイトのページを見て回り、操作できる所を探します。読むだけで、書き込みはしません。」（チェックした画面があれば「…チェックした画面では、テスト用のデータを登録・更新します。そのほかは見るだけです。」）と、主のボタン「点検を始める」を 1 つだけ出します。始められないときは、ボタンを出さずに理由を出します（どの段の確かめで止まったかによらず、最初に当たった理由です）。行う段の一覧は、たたんだ「詳しい内容」の中です。
- ジョブの詳細: 連鎖の段のジョブには「まとめて実行」の欄が出ます（作業の画面の「詳しい内容」の中）。段の一覧（状態と、各段のジョブへのリンク）、連鎖の状態、止まった理由と次にできることです。
- **自動で次の画面へ**: 段のジョブが成功で終わり、次の段が始まると、作業の画面は次の段のジョブの画面へ自動で移ります。最後の段まで行ったら、プロファイルの詳細（画面では「点検するサイト」の画面）へ移ります。止まったとき（安全の違反、ログインの切れ、段の失敗など）は移らず、その画面に要点と次にすることを出します。移るかどうかは、送信の扱い（既定は「削除のほかを通す」）によりません。移った先の要点の 1 行目に、何が終わったかを出します。監査の段が一部未完了（`PARTIAL`。ページの上限など）で終わったときも、連鎖は次の段へ進み、作業の画面も次の段のジョブの画面へ移ります。利用者が止めたときは移りません。最後の段の後に移ったプロファイルの詳細の主のボタンは「結果を見る」です。書き込みの段を行ったときは、要点に書き込みの 1 行（「チェックした画面では登録・更新も行いました。」など）が出ます。
- この欄は、画面のサーバが動いている間だけ出ます（連鎖の記録はメモリの中だけに持ちます。画面のサーバを起動し直すと消えます。各段のジョブの記録は残ります）。

## 確かめていること

- テスト用の小さなサイト（127.0.0.1）で、本物の監査の process と Chromium（テストの既定の Chromium と CLI の起動の設定の両方）を使い、ログインが連鎖ごとに 1 回だけであること（サーバの記録で数える）と、ログインの状態の目印が成果物・管理データ・通信・監査の process の出力のどこにも出ないことを確かめています。
- 止める理由ごとに次の段を始めないこと、READ の定義がないときに READ を行わないこと、改訂の扱い、段の間にほかのジョブを始められないことを、テストで確かめています。
