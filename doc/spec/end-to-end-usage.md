# 通しの使い方（3 つのモード）

管理画面で、公開の監査から、テスト環境の認証つきの監査、承認された書き込み（登録と更新）、台帳と報告までを、通して使う順です。
各段の細かい決まりは、段ごとの文書にあります。ここでは、順と、画面とボタンの名前と、段と段のつながりを書きます。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> テスト用の小さなサイトで確かめています。実際のテスト環境では、まだ確かめていません（「[実テスト環境の手順](real-test-environment.md)」）。認証つきの監査と書き込みは、本番から隔離されていることを確かめたテスト環境だけに使います。

## 全体の流れ

| 段 | すること | プロファイル | サイトへ送るもの | 詳しい手順 |
| --- | --- | --- | --- | --- |
| 0 | 導入、設定のファイル、テスト環境の隔離の確かめ | なし | なし | [導入](getting-started.md) |
| 1 | プロファイルを作る | 3 つ | なし | [監査プロファイル](profiles.md) |
| 2 | 公開の監査 | `PUBLIC_PASSIVE` | `GET`・`HEAD` | [管理画面の監査の実行](local-ui.md#監査の実行) |
| 3 | 認証つきの監査 | `TEST_AUTH_PASSIVE` | ログインの送信、`GET`・`HEAD` | [認証つきの監査](authenticated-audit.md)、[自動ログイン](automated-login.md) |
| 4 | 操作の候補の発見と READ の確かめ | `TEST_APPROVED_WRITE` | ログインの送信、`GET`・`HEAD` | [操作の候補の発見と READ の確かめ](discovery-and-read-check.md) |
| 5 | 登録（CREATE）のシナリオを作って承認する | `TEST_APPROVED_WRITE` | なし | [書き込みのシナリオの承認](scenario-approval.md) |
| 6 | 入力の規則を決める | `TEST_APPROVED_WRITE` | なし | [入力の規則とデータの生成](data-rules.md) |
| 7 | 登録（CREATE）を 1 件送る | `TEST_APPROVED_WRITE` | ログインの送信、`GET`、登録の `POST` 1 件 | [承認された登録](approved-create.md) |
| 8 | 更新（UPDATE）のシナリオを作り、1 件更新する | `TEST_APPROVED_WRITE` | ログインの送信、`GET`、更新の `POST` 1 件 | [承認された更新](approved-update.md) |
| 9 | 台帳と報告を見る | `TEST_APPROVED_WRITE` | なし | [出力と結果の読み方](output.md#書き込みの報告) |

- 監査と、ジョブ（ログインの確かめ、発見、READ の確かめ、書き込み）は、画面全体で同時に 1 つだけです。
- どのジョブも、設定のファイルの読み込みの間隔（`crawl.minNavigationIntervalMs`）とページの上限（`crawl.maxPages`）を守ります。画面からは変えられません（「[サイトへの負荷](site-load.md)」）。

## 0. 準備

1. 「[導入](getting-started.md)」の初期設定を終えます（Node.js、依存、Chromium、`npm run build`、`npm run setup:local`）。
2. テスト環境の設定のファイルを、Git の管理の外の `local/targets/<名前>.json` に作ります。匿名の例 `config/targets/example-test-environment.json.example` の `targetConfig` を写し、実際の値に直します（例は `admin.example.test` を使います）。`site.startUrl` はログインの後の管理画面、`site.allowedOrigins` はテスト環境の Origin です。
3. 設定を確かめます: `node dist/cli/index.js validate-config --config local/targets/<名前>.json`。
4. テスト環境が本番から隔離されていることを確かめ、その記録の参照（例 `isolation-check-example-001`。秘密を書かない）を決めます。隔離が未確認のときは、未確認であることが分かる参照（例 `isolation-unverified-20261016`）にし、読み取りの段（手順 3 と 4）だけを行います。書き込み（手順 5〜8）は、隔離の扱いを決めてから行います（「[実テスト環境の手順](real-test-environment.md#1-事前の確かめ)」）。
5. `npm run ui` で画面を起動し、コンソールの URL を開きます。

## 1. プロファイルを作る

左のメニューの「新しいプロファイル」で、モードごとに 1 つずつ作ります。項目の決まりは「[監査プロファイル](profiles.md)」にあります。値の例は `config/targets/example-test-environment.json.example` の `profiles` にあります。

| 用途 | 環境 | 監査モード | 認証の方式 | テスト環境の Origin | 確かめた記録の参照 |
| --- | --- | --- | --- | --- | --- |
| 公開の監査 | 公開（本番）（`PUBLIC`）。テスト環境のログインの前の画面なら、テスト環境（`TEST`） | 公開の監査（読むだけ）（`PUBLIC_PASSIVE`） | ログインしない（`NONE`） | 空 | 空 |
| 認証つきの監査 | テスト環境（`TEST`） | テスト環境の監査（ログインあり・読むだけ）（`TEST_AUTH_PASSIVE`） | 手でログインする（`MANUAL_SESSION`）か、自動でログインする（`AUTOMATED_LOGIN`） | テスト環境の Origin | 0 の 4 の参照 |
| 書き込み | テスト環境（`TEST`） | テスト環境の監査（承認した書き込みあり）（`TEST_APPROVED_WRITE`） | 手でログインする（`MANUAL_SESSION`）か、自動でログインする（`AUTOMATED_LOGIN`） | テスト環境の Origin | 0 の 4 の参照 |

- 画面の選択肢には、日本語の名前だけが出ます（括弧の中はコードの値です）。

- `TEST_APPROVED_WRITE` のプロファイルでは、読み取りの監査（「監査を始める」）はできません。認証つきの監査は `TEST_AUTH_PASSIVE` のプロファイルで行います。
- プロファイルを編集すると、そのプロファイルの認証の設定は「古い」になり、保存し直すまでジョブを始められません。承認したシナリオは「要再承認」になります。

## 2. 公開の監査

1. 左のメニューの「サイトとプロファイル」の一覧で、公開の監査のプロファイルの行の「最後の Run」の列にある「監査を始める」を押します（プロファイルの詳細の画面にはありません）。このボタンは、状態が「有効」で、今実行できる監査モードと認証の方式の組み合わせ（「公開の監査（読むだけ）」と「ログインしない」、または「テスト環境の監査（ログインあり・読むだけ）」と「手でログインする」か「自動でログインする」）のプロファイルにだけ出ます。
2. 開始の画面で、始め方（「前回の続きから再開する」か「新しく始める」）を選び、「監査を始める」を押します。
3. 監査のジョブの画面で、進み具合と結果を見ます。HTML レポート、`run.json`、`audit.json`、ChatGPT 用のバンドルを開けます。

CLI の `run` でも、同じ公開の監査を行えます（「[導入](getting-started.md#最初の監査cli)」）。

## 3. 認証つきの監査

1. 認証つきの監査のプロファイルの詳細で「認証の設定を開く」を押し、ログインの画面の URL、ログインの送信先、ログインが済んだと判定するパス、読まないパス（ログアウトの画面を必ず入れます）、読む範囲のパスなどを保存します。値の例は、例のファイルの `authSetups` にあります（「[認証の設定を作る](authenticated-audit.md#3-認証の設定を作る)」）。
2. 自動ログインのときは、プロファイルの詳細の「資格情報を開く」でテスト用のアカウントを登録し、「ログインを確かめる」でログインだけを 1 回試します（「[自動ログインの手順](automated-login.md)」）。自動ログインの 3 つのセレクタは、標準の CSS だけで書きます。
3. 「サイトとプロファイル」の一覧の、認証つきの監査のプロファイルの行の「最後の Run」の列にある「監査を始める」から開始の画面を開き、「監査を始める」を押します。
4. 手動のログインのときは、BeakSight が開いたブラウザでログインします。ログインが済むと、BeakSight がそのブラウザを閉じ、読み取りだけで監査します（「[開いたブラウザでログインする](authenticated-audit.md#5-開いたブラウザでログインする)」）。
5. 結果は公開の監査と同じ形です。管理画面の文とスクリーンショットが成果物に入るので、外へ渡す前に「[成果物を外へ渡す前の確かめ](anonymization.md)」を読みます。

## 4. 操作の候補の発見と READ の確かめ

書き込みに使う候補と READ の定義は、書き込みのプロファイル（`TEST_APPROVED_WRITE`）で作ります。シナリオは、そのプロファイルの最後の発見の候補からだけ作れ、照合の READ の定義も、そのプロファイルのものだけを選べるためです。

1. 書き込みのプロファイルで、手順 3 の 1・2 と同じく、認証の設定（と自動ログインなら資格情報）を作ります。
2. プロファイルの詳細の「操作の候補を開く」で画面「操作の候補」を開き、「操作の候補を探す」を押します。BeakSight がログインしてから、読む範囲の管理画面を読むだけで、フォームとボタンを集めて分類します。
3. 「最後の発見」と「候補の一覧」で、分類（`READ`・`CREATE`・`UPDATE`・実行しないもの）を確かめます（「[候補の見方](discovery-and-read-check.md#候補の見方)」）。
4. プロファイルの詳細の「READ の確かめを開く」で画面「READ の確かめ」を開き、「読み取り（READ）の候補」の「この候補で作る」から、送る値と期待を決めて「保存する」を押します。登録した内容を読み直す検索の画面などを、照合の READ に使う定義として作っておきます。
5. 「READ を確かめる」を押し、定義ごとの結果（一致、不一致など）を確かめます。

## 5. 登録（CREATE）のシナリオを作って承認する

1. 画面「操作の候補」で、登録（`CREATE`）の候補の「シナリオを作る」を押します。
2. 送る欄、照らす READ の定義（任意）、上限、承認の期限、副作用の確認の 4 項目、検証の指定（成功の条件、入力の誤りの条件、登録の ID の取り方、照合の READ）を入れて「保存する」を押します（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」、「[検証の指定](approved-create.md#検証の指定)」）。
3. 承認は、手順 6 の入力の規則を保存した後に行います（規則を保存するとシナリオの版が進み、下書きに戻るためです）。

## 6. 入力の規則を決める

1. シナリオの詳細の「入力の規則を開く」を押します。
2. 送る欄ごとに状態（決まった・規則の入力が要る・決まりがぶつかる・外部到達で止めた）を確かめ、決まっていない欄の意味の種類や値の一覧を入れます。
3. 「データの例（送りません）」で、作られる値の形を確かめます。
4. 確認のダイアログの「保存する」で保存します（「[入力の規則とデータの生成](data-rules.md)」）。
5. シナリオの詳細に戻り、「承認する」を押して、確認のダイアログで上限・期限・副作用の確認・最後の承認との差分を読んでから「承認する」を押します（「[承認する](scenario-approval.md#5-承認する)」）。

## 7. 登録（CREATE）を 1 件送る

1. シナリオの詳細の「書き込みを始める画面を開く」を押します。
2. 画面「書き込みを始める」の「始める前に確かめること」（送る欄、送り先、1 回の Run で 1 件、累積の上限、連続の上限、次に実行できる時刻、外部への通知、テスト環境の証跡、承認の状態）を確かめます。
3. 「書き込みを始める」を押し、確認のダイアログの「書き込みを始める」を押します。ジョブの画面へ移ります。手動のログインのときは、開いたブラウザでログインします。
4. 「書き込みの結果」を見ます。照合済み（`VERIFIED`）なら、登録の ID と照合の READ が一致しています。結果が分からない（`UNKNOWN`）ときは、テスト環境で登録の有無を必ず確かめます（「[UNKNOWN の後にすること](approved-create.md#unknown-の後にすること)」）。

## 8. 更新（UPDATE）のシナリオを作り、1 件更新する

1. 画面「操作の候補」で、更新（`UPDATE`）の候補の「シナリオを作る」を押します。
2. 「UPDATE の指定」で、台帳にする登録（CREATE）のシナリオ（手順 5 のシナリオ）、path の型、欄の役割（変える・保つ）を決めます。検証の指定、上限、期限、副作用の確認も入れて保存します（「[UPDATE の指定](approved-update.md#update-の指定)」）。
3. 入力の規則（変える欄だけ）を決めて保存し、承認します。
4. 「書き込みを始める画面を開く」で、「更新するレコード」（台帳のシナリオの照合済みの登録のうち、最も新しいもの）、変える欄、保つ欄、更新の画面を確かめ、「書き込みを始める」と確認のダイアログの「書き込みを始める」を押します。
5. 「書き込みの結果」の「前後の差分」で、変えた欄の前の値と新しい値、保つ欄が変わらなかったことを確かめます。

## 9. 台帳と報告を見る

1. ジョブの画面の「書き込みの報告」で「報告を開く」を押し、`action-report.html` を見ます。「報告の ZIP をダウンロードする」で書き込みのバンドルを落とせます。報告を配らないときは、その理由が出ます（「[報告を配らない場合](output.md#報告を配らない場合)」）。
2. プロファイルの詳細の「監査済みデータの台帳を開く」で、登録した ID、照合の状態、その ID への UPDATE の回数と最後の結果、シナリオごとの累計の件数と上限を確かめます（「[監査済みデータの台帳の読み方](risks-and-audit-logs.md#監査済みデータの台帳の読み方)」）。
3. BeakSight は、登録したデータを削除も復元もしません。テスト環境のデータの片付けは、台帳をもとに、テスト環境の管理者が行います。

## 人が成果物を開いて確かめる項目

| 成果物 | 開き方 | 確かめること |
| --- | --- | --- |
| `report.html`（公開の監査・認証つきの監査） | ジョブの画面の HTML レポートのリンク | Run の状態、未完了の理由、サイトへの負荷（ページの読み込みの回数、許可 Origin への要求）、安全の節（遮断した操作、安全の不変条件の違反が 0 件か）。 |
| ChatGPT 用のバンドル（ZIP） | ジョブの画面のダウンロード | `manifest.json` の一覧、`pages/<pageId>/page.json` の可視テキストと URL、スクリーンショット。外へ渡す前に、渡してよい内容か（「[成果物を外へ渡す前の確かめ](anonymization.md)」）。 |
| `discovery.json`・`read-evidence.json` | ジョブの画面のダウンロード | 候補の分類、READ の結果。ページが書いた値（path、query の名前、欄の名前、選択肢の値）と、READ で読んだ値が入っていること。 |
| `action-report.html` | ジョブの画面の「報告を開く」 | 結果と理由、`UNKNOWN`・`PARTIAL` の注意、送った値、前後の差分（更新）、照合の READ、Guard の記録、承認の要約。先頭の「人が入れた値が入りうる報告です」の注意の有無。 |
| 書き込みのバンドル（ZIP） | ジョブの画面の「報告の ZIP をダウンロードする」 | `manifest.json` の各ファイルの SHA-256 と、人が入れた値の注意。中の JSON が `action-run.json`・`action-evidence.json`・`approval-summary.json` であること。 |
| 監査済みデータの台帳 | プロファイルの詳細の「監査済みデータの台帳を開く」 | 登録した ID が、テスト環境の実際のレコードと合うか。送ったか分からない回の行が、テスト環境で登録されていたか。 |
