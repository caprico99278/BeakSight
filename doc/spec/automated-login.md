# 自動ログインの手順（テスト環境・Windows だけ）

テスト環境の管理画面を、BeakSight が保存したテスト用のアカウントの資格情報で自動でログインし、ログインだけを確かめる手順と、ログインの後に読み取りだけで監査する手順です。守りの範囲、確かめていないこと、残る危険も書きます。
画面の操作の細部は「[管理画面の自動ログイン](local-ui.md#自動ログイン資格情報とログインの確かめ)」に、ログインの後の監査の決まり（読まないパス、伏せ字、セッションが切れたときなど）は「[認証つきの監査](authenticated-audit.md)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 自動ログインは、管理画面からだけ動かせます（CLI からは動かせません）。テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません。

## 使ってよい場合

- **テスト環境の、テスト用のアカウントだけに使います。** 本番の資格情報（本番のアカウント、ふだん使っている自分のパスワード、ほかのサービスと同じパスワード）を、BeakSight に入れないでください。
- **本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします（「[認証つきの監査の使ってよい場合](authenticated-audit.md#使ってよい場合)」と同じです）。
- **Windows だけで使えます。** 資格情報を Windows の暗号化（DPAPI。今の Windows の利用者だけが戻せる形）で保存するためです。Windows でない環境では、資格情報の保存と自動ログインの開始を、画面のサーバが拒みます（画面には「この環境では使えない」と表示します）。
- 多要素認証（MFA）を求めないアカウントにします。BeakSight は MFA の操作をしません。
- ログインのフォームの送信（ページの移動の POST）でログインする画面と、画面の中のスクリプトが token を取りに行く「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」の画面に使えます。スクリプトで送るログインの自動ログインは、下の「[スクリプトで送るログインの自動ログイン](#スクリプトで送るログインの自動ログイン)」にあります。
- ログインの画面とログインの送信先と管理画面が、同じ Origin（プロファイルの `approvedTestOrigins`）にあること。別の Origin のログインのサービス（IdP）は使えません（「[使えないこと](#使えないこと)」）。

## 手順

手動のログインのプロファイルから切り替えるときは、下の「[手動のログインから 1 回で切り替える](#手動のログインから-1-回で切り替える)」を使えます（手順 2〜4 を 1 つの画面で、確認 1 回で行います）。新しく自動ログインのプロファイルを作るときは、手順 1 から行います。

### 1. 設定のファイルを用意する

監査の対象の設定のファイルは、手動のログインと同じです（「[認証つきの監査の手順 1](authenticated-audit.md#1-設定のファイルを用意する)」）。速さの上限（`crawl.minNavigationIntervalMs`、`crawl.maxPages` など）は、このファイルの値のまま使います。

### 2. テスト環境のプロファイルを作る

管理画面の「新しいプロファイル」で、`auth` を `AUTOMATED_LOGIN` にしたプロファイルを作ります。ほかの項目は、手動のログインと同じです（「[認証つきの監査の手順 2](authenticated-audit.md#2-テスト環境のプロファイルを作る)」）。

| 項目 | 値 |
| --- | --- |
| `environment` | `TEST`（画面の名前「テスト環境」） |
| `mode` | `TEST_AUTH_PASSIVE`（画面の名前「テスト環境の監査（ログインあり・読むだけ）」）。`TEST_APPROVED_WRITE` でも、資格情報の保存とログインの確かめは同じ手順で使えます（このモードでは監査は始められません。使えるのは、操作の候補の発見、READ の確かめ、シナリオ、入力の規則、承認された登録と更新です。「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。 |
| `auth` | `AUTOMATED_LOGIN`（画面の名前「自動でログインする」。BeakSight が保存した資格情報でログインする） |
| `approvedTestOrigins` | テスト環境の Origin（ログインの画面、ログインの送信先、管理画面の Origin を含む） |
| `environmentEvidenceRef` | テスト環境が本番から隔離されていることを確かめた記録への参照。隔離が未確認のときは、未確認であることが分かる参照（例 `isolation-unverified-20261016`）。秘密を書きません。 |

### 3. 認証の設定を作る

プロファイルの詳細の「認証の設定を開く」から作ります。手動のログインの項目（ログインの画面の URL、ログインの送信先、ログインが済んだと判定するパス、セッションが切れたと判定するパス、読まないパス、読む範囲のパス。「[認証つきの監査の手順 3](authenticated-audit.md#3-認証の設定を作る)」）に加えて、自動ログインの項目を入れます。パスワードを入れる欄は、ここにはありません。

| 項目 | 内容 |
| --- | --- |
| ユーザー名の欄のセレクタ | ログインの画面のユーザー名の入力の欄を指す CSS セレクタ。 |
| パスワードの欄のセレクタ | パスワードの入力の欄（`type="password"`）を指す CSS セレクタ。 |
| 送信のボタンのセレクタ | ログインのフォームの送信のボタンを指す CSS セレクタ。 |
| 失敗の条件（4 つ） | 資格情報の誤り、アカウントのロック、人の操作（MFA など）が必要、パスワードの期限切れ。それぞれ、使わないか、ログインの送信の後に移る画面のパス（前方一致）と、任意で、その画面にある要素の CSS セレクタ。使わない条件は、パスとセレクタの両方を空にします。 |

- **3 つのセレクタは、標準の CSS セレクタだけで書きます。** Playwright 独自の書き方（`:has-text()`・`:visible`・`>>`、`css=`・`xpath=` などの前置き、`:nth-match()` など）は、保存のときに拒みます（`AUTH_SETUP_SELECTOR_NOT_STANDARD_CSS`）。BeakSight は、ログインのフォームの確かめで、3 つのセレクタを、ページの JS から切り離した読み取り（isolated world）の中で標準の CSS として探し直すためです。保存のときの確かめは近似で、shadow root をまたぐ書き方は保存できても、実行のときにフォームを読めないとして止まります（`LOGIN_FORM_INVALID`。理由「ログインのフォームを読めませんでした」）。この確かめを入れる前に保存した設定も、同じく実行のときに止まります。成功の条件と失敗の条件のセレクタは、この確かめの対象ではありません。
- **3 つのセレクタは、それぞれ、ログインの画面でちょうど 1 つの要素に当たるように書きます。** 当たらない、または 2 つ以上に当たると、値を入れずに止まります（下の「[送信の前のフォームの確かめ](#送信の前のフォームの確かめ)」）。3 つの要素は、同じフォームの中にあることが要ります。
- **成功の条件と失敗の条件は、ログインの送信の後の画面で、ちょうど 1 つだけが当たるように書きます。** BeakSight は、当たった条件がちょうど 1 つのときだけ結果を決めます。どれにも当たらない、または 2 つ以上に当たるときは「結果が分からない」で止めます（成功の条件に当たらないことから、資格情報の誤りと推し量ることはしません）。
  - 同じパスの条件が 2 つ以上あるときは、どれにもセレクタを指定し、セレクタで見分けます（同じパスで、片方にセレクタがない条件は、同時に当たりうるので保存しません）。
  - 成功の条件と同じパスとセレクタの組の失敗の条件は、保存しません。
- ログインの送信の回数は、自動ログインでは 1 回に固定です（`AUTOMATED_LOGIN_MAX_LOGIN_ATTEMPTS`。画面では変えられません）。
- 保存する認証の設定は、フォームの送信でも版 3 の形になります（前の版の形の設定は読みません）。版 3 のフォームの送信の設定でも、自動ログインは今までどおり動くことを、テスト用のサイトで確かめています。

### 4. 資格情報を登録する

プロファイルの詳細の「資格情報を開く」から、テスト用のアカウントのユーザー名とパスワードを入れて保存します。

- パスワードは 2 回入れます。一致しなければ保存しません。
- ユーザー名とパスワードは、それぞれ 4 文字以上 256 文字までです（文字の数は UTF-16 のコード単位で数えます）。4 文字未満の値は保存しません（「ユーザー名かパスワードが短すぎます。自動ログインで値が外へ送られないかを確かめられないため、受け付けません。」）。変更と入れ直しの入力も同じです。前に保存した値は、今どおり使えます（4 文字未満の値でも、復号して使います）。ただし、スクリプトで送るログインの自動ログインでは、4 文字未満の値は、どの要求にも含まれるとみなされるので、ログインできません。
- 値は、画面に一度も表示しません（ユーザー名を含めて）。画面に出すのは、保存の有無、日時、変更の種類、保存したログインの Origin、今の認証の設定と合うか、暗号化の状態、自動ログインを止めているか、だけです。
- ブラウザが、入れたパスワードの保存を勧めることがあります。保存しないでください（BeakSight からは止められません）。
- 登録できないとき: 暗号化を使えない（環境の状態の画面で確かめる）、資格情報のフォルダの権限が広い（下の「[残る危険](#確かめていないこと残る危険)」）、Windows でない、など。

### 手動のログインから 1 回で切り替える

手動のログインが成功し、手動のログインから設定を登録した後に、欄「手動のログインから登録した設定」の「次から自動でログインする」の「自動ログインの設定へ進む」から、資格情報の画面（`/credentials/<profileId>`）の「自動ログインに切り替える」へ進みます。プロファイルの詳細の同じ欄からも進めます。この欄は、認証の設定のある、有効な、手動のログインのプロファイルにだけ出ます。

1 つの画面に、次の 3 つを出します。

| 中身 | 内容 |
| --- | --- |
| 認証の方式 | 今の方式（手でログインする）と、保存の後の方式（自動でログインする）。 |
| ログインの欄のセレクタ | ユーザー名の欄・パスワードの欄・送信のボタンの CSS セレクタ。最後の手動のログインのときに、ログインの画面でそれぞれの欄の候補が 1 つだけだった要素から作った案を入れて出し、「推測（確かめてください）」の印と根拠を付けます。案が違っていれば直せます（直した欄は「人が決める」の印になります）。案のない欄は、人が入れます。 |
| ログインに使う資格情報 | ユーザー名と、パスワードを 2 回。人がこの画面で入れます（手順 4 と同じ決まり）。 |

- **セレクタの案の作り方**: 手動のログインの段の始めに、ログインの画面の見える欄を、入口の確かめと同じ部品で読みます（ユーザー名の欄は見える・押せる `input` の text・email・tel、パスワードの欄は見える `input[type=password]`、送信の要素は同じフォームの送信のボタン）。各欄の候補がちょうど 1 つのときだけ、その要素だけに当たる CSS（`#id`、`tag[name="…"]`、`tag[type="…"]` の順）を案にします。秘密に見える `id`・`name`（長い 16 進、token や JWT の形、メールアドレスの形など）は案に使わず、ほかの形がちょうど 1 つに当たればそれを、なければ案なしにします（入口の確かめの案も同じです）。**入力の値は読みません。** 人が手動のログインで入れた値を、BeakSight は一度も読みません。案は、ログインが成功したときだけ、ジョブの記録（ログインの段のまとめ）に残します。認証の設定には、確認の後の保存まで入れません。SPA などで、ログインの画面を開いた時点で欄がまだ出ていないときは、案を作れません（人が入れます）。案は、最後の手動のログインのジョブのものだけを使います。そのジョブに案がなければ、前のジョブの案には戻らず「案なし」にします。そのジョブの後にプロファイルの改訂が変わった（そのジョブの自動の登録で進んだ場合を除く）ときも、案を使いません。
- **確認のダイアログ**: 「変更を確かめる」で、変えるもの（認証の方式、3 つのセレクタ、ログインの段の POST の回数の上限（自動ログインは 1 回）、資格情報の登録）と、プロファイルの改訂が進むことを出します。承認したシナリオがあれば、その数と、承認が外れて再承認が要ることも出します。パスワードは、ダイアログにも出しません。
- **保存の順**: 「保存する」を押すと、次の順に行います。
  1. 全部を確かめます（プロファイルと、画面が読んだ改訂、認証の設定が今の改訂に結びついているか、方式を変えたプロファイルの確かめ、セレクタを入れた認証の設定の確かめ、資格情報の確かめ（Windows か、ジョブが動いていないか、ログインの Origin、2 回入れたパスワードの一致））。どれかが通らなければ、何も保存しません。
  2. 資格情報のファイルを書きます（暗号化は手順 4 と同じ）。資格情報のファイルがすでにある（自動ログインでなくなったプロファイルに残ったファイル）ときは書かず、何も保存しません。先に資格情報の画面で残ったファイルを削除してください。
  3. 管理データ（プロファイルの認証の方式と、認証の設定のセレクタと回数の上限）を、1 回の書き込み（1 つのトランザクション）で保存します。プロファイルの改訂が 1 つ進みます。
  4. 管理データで失敗したとき（別の保存が先に改訂を進めたときを含む）は、書いた資格情報のファイルを消して、前の状態に戻します。消せなかったときは、その旨を画面に出します（資格情報の画面で削除してください）。
- 失敗の条件（資格情報の誤りなど 4 つ）は、今の認証の設定にあればそのまま、なければ「使わない」で保存します。要るときは、保存の後に認証の設定の画面で足してください。
- **ログインの確かめは自動では始めません。** 保存の後の画面に「ログインを確かめる」のボタン（次の手順）を出します。自動ログインの間隔と上限（手順 5）に数えるため、確かめるときに人が押してください。

### 5. ログインを確かめる

一覧かプロファイルの詳細の「ログインを確かめる」から、ログインだけを 1 回試すジョブ（ジョブの種類「ログインの確かめ」）を始めます。監査は行わず、ブラウザも開きません。Run も成果物も作りません。

- 始められないときは、理由を表示し、開始のボタンを出しません。資格情報がない（`CREDENTIAL_MISSING`）、保存したログインの Origin が今の認証の設定と違う（`CREDENTIAL_STALE`。入れ直しが要る）、暗号化を使えない（`CREDENTIAL_PROTECTION_UNAVAILABLE`）、自動ログインを止めている（`AUTO_LOGIN_HELD`）、間隔・回数・`Retry-After` の上限の中（`AUTO_LOGIN_RATE_LIMITED`。次に始められる日時も表示）、などです。
- 結果は、ジョブの画面の「自動ログイン」の欄に、結果、ログインを送信したか、サーバが示した次に試してよい日時（429 のとき）、フォームの確かめで止めた理由とともに表示します。

### 6. 結果ごとにすること

| 結果 | 送信 | 自動ログインを止めるか | すること |
| --- | --- | --- | --- |
| `SUCCEEDED`（成功） | した | 止めない | 監査を始められます（手順 7）。 |
| `INVALID_CREDENTIALS`（資格情報の誤り） | した | 止める | テスト環境で正しいユーザー名とパスワードを確かめ、資格情報を変更し（手順 9）、停止を解きます。 |
| `ACCOUNT_LOCKED`（アカウントのロック） | した | 止める | テスト環境の管理者にロックの解除を頼み、解除を確かめてから停止を解きます。 |
| `MFA_REQUIRED`（人の操作が必要） | した | 止める | MFA のあるアカウントは使えません。MFA を求めないテスト用のアカウントに変えます。 |
| `CREDENTIAL_EXPIRED`（パスワードの期限切れ） | した | 止める | テスト環境でパスワードを新しくしてから、パスワードを変更します。 |
| `RATE_LIMITED`（回数の制限。HTTP 429） | した | 止める | 時間をおきます。サーバが示した日時（`Retry-After`）を過ぎるまでは、停止を解いても始められません。 |
| `AUTH_RESULT_UNKNOWN`（結果が分からない） | した、または分からない | 止める | どの条件にも当たらない、2 つ以上に当たる、サーバの誤り（5xx）、途中で監査の process が終わった、などです。テスト環境でアカウントの状態を確かめ、成功の条件と失敗の条件を見直します。 |
| `LOGIN_FORM_INVALID`（フォームの確かめで止めた） | していない | 止めない | 表示された理由（セレクタが 1 つに当たらない、POST でない、送信先が違う、など）を見て、認証の設定のセレクタとログインの送信先を見直します。 |
| `LOGIN_FORM_INPUT_FAILED`（値を入れられなかった） | していない、または分からない | 分からないときは止める | セレクタを見直します。止めたときは、アカウントの状態を確かめます。 |
| `CREDENTIAL_CHANGED`（開始の後に資格情報が変わった） | していない | 止めない | 資格情報の画面で今の状態を確かめてから、もう一度始めます。 |
| `CREDENTIAL_UNAVAILABLE`（復号できない） | していない | 止めない | 保存したときと同じ Windows の利用者で画面のサーバを動かしているかを確かめます。直らなければ、削除して登録し直します。 |
| `UNEXPECTED_LOGIN_REQUEST`（ログインの画面の予期しない送信） | していない、した、または分からない | 送信が「していない」でなければ止める | 値を入れてからログインの送信までの間に、ログインの画面が、ログインの送信のほかの要求（画像、別のサイト、別のフォーム、GET に変えた送信など）を出そうとしたので、止めて中止しました。値は送っていません。成功の条件に当たっていても成功にしません。ログインの画面が、入力の値を別の要求で送る作りになっていないかを確かめます。BeakSight はこの形のログインを自動では扱えません。 |
| `UNSUPPORTED_AUTH_STATE`（扱えないログインの形） | した | 止めない | ログインは成功しましたが、許可した Origin の Cookie も localStorage もありません。この形のログインには対応していません。 |

- **止めた自動ログインを再び許す**: 「ログインを確かめる」の画面の「確かめたので自動ログインを再び許す」（確かめのダイアログ）か、資格情報の変更の画面の「自動ログインの停止も解く」（明示の選択）で解きます。テスト環境のアカウントを確かめてから解いてください。解いても、最小の間隔と `Retry-After` は守ります。
- **資格情報を変えただけでは、停止は解けません。** ロックや回数の制限は、サーバの側で続いているかもしれないためです。

### 7. 監査する

左のメニューの「サイトとプロファイル」の一覧で、そのプロファイルの行の「最後の Run」の列にある「監査を始める」を押します（プロファイルの詳細の画面の欄「監査を始める」からも始められます）（同じ行に「ログインを確かめる」もあります）。開始の画面が開きます。「BeakSight が保存した資格情報で自動でログインします。ブラウザは開きません」の案内と、自動ログインの状態（今すぐ始められる、止めている、次に始められる日時）を確かめて、開始します。

- 自動ログインが成功すると、ログインの状態を監査の process のメモリの中だけで新しい監査用のブラウザ（headless）に渡し、手動のログインと同じく、読み取り（GET と HEAD）だけで監査します（「[認証つきの監査の手順 6](authenticated-audit.md#6-監査)」）。
- 自動ログインが成功以外で終わると、監査を始めずに終わります（手順 6 の表のとおり）。
- 自動ログインの試しは、ログインの確かめと監査の両方で、同じ上限に数えます。

### 8. セッションが切れたら

監査の途中で、セッションが切れたと判定するパスの画面に移ったら、手動のログインと同じく、その Run を一部未完了で止めます（「[認証つきの監査の手順 7](authenticated-audit.md#7-セッションが切れたら)」）。監査の途中で、自動でログインし直すことはしません。

同じプロファイルで「前回の続きから再開する」を選んで開始すると、**もう一度自動ログインしてから**、止まったページから続けます。このログインも上限に数えるので、前の試しから最小の間隔をあけるまでは始められません。

### 9. 資格情報を変える・入れ直す・削除する

資格情報の画面（プロファイルの詳細の「資格情報を開く」）で行います。そのプロファイルのジョブ（監査かログインの確かめ）が動いている間は、変更も削除もできません（`CREDENTIAL_IN_USE`）。

- **ユーザー名だけを変える**: 「ユーザー名を変える」を選び、新しいユーザー名を入れます。パスワードは、保存してある暗号文をそのまま使います（戻しません）。
- **パスワードだけを変える**: 「パスワードを変える」を選び、新しいパスワードを 2 回入れます。ユーザー名は、保存してある暗号文をそのまま使います。
- 両方を選ぶと、両方を変えます。どちらも選ばないときと、空の欄は、保存しません（空の欄は「消す」の意味になりません）。
- **入れ直し**: 認証の設定のログインの画面の Origin を変えたときは、保存した資格情報は使えなくなります（「入れ直しが必要」）。ユーザー名とパスワードの両方を入れ直します。
- **削除**: 確かめのダイアログの後に、資格情報のファイルを消します。それ以降、もう一度登録するまで、自動ログインとログインの確かめは始められません。
- **プロファイルの取り消し**: プロファイルを取り消すと、取り消しが成功した後に、そのプロファイルの資格情報のファイルも消し、削除を記録します（ファイルがなければ何もしません）。ジョブが動いている間に取り消した場合などで消せなかったときは、取り消しは成功のままで、画面に案内が出ます。資格情報の画面から削除してください（取り消したプロファイルでも削除はできます）。
- **自動ログインでなくなったプロファイル**: 認証の方式を自動ログインから変えたプロファイルに資格情報のファイルが残っているときは、資格情報の画面（`/credentials/<profileId>`）に削除の操作だけが出ます。登録・変更・入れ直しはできません。
- 変更・入れ直し・削除と停止の解除は、管理データに種類と日時と改訂の番号だけを記録します（値も値のハッシュも記録しません）。

## スクリプトで送るログインの自動ログイン

認証の設定の「ログインの送り方」を「スクリプトの送信」にしたプロファイル（「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」）でも、自動ログインを使えます。画面の中のスクリプトが、承認したサービスの Origin へ token を取りに行く形のログインです。

> テスト用の小さなサイトで、ワーカーの自動ログインと、その後の監査を確かめています。本物の Windows の暗号化（DPAPI）で保存した資格情報での、スクリプトで送るログインの自動ログインは、まだ流していません。実際のテスト環境でも、まだ確かめていません。

### 流れ

1. **ログインの画面を開きます。** 画面そのものの応答が 429 なら「回数の制限」、5xx なら「結果が分からない」で、値を入れずに終わります。
2. **値を入れる前に、フォームを確かめます。** 3 つのセレクタがそれぞれちょうど 1 つの要素に当たること、パスワードの欄が `type="password"` であること、送信の先が同じ画面であることを確かめます。フォームの送り方（method）と送信先（action）は確かめません（送るのはスクリプトで、送信先は Guard が token の送信先と照らすためです）。3 つの要素の置き方は、次のどちらかであれば通します。
   - 3 つとも同じ form の中にある。
   - 3 つとも form の外にある（form のない画面）。このときは、さらに次を確かめます: 3 つが見えていること、ユーザー名とパスワードの欄が編集できること、送信の要素が押せること、送信の要素が `button`・`input[type=submit]`・`input[type=button]`・`role="button"` の要素のどれかで、`href` を持たないこと。外れたら、その要素の理由で止まります。
   - 一部だけが form の中にある画面と、別々の form の中にある画面は、止まります（「フォームの確かめで止めた」）。
3. **資格情報の持ち出しの守りを付けてから、値を入れて押します。** 下の「資格情報の持ち出しの守り」のとおり、token の送信のほかのすべての要求を照らします。
4. **token の送信は 1 回だけ通します。** 送信の窓（フォームの送信の自動ログインの「送信の窓」）は使いません。持ち出しは、資格情報の守りが受け持ちます。
5. **token の送信の応答の状態で、結果を決めます**（下の表）。2xx のときは、成功の確かめ（ログインが済んだと判定するパスと任意のセレクタ、成功のローカル ストレージの鍵の名前、token の送信を 1 回以上通したこと）を待ちます。

### 結果の区分

| token の送信の応答など | 結果 | 自動ログインを止めるか |
| --- | --- | --- |
| 400・401 | 資格情報の誤り（`INVALID_CREDENTIALS`） | 止める |
| 429 | 回数の制限（`RATE_LIMITED`）。サーバが示した待つ時間（`Retry-After`）から、次に始められる時刻を決めます（上限 24 時間） | 止める |
| 423 | アカウントのロック（`ACCOUNT_LOCKED`） | 止める |
| 5xx、表にないほかの状態、応答がない、時間の上限までに決まらない | 結果が分からない（`AUTH_RESULT_UNKNOWN`）。token の送信に応答がなかった回は、試しを 2 回と数えます（フォームの送信の自動ログインの、応答がなかった回と同じ扱い） | token を送っていれば止める |
| 2xx | 成功の確かめに進みます。確かめが済めば成功（`SUCCEEDED`） | 成功なら止めない |
| 資格情報を含む要求を止めた（下） | 結果が分からない（`AUTH_RESULT_UNKNOWN`）。成功の条件を満たしても、成功にしません | 止める |
| ログインの画面が閉じた、token の送信が上限を超えた | 結果が分からない（`AUTH_RESULT_UNKNOWN`） | token を送っていれば止める |

- 止めた自動ログインは、人が確かめて解くまで、次を始められません（「[結果ごとにすること](#6-結果ごとにすること)」と同じです）。ログインを送る前に止まった場合（token を送っていない）は、止めません。
- 資格情報を含む要求を止めたときの「送信」は「分からない」として記録し、自動ログインを止めます。
- 上限（同じプロファイルで 5 分以上あける、24 時間に 10 回まで、`Retry-After` を守る）は、フォームの送信の自動ログインと同じです（「[ログインの送信の回数と上限](#ログインの送信の回数と上限)」）。
- 429 の後に次を始めようとすると、自動ログインを止めている間は、理由「止めている」（`AUTO_LOGIN_HELD`。次に始められる時刻はありません）で始められません。人が止めた状態を解いた後も、`Retry-After` の期限の前なら、理由「回数の制限」（`AUTO_LOGIN_RATE_LIMITED`）と、次に始められる時刻を出して始められません。

### 資格情報の持ち出しの守り

- ログインの段で、承認した token の送信のほかのすべての要求（登録したログインに伴う送信、ページの移動、読み取り、ページの送信、Worker の要求、フォームの既定の送信など）を照らし、入れたユーザー名かパスワードが含まれていれば、その要求を止めます。token の送信そのものは照らしません。
- 比べる所:
  - パスワード: すべての要求（読み取りを含む）の URL、本文、ヘッダ（`Referer` を含む）、その要求に付く Cookie（名前と値）。
  - ユーザー名: 読み取りでない要求の URL、本文、ヘッダだけ（画面がログインの後にユーザー名で読み、セッションの保存にもユーザー名を持つのが普通のためです）。
  - 要求に付く Cookie は、送る前に読みます。読めなければ、含まれるとみなして止めます。
- 比べる形:
  - 入れた値の側は 3 つの形です: そのまま、URL の符号化の形（`%20` と `+` の空白、フォームの符号化の形を含む。16 進の大文字と小文字は区別しません）、JSON の文字列の符号化の形。
  - 要求の側は、そのままの文字列に加えて、`%XX` を戻した形と、さらに `+` を空白に直した形でも比べます（ブラウザが一部の文字だけを `%` の形にする URL に、値をそのまま連結した場合を見つけるためです）。
- 本文を読めない要求（本文があるのに部品が取れない、file や blob の部品を持つ）は、含まれるとみなして止めます。
- 4 文字より短い値は、部分一致で正しく比べられないので、どの要求にも含まれるとみなします（そのため、短い値ではログインの画面そのものを読めません。資格情報の登録は、4 文字未満を受け付けません。「[4. 資格情報を登録する](#4-資格情報を登録する)」）。
- **ログインの後の状態**: 成功を返す直前に、監査に引き継ぐ状態（Cookie の名前と値、ローカル ストレージの鍵と値）にパスワードが含まれていないかを比べます。含まれていれば、「結果が分からない」で止め、状態を監査に引き継ぎません（自動ログインも止まります）。
- 止めた要求は、Safety Ledger にも止めた一覧の表にも載せず、数だけを数えます（URL の query や path に値が入っているためです）。ジョブの詳細の画面のパネル「ログインの段で止めた送信」の欄「資格情報を含む要求を止めた数」に出ます。この数は、「止めた読み取りでない送信」の数には含めません（読み取りの要求も含むためです）。
- 値は、この守りの部品の中だけで持ち、ログインの段を閉じたら捨てます。記録、ワーカーとの通信、管理データ、誤りの文に、値も長さも残しません。比べるための形は、ログインの段の終わりまでメモリに持ちます（「平文を持つ時間」の例外です）。
- 限界:
  - base64、値を分けた形、逆順、`\u` の形の符号化、別の文字コード、二重の符号化で値を運ぶ要求は、見分けません。
  - token の送信そのものは比べません。
  - 4 文字より短い値は比べません（どの要求にも含まれるとみなし、登録で拒みます）。4 文字未満の拒否は、「フォームの送信」のプロファイルの資格情報にも当たります。
  - 本文にだけ値を入れた要求が、ほかの決まり（登録していない送信など）で止まったときは、その決まりの理由で数えます（値は届きません）。
  - 手動のログインでは比べません（利用者が入力するためです）。

## 守りの範囲

### 資格情報の保存

- **保存の場所**: リポジトリの `local/secrets/<profileId>.credential.json`（Git の管理の外）。ユーザー名とパスワードを、それぞれ別に、Windows の DPAPI（今の Windows の利用者だけが戻せる形）で暗号化して保存します。暗号化には、プロファイルの ID、ログインの Origin、項目の名前を加えるので、ほかのプロファイルへの付け替えや、ユーザー名とパスワードの入れ替えでは戻せません。
- **フォルダの権限**: フォルダを作った直後に、継承を外し、今の Windows の利用者だけに読み書きを許します。書く前に毎回、所有者と許可が今の利用者だけであることを確かめ、違えば書きません（`CREDENTIAL_STORAGE_UNSAFE`）。
- **リンクを拒む**: 読む前と書く前（登録、変更、入れ直し、削除）に、`local` と `local/secrets` が junction や symlink でない本物のフォルダであること、資格情報のファイルが普通のファイルで、symlink でもハードリンク（リンクの数が 2 以上）でもないことを確かめ、外れたら読み書きしません（`CREDENTIAL_STORAGE_UNSAFE`。読み出しでも値を返しません）。ハードリンクになったファイルは、画面からは削除できません。人がエクスプローラーなどで消してください（消した後に、もう一度登録します）。
- **置き換え**: 同じフォルダの一時のファイルに書いてから置き換えます。置き換えられなかったときは、古いファイルを残します。画面のサーバは、起動のときに、残った書きかけの一時のファイルを消します。
- **値を出さない**: 値は、画面、Server Function の応答（誤りの応答を含む）、画面のサーバと監査の process のログと出力、成果物（Run のディレクトリ）、管理データ、監査の process との間の通信（IPC）のどこにも出しません。誤りは、コードと項目の名前だけを返します。
- **平文を持つ時間**: 画面のサーバは、保存の要求の処理の間だけ平文を持ち、暗号化の後に捨てます。復号するのは、ログインする監査の process だけで、フォームに値を入れる直前に戻し、入れた後に捨てます。例外: スクリプトで送るログインの自動ログインでは、資格情報の持ち出しの守りが、比べるための形をログインの段の終わりまでメモリに持ちます（「[資格情報の持ち出しの守り](#資格情報の持ち出しの守り)」）。IPC で送るのは、資格情報の改訂の番号（秘密でない）だけです。
- **暗号化の処理**: Windows PowerShell（絶対パス）を、決まった引数と決まった本文（`-EncodedCommand`）で起動し、値は標準入力で渡します。値を、起動の引数・本文・環境変数に入れません。1 回の上限は `CREDENTIAL_PROCESS_TIMEOUT_MS`（10 秒）です。

### 送信の前のフォームの確かめ

値を入れる前に、ログインの画面のフォームを読むだけで確かめます。どれかが外れたら、値を入れずに `LOGIN_FORM_INVALID`（理由のコードつき）で止めます。

- 3 つのセレクタが、それぞれちょうど 1 つの要素に当たる。BeakSight は、ページの JS から切り離した読み取り（isolated world）の中で、document と open な shadow root ごとに標準の CSS として探し直して数えます。Playwright で数えた数と違えば、読めないとして止めます（理由「ログインのフォームを読めませんでした」）。
- ユーザー名の欄、パスワードの欄、送信のボタンが、同じフォームの中にある。
- フォームの送り方が POST（送信のボタンの `formmethod` を含む）。GET のフォームに値を入れると、資格情報が URL の query で届くためです。
- 送信先（送信のボタンの `formaction` を含む）の Origin と path が、認証の設定の「ログインの送信先」と完全に一致する。
- パスワードの欄が `type="password"`。フォームの送信の先が、同じ画面（`target` が自分の frame）。
- 値を入れた後にも、もう一度確かめます（ページのスクリプトが、値を入れたときにフォームを変える場合に止めるため）。

### ログインの送信の回数と上限

- 1 回のジョブで、BeakSight がログインの送信（POST）を通すのは 1 回だけです（`AUTO_LOGIN_MAX_LOGIN_POSTS_PER_JOB`）。2 回目の送信（ページのスクリプトがもう一度送るなど）は、ログインの段の守り（Guard）が止めます。ただし、サーバがログインの送信を受けた後、応答を返す前に接続が切れると、ブラウザが同じ送信を自動でもう一度送ることがあり、サーバには 2 回届くことがあります（DEF-099）。この送り直しは Guard より下の層で起きるので、Guard では止められません。このため、下の上限では、応答がなかった回を 2 回と数えます。
- 同じプロファイルの自動ログインどうしは、5 分（`AUTO_LOGIN_MIN_INTERVAL_MS`）以上あけます。
- 同じプロファイルで、24 時間（`AUTO_LOGIN_DAILY_WINDOW_MS`）に 10 回（`AUTO_LOGIN_DAILY_MAX_ATTEMPTS`）までです（成功を含みます。試し始めた数で数えます）。ログインの送信に応答がなかった回（応答の前に接続が切れた回など）は、2 回と数えます。応答の前に接続が切れると、ブラウザがログインの送信を自動でもう一度送ることがあり、サーバには 2 回届いたかもしれないためです（DEF-099）。管理データには、その回の試しを 2 行書きます（2 行目も「送った」・同じ結果・同じ試し始めた時刻）。応答があった回（500 などの誤りの応答を含みます）は 1 回です。結果が決まらずに終わった試し（監査の process が途中で終わった回、画面のサーバが終わった回）も、すべて 2 回と数えます。BeakSight は、こうした回で送ったかどうかを確かめられないため、ログインを送る前に終わった回も含めて、多く数える側にしています（試しの行を 2 行書きます。2 行目も同じ結果・送信は「分からない」・同じ試し始めた時刻）。監査の process を起動できなかった回は、送っていないことが分かるので 1 回です。ログインの送り方は変えていません（書き込みの送信と違い、ブラウザが送ります）。
- サーバが回数の制限（HTTP 429）で示した待つ時間（`Retry-After`）を守ります。上限は 24 時間（`AUTO_LOGIN_MAX_RETRY_AFTER_MS`）で、それより長い値や読めない値は 24 時間とみなします。
- ログインの送信の後に結果を待つのは 30 秒（`AUTO_LOGIN_RESULT_TIMEOUT_MS`）までです。決まらなければ「結果が分からない」です。
- ログインを送った後に成功以外で終わると（監査の process が途中で終わり、送ったかが分からない場合を含む）、人が確かめて解くまで、そのプロファイルの自動ログインを止めます。資格情報の変更だけでは解けません。
- これらの値は、ユーザーの承認を得た値です（Task 26 の設計書 10 章）。

### ログインの段の通信の制限

- **許可 Origin の外へは何も送らない**: ログインの段（自動ログインと、Task 25 の手動のログインの両方）では、ターゲット設定の `site.allowedOrigins` の外への要求を、種類を問わずすべて止めます（画像、スクリプト、stylesheet、フォント、fetch、XHR、beacon、WebSocket、media、先読み、サブ frame のナビゲーション、main frame のナビゲーション、popup）。止めた数は、ログインの段の記録に、種類ごとに数えます（URL と値は記録しません）。
- **送信の窓**: 自動ログインでは、値を入れ始める直前から、許したログインの送信（送信先への main frame のナビゲーションの POST）を通すまでを「送信の窓」とし、窓の中では、その送信のほかのすべての要求を止めます（同じ Origin の GET、サブリソース、サブ frame、WebSocket、beacon などすべて）。窓は、ログインの段の守り（Guard）が、許したログインの送信を通した時点で閉じます（送信を通さなければ、結果を待つ時間の上限まで開いたままです）。窓の中で要求を止めたら、ページが入力の値を別の要求で送ろうとしたものとして、結果を `UNEXPECTED_LOGIN_REQUEST` にします。値を入れた後、押す前に止めた場合は、押さずに中止します（送信は「していない」）。
- **ブラウザ自身の favicon**: 窓の中の、許可 Origin の `GET /favicon.ico`（query なし）は、止めますが、`UNEXPECTED_LOGIN_REQUEST` の理由には数えません（ブラウザ自身が取りに行くことがあり、値を運べないため）。query つきの favicon は理由に数えます。
- 窓を設けるのは自動ログインだけです。手動のログインの段は、人が値を入れるので窓の始まりを決められず、窓を設けません（許可 Origin の外への制限は働きます）。

### 手動の方式へ切り替えない

自動ログインが失敗しても、BeakSight は、人がログインするためのブラウザ（手動のログイン）を開きません。手動のログインに変えるのは、人がプロファイルの認証の方式を変えたときだけです。

### デバッグの環境変数を外す

監査の process を起動するときに、Playwright や Node のデバッグの出力を有効にする環境変数（`WORKER_EXCLUDED_ENVIRONMENT_VARIABLES`: `DEBUG`、`DEBUG_FILE`、`PWDEBUG`、`PWDEBUGIMPL`、`NODE_DEBUG`、`NODE_DEBUG_NATIVE`、`NODE_OPTIONS`）を外します。デバッグの出力には、フォームに入れた値が出ることがあるためです。公開の監査を含む、すべての監査の process で外します（公開の監査の出力は変わりません）。

### ログインの段の記録

ログインの段の Safety Ledger と、ページの console の文は、保存も表示も、監査の process との間の通信もしません。ページのスクリプトが送ろうとした要求の URL に、ユーザー名が入りうるためです。

### 確かめたこと（目印の検査）

テスト用の小さなサイトで、実行ごとのランダムな値をユーザー名とパスワードの目印にし、画面から登録・変更（ユーザー名だけ、パスワードだけ）・削除し、ログインの確かめと、自動ログインの後の監査を行って、目印が 1 つも出ないことを、UTF-8 と UTF-16LE の両方のバイトで確かめています（本物の DPAPI。Windows）。

- 場面: 成功、資格情報の誤り（止める）、フォームの確かめで止まる、セッションが切れて止まった後の再開、ログインの送信の途中で監査の process が落ちる。変更の前と後の両方の値を探します。
- 探した場所: Run のディレクトリのすべてのファイル（再開のための保存と、ZIP の中身を含む）、管理データのファイルと WAL と SHM と、すべての表のすべての行、資格情報のフォルダのすべてのファイル（暗号文の中に平文がないこと。一時のファイルが残らないこと）、画面のサーバと監査の process の標準出力と標準エラー、監査の process との間の通信のすべて（両方の向き）、画面の HTML（すべての画面と成果物の画面）と Server Function の応答（誤りの応答を含む）、PowerShell の起動の引数と本文。
- 探す読み方が正しいことは、わざと目印を置いたファイル（UTF-16LE、圧縮した ZIP の中、SQLite の WAL など）で見つかることで確かめています。

## 確かめていないこと・残る危険

- **Windows のイベントログ**: PowerShell は、暗号化の処理（ProtectedData を使うスクリプト）の本文を、Windows のイベントログ（PowerShell の Operational のログ。イベントの ID 4104）に自動で記録します。本文は決まった文で、値（平文と暗号文）は入りません（調査で確かめました）。イベントログは、BeakSight からは消せません。
- **人のブラウザのパスワードの保存**: 資格情報の画面で入れたパスワードを、人のブラウザが保存を勧めることがあります。保存すると、ブラウザのパスワードの管理に残ります。BeakSight からは止められません。
- **同じ Windows の利用者の権限で動くもの**: DPAPI は、今の Windows の利用者の権限で動くほかのプログラム、管理者、SYSTEM の権限からは、資格情報を守れません。
- **別の PC や別の利用者に写したファイル**: 資格情報のファイルは、保存した PC の保存した利用者でしか戻せません。リポジトリを別の PC や別の利用者に写した場合は、資格情報を削除して登録し直します（「復号できない」の結果になります）。
- **確かめてから使うまでの間の入れ替え**: リンクの確かめ（上の「リンクを拒む」）と、実際に読む・書くまでの間に、フォルダやファイルを junction やハードリンクに入れ替えられると、見分けられません（確かめと使う間の競争。完全には防げません）。入れ替えには、今の Windows の利用者の権限が要ります（そのような権限を持つプログラムからは、上の「同じ Windows の利用者の権限で動くもの」のとおり、もともと守れません）。
- **広い権限のフォルダ**: `local/secrets/` が、BeakSight が作る前から、広い権限（ほかの利用者が読める、継承がある）で存在すると、BeakSight は自動では絞り直さず、保存を拒みます（`CREDENTIAL_STORAGE_UNSAFE`）。中に要るファイルがないことを確かめてから、そのフォルダを消し、もう一度登録します（BeakSight が作り直し、権限を絞ります）。
- **送信の窓の外に残ること**: ログインの段では、許可 Origin の外へは何も送りません。また、送信の窓（値を入れ始めてから、許したログインの送信を通すまで）の中では、ログインの送信のほかは何も送りません。窓の外では、次のことが残ります。
  - **値を入れる前**: ページのスクリプトは、まだ値を持っていません（BeakSight は、窓を開いてから値を入れます）。
  - **ログインの送信の後**: 窓を閉じた後は、ログインの段の通常の判定に戻り、許可 Origin への読み取り（GET と HEAD）を許します。ページのスクリプトが、入力の値をページの中（Cookie、localStorage、変数など）に残しておき、ログインの送信の後の画面で、許可 Origin への GET の要求（URL や Cookie のヘッダ）に載せて送ると、その値は許可 Origin のサーバ（対象のテスト環境）に届きます。許可 Origin の外へは届きません。ログインの送信の後の画面でのこの形は、検知しません。
  - **ログインの送信の直後のページの離脱**: 送信の窓は、許したログインの送信（POST）を Guard が通した時点で閉じます。そのため、ログインの画面そのものが、ページを離れるときの受け手（`pagehide`・`unload`）で入力の値を読み、同じ Origin への GET（`fetch` の keepalive、画像など）で送ると、その値は対象のテスト環境のサーバに届き、BeakSight は検知しません。許可 Origin の外へは届きません。
  - **手動のログインの段**: 人が値を入れるので、窓を設けません。ページのスクリプトが、入力の値を、許可 Origin への GET の要求に載せて送ると、対象のテスト環境のサーバに届きます。許可 Origin の外へは届きません。
- **人の操作の代わりの範囲**: 確かめは、headless のブラウザと、テスト用の小さなサイトで行いました。実際のテスト環境でのログインと監査は、まだ確かめていません（ユーザーの承認の後に、小さく確かめます）。
- **ブラウザの一時のプロファイル**: 監査の process のブラウザは、ログインごとに新しい記録の残らないコンテキストで動きますが、ブラウザ自身の一時のフォルダの中身は、目印の検査の対象にしていません（推測: 記録の残らないコンテキストなので、値は書かれません。確かめていません）。

## 使えないこと

- Windows 以外での自動ログイン。
- 別の Origin のログインのサービス（IdP。シングルサインオン）、多要素認証（MFA）、CAPTCHA。
- sessionStorage や IndexedDB に頼るログイン。画面の中のスクリプトで送るログインは、「スクリプトの送信」の設定のときだけ扱います（「[スクリプトで送るログインの自動ログイン](#スクリプトで送るログインの自動ログイン)」）。
- 監査の途中での自動の再ログイン（セッションが切れたら止まり、再開で自動ログインし直します）。
- 無人の定期実行（人が画面から始めます）。
- 環境変数、Windows の資格情報マネージャー、平文のファイルによる資格情報の受け渡し。
- CLI からの自動ログイン。
