# 入力の規則とデータの生成（テスト環境だけ）

承認した書き込みのシナリオ（「[書き込みのシナリオの承認](scenario-approval.md)」）の、送る欄に入れる値の作り方（入力の規則）と、BeakSight がそれを決めて保存し、承認に縛るしくみです。値の作り方の決まり、同じ入力で同じ値になる仕組み、重ならない値の作り方、止まる場合、守りの範囲、確かめていないことも書きます。
画面での扱いは「[管理画面の入力の規則](local-ui.md#入力の規則送る値の作り方)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 画面の言葉は、この文書の言葉と違います（入力の規則は「入れる値の決まり」、シナリオは「書き込みの手順」、承認は「書き込みの OK」など）。対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」にあります。**入力の規則を人が見たり直したりする画面はありません。** シナリオの下書きを作るときに、BeakSight が規則を推して付けます（下の「[決まり方](#決まり方)」）。

> **規則を決めて保存するときは、書き込みをしません。** ここで決めた規則から、承認された登録（「[承認された登録の手順](approved-create.md)」）と更新（「[承認された更新の手順](approved-update.md)」。変える欄だけ）が、書き込みのたびに送る値を作ります。テスト用の小さなサイトで確かめています。実際のテスト環境では、API の登録 1 件の値を、推した規則で作って送りました（「[実テスト環境で確かめたこと](real-test-environment.md#実テスト環境で確かめたこと2026-11-02-時点)」）。

## 何をするか

- シナリオの送る欄ごとに、入れる値の作り方を決めます。値は **LLM を使わず**、欄の型と制約、小さな辞書、3 つの業務テンプレート（顧客・予約・商品）から、決まった手順で作ります。
- 作り方が決まらない欄は、推し量って作らずに止めます（`NEEDS_RULE_INPUT`）。決まりがぶつかるときも止めます（`RULE_CONFLICT`）。メールや SMS が実際に届く値は作りません。
- 送る欄すべての作り方が決まっていないシナリオには、実行の許可（書き込みのジョブを始めるための許可）を出しません（`NEEDS_RULE_INPUT`。どの欄の、どの理由かを添えます）。
- **自動で付ける**: シナリオの下書きを作るとき（一覧のチェックの保存、点検の中の自動の下書き、操作さがしの画面の「書き込みの手順を作る」）に、規則がまだない下書きなら、BeakSight が推した規則の集まり（下の「[自動で作った規則](#自動で作った規則推した規則の保存)」）を作って付けます。推せない欄が残ったときは、シナリオの詳細の要点に「BeakSight が入れる値を決められない欄があるので、この画面は試せません。」と出ます。

## 使ってよい場合

- **テスト環境だけに使います。本番には使いません。** 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）のプロファイルのシナリオだけで使えます。ほかのモードでは、規則の保存を拒みます（`RULE_SET_MODE_NOT_WRITE`）。
- 作った値は、承認された登録と更新で、テスト環境のレコードに書き込まれます。登録されてよい値か、メール・SMS・外部の通知が送られない設定かを、テスト環境の管理者と確かめてから使ってください。

## 決まり方

- シナリオの下書きを作るときに、BeakSight が規則を推して保存し、シナリオに付けます（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）。
- 推せない欄がある画面は、試せません。シナリオの詳細の要点に、その 1 行が出ます。
- 人が意味の種類・値の一覧・範囲・関係・一意にする欄の組を決める画面はありません（前の版にあった画面は外しました）。前に人が決めて保存した規則の扱いは「[前に手で作った規則](local-ui.md#前に手で作った規則)」にあります。
- 規則を保存すると、規則の新しい版ができ、シナリオに付け直します。シナリオの版が 1 つ上がり、下書きに戻ります。承認していた場合は「要再承認」になり、理由に「シナリオを編集した」（`SCENARIO_REVISION_CHANGED`）と「入力の規則が変わった」（`INPUT_RULES_CHANGED`）が出ます（「[再承認が要る場合](scenario-approval.md#再承認が要る場合)」）。承認は、規則の版と digest（規則の中身の SHA-256）を縛ります。

### 欄ごとの状態

欄ごとに、次の状態のどれかになります（画面には出しません）。

| 状態 | 意味 |
| --- | --- |
| 決まった | 値の作り方が決まった。 |
| 規則の入力が要る（`NEEDS_RULE_INPUT`） | 作り方が決まらない。その画面は試せない。 |
| 決まりがぶつかる（`RULE_CONFLICT`） | 欄の制約・関係・一意性などがぶつかる。その画面は試せない。 |
| 外部到達で止めた（`EXTERNAL_DELIVERY_BLOCKED`） | メール・電話の欄で、シナリオの副作用の確認が済んでいない（承認と書き込みの開始の確かめでの判定）。 |

- **承認の前は、メール・電話の欄を作れる欄として判定します。** 副作用の確認は、プロファイルの詳細の一覧「登録・更新を試せる画面」のチェックで行うので（「[承認する](scenario-approval.md#5-承認する)」）、承認の前の判定は「承認のときに確認する」前提で行います。承認、実行の許可の発行、書き込みのワーカー、値の生成は、今どおりシナリオの版の確認の値だけで判定します（確認のない版では、書き込みを始めません）。

| 出どころ | 意味 |
| --- | --- |
| 保存した規則（`HUMAN`） | 規則の集まりに保存した規則。最も強い。推したか人が決めたかは、出どころの印で示す（下の「自動で作った規則」）。 |
| 業務テンプレート（`TEMPLATE`） | 欄の名前・型・autocomplete から推した、顧客・予約・商品の規則。 |
| 汎用の規則（`GENERIC`） | 欄の型と制約（数・日時・選択肢・色）から決まる規則。 |
| 送らない側に固定（`OPT_OUT`） | 通知・配信を求める欄を、送らない側に固定した。 |

規則の優先順位は、汎用の規則 → 業務テンプレート → 人の規則（人の上書きが最も強い）です。テンプレートには、サイトに固有の値を書きません。

### 規則の中身

規則は、欄ごとに次を持ちます（推した規則では、BeakSight が決めます）。

- **意味の種類**: 「自動」（業務テンプレートか汎用の規則で決める）か、閉じた一覧の種類（汎用の数・日時・選択・色、姓・名・フルネームとそれぞれのフリガナ、メール、電話、備考、商品名、単価、数量、合計、日付、開始・終了の時刻、人数、固定の一覧、テンプレートの外、番号・コード）です。選べるのは、欄の型に合う種類だけです（合わなければ `SEMANTIC_KIND_TYPE_MISMATCH`）。
- **作り方**: 欄の型と制約から（`FROM_TYPE`）、業務テンプレートと辞書から（`FROM_TEMPLATE`）、人が入れた値の一覧から（`FROM_FIXED_LIST`）。
- **値の一覧**（人が入れた値の一覧から、のときだけ。前に人が保存した規則だけが持ちます）: 件数と長さの上限はありません。値は、欄の型・選択肢・制約に合い、危険な語を含まないものだけです（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。メールの欄は `example.invalid` の宛先だけです。
- **範囲**（最小・最大・刻み）: 数と日時の欄に持ちます。欄の最小・最大の外にはできません（`RANGE_OUTSIDE_FIELD_CONSTRAINT`）。欄に刻み（step）があれば、範囲の最小・最大は欄の刻みの上の値にし、範囲の刻みは欄の刻みの倍数にします（合わなければ `RANGE_OUTSIDE_FIELD_CONSTRAINT`）。数と日時の欄の値の一覧も、欄の刻みの上の値だけを受けます（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。
- 秘密に見える名前（`token`、`session`、`key` など）の欄には、値の一覧を入れられません（規則の保存の部品が拒みます。`RULE_SET_SECRET_FIELD_FIXED_VALUE`）。
- 前に人が入れた値は、管理データにそのまま（平文で）残ります（下の「守りの範囲」）。

### 欄どうしの関係

関係は閉じた一覧の 3 つです。保存した関係に、業務テンプレートの既定の関係を足して当てます（下の「自動で作った規則」の、既定を保存した印のある規則の集まりを除きます）。

- **終了は開始より後**（`END_AFTER_START`）: 開始と終了の時刻（日時）。
- **合計は単価 × 数量**（`TOTAL_EQUALS_UNIT_PRICE_TIMES_QUANTITY`）。判定のときに、合計の欄の制約（最小・最大・刻み、文字の欄なら pattern と長さ）に合う単価と数量の組を求め、組がなければ止めます（`RELATION_UNSATISFIABLE`）。値は、その組から選びます（判定で作れると言えば、作るときも止まりません）。単価と数量のそれぞれの値が `MAX_RELATION_SIDE_VALUES`（100 個）を超えるときは、等しい間隔で間引いた値の組だけを確かめます（間引いた組に合うものがなければ、止める側に寄せます）。
- **フリガナは氏名と同じ人**（`KANA_MATCHES_NAME`）: 氏名の欄 1 つとフリガナの欄 1 つの組です。姓と名で分かれていれば、関係を 2 つ持ちます。

関係の欄が送る欄でないか、意味の種類が役割に合わなければ `RELATION_FIELD_MISMATCH`、範囲の中で満たせなければ `RELATION_UNSATISFIABLE` で止めます。

### 一意にする欄の組

登録するレコードを見分けるための欄の組です（BeakSight の登録を見分ける印は付けません。値の組み合わせで見分けます）。保存した組がなければ、業務テンプレートの既定の組を使います。

- 顧客: 氏名とフリガナの欄すべて。
- 商品: 商品名の欄。
- 予約: 日付・開始の時刻・選択肢の欄。

## 作る値の決まり

### 型と制約で決まる欄（汎用の規則）

- **数**（number・range）: 欄の最小・最大・刻み（と人の範囲）の中の値です。刻みの誤差が出ない形で数えます。range の欄に最小・最大がなければ、HTML の既定（0〜100）を使います。number の欄に最小・最大がなければ止めます（`RANGE_MISSING`）。
- **日時**（date・time・datetime-local・month・week）: 欄の最小・最大（と人の範囲）の中の値です。最小・最大がなければ止めます（`RANGE_MISSING`）。
- **選択肢**（select・radio・checkbox）: 発見した選択肢の値から選びます。空の値と、危険な語に当たる値は使いません（残りがなければ `NO_USABLE_OPTION`）。選択肢の label は使いません。
- **required でない checkbox** は、人が値の一覧を入れない限り、送りません（チェックしません）。名前から通知・同意の欄と分からない欄（`contact_ok`、`allow_call` など）を、受け取る側の値で送らないためです。required の checkbox は、選択肢の値から選びます（通知の語に当たる required の checkbox は、下の「通知・配信を求める欄」のとおり止めます）。
- 数と日時の値は、欄の刻み（step）の上の値だけを作ります。刻みの起点は、欄の最小（なければ HTML の既定の起点。number は 0、date は 1970-01-01 など。value の属性の起点は使いません）です。業務テンプレートの既定の範囲を補うときも、欄の刻みに合わせます。
- **色**（color）。
- 範囲は、欄の最小・最大と人の範囲だけで決めます。業務テンプレートの数と金額の欄にだけ、欄にも人の規則にも最小・最大がないときの一般的な幅（`TEMPLATE_DEFAULT_RANGES`: 人数 1〜4、数量 1〜5、単価 100〜10000（100 刻み））を補います。範囲の手がかりがない日付と数の欄に既定の幅を入れるのは、規則の自動の作成だけです（下の「自動で作った規則」）。
- **番号・コード**（text・search の欄で、pattern が数字だけの決まった桁数のとき。例 `^\d{7}$`、`[0-9]{4}`）: その桁数の数字を作ります。番号・コードを推すのは、推した規則を作って保存するとき（下の「自動で作った規則」）だけです。そのときは、名前の語に当たらない欄も、この pattern があれば推します。辞書から作る種類（氏名・フリガナ・備考・商品名）に当たった欄も、数字だけの pattern なら番号・コードにします。規則を保存していない欄の判定のたびの推しでは、番号・コードを推しません（前と同じく `SEMANTIC_KIND_UNDECIDED` などで止まります）。人が画面で番号・コードを選ぶこともできます。ほかの形の pattern（桁数が決まらない、英字を含む、区切りがあるなど）からは作りません（`PATTERN_UNSUPPORTED`）。

### 業務テンプレートと辞書

| テンプレート | 意味の種類 |
| --- | --- |
| 顧客（`CUSTOMER`） | 姓・名・フルネームとそれぞれのフリガナ（カタカナ）、メール、電話、備考 |
| 予約（`RESERVATION`） | 日付、開始・終了の時刻、人数、選択肢 |
| 商品（`PRODUCT`） | 商品名、単価、数量、合計 |

- 辞書（`src/control/data-rules/dictionaries/`。JSON のデータ）: 姓 40 件・名 40 件（それぞれフリガナつき）、架空の備考の文例 18 件、商品名 18 件。実在の人や会社を指さない、ありふれた語だけです。危険な語・秘密に見える語・外部到達の語に当たらないことを、自動の検査で確かめています。著名人と同じ姓名になりやすい姓と名の組は、選ばない組の閉じた一覧（`avoided-person-names.json`。7 組）に置き、氏名に選びません。
- 意味の種類は、欄の名前の語・型・autocomplete から推します。推せない text・search・textarea の欄は止めます（`SEMANTIC_KIND_UNDECIDED`）。
- 氏名とフリガナは、同じ 1 人から作ります。欄の maxlength に合わせ、欄の pattern がひらがなを求めるなど、カタカナで作れないときは止めます。
- **pattern** は、閉じた単純な形（数字・英字・カタカナ・ひらがなの文字の集まり、区切りの `-`、回数（なし・`+`・`{n}`・`{n,m}`））だけを扱います。ほかの形は止めます（`PATTERN_UNSUPPORTED`）。長すぎる pattern（`MAX_SIMPLE_PATTERN_LENGTH`＝64 文字を超える、部品が `MAX_SIMPLE_PATTERN_TOKENS`＝16 を超える、回数が `MAX_SIMPLE_PATTERN_REPEAT`＝256 を超える、回数が決まらない部品（`+` と `{n,m}`）が `MAX_SIMPLE_PATTERN_VARIABLE_QUANTIFIERS`＝4 を超える）も止めます。pattern に当てる値は `MAX_SIMPLE_PATTERN_VALUE_LENGTH`（256 文字）までです（長い値は合わないとみなします）。

### メールアドレス

- 配送されない予約のドメイン `example.invalid`（`SYNTHETIC_EMAIL_DOMAIN`）の宛先だけを作ります。局所部は `sample` と 10 桁（`SYNTHETIC_EMAIL_LOCAL_DIGITS`）の数字です（例: `sample0123456789@example.invalid`）。
- 対象は、type が `email`、autocomplete が `email`、名前に mail・メール・メアドなどの語がある欄です（`mailaddr`・`contactemail`・`usermail` のように、区切りなしでつないだ名前の一部も一覧に置きます）。
- メールと電話の両方の語に当たる欄（`携帯メール`、`mobile_email`、`tel_mail` など）は、欄の type で決めます。type が `email` ならメール、`tel` なら電話として作り、ほかの type では作りません（`SEMANTIC_KIND_UNDECIDED`）。人が入れる値の一覧も、type が `email` なら合成のメールの形（`example.invalid`）だけ、`tel` なら合成の電話の形だけ、ほかの type ならどちらかの合成の形だけを受けます（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。
- シナリオの副作用の確認「メール・SMS・外部の通知が送られない設定です」（`NO_EXTERNAL_NOTIFICATION`）を確かめるまで作りません（`EXTERNAL_DELIVERY_BLOCKED`）。確かめるのは、一覧のチェックです（承認の前は、作れる欄として判定します。上の「[欄ごとの状態](#欄ごとの状態)」）。

### 電話番号

- `090-0XXX-XXXX` の形だけを作ります（`XXX-XXXX` の 7 桁（`SYNTHETIC_PHONE_VARIABLE_DIGITS`）を決まった手順で作ります）。欄の pattern・maxlength がハイフンを許さないときは、ハイフンなしの `0900XXXXXXX`（11 桁）にします。
- どちらの形も欄の制約に合わなければ、ほかの形（実在しうる番号）に切り替えずに止めます（`PHONE_FORMAT_UNSUPPORTED`）。
- 対象は、type が `tel`、autocomplete が `tel` で始まる値、名前に tel・phone・fax・mobile・keitai・denwa・電話・携帯などの語がある欄です（`mobilephone`・`homephone`・`faxno` のように、つないだ名前の一部も一覧に置きます）。
- メールと同じく、副作用の確認 `NO_EXTERNAL_NOTIFICATION` を確かめるまで作りません。
- 書き込みのたびに、すでに作った番号（生成の履歴。同じプロファイルの登録と更新が送った記録から渡します）と重ならない番号を選びます。ハイフンの有無が違っても、同じ数字なら同じ番号とみなします。
- 電話だけに当たる欄で、人が値の一覧を入れたときは、その一覧を優先します（テスト環境で使ってよい番号を入れるため。メールにも当たる欄は、上の「メールアドレス」のとおり合成の形だけを受けます）。
- **注意**: この形は、公式に架空の番号として保証された番号帯ではありません。通常の携帯電話の番号として割り当てられていない形ですが、将来の割り当ての変更がありえます。また、電話番号を厳しく確かめるシステムでは、登録に失敗することがあります。そのときも、別の形には切り替えません（その画面の書き込みは失敗します）。
- 電話を掛ける操作がなくても、顧客の登録を契機に SMS を送るシステムがあります。外部への通知が送られない設定かは、副作用の確認で人が確かめます。

### 作らない値・送らない値

- **住所**（autocomplete の住所の値、名前の住所の語の欄）: 作りません（`ADDRESS_FIELD`。実在の宛先に届くおそれがあるため）。
- **URL** の欄: 作りません（`URL_FIELD`）。
- **パスワードとファイル**の欄: 送る欄にできません（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）。
- **通知・配信を求める欄**（名前に notify・sms・newsletter・magazine・optin・consent・promotion・marketing・campaign・ads・通知・配信・メルマガ・案内・キャンペーン・広告・連絡を希望・受け取るなどの語がある欄。閉じた一覧）: 「送らない」側に固定します。送らない側の値が選べなければ止めます（`NOTIFICATION_OPT_OUT_UNAVAILABLE`）。名前に否定の語がある通知の欄（配信を止める欄など）は、どちらが送らない側かを推し量らずに止めます。
- **状態の欄**（有効・無効・公開・削除など）: 値を入れません（`STATE_FIELD_NOT_USABLE`）。
- **既定の値がある欄**: 登録（CREATE）では、規則の値で上書きします。ページが欄に書いていた今の値は使いません。更新（UPDATE）では、変える欄だけに規則の値を入れ、保つ欄は更新の前に読んだ値のまま送ります（「[承認された更新の手順](approved-update.md)」）。

## 自動で作った規則（推した規則の保存）

業務テンプレートと汎用の規則で推した規則を、保存した規則として固定する部品があります（`src/control/data-rules/rule-set-inference.ts` の `inferRuleSetContent`）。シナリオの下書きを作るとき（一覧のチェックの保存と点検の中の自動の下書きで作る登録と更新、操作さがしの画面の「書き込みの手順を作る」で作る登録（フォームの送信と API の要求））に、規則がまだない下書きなら、この部品で作った規則の集まりが付きます（「[シナリオの承認の手順](scenario-approval.md#下書きをボタン-1-回で作る)」）。

- **保存した規則は承認に縛られます。** 推した規則も、保存すると規則の digest に入ります。保存した規則の作り方は、BeakSight のコードが変わっても、承認を外さずに変わることはありません。
- **保存した規則のない欄は、判定のたびにその場で推します**（Task 29 からの動き）。この推しは、BeakSight のコードの変更（業務テンプレートの語の一覧、汎用の規則など）で変わることがあり、そのときは承認を外さずに、送る値の作り方が変わりえます。FM2c で足した推し（番号・コード、範囲の既定の幅、API の鍵の制約の補い）は、このその場の推しには入れていません（推した規則を作るときだけに使います）。
- 推した規則を保存しておくので、承認した後に作り方が黙って変わりません。

- **出どころの印**: 保存した規則・欄どうしの関係・一意にする欄の組は、出どころの印（`origin`・`uniqueKeyOrigin`）を持ちます。前の版の画面で人が決めたものは「人が決めた」（`HUMAN`）、推したものをそのまま保存したものは「推した規則（人は確かめていない）」（`INFERRED`）です。判定では、どちらも保存した規則として当てます。人が決めたものを持つ規則の集まりは、チェックの承認の前に、推した規則に替えます（「[前に手で作った規則](local-ui.md#前に手で作った規則)」）。
- **範囲の既定の幅**（推測）: 範囲の手がかり（欄の最小・最大・刻み）が何もない欄だけに入れます。欄に最小・最大があれば、今どおりその範囲を使います。片方だけ、刻みだけの欄にも入れません（範囲の入力が要るまま）。
  - 日付・日時（date・datetime-local）: 基準日（実行の許可の発行日）から `DEFAULT_UNRANGED_DATE_WINDOW_DAYS`（0〜30 日後）。保存するのは日の数だけで、値は書き込みのたびの基準日から求めます。
  - **時刻（time）・月（month）・週（week）の欄には入れません。** 欄に最小・最大がなければ、作り方が決まらず（`RANGE_MISSING`）、その画面は試せません。
  - 数: `DEFAULT_UNRANGED_INTEGER_RANGE`（1〜100 の整数。刻み 1）。
  - シナリオの詳細の「推測した項目（確かめてください）」に、既定の幅を使った欄が出ます（画面のサーバが、同じ部品で求め直します。承認には縛りません）。サイトの検証で拒まれたとき（4xx）は、今どおり書き込みが失敗します（`INPUT_ERROR`）。
  - 基準日からの幅の日の数は、`MAX_BASE_DATE_WINDOW_DAYS`（3650 日）までです。
- **推せない欄**: 推せない欄と、判定が決まらない欄は、理由のコードつきの一覧で返します（その画面は試せません）。メール・電話の欄は、副作用の確認の前でも推して保存しますが、確認が済むまで作りません（`EXTERNAL_DELIVERY_BLOCKED`）。
- **欄どうしの関係と一意にする欄の組**: 作るときに業務テンプレートの既定から求め、推した印つきで保存します（`templateDefaultsSaved`）。この印のある規則の集まりの判定は、保存した関係と組だけを使い、テンプレートの既定を足しません（後でコードが変わっても、関係と組が黙って変わりません）。印のない規則の集まり（人が保存したもの）と、規則の集まりを保存していない場合は、今どおり判定のたびにテンプレートの既定を足します。
- **API のシナリオの鍵の制約**: 推すときだけ、probe で目印を入れた欄の name で、同じ form の候補の欄（同じ型のとき）と結び、その制約で補います。補った範囲（数・日時の欄の最小・最大・刻み）と番号・コードの桁の数（`digitCount`）は、保存する規則に固定します。判定と生成は、今どおり鍵の欄の制約を使いません（前に承認したシナリオの送る値は変わりません）。form の外のボタンの候補と、name のない欄は、補いません。label と placeholder は、発見の記録に足しません。
- **規則の集まりの版**: 出どころの印・基準日からの幅・桁の数・既定を保存した印を持つ版 2（`beaksight-data-rule/2`）で保存し、版 2 の文書だけを読みます。前の版（版 1）の文書は読みません。管理データにあれば、管理データの誤り（`DATABASE_INTEGRITY_FAILED`）で止まります（版 1 の文書の読み替えは、利用者のデータに残っていないので捨てました）。

## 同じ入力で同じ値（決定性）

- 値は、seed から決まった手順で作ります。seed は、次の 5 つの要素と形式の版（`DATA_SEED_FORMAT_VERSION`＝1）を、鍵を並べた JSON にして SHA-256 にかけた値です。
  1. プロファイルの ID
  2. シナリオの ID
  3. シナリオの版
  4. 規則の集まりの digest
  5. 実行の許可の ID（許可は 1 回だけ使えるので、書き込みのジョブごとに別の seed になります）
- seed と用途（欄の名前など）とカウンタから SHA-256 で整数の列を取り出し、辞書・テンプレート・範囲から値を選びます。範囲の中の値は、偏りが出ないように選び直します（選び直しの上限は `MAX_REJECTION_DRAWS`＝64 回。超える確率は 2^-64 未満です）。
- **乱数と今の時刻を使いません**（`Math.random`、`node:crypto` の乱数、`Date.now()` などを、生成の部品に書かないことを自動の検査で確かめます）。
- 基準日（実行の許可の発行日。Asia/Tokyo の日付）は、形を確かめて記録に残します。日付と時刻の範囲は、欄の最小・最大と人が決めた範囲で決まります。ただし、規則の自動の作成が既定の幅（基準日からの幅）を入れた日付・日時の欄だけは、基準日から幅を求めます（下の「自動で作った規則」。2026-10-22 のユーザーの判断で改めました）。
- 同じ 5 つの要素なら、いつ作っても同じ値です。どれかが変われば、別の値になります。作った値には、使った seed と基準日を添えます。

## 重ならない値（一意性）

- 一意にする欄の組の値が、すでに使った組（そのシナリオと、同じ台帳の登録と更新のシナリオが送った記録から渡します）とぶつかったときは、カウンタを進めて決まった手順で作り直します。
- 作り直しは `MAX_UNIQUE_RETRIES`（32 回）までです。それでも作れなければ止めます（`UNIQUE_COMBINATIONS_EXHAUSTED`。組み合わせの数が足りません。一意にする欄を見直すか、値の一覧を増やしてください）。
- 電話番号は、一意にする欄の組と同じ作り直しで、生成の履歴と重ならない番号を選びます。

## 止まる場合

止まるときは、欄ごとに理由のコードと細分を記録します。

| コード | 細分 | 利用者の言葉で |
| --- | --- | --- |
| `NEEDS_RULE_INPUT` | `NO_RULE` | この欄の値の作り方が決まっていない。 |
| | `REQUIRED_FIELD_NOT_SELECTED` | 必須の欄が、シナリオの送る欄に選ばれていない（シナリオを変える）。 |
| | `SEMANTIC_KIND_UNDECIDED` | 欄の名前と型から、意味の種類を推せない（推し量って作らない）。 |
| | `PATTERN_UNSUPPORTED` | 欄の pattern が扱える単純な形でないか、作る値が合わない。 |
| | `RANGE_MISSING` | 数や日時の範囲（最小と最大）が決まっていない。 |
| | `RANGE_EMPTY` | 範囲の最小が最大を超えている。 |
| | `CONSTRAINT_UNSUPPORTED` | 欄の最小・最大・刻みの形を扱えない（`any`、指数の表記、ありえない日時など）。 |
| | `LENGTH_UNSATISFIABLE` | 欄の長さの制約に合う値を作れない。 |
| | `NO_USABLE_OPTION` | 選べる選択肢がない（空の値と危険な語の値を除くと残らない）。 |
| | `URL_FIELD` | URL の欄の値は作らない。 |
| | `ADDRESS_FIELD` | 住所の欄の値は作らない。 |
| | `PHONE_FORMAT_UNSUPPORTED` | 欄の制約に、合成の電話番号の形が合わない（ほかの形に切り替えない）。 |
| `RULE_CONFLICT` | `SEMANTIC_KIND_TYPE_MISMATCH` | 選んだ意味の種類が、欄の型に合わない。 |
| | `FIXED_VALUE_VIOLATES_CONSTRAINT` | 人が入れた値が、欄の型・選択肢・制約に合わないか、危険な語を含む。 |
| | `RANGE_OUTSIDE_FIELD_CONSTRAINT` | 人が入れた範囲が、欄の最小・最大の外。 |
| | `RELATION_FIELD_MISMATCH` | 関係の欄が送る欄でないか、意味の種類が役割に合わない。 |
| | `RELATION_UNSATISFIABLE` | 関係（終了は開始より後、合計は単価 × 数量）を範囲の中で満たせない。 |
| | `UNIQUE_COMBINATIONS_EXHAUSTED` | 一意にする欄の組を、使った組と重ならないように作れない。 |
| | `STATE_FIELD_NOT_USABLE` | 状態の欄に値を入れることになる。 |
| | `NOTIFICATION_OPT_OUT_UNAVAILABLE` | 通知・配信の欄で、「送らない」側の値が選べない（否定の名前の欄を含む）。 |
| | `FIELD_NOT_SENDABLE` | 送る欄が、候補の送れる欄でない（発見をやり直してシナリオを作り直す）。 |
| `EXTERNAL_DELIVERY_BLOCKED` | `EXTERNAL_NOTIFICATION_UNCONFIRMED` | メール・電話の欄は、副作用の確認 `NO_EXTERNAL_NOTIFICATION` を確かめるまで作らない。 |

## 上限と名前つきの定数

人が入れる値の一覧の件数と値 1 つの長さ、欄ごとの規則・関係・一意にする欄の件数には、上限がありません（前の `MAX_FIXED_VALUES` 50 件・`MAX_FIXED_VALUE_LENGTH` 256 文字・`MAX_FIELD_RULES` 200 件などは撤廃しました）。

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `MAX_UNIQUE_RETRIES` | 32 回 | 一意にする欄の組の作り直しの上限。 |
| `SYNTHETIC_EMAIL_DOMAIN` | `example.invalid` | 合成のメールアドレスのドメイン。 |
| `SYNTHETIC_PHONE_PREFIXES` | `090-0`・`0900` | 合成の電話番号の頭（ハイフンつき・ハイフンなし）。 |
| `SYNTHETIC_PHONE_VARIABLE_DIGITS` | 7 桁 | 合成の電話番号の、作る桁の数。 |
| `TEMPLATE_DEFAULT_RANGES` | 人数 1〜4、数量 1〜5、単価 100〜10000 | 欄にも人の規則にも範囲がないときの補い。 |
| `DEFAULT_UNRANGED_DATE_WINDOW_DAYS` | 基準日から 0〜30 日後 | 規則の自動の作成が、範囲の手がかりのない日付・日時の欄に入れる既定の幅。 |
| `DEFAULT_UNRANGED_INTEGER_RANGE` | 1〜100 の整数 | 規則の自動の作成が、範囲の手がかりのない数の欄に入れる既定の幅。 |
| `MAX_BASE_DATE_WINDOW_DAYS` | 3650 日 | 保存した規則の基準日からの幅の、日の数の上限。 |
| `MAX_DIGIT_CODE_DIGITS` | 256 桁 | 番号・コードの桁の数の上限（pattern の回数の上限と同じ）。 |
| `MAX_SIMPLE_PATTERN_LENGTH` | 64 文字 | 扱う pattern の長さの上限。 |
| `MAX_SIMPLE_PATTERN_VARIABLE_QUANTIFIERS` | 4 個 | pattern の、回数が決まらない部品（`+` と `{n,m}`）の数の上限。 |
| `MAX_SIMPLE_PATTERN_VALUE_LENGTH` | 256 文字 | pattern に当てる値の長さの上限。 |
| `MAX_RELATION_SIDE_VALUES` | 100 個 | 合計 = 単価 × 数量 を確かめるときの、単価と数量のそれぞれの値の数の上限（超えれば間引く）。 |
| `DATA_SEED_FORMAT_VERSION` | 1 | seed の形式の版。 |
| `MAX_REJECTION_DRAWS` | 64 回 | 偏りを避けるための選び直しの上限。 |

## サイトへの読み込み

- 入力の規則を推して保存するのは、管理データの中だけで行います。**サイトへは何も送りません**（読み込みも書き込みもしません）。
- サイトへ届くのは、発見と READ の確かめのジョブの要求だけです（「[サイトへの読み込み](discovery-and-read-check.md#サイトへの読み込み)」）。

## 守りの範囲

- **入力の規則の保存では、書き込みをしません。** 入力の規則の部品（`src/control/data-rules/`）は、ブラウザ・ワーカー・Playwright など、要求を送る部品を使いません（自動の検査で確かめます）。作った値を送るのは、承認の後に点検の書き込みの段で動く登録と更新のジョブだけです。
- **LLM を使いません。** 依存（`package.json` と `package-lock.json`。間接の依存を含む）に LLM の SDK と合成データのライブラリ（OpenAI・Anthropic・Google・Cohere・Mistral・Ollama・LangChain・Faker など。閉じた一覧）がないことと、BeakSight のコードと画面のコード（起動の部品とビルドの補助を含む）がそれらを読み込まないことを、自動の検査（`tests/architecture/llm-dependency.test.ts`）で確かめます。
- **ページが書いた pattern を正規表現にしません。** 閉じた単純な形だけを、1 文字ずつ読んで解釈します（悪意のある pattern で管理の側が止まらないように）。生成の部品は、正規表現を実行時に組み立てません（自動の検査）。
- **前に人が入れた値は、管理データに平文で残ります。** READ の確かめの定義の値と同じ扱いです。管理データ（`local-data/`）はテスト環境のデータと同じに扱ってください。
- **規則の版は追記だけです。** 規則の版の写し（`rule_set_revisions`）は書き換えも削除もしません。シナリオごとの規則の集まり（`rule_sets`）は、最新の版の番号だけを進めます。どちらの表も、書くのは保存の部品だけで、版の写しを書き換える文（`UPDATE`・`DELETE` など）を BeakSight のコードに書かないことを自動の検査で確かめます。管理データのファイルを別の道具で書き換えた場合の守りは、承認の記録と同じく限られます（「[守りの範囲](scenario-approval.md#守りの範囲)」）。
- **秘密を持ちません。** 規則の集まりは、ページの入力の欄の今の値、hidden の値、CSRF のトークン、選択肢の label、資格情報、Cookie、localStorage の値を使いません。

### 確かめたこと（目印の検査）

一覧のチェックで規則を推して付ける流れの目印の検査は、「[書き込みのシナリオの承認の確かめたこと](scenario-approval.md#確かめたこと目印の検査)」と同じ検査（`apps/local-ui/tests/scenario-approval-secret-markers.test.ts`）で確かめています（規則の集まりと版の写しの表を含めて探します）。前にあった、入力の規則の画面の場面は、画面を外したので消しました。秘密に見える名前の欄に人の固定の値を保存させないことは、保存の部品の単体の検査（`RULE_SET_SECRET_FIELD_FIXED_VALUE`）で確かめています。

## 確かめていないこと・使えないこと

- **書き込みの実行**: ここで決めた規則から値を作って送るのは、承認された登録と更新です。送った値は、管理データの書き込みの結果と、書き込みの成果物（`action-run.json`、`action-evidence.json`、`action-report.html`、書き込みのバンドル）に平文で残ります（「[成果物を外へ渡す前の確かめ](anonymization.md)」）。
- **READ の結果の値を使う生成**（営業時間など、サイトから読んだ値に合わせる生成）: 作りません。選択肢は、発見した選択肢の値だけを使います。
- **住所の生成**: 作りません。
- **更新（UPDATE）の値**: 変える欄と保つ欄は、シナリオの UPDATE の指定で決めます。メールと電話は既定で保ちます（「[UPDATE の指定](approved-update.md#update-の指定)」）。
- **`090-0XXX-XXXX` の形のほかの電話番号の生成**: 作りません。
- **実際のテスト環境**: API の登録 1 件でだけ使いました。欄の形ごとに（電話番号の形など）、テスト環境が受け付けるかは確かめていません。
- 画面と CLI からの入力の規則の操作。
