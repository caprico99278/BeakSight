# 入力の規則とデータの生成（テスト環境だけ）

承認した書き込みのシナリオ（「[書き込みのシナリオの承認](scenario-approval.md)」）の、送る欄に入れる値の作り方（入力の規則）を決め、保存し、承認に縛る手順です。値の作り方の決まり、同じ入力で同じ値になる仕組み、重ならない値の作り方、止まる場合、守りの範囲、確かめていないことも書きます。
画面の操作の細部は「[管理画面の入力の規則](local-ui.md#入力の規則送る値の作り方)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> **入力の規則の画面では、書き込みをしません。データの例もサイトに送りません。** ここで決めた規則から、承認された登録（「[承認された登録の手順](approved-create.md)」）と更新（「[承認された更新の手順](approved-update.md)」。変える欄だけ）が、書き込みのたびに送る値を作ります。テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません。

## 何をするか

- シナリオの送る欄ごとに、入れる値の作り方を決めます。値は **LLM を使わず**、欄の型と制約、小さな辞書、3 つの業務テンプレート（顧客・予約・商品）、人が入れた値の一覧から、決まった手順で作ります。
- 作り方が決まらない欄は、推し量って作らずに止めます（`NEEDS_RULE_INPUT`）。決まりがぶつかるときも止めます（`RULE_CONFLICT`）。メールや SMS が実際に届く値は作りません。
- 送る欄すべての作り方が決まっていないシナリオには、実行の許可（書き込みのジョブを始めるための許可）を出しません（`NEEDS_RULE_INPUT`。どの欄の、どの理由かを添えます）。
- 規則を保存すると、規則の新しい版ができ、シナリオに付け直します。シナリオは下書きに戻るので、承認していた場合は、もう一度承認が要ります。

## 使ってよい場合

- **テスト環境だけに使います。本番には使いません。** 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）のプロファイルのシナリオだけで使えます。ほかのモードでは、画面に編集とデータの例を出さず、サーバも保存を拒みます（`RULE_SET_MODE_NOT_WRITE`）。
- 作った値は、承認された登録と更新で、テスト環境のレコードに書き込まれます。登録されてよい値か、メール・SMS・外部の通知が送られない設定かを、テスト環境の管理者と確かめてから使ってください。

## 手順

### 1. シナリオの詳細から開く

シナリオを作り（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）、シナリオの詳細の「入力の規則を開く」を押すと、画面「入力の規則」が開きます。

- 画面の上に、入力の規則の状態（未設定・すべて決まった・不足あり）と、保存した規則の版を出します。シナリオの一覧と詳細にも、同じ状態を出します。
- まだ保存していなくても、業務テンプレートと汎用の規則で決まる欄は「決まった」と出ます。保存するまで、シナリオには付きません（状態は「未設定」のままです）。

### 2. 欄ごとの状態を見る

送る欄ごとに、状態と、その理由の説明と手順、当てた規則の出どころ、外部到達の種類を出します。送る欄に選ばれていない必須の欄も、理由とともに並びます。

| 状態 | 意味 |
| --- | --- |
| 決まった | 値の作り方が決まった。 |
| 規則の入力が要る（`NEEDS_RULE_INPUT`） | 作り方が決まらない。人が意味の種類か値の一覧を入れる。 |
| 決まりがぶつかる（`RULE_CONFLICT`） | 欄の制約・関係・一意性などがぶつかる。規則かシナリオを直す。 |
| 外部到達で止めた（`EXTERNAL_DELIVERY_BLOCKED`） | メール・電話の欄で、シナリオの副作用の確認が済んでいない。 |

| 出どころ | 意味 |
| --- | --- |
| 人の規則（`HUMAN`） | 保存した人の規則。最も強い。 |
| 業務テンプレート（`TEMPLATE`） | 欄の名前・型・autocomplete から推した、顧客・予約・商品の規則。 |
| 汎用の規則（`GENERIC`） | 欄の型と制約（数・日時・選択肢・色）から決まる規則。 |
| 送らない側に固定（`OPT_OUT`） | 通知・配信を求める欄を、送らない側に固定した。 |

規則の優先順位は、汎用の規則 → 業務テンプレート → 人の規則（人の上書きが最も強い）です。テンプレートには、サイトに固有の値を書きません。

### 3. 意味の種類・作り方・値の一覧・範囲を決める

決まらない欄や、変えたい欄は、欄ごとに次を決めます。

- **意味の種類**: 「自動」（業務テンプレートか汎用の規則で決める）か、閉じた一覧の種類（汎用の数・日時・選択・色、姓・名・フルネームとそれぞれのフリガナ、メール、電話、備考、商品名、単価、数量、合計、日付、開始・終了の時刻、人数、固定の一覧、テンプレートの外）です。選べるのは、欄の型に合う種類だけです（合わなければ `SEMANTIC_KIND_TYPE_MISMATCH`）。
- **作り方**: 欄の型と制約から（`FROM_TYPE`）、業務テンプレートと辞書から（`FROM_TEMPLATE`）、人が入れた値の一覧から（`FROM_FIXED_LIST`）。
- **値の一覧**（人が入れた値の一覧から、のときだけ）: 1 行に 1 つ、`MAX_FIXED_VALUES`（50 件）まで、1 つは `MAX_FIXED_VALUE_LENGTH`（256 文字）までです。値は、欄の型・選択肢・制約に合い、危険な語を含まないものだけです（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。メールの欄には `example.invalid` の宛先だけを入れられます。
- **範囲**（最小・最大・刻み）: 数と日時の欄に決めます。欄の最小・最大の外にはできません（`RANGE_OUTSIDE_FIELD_CONSTRAINT`）。欄に刻み（step）があれば、範囲の最小・最大は欄の刻みの上の値にし、範囲の刻みは欄の刻みの倍数にします（合わなければ `RANGE_OUTSIDE_FIELD_CONSTRAINT`）。数と日時の欄の値の一覧も、欄の刻みの上の値だけを受けます（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。
- 秘密に見える名前（`token`、`session`、`key` など）の欄には、値の一覧を入れられません（規則の保存の部品が拒みます。`RULE_SET_SECRET_FIELD_FIXED_VALUE`）。
- 人が入れた値は、管理データにそのまま（平文で）残ります（下の「守りの範囲」）。

### 4. 欄どうしの関係を決める

関係は閉じた一覧の 3 つです。人が決めた関係に、業務テンプレートの既定の関係を足して当てます（当てる関係を画面に出します）。

- **終了は開始より後**（`END_AFTER_START`）: 開始と終了の時刻（日時）。
- **合計は単価 × 数量**（`TOTAL_EQUALS_UNIT_PRICE_TIMES_QUANTITY`）。判定のときに、合計の欄の制約（最小・最大・刻み、文字の欄なら pattern と長さ）に合う単価と数量の組を求め、組がなければ止めます（`RELATION_UNSATISFIABLE`）。値は、その組から選びます（判定で作れると言えば、作るときも止まりません）。単価と数量のそれぞれの値が `MAX_RELATION_SIDE_VALUES`（100 個）を超えるときは、等しい間隔で間引いた値の組だけを確かめます（間引いた組に合うものがなければ、止める側に寄せます）。
- **フリガナは氏名と同じ人**（`KANA_MATCHES_NAME`）: 氏名の欄 1 つとフリガナの欄 1 つの組です。姓と名で分かれていれば、関係を 2 つ持ちます。

関係の欄が送る欄でないか、意味の種類が役割に合わなければ `RELATION_FIELD_MISMATCH`、範囲の中で満たせなければ `RELATION_UNSATISFIABLE` で止めます。

### 5. 一意にする欄の組を決める

登録するレコードを見分けるための欄の組です（BeakSight の登録を見分ける印は付けません。値の組み合わせで見分けます）。選ばなければ、業務テンプレートの既定の組を使います（当てる組を画面に出します）。

- 顧客: 氏名とフリガナの欄すべて。
- 商品: 商品名の欄。
- 予約: 日付・開始の時刻・選択肢の欄。

### 6. データの例を見る

送る欄すべての作り方が決まったときだけ、この画面のための決まった値で作った例を `EXAMPLE_COUNT`（3 つ）出します。

- **データの例はサイトに送りません。** この画面には、サイトへ要求を送る部品がありません。
- メールアドレスと電話番号には、合成の形であることを添えます。通知の欄は「送らない」と出ます。
- 書き込みのモードでないプロファイルには、データの例を作りません（画面のサーバも返しません）。
- 実際の書き込みでは、実行の許可ごとに別の値になります（下の「同じ入力で同じ値」）。

### 7. 保存する（再承認になる）

「保存する」を押すと、確認のダイアログが開きます（開くと「やめる」にフォーカス）。ダイアログの「保存する」を押したときだけ保存します。

- 保存すると、規則の新しい版ができ（前の版は変えずに残ります）、シナリオに付け直します。シナリオの版が 1 つ上がり、下書き（`DRAFT`）に戻ります。
- 承認していた場合は「要再承認」になり、理由に「シナリオを編集した」（`SCENARIO_REVISION_CHANGED`）と「入力の規則が変わった」（`INPUT_RULES_CHANGED`）が出ます（「[再承認が要る場合](scenario-approval.md#再承認が要る場合)」）。
- ほかの画面で先に変えられていたときは、保存せずに知らせます（`RULE_SET_REVISION_CONFLICT`。読み込み直してから、もう一度保存します）。規則は保存できたのにシナリオに付けられなかったときも、そのことを知らせます（規則の版は残ります）。

### 8. もう一度承認する

シナリオの詳細で、内容と差分を確かめてから、もう一度承認します（「[承認する](scenario-approval.md#5-承認する)」）。承認は、規則の版と digest（規則の中身の SHA-256）を縛ります。後で規則を変えると、また再承認が要ります。

## 作る値の決まり

### 型と制約で決まる欄（汎用の規則）

- **数**（number・range）: 欄の最小・最大・刻み（と人の範囲）の中の値です。刻みの誤差が出ない形で数えます。range の欄に最小・最大がなければ、HTML の既定（0〜100）を使います。number の欄に最小・最大がなければ止めます（`RANGE_MISSING`）。
- **日時**（date・time・datetime-local・month・week）: 欄の最小・最大（と人の範囲）の中の値です。最小・最大がなければ止めます（`RANGE_MISSING`）。
- **選択肢**（select・radio・checkbox）: 発見した選択肢の値から選びます。空の値と、危険な語に当たる値は使いません（残りがなければ `NO_USABLE_OPTION`）。選択肢の label は使いません。
- **required でない checkbox** は、人が値の一覧を入れない限り、送りません（チェックしません）。名前から通知・同意の欄と分からない欄（`contact_ok`、`allow_call` など）を、受け取る側の値で送らないためです。required の checkbox は、選択肢の値から選びます（通知の語に当たる required の checkbox は、下の「通知・配信を求める欄」のとおり止めます）。
- 数と日時の値は、欄の刻み（step）の上の値だけを作ります。刻みの起点は、欄の最小（なければ HTML の既定の起点。number は 0、date は 1970-01-01 など。value の属性の起点は使いません）です。業務テンプレートの既定の範囲を補うときも、欄の刻みに合わせます。
- **色**（color）。
- 範囲は、欄の最小・最大と人の範囲だけで決めます。業務テンプレートの数と金額の欄にだけ、欄にも人の規則にも最小・最大がないときの一般的な幅（`TEMPLATE_DEFAULT_RANGES`: 人数 1〜4、数量 1〜5、単価 100〜10000（100 刻み））を補います。

### 業務テンプレートと辞書

| テンプレート | 意味の種類 |
| --- | --- |
| 顧客（`CUSTOMER`） | 姓・名・フルネームとそれぞれのフリガナ（カタカナ）、メール、電話、備考 |
| 予約（`RESERVATION`） | 日付、開始・終了の時刻、人数、選択肢 |
| 商品（`PRODUCT`） | 商品名、単価、数量、合計 |

- 辞書（`src/control/data-rules/dictionaries/`。JSON のデータ）: 姓 40 件・名 40 件（それぞれフリガナつき）、架空の備考の文例 18 件、商品名 18 件。実在の人や会社を指さない、ありふれた語だけです。危険な語・秘密に見える語・外部到達の語に当たらないことを、自動の検査で確かめています。著名人と同じ姓名になりやすい姓と名の組は、選ばない組の閉じた一覧（`avoided-person-names.json`。7 組）に置き、氏名に選びません。
- 意味の種類は、欄の名前の語・型・autocomplete から推します。推せない text・search・textarea の欄は止めます（`SEMANTIC_KIND_UNDECIDED`）。
- 氏名とフリガナは、同じ 1 人から作ります。欄の maxlength に合わせ、欄の pattern がひらがなを求めるなど、カタカナで作れないときは止めます。
- **pattern** は、閉じた単純な形（数字・英字・カタカナ・ひらがなの文字の集まり、区切りの `-`、回数（なし・`+`・`{n}`・`{n,m}`））だけを扱います。ほかの形は止めます（`PATTERN_UNSUPPORTED`）。長すぎる pattern（`MAX_SIMPLE_PATTERN_LENGTH`＝64 文字を超える、部品が `MAX_SIMPLE_PATTERN_TOKENS`＝16 を超える、回数が `MAX_SIMPLE_PATTERN_REPEAT`＝256 を超える、回数が決まらない部品（`+` と `{n,m}`）が `MAX_SIMPLE_PATTERN_VARIABLE_QUANTIFIERS`＝4 を超える）も止めます。pattern に当てる値は `MAX_SIMPLE_PATTERN_VALUE_LENGTH`（256 文字）までです（長い値は合わないとみなします）。

### メールアドレス

- 配送されない予約のドメイン `example.invalid`（`SYNTHETIC_EMAIL_DOMAIN`）の宛先だけを作ります。局所部は `sample` と 10 桁（`SYNTHETIC_EMAIL_LOCAL_DIGITS`）の数字です（例: `sample0123456789@example.invalid`）。
- 対象は、type が `email`、autocomplete が `email`、名前に mail・メール・メアドなどの語がある欄です（`mailaddr`・`contactemail`・`usermail` のように、区切りなしでつないだ名前の一部も一覧に置きます）。
- メールと電話の両方の語に当たる欄（`携帯メール`、`mobile_email`、`tel_mail` など）は、欄の type で決めます。type が `email` ならメール、`tel` なら電話として作り、ほかの type では作りません（`SEMANTIC_KIND_UNDECIDED`）。人が入れる値の一覧も、type が `email` なら合成のメールの形（`example.invalid`）だけ、`tel` なら合成の電話の形だけ、ほかの type ならどちらかの合成の形だけを受けます（合わなければ `FIXED_VALUE_VIOLATES_CONSTRAINT`）。
- シナリオの副作用の確認「メール・SMS・外部の通知が送られない設定です」（`NO_EXTERNAL_NOTIFICATION`）を確かめるまで作りません（`EXTERNAL_DELIVERY_BLOCKED`）。

### 電話番号

- `090-0XXX-XXXX` の形だけを作ります（`XXX-XXXX` の 7 桁（`SYNTHETIC_PHONE_VARIABLE_DIGITS`）を決まった手順で作ります）。欄の pattern・maxlength がハイフンを許さないときは、ハイフンなしの `0900XXXXXXX`（11 桁）にします。
- どちらの形も欄の制約に合わなければ、ほかの形（実在しうる番号）に切り替えずに止めます（`PHONE_FORMAT_UNSUPPORTED`）。
- 対象は、type が `tel`、autocomplete が `tel` で始まる値、名前に tel・phone・fax・mobile・keitai・denwa・電話・携帯などの語がある欄です（`mobilephone`・`homephone`・`faxno` のように、つないだ名前の一部も一覧に置きます）。
- メールと同じく、副作用の確認 `NO_EXTERNAL_NOTIFICATION` を確かめるまで作りません。
- 書き込みのたびに、すでに作った番号（生成の履歴。同じプロファイルの登録と更新が送った記録から渡します）と重ならない番号を選びます。ハイフンの有無が違っても、同じ数字なら同じ番号とみなします。
- 電話だけに当たる欄で、人が値の一覧を入れたときは、その一覧を優先します（テスト環境で使ってよい番号を入れるため。メールにも当たる欄は、上の「メールアドレス」のとおり合成の形だけを受けます）。
- **注意**: この形は、公式に架空の番号として保証された番号帯ではありません。通常の携帯電話の番号として割り当てられていない形ですが、将来の割り当ての変更がありえます。また、電話番号を厳しく確かめるシステムでは、登録に失敗することがあります。そのときは別の形に切り替えず、テスト環境で使ってよい番号（テスト環境で許された専用の番号、管理下のテスト用の回線の番号など）を、人が値の一覧に入れてください。
- 電話を掛ける操作がなくても、顧客の登録を契機に SMS を送るシステムがあります。外部への通知が送られない設定かは、副作用の確認で人が確かめます。

### 作らない値・送らない値

- **住所**（autocomplete の住所の値、名前の住所の語の欄）: 作りません。人が入れた値だけを使います（`ADDRESS_FIELD`。実在の宛先に届くおそれがあるため）。
- **URL** の欄: 作りません。人が入れた値だけを使います（`URL_FIELD`）。
- **パスワードとファイル**の欄: 送る欄にできません（「[シナリオを作る](scenario-approval.md#4-シナリオを作る)」）。
- **通知・配信を求める欄**（名前に notify・sms・newsletter・magazine・optin・consent・promotion・marketing・campaign・ads・通知・配信・メルマガ・案内・キャンペーン・広告・連絡を希望・受け取るなどの語がある欄。閉じた一覧）: 「送らない」側に固定します。送らない側の値が選べなければ止めます（`NOTIFICATION_OPT_OUT_UNAVAILABLE`）。名前に否定の語がある通知の欄（配信を止める欄など）は、どちらが送らない側かを推し量らずに止めます。
- **状態の欄**（有効・無効・公開・削除など）: 値を入れません（`STATE_FIELD_NOT_USABLE`）。
- **既定の値がある欄**: 登録（CREATE）では、規則の値で上書きします。ページが欄に書いていた今の値は使いません。更新（UPDATE）では、変える欄だけに規則の値を入れ、保つ欄は更新の前に読んだ値のまま送ります（「[承認された更新の手順](approved-update.md)」）。

## 同じ入力で同じ値（決定性）

- 値は、seed から決まった手順で作ります。seed は、次の 5 つの要素と形式の版（`DATA_SEED_FORMAT_VERSION`＝1）を、鍵を並べた JSON にして SHA-256 にかけた値です。
  1. プロファイルの ID
  2. シナリオの ID
  3. シナリオの版
  4. 規則の集まりの digest
  5. 実行の許可の ID（許可は 1 回だけ使えるので、書き込みのジョブごとに別の seed になります）
- seed と用途（欄の名前など）とカウンタから SHA-256 で整数の列を取り出し、辞書・テンプレート・範囲から値を選びます。範囲の中の値は、偏りが出ないように選び直します（選び直しの上限は `MAX_REJECTION_DRAWS`＝64 回。超える確率は 2^-64 未満です）。
- **乱数と今の時刻を使いません**（`Math.random`、`node:crypto` の乱数、`Date.now()` などを、生成の部品に書かないことを自動の検査で確かめます）。
- 基準日（実行の許可の発行日。Asia/Tokyo の日付）は、形を確かめて記録に残すだけで、作る値を変えません。日付と時刻の範囲は、欄の最小・最大と人が決めた範囲だけで決まります（基準日からの相対の範囲は作りません）。
- 同じ 5 つの要素なら、いつ作っても同じ値です。どれかが変われば、別の値になります。作った値には、使った seed と基準日を添えます。

## 重ならない値（一意性）

- 一意にする欄の組の値が、すでに使った組（そのシナリオと、同じ台帳の登録と更新のシナリオが送った記録から渡します）とぶつかったときは、カウンタを進めて決まった手順で作り直します。
- 作り直しは `MAX_UNIQUE_RETRIES`（32 回）までです。それでも作れなければ止めます（`UNIQUE_COMBINATIONS_EXHAUSTED`。組み合わせの数が足りません。一意にする欄を見直すか、値の一覧を増やしてください）。
- 電話番号は、一意にする欄の組と同じ作り直しで、生成の履歴と重ならない番号を選びます。

## 止まる場合

止まるときは、欄ごとに理由のコードと細分を出し、画面に説明と手順を出します。

| コード | 細分 | 利用者の言葉で |
| --- | --- | --- |
| `NEEDS_RULE_INPUT` | `NO_RULE` | この欄の値の作り方が決まっていない。 |
| | `REQUIRED_FIELD_NOT_SELECTED` | 必須の欄が、シナリオの送る欄に選ばれていない（シナリオを変える）。 |
| | `SEMANTIC_KIND_UNDECIDED` | 欄の名前と型から、意味の種類を推せない（推し量って作らない）。 |
| | `PATTERN_UNSUPPORTED` | 欄の pattern が扱える単純な形でないか、作る値が合わない。 |
| | `RANGE_MISSING` | 数や日時の範囲（最小と最大）が決まっていない。 |
| | `RANGE_EMPTY` | 範囲の最小が最大を超えている。 |
| | `CONSTRAINT_UNSUPPORTED` | 欄の最小・最大・刻みの形を扱えない（`any`、指数の表記、ありえない日時など）。 |
| | `LENGTH_UNSATISFIABLE` | 欄の長さの制約に合う値を作れない。 |
| | `NO_USABLE_OPTION` | 選べる選択肢がない（空の値と危険な語の値を除くと残らない）。 |
| | `URL_FIELD` | URL の欄の値は作らない。 |
| | `ADDRESS_FIELD` | 住所の欄の値は作らない。 |
| | `PHONE_FORMAT_UNSUPPORTED` | 欄の制約に、合成の電話番号の形が合わない（ほかの形に切り替えない）。 |
| `RULE_CONFLICT` | `SEMANTIC_KIND_TYPE_MISMATCH` | 選んだ意味の種類が、欄の型に合わない。 |
| | `FIXED_VALUE_VIOLATES_CONSTRAINT` | 人が入れた値が、欄の型・選択肢・制約に合わないか、危険な語を含む。 |
| | `RANGE_OUTSIDE_FIELD_CONSTRAINT` | 人が入れた範囲が、欄の最小・最大の外。 |
| | `RELATION_FIELD_MISMATCH` | 関係の欄が送る欄でないか、意味の種類が役割に合わない。 |
| | `RELATION_UNSATISFIABLE` | 関係（終了は開始より後、合計は単価 × 数量）を範囲の中で満たせない。 |
| | `UNIQUE_COMBINATIONS_EXHAUSTED` | 一意にする欄の組を、使った組と重ならないように作れない。 |
| | `STATE_FIELD_NOT_USABLE` | 状態の欄に値を入れることになる。 |
| | `NOTIFICATION_OPT_OUT_UNAVAILABLE` | 通知・配信の欄で、「送らない」側の値が選べない（否定の名前の欄を含む）。 |
| | `FIELD_NOT_SENDABLE` | 送る欄が、候補の送れる欄でない（発見をやり直してシナリオを作り直す）。 |
| `EXTERNAL_DELIVERY_BLOCKED` | `EXTERNAL_NOTIFICATION_UNCONFIRMED` | メール・電話の欄は、副作用の確認 `NO_EXTERNAL_NOTIFICATION` を確かめるまで作らない。 |

## サイトへの読み込み

- 入力の規則の画面の表示、データの例、保存は、管理データの中だけで行います。**サイトへは何も送りません**（読み込みも書き込みもしません）。
- サイトへ届くのは、発見と READ の確かめのジョブの要求だけです（「[サイトへの読み込み](discovery-and-read-check.md#サイトへの読み込み)」）。

## 守りの範囲

- **入力の規則の画面と保存では、書き込みをしません。** 入力の規則の部品（`src/control/data-rules/`）は、ブラウザ・ワーカー・Playwright など、要求を送る部品を使いません（自動の検査で確かめます）。作った値を送るのは、承認の後に人が始める登録と更新のジョブだけです。
- **LLM を使いません。** 依存（`package.json` と `package-lock.json`。間接の依存を含む）に LLM の SDK と合成データのライブラリ（OpenAI・Anthropic・Google・Cohere・Mistral・Ollama・LangChain・Faker など。閉じた一覧）がないことと、BeakSight のコードと画面のコード（起動の部品とビルドの補助を含む）がそれらを読み込まないことを、自動の検査（`tests/architecture/llm-dependency.test.ts`）で確かめます。
- **ページが書いた pattern を正規表現にしません。** 閉じた単純な形だけを、1 文字ずつ読んで解釈します（悪意のある pattern で管理の側が止まらないように）。生成の部品は、正規表現を実行時に組み立てません（自動の検査）。
- **人が入れた値は、管理データに平文で残ります。** READ の確かめの定義の値と同じ扱いです。秘密に見える名前の欄には入れられませんが、ほかの欄に秘密や実在の個人情報を入れれば、そのまま残ります。テスト環境で使ってよい値だけを入れ、管理データ（`local-data/`）はテスト環境のデータと同じに扱ってください。
- **規則の版は追記だけです。** 規則の版の写し（`rule_set_revisions`）は書き換えも削除もしません。シナリオごとの規則の集まり（`rule_sets`）は、最新の版の番号だけを進めます。どちらの表も、書くのは保存の部品だけで、版の写しを書き換える文（`UPDATE`・`DELETE` など）を BeakSight のコードに書かないことを自動の検査で確かめます。管理データのファイルを別の道具で書き換えた場合の守りは、承認の記録と同じく限られます（「[守りの範囲](scenario-approval.md#守りの範囲)」）。
- **秘密を持ちません。** 規則の集まりとデータの例は、ページの入力の欄の今の値、hidden の値、CSRF のトークン、選択肢の label、資格情報、Cookie、localStorage の値を使いません。データの例と人が入れた値は、入力の規則の画面と管理データに出ます（設計どおりです）。

### 確かめたこと（目印の検査）

テスト用の小さなサイトで、実行ごとのランダムな値を目印にし（セッションの Cookie、localStorage、資格情報、CSRF のトークン、hidden の値、入力の欄の今の値（送る欄の今の値を含む）、選択肢の label、表の行の中身）、手動のログインのプロファイルで、画面から発見 → READ の定義の作成 → シナリオの作成 → 入力の規則の画面（データの例）→ 保存 → 承認 → 人が入れた値の一覧を足して保存（再承認になる）→ データの例 → 再承認を行って、目印が 1 つも出ないことを、UTF-8 と UTF-16LE の両方のバイトで確かめています（`apps/local-ui/tests/data-rule-secret-markers.test.ts`）。

- 探した場所: Run のディレクトリのすべてのファイル、管理データのファイルと WAL と SHM と、すべての表のすべての行（規則の集まりと版の写しを含む）、画面のサーバとワーカーの標準出力と標準エラー、ワーカーとの間の通信のすべて（両方の向き）、子プロセスの起動の引数、すべての画面の HTML（入力の規則の画面を含む）と成果物の画面、Server Function の応答（入力の規則の画面の値と保存の応答を含む）。
- 同じ確かめで、サイトに届いた要求が、GET と HEAD のほかは発見のジョブのログインの送信 1 回だけであること、入力の規則の画面の表示・データの例・保存・承認の間はサイトへの要求が 0 件であることを確かめています。
- 探す読み方が正しいことは、わざと目印を置いたファイル（UTF-16LE）が見つかることと、出てよい値（人が入れた値、データの例の値）が、管理データの表の行と入力の規則の画面で見つかることで確かめています。

## 確かめていないこと・使えないこと

- **書き込みの実行**: ここで決めた規則から値を作って送るのは、承認された登録と更新です。送った値は、管理データの書き込みの結果と、書き込みの成果物（`action-run.json`、`action-evidence.json`、`action-report.html`、書き込みのバンドル）に平文で残ります（「[成果物を外へ渡す前の確かめ](anonymization.md)」）。
- **READ の結果の値を使う生成**（営業時間など、サイトから読んだ値に合わせる生成）: 作りません。選択肢は、発見した選択肢の値だけを使います。
- **住所の生成**: 作りません（人が入れた値だけ）。
- **更新（UPDATE）の値**: 変える欄と保つ欄は、シナリオの UPDATE の指定で決めます。メールと電話は既定で保ちます（「[UPDATE の指定](approved-update.md#update-の指定)」）。
- **`090-0XXX-XXXX` の形のほかの電話番号の生成**: 作りません。
- **実際のテスト環境**: まだ接続して確かめていません。電話番号の形をテスト環境が受け付けるかも、まだ確かめていません。
- CLI からの入力の規則の操作。
