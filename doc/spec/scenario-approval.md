# 書き込みのシナリオの承認の手順（テスト環境だけ）

テスト環境の管理画面で、操作の候補の発見で見つかった登録（CREATE）・更新（UPDATE）の候補を「シナリオ」にし、一覧「登録・更新を試せる画面」のチェックで承認し、チェックを外して撤回する手順です。再承認が要る場合、上限と期限、守りの範囲、確かめていないことも書きます。
画面の操作の細部は「[管理画面の書き込みのシナリオ](local-ui.md#書き込みのシナリオ承認と撤回)」に、発見と READ の確かめは「[操作の候補の発見と READ の確かめ](discovery-and-read-check.md)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 画面の言葉は、この文書の言葉と違います（シナリオは「書き込みの手順」、承認は一覧の「チェック」（説明の文では「書き込みの OK」）、撤回は「チェックを外す」、発見は「操作さがし」、入力の規則は「入れる値の決まり」、照合は「答え合わせ」など）。対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」にあります。

> **承認しただけでは、書き込みは始まりません。** シナリオの下書き・承認・撤回は、管理データの中だけで行い、サイトへは何も送りません。書き込みは、次の点検の最後の書き込みの段で、ジョブの管理が実行の許可を出して始めます（「[承認された登録の手順](approved-create.md)」「[承認された更新の手順](approved-update.md)」）。送る値の作り方（入力の規則）は「[入力の規則とデータの生成](data-rules.md)」にあります。テスト用の小さなサイトで確かめています。実際のテスト環境では、チェックの保存からの API の登録 1 件を確かめました（「[実テスト環境で確かめたこと](real-test-environment.md#実テスト環境で確かめたこと2026-11-02-時点)」）。

## 使ってよい場合

- **テスト環境だけに使います。本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします（「[認証つきの監査の使ってよい場合](authenticated-audit.md#使ってよい場合)」と同じです）。
- 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）のプロファイルだけで使えます。ほかのモードのプロファイルでは、シナリオへの案内も下書きを作るボタンも出ず、サーバも作成を拒みます（`SCENARIO_MODE_NOT_WRITE`。「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。
- 承認は「このテスト環境に、この形の書き込みを、1 回に 1 件ずつ送ってよい」という人の判断の記録です。テスト環境の管理者と、登録・更新されるレコード、通知や外部のサービスへの影響を確かめてから承認してください。

## 手順

### 1. プロファイルを用意する

認証つきの読み取りの監査（`TEST_AUTH_PASSIVE`）で使っているプロファイルで、点検の後のプロファイルの詳細の一覧「登録・更新を試せる画面」で画面に初めてチェックを入れると、その保存が、監査モードを `TEST_APPROVED_WRITE` にして保存します（「[監査プロファイルの保存の後](profiles.md#保存の後)」）。確認のダイアログと、隔離の扱いの選択はありません。新しいプロファイルは作りません。認証の方式は、手動のログイン（`MANUAL_SESSION`）か自動ログイン（`AUTOMATED_LOGIN`。Windows だけ）です。

- 認証の設定（自動ログインなら資格情報も）は、同じプロファイルのものをそのまま使います（「[認証つきの監査の手順](authenticated-audit.md#手順)」、「[自動ログインの手順](automated-login.md#手順)」）。切り替えは、認証の設定が今の改訂のものであるプロファイルでだけ行えます（行えないときは、チェックの保存が「このサイトを書き込みに使えるようにできませんでした。…」で拒まれます）。
- 切り替えでプロファイルの改訂が 1 つ進みますが、切り替えだけの改訂は、発見の結果の古さの判定では同じ改訂とみなすので、操作の候補の発見のやり直しは要りません。
- このモードでも、読み取りの監査（`AUDIT`。読み取りだけ）を始められます。ほかに使えるのは、認証の設定、資格情報、操作の候補の発見、READ の確かめ、一覧のチェック（シナリオの下書き・承認・撤回）、承認された登録と更新、監査済みデータの台帳です。

### 2. ログインして、操作の候補を探す

プロファイルの詳細の「点検を始める」を押すと、監査 → 発見 → READ の確かめをまとめて行います（「[まとめて実行](stage-chain.md)」）。発見だけをやり直すときは、プロファイルの詳細の「詳しい内容」の「操作さがしの結果を見る」で画面を開き、「もう一度さがす」（まだ発見していなければ「操作さがしを始める」）を押します（「[操作の候補を探す（発見）](discovery-and-read-check.md#3-操作の候補を探す発見)」）。

- ジョブの初めにログインします。手動のログインなら、開いたブラウザで人がログインします。自動ログインなら、BeakSight が保存した資格情報で 1 回だけ送信します（「[ログインする](discovery-and-read-check.md#2-ログインする)」）。
- 発見は読むだけです。フォームの送信、入力、クリックはしません。
- シナリオは、**最後の**発見の結果の候補からだけ作れます。発見をやり直すと、候補の突き合わせ（ドリフト）が変わり、承認の判定にも響きます（「[再承認が要る場合](#再承認が要る場合)」）。

### 3. 照らす READ の定義を作る（任意）

**ふだんは要りません。** 書き込みの後に読む答え合わせ（検証の指定の「照合の READ」）の定義は、シナリオの下書きを作るときに BeakSight が作ります（照合の専用の定義。単独の READ の確かめのジョブでは読みません。「[検証の指定](approved-create.md#検証の指定)」）。READ の確かめの画面は、読み取りの点検をしたいときだけの任意の画面です（「[READ の確かめの定義を作る](discovery-and-read-check.md#4-read-の確かめの定義を作る)」）。

- 下の「照らす READ の定義」（任意）は、定義の参照（定義の ID と版）だけを持ち、承認を縛ります（定義が変わると再承認。`READ_CHECK_CHANGED`）。書き込みの後に、この参照の定義を読むことはしません。人が選ぶ画面はありません。
- 書き込みの後に実際に読む READ は、検証の指定の「照合の READ」で決めます（定義の参照、生成した値への結び付け、期待）。登録と更新には、この指定が要ります。

### 4. シナリオを作る

**シナリオは、BeakSight が下書きを作ります。** 人が手でシナリオを作る・変える画面はありません。操作さがしの画面か、シナリオが 0 件の一覧の主のボタン「書き込みの手順を作る」を 1 回押すと（確認のダイアログはありません）、最後の発見の結果の登録（CREATE）の候補（フォームの送信と API の要求の両方）から、シナリオの下書きを作り、入力の規則を推して付けます（下の「[下書きをボタン 1 回で作る](#下書きをボタン-1-回で作る)」）。更新（UPDATE）のシナリオは、一覧「登録・更新を試せる画面」のチェックの保存（と、点検の中の自動の下書き）で、BeakSight が変える欄を決めて作ります（「[承認された更新の画面の手順](approved-update.md#画面の手順)」）。

**チェックが承認を兼ねます。** 一覧「登録・更新を試せる画面」で画面にチェックを入れると、その画面の登録（と更新）のシナリオを下書きして、この文書の承認（承認の記録と digest。副作用の確認の 4 項目を確かめたことにする）を 1 回で行います。確認のダイアログはありません。チェックを外すと、撤回します。承認が無効になった（サイトの設定が変わった、など）画面は、自動で承認し直さず、行を「もう一度チェックしてください」にします（「[登録・更新を試せる画面](local-ui.md#登録更新を試せる画面)」）。

- **チェックを入れたときの作り直し**（OP-S）: チェックを入れるたびに、最後の発見の結果と今の下書きの作り方で、その画面の登録の手順を作り直します。前の手順と同じなら承認だけを行い、違えば新しい版を作って、その版を承認します。承認の決まり（digest、縛る事実、期限）は変わりません。
- **点検の始めの作り直し**（OP-T）: まとめて実行を始めるときにも、チェックした画面の登録の手順を同じく作り直して比べます。照合（答え合わせ）だけが違うときは、新しい版を自動で承認します。送る中身が違うときは、承認を取り消し、行を「もう一度チェックしてください」（`RECHECK_NEEDED`）にします。一覧のどのチェックの行にも結び付かない承認済みの登録と、結ぶ更新は取り消します（記録の理由 `UNLISTED_APPROVAL_REVOKED`）。この確かめを終えられないときは、点検を始めません（`WRITE_GRANT_REJECTED`。記録の理由 `UNLISTED_APPROVAL_GUARD_FAILED`）。どれも管理データの中だけで行い、サイトへは何も送りません。

シナリオにできる候補は、登録（CREATE）か更新（UPDATE）の候補だけです。ほかの分類の候補（`READ`、`NEEDS_BINDING`、`NOT_EXECUTABLE`、`UNSUPPORTED_READ_TRANSPORT`、`BLOCKED_EXTERNAL`、`DISPLAY_ONLY`）からは作れません。例外は、送らずに観察した型が `API_CREATE`・`API_UPDATE` の候補で、API のシナリオとして作れます（下の「[API のシナリオ](#api-のシナリオ)」）。操作さがしの画面の候補の一覧（「詳しい内容」の「見つかった操作」）は、画面ごとの分類を見るだけで、候補からシナリオを作るボタンはありません。1 つのシナリオは、1 つの候補（要求の形 1 つ）だけです。登録してから更新する、のような複数の段は扱いません。

シナリオは、次の内容を持ち、保存すると版 1 の下書き（`DRAFT`）になります。中身は BeakSight が決めます。

- **送る欄**: 候補の、見えていて、読み取り専用でも無効でもない欄だけです。次の欄は送る欄にできません（理由のコードを記録します）。
  - 秘密に見える名前（`token`、`session`、`code`、`state`、`key` など）の欄（`SCENARIO_FIELD_SECRET_LIKE`）。
  - 名前に危険な語（削除、取り消し、一括、無効、`delete`、`cancel` など）のある欄（`SCENARIO_FIELD_DANGEROUS_WORD`）。英語の語は、名前を語に分けて（`_`・`-`・`.`・大文字の切れ目・数字の境など）、語の単位で比べます。そのため `delete_flag`・`deleteFlag` は選べませんが、`deleted_at`・`undelete`・`include_disabled` は選べます（語が `delete`・`disable` と一致しないため）。日本語の語は、名前の中のどこにあっても当たります（`削除フラグ` は選べません）。判定は、発見の分類が GET の form の欄の名前に使うものと同じです。
  - パスワードの欄とファイルの欄。名前にかかわらず選べません（`SCENARIO_FIELD_TYPE_NOT_SENDABLE`）。
  - hidden の欄、`_method` の欄、読み取り専用・無効・見えない欄（`SCENARIO_FIELD_NOT_ALLOWED`）。
- **照らす READ の定義**（任意）: このプロファイルの、削除していない定義の参照です。
- **上限**: 1 回の Run の上限（`DEFAULT_MAX_CREATES_PER_RUN`＝1 件）です。1 件しか通らないので、画面では決まった値として表示だけにします。更新（UPDATE）のシナリオも、同じ値を使います（「[承認された更新の上限](approved-update.md#上限)」）。
- 累積の件数と承認の期限の日数は、撤廃しました（2026-11）。画面に欄も表示もありません。シナリオには、前の既定と同じ値（20 件・30 日）を見えないまま記録します。承認の digest の形を変えないための名残で、どの判定にも使いません。前に保存したシナリオの値は、そのまま読みます。
- **検証の指定**: 結果の判定のしかた、登録の ID の取り方、照合の READ です（「[検証の指定](approved-create.md#検証の指定)」）。フォームの送信のシナリオでは、BeakSight が観察から決めます。決められなかったことは、シナリオの詳細の要点に 1 行ずつ出ます。
- **副作用の確認**: 次の 4 項目です。一覧で画面にチェックを入れると、4 項目を確かめたことにします（下の「[承認する](#5-承認する)」）。記録の形（シナリオの版と承認の digest に副作用の確認が入り、承認がその digest を縛る）は変わりません。
  - 登録・更新されるのは、テスト環境のレコードだけであること。
  - メール・SMS・外部の通知が送られない設定であること。
  - 決済や外部のサービスに及ばないこと。
  - 削除・無効化・取り消しに当たらないこと。

保存のときに、サーバが、最後の発見の候補に照らして確かめ直します。拒んだときは、理由を項目ごとに出します。

- 作るときに、最後の発見の `discovery.json` から、その候補の詳しい内容（値を持たない形）を管理データに写します（発見の根拠の写し）。後で成果物を消しても、根拠と差分を出せるようにするためです。
- 入力の規則（送る値の作り方）は、下書きを作るときに、規則がまだない下書きなら、BeakSight が推して付けます（「[入力の規則とデータの生成](data-rules.md)」）。推せない欄があるときは、シナリオの詳細の要点に「BeakSight が入れる値を決められない欄があるので、この画面は試せません。」と出ます。

BeakSight が下書きを作り直すと（チェックの入れ直し、点検の始めの確かめ）、版が 1 つ進みます。前の版の内容は、変えずに残ります（「版の履歴」）。

### 5. 承認する

一覧「登録・更新を試せる画面」で画面にチェックを入れると、その画面の登録（と更新）のシナリオを承認します。承認のための別のボタンやダイアログはありません。

- **副作用の確認は、このチェックです。** チェックを入れると、4 項目をすべて確かめたことにして承認します。どれかに当たらない画面には、チェックを入れないでください。まだ確かめていない項目がある版は、1 つのトランザクションで、確かめた次の版を作り、その版を承認します（承認の digest は、その版のものです。版が 1 つ進みます）。
- サーバは、シナリオの版と承認の digest（承認を縛る内容の SHA-256）を、今の事実から求め直して承認します。今の事実で承認できないとき（候補がない、プロファイルが変わった、など。`SCENARIO_NOT_APPROVABLE`）は、承認せず、行に理由を出します。
- 承認すると、承認の記録を 1 件足し、シナリオは承認済み（`APPROVED`）になります。承認の記録には、承認の digest、縛った事実（下の「再承認が要る場合」の項目の値）、承認の日時、期限の日時、承認者 `LOCAL_OPERATOR` を書きます。
- 前に人が画面で決めた入力の規則が付いたシナリオは、承認の前に、推した規則に替えます（「[前に手で作った規則](local-ui.md#前に手で作った規則)」）。

**承認だけでは、書き込みは始まりません。** 書き込みは、次の点検の最後の書き込みの段で行います（「[画面の手順](approved-create.md#画面の手順)」）。

### 6. 撤回する

一覧でチェックを外すと、その画面の登録と更新のシナリオの承認を撤回します（確認のダイアログはありません）。点検の始めの確かめでも、一覧のどのチェックの行にも結び付かない承認を撤回します（上の「点検の始めの作り直し」）。

- 撤回の記録を 1 件足し、シナリオは撤回済み（`REVOKED`）になります。承認の記録は消さず、書き換えません。
- 同じ手続きの中で、まだ消費していない実行の許可を無効にし、送っていない件数の予約（`RESERVED`）を返します（`RELEASED`）。
- 送った書き込みは取り消せません。
- 動いている書き込みのジョブに、止める合図は送りません。ジョブは、送る直前の確かめ直しで、承認が取り消されていれば送りません。確かめ直しの答えを受けた後の短い間にチェックを外したときは、送ります（「[確かめていないこと](approved-create.md#確かめていないこと使えないこと)」）。
- 撤回の後に使うときは、もう一度チェックを入れます。

## API のシナリオ

ページのスクリプトが API の要求で書き込む画面（form のない画面を含む）のシナリオです。送り方は「API の要求」になります（form のシナリオは「フォームの送信」）。書き込みの手順は「[承認された登録の API の登録](approved-create.md#api-の登録)」にあります。API の更新（UPDATE）の書き込みの手順は「[承認された更新の API の更新](approved-update.md#api-の更新)」にあります。前の形で保存したシナリオの版（Task 41 より前に保存した、保つ鍵などの指定を持たない API の更新、UPDATE の指定や検証の指定を入れる前に保存した版）は読みません。管理データにあれば、管理データの誤り（`DATABASE_INTEGRITY_FAILED`）で止まります（前の形の読み替えは、利用者のデータに残っていないので捨てました）。

### 作り方

- 書き込みのモードのプロファイルで発見を行います。ページを送らずに観察した型（「[送らずに観察する押下（probe）](discovery-and-read-check.md#送らずに観察する押下probe)」）が `API_CREATE`（か `API_UPDATE`）の候補があると、操作さがしの画面の「書き込みの手順を作る」が、その型の行ごとに API のシナリオの下書きを作ります（下の「[下書きをボタン 1 回で作る](#下書きをボタン-1-回で作る)」）。候補から 1 つずつ作るボタンは、今はありません。
- 「API の要求の型と、送る鍵」は、発見で観察した型から埋まります。値は入れません。
  - 「本文の鍵と欄」: 欄に値を入れて送る本文の鍵です。欄に対応する鍵は、すべて送ります（決まった値なので、表示だけです）。
  - 「ページが決める鍵」: 欄に対応せず、ページが値を決める鍵です。すべて許します（決まった値なので、表示だけです）。値は照らさず、実行したときの値を書き込みの結果の記録に残します。秘密に見える名前の鍵と、値が object・配列の鍵があると、そのシナリオは保存できません（理由を示します）。秘密に見える名前は語の部分一致で見分けます（`accesstoken` のような区切りのない名前も当たります）。部分一致の誤検知として、鍵の名前がちょうど `author`・`footprint` のときだけは除きます（Task 44 の P4-2。`author_token` などは今どおり当たります）。
  - 「ページが付けるヘッダの名前」: ブラウザが付ける名前を除いた名前の案です。承認に結びます。
  - 「登録の ID を読む応答の鍵（任意）」: 応答の本文の、登録の ID の鍵の名前です（「[API の登録](approved-create.md#api-の登録)」）。秘密に見える名前は使えません。
- 検証の指定は 2 項目です（登録の ID の取り方と、照合の READ。「[API の検証の指定](approved-create.md#api-の検証の指定)」）。成功の条件と入力の誤りの条件は使いません。

### 下書きをボタン 1 回で作る

操作さがしの画面の主のボタン「書き込みの手順を作る」で、最後の発見の結果から、シナリオの下書きをまとめて作れます。API の要求の型の行（下）と、フォームの送信の登録の候補（「[検証の指定](approved-create.md#検証の指定)」の「決め方」。送る欄は、必須の欄と送らないと保存できない欄のうち送れる欄で、文字の欄がなければ最初の送れる文字の欄を足します）の両方です。作るのは下書きだけです。承認・副作用の確認・実行の許可・書き込みは行いません。サイトには接続しません（管理データと発見の結果のファイルだけを読みます）。

- **押せるとき**: 承認した書き込みのモードのプロファイルで、最後の発見の時のプロファイルの改訂が今の改訂と同じときだけです。書き込みのモードへの切り替え（一覧のチェックの保存）だけで進んだ改訂は、同じ改訂とみなします（切り替えの前の発見の結果から作れます。承認したサービスの Origin の一覧が変わった改訂と、保存の記録から確かめられない改訂は、同じとみなしません）。違うときは、理由（「前回の操作さがしの後に、サイトの設定を変えました」など）と次にできること（発見をやり直す）が出ます。下書きがもうあるときは、主のボタンは「書き込みの手順を見る」になります。シナリオが 0 件の一覧では、使える発見の結果がないとき、主のボタン「書き込みの手順を作る」が発見を始めます。
- **1 回の押下で作る**: 確認のダイアログはありません（下書きはサイトへ何も送らず、承認の前に中身を見られるためです）。作った結果は「書き込みの手順を N 個作りました。」の 1 行と、作った結果の一覧（画面ごとに作ったか、更新の案内）で出ます。新しく作るものがなかったとき（ほかの画面で先に作ってあった、など）は「新しく作る書き込みの手順はありませんでした。」です。画面を開いた後にプロファイルか最後の発見が変わったら、何も作りません（理由と、読み込み直す手順が出ます）。
- **登録（`API_CREATE` の型の行ごとに 1 つ）**: 送る鍵は欄に対応する鍵のすべて、ページが決める鍵は選べる鍵のすべてです。副作用の確認の 4 項目は、どれも確かめていない状態で作ります（一覧のチェックで確かめます）。
  - 登録の ID を読む応答の鍵は、同じ表（同じ送り先の Origin と path の型）の更新の型の filter の名前が 1 つだけのとき、その名前から推します（推測の印）。推せなければ空にします。
  - 入力の規則は、推した規則の集まり（「[入力の規則とデータの生成](data-rules.md)」）を作って付けます。推せなかった欄があれば、シナリオの詳細の要点に 1 行出ます（その画面は試せません）。
  - 照合の READ: 読めた画面の path のうち、登録の画面の path（か、その 1 つ上の path）の直下に ID に見える区切り（レコードの ID の形で、数字を含む区切り）を 1 つ足した path から、`{id}` の型の画面の READ の定義を推して作ります（推測の印。定義の期待は、決まりのとおり仮の 1 件です。型の定義は単独では読みません）。同じ型の定義が既にあれば、それを使います。定義の数が上限（1 つのプロファイルで 20）に達しているときと、読まないパスなどの保存の確かめに当たるときは作りません。
  - 照合の READ の期待は、入力の規則を付けた後に、実行のたびに値が変わる欄の最初の 1 つと比べる「本文が含む」を推して入れます（推測の印）。推せなければ空にし、推せなかった理由（入力の規則を付けられなかった、照合の READ の定義がない、値が変わる欄がない、結んだ版の保存が拒まれた）が出ます。
  - 照合の READ に結べないときは、推した型の定義を作りません（作った後に結べなかった定義は取り消します）。結ばれない定義が、定義の数の上限に数えられることはありません。同じ型の既にある定義は、そのまま残します。
- **更新（`API_UPDATE` の型の行と、フォームの更新の候補）**: このボタンでは作りません（結果の一覧に、行の状態だけが出ます）。更新は、一覧のチェックの保存と点検の中の自動の下書きが、BeakSight の決めた変える欄で作ります。
  - 台帳（結び付く登録のシナリオがちょうど 1 つのとき）と更新の画面の型（選べる型の先頭。2 つ以上のときは推測の印）を、BeakSight が選びます。
  - 作るときに、推した入力の規則の集まりを付け（承認の前）、照合の READ と登録の ID の型を、台帳の登録のシナリオから写します（「[承認された更新の画面の手順](approved-update.md#画面の手順)」）。
- **既にあるもの**: 同じ型の行のシナリオが既にあれば（下書き・承認済み・撤回済みのどれでも）、作らず、「既にあります」と出します。既にあるシナリオは書き換えません。
- **推測の印**: シナリオの詳細の「詳しい内容」の「推測した項目（確かめてください）」に、推した値のまま残る項目が出ます。印は表示のときに求め直すもので、承認には結び付きません。
  - 登録の ID を読む応答の鍵、照合の READ の画面の型、照合の READ の期待の欄: 自動の下書きが作ったシナリオで、自動の下書きの値のままのときだけ出します。前に人が作った・変えたシナリオの値には、推した値と同じでも出しません。副作用の確認などで版を上げても、値が変わらなければ出ます。
  - 更新の画面の型: 選べる型が 2 つ以上で、BeakSight が選んだ先頭の型のときに出ます。
  - 範囲の既定の幅を入れた欄: 推した入力の規則が、範囲の手がかりのない日付・数の欄に既定の幅を入れたまま（「[入力の規則とデータの生成](data-rules.md)」）。

### 保存で拒むもの

保存のときに、最後の発見の索引に照らして確かめ直します。次のときは保存しません（一覧の行に、試せない理由が出ます）。

- 候補の型が `API_CREATE`・`API_UPDATE` でない（`SCENARIO_API_CANDIDATE_NOT_API`）。論理削除にあたる鍵がある（`SCENARIO_API_STATE_KEY`）。method の上書きがある（`SCENARIO_API_METHOD_OVERRIDE`・`SCENARIO_API_HEADER_METHOD_OVERRIDE`）。
- 送り先の Origin が承認したサービスの Origin でない（`SCENARIO_API_ORIGIN_NOT_APPROVED`）。型が実行できない形（`SCENARIO_API_SHAPE_NOT_EXECUTABLE`）。
- 送る欄と鍵がちょうど 1 つずつ対応しない、欄の型と JSON の型が合わない（`SCENARIO_API_FIELD_KEY_MISMATCH`・`SCENARIO_API_FIELD_TYPE_MISMATCH`）。許していない鍵（`SCENARIO_API_KEY_NOT_ALLOWED`）。
- ページが決める鍵や、登録の ID の鍵の名前が秘密に見える（`SCENARIO_API_PAGE_KEY_SECRET_LIKE`・`SCENARIO_API_RECORD_ID_KEY_SECRET_LIKE`）。ページが決める鍵の値が object（`SCENARIO_API_PAGE_KEY_NOT_SCALAR`）。
- 一覧（配列）の鍵は、登録（作成）だけで、入れ子のない、文字・数・真偽・null の一覧に限って許します。要素が object・配列（`SCENARIO_API_ARRAY_NESTED`）、要素の数か文字の長さが上限を超える（`SCENARIO_API_ARRAY_OVER_LIMIT`。要素 20・文字 200）、欄の値が入る一覧の要素が文字でない・1 つでない（`SCENARIO_API_ARRAY_ELEMENT_TYPE_MISMATCH`・`SCENARIO_API_ARRAY_ELEMENT_COUNT_MISMATCH`）ときは拒みます。更新の一覧の鍵と、一覧の中身を記録していない古い発見の型は、`SCENARIO_API_PAGE_KEY_NOT_SCALAR` で拒みます（発見をやり直します）。ページが決める一覧は、発見のときの要素の型と数を承認に含め、書き込みの直前に照らします。欄の値が入る一覧は、位置ごとに照らします。欄の位置は入れた値と完全に一致し、ほかの位置は承認した空の値（空の文字か null）と一致し、要素の数が承認と同じであることを求めます（2026-11-09 DEF-234 の段 A1）。1 つの一覧に欄の印が 2 つ以上ある鍵は、位置ごとの欄の鍵（`key[0]`・`key[1]` のような道）に分けて受け、欄ごとに値を作って入れます（DEF-234 の段 A2）。位置ごとに分けられない形（1 つの位置に印が 2 つ、要素が 21 以上で位置の情報がない、道がほかの鍵と重なる・長すぎる）は拒みます（`SCENARIO_API_ARRAY_MULTIPLE_FIELDS`）。位置の情報がない古い発見の型で、要素が 2 つ以上の欄の一覧は、発見をやり直すまで `SCENARIO_API_ARRAY_ELEMENT_COUNT_MISMATCH` で拒みます。ページが決める一覧の要素の値そのものは照らさず、結果の記録に残します。
- 更新の filter の名前が要求の型と違う（`SCENARIO_API_FILTER_MISMATCH`）。
- 更新で、欄として識別できないページが決める鍵がある（`SCENARIO_API_PAGE_KEY_NOT_IDENTIFIABLE`）。更新では、ページが決める鍵は、更新の画面の欄として識別でき、送る前の値と照らせるものだけを許します。
- 更新で、台帳の ID と filter が結び付かない（`SCENARIO_API_FILTER_NOT_BOUND_TO_LEDGER_ID`・`SCENARIO_UPDATE_PATH_NOT_BOUND_TO_LEDGER_ID`。「[台帳の ID と filter の結び付け](approved-update.md#台帳の-id-と-filter-の結び付け)」）。
- 候補を見つけた発見の後に、プロファイルを編集した（`SCENARIO_API_DISCOVERY_PROFILE_STALE`。書き込みのモードへの切り替えだけなら当たりません。発見をやり直します）。
- 照合の READ（`{id}` の型の画面の READ）の期待が、行の数だけ（`SCENARIO_API_READ_VERIFICATION_NOT_BOUND`。「[API の検証の指定](approved-create.md#api-の検証の指定)」）。

### 再承認が要る場合（API のシナリオだけの理由）

下の「再承認が要る場合」の理由に加えて、API のシナリオには次の理由があります。

| 理由 | 利用者の言葉で |
| --- | --- |
| `CANDIDATE_SHAPE_CHANGED` | 最後の発見で、ページが送る要求の型（送り先、本文の鍵、ページが付けるヘッダの名前など）が、承認した型と違った。 |
| `CANDIDATE_SHAPES_UNAVAILABLE` | 対象の候補の要求の型の記録が、管理データにまだない（発見をやり直す）。 |
| `CANDIDATE_FIELDS_CHANGED` | 要求の型は同じでも、本文の鍵に値を入れる欄（名前か CSS）が、承認した対応と違った。 |
| `API_ORIGIN_NOT_APPROVED` | シナリオの送り先の Origin が、今のプロファイルの承認したサービスの Origin の一覧の、同じ位置にない。 |
| `API_DISCOVERY_PROFILE_STALE` | 最後の発見が、プロファイルを編集する前の内容で行われた（発見をやり直す）。 |

## 再承認が要る場合

承認が今も有効かは、1 つの判定（`src/control/approval/approval-validity.ts`）だけで決めます。画面の表示、実行の許可の発行、書き込みの前の確かめ直し（登録と更新のジョブ）は、すべてこの判定を通します。次のどれかに当たると、承認は無効になり、画面に「要再承認」（期限切れ、撤回済み、未承認はその状態）と理由を出します。理由は、当たったものをすべて出します。

| 理由 | 利用者の言葉で |
| --- | --- |
| `SCENARIO_REVISION_CHANGED` | 承認した後に、シナリオの版が変わった（下書きの作り直しなど）。 |
| `PROFILE_REVISION_CHANGED` | 承認した後に、プロファイルを編集した。どの項目の編集でも、承認は引き継がない。 |
| `AUTH_SETUP_CHANGED` | 承認した後に、認証の設定が変わった。自動ログインなら、資格情報を登録・変更・削除したときも（下の注）。 |
| `TARGET_CONFIG_CHANGED` | 承認した後に、プロファイルが指す設定のファイル（ターゲットの設定）の内容が変わった。 |
| `CANDIDATE_CHANGED` | 最後の発見で、対象の候補の入力の規則（必須・制約・選択肢など）か分類が変わった。 |
| `CANDIDATE_MISSING` | 最後の発見で、対象の候補が見つからないか、その画面を読み直していない。更新（UPDATE）のシナリオは、path の ID の区切りを型にした識別で確かめます。 |
| `CANDIDATE_TEMPLATES_UNAVAILABLE` | 更新（UPDATE）のシナリオで、最後の発見の、型にした識別の digest の一覧をまだ集められない（管理データの版 9 より前の状態）。 |
| `INPUT_RULES_CHANGED` | 入力の規則の参照（集まり・版・digest）が変わった。 |
| `READ_CHECK_CHANGED` | 照らす READ の確かめの定義か、検証の指定の照合の READ の定義が、変わったか、削除されたか、見つからない。 |
| `EXPIRED` | （前の記録だけ）承認の期限を過ぎた。承認の期限は撤廃したので、今は出ません。 |
| `REVOKED` | 最後の承認を撤回した（チェックを外した、など）。 |
| `NOT_APPROVED` | まだ承認していない。 |
| `PROFILE_RETIRED` | プロファイルを取り消した。取り消したプロファイルのシナリオは承認できない。 |
| `MODE_NOT_WRITE` | プロファイルの監査モードが、承認した書き込みのモード（`TEST_APPROVED_WRITE`）でなくなった。 |

- 自動ログインのプロファイルでは、承認は資格情報の値ではなく、資格情報の「事実」を縛ります: 資格情報のファイルの版と、資格情報の登録・変更・削除の記録（管理データの `credential_events`）の最後の記録です。資格情報を変えると版が進み、削除して別の値で登録し直すと（版は 1 に戻りますが）記録が増えるので、どちらも `AUTH_SETUP_CHANGED` になります。自動ログインの停止を解く操作は、資格情報の変更に数えません。手動のログインのプロファイルでは、資格情報を縛りません。
- 候補の判定は、承認の記録に固定した候補の 2 つの digest（識別と規則）と、最後の発見の索引の digest の比べで決めます。発見をやり直して候補が `CHANGED` になっても、2 つの digest が同じなら承認は有効のままです。
- どの理由でも、自動では引き継ぎません。一覧の行が「もう一度チェックしてください」になるので、もう一度チェックを入れます（点検の始めの確かめで、答え合わせだけが違うときは、自動で承認します）。

## 上限と期限

上限は、名前つきの定数（`src/control/approval/scenario-contracts.ts`）です。承認の期限、累積の件数、書き込みの間隔と 1 日の件数は、2026-11 に撤廃しました（承認は、型の digest が変わるか、チェックを外して撤回するまで有効です）。

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `DEFAULT_MAX_CREATES_PER_RUN` | 1 件 | 1 回の Run で書き込める件数（1 つのジョブが送るのは承認した 1 回）。 |
| `WRITE_JOB_CONCURRENCY` | 1 | 書き込みの同時実行の数（シナリオとプロファイルをまたいで 1 つ）。 |
| `EXECUTION_GRANT_TTL_MS` | 5 分 | ジョブが始まらなかった許可を、古い許可として捨てるまでの時間（同時実行の枠を空けるため）。ジョブが動いている許可は、期限で切れません。 |
| `APPROVAL_TTL_DAYS`・`DEFAULT_MAX_CUMULATIVE_CREATES` | 30・20 | 新しく作るシナリオに見えないまま記録する名残の値（承認の digest の形を変えないため）。どの判定にも使いません。 |

- **実行の許可**（ExecutionGrant）: 書き込みのジョブ（登録と更新）は、承認が今も有効であることを、1 つのジョブに結び付いた、期限つきで 1 回だけ使える許可で確かめてから始めます。許可は、承認の判定のやり直し、入力の規則の参照があること（なければ `NEEDS_RULE_INPUT`）、消費していない許可がないこと、上限の残り、書き込みの同時実行の枠を、1 つの手続きの中で確かめてから出します。偽造（ない ID、別のシナリオ・ジョブ・プロファイル・版への流用）、期限切れ、2 回目の使用は拒みます。許可は、点検の最後の書き込みの段で、チェックした画面ごとにジョブの管理が出します。
- **件数の予約**（WriteReservation）: 許可を出すときに、同じ手続きの中で、1 回の Run の件数を予約します（累積の上限は撤廃しました）。1 つの許可に予約は 1 件です。累積の件数には、予約中（`RESERVED`）・送った（`COMMITTED`）・送ったか分からない（`UNKNOWN`）を数え、送る前に返した予約（`RELEASED`）は数えません。期限を過ぎて、まだ無効にしていない許可の予約も数えません（次の許可を出すときに、無効にして返すため）。画面の「使った件数」も、同じ数え方の部品で数えます。
- **書き込みの前の確かめ直し**（登録と更新のジョブが、送る直前に呼びます）: 許可が消費済みで、無効でなく、その予約が予約中（`RESERVED`）のままで、承認が今も有効で、承認の記録と版が許可を出したときと同じときだけ受けます。予約を送った・分からない・返した後（`GRANT_RESERVATION_SETTLED`）は受けません（1 つの許可で 2 件目を送らない）。時計が巻き戻って、承認より前の時刻で許可を出そうとしたとき（`GRANT_CLOCK_BEFORE_APPROVAL`）と、許可を出した時刻より前の時刻で使おうとしたとき（`GRANT_CLOCK_BEFORE_ISSUE`）も拒みます。
- 2 つの許可の発行が同時に来ても、予約の合計は上限を超えません。撤回と発行が同時に来ても、撤回の後に有効な許可は残りません。

## サイトへの読み込み

- シナリオの下書き・承認・撤回（一覧のチェック）は、管理データの中だけで行います。**サイトへは何も送りません**（読み込みも書き込みもしません）。
- 下書きを作る（「書き込みの手順を作る」）のも、管理データと発見の結果のファイルを読むだけで、サイトへは送りません。
- サイトへ届くのは、手順 2 の発見と、手順 3 の READ の確かめのジョブの要求だけです。間隔と上限は「[サイトへの読み込み](discovery-and-read-check.md#サイトへの読み込み)」と同じです（読み込みどうしの間隔は設定の `crawl.minNavigationIntervalMs` 以上、読み込み直しはしません）。

## 守りの範囲

- **シナリオの下書き・承認・撤回では、書き込みをしません。** 承認の部品（`src/control/approval/`）は、ブラウザやワーカーなど、要求を送る部品を使いません（自動の検査で確かめます）。サイトへ書き込むのは、承認の後に点検の書き込みの段で動く登録と更新のジョブ（ワーカー）だけです。
- **承認と撤回の記録は、追記だけです。** 承認と撤回の記録（`approval_receipts`）と、シナリオの版の写し（`scenario_revisions`）は、書き換えも削除もしません（`UPDATE`・`DELETE`・`REPLACE`・upsert の文を BeakSight のコードに書かないことを、自動の検査で確かめます）。管理データを開き直しても（画面のサーバの再起動）、承認は同じ内容のまま読め、有効なら使えます。
- **管理データのファイルを直接書き換えた場合の守りは限られます。** 追記だけの決まりは BeakSight のコードの決まりで、データベースの仕組み（trigger など）では止めていません。管理データのファイル（`local-data/`）を別の道具で書き換えると、記録を変えられます。承認の判定は、記録の承認の digest を今の内容から求め直して比べ、期限は記録の期限と「承認の日時 + 承認した版の日数」の早い方を使いますが、承認の日時と期限の日時を両方書き換えると、期限が延びることがあります。管理データのファイルは、このコンピュータの利用者だけが書けるようにしてください。
- **承認者は `LOCAL_OPERATOR` です。** 利用者の ID がない（このコンピュータの 1 人だけが使う）ので、固定の値を記録します。OS の利用者名などは記録しません。
- **承認と撤回は、一覧のチェックの保存と、点検の始めの確かめだけです。** チェックの保存は、同じ Origin からの POST だけを受けます（CSRF の確かめ。「[管理画面の守り](local-ui.md#守り)」）。
- **秘密を持ちません。** シナリオ、発見の根拠の写し、承認と撤回の記録、実行の許可と予約には、入力の値、CSRF のトークン、hidden の値、選択肢の label、資格情報、Cookie、localStorage の値を持ちません。
- **ページが書いた値は、発見の根拠の写しに残ります。** 送信先の path と query の名前、欄の名前、欄の制約（`pattern`・`min`・`max` などの属性の文字列）、選択肢の値は、ページが書いた値のまま管理データに写します（`discovery.json` と同じです。「[候補の見方](discovery-and-read-check.md#候補の見方)」）。ページがそこに個人情報や表の行の中身を書けば、管理データに残ります。シナリオの詳細の画面は、送る欄の名前だけを出し、選択肢の値は出しません。管理データ（`local-data/`）は、テスト環境のデータと同じに扱ってください。

### 確かめたこと（目印の検査）

テスト用の小さなサイトで、実行ごとのランダムな値を目印にし（セッションの Cookie、localStorage、資格情報、CSRF のトークン、hidden の値、入力の欄の今の値、選択肢の label、表の行の中身）、手動のログインと自動ログイン（本物の DPAPI。Windows）のそれぞれで、画面から発見 → READ の定義の作成 → 一覧で登録の画面にチェックを入れる（シナリオの下書きと承認。結ぶ更新の下書きを含む）→ チェックを外す（撤回）を行って、目印が 1 つも出ないことを、UTF-8 と UTF-16LE の両方のバイトで確かめています。

- 探した場所: Run のディレクトリのすべてのファイル（`discovery.json`）、管理データのファイルと WAL と SHM と、すべての表のすべての行（シナリオ、版の写し（発見の根拠の写し）、承認と撤回の記録、実行の許可、予約を含む）、画面のサーバとワーカーの標準出力と標準エラー、ワーカーとの間の通信のすべて（両方の向き）、すべての画面の HTML（サイトの画面の一覧、シナリオの一覧・詳細の画面を含む）と成果物の画面、Server Function の応答、子プロセスの起動の引数。
- 実行の許可と予約の表にも行がある状態で探すため、テストだけの操作として、入力の規則の参照を付け、承認の後に実行の許可を 1 つ出しています。チェックを外す撤回で、その許可が無効になり、予約が返り、次の許可の発行が拒まれることも確かめています。
- 同じ確かめで、サイトに届いた要求が、GET と HEAD のほかは発見のジョブのログインの送信 1 回だけであること、チェックを入れる・外す間はサイトへの要求が 0 件であることを確かめています。
- 探す読み方が正しいことは、わざと目印を置いたファイル（UTF-16LE）が見つかることと、秘密でない値（シナリオの ID、承認の digest、実行の許可の ID）が管理データの表の行とシナリオの画面で見つかることで確かめています。

## 確かめていないこと・使えないこと

- **入力の規則の中身**（送る値の作り方）: 「[入力の規則とデータの生成](data-rules.md)」にあります（確かめていないことも、そちらに書きます）。送る欄すべての作り方が決まっていないシナリオには、実行の許可を出せません。
- **書き込みの実行**: 「[承認された登録の手順](approved-create.md)」と「[承認された更新の手順](approved-update.md)」にあります（送ったか分からない場合の扱い、照合の READ、確かめていないことを含みます）。
- **複数の段のシナリオ**（登録してから更新する、など）: 扱いません。
- **実際のテスト環境**: 一覧のチェックの保存で、API の登録の手順 1 つを下書きして承認し、次の点検の登録まで確かめました（「[実テスト環境で確かめたこと](real-test-environment.md#実テスト環境で確かめたこと2026-11-02-時点)」）。
- CLI からのシナリオの操作。
