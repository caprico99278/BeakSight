# 書き込みのシナリオの承認の手順（テスト環境だけ）

テスト環境の管理画面で、操作の候補の発見で見つかった登録（CREATE）・更新（UPDATE）の候補を「シナリオ」にし、人が内容を確かめて承認し、撤回する手順です。再承認が要る場合、上限と期限、守りの範囲、確かめていないことも書きます。
画面の操作の細部は「[管理画面の書き込みのシナリオ](local-ui.md#書き込みのシナリオ承認と撤回)」に、発見と READ の確かめは「[操作の候補の発見と READ の確かめ](discovery-and-read-check.md)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> **承認しただけでは、書き込みは始まりません。** シナリオの作成・変更・承認・撤回は、管理データの中だけで行い、サイトへは何も送りません。書き込みは、承認の後に、人が画面「書き込みを始める」から 1 件ずつ始めます（「[承認された登録の手順](approved-create.md)」「[承認された更新の手順](approved-update.md)」）。送る値の作り方（入力の規則）は「[入力の規則とデータの生成](data-rules.md)」にあります。テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません。

## 使ってよい場合

- **テスト環境だけに使います。本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします（「[認証つきの監査の使ってよい場合](authenticated-audit.md#使ってよい場合)」と同じです）。
- 監査モードが `TEST_APPROVED_WRITE`（承認した書き込み）のプロファイルだけで使えます。ほかのモードのプロファイルでは、シナリオへの案内も「シナリオを作る」も出ず、サーバも作成を拒みます（`SCENARIO_MODE_NOT_WRITE`。「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。
- 承認は「このテスト環境に、この形の書き込みを、この件数まで、この期限まで送ってよい」という人の判断の記録です。テスト環境の管理者と、登録・更新されるレコード、通知や外部のサービスへの影響を確かめてから承認してください。

## 手順

### 1. プロファイルを用意する

監査モードを `TEST_APPROVED_WRITE`、環境を `TEST` にしたプロファイルを作ります（「[監査プロファイル](profiles.md)」）。認証の方式は、手動のログイン（`MANUAL_SESSION`）か自動ログイン（`AUTOMATED_LOGIN`。Windows だけ）です。

- 認証の設定（自動ログインなら資格情報も）を作ります。手順は、認証つきの読み取りの監査と同じです（「[認証つきの監査の手順 1〜3](authenticated-audit.md#手順)」、「[自動ログインの手順 1〜5](automated-login.md#手順)」）。
- このモードの監査（`AUDIT`）は始められません。使えるのは、認証の設定、資格情報、ログインの確かめ、操作の候補の発見、READ の確かめ、シナリオの作成・変更・承認・撤回、入力の規則、承認された登録と更新、監査済みデータの台帳です。

### 2. ログインして、操作の候補を探す

プロファイルの詳細の「操作の候補と READ の確かめ」から画面「操作の候補」を開き、「操作の候補を探す」を押します（「[操作の候補を探す（発見）](discovery-and-read-check.md#3-操作の候補を探す発見)」）。

- ジョブの初めにログインします。手動のログインなら、開いたブラウザで人がログインします。自動ログインなら、BeakSight が保存した資格情報で 1 回だけ送信します（「[ログインする](discovery-and-read-check.md#2-ログインする)」）。
- 発見は読むだけです。フォームの送信、入力、クリックはしません。
- シナリオは、**最後の**発見の結果の候補からだけ作れます。発見をやり直すと、候補の突き合わせ（ドリフト）が変わり、承認の判定にも響きます（「[再承認が要る場合](#再承認が要る場合)」）。

### 3. 照らす READ の定義を作る（任意）

書き込みの後に結果を照らす READ の確かめの定義を、先に作っておけます（「[READ の確かめの定義を作る](discovery-and-read-check.md#4-read-の確かめの定義を作る)」）。

- 下の「照らす READ の定義」（任意）は、定義の参照（定義の ID と版）だけを持ち、承認を縛ります（定義が変わると再承認。`READ_CHECK_CHANGED`）。書き込みの後に、この参照の定義を読むことはしません。
- 書き込みの後に実際に読む READ は、検証の指定の「照合の READ」で決めます（定義の参照、生成した値への結び付け、期待。「[検証の指定](approved-create.md#検証の指定)」）。登録と更新には、この指定が要ります。

### 4. シナリオを作る

画面「操作の候補」の、登録（CREATE）か更新（UPDATE）の候補の「シナリオを作る」から開きます。ほかの分類の候補（`READ`、`NEEDS_BINDING`、`NOT_EXECUTABLE`、`UNSUPPORTED_READ_TRANSPORT`、`BLOCKED_EXTERNAL`、`DISPLAY_ONLY`）からは作れません。1 つのシナリオは、1 つの候補（要求の形 1 つ）だけです。登録してから更新する、のような複数の段は扱いません。

次を決めて保存すると、版 1 の下書き（`DRAFT`）になります。

- **送る欄**: 候補の、見えていて、読み取り専用でも無効でもない欄だけを選べます。次の欄は選べず、その欄に理由を出します。
  - 秘密に見える名前（`token`、`session`、`code`、`state`、`key` など）の欄（`SCENARIO_FIELD_SECRET_LIKE`）。
  - 名前に危険な語（削除、取り消し、一括、無効、`delete`、`cancel` など）のある欄（`SCENARIO_FIELD_DANGEROUS_WORD`）。英語の語は、名前を語に分けて（`_`・`-`・`.`・大文字の切れ目・数字の境など）、語の単位で比べます。そのため `delete_flag`・`deleteFlag` は選べませんが、`deleted_at`・`undelete`・`include_disabled` は選べます（語が `delete`・`disable` と一致しないため）。日本語の語は、名前の中のどこにあっても当たります（`削除フラグ` は選べません）。判定は、発見の分類が GET の form の欄の名前に使うものと同じです。
  - パスワードの欄とファイルの欄。名前にかかわらず選べません（`SCENARIO_FIELD_TYPE_NOT_SENDABLE`）。
  - hidden の欄、`_method` の欄、読み取り専用・無効・見えない欄（`SCENARIO_FIELD_NOT_ALLOWED`）。
- **照らす READ の定義**（任意）: このプロファイルの、削除していない定義から選びます。
- **上限**: 1 回の Run の上限と、累積の上限です。既定（`DEFAULT_MAX_CREATES_PER_RUN`＝1 件、`DEFAULT_MAX_CUMULATIVE_CREATES`＝20 件）以下にだけできます。1 件より小さくはできません。1 回の Run の上限は、累積の上限以下にします。更新（UPDATE）のシナリオも、同じ値を使います（「[承認された更新の上限](approved-update.md#上限)」）。
- **承認の期限**: 承認してから期限までの日数です。既定（`APPROVAL_TTL_DAYS`＝30 日）以下にだけできます。1 日より短くはできません。
- **副作用の確認**: 次の 4 項目です。保存は確かめていない項目があってもできますが、承認は 4 項目すべてを確かめるまでできません。
  - 登録・更新されるのは、テスト環境のレコードだけであること。
  - メール・SMS・外部の通知が送られない設定であること。
  - 決済や外部のサービスに及ばないこと。
  - 削除・無効化・取り消しに当たらないこと。

保存のときに、サーバが、最後の発見の候補に照らして確かめ直します。拒んだときは、理由を項目ごとに出します。

- 作るときに、最後の発見の `discovery.json` から、その候補の詳しい内容（値を持たない形）を管理データに写します（発見の根拠の写し）。後で成果物を消しても、根拠と差分を出せるようにするためです。
- 入力の規則（送る値の作り方）は、シナリオを作った後に、シナリオの詳細の「入力の規則を開く」から決めます（「[入力の規則とデータの生成](data-rules.md)」）。保存するまで、シナリオの詳細には「未設定。入力の規則を決めるまで、実行の許可は出せません。」と出ます。規則を保存すると、シナリオの版が 1 つ上がり、下書きに戻ります（承認していた場合は再承認が要ります）。

シナリオを変えるときは、詳細の「変える」から開きます（候補は変えられません）。保存するたびに版が 1 つ進み、下書きに戻ります。前の版の承認は引き継ぎません。前の版の内容は、変えずに残ります（「版の履歴」）。

### 5. 承認する

シナリオの詳細の「承認する」を押すと、確認のダイアログが開きます。

- ダイアログは、開くと「やめる」にフォーカスします。Enter や Escape だけでは承認しません。「承認する」を選んで押したときだけ承認します。
- ダイアログには、上限、承認の期限、副作用の確認、最後の承認との差分（項目ごとに「前の値 → 今の値」と説明）を出します。差分を読んでから承認してください。
- サーバは、画面に出したシナリオの版と承認の digest（承認を縛る内容の SHA-256）を、今の事実から求め直した値と比べます。違えば「画面が古い」として承認しません（`SCENARIO_REVISION_CONFLICT`、`SCENARIO_APPROVAL_DIGEST_MISMATCH`）。画面を読み込み直し、今の内容と差分を確かめてから、もう一度承認します。
- 副作用の確認に未確認の項目があるとき（`SCENARIO_SIDE_EFFECTS_UNCONFIRMED`）と、今の事実で承認できないとき（候補がない、プロファイルが変わった、など。`SCENARIO_NOT_APPROVABLE`）は、承認しません。
- 承認すると、承認の記録を 1 件足し、シナリオは承認済み（`APPROVED`）になります。承認の記録には、承認の digest、縛った事実（下の「再承認が要る場合」の項目の値）、承認の日時、期限の日時、承認者 `LOCAL_OPERATOR` を書きます。
- 承認済みのシナリオを、もう一度承認することもできます（記録が 1 件増え、期限は新しい承認から数えます）。

**承認だけでは、書き込みは始まりません。** 書き込みは、承認の後に、シナリオの詳細の「書き込みを始める画面を開く」から開く画面「書き込みを始める」で、人が確認のダイアログを経て始めます（「[画面の手順](approved-create.md#画面の手順)」）。

### 6. 撤回する

承認済みのシナリオの詳細の「承認を撤回する」を押すと、確認のダイアログが開きます（開くと「やめる」にフォーカス）。「撤回する」を押したときだけ撤回します。

- 撤回の記録を 1 件足し、シナリオは撤回済み（`REVOKED`）になります。承認の記録は消さず、書き換えません。
- 同じ手続きの中で、まだ消費していない実行の許可を無効にし、送っていない件数の予約（`RESERVED`）を返します（`RELEASED`）。
- 送った書き込みは取り消せません。
- 撤回とシナリオの変更のときは、親（画面のサーバ）が、そのシナリオの動いている書き込みのジョブに止める合図を送ります。送る直前の確かめ直しの答えを受けた後の短い間に撤回したときは、送ります（「[確かめていないこと](approved-create.md#確かめていないこと使えないこと)」）。
- 撤回できるのは、承認済みのシナリオだけです（`SCENARIO_NOT_APPROVED`）。撤回の後に使うときは、内容を確かめてから、もう一度承認します。

## 再承認が要る場合

承認が今も有効かは、1 つの判定（`src/control/approval/approval-validity.ts`）だけで決めます。画面の表示、実行の許可の発行、書き込みの前の確かめ直し（登録と更新のジョブ）は、すべてこの判定を通します。次のどれかに当たると、承認は無効になり、画面に「要再承認」（期限切れ、撤回済み、未承認はその状態）と理由を出します。理由は、当たったものをすべて出します。

| 理由 | 利用者の言葉で |
| --- | --- |
| `SCENARIO_REVISION_CHANGED` | 承認した後に、シナリオを編集した（版が変わった）。 |
| `PROFILE_REVISION_CHANGED` | 承認した後に、プロファイルを編集した。どの項目の編集でも、承認は引き継がない。 |
| `AUTH_SETUP_CHANGED` | 承認した後に、認証の設定が変わった。自動ログインなら、資格情報を登録・変更・削除したときも（下の注）。 |
| `TARGET_CONFIG_CHANGED` | 承認した後に、プロファイルが指す設定のファイル（ターゲットの設定）の内容が変わった。 |
| `CANDIDATE_CHANGED` | 最後の発見で、対象の候補の入力の規則（必須・制約・選択肢など）か分類が変わった。 |
| `CANDIDATE_MISSING` | 最後の発見で、対象の候補が見つからないか、その画面を読み直していない。更新（UPDATE）のシナリオは、path の ID の区切りを型にした識別で確かめます。 |
| `UPDATE_SPEC_MISSING` | 更新（UPDATE）のシナリオの版に、UPDATE の指定がない（UPDATE の指定を入れる前に保存した版）。 |
| `CANDIDATE_TEMPLATES_UNAVAILABLE` | 更新（UPDATE）のシナリオで、最後の発見の、型にした識別の digest の一覧をまだ集められない（管理データの版 9 より前の状態）。 |
| `INPUT_RULES_CHANGED` | 入力の規則の参照（集まり・版・digest）が変わった。 |
| `READ_CHECK_CHANGED` | 照らす READ の確かめの定義か、検証の指定の照合の READ の定義が、変わったか、削除されたか、見つからない。 |
| `EXPIRED` | 承認の期限を過ぎた（ちょうど期限の時刻を含む）。 |
| `REVOKED` | 最後の承認を撤回した。 |
| `NOT_APPROVED` | まだ承認していない。 |
| `PROFILE_RETIRED` | プロファイルを取り消した。取り消したプロファイルのシナリオは承認できない。 |
| `MODE_NOT_WRITE` | プロファイルの監査モードが、承認した書き込みのモード（`TEST_APPROVED_WRITE`）でなくなった。 |

- 期限切れは保存せず、読むたびに時計と承認の記録の期限から求めます。
- 自動ログインのプロファイルでは、承認は資格情報の値ではなく、資格情報の「事実」を縛ります: 資格情報のファイルの版と、資格情報の登録・変更・削除の記録（管理データの `credential_events`）の最後の記録です。資格情報を変えると版が進み、削除して別の値で登録し直すと（版は 1 に戻りますが）記録が増えるので、どちらも `AUTH_SETUP_CHANGED` になります。自動ログインの停止を解く操作は、資格情報の変更に数えません。手動のログインのプロファイルでは、資格情報を縛りません。
- 候補の判定は、承認の記録に固定した候補の 2 つの digest（識別と規則）と、最後の発見の索引の digest の比べで決めます。発見をやり直して候補が `CHANGED` になっても、2 つの digest が同じなら承認は有効のままです。
- どの理由でも、自動では引き継ぎません。内容と差分を確かめてから、もう一度承認します。

## 上限と期限

上限と期限は、名前つきの定数（`src/control/approval/scenario-contracts.ts`）と、その承認された値です。シナリオで既定より小さくはできますが、大きくはできません（大きくするのは、利用者の判断で既定値を変えるときだけです）。

| 定数 | 承認された値 | 意味 |
| --- | --- | --- |
| `APPROVAL_TTL_DAYS` | 30 日 | 承認の期限の日数の既定（と上限）。 |
| `DEFAULT_MAX_CREATES_PER_RUN` | 1 件 | 1 回の Run で書き込める件数の既定（と上限）。 |
| `DEFAULT_MAX_CUMULATIVE_CREATES` | 20 件 | シナリオの累積で書き込める件数の既定（と上限）。 |
| `WRITE_JOB_CONCURRENCY` | 1 | 書き込みの同時実行の数（シナリオとプロファイルをまたいで 1 つ）。 |
| `EXECUTION_GRANT_TTL_MS` | 5 分 | 実行の許可の期限（許可を出してから、書き込みのジョブを始めるまで）。 |

- **実行の許可**（ExecutionGrant）: 書き込みのジョブ（登録と更新）は、承認が今も有効であることを、1 つのジョブに結び付いた、期限つきで 1 回だけ使える許可で確かめてから始めます。許可は、承認の判定のやり直し、入力の規則の参照があること（なければ `NEEDS_RULE_INPUT`）、消費していない許可がないこと、上限の残り、書き込みの同時実行の枠を、1 つの手続きの中で確かめてから出します。偽造（ない ID、別のシナリオ・ジョブ・プロファイル・版への流用）、期限切れ、2 回目の使用は拒みます。許可は、画面「書き込みを始める」の確認のダイアログで「書き込みを始める」を押したときに出します。
- **件数の予約**（WriteReservation）: 許可を出すときに、同じ手続きの中で、1 回の Run と累積の上限の残りから件数を予約します。1 つの許可に予約は 1 件です。累積の件数には、予約中（`RESERVED`）・送った（`COMMITTED`）・送ったか分からない（`UNKNOWN`）を数え、送る前に返した予約（`RELEASED`）は数えません。期限を過ぎて、まだ無効にしていない許可の予約も数えません（次の許可を出すときに、無効にして返すため）。画面の「上限と使った件数」も、同じ数え方の部品で数えます。
- **書き込みの前の確かめ直し**（登録と更新のジョブが、送る直前に呼びます）: 許可が消費済みで、無効でなく、その予約が予約中（`RESERVED`）のままで、承認が今も有効で、承認の記録と版が許可を出したときと同じときだけ受けます。予約を送った・分からない・返した後（`GRANT_RESERVATION_SETTLED`）は受けません（1 つの許可で 2 件目を送らない）。時計が巻き戻って、承認より前の時刻で許可を出そうとしたとき（`GRANT_CLOCK_BEFORE_APPROVAL`）と、許可を出した時刻より前の時刻で使おうとしたとき（`GRANT_CLOCK_BEFORE_ISSUE`）も拒みます。
- 2 つの許可の発行が同時に来ても、予約の合計は上限を超えません。撤回と発行が同時に来ても、撤回の後に有効な許可は残りません。

## サイトへの読み込み

- シナリオの作成・変更・承認・撤回は、管理データの中だけで行います。**サイトへは何も送りません**（読み込みも書き込みもしません）。
- サイトへ届くのは、手順 2 の発見と、手順 3 の READ の確かめのジョブの要求だけです。間隔と上限は「[サイトへの読み込み](discovery-and-read-check.md#サイトへの読み込み)」と同じです（読み込みどうしの間隔は設定の `crawl.minNavigationIntervalMs` 以上、読み込み直しはしません）。

## 守りの範囲

- **シナリオの作成・変更・承認・撤回では、書き込みをしません。** 承認の部品（`src/control/approval/`）は、ブラウザやワーカーなど、要求を送る部品を使いません（自動の検査で確かめます）。サイトへ書き込むのは、承認の後に人が始める登録と更新のジョブ（ワーカー）だけです。
- **承認と撤回の記録は、追記だけです。** 承認と撤回の記録（`approval_receipts`）と、シナリオの版の写し（`scenario_revisions`）は、書き換えも削除もしません（`UPDATE`・`DELETE`・`REPLACE`・upsert の文を BeakSight のコードに書かないことを、自動の検査で確かめます）。管理データを開き直しても（画面のサーバの再起動）、承認は同じ内容のまま読め、有効なら使えます。
- **管理データのファイルを直接書き換えた場合の守りは限られます。** 追記だけの決まりは BeakSight のコードの決まりで、データベースの仕組み（trigger など）では止めていません。管理データのファイル（`local-data/`）を別の道具で書き換えると、記録を変えられます。承認の判定は、記録の承認の digest を今の内容から求め直して比べ、期限は記録の期限と「承認の日時 + 承認した版の日数」の早い方を使いますが、承認の日時と期限の日時を両方書き換えると、期限が延びることがあります。管理データのファイルは、このコンピュータの利用者だけが書けるようにしてください。
- **承認者は `LOCAL_OPERATOR` です。** 利用者の ID がない（このコンピュータの 1 人だけが使う）ので、固定の値を記録します。OS の利用者名などは記録しません。
- **承認と撤回は、確認のダイアログの後の画面の操作だけです。** どちらも同じ Origin からの POST だけを受け（CSRF の確かめ。「[管理画面の守り](local-ui.md#守り)」）、画面に出した版と承認の digest をサーバで照らします。
- **秘密を持ちません。** シナリオ、発見の根拠の写し、承認と撤回の記録、実行の許可と予約には、入力の値、CSRF のトークン、hidden の値、選択肢の label、資格情報、Cookie、localStorage の値を持ちません。
- **ページが書いた値は、発見の根拠の写しに残ります。** 送信先の path と query の名前、欄の名前、欄の制約（`pattern`・`min`・`max` などの属性の文字列）、選択肢の値は、ページが書いた値のまま管理データに写します（`discovery.json` と同じです。「[候補の見方](discovery-and-read-check.md#候補の見方)」）。ページがそこに個人情報や表の行の中身を書けば、管理データに残ります。シナリオの詳細の画面は、欄の名前・型・属性・制約だけを出し、選択肢の値は出しません。管理データ（`local-data/`）は、テスト環境のデータと同じに扱ってください。

### 確かめたこと（目印の検査）

テスト用の小さなサイトで、実行ごとのランダムな値を目印にし（セッションの Cookie、localStorage、資格情報、CSRF のトークン、hidden の値、入力の欄の今の値、選択肢の label、表の行の中身）、手動のログインと自動ログイン（本物の DPAPI。Windows）のそれぞれで、画面から発見 → READ の定義の作成 → シナリオの作成 → 承認 → 撤回を行って、目印が 1 つも出ないことを、UTF-8 と UTF-16LE の両方のバイトで確かめています。

- 探した場所: Run のディレクトリのすべてのファイル（`discovery.json`）、管理データのファイルと WAL と SHM と、すべての表のすべての行（シナリオ、版の写し（発見の根拠の写し）、承認と撤回の記録、実行の許可、予約を含む）、画面のサーバとワーカーの標準出力と標準エラー、ワーカーとの間の通信のすべて（両方の向き）、すべての画面の HTML（シナリオの一覧・作成・詳細・変更の画面を含む）と成果物の画面、Server Function の応答、子プロセスの起動の引数。
- 実行の許可と予約の表にも行がある状態で探すため、テストだけの操作として、入力の規則の参照を付け、承認の後に実行の許可を 1 つ出しています。画面からの撤回で、その許可が無効になり、予約が返り、次の許可の発行が拒まれることも確かめています。
- 同じ確かめで、サイトに届いた要求が、GET と HEAD のほかは発見のジョブのログインの送信 1 回だけであること、シナリオの作成・承認・撤回の間はサイトへの要求が 0 件であることを確かめています。
- 探す読み方が正しいことは、わざと目印を置いたファイル（UTF-16LE）が見つかることと、秘密でない値（シナリオの ID、承認の digest、実行の許可の ID）が管理データの表の行とシナリオの画面で見つかることで確かめています。

## 確かめていないこと・使えないこと

- **入力の規則の中身**（送る値の作り方と、データの例の表示）: 「[入力の規則とデータの生成](data-rules.md)」にあります（確かめていないことも、そちらに書きます）。送る欄すべての作り方が決まっていないシナリオには、実行の許可を出せません。
- **書き込みの実行**: 「[承認された登録の手順](approved-create.md)」と「[承認された更新の手順](approved-update.md)」にあります（送ったか分からない場合の扱い、照合の READ、撤回で動いている書き込みのジョブを止めること、確かめていないことを含みます）。
- **複数の段のシナリオ**（登録してから更新する、など）: 扱いません。
- **実際のテスト環境**: まだ接続して確かめていません（ユーザーの承認の後に、小さく確かめます）。
- CLI からのシナリオの操作。
