# 認証つきの監査の手順（ログインあり・読むだけ）

テスト環境の管理画面などを、人がログインした状態で、読み取りだけで監査する手順と、守りの範囲、使えないこと、確かめていないことです。
画面の操作の細部は「[管理画面](local-ui.md#認証つきの監査ログインあり読むだけ)」にあります。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 認証つきの監査は、管理画面からだけ動かせます（CLI からは動かせません）。テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません。

## 使ってよい場合

- **テスト環境だけに使います。本番には使いません。** 本番から隔離されていることを確かめたテスト環境だけを対象にします。ただし、この手順（読み取りだけ）は、隔離を観察するためにも使えます。隔離をまだ確かめていないテスト環境で、読み取りの段（認証つきの監査、自動ログイン、操作の候補の発見と READ の確かめ）だけを行うときは、未確認であることが分かる参照（例 `isolation-unverified-20261016`）を入れます（「[実テスト環境の手順](real-test-environment.md)」）。
- **テスト環境のデータを使います。** 監査の結果（見えている文、スクリーンショット）には、管理画面に表示されたデータがそのまま写ります。本番の個人データを、テスト環境に入れないでください。
- ログインの画面と、監査する管理画面が、同じ Origin（プロファイルの `approvedTestOrigins`）にあること。別の Origin のログインのサービス（IdP。シングルサインオン）へ画面が移るログインと、多要素認証（MFA）は使えません（「[使えないこと](#使えないこと)」）。画面の中のスクリプトが、別のホストの認証のサービスへ token を取りに行くログインは、「[スクリプトで送るログイン](#スクリプトで送るログイン)」の設定で扱います（手動のログインと自動ログイン）。
- ログインに使う利用者は、テスト環境の、監査に使ってよい利用者にします。手動のログイン（`MANUAL_SESSION`）では、BeakSight は資格情報を受け取らず、保存もしません（ログインは人が行います）。保存した資格情報で BeakSight がログインする自動ログイン（`AUTOMATED_LOGIN`。Windows だけ）は、「[自動ログインの手順](automated-login.md)」にあります。

## 手順

### 1. 設定のファイルを用意する

監査の対象の設定のファイル（「[設定のファイル](configuration.md)」）に、テスト環境の管理画面を書きます。

- `site.startUrl`: 監査を始める管理画面の URL（ログインの後の画面）。
- `site.allowedOrigins`: テスト環境の Origin。
- 速さの上限（`crawl.minNavigationIntervalMs`、`crawl.maxPages` など）は、公開の監査と同じく、このファイルの値のまま使います。ページの上限・時間の上限・読み込みの間隔の 3 つは、ファイルが `local/targets/` の中にあれば、プロファイルの詳細の「監査の負荷」で変えられます（間隔は今の下限より短くできません。「[管理画面](local-ui.md#サイトへの負荷の決まり)」「[サイトへの負荷](site-load.md)」）。
- `crawl.allowedQueryParameters` に、下の「[秘密を出さないこと](#秘密を出さないこと)」の一覧の名前（`token`、`session`、`code`、`state` など）を入れると、認証つきの監査は始まりません（ログインの前に（ログイン用のブラウザを開かずに）、設定の誤り（`CONFIG_ERROR`）で終わります）。Task 44 の P4-1 から、公開の監査も同じ理由で始まりません（成果物と保存の URL の、秘密に見える名前の値を伏せるため）。

### 2. テスト環境のプロファイルを作る

管理画面の「新しいプロファイル」で、次の値のプロファイルを作ります（項目の決まりは「[監査プロファイル](profiles.md)」）。

| 項目 | 値 |
| --- | --- |
| `environment` | `TEST`（画面の名前「テスト環境」） |
| `mode` | `TEST_AUTH_PASSIVE`（画面の名前「テスト環境の監査（ログインあり・読むだけ）」）。`TEST_APPROVED_WRITE`（承認した書き込み）のプロファイルでも、同じ手順で認証の設定を作れます。ただし、`TEST_APPROVED_WRITE` では監査は始められません。そのモードで使えるのは、操作の候補の発見、READ の確かめ、シナリオ、入力の規則、承認された登録と更新です（「[モードごとに使える操作](profiles.md#モードごとに使える操作)」）。 |
| `auth` | `MANUAL_SESSION`（画面の名前「手でログインする」） |
| `approvedTestOrigins` | テスト環境の Origin（1 件以上）。設定のファイルの `site.allowedOrigins` に含まれること。ログインの状態（Cookie、localStorage、IndexedDB）は、この Origin のもの（Cookie は、この Origin へ送るもの）を監査に渡します（「[監査の段](#監査の段)」）。 |
| `approvedServiceOrigins`（画面の名前「承認したサービスの Origin（1 行に 1 つ）」） | 任意。スクリプトで送るログインの、認証のサービスと API の Origin（「[スクリプトで送るログイン](#スクリプトで送るログイン)」、「[`approvedServiceOrigins`](profiles.md#approvedserviceorigins)」）。フォームの送信のログインでは空のままにします。 |
| `environmentEvidenceRef` | テスト環境が本番から隔離されていることを確かめた記録への参照（記録の ID など）。隔離が未確認のときは、未確認であることが分かる参照（例 `isolation-unverified-20261016`）。秘密を書きません。 |

### 3. 認証の設定を作る

プロファイルの詳細の「認証の設定を開く」から、認証の設定を作ります。パスワードや Cookie の値を入れる欄はありません。

| 項目 | 内容 |
| --- | --- |
| ログインの画面の URL | ログインのフォームがある画面。`approvedTestOrigins` の Origin にあること。秘密に見える名前の query（`password`、`token`、`session` など）を含む URL は保存しません。 |
| ログインの送り方 | 「フォームの送信」か「スクリプトの送信」。ログインのボタンを押したときの送り方です（確かめ方は「[ログインの方式の確かめ方](real-test-environment.md#ログインの方式の確かめ方)」）。「スクリプトの送信」の欄は「[スクリプトで送るログイン](#スクリプトで送るログイン)」にあります。自動ログインのプロファイルでも選べます（「[スクリプトで送るログインの自動ログイン](automated-login.md#スクリプトで送るログインの自動ログイン)」）。 |
| ログインの送信先 | 「フォームの送信」のとき。ログインのフォームの送信先（Origin と path）。ログインの間だけ、ここへの送信（POST）を許します。 |
| ログインが済んだと判定するパス | ログインの後に移る画面の path（前方一致）。任意で、その画面にある要素の CSS セレクタも指定します。ログインの画面にも当たるパスは保存しません。 |
| セッションが切れたと判定するパス | 空なら、ログインの画面の path。監査の途中で、この path の画面に移ったら、セッションが切れたと判断します。 |
| 読まないパス | 監査で読まない path（前方一致）。**ログアウトの画面を必ず入れます。** ほかにも、開くだけで状態が変わる画面（承認、送信、取り消しなど）があれば入れます。 |
| 読む範囲のパス | 監査で読む path（前方一致）。空なら絞りません。管理画面の範囲に絞るときに使います。 |
| ログインの送信の回数の上限 | 1〜3 回。総当たりをしないための上限です。 |

- 認証の設定は、保存したときのプロファイルの改訂に結びつきます。プロファイルを変更したら、認証の設定を見直して保存し直します（それまでは監査を始めません）。
- 認証の設定は、「フォームの送信」でも「スクリプトの送信」でも版 3 の形で保存します。前の版の形（版 1・版 2）の設定は読みません。管理データにあれば、管理データの誤り（`DATABASE_INTEGRITY_FAILED`）で止まります（前の版の形の読み替えは、利用者のデータに残っていないので捨てました）。

### 4. 監査を始める

左のメニューの「サイトとプロファイル」の一覧で、そのプロファイルの行の「最後の Run」の列にある「監査を始める」を押します（プロファイルの詳細の画面の欄「監査を始める」からも始められます）。このボタンは、状態が「有効」で、今実行できる監査モードと認証の方式の組み合わせ（「公開の監査（読むだけ）」と「ログインしない」、または「テスト環境の監査（ログインあり・読むだけ）」と「手でログインする」か「自動でログインする」）のプロファイルにだけ出ます。開始の画面が開きます。ログインの案内、ログインの画面の URL、読む範囲を確かめて、開始します。

- 「前回の続きから再開する」（既定）か「新しく始める」を選びます（「[監査の実行](local-ui.md#始める)」）。
- 認証の設定がない・古い・誤りがあるときは、理由と認証の設定の画面へのリンクを表示し、開始のボタンを出しません。

### 5. 開いたブラウザでログインする

開始すると、BeakSight がブラウザ（Chromium）を開き、ログインの画面を表示します。ジョブの画面の「ログイン」は「ログイン待ち」になり、欄「手動のログイン」に「ログインを終えた」のボタンと説明が出ます。

- 開いたブラウザで、ログインの画面からログインします。**手動のログインの間は、ページが出す読み取りでない送信（ログインの送信、外部の認証のサービスへの token の送信、ページの手続きの呼び出し、事前確認など）を止めずに通します。** 普通のブラウザで人が操作するのと同じで、その送信はサイトへ届きます。BeakSight は、通した送信の形（Origin・パス・method・種類・query の名前と数）だけを記録し、値（本文、query の値、ヘッダの値、Cookie、token）は記録しません。認証の設定が「フォームの送信」のままでも、手動のログインは止まりません。
- ログインが済んだら、ジョブの画面の「ログインを終えた」を押します。BeakSight がログインの状態を取り出してブラウザを閉じ、監査を始めます。ボタンの欄は消え、「ログイン」は「ログイン済み」になります。ログインが済んだと判定するパスの画面に移る（今の成功の条件に当たる）と、押さなくても先へ進みます。
- 「ログインを終えた」を受け付けるのは、ジョブが「ログイン待ち」の間の 1 回だけです。受け付けられないときは、欄に理由を出します（ジョブが見つからない、ジョブがもう動いていない、ログインを待っていない（ログインの前か後、または止める要求の後）、もう知らせてある）。
- 手動のログインの間に通すのは、読み取りでない送信だけです。**読み取り（GET と HEAD）の決まりは、手動のログインの間も変わりません。許可 Origin の外への読み取りは止めます**（承認したサービスの Origin への読み取りは、下の「[ログインの段で通すもの・止めるもの](#ログインの段で通すもの止めるもの)」のとおりです）。人が入れた値を、ページのスクリプトが別の Origin への読み取り（URL の query など）に載せて運ぶことを防ぐためです。
- ダウンロード、外部のアプリの起動（`tel:` など）、WebSocket、許可 Origin の外への画面の移動は、手動のログインの間も今までどおり止めます。
- ログインのほかの操作はしないでください（別のタブを開く、アドレスバーに URL を入れる、ほかの画面へ移る、など。「[確かめていないこと](#確かめていないこと)」）。
- 10 分の中にログインが済まないと「ログインの時間切れ」で、監査を始めずに終わります。ログインのブラウザを閉じると「ログインを続けられない」で終わります。
- ログインの後に、許可した Origin の Cookie も localStorage もないときは「扱えないログインの形」で終わります（別の Origin のログインや、sessionStorage に頼るログイン）。
- **手動のログインから設定を自動で登録します**: 手動のログインが成功し（成功の条件に当たったか、「ログインを終えた」を押したとき）、その間に送信を通したジョブは、ジョブが終わった後に（終わり方によりません）、BeakSight が、通した送信の記録とログインの後の状態の鍵の名前から、Guard を通るための設定（認証の設定の「スクリプトの送信」の token の送信先・ログインに伴う送信・成功のローカル ストレージの鍵と、プロファイルの承認したサービスの Origin）を組み立て、利用者の操作なしで保存します。値（パスワード、token、秘密に見える名前の query の値）は保存しません。自動ログインは、この設定で、登録した送信だけを通します（下の「[ログインの段で通すもの・止めるもの](#ログインの段で通すもの止めるもの)」）。自動で登録するものの決まりは次のとおりです。
  - token の送信先は、1 つに決まるときだけ登録します（今の設定の送信先と、通した token の送信の送り先が 2 つ以上なら、登録しません）。
  - ログインに伴う送信は、次のすべてを満たす送信だけです: token の送信より前に通した。種類が fetch か xhr。token の送信先と同じ Origin。符号化していない手続きの呼び出しの path（`/rpc/`）で、名前に書き込みの語を含まない。読まないパスと、危険な語を含むパス（ログアウトなど）でない。
  - 承認したサービスの Origin に足すのは、token の送信先の Origin だけです。
  - ほかの通した送信（第三者の解析の送信、token の後の送信など）は登録しません。通した送信の表の「登録する」の案として出るだけです。
- 登録の結果は、ジョブの画面の欄「手動のログインから登録した設定」に出ます（終わったジョブの画面は、結果が書かれるまで、短い間だけ読み直しを続けます）。登録したときは「このジョブの手動のログインから、設定を登録しました。」と、保存したプロファイルの改訂と、足した承認したサービスの Origin を出します。登録しなかったときは、理由と次にすることを出します。

  | 理由 | 意味 |
  | --- | --- |
  | 通した送信がない | 登録するものがありません。 |
  | token の送信が見つからない | 通した送信に、token の送信の形（`grant_type` を持つ送信）がありません。 |
  | 成功の鍵の案がない | ログインの後のローカル ストレージに、新しい鍵が見つかりません。 |
  | 足すものがない | 通した送信は、今の設定にすべて入っています。 |
  | プロファイルか認証の設定が変わった | ジョブを始めた後に、プロファイルか認証の設定が変わったので、利用者の変更を上書きしません。 |
  | 保存の確かめを通らなかった | 組み立てた設定を、保存の確かめが受け付けません。 |
  | token の送信先が 1 つに決まらない | token の送信先が 2 つ以上あります。通した送信の表の token の行から「登録する」で、正しい送信先を選んで登録します。 |

- 登録した中身は、ジョブの画面とプロファイルの画面の欄「手動のログインから登録した設定」に出ます。違っていれば、欄の「認証の設定の画面で見直す」から直します。登録しなかったときは、通した送信の表の「登録する」（「[観察した要求の登録](#観察した要求の登録)」）から入れられます。
- 設定を保存すると、プロファイルの改訂が進みます。承認済みのシナリオや、発見・READ の確かめの結果は、やり直しが要ることがあります。

### 6. 監査

- ログインの状態は、監査の process のメモリの中だけで使います。新しい監査用のブラウザ（headless）に渡し、公開の監査と同じく、読み取り（GET と HEAD）だけで監査します。
- 読まないパスと、既定で読まない語を含む URL は、巡回の候補から外し、画面の移動（ページの中のリンクや `location.href` の移動、iframe の画面）でも読みません。
- ページが自分で読み込む文書でない GET・HEAD（スクリプト、スタイルシート、画像、フォント、動画、fetch・XHR のデータなど）は、読まないパスや既定で読まない語に当たっても、読む範囲の外でも、止めずに通します（2026-10-23 から。ユーザーの判断）。止めると、画面の部品が動かず、偽の指摘（読み込みの失敗など）が出るためです。送信の扱い（`READ_ONLY`・`PASS_EXCEPT_DELETE`）と、公開・認証つきによらず同じです。Interaction の読み込み、ログインの段・書き込みの段では、今どおり止めます。
- ページ自身のデータの GET がログアウトなどでセッションを切った場合は、セッションの切れとして記録して止まります（下の「セッションが切れたら」）。
- 進み具合と結果の見方は、公開の監査と同じです（「[進み具合と結果](local-ui.md#進み具合と結果)」）。

### 7. セッションが切れたら

監査の途中で、セッションが切れたと判定するパスの画面に移ったら、その Run を一部未完了で止めます（終わり方は「認証のセッションが切れて止まった」）。そのページは、ログインの画面を監査しないように捨てます。

移ったかどうかは、画面の最後の URL か、BeakSight が止めた画面の移動の先（ログインの画面が読む範囲の外のとき）が、セッションが切れたと判定するパスで始まるかで決めます。画面を読み込んだ直後だけでなく、次の時機にも確かめます（2026-10-25 から）。読み込みの後に、画面のスクリプトがログインの画面へ移すサイト（ログインの状態を後から確かめる SPA など）でも、止まるためです。

| 時機 | 監査の Run | 発見・READ の確かめ |
| --- | --- | --- |
| 読み込みの直後 | デスクトップ・モバイルの読み込みと、幅の走査の各幅の読み込み | 各画面の読み込み |
| 落ち着きを待った後 | 同じ | 各画面（発見は、リンクを拾う前と、送らずに確かめる押下の前） |
| 次の読み込みの前 | 幅の走査の前と各幅の前、モバイルの前（それまでに読み込んだ画面を確かめ直す） | なし（1 回に 1 画面だけを読むため。前の画面の終わりの確かめが同じ役です） |
| ページの終わり | モバイルを閉じる前と後（成果物にそのページを書く前） | 各画面の読み取りの後と、閉じた後 |

どの時機で見つけても、扱いは同じです（そのページを捨てて止め、次のページを読みません）。確かめは、ブラウザの中の記録を読むだけで、サイトへの要求を増やしません。セッションが切れたと判定するパスで始まらない移動では止めません。

- ジョブの画面に「ログインの状態が切れた」と、止まったページの URL（下の「[秘密を出さないこと](#秘密を出さないこと)」のとおり、秘密に見える query の値は伏せ字）と、認証の設定の画面へのリンクを表示します。
- 開くだけでログアウトする画面など、セッションを壊すページで止まった場合は、そのページを認証の設定の「読まないパス」に足すと、次から読みません。

#### セッションの切れの記録

セッションが切れたと判定した読み込み 1 回について、原因を後から調べるための記録（セッションの切れの証拠）を残します。記録はパスと query の名前と数だけで、token、Cookie の値、query の値、本文、ヘッダの値は残しません。

| 項目 | 中身 |
| --- | --- |
| 判定した段階 | 監査の Run は `desktop:passive` などの場所（読み込みの直後）。後の時機で見つけたときは、末尾に時機を足します（`desktop:passive:settled` は落ち着きを待った後、`desktop:stress-layout:before-next-load` は次の読み込みの前、`mobile:passive:page-end` はページの終わり）。発見と READ の確かめは、ログインの状態の鍵が消えたときだけ `session-key`（パスで判定したときは、時機によらず空） |
| 頼んだページ・行き着いた先 | パスと query の名前（例 `/admin/members?page`）。値に見える区切りは `[REDACTED]` に伏せます。行き着いた先は、画面の最後の URL か、BeakSight が止めた移動の先（ログインの画面が読む範囲の外のとき）のどちらで見たかも残します |
| 読み込みの経路 | 画面の文書の要求の順（サーバのリダイレクトの各段と、画面のスクリプトによる移動）。Origin は「許可した Origin」「承認したサービスの Origin」「そのほか」の区別だけを残します。10 段まで |
| 止めた要求 | その読み込みの間に Guard が止めた要求の、メソッド・Origin の区別・パス・理由・回数。8 行まで（超えた分は数だけ） |
| ログインの状態の名前の違い | 監査用のブラウザに入れた状態と、読み込みの後に読んだ状態の、許可した Origin と承認したサービスの Origin の、ローカル ストレージの鍵と Cookie の名前と IndexedDB のデータベースの名前の違い（消えた名前・増えた名前の数）。名前は、ログインの段の観察と同じく、先頭と末尾の一般の語（`token`・`auth`・`session` など）だけを残し、間の部分は残しません |

記録は次の場所に残ります。読み込みの後の状態の読み取りは、ブラウザの中の状態を読むだけで、サイトへの要求を増やしません。

- 監査の Run: `run.json` の `authentication.sessionLoss`（その実行が切れで止まったときの 1 件。再開して最後まで終えた実行の `run.json` には残りません）。
- 発見と READ の確かめ: `discovery.json`・`read-evidence.json` の `sessionLoss`。
- ジョブの画面: 「止まったページの URL」の下の「セッションが切れたと判定した読み込みの記録」。

### 8. 再開する

同じプロファイルで「前回の続きから再開する」を選んで開始すると、**もう一度ログインしてから**、止まったページから続けます（ログインの状態は保存しないため）。止まったページは、再開のときに待ち行列に戻ります。

## スクリプトで送るログイン

ログインのボタンを押すと、画面の中のスクリプト（fetch か XHR）が、別のホストの認証のサービスへ token を取りに行き、ログインの状態をローカル ストレージに置く形のログインです。手動のログイン（`MANUAL_SESSION`）と、自動ログイン（`AUTOMATED_LOGIN`。「[スクリプトで送るログインの自動ログイン](automated-login.md#スクリプトで送るログインの自動ログイン)」）で使えます。

> テスト用の小さなサイト（画面のスクリプトが別のホストの認証のサービスへ token を取りに行く形）で、本物のワーカーの手動のログインから監査の終わりまでを確かめています。実際のテスト環境では、まだ確かめていません。

### 設定

プロファイル:

- 「承認したサービスの Origin（1 行に 1 つ）」に、認証のサービスと API の Origin を書きます（4 つまで）。監査の対象の Origin（設定のファイルの `site.allowedOrigins`）は書きません（「[`approvedServiceOrigins`](profiles.md#approvedserviceorigins)」）。

認証の設定（「ログインの送り方」で「スクリプトの送信」を選ぶと、枠「スクリプトで送るログイン」が出ます）:

| 欄 | 内容 |
| --- | --- |
| token の送信先の Origin | プロファイルの「承認したサービスの Origin」から選びます。 |
| token の送信先のパス | `/` で始まるパス。query は、下の「必須の query」に書きます。 |
| 送信の method | 「POST だけ」（変えられません）。 |
| 必須の query | token の送信の query の、名前と値の組（4 つまで。「query の組を足す」で足します）。要求の query が、この組とちょうど同じときだけ通します。比べるのは、名前と値を decode した後です。順は問いません。組が足りない、余分な組がある、同じ名前の組が重なる、大文字と小文字が違う、値が違うときは通しません。空の組（`&` だけ）は無視します。URL の `#` の後（fragment）は、ブラウザがサーバに送りません。秘密に見える名前は書けません。値に見える文字列（長いランダムな値の形）やメールアドレスの形の値も書けません（`AUTH_SETUP_SECRET_LIKE_VALUE`）。 |
| ログインに伴う送信 | ログインの画面のスクリプトが、token のほかに送る `POST`（8 つまで。「送信を足す」で足します）。行ごとに「N 行目 Origin」（承認したテスト環境の Origin か、承認したサービスの Origin）、「N 行目 パス」（完全な一致）、「N 行目 1 回のログインの回数」（1〜3）を書きます。既定は空です。**まず空で試し、止めた記録を見て、要るものだけを登録します。** 登録するかは、その送信が読み取りか、ログインに要る処理かを、利用者が判断します（BeakSight は、この送信の query と本文を照らしません）。 |
| 成功のローカル ストレージの鍵 | 「鍵の Origin」（承認したテスト環境の Origin から選びます）、「鍵の名前の接頭辞」、「鍵の名前の接尾辞」（例: `-auth-token`）。ログインの後に、その Origin のローカル ストレージに、接頭辞で始まり接尾辞で終わる名前の鍵があれば、ログインが済んだとみなします（今の成功の条件に足します。値は読みません）。接頭辞と接尾辞の両方を空にはできません。 |
| ログインの送信の回数の上限 | 1〜3 回。token の送信の回数の上限になります。 |

- 「スクリプトの送信」では、「ログインの送信先」（フォームの送信先）は空でかまいません。
- **手動のログインのプロファイルでは、token の送信先と成功のローカル ストレージの鍵も、空のまま保存できます**（入口の確かめの案のまま。「ログインが済んだと判定するパス」は入れます）。この設定で監査などを始め、BeakSight が開くブラウザで一度手動でログインすると、ログインの成功の後に、通した送信と観察から送信先と鍵を自動で登録します（「[5. 開いたブラウザでログインする](#5-開いたブラウザでログインする)」の「手動のログインから設定を自動で登録します」。手動のログインの段は、今どおり送信を止めずに通して形だけを記録します）。鍵がない間は、成功の条件の画面（と要素）か「ログインを終えた」でログインを終えます。入口の確かめの結果と認証の設定の画面にも、この旨を出します。プロファイルの承認したサービスの Origin も、先に足さなくてかまいません（自動の登録が token の送信先の Origin を足します）。そのため、手動のログインのプロファイルの認証の設定の画面は、承認したサービスの Origin がなくても「先にプロファイルの画面で足してください」の誤りの文を出さず、入口の確かめの案の文も「空のまま保存してください」にします（Task 44 の T44h の判断 (2)。先にプロファイルを直すと改訂が進み、認証の設定が古くなって手順が増えるためです）。**自動ログインのプロファイルでは、今どおり両方が要ります**（`AUTH_SETUP_SCRIPT_LOGIN_REQUIRED`）。承認したサービスの Origin がなければ、誤りの文を出します。
- 保存できない値は、項目ごとに理由を出します。例: サービスの Origin がプロファイルにない（`AUTH_SETUP_SERVICE_ORIGIN_NOT_APPROVED`）、必須の query が正しくない（`AUTH_SETUP_REQUIRED_QUERY_INVALID`）、同じ送信先の重なり（`AUTH_SETUP_LOGIN_SIDE_REQUEST_DUPLICATED`）、鍵の形が正しくない（`AUTH_SETUP_STORAGE_KEY_INVALID`）、必須の query の値が値に見える（`AUTH_SETUP_SECRET_LIKE_VALUE`）。
- 前に保存した設定でも、今の検証に当たるもの（必須の query の値が値に見える、など）は、ジョブの開始の前の確かめで拒まれます。設定を開いて直してから始めます。

### ログインの段で通すもの・止めるもの

「スクリプトの送信」の設定では、**自動ログインの**ログインの段の Guard が、次のとおりに判定します（自動ログインは人が見ていないので、登録した送信だけを通します）。手動のログインの段では、ページの読み取りでない送信を止めずに通し、形だけを記録します（読み取りの決まりは変わらず、許可 Origin の外への読み取りは止めます。上の「[5. 開いたブラウザでログインする](#5-開いたブラウザでログインする)」）。ジョブの画面のパネルには、止めた送信と、手動のログインの間に通した送信を分けて出し、通した送信の行からも「登録する」（「[観察した要求の登録](#観察した要求の登録)」）を使えます。

| 要求 | 扱い |
| --- | --- |
| CORS の事前確認（`OPTIONS`） | Guard が代わりに答え、サーバには送りません（今までどおり）。 |
| 承認したサービスの Origin への読み取り（`GET`・`HEAD`。ページの移動でないもの） | 通します。そのサービスの Origin を巡回することはありません。 |
| token の送信 | `POST` で、種類が fetch か XHR で、Origin・パス・必須の query が設定とちょうど同じで、回数の上限の中のときだけ通します。 |
| 登録したログインに伴う送信 | `POST` で、種類が fetch か XHR で、Origin とパスが登録した行とちょうど同じで、その行の回数の中のときだけ通します。 |
| token の送信先への、種類が document（フォームの送信）・beacon（`sendBeacon`）などの `POST` | 送信先が同じでも止めます。 |
| query が違う token の送信、回数を超えた送信、登録していない `POST`、ほかの読み取りでない要求 | 止めて、ログインの段の記録に数えます。ジョブの画面のパネル「ログインの段で止めた送信」に、Origin・パス・種類・理由・回数を出します（下の「[ログインの結果と、止めた送信の見方](#ログインの結果と止めた送信の見方)」）。 |
| 許可 Origin と承認したサービスの Origin の外への要求 | 今までどおり、すべて止めます。 |

- token の送信を通した後は、送信の窓を開きます。窓の中で通すのは、回数の中の token の送信、承認したサービスの Origin への読み取り、登録したログインに伴う送信、許可 Origin の中の読み取りです。BeakSight がログインの成功を確かめた時点で、窓を閉じます。
- 手動のログインの段では、「スクリプトの送信」の設定に token の送信先がまだないとき（入口の確かめの案のまま保存した手動のログインのプロファイル）も、プロファイルの承認したサービスの Origin への読み取り（`GET`・`HEAD`。ページの移動でないもの）を通します（Task 44 のレビューの M-1）。ログインの後の画面が、サービスの API から一覧などを読めるようにするためです。読み取りでない送信は、今までどおり止めずに通して形を記録します。自動ログインの段は、token の送信先がない設定では始めません（今までどおり）。

### ログインの結果と、止めた送信の見方

- **成功**: 次のすべてを満たすことです。BeakSight が token の送信を 1 回以上通したこと。今の成功の条件（ログインが済んだと判定するパスと、任意のセレクタ）に当たること。さらに、「成功のローカル ストレージの鍵」の Origin のローカル ストレージに、接頭辞で始まり接尾辞で終わる名前の鍵があることです。BeakSight は、ログインのブラウザの状態を BeakSight の側で読み、鍵の名前だけを見ます（値は読みません。ページの中では読みません）。接頭辞と接尾辞が重なる名前（名前の長さが、接頭辞と接尾辞の長さの合計より短いもの）は当たりません。
- **token の送信の回数の上限を超えた**: 上限を超えて token の送信をしようとして止めたら、「ログインの回数の上限」（`LOGIN_ATTEMPTS_EXCEEDED`）で、監査を始めずに終わります。種類（document など）や query が違うために止めた送信は、試みに数えません。
- **登録していないログインに伴う送信**: 画面のスクリプトが、登録していない `POST`（ログインの前の手続きの呼び出しなど）を送り、それを止めたために画面がログインを進めないときは、ログインが済みません。待てば「ログインの時間切れ」（`LOGIN_TIMEOUT`）で終わりますが、時間切れを待つ必要はありません。ジョブの画面の「監査を止める」で止めても、下のパネルの表と数は残ります（ジョブは止めた状態で終わり、最後のログインの状態は「ログインを待っている」のままです）。どの送信を止めたかは、そのパネルの表で分かります。
- **ポップアップからの送信**: ログインの段で、ページが空のポップアップ（`about:blank`）から送信すると、その送信はサーバに届かないのに、token の送信の回数を使うことがあります。そのため、ログインが回数の上限で終わることがあります（届かない側なので、安全は保たれます）。
- **パネル「ログインの段で止めた送信」**（ジョブの詳細の画面）:
  - 「数のまとめ」: 「通した token の送信」「通したログインに伴う送信」「承認したサービスの Origin への読み取り」「止めた読み取りでない送信」「資格情報を含む要求を止めた数」の 5 つ（フォームの送信のログインでは「止めた読み取りでない送信」だけ）。
  - 「資格情報を含む要求を止めた数」は、自動ログインの資格情報の持ち出しの守りが止めた要求の数です（「[資格情報の持ち出しの守り](automated-login.md#資格情報の持ち出しの守り)」。手動のログインでは 0 です）。読み取りの要求も含むので、「止めた読み取りでない送信」の数には含めません。表の行にも出ません。
  - 表: 止めた送信を、Origin・パス・種類・理由・回数で出します（同じ Origin・パス・種類・理由は 1 行にまとめます）。8 行までで、超えた分は「ほかに N 件の送信を止めました」と数だけを出します。
  - パスは、query・本文・値を持ちません。値に見える区切り（長い base64url、標準の base64（`+`・`/`・`=` を使う形）、長い 16 進、JWT の形）と、メールアドレスの形の区切りは `[REDACTED]` に伏せ、「（値に見える区切りを伏せました）」と添えます。
  - 伏せられないもの（限界）: 短い値（23 字以下の base64url、31 字以下の 16 進）、数字を含まない英大文字と英小文字だけの長い値、JWT の形でない `.` 区切りの値、`~` で始まる値。パスに値が入る画面では、表のパスに値が見えることがあります。
  - 種類は、ブラウザが報告した値です。ブラウザは、画面の `fetch()` を `xhr` と報告することがあります。
  - 止めた送信があるときは、「認証の設定を開く」のボタンを出します。ログインに要る送信なら、「ログインに伴う送信」に登録します（読み取りか、ログインに要る処理かは、利用者が判断します）。
  - この一覧は、管理データとジョブの画面だけにあり、Run の成果物（`run.json` やバンドルなど）には入りません。
- ログインの状態は、承認したテスト環境の Origin のローカル ストレージと Cookie を、監査の段に渡します。DEF-139 から、承認したサービスの Origin へ送る Cookie と、承認したサービスの Origin の IndexedDB も渡します（ローカル ストレージは、今までどおり承認したテスト環境の Origin のものだけ。「[監査の段](#監査の段)」）。
- ログインの後の監査の段の扱いは、次の節「[スクリプトで送るログインの後の監査](#スクリプトで送るログインの後の監査)」にあります。

## スクリプトで送るログインの後の監査

「スクリプトで送るログイン」の設定のプロファイルでは、ログインの後の監査の段でも、承認したサービスの Origin（認証のサービスと API）を扱います。フォームの送信のログインの監査と、公開の監査の振る舞いは変わりません。

> テスト用の小さなサイト（画面のスクリプトが別のホストの API を読む形）で、本物のワーカーで監査を最後まで（`COMPLETE`）確かめています。上限に届いたとき、再開、ログインの状態が消えたとき、401 の数は、監査の部品の層のテストで確かめています（本物のワーカーでは確かめていません）。実際のテスト環境では、まだ確かめていません。

### 設定

認証の設定の枠「スクリプトで送るログイン」の中に、次の欄があります。

| 欄 | 内容 |
| --- | --- |
| 監査で通す読み取りの手続きの呼び出し | 監査の段で、ページのスクリプトが送る `POST` のうち、ここに登録した送信先へのものだけを通します（8 つまで。「呼び出しを足す」で足し、「N 行目 この呼び出しを消す」で消します）。行ごとに「N 行目 呼び出しの Origin」（承認したサービスの Origin か、承認したテスト環境の Origin）、「N 行目 呼び出しのパス」（完全な一致）、「N 行目 1 回の読み込みの回数」（1〜10）を書きます。既定は空です。 |
| サービスの Origin への要求の上限 | 「1 分あたりの上限」（1〜600）と「1 回の Run あたりの上限」（1〜10,000）。空なら、1 分あたり 600 件と、1 回の Run の全体で「10,000 件か、ページの上限 × 200 件の大きいほう」を使います（2026-10-21 から。例: ページの上限 140 なら 28,000 件）。「1 分あたりの上限」に届くと、次の読み込みの前に待ってから続けます（止めません）。「1 回の Run あたりの上限」は、再開をまたいだ Run の全体の上限で、届くと止めます。小さくはできますが、大きくはできません。前の範囲（1〜120、1〜600）で保存した値は、そのまま使えます。 |

- **登録するのは、データを読むだけの手続きの呼び出しだけです。** 読むだけかどうかは、利用者が判断します（BeakSight は、その送信の query と本文を照らしません）。**まず空で試し、監査の成果物の `page.json` の安全の記録（止めた要求 `blockedRequests`）を見て、要るものだけを登録します。**
- この 2 つの欄は、「スクリプトの送信」のときだけ持てます。同じ送信先を 2 回書けません（`AUTH_SETUP_AUDIT_READ_REQUEST_DUPLICATED`）。欄を使わずに保存した設定は、前と同じ文書のままです（承認は無効になりません）。

### 監査の段で通すもの・止めるもの

| 要求 | 扱い |
| --- | --- |
| 承認したサービスの Origin への読み取り（`GET`・`HEAD`） | デスクトップとモバイルの読み込みで通し、数えます。送信の扱いが `PASS_EXCEPT_DELETE` のときは、幅の走査の読み込みでも同じに通し、同じ上限で数えます（Task 44 の P1-1）。送信の扱いが `READ_ONLY` の幅の走査と、Interaction の読み込み（送信の扱いによらない）では、承認したサービスの Origin へは何も送りません（iframe の文書を含みます）。その読み取りは理由 `SERVICE_ORIGIN_REVISIT` で止め、`page.json` の安全の記録（`blockedRequests`）に残します。そのため、`READ_ONLY` の幅の走査では API のデータが空のまま表示されることがあります（限界）。 |
| 登録した読み取りの手続きの呼び出し | `POST` で、種類が fetch か XHR で、Origin とパスが登録した行とちょうど同じで、その読み込みでの回数の中のときだけ通します。読まないパスと、既定で読まない語に当たる呼び出しは止めます（読む範囲は当てません）。`READ_ONLY` の幅の走査と、Interaction の読み込みでは通しません（`PASS_EXCEPT_DELETE` の幅の走査では、デスクトップとモバイルと同じ回数で通します）。 |
| token の送信先への、必須の query と違う `POST`（token の更新など） | 止めます。数は `run.json` の `authentication.tokenRefreshBlocked` に残ります。 |
| ほかの読み取りでない要求（サーバの関数の呼び出し、計測の送信など） | 今どおり止めて、Safety Ledger に記録します（`page.json` の `blockedRequests`）。 |
| WebSocket | 今どおり止めます。 |
| ページが出す文書でない `GET`・`HEAD`（スクリプト・スタイルシート・画像・フォント・動画（音声）・fetch・XHR など） | 読む範囲の外でも、読まないパスや既定で読まない語に当たっても、読みます（2026-10-23 の BN-0 から。SPA の画面が、範囲の外の資源とデータを読み込むため）。Origin の決まり、承認したサービスの Origin への要求の上限、1 画面の要求の上限は、今どおりです。 |
| 許可 Origin の、読む範囲の外への画面の移動（main frame と iframe の文書） | 今どおり、読む範囲で絞ります。 |
| 読まないパスと、既定で読まない語を含む URL への画面の移動（巡回、ページの中の移動、iframe の文書） | 今どおり読みません。 |
| Interaction の読み込みの、読む範囲の外・読まないパス・既定で読まない語の要求 | 今どおり、ページが出す文書でない要求も含めて読みません。 |

- 出口の中継は、要求の種類が分からないので、読まないパス・読む範囲・危険な語を、ページの文書でない読み取りにも当てて判定します（BN-0 の前と同じ）。そのうえで、ページが出す文書でない `GET`・`HEAD` のうち、その環境の Guard が通した（中継に知らせた）要求だけを、除外の URL でも通します。Guard を通らずに中継に来た除外の URL への要求（先読みなど）は、中継が拒んで `GUARD_BYPASS_EGRESS` で記録します（2 段目の守り。https の要求は中身が見えないので、宛先の host とポートだけで判定します）。
- 設定の検証は、「監査で通す読み取りの手続きの呼び出し」のパスが、読まないパスか既定で読まない語に当たるものを、保存しません。比べる形は Guard と同じです（`%XX` を戻した形、連続した `/` をまとめた形、各 segment の `;` から後を外した形、`.` と `..` を解決した形と、それらの大文字・小文字を畳んだ形）。たとえば `/%6Cogout` は `/logout` として当たります。形を作れないパスも保存しません。
- 出口の中継も、幅の走査の Context では、承認したサービスの Origin への要求を通しません。Interaction の Context の中継は、この方針を持ちません（認証つきの監査は Interaction を行わないので、限界として書いておきます）。
- 監査の段の決まりを持つ Context で、上限を数える部品が渡されていないときは、BeakSight はその Context を作りません（安全の側に倒します）。
- 限界（ページが出す読み取りの扱い。BN-0 から）: ページが自分で出す `GET` は、読まないパスや既定で読まない語の URL でも届きます（例: `GET /api/logout` を fetch で呼ぶ画面）。`GET` でサイトの状態を変えるサイトでは、その変化が起きえます（人がその画面を開いたときと同じです）。画面の移動（main frame と iframe の文書）は、今どおり止まります。

### 要求の上限

- 承認したサービスの Origin への要求（読み取りと、通した登録の呼び出し）は、送る前に数えます。どの読み込みの要求も数えます。上限は、1 分あたり（直近の 60 秒。実行（起動）ごとの窓。既定と最大は 600 件）と、再開をまたいだ Run の全体（設定に書くときの最大は 10,000 件。空のときの既定は、10,000 件か、ページの上限 × 200 件の大きいほう）です。1 ページあたり 200 件は、Desktop と Mobile の最初の読み込みと幅の走査の読み込みで、1 ページ約 175 件を送った実テスト環境の数に、余裕を足した量です。
- **1 分あたりの上限では、要求を止めません。** ページの読み込みの途中で要求を断ると、不自然な遮断になり、サイトに検知されるおそれがあるためです。代わりに、次の読み込み（次のページ、デスクトップの後のモバイル、幅の走査など）を始める前に、直近の 60 秒に数えた要求が上限以上なら、上限を下回るまで待ちます（1 回の待ちは最大 60 秒。ページの読み込みの間隔の待ちと重なり、長い方を待ちます）。1 回の読み込みで、ページが上限を超える数の要求を出すことはあります（ページの自然な送信なので止めません）。
- 待つ間は、ジョブの画面の進みの欄に「サービスへの要求が 1 分あたりの上限に届いたため、次の読み込みの前に〜待ちます（N 回目。合計〜）」の知らせが出ます。待った回数と時間の合計は、`run.json` の `authentication.serviceRequestPacingWaits`・`authentication.serviceRequestPacingWaitMs` に、再開をまたいで積み上げて残ります。
- **Run の全体の上限に届くと、止めます。** それを超える要求は止めて、理由 `SERVICE_REQUEST_LIMIT_REACHED` で記録します。上限で止めた要求が 1 つでもあれば、Run は一部未完了（`PARTIAL`）で、未完了の理由に `SERVICE_REQUEST_LIMIT_REACHED` が残ります。
- Run の全体の上限に届くと、次のページを始めません。残りのページは、理由 `SERVICE_REQUEST_LIMIT_REACHED` のスキップになり、終わり方は「API の要求の上限で停止」（`STOPPED_BY_SERVICE_REQUEST_LIMIT`）です。残りのページがないときの終わり方は、`COMPLETED` のままです。
- 「前回の続きから再開する」で始めると、スキップしたページを待ち行列に戻し、続きを監査します。1 分あたりの窓は、新しい実行で新しく始まります。Run の全体の上限の数は、再開をまたいで引き継ぎます。そのため、Run の全体の上限に届いた後の再開は、すぐに「API の要求の上限で停止」で止まります。`run.json` の数は、再開をまたいで積み上げます。
- 上限の既定を変えた（2026-10-20。1 分あたり 120 件・Run の全体 600 件から、600 件・10,000 件へ）ため、上限の欄を空のまま保存した設定で、変える前に止まった Run は、再開の比べで設定が違うとみなされ、続きから再開できないことがあります（推測。新しく始めてください）。
- 1 回の Run の全体の既定を、ページの上限に比べた値にした（2026-10-21。10,000 件から「10,000 件か、ページの上限 × 200 件の大きいほう」へ）ため、上限の欄を空のまま保存した設定で、ページの上限が 51 以上の Run のうち、変える前に止まった Run は、再開の比べで設定が違うとみなされ、続きから再開できません（1 回だけの影響。新しく始めてください）。ページの上限が 50 以下の Run は、既定が 10,000 件のままなので変わりません。
- 再開のときの Run の全体の数は、再開のための保存の数と、負荷の記録の数の大きい方から始めます。監査の段の数を持たない保存からは再開せず、理由 `AUDIT_STAGE_COUNTS_MISSING` で止めます（この理由の専用の表示の文はありません）。このとき、ジョブはログインの後に失敗として終わります。開始の画面で「新しく始める」を選んで、新しい Run として始め直します。
- 限界: 強制終了（2 回目の Ctrl+C、画面のサーバの強制終了など）すると、最後の保存の後に数えた分が失われ、再開した後に、最大でページ 1 つ分だけ Run の全体の上限を超えることがあります（負荷の記録と同じ前例です）。再開のための保存を別の道具で書き換えると、「上限に届いた」印を消せてしまいます（保存の書き換えは守りの範囲の外です）。

### 発見・READ の確かめ・書き込みのジョブ

スクリプトで送るログインの設定のプロファイルでは、操作の候補の発見、READ の確かめ、書き込み（登録と更新）のジョブも、ジョブの監査の段の決まり（承認したサービスの Origin への要求の上限、鍵の消失、401 の数）を持ちます。ジョブの詳細には、欄「ログインの後の読み取りの数」を出します（「[SPA の画面の発見と READ](discovery-and-read-check.md#spa-の画面の発見と-read)」）。

- 上限は、認証の設定の「サービスの Origin への要求の上限」と同じ値で、1 分あたりと、1 回のジョブの全体です。1 分あたりの上限では、監査と同じく止めずに、次の画面の読み込みの前に待ちます（発見と READ の確かめ。待つ間は同じ知らせが出て、待った回数と時間は成果物の `authentication` に残ります）。
- これらのジョブでは、承認したサービスの Origin への `GET` と `HEAD` は、上限の中で通します。
- 発見と READ の確かめのジョブでは、「監査で通す読み取りの手続きの呼び出し」に登録した呼び出しも、監査の段と同じ決まりで通します。書き込みのジョブでは通しません。
- 発見と READ の確かめのジョブは、1 回のジョブの全体の上限に届いたら残りの画面（定義）を読まずに一部未完了（`PARTIAL`）で終わり、成果物の `authentication` に数を残します。鍵が消えたら、セッションの切れ（場所の印 `session-key`）で終わります（「[SPA の画面の発見と READ](discovery-and-read-check.md#spa-の画面の発見と-read)」）。
- 書き込みのジョブは、画面の確かめの後・書き込みの段を開く前と、押す直前に、鍵が消えていたか上限に届いていたら、送らずに止めます（「[承認された登録の手順](approved-create.md)」）。

### ログインの状態が消えたとき

- 監査の途中で、「成功のローカル ストレージの鍵」の形の名前が、ブラウザの状態から消えたら、セッションが切れたとみなし、今のセッションの切れと同じく止めます（終わり方 `STOPPED_BY_AUTH_SESSION_LOST`、場所の印 `session-key`）。BeakSight は鍵の名前だけを見て、値は読みません。
- 承認したサービスの Origin から 401 の応答が返った数は、記録するだけです。それだけでは、セッションが切れたとはみなしません。
- セッションが切れたと判定するパスの決まりは、今のままです。

### 記録と成果物

- `run.json` の `load.approvedServiceOrigins`（承認したサービスの Origin への要求の数と、1 分あたりの最大）と `authentication`（通した登録の呼び出しの数、止めた token の更新の数、止めたほかの読み取りでない要求の数、サービスの Origin からの 401 の数、上限に届いたか、1 分あたりの上限で待った回数と時間）。スクリプトで送るログインの監査の Run だけが持ちます（「[出力と結果の読み方](output.md#スクリプトで送るログインの監査の記録)」）。
- 成果物（`page.json`・`run.json`・HTML レポート・ChatGPT 用のバンドルの中身）の、承認したサービスの Origin の URL は、query の名前を残して値をすべて `[REDACTED]` に伏せ、path の値に見える区切りと fragment の値も伏せます。例: token の更新の URL は `grant_type=[REDACTED]` のように記録します。文の中で前置き（`url=` など）の後や、ほかの URL の中に入ったサービスの Origin の URL も伏せます。サービスのホストへの `ws://`・`wss://` の URL も伏せます。文の中では、サービスの Origin の URL の始まりから、文の候補の終わりまで（query の値に入った別の URL を含む）を 1 つの URL として伏せます。
- 伏せすぎることがあります（安全の側）: 文の中にサービスの Origin の URL があると、その URL の始まりから、空白などで区切られるまでの続き（後ろに続く許可 Origin の URL の query の値や、間の本文）まで伏せることがあります。見えている文（`visible-text.txt` と `page.json` の可視テキスト）でも同じです。例: `<サービスの URL>?q=…&next=<許可 Origin の URL>?id=…` のように続く文では、`next=` の後ろの値まで `[REDACTED]` になることがあります。
- 伏せない限界: scheme のない `//ホスト/…` の形、許可 Origin の URL の query に percent-encode で入ったサービスの Origin の URL、名前の形の path の区切り、数字の ID と UUID（ID として伏せない設計です）。
- 限界: 負荷の数（`load.approvedServiceOrigins.count` と、許可 Origin の外の数）は、本文を読まない応答（401 など）を数えないことがあり、少なく出ることがあります。上限の数えは送る前に行うので、上限には影響しない見込みです（推測）。

## 入口の確かめ

認証の設定を作る前に、ログインの画面の欄と送り方を調べて、認証の設定の案を作るジョブです（ジョブの種類「入口の確かめ」）。

- **始め方**: プロファイルの詳細か、認証の設定の画面の「入口を確かめる」を押します。認証の設定と資格情報は要りません。公開の監査のプロファイル（ログインしない）と、テスト環境の 2 つのモード（手でログインする・自動でログインする）のプロファイルで始められます。
- **読むもの**: ログインしないで、Guard の付いた読み取りだけの環境で、開始の URL を 1 回だけ読みます。表示が落ち着いたら凍結し、ページの JS から切り離した読み取り（isolated world）で、次を読みます。
  - 移った先: 許可 Origin の中ならその path、外なら Origin だけ（許可 Origin の外へは移りません。移ろうとした記録は Safety Ledger の `blockedNavigations` に残ります）。
  - ログインの画面に見えるか（見えるパスワードの欄があるか）。
  - ユーザー名の欄・パスワードの欄・送信の要素の、見える候補の数と、ちょうど 1 つのときはそれを指す一意な CSS。
  - 3 つの要素の置き方（「3 つが同じ form の中」「3 つとも form の外」「混ざっている」）と、form の method と action。
- **読まないもの**: 欄の値は読みません。送信、入力、押下、書き込みはしません。読み込みは 1 回だけで、ほかのジョブと同時には動きません。
- **終わり方**: 「読んだ」「許可 Origin の外へ移ろうとした」「読めなかった」。
- **結果**: ジョブの詳細の「入口の確かめの結果」に、移った先、ログインの画面に見えるか、欄の候補、form、認証の設定の案（ログインの開始の URL、セッションの切れの path、送り方（form の送信の action が許可 Origin の中の POST なら「フォームの送信」とその送信先、form がない・action がないなら「スクリプトで送る」）、自動ログインのセレクタ）を出します。「認証の設定の画面で案を確かめる」から開けます。成果物は `entry-check.json` です（「[出力と結果の読み方](output.md#入口の確かめの成果物)」）。
- **読み込み直しの上限**: ページ自身の読み込み直しや移動（JS の `location.reload()`、meta の転送、iframe の中の読み込み直しなど）は、frame ごとに 2 回までです。超えたら止め、終わり方は「読めなかった」（`READ_FAILED`）になります。届いた文書の要求の数は、`entry-check.json` の `documentRequests`（main frame）と `childFrameDocumentRequests`（子の frame）に残ります（「[ページ自身の読み込み直しの上限](site-load.md#ページ自身の読み込み直しの上限)」）。
- **案の使われ方**: 保存した認証の設定がないときだけ、最後に成功した入口の確かめの案で、新しい認証の設定の欄を埋めます（開始の URL の path の案より優先します）。開始の URL の path で埋めた成功の画面の path が、ログインの画面の path に当たるときは、成功の画面の path を空にします（人が入れます）。案は、保存するまで案です。
- ジョブの種類「入口の確かめ」は、管理データの版 12 で足しました（今の BeakSight は、管理データを版 17 の形で作ります）。

## 観察した要求の登録

ログインの段で止めた要求と、ログインの段で観察したことから、認証の設定の案を作り、利用者が確かめて保存する手順です。BeakSight は、利用者が保存したものだけを通します。

### ジョブの詳細で見るもの

- パネル「ログインの段で止めた送信」の表に、列「query の名前」（4 つまで。超えた分は「ほか N 件」）と「登録」があります。query の値は残しません。ただし、`grant_type` の値だけは残し、`grant_type=password` の形で出します（token の送信の形を見分けるため）。
- 行の「登録する」は、**確認のダイアログの後に、その場で保存します（画面は移りません）**。ダイアログには、足すもの（token の送信先と必須の query の名前、またはログインに伴う送信と回数）と、プロファイルの「承認したサービスの Origin」に足す Origin と、保存した後のプロファイルの改訂を出します。確認すると、プロファイル（足す Origin と改訂）と認証の設定を 1 回で保存し、行に「登録しました（プロファイルは改訂 N になりました）。」を出します。保存するとプロファイルの改訂が進むので、承認済みのシナリオや、発見・READ の確かめの結果は、やり直しが要ることがあります。組み立ては、手動のログインからの自動の登録と同じ部品を使います。
  - 成功のローカル ストレージの鍵は、今の設定の鍵か、そのジョブのログインの観察の案（許可 Origin のもの）を入れます。どちらもないときは、登録しません（「認証の設定の画面で直す」から鍵の形を入れます）。
  - フォームの送信の設定は、スクリプトで送るログインの設定にします。今の設定がスクリプトで送るログインなら、その行だけを足します。
  - 自動の登録が足さない行（token の後の送信、別の Origin の送信など）も、利用者はこの「登録する」で足せます。読まないパスと、危険な語（ログアウト・削除など）を含むパスの行は、登録しません（ダイアログを出さずに理由を出します）。
  - 確認の後にプロファイルが変わっていたときは、保存しません（読み直して、もう一度押します）。
  - 行の「認証の設定の画面で直す」は、今までどおり、認証の設定の画面を下書きつきで開きます（下の「[下書きと保存](#下書きと保存)」）。
- 行の種類で登録先を分けます。
  - `grant_type` の値を記録した行（token の送信の形）: token の送信先として登録します（送り方は「スクリプトで送る」。token の送信先の Origin とパスと、必須の query `grant_type=<記録した値>`）。今の送信先と違えば、その行の送信先に替えます。
  - ほかの、まだ登録していない読み取りでない要求: ログインに伴う送信として登録します（POST。その場で保存するときの回数の上限は、閉じた上限の最大。下書きでは 1）。
  - 値に見える区切りを伏せたパスの行: ボタンを出しません（「値に見える区切りを伏せたパスなので、登録の案を作れません。認証の設定に手で入れてください。」）。
  - 登録してある送信の上限か送り方で止めた行と、token の送信先への必須の query が違う送信の行: ボタンを出しません（登録した token の送り方を置き換えないためです。認証の設定を開いて、手で直します）。
- 欄「ログインの段で観察した案」（ログインの段の始めと終わりに読んだことから作った案。値と画面の文字は残しません）:
  - 「新しく出たローカル ストレージの鍵の名前の形（成功の鍵の名前の案。最初と最後の部分だけで、間の部分は残しません）」と「鍵の Origin」: ログインの前と後で、ログインの画面の Origin のローカル ストレージの鍵の名前を比べ、新しく出た名前から作った案です。名前を区切り（`.`、`:`、`_`、`/`、`-`）で分け、最初の部分と最後の部分のうち、閉じた一覧の一般の語（`token`、`auth`、`session`、`idtoken`、`access`、`refresh`、`jwt` など。`LOGIN_STORAGE_KEY_GENERAL_WORDS`）に当たる側だけを出します。最初の部分が当たればその部分と後ろの区切りを接頭辞の案に、最後の部分が当たれば前の区切りとその部分を接尾辞の案にします。当たらない側は空にし、利用者が入れます（片側が空でも、成功の鍵の確かめに使えます）。画面では、接頭辞と接尾辞の間を `…` にして出します（例: `app.<利用者の名前>.token` の案は、接頭辞が空、接尾辞が `.token` です）。両側とも当たらない名前と、区切りのない名前は、案にしません。区切りが 1 つで両側とも当たるときは、接尾辞だけを出します。間の部分と、当たらない端の部分（利用者の名前や ID が入りうる）は、記録・管理データ・画面・下書きのどこにも残しません。値は読みません。
  - 「成功の画面のセレクタの案」: ログインの段が終わった画面（ログインの後の画面）を凍結してから読み、ログアウトの語に当たる見えるリンクかボタンの、ログアウトの語を含む属性（id、name、リンクの href）から作った一意な CSS です。属性の値のうちログアウトの語のほかの部分は、閉じた一覧の一般の語（`button`、`btn`、`link`、`menu`、`nav` など）と区切りだけのものに限ります（利用者の名前や ID が入りうる値を案にしないためです）。リンクの href は、`/` で始まる短い path で、query・fragment・値に見える区切りのないものだけです。ナビゲーションや見出しの中の要素の案は出しません。ログインの画面にもあった CSS と、Playwright が解釈できない CSS は外します。管理データには CSS だけを残し、要素の文字は残しません。
  - 自動ログインのログインの段では、案を、入れた資格情報と照らします（資格情報の守りと同じ比べ方）。逆向きにも比べます: ユーザー名を区切りと `@` で分けた 4 文字以上の部分と、案の部分を、NFKC と大文字・小文字を畳んで比べます。資格情報を含む案は捨てて、捨てた数だけを出します（「入れた資格情報を含んだので、1 件の案を捨てました。」の形）。
  - 手動のログインの段だけ、ログインの画面の 3 つの欄（ユーザー名の欄・パスワードの欄・送信のボタン）の CSS の案も、ログインが成功したときに残します（入口の確かめと同じ部品で、各欄の候補がちょうど 1 つのときだけ。入力の値は読みません）。この欄には出さず、「[手動のログインから 1 回で切り替える](automated-login.md#手動のログインから-1-回で切り替える)」の画面の案に使います。
  - ログインの段のまとめが管理データの上限より大きいときは、観察した案と query の名前を省きます（「ログインの段のまとめが大きすぎたので、観察した案と query の名前を省きました。」）。
  - 「案を認証の設定に入れる」で、認証の設定の画面を下書きつきで開きます。

### 下書きと保存

- 行の「認証の設定の画面で直す」と「案を認証の設定に入れる」は、その場では保存しません。認証の設定の画面を、下書き（画面の URL に持たせる。保存しない）つきで開きます。画面には「URL で受け取った下書き」の知らせが出ます。下書きはジョブに結び付かず、URL で受け取ったものとして扱います（保存の前に、利用者が確かめます）。
- 欄に入れる値の優先の順は、次のとおりです。
  1. 保存した設定の値（なければ、開始の URL の path の案と、今の既定）。
  2. 入口の確かめの案（保存した設定がないときだけ）。
  3. 観察した要求の下書き（保存した設定があっても入れます。いちばん新しい観察として、前の値の上に入れます）。ログインに伴う送信は、今の一覧に足します（同じ Origin とパスは重ねません。回数の上限は 1）。成功の鍵の名前の案は、接頭辞の案を「鍵の名前の接頭辞」に、接尾辞の案を「鍵の名前の接尾辞」に入れます（名前の全体は持ちません）。案が空の側は空のまま入るので、要れば利用者が入れます。
- 保存すると、保存の時点の欄の token の送信先とログインに伴う送信の Origin のうち、プロファイルの「承認したサービスの Origin」にないものを足し（足す Origin は、下書きではなく、保存の時点の欄から決め直します）、プロファイルと認証の設定を 1 回で保存します（画面に、足す Origin の知らせが出ます）。1 回で保存するので、プロファイルの改訂で認証の設定が「古い」になりません。ほかの画面で先に変えられていたときは、保存しません。
- 下書きの形が正しくないときは、欄に入れません（「URL で受け取った下書きの形が正しくないので、欄に入れませんでした。」）。

### 繰り返しの流れ

止められる要求がなくなるまで、利用者が次を繰り返します（毎回、利用者が押します。ログインの上限は今どおりです）。

1. **観察**: ログインの段のあるジョブ（手動のログインの監査や発見、自動ログインのログインの確かめなど）を始め、ジョブの詳細のパネル「ログインの段で止めた送信」を見ます。
2. **登録**: token の送信の形の行と、ログインに要る送信の行の「登録する」から、認証の設定の画面で確かめて保存します。登録するかは、利用者が判断します。
3. **もう一度ログインの確かめ**: もう一度ログインの段のあるジョブを始めます。止めた要求が残っていれば、1 に戻ります。
4. **鍵の名前の案**: ログインが進むと、欄「ログインの段で観察した案」に、成功の鍵の名前の案が出ます。「案を認証の設定に入れる」で入れて保存します。
5. **成功**: 成功の条件（成功の画面の path、成功のローカル ストレージの鍵、token の送信を 1 回以上通したこと）がそろうと、ログインが成功します。
6. **セレクタの案**: 成功した後に、欄「ログインの段で観察した案」に成功の画面のセレクタの案が出ます。要れば入れて保存します。

### 限界

- 止めた要求の行は method を持ちません。そのため、ログインに伴う送信の下書きは POST に固定します。実際の送信が POST でなければ、Guard が今どおり止めます（認証の設定で手で直すことはできません。ログインに伴う送信の method は POST だけです）。
- 値に見える区切りを伏せたパスは、登録の案を作れません。手で入れます。
- 成功の画面のセレクタの案は、ログアウトの語を含む属性で一意に指せる要素がなければ出しません（人が入れます）。
- 成功の鍵の名前の案は、端の部分が一般の語に当たる名前だけです。端が一般の語でない名前と、区切りのない名前は、人が入れます。
- token の送信先への必須の query が違う送信の行は、登録の案を作りません。認証の設定で手で直します。

## 守りの範囲

### ログインの段

- 許す送信は、認証の設定の「ログインの送信先」（Origin と path が完全に一致）への、ページの移動（main frame のナビゲーション）の POST だけです。回数の上限までです。「スクリプトの送信」の設定では、上の「[ログインの段で通すもの・止めるもの](#ログインの段で通すもの止めるもの)」のとおりです（フォームの送信先への POST は許しません）。
- ほかの送信（ほかの POST、送信のビーコン、WebSocket、Service Worker、別の Origin へのページの移動、外部のアプリの起動、ポップアップ）は、公開の監査と同じく止めます。ログインの後の別の Origin への移動も止めます。
- ログインの段では、ターゲット設定の許可 Origin（`site.allowedOrigins`）の外へは、読み取り（GET と HEAD）の要求も送りません。画像、スクリプト、stylesheet、フォント、fetch、iframe などのサブリソースとサブ frame の移動も止めます（公開の監査と監査の段では、今までどおり、許可 Origin の外のサブリソースを読みます）。ページのスクリプトが、人が入れた値を別のサイトへの要求に載せて送ることを防ぐためです。許可 Origin への読み取りは許すので、ページのスクリプトが値を許可 Origin への GET に載せると、対象のテスト環境のサーバには届きます（自動ログインの「送信の窓」は、手動のログインの段にはありません。「[自動ログインの手順](automated-login.md)」）。
- ログインのブラウザは、監査の前に閉じます。ログインの段で許した送信は、監査には持ち越しません。

### 監査の段

- 監査の段の送信の決まりは、公開の監査と同じです（GET と HEAD だけ。「[読み取り専用の保証](safety.md)」）。
- 読まないパス、読む範囲のパスの外、既定で読まない語（`logout`、`signout`、`sign-out`、`log-out`、`delete`、`remove`、`destroy`、`cancel`）を path か query に含む URL は、巡回でも、ページの中の画面の移動（main frame と iframe の文書）でも読みません。止めた要求は、Safety Ledger の `blockedAuditExclusions` に記録します。ページが自分で出す文書でない `GET`・`HEAD` には、この決まりを当てません（BN-0。上の「監査の段で通すもの・止めるもの」）。Interaction の読み込みでは、今どおりすべての要求に当てます。robots.txt と sitemap.xml が読む範囲の外なら、取りに行かずに「範囲の外」と記録します。
  - 許可 Origin への要求の path は、書かれたままの形に加えて、別の書き方の形でも比べます。別の書き方とは、percent-encode を（重ねたものも）戻した形、連続した `/` を 1 つにまとめた形、各 segment の `;` から後（path の引数）を外した形、`.` と `..` を解決した形と、それらを重ねた形です。読まないパスと既定で読まない語は、大文字と小文字を区別せず、どれか 1 つの形に当たれば読みません。この 2 つは、全角の文字や互換の文字を Unicode の NFKC で畳み、大文字と小文字をそろえた形でも比べます。
  - 読む範囲のパスは、畳み込みの形を使わずに（大文字と小文字を区別して）比べ、すべての形が読む範囲に入るときだけ読みます（畳み込みで読む範囲を広げないため）。
  - 安全のため、次の URL も読まず、`blockedAuditExclusions` に記録します。decode できない形（`%` の後に 16 進の 2 文字が続かないもの。文字の `%` を含む正当なパスも含みます）。percent-encode を決まった回数まで戻しても、まだ変わり続ける形。比べる形の数が上限（`src/safety/request-policy.ts` の `MAX_AUDIT_PATH_FORMS`）を超える長いパス。
- 監査に渡すログインの状態は、普通のブラウザが、そのページに持つものに近づけてあります（DEF-139）。
  - Cookie: ブラウザが `approvedTestOrigins` の host か、承認したサービスの Origin（スクリプトで送るログインのとき）の host へ送る Cookie です。ドメインがその host と一致する Cookie と、親ドメインの Cookie（例: host が `app.example.test` のときの `Domain=example.test` の Cookie）を含みます。ほかのサブドメインの Cookie、IP アドレスの host への親ドメインの Cookie、区切りのない 1 語のドメイン（`com` など）の Cookie は渡しません。
  - localStorage: `approvedTestOrigins` の Origin のものだけです。
  - IndexedDB: `approvedTestOrigins` の Origin と、承認したサービスの Origin のものです。中身は読まずに、そのまま渡します。
  - sessionStorage と、ほかの Origin の状態は渡しません。
  - 値はメモリの中だけに持ち、どこにも書きません（下の「[秘密を出さないこと](#秘密を出さないこと)」）。ログインの段の終わり、監査の途中でブラウザの Context を作り直すとき、発見・READ の確かめ・書き込みのどれも、同じ決まりで渡します。
  - 限界（ページを離れるときの送信の応答。Task 44 のレビューの M-2）: 送信の扱いが `PASS_EXCEPT_DELETE` のとき、監査するページのデスクトップとモバイルの読み込みを閉じる前に、まず認証の状態を読み、その後でページを離れます（「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」）。そのため、ページを離れるときの送信（`sendBeacon`、keepalive の fetch など）の応答でサイトが更新した Cookie（応答の `Set-Cookie`）は、次の Context に渡りません。ページを離れるときにページ自身が書き換えた localStorage なども同じです。次の Context は、ページを離れる前に読んだ状態で始まります。サイトが、ページを離れるときの送信の応答でログインの状態を更新する作りなら、次のページでセッションの切れになることがあります（確かめていません）。
- 渡す Cookie は、その host だけに送る Cookie にします（ログインの画面が、サブドメインにも送る形（Domain 属性つき）で作った Cookie も、親ドメインの Cookie も、一致した host だけに送る形にして渡します）。そのため、許可した host のサブドメインや、親ドメインのほかのサブドメインには送りません。親ドメインの Cookie と、同じ host・名前・パスの Cookie があるときは、その host の Cookie を渡します。ただし、同じ host の別の port には、Cookie の決まり（Cookie は port で分かれない）により送られることがあります。同じ host で、別の port に監査してはいけないサービスがあるテスト環境では、注意してください。
- **ログインの後の状態の名前の記録**: ログインの段の終わり（手動・自動のどちらも。状態を読んだとき）に、ログインの後のブラウザの状態の名前だけを記録します。値と中身は記録しません。原因を後から調べるための記録です（例: 2 ページ目でログインの画面へ移されるとき、要る Cookie や IndexedDB を引き継いだか）。
  - Cookie: ドメイン、パス（値に見える区切りは `[REDACTED]`）、その host だけに送る Cookie か、名前の形、監査に引き継いだか、許可の外なので外したか。
  - ローカル ストレージの鍵と IndexedDB のデータベース: Origin、名前の形、引き継いだか外したか。
  - 名前は、ログインの段の観察と同じく、先頭と末尾の一般の語（`token`・`auth`・`session` など）だけを残し、間の部分と名前の全体は残しません。一般の語のない名前は「（一般の語のない名前）」と出します。
  - 同じ行は数にまとめます。置き場所ごとに 16 行までで、超えた分は数だけを残します。
  - 記録は、管理データ（ジョブのログインの段のまとめ）とジョブの画面の「ログインの段」の欄だけにあり、Run の成果物には入りません。まとめが管理データの大きさの上限を超えるときは、ログインの段の観察と一緒に省きます。
- **クリックによる操作の確かめ（Interaction）は行いません**（管理画面のボタンやリンクは、開くだけで状態を変えることがあるため）。`run.json` の有効な設定の `audit.interactions` は `false` になります。

### 秘密を出さないこと

- **ログインの状態（Cookie、localStorage、IndexedDB）と資格情報は保存しません。** 成果物（Run のディレクトリ。再開のための保存と ChatGPT 用のバンドルを含む）、管理データ、画面、ログ、監査の process との間の通信のどこにも書きません。
  - [まとめて実行](stage-chain.md) では、ログインの状態を、監査の process のメモリの中だけで次の段へ渡します（ジョブの間では渡しません）。
- **URL の秘密を伏せ字にします。** 認証つきの監査では、成果物に書くすべての文字列の中の URL と、セッションの切れの知らせの URL について、次を `[REDACTED]` に置き換えます。
  - 名前が次の一覧に当たる query の値（大文字と小文字、`-`・`_`・`.` の区切り、percent-encode の違いを問わず、名前の全体が一致するもの。値が空のものはそのまま）: `token`、`access_token`、`id_token`、`refresh_token`、`auth_token`、`session_token`、`csrf_token`、`xsrf_token`、`authenticity_token`、`jwt`、`ticket`、`session`、`sessionid`、`sid`、`phpsessid`、`jsessionid`、`auth`、`authorization`、`key`、`apikey`、`api_key`、`access_key`、`secret`、`client_secret`、`password`、`passwd`、`pwd`、`pass`、`otp`、`code`、`state`、`nonce`、`csrf`、`xsrf`、`signature`、`sig`、`x-amz-signature`、`x-amz-credential`、`x-amz-security-token`、`samlrequest`、`samlresponse`、`relaystate`、`credential`、`credentials`。
  - URL の利用者名とパスワード（公開の監査と同じ伏せ字）。
  - 例: `https://test.example/admin/report?token=…&page=2` は、`https://test.example/admin/report?token=[REDACTED]&page=2` と記録します。
- 巡回の判定（同じページかどうか）は、伏せ字の前の URL で行います。ページの URL（巡回の記録）には、一覧の名前の query を残しません（`crawl.allowedQueryParameters` に一覧の名前を入れられないため）。そのため、伏せ字で別のページが同じに見えることはなく、セッションの切れで止まった Run も、伏せ字の後の保存から再開できます。
- 公開の監査では、伏せ字を通しません（出力は今のまま）。
- **見えている文とスクリーンショットは伏せません。** 管理画面に表示されたデータ（テスト環境のデータ）が写ります。

テスト用の小さなサイトで、Cookie の値（入れ替わった値を含む）、localStorage の値、IndexedDB の値、ログインの送信の資格情報、URL の query の値を目印にして、Run のディレクトリのすべてのファイル（再開のための保存と、ZIP の中身を含む）、管理データ、画面のサーバと監査の process の出力、監査の process との間の通信の記録、画面の HTML と応答を検索し、目印が 1 つも出ないことを確かめています（セッションの切れで止まった場合と、再開した場合を含む）。

## 使えないこと

- 別の Origin のログインのサービス（IdP。シングルサインオン）を通るログイン。認証の設定の「許す IdP の Origin」は、空だけを受けます。
- 多要素認証（MFA）。
- sessionStorage や IndexedDB に頼るログイン。画面の中のスクリプトで送るログインは、「スクリプトの送信」の設定のときだけ扱います（手動のログインと自動ログイン）。
- 手動のログインのプロファイルでの、資格情報の自動の入力。自動ログインは、認証の方式を `AUTOMATED_LOGIN` にしたプロファイルで使います（「[自動ログインの手順](automated-login.md)」。Windows だけ）。
- CLI からの認証つきの監査。
- `TEST_APPROVED_WRITE` のプロファイルでの監査（読み取りの監査は `TEST_AUTH_PASSIVE` のプロファイルで行います。書き込みは「[承認された登録の手順](approved-create.md)」）。

## 確かめていないこと

- **人がログインのブラウザで、ログインのほかの操作をした場合。** 別のタブや別のウィンドウを開く、アドレスバーに URL を入れる、開発者ツールを使う、などです。同じブラウザの中の要求は、ログインの段の守り（上の「[ログインの段](#ログインの段)」）を通りますが、テストでは、headless のブラウザで、人の操作を自動の操作で代えて確かめただけです。
- 実際のテスト環境でのログインと監査（まだ接続していません。ユーザーの承認の後に、小さく確かめます）。
- 手動のログインの段に、資格情報を自動で入れる処理がないこと: 自動の検査（`worker-login-hooks`）は、`src/` の中のコードの文字列を調べる近似の検査です。ページの入力の欄に値を入れる操作を使ってよいのは、自動ログインの入力の部品（`src/browser/login-form-submitter.ts`）だけで、それを参照してよいのは自動ログインの段だけです（「[自動ログインの手順](automated-login.md)」）。`page.evaluate` でページに値を書き込む場合は、捕まえません。
- 伏せ字にしない秘密: URL の fragment（`#` の後。例: `#access_token=…`）、query の値の中に percent-encode して入れた URL の中の秘密、一覧にない名前の query の値、URL でない文（見えている文、console の文、誤りの文）の中の秘密。
- 設定のファイルの `site.startUrl` に、一覧の名前の query（例: `?token=…`）がある場合の再開: 再開のための保存の有効な設定も伏せ字になるので、再開の比べで設定が違うと判断され、新しい Run を始める可能性があります（推測。確かめていません）。
