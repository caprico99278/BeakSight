# 承認された更新（UPDATE）の手順（テスト環境だけ）

テスト環境で、承認したシナリオ（「[書き込みのシナリオの承認](scenario-approval.md)」）に従って、BeakSight が前に登録したレコード 1 件だけを実際に更新し、結果を判定し、更新の後の画面と READ で、指定した欄だけが変わったことを照合する手順です。対象の選び方、結果の種類、上限、サイトへの読み込み、守りの範囲、確かめていないことも書きます。登録（CREATE）と同じ所は「[承認された登録（CREATE）の手順](approved-create.md)」を参照します。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> テスト用の小さなサイトで確かめています。実際のテスト環境へは、まだ接続して確かめていません（「[実テスト環境の手順](real-test-environment.md)」）。

## 使ってよい場合（前提）

- 登録（CREATE）と同じです（「[使ってよい場合](approved-create.md#使ってよい場合前提)」）。テスト環境だけ、監査モード `TEST_APPROVED_WRITE`、環境の証跡、4 つの副作用の確認、入力の規則（変える欄の作り方）、検証の指定（成功と入力の誤りの条件、ID の取り方、照合の READ）が要ります。
- **更新できるのは、BeakSight が登録して照合したレコードだけです。** 参照した登録のシナリオで、結果が `VERIFIED` の登録が 1 件もなければ、実行の許可を出しません（`TARGET_RECORD_UNAVAILABLE`）。BeakSight が作っていないレコードは更新しません。
- 削除、一括の更新、1 回の Run で複数のレコード、複数の段のシナリオは扱いません。

## UPDATE の指定

更新の候補（発見の結果で、分類が UPDATE の form）からシナリオを作るときに、次を指定します（承認の digest の項目なので、変えると再承認が要ります）。

| 項目 | 内容 |
| --- | --- |
| 台帳の参照 | 更新の対象を選ぶ登録（CREATE）のシナリオ（同じプロファイルの、ほかの CREATE のシナリオ 1 つ）。 |
| path の型 | 更新の画面の path と送信先の path を、レコードの ID の区切りを `{id}` にした型で持ちます（例 `/members/{id}/edit` と `/members/{id}`。それぞれ `{id}` をちょうど 1 つ、区切りの全体に）。型に、発見で見た候補の ID の区切りを入れると、候補の具体的な path に同じ値で戻ることを確かめます（戻らなければ `SCENARIO_UPDATE_PATH_MISMATCH`、戻る値が ID の形でなければ `SCENARIO_UPDATE_RECORD_ID_UNSAFE`）。`{id}` の位置は、台帳の登録の ID の取り方に合わせます。登録の ID を path の型（例 `/members/{id}`）から取る台帳なら、送信先の型の `{id}` の後ろの区切りの並びが台帳の型と同じ（台帳が `/members/{id}` なら後ろなし）で、`{id}` の前の並びが台帳の型の前の並び全体と後ろから続けて一致する（`/admin/members/{id}` は合い、`/members/{id}/notes/5` と、台帳 `/a/members/{id}` に対する `/b/members/{id}` は合わない）こと、要素から取る台帳なら、送信先の型の `{id}` が最後の区切りであることを求めます（外れれば `SCENARIO_UPDATE_PATH_NOT_BOUND_TO_LEDGER_ID`。画面では、合わない型の組を選べません）。台帳の取り方が後で変わったときは、実行の許可を出すときに確かめ直し、同じ理由で始めません。 |
| 変える欄 | 新しい値を送る欄（1 つ以上。`SCENARIO_UPDATE_NO_CHANGED_FIELD`）。値は入力の規則で作ります。 |
| 保つ欄 | 更新の前に読んだ値（前の値）のまま送る欄。見えていて編集できる欄は、すべて変える欄か保つ欄のどちらかです（既定は保つ。漏れは `SCENARIO_UPDATE_FIELD_ROLE_MISSING`、重なりは `SCENARIO_UPDATE_FIELD_ROLE_OVERLAP`）。人が保つ欄の期待の値を決める必要はありません。 |

- **メールと電話は、既定で保ちます。** 変える欄に選んだときだけ、合成の値（`example.invalid` のメール、`090-0XXX-XXXX` の電話）にし、副作用の確認 `NO_EXTERNAL_NOTIFICATION` を求めます（「[入力の規則とデータの生成](data-rules.md)」）。
- **状態の欄は、保つだけです。** 状態の語（有効・無効・公開・削除・表示・非表示・フラグなど。閉じた一覧）に当たる名前の欄は、変える欄にできません（`SCENARIO_STATE_FIELD_NOT_CHANGEABLE`）。変える select・radio の選択肢から、無効化の語の値と文言を除きます。
- **削除の語の欄も、保つだけです。** 危険な語（削除・取り消し・無効化・一括など）と、欄の名前のための削除の語（`removed`・`trashed`・`withdrawn`・`void`・`unsubscribed`・`locked`・`banned` など。閉じた一覧）に当たる名前の欄（`_destroy`、`delete_*`、`remove_*`、`is_removed` など）は、変える欄にできません（`SCENARIO_REMOVAL_FIELD_NOT_CHANGEABLE`）。語は名前の語の単位で比べます（`lock_version`・`banner_text` には当たりません）。
- **秘密に見える名前の欄がある画面は、実行しません。** 秘密に見える名前の見える欄（`SCENARIO_UPDATE_FORM_HAS_SECRET_LIKE_FIELD`）や、状態の語に当たり秘密に見える名前でもある見えない欄（`state` など。`SCENARIO_UPDATE_FORM_HAS_SECRET_LIKE_STATE_FIELD`）があると、値を読めず照らせないので受けません。ページが作る値の名前の閉じた一覧（CSRF のトークンなど。名前だけを照らす）の外の、秘密に見える名前の hidden・readonly・見えない欄がある画面も受けません（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`。登録と同じ。「[送る欄に選ばなかった欄](approved-create.md#送る欄に選ばなかった欄)」）。

## 画面の手順

登録（CREATE）の画面の手順（「[画面の手順](approved-create.md#画面の手順)」）と同じ順です。違うところは次のとおりです。

1. **先に登録を照合済みにする**: 同じプロファイルの登録（CREATE）のシナリオで、結果が「照合済み」（`VERIFIED`）の登録が 1 件以上あることが要ります。
2. **シナリオを作る**: 画面「操作の候補」で、更新（UPDATE）の候補の「シナリオを作る」を押します。送る欄の選択の代わりに「UPDATE の指定」が出ます。
   - 「台帳にする登録（CREATE）のシナリオ」を選びます。
   - 「path の型」を選びます。候補の path から型を作れないとき、または手で入れるときは「手で入力する」を選び、「更新の画面の path の型」と「送信先の path の型」を入れます。
   - 「欄の役割」で、見えていて編集できる欄ごとに「変える」か「保つ」を選びます（既定は保つ）。状態の欄と、秘密に見える名前の欄は変えられません（理由が出ます）。変える欄は 1 つ以上要ります。
   - 検証の指定、上限、承認の期限、副作用の確認は、登録と同じに入れます。
3. **入力の規則を決める・承認する**: 登録と同じです。値を作るのは変える欄だけです。
4. **書き込みを始める画面を開く**: シナリオの詳細の「書き込みを始める画面を開く」を押します。画面「書き込みを始める」に、送る欄の代わりに「更新するレコード」（台帳のレコードのうち最も新しいもの）、「変える欄」、「保つ欄」、「更新の画面」、送り先が出ます。対象にできるレコードがなければ、その旨が出て、始められません。
5. **始める**: 「書き込みを始める」を押し、確認のダイアログ（「テスト環境の上のレコード 1 件を更新します。」）の「書き込みを始める」を押します。画面が見せた「更新するレコード」と、始めるときに選び直したレコードが違えば、始めません（`TARGET_SELECTION_CHANGED`）。
6. **結果を見る**: ジョブの画面の「書き込みの結果」に、登録と同じ項目に加えて「更新の対象のレコード」と「取れた ID」、「前後の差分」（変えた欄の前の値・新しい値・更新の後の照合、保つ欄の照合）が出ます。報告と台帳は登録と同じです。台帳の「この ID への UPDATE」に、回数と最後の結果が出ます。

## 対象の選び方

- 実行の許可の発行の中で、参照した登録のシナリオの `VERIFIED` の登録のうち、**登録の時刻が最も新しい 1 件**を自動で選びます。人は ID を入力しません。
- 開始の画面に、その ID を「更新の予定のレコード」として出します。発行の時に選び直した結果が、画面が見せた予定と違えば止めます（`TARGET_SELECTION_CHANGED`。許可は出ません）。
- 選んだ ID は、実行の許可と予約に結び付け、ワーカーは親から受け取った ID だけを使います（具体的な path は、親が型に ID を入れて作ります）。
- **外すレコードはありません。** 前の更新の結果（`UNKNOWN` を含む）によらず、同じレコードを何度でも更新できます。レコードごとの更新の回数も数えません。

## 実行の流れ

1 回の更新のジョブ（`WRITE_UPDATE`）は、次の順に進みます。どの段で止まっても、送っていなければ件数の予約を返します（`RELEASED`）。

1. **確かめ・実行の許可・値の生成・ログイン**: 登録と同じです（「[実行の流れ](approved-create.md#実行の流れ)」の 1〜4）。値を作るのは変える欄だけです。
2. **更新の前の読み取り**: 凍結した Context で、対象の ID の更新の画面を 1 回読み（GET）、候補を読み直します。承認した型にした識別の digest と規則の digest が同じ候補がちょうど 1 つあることを確かめ（下の「ID の区切りの決め方」）、同じ画面で、変える欄と保つ欄の今の値、状態の名前の欄の値、同じ名前の hidden と checkbox の組の hidden の値を読みます（前の値）。あわせて、**ほかの hidden・readonly・見えない欄の値**（`lock_version` など。見えない checkbox・radio・select を含む）も読みます。この値は送る中身の照合だけに使い、記録せず、更新の後の照合では比べません（楽観的なロックの版のように、更新で変わる値があるため）。**ページが作る値の名前の閉じた一覧（CSRF のトークンなど）に当たる欄の値だけは読みません**（名前だけを照らします。下の「守りの範囲」）。前の値は台帳の値とは比べません。
3. **照合の期待を作る**: 変える欄は新しい値、保つ欄・状態の名前の欄・組の hidden は前の値、ほかの hidden・readonly・見えない欄（見えない checkbox・radio・select を含む）は読んだ値、disabled の欄は送られない、`_method` は承認した候補の上書き（PUT か PATCH）。
4. **書き込みの画面と入力**: 書き込みの段の Context で、更新の画面をもう一度読み（GET）、フォームを確かめ、画面の値が前の値と同じかを確かめます（違えば送らない）。**値を入れるのは変える欄だけです**（保つ欄には触りません）。
5. **送る直前の確かめ直し**: 押す前の読み込みの間隔を待った後、押す直前に、親が承認と許可（対象の ID を含む）を求め直します。登録と同じです。
6. **送信**: ブラウザで押します。送る中身は、ブラウザの内部の層で照合し、照合が通った要求だけを、BeakSight の送り手が 1 回だけ送ります（「[登録の要求の送り方](approved-create.md#登録の要求の送り方)」と同じ）。
7. **判定**: 登録と同じ判定に加えて、成功の後に取れた ID が対象の ID と同じであることを求めます（違えば `UNKNOWN` の `RECORD_ID_MISMATCH`）。
8. **更新の後の照合**: 書き込みの段を閉じた後、凍結した Context で対象の更新の画面をもう一度 1 回読み、同じ確かめをして、欄ごとに比べます（変えた欄は新しい値、保つ欄・状態の名前の欄・組の hidden は前の値）。
9. **照合の READ**: 一致しない欄がなければ、シナリオの照合の READ（結び付けた値は新しい値）を行います。
10. **記録と報告**: 登録と同じく、ワーカーが書き込みの報告（4 つ）と `action-run.json` を書き、親が管理データに結果と証拠（下）を記録し、予約を締め、報告を確かめます（「[書き込みの報告](output.md#書き込みの報告)」）。

- 値の比べ方は、完全な一致です。改行は CR LF・CR・LF を同じと見なすだけで、ほかの正規化はしません。

## ID の区切りの決め方

- 更新の画面の確かめでは、読み直した候補ごとに、画面の path と送信先の path で、**値が対象の ID と同じ区切りの組がちょうど 1 つ**のときだけ、その組を `{id}` にした型にした識別の digest を求め、承認した値と照らします。
- 同じ値の区切りが 0 組、または 2 組以上ある候補は照らしません（どの区切りが ID か決められないので、止める側）。
- 規則の digest（欄ごとの必須・制約・選択肢など）も、承認した候補と同じことを求めます。レコードによって選択肢などが変わる画面は止まります。

## 証拠と記録

- **欄ごとの証拠**（`action-run.json` と `action-evidence.json` の `update.updateEvidence` と、管理データの書き込みの結果）: 欄ごとに 1 つ、変えた欄（`CHANGED`）、保つ欄と状態の名前の欄（`KEPT`）の順です。どの欄も、更新の後の照合で一致したか（照合できなければ null）を持ちます。
- **変えた欄は、前の値と新しい値を記録します**（前後の差分を画面に出すため。平文）。前の値がない変えた欄（前にチェックしていない checkbox など）は、空の値で記録します。
- **前の値には、BeakSight でない人の値も入りえます。** 対象は BeakSight が登録したテストのレコードですが、登録の後に人やほかの仕組みがテスト環境でそのレコードを編集していれば、更新の前に読んだ値はその値です。その値も平文のまま管理データ、`action-run.json`、書き込みの報告（`action-evidence.json`、`action-report.html`、書き込みのバンドル）に記録され、結果の画面（前後の差分）に出ます。報告の先頭とバンドルの目録には、人が入れた値が入りうることの注意が出ます（「[成果物を外へ渡す前の確かめ](anonymization.md)」）。テスト環境のレコードに、記録に残してはならない値を入れないでください。
- **保つ欄・hidden の値・readonly の値・CSRF のトークンは記録しません**（保つ欄は一致の真偽だけ。送る中身の照合のために読んだ hidden・readonly・見えない欄の値も残しません）。
- 照合まで進まなかった回（送らなかった回、成功でない回）は、証拠を持ちません。更新の後の画面が開けなかった回は、どの欄も「照合できない」の証拠を持ちます。

## 結果の種類と意味

結果の種類は登録と同じです（「[結果の種類と意味](approved-create.md#結果の種類と意味)」）。UPDATE で加わる理由は次のとおりです。

| 理由 | 結果 | 意味 |
| --- | --- | --- |
| `RECORD_ID_MISMATCH` | `UNKNOWN` | 成功の後に取れた ID が、対象の ID と違う（どのレコードが変わったか分からない）。 |
| `UNEXPECTED_FIELD_CHANGE` | `UNKNOWN` | 更新の後の照合で、変えた欄が新しい値でない、または保つ欄・状態の名前の欄・組が変わった（副作用の疑い。成功と偽りません）。 |
| `UPDATE_POSTCHECK_UNDETERMINED` | `PARTIAL` | 更新の後の照合を判定できない（画面が開けない、digest が違う、欄が読めない）。 |

- `UNKNOWN` の後にすることは、登録と同じです（「[UNKNOWN の後にすること](approved-create.md#unknown-の後にすること)」）。テスト環境で、レコードの状態を確かめてください。シナリオは止めず、次の Run も同じレコードを更新できます。

## 上限

登録と同じ名前つきの定数を使います（「[上限](approved-create.md#上限)」）。UPDATE のシナリオにも、同じく効きます。

- 1 回の Run で 1 件、シナリオの累積の上限（既定 20 件。`UNKNOWN` も使った件数）、書き込みの同時実行は 1 つ、同じシナリオの連続は 5 分以上、24 時間に 5 件まで。
- **レコードごとの上限はありません**（同じレコードを何度でも更新できる。二重の更新は、1 回の Run で 1 件、同時に 1 つの枠、実行の許可の 1 回だけの消費、送り手が 1 回だけ送ること、で防ぎます）。

## サイトへの読み込み

- 成功の 1 回の更新で、ログインのほかにサイトへ送る読み込みと書き込みは **6 回**です: 更新の前の読み取り（GET）、書き込みの画面（GET）、更新の POST（と、結果の画面への redirect の GET）、更新の後の読み取り（GET）、照合の READ の対象の画面（GET）、READ（GET）。
- 更新の後の照合で一致しない欄があれば、照合の READ は行いません（結果は `UNKNOWN` に決まるので、要求を増やしません）。
- 送らずに止めた回は 2 回以下です（更新の前の読み取りと、書き込みの画面）。
- どの読み込みも、設定の間隔（`crawl.minNavigationIntervalMs`）を守ります。**読み込み直しはしません。**

## 守りの範囲

- **送る中身の照合**（書き込みの段の Guard。登録と同じ守りに加えて）: 保つ欄の値、状態の名前の欄の値、組の hidden の値と checkbox のチェックの状態、hidden・readonly・見えない欄の値（`lock_version` など。見えない checkbox・radio・select を含む。更新の前に読んだ値と完全に一致。ページが作る値の名前の閉じた一覧に当たる欄は名前だけ）、disabled の欄が送られないこと、`_method` の値（承認した候補の上書きと完全に一致。`DELETE` は送りません）を照らします。チェックしていない checkbox・選んでいない radio は、送られないことを照らします。外れたら送りません（`BLOCKED`・`PAYLOAD_MISMATCH`）。ページの JS が送信の前に状態の欄を変える、`_method` を `DELETE` にする、組の checkbox を外す、`deleted=1` のような欄を足す、のどれでも、更新の要求はサイトに届きません。
- **前の値の確かめ**: 書き込みの段の画面の値が、更新の前に読んだ値と違えば、入力の前に止めます（`BLOCKED`・`PRECHECK_FAILED`）。入れた後と押す直前にも、変える欄でない値が前の値のままかを確かめます。
- **変える欄の前の値の上限**: 変える欄の前の値が 8,192 文字（`MAX_SUBMITTED_VALUE_LENGTH`）を超えるときは、証拠に書けないので送りません（`BLOCKED`・`PRECHECK_FAILED`）。
- **送る直前の確かめ直しと撤回**: 登録と同じです（「[守りの範囲](approved-create.md#守りの範囲)」）。撤回とシナリオの変更のときは、親が、そのシナリオの動いている書き込みのジョブに止める合図を送ります。
- **記録**: 資格情報、Cookie、CSRF のトークン、hidden の値、readonly の値、保つ欄の値、`lock_version` は、管理データ・成果物・ログ・ワーカーとの通信に残しません。前の値として記録するのは変えた欄の値だけです。

## API の更新

ページのスクリプトが API の要求（`PATCH`）で更新する画面の、API のシナリオ（送り方「API の要求」。「[API のシナリオ](scenario-approval.md#api-のシナリオ)」）の更新です。対象の選び方、上限、件数の予約、送る直前の確かめ直し、`UNKNOWN` の後にすることは、form の更新と同じです。手順は「[実テスト環境の手順の API の更新](real-test-environment.md#11-api-の更新)」にもあります。

> テスト用の小さなサイトで、両方の Chromium で確かめています。実際のテスト環境では、まだ確かめていません。

### form の更新との違い

| 項目 | form の更新 | API の更新 |
| --- | --- | --- |
| 候補 | 分類が `UPDATE` の form | 送らずに観察した型が `API_UPDATE`（`PATCH`、filter がちょうど 1 つの `eq` で、値が画面の path の最後の ID と同じ）の候補。「API のシナリオを作る（PATCH <path の型>）」から作ります |
| 対象の結び付け | 送信先の path の `{id}` | filter の値（`eq.<対象の ID>`）。Guard が完全に一致することを照らします |
| path の型 | 更新の画面と送信先の 2 つの型 | 更新の画面の path の型 1 つ（`{id}` は画面の path の最後の ID の区切り） |
| 欄の役割 | 見えていて編集できる欄ごとに、変える・保つ | 目印を入れた欄の鍵ごとに、変える・保つ（既定は保つ。メールと電話も既定で保つ。変える欄は 1 つ以上） |
| 保つ欄の照合 | 前の値のまま送ることを照らす | 本文にあれば前の値と完全に一致することを照らし、本文になければ通します（`PATCH` で送らない欄は変わらない扱いで、後の照合で確かめます）。前の値は、台帳が知る値（BeakSight が送った値）とも比べ、違えば送りません |
| 台帳 | 同じプロファイルの登録のシナリオ | 同じ送り先（API の Origin と path の型）の API の登録のシナリオだけ |
| ページが決める鍵 | — | 更新の画面の欄として識別できる鍵だけを許し、前の値と照らします（識別できない鍵を持つ型は作れない。`SCENARIO_API_PAGE_KEY_NOT_IDENTIFIABLE`）。値は記録しません |
| 検証の指定 | 成功の条件、入力の誤りの条件、ID の取り方、照合の READ | 照合の READ だけ（`{id}` の型の画面の READ。生成した値と比べる期待が要る。「[API の検証の指定](approved-create.md#api-の検証の指定)」） |
| 結果の判定 | 成功・入力の誤りの条件 | 応答の HTTP の状態（「[API の結果の判定](approved-create.md#api-の結果の判定)」）と、下の更新だけの理由 |
| 前後の画面の確かめ | 型にした識別の digest と規則の digest | 画面の path を型にした識別の digest（path の最後の ID が対象の ID） |

### 台帳の ID と filter の結び付け

台帳のレコードの ID で、更新の行を選べることを、保存と実行の許可の発行で確かめます。

- 台帳にできるのは、API の登録のシナリオで、送り先が更新と同じ（API の Origin と path の型が同じ。同じ表）ものだけです。違えば `SCENARIO_API_FILTER_NOT_BOUND_TO_LEDGER_ID` です。シナリオの画面の台帳の選択肢も、下の結び付けに合う登録のシナリオだけに絞られます。

- 台帳の登録のシナリオが、登録の ID を応答の本文の鍵から取るとき: その鍵の名前が filter の名前と同じであることを求めます（違えば `SCENARIO_API_FILTER_NOT_BOUND_TO_LEDGER_ID`）。**この形が確実です。**
- 台帳が URL の型から ID を取るとき: 台帳の型と更新の画面の型で、`{id}` の位置（区切りの番号）と、`{id}` より前の区切りがすべて同じであることを求めます。後ろの区切りは違ってよい（例: `/admin/members/{id}` と `/admin/members/{id}/edit`）。
- 台帳が画面の要素から ID を取るとき: 更新の画面の `{id}` が、最後の ID の区切りであることを求めます。
- 合わなければ `SCENARIO_UPDATE_PATH_NOT_BOUND_TO_LEDGER_ID` です。保存の後に台帳の取り方が変わったときも、許可の発行で止めます。

### 実行の流れ（API の更新）

1. **前の読み取り**（`GET`）: 凍結した Context で、対象の ID の更新の画面を 1 回読みます。画面の path を型にした識別で承認した候補がちょうど 1 つあり、その path の最後の ID が対象の ID であることを確かめます。変える欄・保つ欄・ページが決める鍵の欄の今の値を、落ち着くまで待って読みます（メモリの中だけ）。
   - **値の落ち着きの待ち**（前の読み取り・書き込みの画面・押す直前の読み直し・後の照合で同じ）: ページの要求が止んで（読み込み中の要求がなく、500 ミリ秒静か）、欄の値が続けて 2 回同じになってから読みます。要求が止むのを待つのは最大 3 秒（`API_WRITE_VALUE_QUIET_TIMEOUT_MS`）で、開いたままの要求があるページは、3 秒の後に、欄の値を 0.5 秒（`API_WRITE_VALUE_SETTLE_INTERVAL_MS`）おきに読み、続けて 2 回同じなら進みます（最大 10 回。`API_WRITE_VALUE_SETTLE_MAX_READS`。落ち着かなければ送らない）。同じ Run の残りの読み取りでは、3 秒の待ちを省きます。テスト用のサイトでは、開いたままの要求がある画面の更新の 1 回に、約 14 秒かかりました。
   - **目印の欄がすべて空なら送らない**: 目印を入れた欄（変える欄と保つ欄）の値がすべて空なら、値が入る前の画面とみなして送りません（`BLOCKED`、`PRECHECK_FAILED`）。
   - **保つ欄は、台帳が知る値と比べる**: 親が、対象のレコードについて、照合済みの登録で送った値に、照合済みの更新で送った値を時刻の順に重ね、保つ鍵ごとに最後に分かっている値（空を含む）を求めてワーカーに渡します（BeakSight が作ったテストの値だけです）。前の読み取りか押す直前の読み直しで、保つ欄の値がこの値と違えば送りません（`BLOCKED`、`PRECHECK_FAILED`）。値が入る前の仮の値（「読み込み中」など）を出す画面と、BeakSight の外（テスト環境の画面で人が変えるなど）で保つ欄の値が変わったレコードは、ここで止まります。外で変わったレコードは更新できないので、新しく登録してから更新します。これは API の更新だけの決まりです（form の更新は、前の値を台帳と比べません）。
   - **止めた具体的な理由**: 送る前の確かめで止めた（`PRECHECK_FAILED`）ときは、`action-run.json` の任意の項目 `precheckDetail` に、具体的な理由（台帳が知る保つ値と違う `KNOWN_KEPT_VALUE_MISMATCH`、目印の欄がすべて空 `PRIOR_VALUES_EMPTY`、前の値と違う `PRIOR_VALUE_CHANGED`、前の値を使えない `PRIOR_VALUE_UNUSABLE` など。一覧は `src/control/actions/action-contracts.ts` の `PRECHECK_FAILURE_DETAILS`）を残します。ジョブの画面の欄「送らずに止めた理由」に、説明と次にできることを出します。送る・送らないの判定は変わりません。前に書いた記録は項目を持ちません。
   - 限界: 台帳が知らない保つ欄（登録で送らなかった欄）は、台帳の値と比べられません。その欄だけをページのタイマーで遅れて入れる画面は、見分けられないことがあります。
2. **書き込みの画面**（`GET`）: 更新の画面を開き直し、値が前の値と同じかを確かめます（違えば送らない）。変える欄にだけ値を入れます。押す直前（送る直前の確かめ直しの前）に欄を読み直し、保つ欄とページが決める鍵の欄が前の値のまま、変える欄が入れた値のまま、保つ欄が台帳が知る値のままでなければ押しません。読み直しの後にページが値を変えても、送る瞬間に Guard が前の値と照らして止めます。
3. **送信**（`PATCH` 1 回）: 2 段の窓で、Guard が承認した型、filter の値、変える鍵の生成した値、本文にある保つ鍵とページが決める鍵の前の値、承認の外の状態の鍵がないこと（`BODY_STATE_KEY_UNEXPECTED`）を照らし、一致した 1 回だけを BeakSight の送り手が送ります。ページが保つ値や filter を書き換えると、送りません。
4. **判定**: 応答の状態で判定します。登録の ID は対象の ID とします（応答が 204 で本文がなくても、ID が取れないことにはなりません）。
5. **後の照合**（`GET`）: 書き込みの段を閉じた後、凍結した Context で更新の画面を 1 回読み直し（同じ落ち着きの待ち）、変えた欄は新しい値、保つ欄とページが決める鍵の欄は前の値であることを、欄ごとに照らします。保つ欄が台帳が知る値と違えば、照合できない（`UPDATE_POSTCHECK_UNDETERMINED`）です。
6. **照合の READ**（`GET`）: 後の照合で一致しない欄がなければ、`{id}` に対象の ID を入れた画面を 1 回読みます。

- 成功の 1 回で、ログインのほかにサイトへ送る読み込みと書き込みは **5 回**です（前の読み取り、書き込みの画面、`PATCH`、後の照合、照合の READ）。読み取りでない要求は `PATCH` の 1 回だけです。どの読み込みも、設定の間隔を守ります。

### 登録してから更新する

更新のシナリオの画面「書き込みを始める」から、1 回の操作で、台帳の登録のシナリオの書き込み（登録 1 回）と、続けて更新のシナリオの書き込み（更新 1 回）を行えます。続けて始める決まりは画面のサーバが持ち、ワーカーと Guard は変わりません。form の更新のシナリオでも同じ作りです。手順は「[実テスト環境の手順の登録してから更新する](real-test-environment.md#115-登録してから更新する)」にもあります。

- **ボタンが出るとき**: 更新の対象にできる照合済みのレコードがない（許可の発行の `TARGET_RECORD_UNAVAILABLE` にあたる）か、最新のレコードで前の更新が照合済みにならずに止まったとき。注意「登録してから更新する」とボタン「登録してから更新する」が出ます。
- **ボタンが出ないとき**: 更新の予定のレコードがあり、前の更新が止まっていないとき。注意が出ても、台帳の登録のシナリオか更新のシナリオのどちらかが今は始められないとき（承認、検証の指定、上限、間隔、許可の確かめ。更新のシナリオは対象のレコードのほかの確かめで見ます）は、ボタンを出さず、始められない旨を出します。
- **確認のダイアログ**（「登録してから更新しますか」）: 「1 回目: 登録（シナリオ <id>）」と「2 回目: 更新（シナリオ <id>）」を、それぞれの送り先と累積の残り（上限）とともに出します。更新するレコードは「1 回目で登録して照合済みになったレコード」です。
- **何も始めずに拒むとき**: `CHAIN_NOT_OFFERED`（使う場面でない）、`CREATE_NOT_STARTABLE`（登録のシナリオが始められない）、`UPDATE_NOT_STARTABLE`（更新のシナリオが始められない、画面の版が古い）。
- **続けて更新を始める条件**: 登録のジョブの結果が照合済み（`VERIFIED`）で、登録の ID が記録にあり、更新の予定の対象がその ID と同じとき。予定の ID を許可の発行に渡して、更新のジョブを始めます。始めないときの理由は、`CREATE_NOT_VERIFIED`（登録が照合済みにならなかった）、`CREATE_RECORD_ID_MISSING`（登録の ID が記録にない）、`PLANNED_TARGET_MISMATCH`（予定の対象が登録したレコードと違う）、`UPDATE_START_REJECTED`（更新の許可の発行かジョブの開始が拒んだ）、`CREATE_WAIT_TIMEOUT`（登録のジョブが 60 分の中で終わらなかった）です。登録のジョブの画面の「続けて更新する予定」に、状態と理由が出ます。
- **予定はメモリの中だけ**: 管理データに書きません。画面のサーバが止まれば、予定は消え、更新は始めません（安全側）。
- **別々の許可と上限**: 登録と更新は別のシナリオなので、別々の実行の許可・件数の予約・上限を使います（同じシナリオの間隔には当たりません）。
- **ログインと待ち**: ログインは、登録と更新のそれぞれのジョブで行います。
  - 手動のログインのプロファイルでは、待ちはありません。登録と更新のそれぞれで、人がログインします。
  - 自動ログインのプロファイルでは、自動ログインどうしの 5 分の間隔（`AUTO_LOGIN_MIN_INTERVAL_MS`）があるので、登録のすぐ後の更新は、開始の前の確かめで止まります（`AUTO_LOGIN_RATE_LIMITED`。次に始められる時刻つき）。このときだけ、状態を「自動ログインの間隔を待っています（待った後に続けて更新します）」（`WAITING_LOGIN_INTERVAL`）にし、次に始められる時刻（ふつうは約 5 分後）まで待ってから、開始の前の確かめと実行の許可の発行をやり直し、更新を 1 回だけ始めます。許可は待った後にだけ出します。次に始められる時刻が 10 分（`WRITE_CHAIN_LOGIN_WAIT_LIMIT_MS`）より先なら待たず、更新は始めません（`UPDATE_START_REJECTED`）。ほかの理由で始められないときも、待たずに始めません。間隔の決まりは変わりません。
  - 待つ間は、登録のジョブの画面の「続けて更新する予定」に「更新を始め直す時刻」が出て、画面は読み直しを続けます。
  - 待つ間に別のジョブを始めると、やり直しの確かめで止まり、更新は始まりません（やり直しは 1 回だけ）。待つ間に画面のサーバを止めると、予定が消え、更新は始まりません。

### 更新だけの結果

| 場面 | 結果 | 理由 |
| --- | --- | --- |
| 後の照合で一致しない欄がある（サーバの副作用、204 で何も変わっていない、など） | `UNKNOWN` | `UNEXPECTED_FIELD_CHANGE` |
| 2xx で、応答の本文が空の一覧 `[]`（更新した行がない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
| 2xx で、応答の本文が 2 行以上の一覧（どの行が変わったか分からない） | `UNKNOWN` | `MULTIPLE_CONDITIONS_MATCHED` |
| 2xx で、応答の本文が空でなく、1 MiB を超えるか JSON として読めない（行の数が分からない） | `UNKNOWN` | `NO_CONDITION_MATCHED` |
| 応答の本文の ID の鍵の値が、対象の ID と違う | `UNKNOWN` | `RECORD_ID_MISMATCH` |
| 後の照合を読めない | `PARTIAL` | `UPDATE_POSTCHECK_UNDETERMINED` |

- 証拠は form の更新と同じ形です（上の「[証拠と記録](#証拠と記録)」）。変えた欄は前の値と新しい値を記録し、保つ欄とページが決める鍵は一致の真偽だけを記録します。ページが決める鍵の値は、更新では残しません。
- 限界: filter の値と query の名前は、URL の percent-encode を戻した後で比べます。filter の列の名前は確かめられません（人がテスト環境の API の定義で確かめます。シナリオの画面に注意が出ます）。

## 確かめていないこと・使えないこと

- **確かめ直しの後の撤回**: 送る直前の確かめ直しの答えを受けてから、更新の要求がサイトに届くまでの短い間に撤回やシナリオの変更をしたときは、更新を送ります（登録と同じ。「[確かめていないこと](approved-create.md#確かめていないこと使えないこと)」）。
- **前の値がない変えた欄**: 空の値として記録します（「値がなかった」と「空の値だった」を区別しません）。
- **名前だけを照らす欄**（ページが作る値の名前の閉じた一覧。CSRF のトークンなど）: 値を読まないので、名前だけを照らします。ページの JS がその値を書き換えて送っても、送る中身の照合では見つけられません（秘密を読まない・残さないことを優先した限界）。`token` の語に当たる `auth_token`・`access_token`・`api_token` なども、この一覧に当たるので名前だけを照らします（同じ限界）。一覧の外の秘密に見える名前の hidden・readonly・見えない欄（`SCENARIO_FORM_HAS_UNREADABLE_SECRET_FIELD`）や、秘密に見える名前の見える欄がある画面は、そもそも受けません（上の「UPDATE の指定」）。
- **読み込みのたびに値が変わる、秘密に見えない名前の hidden がある画面**（時刻や要求の番号など）: 更新の前の読み取りの値と照らすので、更新は止まります（止める側）。ページが作る値の名前の閉じた一覧に当たる欄（`nonce`・CSRF のトークンなど）は名前だけを照らすので、値が変わっても止まりません。
- **値を照らす欄が同じ名前で 2 つ以上ある画面**: 止まります。**見えない checkbox・radio・select** も、値を照らします（checkbox・radio はチェックの状態と値、select は選んだ値）。
- **前の値に人の値が入る**: 上の「証拠と記録」のとおり、ほかの更新者が入れた値も、変えた欄の前の値として平文で記録され、画面に出ます。
- **レコードによって選択肢などが変わる画面**: 規則の digest が承認した候補と違うので、止まります（止める側）。
- **同じ値の区切りが 2 つ以上ある path**（例 `/users/12/items/12/edit`）: どの区切りが ID か決められないので、止まります。
- **ID の後ろに区切りを持つ送信先**（例 `/members/{id}/update`）: 登録の ID を path の型（例 `/members/{id}`）から取る台帳では、送信先の型の `{id}` の後ろの並びが台帳の型と同じでなければならないので、結び付かず、UPDATE のシナリオにできません（`SCENARIO_UPDATE_PATH_NOT_BOUND_TO_LEDGER_ID`）。違うレコードへ書き込まないための、止める側の限界です。
- **サーバが値を整形する画面**（前後の空白を除く、大文字にするなど）: 完全な一致で比べるので、止まるか `UNKNOWN` になります。必要なら、後で正規化の閉じた一覧を足します。
- **サーバの側の通知**、**ブラウザと完全には同じでない要求**、**HTTP/2 だけを話すサイト**: 登録と同じです。
- **実際のテスト環境**: まだ接続して確かめていません。
