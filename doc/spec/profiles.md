# 監査プロファイル

サイトと環境ごとに、監査の方式（監査モード）を選ぶための「監査プロファイル」の形と決まりです。

[README に戻る](../../README.md)・[仕様の索引](README.md)

> 監査プロファイルは、管理画面（「[管理画面（ローカル）](local-ui.md)」）の「サイトを足す」で登録し、管理データ（SQLite）に保存します。管理画面からの監査、操作の候補の発見、READ の確かめ、書き込みは、すべてプロファイルから始めます。
>
> 画面では、プロファイルは「点検するサイト」（短く「サイト」）、監査は「点検」と出ます。ほかの語の対応は「[画面の語と文書の語](local-ui.md#画面の語と文書の語)」にあります。
>
> CLI（`run`、`validate-config`）は、プロファイルを読みません。監査の対象の設定のファイル（ターゲット JSON。「[監査の対象の設定](configuration.md)」）だけで、公開の監査（`PUBLIC_PASSIVE`）を行います。

## 監査プロファイルとは

監査プロファイルは、1 つのサイトの 1 つの環境（本番の公開の環境か、テスト環境か）について、どの監査モードで監査するかを決める JSON の文書です。
管理画面で登録すると、管理データに保存します。ターゲット JSON とは別の文書で、ターゲット JSON を相対パスで参照します。

- ターゲット JSON には、監査モードを書けません（下の「[旧ターゲット JSON の扱い](#旧ターゲット-json-の扱い)」）。
- 本番とテスト環境は、別のプロファイルにします。
- URL の文字列や名前（`test`、`staging` など）だけで、BeakSight がテスト環境と見なすことはありません。テスト環境かどうかは、プロファイルの `environment` と、環境の確認の参照（`environmentEvidenceRef`）で決めます。

## 管理画面でのプロファイルの作り方

左のメニューの「サイトを足す」で作ります。作成の画面に見える入力は、次の 3 つだけです。

1. 「開始のアドレス」（必須）: 監査を始める画面の URL。テスト環境では、ログインの後の管理画面の URL です。
2. 「使い方」: 「ログインが必要なサイト」（既定。`TEST`・`TEST_AUTH_PASSIVE`・`MANUAL_SESSION`）か、「ログインしなくても見られるサイト」（`PUBLIC`・`PUBLIC_PASSIVE`・`NONE`）。
3. ボタン「点検を始める」（1 つだけ）: 保存に続けて、同じ押下で入口の確かめ（画面では「サイトの下調べ」）を 1 回始め（「[入口の確かめ](authenticated-audit.md#入口の確かめ)」。ログインしないで開始の URL を 1 回 `GET`）、そのジョブの画面へ移ります。下調べが終わると、続けて点検（ログインが必要なサイトはまとめて実行、ログインしなくても見られるサイトは公開の監査）を始めます。ボタンの下に「押すと、サイトを下調べしてから点検を始めます。ログインの画面が開いたら、いつもどおりログインしてください。次からは BeakSight がログインします。」（ログインしなくても見られるサイトは「押すと、サイトを下調べしてから点検を始めます。」）が出ます。入口の確かめを始められなかったときは、プロファイルは保存したまま、プロファイルの詳細へ移り、理由と「サイトの下調べをやり直す」の案内が出ます。

- 隔離の扱いは、画面のどこでも聞きません（責務の外です。テスト環境のアドレスは、利用者が入れたものを使います）。テスト環境のプロファイルには、保存した日付で、「確かめていない」の固定の形の参照 `isolation-unverified-<YYYYMMDD>` を BeakSight が入れます（下の「[`environmentEvidenceRef`](#environmentevidenceref)」）。画面には出しません。
- 作成の画面には、名前・設定のファイル・許可 Origin・環境・監査モード・認証の方式などの欄はありません（前の「詳しい設定」の欄は外しました）。どれも下の決め方で BeakSight が決めます。作った後は、プロファイルの詳細の「詳しい内容」のサイトの設定（プロファイルの編集）で直せます。

自動ログインと書き込みには、同じプロファイルを使います。自動ログインへは、1 回目の点検で手でログインした後に、BeakSight がそのとき入れた ID とパスワードを保存して切り替えます（「[自動ログインの手順](automated-login.md#手順)」）。書き込みには、点検の後のプロファイルの詳細の一覧「登録・更新を試せる画面」で画面にチェックを入れると、その保存が、同じプロファイルの監査モードを `TEST_APPROVED_WRITE` にします（「[登録・更新を試せる画面](local-ui.md#登録更新を試せる画面)」）。別のプロファイルを作って、同じ値を写すことはしません。

### BeakSight が決める値

ほかの値は、BeakSight が次の決め方で決めて保存します（作成の画面には欄がありません）。

| 値 | 決め方 |
| --- | --- |
| 名前（`profileId`） | 開始の URL のホスト名を、名前の決まり（小文字の英数字とハイフン）に合う形に直したもの。今あるプロファイル（取り消したものを含む）と重なれば `-2`、`-3` を付けます。 |
| 設定のファイル | 「対象のサイトの設定」の既定は「開始の URL から決める」です。同じ開始の URL（Origin と path）の設定のファイルが `config/targets/`・`local/targets/` にちょうど 1 つあれば、それを使います（中身は変えません）。同じサイト（開始の URL の Origin を `site.allowedOrigins` に含む）の設定のファイルがなければ、新しく作ります（下の「[作るファイル](#作るファイル)」）。次のときは、何も保存せずに止め、理由と候補のファイルを出します。保存の拒否の知らせの中の「どれを使いますか」で、使うファイルか「開始のアドレスから新しく作る」を選んで、もう一度保存します。<br>・同じ開始の URL の設定のファイルが 2 つ以上ある。<br>・同じサイトの設定のファイルはあるが、どれも別の開始の URL のもの（「同じサイトの設定のファイルが、別の開始の URL であります。…」）。「開始の URL から新しく作る」を選ぶと、いつも新しく作ります。 |
| 許可 Origin | 新しく作るとき、開始の URL の Origin 1 つ。作成の画面では、ほかの Origin を足せません（既知の制限）。ほかの Origin も読むときは、作った設定のファイルの `site.allowedOrigins` を直します。 |
| テスト環境の Origin | テスト環境のモードのとき、許可 Origin を写します（すでにある設定のファイルを使うときは、そのうちの開始の URL の Origin）。 |
| 環境・監査モード・認証の方式 | 「使い方」の 2 択から決まります。作成でも編集でも、認証の方式を自動ログインにする保存は拒みます。自動ログインへは、手動のログインの後の切り替えだけで入ります（下の「[自動ログインへの入り方と、変えられない値](#自動ログインへの入り方と変えられない値)」）。ログインの希望（`loginPreference`）は省きます（自動ログイン）。 |
| 承認したサービスの Origin | 作成の画面にはありません（空で保存します）。手動のログインの観察だけが足します（下の「[`approvedServiceOrigins`](#approvedserviceorigins)」）。 |

- 開始の URL は、設定のファイルと同じ決まり（`http:` か `https:`、利用者名とパスワードを含まない）で確かめます。fragment（`#` の後）も持てません。

### 作るファイル

- 新しく作るときは、`local/targets/<名前>.json` を作ります。中身は、`target.id`（名前）、`site.startUrl`、`site.allowedOrigins`、負荷（`crawl`）と出力（`output`）です。負荷は、最初の監査のための控えめな値で作ります。ページの上限（`crawl.maxPages`）は 3、ページの読み込みの間隔（`crawl.minNavigationIntervalMs`）は 10 秒（`10000`）です（`GENERATED_TARGET_CRAWL_LIMITS`）。ほかの負荷の項目と出力は既定値です（「[既定値](configuration.md#既定値)」）。CLI の既定値（ページの上限 500、間隔 5 秒）は変わりません。
- **読む範囲を広げるときは、作ったファイルを直します。** `crawl.maxPages` と `crawl.minNavigationIntervalMs` などを、サイトの運営者と決めた値にします（「[サイトへの負荷](site-load.md)」）。ページの上限・時間の上限・読み込みの間隔の 3 つは、プロファイルの詳細の「詳しい内容」の「監査の負荷」（画面では「点検の負荷」）でも変えられます（「[管理画面](local-ui.md#サイトへの負荷の決まり)」）。ほかの項目は、画面からは変えられません。ファイルを直したら `node dist/cli/index.js validate-config --config local/targets/<名前>.json` で確かめます。
- 同じ名前のファイルがあれば、上書きせずに止めます（`TARGET_CONFIG_EXISTS`。プロファイルも作りません）。名前は、`local/targets/` にすでにあるファイルの名前を避けて決めます。
- 名前が Windows の予約名（`con`、`nul`、`aux`、`prn`、`com1`〜`com9`、`lpt1`〜`lpt9` など。大文字と小文字を問いません）に当たるときは、止まらずに、BeakSight が末尾に番号を付けた名前（`con-2` など。すでにある名前は避けます）にして作ります（作成の画面に名前の欄はないためです）。
- 置き場所のフォルダ（`local` か `local/targets`）が、ほかの場所へのリンク（junction・シンボリックリンク）か、フォルダでないときは、何も書かずに止まります（`TARGET_CONFIG_LOCATION_UNSAFE`。プロファイルも作りません）。フォルダがなければ作り、作った後にもう一度確かめます。
- 書く前に、プロファイルの決まりと設定の決まりで確かめます（合わなければ `TARGET_SITE_INVALID` か `TARGET_CONFIG_INVALID`。ファイルは作りません）。書いた後に読み直してから、プロファイルを保存します。プロファイルの保存に失敗したときは、作ったファイルの中身が同じときだけ消します（途中にリンクがあれば消しません）。
- ファイルは、一時のファイルに書いてから、ハードリンクで置きます（同じ名前のファイルを上書きしないため）。ハードリンクを張れない置き場所（`local/targets/` のフォルダ）では、書けずに止まります（`TARGET_CONFIG_WRITE_FAILED`。プロファイルも作りません）。

### 欄の出し分けと初めの値

- 作成の画面は、上の 3 つの入力だけです（設定のファイルが決まらないときだけ、拒否の知らせの中に「どれを使いますか」の選択が出ます）。
- プロファイルの編集（プロファイルの詳細の「詳しい内容」の中）では、次のとおりです。
- 「監査モード」を選ぶと、「環境」と「認証の方式」の初めの値を、受ける組み合わせ（下の「[受ける組み合わせ](#受ける組み合わせ)」）に合わせます。
- 「テスト環境の Origin」の欄は、テスト環境のモード（`TEST_AUTH_PASSIVE`・`TEST_APPROVED_WRITE`）のときだけ出します。
- 「テスト環境であることを確かめた記録の参照」の欄は、環境がテスト環境（`TEST`）のときだけ出します（公開の監査のモードで環境をテスト環境にしたときも出ます）。
- 隠した欄の値は送りません。隠した欄に関わる保存の誤りは、フォームの上に出します。

### 保存の後

- 保存すると、入口の確かめのジョブの画面へ移ります。入口の確かめがログインの画面を見つけると、BeakSight が認証の設定を案で保存し、続けて点検（まとめて実行）を始めて、その作業の画面へ移ります（「[入口の確かめ](authenticated-audit.md#入口の確かめ)」）。点検を続けて始めなかったとき（ログインの画面に見えない、案を保存できない、など）は、プロファイルの詳細へ移り、要点に何が起きたか（「サイトの下調べが終わりました。…」）と理由が出ます。ログインしなくても見られるサイトは、入口の確かめの後に、公開の監査を続けて始めます。
- **1 回目の点検**: ログインが必要なサイトでは、開いたブラウザで手で 1 回ログインします。その後に、BeakSight がそのとき入れた ID とパスワードを保存し、プロファイルを自動ログインに切り替えます（「[1 回目の手でのログインから切り替える](automated-login.md#1-回目の手でのログインから切り替える)」）。
- **プロファイルの詳細の形**: 上から、要点（見出し「今の様子」。今の状態の 1〜2 文）、主のボタン 1 つ（と、あれば同じ行の右に二次のボタン 1 つ）、一覧「登録・更新を試せる画面」（操作さがしを使うプロファイルだけ。「[登録・更新を試せる画面](local-ui.md#登録更新を試せる画面)」）、たたんだ「詳しい内容」1 つです。主のボタンは、プロファイルの今の段で 1 つに決まります（判定は `apps/local-ui/src/display/next-steps.ts` の `profileStageOf` の 1 か所。サイトの一覧の行も同じ判定です）。押せないときは、ボタンを出さずに、理由や「◯◯ から始められます。」を要点に出します。

  | 段（今の状態） | 主のボタン | 二次のボタン |
  | --- | --- | --- |
  | 認証の設定がまだない（入口の確かめがまだ・失敗） | 「サイトの下調べをやり直す」（今始められるときだけ） | — |
  | 入口の確かめの案から認証の設定を作れなかった | 「ログインの設定を開く」 | — |
  | 認証の設定が古い・誤りがある | 「ログインの設定を開く」 | — |
  | 自動ログインの資格情報がない・入れ直しが要る | 「ID とパスワードの画面を開く」 | — |
  | 自動ログインの間隔の中 | なし（「◯◯ から始められます。」。最新の点検の報告があれば「結果を見る」） | — |
  | 自動ログインを止めている（停止の hold） | なし | 「自動ログインの停止を解く」（ログインの確かめの画面。画面の題は「自動ログインの再開」） |
  | ほかの理由で始められない | なし | — |
  | 監査を始められる（1 回目。公開・手動のログイン・自動ログインの最初の点検） | 「点検を始める」 | — |
  | ほかに進む段がなく、最新の点検の報告がある | 「結果を見る」 | 「点検を始める」 |
  | ほかに進む段がなく、報告がない | 「点検を始める」 | — |

- 前の「次から自動でログインする」「書き込みも試す」「書き込みの手順へ」の段は、なくしました（設計書 `doc/design/2026-10-27-beaksight-one-pass-flow-design.md` の 4.1 の D5・D7、4.1.1）。書き込みのモードのプロファイルも、ほかと同じ段で進みます。点検を終えて移ってきた直後は、どの段でも主のボタンが「結果を見る」になり、表の主のボタンは二次のボタンになります。
- **詳しい内容**: 監査モードと認証の方式（画面では「点検のしかた」「ログインのしかた」）、「ほかの画面」への入口（「サイトの下調べをやり直す」、「ログインの設定を開く」、「ID とパスワードの画面を開く」、「操作さがしの結果を見る」、「見るだけの確かめを開く」、「書き込みの手順へ」、「作ったデータの一覧を開く」など。主のボタン・二次のボタンと同じものは出しません。どれもふだんの流れでは開きません）、「表示の設定」、「点検の負荷」、サイトの設定（プロファイルの編集。「毎回手でログインする」を含む）、「このサイトの登録を取り消す」が入ります。
- **ログインの確かめ（`LOGIN_CHECK`）は、ふだんの流れから外しました。** 画面からログインの確かめのジョブを始める道はありません。自動ログインのプロファイルでは、監査の最初の自動ログインが、ログインできるかの確かめを兼ねます。ログインに失敗すると、監査は止まり、ジョブの画面に理由が出ます。ログインの確かめの画面は、自動ログインを止めたとき（停止の hold）に、確かめてから停止を解く入口（「確かめたので再開する」）としてだけ残ります。
- **書き込みのモードへの切り替え**: 一覧「登録・更新を試せる画面」で画面に初めてチェックを入れると、その保存が、監査モードを `TEST_APPROVED_WRITE` にしたプロファイルの次の改訂を保存し、認証の設定をその改訂に結びつけ直します（中身は変えないので、認証の設定の保存し直しは要りません）。確認のダイアログと、隔離の扱いの選択はありません（隔離の参照は、今の「確かめていない」の参照のままです）。資格情報・承認したサービスの Origin・設定のファイルは、同じプロファイルのものをそのまま使います。切り替えの前の発見の結果は、そのまま一覧の行とシナリオの下書きに使えます（切り替えのほかにプロファイルを変えていなければ、発見のやり直しは要りません）。戻すボタンはありません（詳しい内容のプロファイルの編集で直せます）。
- 承認したサービスの Origin は、プロファイルの詳細の「詳しい内容」（プロファイルの編集）に、読むだけの一覧と「消す」だけを出します（足す欄はありません。下の「[`approvedServiceOrigins`](#approvedserviceorigins)」）。
- **作業の後に自動で移る**: 入口の確かめ・監査・まとめて実行（書き込みの段を含む）のジョブが成功で終わると、ジョブの画面から次の画面（続けて始めた点検の作業か、プロファイルの詳細）へ自動で移ります。監査は、一部のページを見られなかったときも移り、移ったプロファイルの詳細の主のボタンは「結果を見る」になります。失敗、安全の違反、書き込みの結果が分からない（`UNKNOWN`）、ページが出した送信を通した監査、利用者が止めたときは移らず、ジョブの画面に理由と次にすることを出します（「[監査の実行](local-ui.md#監査の実行)」）。

### 自動ログインへの入り方と、変えられない値

資格情報を、人が手動のログインで観察していない送信先へ送らないための決まりです（画面のサーバと管理データの保存の部品が拒みます）。

- **自動ログインへは、切り替えだけで入ります。** 1 回目の点検の手でのログインの後の切り替え（「[1 回目の手でのログインから切り替える](automated-login.md#1-回目の手でのログインから切り替える)」）と、ふだんの流れの外の ID とパスワードの画面からの切り替えのほかに、自動ログインへ入る道はありません。作成でも、詳しい内容のプロファイルの編集でも、認証の方式を自動ログイン（`AUTOMATED_LOGIN`）にする保存を拒みます。今ある自動ログインのプロファイルを、方式を変えずに保存すること、編集で手動のログインへ戻すことは受けます。
- **自動ログインのプロファイルでは、ログインの送信先を変えられません。** 認証の方式が自動ログインのまま、次を変える保存（プロファイルの編集と、認証の設定の保存）を拒みます。
  - ログインの画面の URL、ログインの送り方、token の送信先（Origin・パス・必須の query）、ログインに伴う送信の送信先、フォームの送信先、自動ログインのセレクタ、設定のファイル。
  - 承認したサービスの Origin と、テスト環境の Origin を足すこと（消すことは受けます）。
- 変えたいときは、詳しい内容のプロファイルの編集で手動のログインへ戻し（「[手動のログインへ戻す](automated-login.md#手動のログインへ戻す)」）、手動のログインで 1 回ログインして観察し直してから、もう一度切り替えます。
- 読まないパス、読む範囲のパス、成功の条件、セッションの切れの条件、失敗の条件、上限など、送信先でない値は、自動ログインのままでも直せます。
- **ログインの送信先は、入口の確かめと手動のログインの観察からだけ入ります（認証の方式によりません）。** 手動のログインのプロファイルでも、認証の設定の画面（詳しい内容の「ログインの設定を開く」）の保存で、認証の設定がすでにあるときは、ログインの画面の URL、ログインの送り方、token の送信先（Origin・パス・必須の query）、ログインに伴う送信の送信先、フォームの送信先、自動ログインのセレクタを変える保存を拒みます（理由「ログインの送信先は、入口の確かめと手動のログインの観察からだけ入ります」）。認証の設定がまだないときの最初の保存は、送信先が最後の入口の確かめの案と同じとき（入口の確かめの案がなければ、ログインの画面の URL のほかに送信先のない形のとき）だけ受けます。token の送信先とログインに伴う送信は、手動のログインの後の自動の登録、ログインの段の表の行の「登録する」、行から開いた下書きの保存（行の Origin・パス・必須の query と同じときだけ）が入れます。認証の設定の画面では、認証の設定があるとき、送信先の項目は読むだけで出します。
- ログインの送信先を変えたいとき（サイトのログインの作りが変わったときなど）は、今は、プロファイルを作り直します（作成で入れるのは開始の URL だけです）。既知の制限です。
- 作成・編集の口の判定は、管理データの保存のトランザクションの中で、画面が読んだ改訂と今の改訂を照らしてから、保存してある値に対して行います（同時の別の保存で、判定を抜けられません）。
- サイトの一覧（左のメニューの「点検するサイト」）の行には、名前、点検のしかた、前回の点検（状態と「詳細」）、次にすること（プロファイルの詳細と同じ判定の段の短い文と「続ける」）を出します。監査を始められない行も、段の文で理由が分かります。

## プロファイルの形

```json
{
  "schemaVersion": "beaksight-profile/1",
  "profileId": "example-test",
  "revision": 1,
  "targetConfigPath": "local/targets/example-test.json",
  "environment": "TEST",
  "mode": "TEST_AUTH_PASSIVE",
  "auth": "MANUAL_SESSION",
  "approvedTestOrigins": ["http://127.0.0.1:8080"],
  "environmentEvidenceRef": "isolation-check-2026-10-09"
}
```

`approvedServiceOrigins` と `loginPreference` のほかは、すべての項目が必須です。知らない項目があると、拒否されます。

| 項目 | 意味 |
| --- | --- |
| `schemaVersion` | プロファイルの形の版。`"beaksight-profile/1"` だけを受けます。 |
| `profileId` | プロファイルの ID。 |
| `revision` | プロファイルの改訂の番号。 |
| `targetConfigPath` | 参照するターゲット JSON への相対パス。 |
| `environment` | 環境の種類（`PUBLIC` か `TEST`）。 |
| `mode` | 監査モード（`PUBLIC_PASSIVE`、`TEST_AUTH_PASSIVE`、`TEST_APPROVED_WRITE`）。 |
| `auth` | 認証の方式（`NONE`、`MANUAL_SESSION`、`AUTOMATED_LOGIN`）。 |
| `approvedTestOrigins` | テスト環境の認証・書き込みのモードで、認証と書き込みを許す Origin の一覧。 |
| `environmentEvidenceRef` | テスト環境が本番から隔離されていることを確かめた記録への、秘密を含まない参照（記録の ID など）。画面で作ったプロファイルは、「確かめていない」の固定の形の参照。ないときは `null`。 |
| `loginPreference` | 任意。ログインの希望（`AUTOMATIC`・`MANUAL_EVERY_TIME`）。省けば `AUTOMATIC`（自動ログイン）。`MANUAL_EVERY_TIME`（画面の名前「毎回手でログインする」）なら、自動ログインのプロファイルでも点検のたびに手でログインし、手でのログインの値を受け取りません。保存した資格情報は消しません。項目のないプロファイルは、そのまま読めます。 |
| `approvedServiceOrigins` | 任意。スクリプトで送るログインの、認証のサービスと API の Origin の一覧（画面の名前「承認したサービスの Origin」）。ないときは空と同じです。手動のログインの観察だけが足します。下の「[`approvedServiceOrigins`](#approvedserviceorigins)」。 |

## 監査モード、環境、認証の方式

監査モード:

| 値 | 意味 |
| --- | --- |
| `PUBLIC_PASSIVE` | 公開の監査。ログインせず、`GET` と `HEAD` だけで観測します（今の BeakSight の監査。「[読み取り専用と安全](safety.md)」）。 |
| `TEST_AUTH_PASSIVE` | テスト環境で、ログインした後の画面を、読み取りだけで監査します（「[認証つきの監査の手順](authenticated-audit.md)」）。 |
| `TEST_APPROVED_WRITE` | テスト環境で、`TEST_AUTH_PASSIVE` の操作に加えて、承認した書き込みの操作を行います。読み取りの監査（読み取りだけ）、書き込みの前の準備（認証の設定、操作の候補の発見、READ の確かめ）、書き込みのシナリオ（作成・変更・承認・撤回）、入力の規則、承認された登録（CREATE）と更新（UPDATE）を使えます。ふつうは、`TEST_AUTH_PASSIVE` のプロファイルの詳細の一覧「登録・更新を試せる画面」で画面にチェックを入れたときに、その保存がこのモードにします（下の「[モードごとに使える操作](#モードごとに使える操作)」）。 |

環境:

| 値 | 意味 |
| --- | --- |
| `PUBLIC` | 本番の公開の環境。 |
| `TEST` | テスト環境。 |

認証の方式:

| 値 | 意味 |
| --- | --- |
| `NONE` | ログインしません。 |
| `MANUAL_SESSION` | 利用者が、BeakSight が開いたブラウザで手でログインした状態を使います（「[認証つきの監査の手順](authenticated-audit.md)」）。 |
| `AUTOMATED_LOGIN` | BeakSight が、保存したテスト用のアカウントの資格情報（ふつうは 1 回目の点検の手でのログインで受け取ったもの）で、ログインの操作を行います（Windows だけ。「[自動ログインの手順](automated-login.md)」）。 |

## モードごとに使える操作

管理画面とジョブの管理は、どのモードのプロファイルで何を使えるかを、1 つの表（`src/control/execution-policy.ts` の `PROFILE_OPERATION_POLICY`）だけで決めます。表にない組み合わせは、始めずに理由を返します（モードが理由なら `MODE_NOT_EXECUTABLE`、認証の方式が理由なら `AUTH_STRATEGY_NOT_EXECUTABLE`）。

| 操作 | `PUBLIC_PASSIVE` | `TEST_AUTH_PASSIVE` | `TEST_APPROVED_WRITE` |
| --- | --- | --- | --- |
| 監査（`AUDIT`） | 使える（`NONE`） | 使える（手動のログインと自動ログイン） | 使える（手動のログインと自動ログイン。読み取りだけ） |
| 認証の設定の保存 | 使えない | 使える（手動のログインと自動ログイン） | 使える（手動のログインと自動ログイン） |
| 資格情報の保存と変更 | 使えない | 自動ログインだけ | 自動ログインだけ |
| ログインの確かめ（`LOGIN_CHECK`。ジョブの種類としては残るが、画面から始める道はない。上の「[保存の後](#保存の後)」） | 使えない（`AUTH_STRATEGY_NOT_EXECUTABLE`） | 自動ログインだけ | 自動ログインだけ |
| 操作の候補の発見（`DISCOVERY`） | 使えない（`MODE_NOT_EXECUTABLE`） | 使える | 使える |
| READ の確かめ（`READ_CHECK`。定義の保存を含む） | 使えない（`MODE_NOT_EXECUTABLE`） | 使える | 使える |
| 書き込みのシナリオ（`SCENARIO`。作成・変更・承認。書き込みの実行ではない） | 使えない（シナリオの画面とサーバの理由は `SCENARIO_MODE_NOT_WRITE`） | 使えない（同じ） | 使える（手動のログインと自動ログイン。「[書き込みのシナリオの承認の手順](scenario-approval.md)」） |
| 承認された登録（`WRITE_CREATE`） | 使えない（`MODE_NOT_EXECUTABLE`） | 使えない（`MODE_NOT_EXECUTABLE`） | 使える（手動のログインと自動ログイン。「[承認された登録の手順](approved-create.md)」） |
| 承認された更新（`WRITE_UPDATE`） | 使えない（`MODE_NOT_EXECUTABLE`） | 使えない（`MODE_NOT_EXECUTABLE`） | 使える（手動のログインと自動ログイン。「[承認された更新の手順](approved-update.md)」） |

- `TEST_APPROVED_WRITE` で使える操作の条件（認証の設定が今のプロファイルの改訂のものであること、自動ログインなら資格情報と上限、Windows だけであること）は、`TEST_AUTH_PASSIVE` と同じです。
- `TEST_APPROVED_WRITE` でサイトへ書き込みの要求を送るのは、承認された登録と更新のジョブだけです（ふだんは、点検のまとめて実行の最後の、チェックした画面の書き込みの段）。ほかの操作（監査、ログインの確かめ、操作の候補の発見、READ の確かめ、シナリオ、入力の規則）で BeakSight が送るのは、ログインの送信と、`GET`・`HEAD`（と、認証の設定で登録した読み取りの手続きの呼び出し）だけです（「[操作の候補の発見と READ の確かめの手順](discovery-and-read-check.md)」）。ほかに、ページが自動でする送信のうち削除と危険な語のほかが、送信の扱い（既定は「削除のほかを通す」）のとおりに届きます（「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」）。
- `TEST_APPROVED_WRITE` の監査（`AUDIT`）は、`TEST_AUTH_PASSIVE` の監査と同じ扱いです。監査の段で BeakSight が書き込みを送ることはありません。ページが自動でする読み取りでない送信は、監査モードによらず、プロファイルの表示の設定の送信の扱い（既定は「削除のほかを通す」）で決まります（「[監査の段の送信の扱い](safety.md#監査の段の送信の扱い)」）。チェックした画面がないときは、開始の画面に「この点検は見るだけで行います（書き込みは送りません）。」を出します。読み取りの監査のために、プロファイルを別に作ることはしません。
- 書き込みのモードから `TEST_AUTH_PASSIVE` に戻すボタンはありません。戻すときは、プロファイルの詳細の「詳しい内容」のプロファイルの編集で、監査モードを直します（改訂が進み、認証の設定の保存し直しと、シナリオの再承認が要ります）。

## 受ける組み合わせ

環境、監査モード、認証の方式の組み合わせは、次の表の行だけを受けます。表にない組み合わせは、すべて拒否します。

| `environment` | `mode` | `auth` | `approvedTestOrigins` | `environmentEvidenceRef` |
| --- | --- | --- | --- | --- |
| `PUBLIC` | `PUBLIC_PASSIVE` | `NONE` | 空 | `null` |
| `TEST` | `PUBLIC_PASSIVE` | `NONE` | 空 | `null` か、空でない文字列（任意） |
| `TEST` | `TEST_AUTH_PASSIVE` | `MANUAL_SESSION` か `AUTOMATED_LOGIN` | 1 件以上 | 空でない文字列（必須） |
| `TEST` | `TEST_APPROVED_WRITE` | `MANUAL_SESSION` か `AUTOMATED_LOGIN` | 1 件以上 | 空でない文字列（必須） |

認証の方式の欄に 2 つの値を持つ行があるので、受ける組み合わせは 6 通りです。

- `PUBLIC_PASSIVE` は、どの環境でも認証なし（`NONE`）です。
- `PUBLIC` の環境では、`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` を選べません。

### テスト環境の `PUBLIC_PASSIVE`

テスト環境を `PUBLIC_PASSIVE` で監査するのは、**ログインの前の画面だけ**を監査する使い方です。
ログインはしません。ログインの後ろの画面の監査は、`TEST_AUTH_PASSIVE` の役割です。

## 各値の規則

値の規則に 1 つでも合わなければ、プロファイルを拒否します。

### `profileId`

- 小文字の英数字とハイフンだけで、先頭は英数字、全体で 1〜63 文字です（`^[a-z0-9][a-z0-9-]{0,62}$`）。
- 顧客名など、対象を特定できる名前を避けるのは、運用の決まりです。BeakSight は形だけを判定します。

### `revision`

- 1 以上の整数です（JavaScript で正確に扱える整数の範囲。`9007199254740991` まで）。
  - 整数でない値、1 より小さい値は、形の誤り（`PROFILE_SCHEMA_INVALID`）です。
  - 正確に扱える範囲を超える整数（`9007199254740992` 以上）も `PROFILE_SCHEMA_INVALID` ですが、形の確かめ（スキーマ）は通るので、ほかの規則の誤りのコードと一緒に返ります（下の「[拒否のコード](#拒否のコード)」）。
- 同じ `profileId` のプロファイルを改訂するときは、前の改訂より大きい値だけを受けます。同じ値と小さい値は拒否します（`PROFILE_REVISION_NOT_ADVANCED`）。
- `profileId` の違うプロファイルは、改訂として受けません（`PROFILE_REVISION_NOT_ADVANCED`）。
- 改訂の確かめでは、前と次の改訂の番号が、どちらも 1 以上の正確に扱える整数のときだけ比べます。そうでない値（`NaN`、無限大、小数、文字列、`null`、負の数など）は、比べずに `PROFILE_REVISION_NOT_ADVANCED` にします（形の誤りなら `PROFILE_SCHEMA_INVALID` も返します）。
- 改訂の確かめは、次の改訂として、上の検証（「[各値の規則](#各値の規則)」のすべて）で受けたプロファイルだけを受けます。検証を通していない値、検証で受けた値を写した値は、`PROFILE_SCHEMA_INVALID` で拒否します（組み合わせの規則を確かめていないプロファイルを、改訂として受けないためです）。前の改訂（保存してあった値）は、形だけを確かめます。
- 改訂の確かめは、例外を投げずに、当たった誤りのコードをすべて返します（写せない値も、拒否の結果になります）。

### `targetConfigPath`

- 区切りが `/` の相対パスです。
- 使える文字は、ASCII の英字（`A`〜`Z`、`a`〜`z`）、数字（`0`〜`9`）、`.`、`_`、`/`、`-` だけです。`%`、空白、全角の文字、英字以外の文字（`é` など）、制御文字、文字の向きを変える文字、ゼロ幅の文字を含むパスは拒否します。
- `config/targets/` か `local/targets/` の下の、名前のある `.json` のファイルだけを受けます（例: `config/targets/example.json`、`local/targets/example-test.json`）。
- 絶対パス、ドライブ名（`C:` など）、`\`、`..`（親のディレクトリ。名前の中にあっても）、`:` を含むパスは拒否します。
- パスの先のターゲット JSON は、プロファイルを使う側が読みます。BeakSight の判定は、パスの形だけを見ます。

### `approvedTestOrigins`

- `TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` では、1 件以上が必要です。`PUBLIC_PASSIVE` では、空にします。
- 各値は、Origin の正規の書き方（`new URL(値).origin` と同じ文字列）にします。末尾の `/`、パス、大文字、既定のポート（`:443` など）を含む書き方は拒否します。
  - 受ける例: `https://example.com`、`http://127.0.0.1:8080`
  - 拒否する例: `https://example.com/`、`https://example.com/login`、`HTTPS://EXAMPLE.COM`、`https://example.com:443`
- scheme は `https:` です。`http:` は、host がループバックのアドレス（`localhost`、`127.0.0.1`、`[::1]`）のときだけ受けます（例: `http://example.com` は拒否）。
- 同じ値を 2 回書けません。
- 参照するターゲット JSON の `site.allowedOrigins` に含まれる Origin だけを受けます。監査の範囲の外に、認証と書き込みの許可を作らないためです（例: `site.allowedOrigins` が `https://example.com` だけなら、`https://example.invalid` は拒否）。

### `environmentEvidenceRef`

- テスト環境が本番から隔離されていることを確かめた記録への、秘密を含まない参照です。パスワードやトークンを書かないでください。
- 隔離をまだ確かめていないテスト環境で、読み取りの段（認証つきの監査、自動ログイン、操作の候補の発見と READ の確かめ）だけを行うときは、未確認であることが分かる参照（例 `isolation-unverified-20261016`）にします。テスト環境のプロファイルを作ると、BeakSight が保存した日付で `isolation-unverified-<YYYYMMDD>` を入れます（画面では聞かず、出しません。形の定義は `apps/local-ui/src/server/isolation-evidence-ref.ts`）（「[実テスト環境の手順](real-test-environment.md)」）。書き込みのモードへの切り替え（一覧のチェックの保存）も、この参照のまま行います。確かめた記録の参照に替えるときは、プロファイルの編集で直します。
- 1〜200 文字です。文字の数は UTF-16 のコード単位で数えます（絵文字などの一部の文字は、1 文字で 2 と数えます）。
- 次の値は拒否します。
  - 空白とゼロ幅の文字（U+200B〜U+200D、U+2060、U+FEFF）だけの値
  - 改行、制御文字を含む値
  - 文字の向きを変える文字（U+202A〜U+202E、U+2066〜U+2069、U+200E、U+200F）を含む値
  - 対になっていないサロゲート（UTF-16 の壊れた文字）を含む値
- `PUBLIC` の環境では `null` にします。
- `TEST` の環境の `PUBLIC_PASSIVE` では、任意です。`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` では、必須です。
- BeakSight が判定するのは、参照があるかと、その形だけです。参照の中身（確かめた記録か、未確認の印か）は読みません。そのため、未確認の参照でも、書き込みの実行の許可を拒みません。書き込み（`TEST_APPROVED_WRITE`）に進む前に、隔離の扱いを人が判断します（「[実テスト環境の手順](real-test-environment.md)」）。

### `approvedServiceOrigins`

- スクリプトで送るログイン（「[スクリプトで送るログイン](authenticated-audit.md#スクリプトで送るログイン)」）で、画面のスクリプトが送る先の、認証のサービスと API の Origin です。任意の項目で、ないときは空と同じです。項目のないプロファイルは、今までと同じ文書のままです。
- **足すのは、手動のログインの観察だけです。** 手動のログインの成功の後の自動の登録と、手動のログインのジョブの、ログインの段の表の行の「登録する」と、その行から開いた認証の設定の画面の下書きの保存が、token の送信先（とログインに伴う送信）の Origin を足します。どれも、画面のサーバがジョブの記録と行から組み立て直した Origin だけを足します（画面が送った値は使いません）。作成はこの値を受けず、プロファイルの編集は、消すことだけを受けて、足すことを拒みます（画面は、読むだけの一覧と「消す」だけです。要らない Origin を外してから保存します）。
- 自動ログインの記録（自動ログインのジョブの行）と、認証の方式が自動ログインのプロファイルからは、新しい Origin を足す登録を拒みます（`NEW_TARGET_FROM_AUTOMATED_LOGIN`）。入れた資格情報が、手動のログインで観察していない送信先へ送られないようにするためです。足すときは、手動のログインに戻します（「[手動のログインへ戻す](automated-login.md#手動のログインへ戻す)」）。
- `TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` だけで書けます。`PUBLIC_PASSIVE` では空にします（`PROFILE_SERVICE_ORIGIN_INVALID`）。
- 4 件までです。同じ値は 2 つ持てません。観察からの登録でも、4 件を超えるか同じ値が重なる保存は、プロファイルの確かめが拒みます（どちらも `PROFILE_SCHEMA_INVALID`）。
- 書き方は `approvedTestOrigins` と同じです。Origin の正規の書き方で、scheme は `https:`。`http:` は、host がループバックのアドレスのときだけ受けます（`PROFILE_SERVICE_ORIGIN_INVALID`）。
- 参照するターゲット JSON の `site.allowedOrigins`（監査で読む範囲）に含まれる Origin（管理画面の Origin）は入りません（`PROFILE_SERVICE_ORIGIN_INSIDE_TARGET`。「管理画面の Origin…は、承認したサービスの Origin に入れません。手動のログインでログインすると、ログインのサーバの Origin が自動で入ります。」）。サービスの Origin を書いても、巡回の対象、読み込みの数え方、robots.txt と sitemap.xml の取得の対象は広げません。
- ログインの段では、この Origin への読み取り（ページの移動でないもの）と、認証の設定に登録した送信だけを通します。監査の段の扱いは今までどおりです（許可 Origin の外への読み取りは送ります）。
- この項目を変えると（「消す」の保存も、自動の登録も）、プロファイルの改訂が進みます。プロファイルの編集で変えたときは、認証の設定は保存し直しが要ります（自動の登録と行の「登録する」は、認証の設定と 1 回で保存するので、古くなりません）。書き込みのシナリオの承認は「要再承認」になります（どの項目の編集でも同じです）。

## 拒否のコード

拒否したときは、次のコード（1 件以上）と、英語の技術的な詳細を返します。管理画面は、項目ごとに日本語の理由を表示します。

| コード | 意味 |
| --- | --- |
| `PROFILE_SCHEMA_INVALID` | プロファイルの形の誤り: 知らない項目、項目の不足、値の型の誤り、一覧にない値、`schemaVersion` の違い、`revision` が 1 以上の整数でない、`profileId` の形の誤り、`approvedTestOrigins` の重複、`environmentEvidenceRef` が空の文字列か 200 文字（コードポイント）を超える。これらの形の誤り（スキーマの誤り）があるときは、このコードだけを返し、下の規則は確かめません。`revision` が正確に扱える整数の範囲を超えるときもこのコードですが、スキーマは通るので、ほかの規則のコードと一緒に返ります。改訂の確かめでは、写せない値、形の誤り、検証で受けていない次の改訂も、このコードです。 |
| `PROFILE_ID_INVALID` | `profileId` の形の誤り（形の確かめの後に、もう一度確かめる規則。形の誤りは、ふつうは `PROFILE_SCHEMA_INVALID` になります）。 |
| `PROFILE_TARGET_PATH_INVALID` | `targetConfigPath` の誤り。 |
| `PROFILE_MODE_ENVIRONMENT_MISMATCH` | 監査モードを、その環境で選べない（例: `PUBLIC` の環境の `TEST_AUTH_PASSIVE`）。`PUBLIC` の環境で `environmentEvidenceRef` が `null` でない場合も、このコードです。 |
| `PROFILE_AUTH_MISMATCH` | 認証の方式が、監査モードに合わない（例: `PUBLIC_PASSIVE` の `MANUAL_SESSION`、`TEST_AUTH_PASSIVE` の `NONE`）。 |
| `PROFILE_TEST_ORIGINS_REQUIRED` | `TEST_AUTH_PASSIVE` か `TEST_APPROVED_WRITE` で、`approvedTestOrigins` が空。 |
| `PROFILE_TEST_ORIGIN_INVALID` | `approvedTestOrigins` の値の書き方か scheme の誤り。`PUBLIC_PASSIVE` で `approvedTestOrigins` が空でない場合も、このコードです。 |
| `PROFILE_TEST_ORIGIN_OUTSIDE_TARGET` | `approvedTestOrigins` の値が、参照するターゲット JSON の `site.allowedOrigins` に含まれない。 |
| `PROFILE_ENVIRONMENT_EVIDENCE_REQUIRED` | `TEST_AUTH_PASSIVE` か `TEST_APPROVED_WRITE` で、`environmentEvidenceRef` が `null`。値が空白とゼロ幅の文字だけの場合、UTF-16 のコード単位で 200 を超える場合、改行・制御文字・文字の向きを変える文字・対になっていないサロゲートを含む場合も、このコードです。 |
| `PROFILE_SERVICE_ORIGIN_INVALID` | `approvedServiceOrigins` の値の書き方か scheme の誤り。`PUBLIC_PASSIVE` で空でない場合も、このコードです。 |
| `PROFILE_SERVICE_ORIGIN_INSIDE_TARGET` | `approvedServiceOrigins` の値が、参照するターゲット JSON の `site.allowedOrigins` に含まれる。 |
| `PROFILE_REVISION_NOT_ADVANCED` | 改訂の `revision` が、前の改訂より大きくない。前か次の `revision` が、1 以上の正確に扱える整数でない（比べられない）。または、前の改訂と `profileId` が違う。 |

形が正しいときは、当たった規則のコードを、すべて返します（例: `PUBLIC` の環境の `TEST_AUTH_PASSIVE` と `NONE` は、`PROFILE_MODE_ENVIRONMENT_MISMATCH` と `PROFILE_AUTH_MISMATCH` の両方を返します。`approvedTestOrigins` や `environmentEvidenceRef` にも誤りがあれば、そのコードも返します）。
`revision` が正確に扱える整数の範囲を超えるときは、`PROFILE_SCHEMA_INVALID` と、ほかの規則のコードを一緒に返します（例: `revision` が `1e300` で、`PUBLIC` の環境の `TEST_AUTH_PASSIVE` なら、`PROFILE_SCHEMA_INVALID` と `PROFILE_MODE_ENVIRONMENT_MISMATCH` などを返します）。

### 判定を呼ぶ側の決まり

プロファイルの判定は、参照するターゲット JSON を読み込んだ結果（プロファイルを使う側が、これまでの設定の読み込みで読んだもの）を受け取って、`approvedTestOrigins` が `site.allowedOrigins` に含まれるかを確かめます。

- 受け取ったターゲット JSON の形が正しくない（読み込みの結果でない値を渡した。たとえば `site.allowedOrigins` がない）ときは、判定がそれを読む場合（`TEST_AUTH_PASSIVE` と `TEST_APPROVED_WRITE` で、`approvedTestOrigins` の値の書き方が正しい場合）に、拒否の結果を返さずに、例外（`TypeError`）で止まります。これは呼び出し側の誤りで、そのプロファイルを受けることはありません（止まる側なので安全です）。
- プロファイルの値の誤りは、例外ではなく、上の拒否のコードで返します。

## 旧ターゲット JSON の扱い

プロファイルのない、これまでのターゲット JSON だけの監査は、つねに `PUBLIC_PASSIVE` です。

- ターゲット JSON には、監査モードを書けません。`mode`、`environment`、`auth`、`profile` などの項目を書くと、知らない項目として設定のエラー（`unknown configuration key`）になります。
- プロファイルのないターゲット JSON での監査（CLI）は、認証のない公開の監査です。管理データにプロファイルを作りません。
- 公開の監査の判定（Guard）、URL の扱い、停止と再開、出力の形式（「[出力](output.md)」）は、プロファイルの追加の前と変わりません。
