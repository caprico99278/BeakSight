# BeakSight 開発スキル

BeakSightの設計と製造を、品質を落とさず効率良く進めるための作業手順です。
このスキルが扱うのは「誰が何を決め、誰が何を書くか」「困ったときにどう動くか」「何をしてはいけないか」の3点です。
BeakSight自体の仕様（SSOT、安全性の不変条件、完了判定など）は `doc/design/` の設計書が正であり、このスキルはそれを置き換えません。

## 1. 役割分担

このスキルでは、作業者を2つの役割に分けます。
役割を分けるのは、設計判断と実装作業を混ぜると、場当たり的な修正が設計書に反映されないまま積み重なり、後から誰も全体像を説明できなくなるからです。

| 役割 | 担当 | 行うこと | 行わないこと |
| --- | --- | --- | --- |
| 設計者 | このチャットのメインAI | 要件の整理、設計書と実装計画の作成・改訂、サブタスクへの分解、実装者への指示、成果の検証、ユーザーへの報告 | `src/`・`tests/`・`fixtures/`・`schemas/`・`config/`・`tools/` の直接編集 |
| 実装者 | Agentツールで起動するサブエージェント | 指示されたサブタスクの範囲内で、TDDにより実装とテストを行い、結果を日本語で報告する | 設計の変更、範囲外の修正、Blockerの独自回避 |

設計者がコードを直接直したくなる場面（1行で済む修正、明らかなtypoなど）でも、実装サブタスクとして実装者に渡してください。
小さな修正ほど記録から漏れやすく、後で「なぜこうなっているのか」を追えなくなるためです。

設計者が編集してよいファイルは次のとおりです。

- `doc/design/` 配下の設計書と実装計画
- 作業記録置き場（`.superpowers/sdd/<計画名>/`、Git管理対象外）の進捗台帳・指示書・報告書
- ユーザーから明示的に頼まれた場合の `README.md` などの利用者向けドキュメント

設計者は、検証のためにテストやビルドを実行し、コードを読むことは自由に行ってかまいません。

## 2. Gitの取り扱い

Gitの操作には、ユーザーが定めた次の制約があります。

**禁止する操作**

- `git commit`（`--amend` を含む）と `git push`。コミットを作る・動かす操作（`merge`、`rebase`、`cherry-pick`、`pull`、`revert`、`tag`）と、デスクトップアプリの `sync_with_base_branch` も同様に使わない。
- 作業ツリーやファイルをHEAD（または過去のコミット）の状態に戻す操作。具体的には `git checkout -- <path>`、`git checkout HEAD`、`git restore`、`git reset`、`git stash`、`git switch`、`git clean`、`git show HEAD:<path> > <path>` のような上書き、`git worktree add` による過去版の展開。
- Agentツールの `isolation: "worktree"`。これはHEADから新しい作業ツリーを作るため、未コミットの作業を含まない古い状態で実装が進んでしまう。

**許可する操作**（表示だけで、作業ツリー・インデックス・HEADを変えないもの）

- `git status`、`git diff`、`git log`、`git blame`、`git show`（標準出力への表示のみ）

`git commit` と `git push` は、`.claude/settings.json` の許可ルールと、PreToolUseフック（`.claude/hooks/block-git-commit-push.mjs`）によって仕組みの上でも止めています。
このフックはサブエージェントのツール実行にも適用されます。コマンドの文字列に `git commit` や `git push` が含まれているだけでも止まるため、それらの文字列を `echo` やテストの入力に書きたいときは、ファイルに書いてから読み込むなど、コマンドに直接書かない形にしてください。
フックに止められても、フックの無効化や回避を試みてはいけません。

**クラウドの環境での例外（2026-09-25 ユーザー指示）**: クラウドの環境（環境変数 `CLAUDE_CODE_REMOTE` が `true`）では、コンテナがセッションの終了で消え、ユーザーがそこでコミットできません。そのため、フックはクラウドの環境では `git commit` と `git push` を止めません。`settings.json` の Bash の deny も外しました。
クラウドでコミットとプッシュを行うのは、設計者だけです。対象は、セッションで指定された作業ブランチだけにします。行うのは、検証を終えた区切りか、セッションを終える前です。実装者とレビュー担当には、これまでどおりコミットとプッシュを禁止します。HEAD に戻す操作の禁止は、クラウドでも変わりません。

コミットが禁止されているため、これまでの作業はすべて未コミットの変更として作業ツリーにだけ存在します。
HEADに戻す操作は、その作業を一瞬で消してしまう可能性があります。
「この不具合は前からあったのか」を確かめたくなっても、HEADに戻して確認してはいけません。
代わりに、第4章の手順どおり、発生時期を問わず現在の作業ツリーで再現させて不具合として扱います。

変更の範囲や前後関係を記録したいときは、コミットの代わりに次を使います。

- 変更前後のファイルの SHA-256（PowerShellの `Get-FileHash`）
- 実装者の報告書に記載する変更ファイル一覧
- `git diff` の表示結果（記録としてのみ使い、差分を元に戻す操作はしない）

## 3. 基本の作業の流れ

### 3.1 着手前

1. 関係する設計書と実装計画を `doc/design/` から読む。とくに `2026-08-27-beaksight-implementation-tasks.md` のSSOT Owner Matrix、Safety Invariants、禁止事項は、どの作業でも前提になる。文書どうしの優先順位は第8章を参照する。
2. 作業記録置き場の `progress.md` の末尾を読み、現在の状態、過去の判断（Ruling）、未解決事項を把握する。
3. 共通部品台帳（`doc/design/beaksight-shared-components.md`）と、作業記録置き場の `defects.md`・`commonization-candidates.md` を読む。台帳がまだなければ、最初の設計作業で作る（`references/shared-components-policy.md`）。
4. `git status` で作業ツリーの状態を確認する（表示のみ）。
5. ユーザーの依頼が既存の設計書で説明できるかを判断する。説明できない場合は、新しい設計書を書くか、既存の設計書に追補する。仕様そのものを決める必要がある場合（スコープの拡大、新しい依存パッケージ、実サイトへのアクセスなど）は、書く前にユーザーに確認する。

### 3.2 設計

設計書と実装計画は `doc/design/` に次の名前で置きます。

```text
doc/design/YYYY-MM-DD-beaksight-<題目>-design.md
doc/design/YYYY-MM-DD-beaksight-<題目>-implementation-plan.md
```

構成は `references/design-doc-template.md` に従ってください。
新しく書く設計書と実装計画は日本語で書きます（第7章）。既存の英語の設計書を書き換える必要はありません。

実装計画では、作業を「実装者1人が1回の起動で終えられる大きさ」のサブタスクに分けます。
目安は、変更するproductionファイルが1〜3個程度で、REDにするテストが明確に書ける大きさです。
大きすぎるサブタスクは、実装者が途中で判断に迷い、設計にない選択を独自に行う原因になります。

設計では、新しく作るものが既存の共通部品で済まないか、後続のTaskでも使われないかを必ず確認します（第6章）。

### 3.3 実装者への依頼

サブタスクごとに実装者（`subagent_type: "general-purpose"`）を1人起動します。
指示書は `references/implementer-brief-template.md` を埋めて作り、作業記録置き場に `<サブタスクID>-brief.md` として保存してから、その内容をAgentツールのpromptに渡します。

サブエージェントはこのスキルも会話の経緯も知りません。
Gitの禁止事項、日本語での報告、Blocker時に止まるルールは、毎回指示書に書いて渡してください。

同じファイルに触れる実装者を同時に動かしてはいけません。並列にするのは、変更ファイルが重ならないことを設計者が確認できた場合だけにします。

### 3.4 検証

実装者の報告を受け取ったら、設計者が自分で次を確認します。報告の「PASSしました」をそのまま信じるのではなく、新しく実行した結果で判断してください。

1. 報告された変更ファイルが、指示した範囲に収まっているか（`git status`、`git diff` で確認）。
2. サブタスクの受け入れ条件に対応するテストを実行し、PASSするか。
3. 必要に応じて `npm run verify`（型チェック → 全テスト → ビルド）を実行する。
4. テストの削除・弱体化・skip化で見かけ上PASSさせていないか。
5. SSOT Owner Matrixに反する第二のownerや、`src/**` へのtarget固有情報の混入がないか。
6. 共通部品台帳にある部品と同じ意味の処理・定数・文字列リテラルを、新しく書いていないか（第6章）。

問題があれば、その内容を設計者が指示書の修正版（`<サブタスクID>-fix-round-N-brief.md`）にまとめ、実装者を起動し直します。

重要なチェックポイント（設計書で指定されたTask、または大きな設計変更の直後）では、読み取り専用のレビュー担当サブエージェントを別に起動して独立レビューを受けます。
レビュー担当には「ファイルを編集しないこと」「指摘は重大度（Critical / Important / Minor）付きで日本語で返すこと」を指示してください。

実装タスク指示の第12章で指定されたチェックポイント（Task 3、5、11、14、15、18、21）の後は、独立レビューでCritical 0件・Important 0件になったうえで、ユーザーの承認を得るまで次のTaskに進みません。

### 3.5 記録と報告

各サブタスクの結果を `progress.md` に追記し、ユーザーには `references/report-templates.md` の「設計者からユーザーへの報告」の形式で報告します。
実行できなかったコマンドやテストは、必ず「未実行項目」として報告してください。実行していないものをPASS扱いにしてはいけません。

## 4. Blockerに遭遇したとき

Blockerとは、実装計画どおりに進めることができない状態のことです。例を挙げます。

- 設計書どうし、または設計書と既存コードが矛盾している
- 設計の前提（既存APIの形、ファイルの責務など）が実際のコードと違う
- 計画どおりのテストがREDにならない、または計画どおりの実装でGREENにならない
- 計画どおりに作ると、SSOTの第二ownerや安全性違反が必要になる

Blockerへの対応は、必ず次の順で行います。

1. **実装者が止まる。** 実装者は回避策を自分で考えて進めてはいけません。作業を止め、`references/report-templates.md` の「Blocker報告」の形式で、何が、どこで、なぜ進めないのかを報告します。
2. **設計者が原因を分析する。** コードを読み、必要なら現在の作業ツリーでテストを実行して事実を確かめます。
3. **設計者が設計を修正する。** 設計書と実装計画に修正を加え、「設計変更履歴」に、変更日、変更理由（どのBlockerに対応したか）、変更内容、影響範囲を日本語で記録します。
4. **設計者がサブタスクを定義し直し、新しい実装者に依頼する。** 修正後の設計に沿った指示書を作り、実装者を起動します。

ただし、Blockerの解消に次のような判断が必要な場合は、設計者だけで決めずにユーザーに確認します。

- 製品仕様やスコープの変更
- 新しい依存パッケージの追加や更新
- 実際の監査対象サイトへのアクセス
- ブラウザのインストールなど、開発環境そのものの変更

## 5. 既存不具合に遭遇したとき

既存不具合とは、現在のサブタスクとは別の原因で、すでにコードやテストに存在している不具合のことです。

既存不具合は、見つけた人がその場で直すのではなく、独立した実装サブタスクとして扱います。
その場で直すと、今のサブタスクの変更と不具合修正が混ざり、どちらの変更が何を直したのかを説明できなくなるからです。

1. **発見者が報告する。** 実装者が見つけた場合は、報告書の「発見事項」に書きます。現在のサブタスクを続けられない場合はBlockerとして報告します（第4章）。範囲外の修正を黙って行ってはいけません。
2. **設計者が不具合台帳に登録する。** 作業記録置き場の `defects.md` に `DEF-NNN` の番号で、現象、再現手順、影響範囲、発見した経緯を記録します。
3. **設計者が修正の設計を書く。** 原因の分析、修正方針、SSOTや安全性への影響、受け入れ条件（どのテストがREDからGREENになれば直ったと言えるか）を、設計書に追補するか、規模が大きい場合は専用の設計書として作ります。
4. **設計者が実装サブタスクとして依頼する。** 実装者は、まず不具合を再現するテストを書いてREDを確認し、次に最小の修正でGREENにします。
5. **設計者が検証し、台帳を更新する。**

「この不具合は今回の変更で入ったのか、前からあったのか」の判定には時間をかけません。
第2章のとおり、HEADに戻して確かめることは禁止です。
発生時期がどちらであっても、直す手順は同じです。発生時期について分かることがあれば、`git log` や `git blame` の表示と、コードを読んだ結果から推測として台帳に書いてください。

## 6. 共通化とSSOTの進め方

BeakSightでは、同じ機能を少しずつ変えて複製することを避け、変更が1か所で済む構造を保ちます。
SSOT Owner Matrixは主要な意味のownerだけを定めています。ここでは、それより細かい共通部品と、UI/UXの共通仕様にも同じ考え方を広げます。

### 6.1 共通部品

- 設計者は共通部品台帳（`doc/design/beaksight-shared-components.md`）を更新し続け、共通関数、定数、上限値、理由コード、表示カタログ、テスト補助の置き場所と責務を記録する。SSOT Owner Matrixの内容は台帳に書き写さず、参照先だけを示す。
- 設計の段階で、新しく作るものが台帳の部品で済まないか、後続のTaskでも使われないかを確認する。使われる見込みがあれば、最初から共通部品として設計する。
- 実装者への指示書には、台帳から「使うべき共通部品」を抜き出して渡す。実装者は、範囲外にある既存処理を使えないときに複製を作らず、Blockerとして止まる。
- 既存コードに重複を見つけたら、作業記録置き場の `commonization-candidates.md` に `CC-NNN` として記録し、共通化を独立したサブタスクとして扱う。重複のせいで振る舞いがずれている場合は、既存不具合として扱う（第5章）。
- 共通化候補は、ユーザーが開発を明示的に指示するまで着手しない（2026-09-23 ユーザー指示）。登録と報告までにとどめる。ただし、新しく書くコードで同じ重複を増やさないことは常に守る。
- 意味が違うもの、安全の境界（Passive ContextとIsolated Interaction Context）をまたぐもの、ブラウザ内とNode側で実行環境が違うものは、見た目が似ていても安易に共通化しない。

詳細は `references/shared-components-policy.md` にあります。

### 6.2 UI/UX

HTMLレポート、CLIの出力、ChatGPT用バンドルは、同じRunの結果を見せる3つの表示面です。
表示言語、表示に関わるownerのファイルと責務、UI Gate（自動検査）は、ユーザーの承認を得て `doc/design/2026-09-23-beaksight-ui-ssot-design.md`（UI追補設計書）で決まっています。要点は次のとおりです。

- 利用者に見せる文は日本語にする。JSONのキー、ID、状態の値、理由コードは英数字のままにし、表示するときに日本語のラベルに変換する。
- 確定したRunから表示用モデルを1回だけ組み立て、3つの表示面はそれを描画するだけにする。件数の集計や対応づけを表示面ごとにやり直さない。
- Severity、各種Status、category、理由コード、Viewportなどの表示（ラベル、順序、色、説明）は、表示カタログで1回だけ定義する。値の意味は各ownerが決め、カタログは表示のしかただけを持つ。
- HTMLは、エスケープを必ず通す部品関数で組み立てる。色や余白はCSSトークンで1か所に定義する。URLをリンクにするかどうかは、`classifyUrl` の結果で判断する。
- 日時・数値・指標値の書式と、利用者向けの文言は、それぞれ1か所にまとめる。Findingの文言はRuleが持ち、表示面では作り直さない。
- 新しいRule、category、状態を追加するときに、表示面のコードを変更しなくてよいことを、設計の完了条件に含める。

Task 12（Rule Catalog）、Task 15（完了状態）、Task 16（レポート）、Task 17（CLI）の設計をするときは、着手前にUI追補設計書と `references/ui-ux-ssot.md` を読んでください。
これらのTaskで作る型や集計が、表示の共通化の土台になるためです。

### 6.3 開発用の検査は速さを要件にする

UI GateやArchitecture Gatesのような、構造を守るための自動検査は、速く動くことを要件にします（2026-09-23 ユーザー指示）。遅い検査は、待ち時間で生産性を落とすうえに、実行が省略されるようになって意味を失うからです。

- 検査ファイル1つあたり1秒以内に終わること。実装したときと変更したときに所要時間を記録し、超えたら不具合として扱う。
- Node.js標準の `fs`、正規表現、文字列の検索で判定する。TypeScriptのコンパイラAPI、AST解析、ESLintなどの外部ツール、新しい依存パッケージ、ブラウザや子プロセスの起動、ビルド結果を前提にした検査は使わない。
- 対象ファイルの読み込みは1回だけ行い、各検査で共有する。
- `npm test` で毎回実行される場所に置く。

詳細は `references/ui-ux-ssot.md` 第6章とUI追補設計書 第6章にあります。

## 7. 日本語での報告とドキュメント作成

ユーザーへの報告、設計書、実装計画、指示書、実装者やレビュー担当の報告は、すべて意味の通る日本語で書きます。
「意味の通る」とは、BeakSightの前提知識を持つ読み手が、読み返さずに一度で内容を理解できることを指します。

とくに次の点を守ってください。詳しい例は `references/japanese-writing-guide.md` にあります。

- 結論を先に書く。何が終わり、何が終わっていないかを最初に述べる。
- 1つの文には1つの内容だけを書く。主語と述語が対応しているかを確認する。
- 英語は、コード上の識別子、ファイル名、コマンド、固有名詞、定着した用語（SSOT、Blocker、PASS/FAILなど）に限って使う。英単語を助詞でつなぐだけの文（例: 「guardのphaseをretryしてcloseをdrainする」）は書かない。
- 「対応しました」「修正しました」だけで終わらせず、何を、どう変え、その結果どうなったかを書く。
- 推測と確認済みの事実を区別する。確認していないことは「未確認」と書く。

実装者への指示書にも、報告を日本語で書くよう毎回明記してください。
サブエージェントの報告が英語や意味の通らない日本語で返ってきた場合は、設計者がその内容を確認し、日本語で整理し直してからユーザーに伝えます。

### 8.2 守るべき前提

以下は設計書で定められた内容の要約です。詳細と正確な定義は設計書を参照してください。

- **SSOT**: 同じ意味の判断には、productionのownerを1つだけ置く。ownerの一覧は `2026-08-27-beaksight-implementation-tasks.md` の第5章。第二のownerが必要に見えたら、実装者はBlockerとして止まる。
- **Target Isolation**: `src/**` にtarget固有の名前、domain、URL、selectorを書かない。target固有情報は `config/targets/**` か、Git管理対象外の `local/` に置く。
- **読み取り専用**: Passive ContextでGET/HEAD以外を送信しない。フォーム送信、`tel:` などの外部起動、ダウンロードを行わない。
- **完了の正直さ**: 実行していないテストをPASS扱いにしない。PARTIALをCOMPLETEと報告しない。テストを削除・弱体化してPASSさせない。
- **TDD**: RED → 最小実装 → GREEN → 関連する検証、の順で進める。
- **実サイトへのアクセス禁止**: ユーザーの明示的な許可なしに、実際の監査対象サイトへアクセスしない。検証はローカルのfixtureで行う。
- **依存パッケージ**: ユーザーの事前承認なしに、追加・更新・ダウンロードをしない。
- **Evidenceを先に集め、Findingは後で作る**: CollectorはFindingを作らない。Reporterは判定しない。意味や見た目の良し悪しをFindingにしない。
- **Playwrightの起動失敗**: サンドボックス内でChromiumの起動が `spawn EPERM` で失敗することがある。これは製品の不具合ではなく環境の制約なので、同じコマンドを実行し直せる環境で再実行し、除外した失敗として記録する。テスト結果のPASSやFAILに数えてはいけない。
