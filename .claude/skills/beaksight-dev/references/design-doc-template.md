# 設計書・実装計画のテンプレート

設計書は「何を、なぜ、どういう構造で作るか」を、実装計画は「どの順で、どのファイルを、どのテストで確かめながら作るか」を書きます。
設計書を読んだ人が実装計画なしでも方針を説明でき、実装計画を読んだ実装者が設計判断をせずに作業できる状態を目指してください。

見出しは必要に応じて増減してかまいません。ただし「設計変更履歴」「対象外」「完了条件」は省略しないでください。これらがないと、Blocker対応で設計が変わったときに、何がいつ変わったのかを後から追えなくなります。

---

## 設計書（`YYYY-MM-DD-beaksight-<題目>-design.md`）

```markdown
# BeakSight <題目> 設計書

作成日: YYYY-MM-DD
状態: 草案 / ユーザー承認済み / 改訂中
対象範囲: <この設計書が扱う範囲を1文で>

## 1. 目的

<何が問題で、この設計によって何が解決するのかを書く。>

## 2. 根拠となる文書と優先順位

- 従う文書: <設計書・実装計画のパス>
- この設計書が置き換える箇所: <ある場合のみ。文書名と節番号>
- 引き続き守る不変条件: <SSOT owner、Safety Invariantsなど、この設計に関係するもの>

## 3. 採用する設計

<構造、責務の分け方、データの流れを書く。検討して採用しなかった案があれば、その理由も1〜2文で書く。>

## 4. 詳細設計

### 4.1 <構成要素ごとの節>

<型、関数の入出力、状態遷移、エラー時の扱い。>

## 5. SSOTと安全性への影響

| 項目 | owner | この設計での扱い |
| --- | --- | --- |
| <例: URL正規化> | `src/crawl/normalize-url.ts` | <変更なし / 利用のみ / 拡張> |

第二のownerを作らないこと、`src/**` にtarget固有情報を入れないことを、この設計がどう守るかを書く。

## 6. 共通部品と共通仕様

| 区分 | 名前 | 置き場所 | この設計での扱い |
| --- | --- | --- | --- |
| 利用する既存の部品 | <例: `classifyUrl`> | <パス> | 利用のみ |
| 新しく作る共通部品 | <名前> | <パス> | 新設。共通部品台帳に追記する |
| 共通化しないと判断したもの | <名前> | <パス> | <共通化しない理由> |

- 新しく作るもののうち、後続のTaskでも使われる見込みがあるもの: <あれば、どのTaskで使われるか>
- 表示に関わる場合: 表示用モデル、表示カタログ、部品、書式、文言のどれを使い、どれを追加するか（`ui-ux-ssot.md`）。
- 変更容易性の確認: <この設計の後で、Rule・category・状態などを1つ追加するとき、変更が必要になるファイルはどれか>

## 7. テスト設計

<どのテストをREDにして、何が確認できればGREENとみなすか。単体・コンポーネント・結合のどこで確かめるか。>

## 8. 対象ファイル

| パス | 責務 | 変更の種類 |
| --- | --- | --- |
| `src/...` | ... | 新規 / 変更 |

## 9. 対象外

<この設計ではやらないこと。やらない理由も短く書く。>

## 10. 完了条件

- [ ] <確認可能な条件。例: `npx vitest run tests/unit/xxx.test.ts` がPASSする>
- [ ] `npm run verify` がPASSする

## 11. 設計変更履歴

| 日付 | 契機 | 変更内容 | 影響範囲 |
| --- | --- | --- | --- |
| YYYY-MM-DD | 初版 | - | - |
| YYYY-MM-DD | Blocker: <サブタスクID>の報告 | <何をどう変えたか> | <影響するサブタスク・ファイル> |
| YYYY-MM-DD | 既存不具合: DEF-NNN | <何をどう変えたか> | <影響するサブタスク・ファイル> |
```

## 実装計画（`YYYY-MM-DD-beaksight-<題目>-implementation-plan.md`）

```markdown
# BeakSight <題目> 実装計画

設計書: `doc/design/YYYY-MM-DD-beaksight-<題目>-design.md`
目標: <1文で>
作業記録置き場: `.superpowers/sdd/<計画名>/`

## 全体の制約

- Gitのcommit・pushは禁止。HEADに戻す操作（checkout、restore、reset、stash など）も禁止。表示だけの `git status`・`git diff`・`git log`・`git blame`・`git show` は使ってよい。
- 依存パッケージの追加・更新はユーザーの事前承認が必要。
- 実サイトにはアクセスしない。検証はローカルfixtureで行う。
- `src/**` はtarget-agnosticに保つ。
- <この計画固有の制約>

## サブタスク一覧

| ID | 内容 | 依存 | 状態 |
| --- | --- | --- | --- |
| T1 | ... | なし | 未着手 / 実装中 / 検証中 / 完了 / Blocker |
| DEF-001 | 既存不具合: ... | T1 | ... |

## T1: <サブタスク名>

**変更するファイル**
- 変更: `src/...`
- テスト: `tests/...`

**受け取るもの・提供するもの**
- 利用する既存API: ...
- 使うべき共通部品（共通部品台帳から）: ...
- 新たに提供するAPI: ...

**手順**
1. RED: `<テストファイル>` に `<テスト名>` を追加し、`npx vitest run <テストファイル>` で失敗することを確認する。期待する失敗理由: ...
2. 最小実装: ...
3. GREEN: 同じコマンドでPASSすることを確認する。
4. 関連する検証: `npx vitest run <関連テスト>`

**受け入れ条件**
- ...

**Blockerとして止まるべき状況**
- <このサブタスクで起こりそうな、設計判断が必要になる状況>
```

## 見直しのチェック

書き終えたら、次を確認してください。

- 実装者が「どちらにすべきか」と迷う箇所が残っていないか。残っていれば、それは設計者が決めるべきことなので書き足す。
- 「適切に」「必要に応じて」「など」で、判断を実装者に丸投げしていないか。
- 型名・関数名・ファイルパスが、設計書と実装計画と既存コードで一致しているか。
- 各サブタスクの受け入れ条件が、コマンドの実行結果で確かめられる形になっているか。
- 既存の部品と同じ意味のものを、新しく作る設計になっていないか。新しく作る共通部品は、共通部品台帳に追記したか。
- 表示に関わる設計なら、集計・ラベル・色・書式・文言を表示面ごとに持たせていないか（`ui-ux-ssot.md`）。
- 日本語として一度読んで意味が通るか（`japanese-writing-guide.md`）。
