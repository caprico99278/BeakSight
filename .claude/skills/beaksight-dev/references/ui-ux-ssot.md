# UI/UXの共通化とSSOT

BeakSightで利用者の目に触れるものは、次の4つです。

| 表示面 | 実装計画での位置 | 主な読み手 |
| --- | --- | --- |
| HTMLレポート（`report.html`） | Task 16 `src/report/html-report.ts` | 監査結果を確認する人 |
| CLIの出力（標準出力・標準エラー・終了コード） | Task 17 `src/cli/index.ts` | 実行する人、呼び出し元のスクリプト |
| ChatGPT用バンドル（`chatgpt/*.json` と ZIP） | Task 16 `src/report/chatgpt-bundle.ts` | 後段の意味監査（ChatGPT）と、その結果を読む人 |
| 設定エラーなどの利用者向けメッセージ | `src/config/`、`src/cli/` | 設定を書く人 |

これらは同じRunの結果を、それぞれ違う形で見せます。
同じ結果を見せているのに、件数の数え方、重大度の呼び方や色、状態の言い回しが表示面ごとに違うと、読み手はどれが正しいのか判断できなくなります。
また、ラベル1つを変えるたびに3か所を直すことになり、直し漏れが起きます。
この文書は、それを防ぐための設計ルールです。

このルールの目的は、次の状態を保つことです。

> 新しいRule、category、severity、状態、表示項目を1つ追加するとき、変更が必要なのは「定義を持つカタログ」と「その項目を生み出す処理」だけで、各表示面のコードは変更しなくてよい。

設計書を書くときは、この状態が保たれているかを完了条件に含めてください。

**決定事項の正**: 2026-09-23に、ユーザーの承認を得て `doc/design/2026-09-23-beaksight-ui-ssot-design.md`（UI追補設計書）を作りました。そこで次のことが決まっています。この文書と食い違う場合は、UI追補設計書が正です。

- 表示言語は日本語（UI追補設計書 第3章）
- 表示に関わるownerのファイルと責務（第4章）
- UI Gate（GATE-UI01〜06）と、その速さの要件（第6章）

この文書は、それらを設計するときの考え方と注意点を説明するものです。モジュールのパスは、この文書には書かず、UI追補設計書を参照してください。

## 1. 表示の流れを1本にする

実装タスク指示の第4.3節（No Duplicate Processing Flow）を、表示にも同じように当てはめます。

```text
確定したRun（RunSummary / PageAuditResult[] / Finding[] / Evidence / Safety Ledger）
   ↓  1回だけ組み立てる
表示用モデル（例: ReportViewModel）
   ├─ HTMLレポートの描画
   ├─ CLIの結果表示
   └─ ChatGPT用バンドルの summary / findings / pages
```

- 件数の集計、並べ替え、グループ分け、ページとFindingとEvidenceとScreenshotの対応づけは、表示用モデルを組み立てる処理で**1回だけ**行います。
- 各表示面の描画処理は、表示用モデルを受け取って文字列やファイルに変換するだけの純粋な関数にします。生のEvidenceを読み直して、独自に集計や判定をしてはいけません。
- 設計書の方針「Reporterは監査判定を行ってはいけない」は、表示用モデルの組み立て処理にも適用されます。組み立て処理は、確定済みの情報を並べ替え、数え、対応づけるだけです。新しいFindingやseverityの判断は行いません。
- とくに「ERROR / WARN / INFO / SAFETY の件数」と「サイト品質のFindingとSafetyイベントを分けた集計」（設計書 第13章）は、HTMLレポート、CLI、`chatgpt/summary.json` のすべてに出ます。この集計を持つ場所は1つだけにしてください。

表示用モデルを置くモジュールは、UI追補設計書 第4章で決まっています。型名と関数名は、Task 16の設計で決めます。

## 2. 表示用の語彙はカタログで1回だけ定義する

表示に関わる値の一覧と、その表示のしかたは、カタログとして1か所で定義します。

| 語彙 | 値の定義元（意味のowner） | カタログに持たせるもの |
| --- | --- | --- |
| Severity | `src/core/contracts.ts` | 表示順、ラベル、色トークン、短い説明、サイト品質かSafetyかの区別 |
| Run Status | `src/core/contracts.ts`（導出は `deriveRunStatus()`） | ラベル、説明（終了コードは表示カタログではなく、CLIの終了コード表が持つ） |
| Page Audit Status | `src/core/contracts.ts` | ラベル、説明、色トークン |
| Interaction Status | `src/core/contracts.ts` | ラベル、説明 |
| Finding category | Rule Catalog（Task 12） | ラベル、レポートでの節の順序、節のアンカー名 |
| 未完了・スキップ・ブロックの理由 | 各ownerが発行する理由コード | 利用者向けの説明文 |
| Viewport | `src/config/`（既定値） | ラベル（例: デスクトップ 1440×900） |
| Evidenceの種類 | `src/core/contracts.ts`（`EvidenceType`） | ラベル、Evidence IDの接頭辞（`EV-NET-` など） |

守ること:

- **値の意味と表示を分けます。** どのRuleがどのcategoryに属し、どのseverityになるかはRule Catalogが決めます。表示用カタログは「そのcategoryをどう呼び、どの順に並べるか」だけを持ちます。表示用カタログが所属や重さを決め直してはいけません。
- **閉じた型にします。** 値の一覧は `as const` の配列として1回だけ書き、union型はそこから導出します。カタログは `satisfies Record<Severity, SeveritySpec>` のように書き、値を1つ追加したらカタログの書き漏れが型エラーになるようにします。
- **文字列リテラルをばらまきません。** `'ERROR'` や `'COMPLETE'` を、表示面のコードで比較や分岐に直接書くことは避けます。分岐が必要なら、カタログの属性（例: `isSafety`、`order`）を使います。
- **分岐は網羅します。** unionに対する `switch` には `never` による網羅チェックを付けます。

### 型の開きへの対応

現時点で、`Finding.category` と `PageAuditResult.incompleteReasons`、`RunSummary.incompleteReasons` は `string` です。
このままでは、表示用カタログとの対応を型で保証できません。
これらを閉じたunion型や構造化された理由コードに変えるかどうかは、Task 12（category）とTask 15・16（理由コード）の設計で判断してください。
この変更はJSON Schemaにも関わるため、スキーマの版と併せて設計書に記録します。

## 3. HTMLレポートの部品

HTMLレポートは静的HTMLで、SPAフレームワークは使いません（実装計画 Task 16）。
その範囲で、同じ見た目と振る舞いを持つものは、HTML文字列を返す部品関数として1回だけ作ります。

作ることになる部品の例です。名前と分け方はTask 16の設計で決めます。

| 部品 | 使われる場所 |
| --- | --- |
| Severityバッジ | トップの集計、Finding一覧、ページ一覧 |
| 状態バッジ（Run / Page / Interaction） | トップの集計、ページ一覧、Interactionの節 |
| 件数サマリー | トップ、各categoryの節、各ページ |
| Finding行 | categoryの節、ページの節 |
| Evidence参照（IDとリンク） | Finding行、ページの節 |
| Screenshot参照 | Finding行、ページの節 |
| URL表示 | あらゆる場所 |
| 節の見出しとアンカー | すべての節 |
| 表 | 一覧を出すすべての場所 |

守ること:

- **エスケープは1か所で行います。** HTMLへ文字列を入れる処理は、1つのエスケープ関数か、エスケープを必ず通す部品だけが行います。部品の外で、テンプレート文字列にEvidenceの値を直接埋め込んではいけません。これは見た目の統一のためだけでなく、レポートへのスクリプト注入を防ぐ安全性の要件です（Task 16 Step 3）。
- **URLをリンクにするかどうかは、URLの意味のownerが決めます。** `mailto:`、`tel:`、外部Originなどを、クリックできるリンクにするかテキストにするかは、URL表示部品が判断します。ただし、その判断に独自の正規表現は使わず、`normalizeUrl` と `classifyUrl`（SSOT Owner Matrix）の結果を使います。表示のためにURL判定を作り直すことは、ARCH04違反と同じ種類の重複です。
- **見た目の値はトークンにします。** 色、余白、文字サイズ、角丸などは、1か所で定義したCSSカスタムプロパティ（トークン）で表します。部品やページのコードに色コードを直接書きません。Severityや状態の色は、第2章のカタログから同じトークンを参照します。
- **スタイルシートは1つにします。** ページや節ごとに `<style>` や `style=""` を追加しません。
- **レポート自体のアクセシビリティを守ります。** BeakSightは色のコントラストやアクセシビリティを監査するツールです。そのレポートが同じ基準を満たしていないと、信頼されません。`<html lang>`、見出しの階層、表の見出しセル、色だけに頼らない表現（バッジには文字も入れる）、十分なコントラストを、部品の段階で満たしてください。
- **部品ごとにテストを書きます。** カタログの全値が部品で描画できること、エスケープされること、危険なschemeがリンクにならないことを、部品の単位で確かめます。

## 4. 書式を1か所にまとめる

同じ種類の値は、どの表示面でも同じ書式で表示します。書式を決める関数は1つのモジュールにまとめます。

- 日時: JSONには ISO 8601 で保存します。表示は `Asia/Tokyo` とし、1つの書式関数で行います。
- 時間: ミリ秒（ms）と秒の使い分け、小数の桁数。
- データ量: バイトの単位（B / KB / MB）と桁数。
- 指標値: CLSは小数、LCPなどはms。観測できなかった値は、0や「良好」と表示せず、「未観測」と表示します（設計書 14.11）。
- 件数と割合: 桁区切りの有無、割合の小数の桁数。

## 5. 利用者向けの文言

- **Findingの `message` はRuleが持ちます。** 表示面でFindingの文言を作り直したり、言い換えたりしません。
- **理由コードと説明文を分けます。** 未完了、スキップ、ブロック、観測不能などの理由は、コードとして記録します。説明文への変換は、文言カタログの1か所で行います。表示面ごとに、同じ理由を別の言葉で説明してはいけません。
- **CLIの文言も1か所にまとめます。** 使い方の表示、設定エラーの説明、実行結果の要約は、文言カタログか、CLI内の1つの定義から出力します。スタックトレースは表示しません（Task 17 Step 3）。
- **終了コードの対応表は1つだけにします。** Run Statusから終了コードへの対応（設計書 第28章）と `CONFIG_ERROR = 4` は、1つの表で定義します。CLIの分岐やテストにも、この表から値を取ります。
- **表示言語は日本語です**（2026-09-23 ユーザー決定。UI追補設計書 第3章）。利用者に見せる文はすべて日本語にします。JSONのキー、各種ID、Severityや状態の値、理由コード、ファイル名は、機械が読む識別子なので英数字のままにし、表示するときに日本語のラベルに変換します。
- **CLIの日本語出力は、Windows PowerShellでも確かめます。** コンソールの文字コードの設定によって文字化けすることがあるためです（UI追補設計書 3.3）。

## 6. 仕組みで確かめる

ルールを文書に書くだけでは、実装が進むうちに崩れます。
そのため、UI追補設計書 第6章でUI Gate（GATE-UI01〜06）を定め、自動検査で確かめることにしました（2026-09-23 ユーザー承認）。
検査の内容と実装の時期は、UI追補設計書を参照してください。

UI Gateに限らず、開発のために追加する検査は、**速さを要件にします**。遅い検査は、待ち時間で生産性を落とすうえに、実行が省略されるようになって意味を失うからです（ユーザーの指示）。

- `tests/architecture/` の検査ファイルは、1ファイルあたり1秒以内に終わること。Vitestが表示する所要時間で判定する。
- 対象ファイルの読み込みは、テストファイルの中で1回だけ行い、各検査で共有する。
- Node.js標準の `fs`、正規表現、文字列の検索で判定する。TypeScriptのコンパイラAPI、AST解析、ESLintなどの外部ツール、新しい依存パッケージ、ブラウザや子プロセスの起動、ビルド結果（`dist/`）は使わない。
- 近似による誤検知は、除外の一覧に理由を付けて加えることで対処する。厳密さのために検査を重くしない。
- `npm test` と `npm run verify` で毎回実行される場所に置く。
- 実装したときと変更したときに所要時間を記録し、上限を超えたら不具合として扱う。
