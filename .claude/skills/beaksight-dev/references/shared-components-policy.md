# 共通部品と共通仕様のSSOT化

BeakSightでは、SSOT Owner Matrix（`2026-08-27-beaksight-implementation-tasks.md` 第5章）が、主要な意味（URL正規化、安全判定、Run Statusなど）のownerを定めています。
この文書は、それより細かい単位の共通部品にも同じ考え方を広げるための手順です。対象は、ユーティリティ関数、定数、上限値、理由コード、テスト用の準備処理などです。

同じ処理が2か所にあると、片方だけが直されて、振る舞いがずれていきます。
BeakSightでは、そのずれが「一部の経路だけ安全判定が甘い」「表示だけ件数が違う」といった、見つけにくい不具合になります。
共通化の目的は、コードの行数を減らすことではありません。**1つの変更が、1か所の修正で全体に正しく伝わる状態を保つこと**です。

---

## 1. 設計者が行うこと

### 1.1 共通部品台帳を持つ

設計者は `doc/design/beaksight-shared-components.md`（共通部品台帳）を更新し続けます。
台帳には、SSOT Owner Matrixに載っていない共通部品（型、定数、関数、テスト補助など）を載せます。
SSOT Owner Matrixと、UI追補設計書（`doc/design/2026-09-23-beaksight-ui-ssot-design.md`）第4章のownerは、台帳に書き写さず参照先だけを示します。書き写すと、台帳自体が重複の元になるためです。

新しい共通部品を設計で決めたら、台帳の「決定済みで、まだ作られていない共通部品」に追記します。実装が終わったら「既存の共通部品」に移します。

実装者への指示書には、台帳から「このサブタスクで使うべき共通部品」を抜き出して書きます。
実装者は台帳を知らない前提で指示してください。

### 1.2 設計の段階で共通部品を見つける

設計書を書くとき、新しく作るものについて次を確認します。

1. 同じ意味の処理や定数が、台帳やSSOT Owner Matrixにすでにないか。あれば、それを使う設計にする。
2. 今回作るものが、ほかのTaskでも使われる見込みがあるか。実装計画の後続Taskを読んで判断する。見込みがあれば、最初から共通部品として置き場所と名前を決める。
3. 既存の似た処理を、今回の変更に合わせて少しだけ変えた複製を作ろうとしていないか。その場合は、既存の処理を拡張する設計にするか、差分を引数として受け取る形にする。

「あとで共通化する」という判断は、その時点で共通化候補台帳（第3章）に記録した場合にだけ許されます。記録のない「あとで」は、実際には行われません。

### 1.3 新しいownerを作るとき

共通部品が、SSOT Owner Matrixにある意味と重なる場合は、新しい部品を作らず、既存のownerを使うか拡張します。
Owner Matrixにない新しい意味のownerを作る場合（例: 表示用モデル、表示カタログ、書式関数）は、設計書に記録し、台帳に載せ、ユーザーの承認を得てから実装に進みます。

## 2. 実装者に守らせること

実装者への指示書には、次の内容を毎回含めます（`implementer-brief-template.md` に組み込み済み）。

- 使うべき共通部品の一覧（台帳からの抜き出し）。
- 新しい関数、定数、型を作る前に、同じ意味のものが `src/` にないかを検索すること。
- 見つけた既存の処理が、指示された範囲の外にあって手を加えられない場合は、複製を作らずにBlockerとして報告すること。
- 共通部品の振る舞いを、呼び出し側で上書きしたり、補正したりしないこと。部品の振る舞いが合わないと感じたら、報告すること。

## 3. 共通化候補台帳

既存コードに重複を見つけたものの、今のサブタスクでは直さないものは、作業記録置き場の `commonization-candidates.md` に記録します。
重複そのものが不具合（片方だけ振る舞いが違う）になっている場合は、既存不具合として `defects.md` に登録します（SKILL.md 第5章）。

```markdown
## CC-NNN: <何が重複しているかを1行で>

- 状態: 登録済み / 設計中 / 対応済み / 対応しない
- 見つけた日と経緯: YYYY-MM-DD、<どの作業中に>
- 重複している箇所: `パス:行`、`パス:行`
- 違い: <完全に同じか、どこが違うか。違いが意図的かどうか>
- 放置した場合の影響: <片方だけ直されたら何が起きるか>
- 共通化の案: <置き場所と名前の案>
- 対応するサブタスク: <ID。未定なら「未定」>
```

共通化は、それ自体を1つの実装サブタスクとして扱います。
今のサブタスクの作業に混ぜると、何のための変更なのかが分からなくなるからです。

**着手の条件**: 台帳に登録した候補は、ユーザーが開発を明示的に指示するまで着手しません（2026-09-23のユーザーの指示）。設計者は、候補を見つけたら登録し、ユーザーへの報告の「残っている課題」に件数と重要なものを書くところまでにします。ただし、新しく書くコードで同じ重複を増やさないことは、候補の保留とは関係なく守ります。

### 3.1 振る舞いが違う重複をまとめるとき

名前や見た目が同じでも、振る舞いが少しずつ違う重複があります（例: 切り詰める長さが違う、例外を投げるか `null` を返すかが違う、「可視」の定義が違う）。
これを1つにまとめると、少なくとも片方の呼び出し元の振る舞いが変わります。
そのため、次の手順で進めます。

1. 設計者が、どの定義を正とするか、呼び出し元ごとの違いを残す必要があるか（引数で受け取るか）を設計書で決める。
2. 振る舞いが変わる呼び出し元について、変わる前の振る舞いを確かめるテストと、変わった後の振る舞いを確かめるテストを用意する。
3. 振る舞いの変化がEvidenceやFindingの内容に影響する場合は、スキーマの版やRuleの版（`ruleVersion`）を上げる必要があるかを判断する。

振る舞いの違いが意図されたものではなく、片方が誤っていると分かった場合は、既存不具合として扱います。

## 4. 共通化しすぎない

次の場合は、見た目が似ていても共通化しません。判断した理由を設計書に書いておいてください。

- **意味が違う場合**: たまたま同じ数値や同じ処理になっているだけで、変わる理由が別々のもの。例えば、Interactionの候補数の上限とクロールのページ数の上限は、どちらも数値の上限ですが、変わる理由が違います。1つの定数にまとめると、片方の変更がもう片方を壊します。
- **安全の境界をまたぐ場合**: Passive ContextとIsolated Interaction Contextは、意図的に分けられています（設計書 第6章）。コードが似ていても、両者の境界を越える共通部品を作るときは、安全性への影響を設計書で説明してください。
- **ブラウザ内とNode側で実行環境が違う場合**: `page.evaluate` に渡す関数は直列化されてブラウザ内で実行されるため、Node側のモジュールを import できません。ブラウザ内の処理を共通化するには、スクリプトを文字列として注入するなどの方式が必要です（前例: `src/evidence/performance-collector.ts` の `web-vitals` の注入）。方式、注入の単位、注入に失敗したときの扱いを設計書で決めてから共通化してください。上限値のように値だけを共有したい場合は、Node側で定義した値を `evaluate` の引数として渡す方式が使えます（前例: 各collectorの `*_LIMITS`）。
- **テストの見通しが悪くなる場合**: テストの準備処理を共通化しすぎると、各テストが何を前提にしているのかが読み取れなくなります。テスト補助にまとめるのは、準備と後片付けの手順（fixtureサーバやブラウザの起動と終了など）に留めます。検証の内容は各テストに書きます。

---

## 5. レビューの観点

独立レビューの担当には、次の観点を必ず含めます（`implementer-brief-template.md` に組み込み済み）。

- 台帳やSSOT Owner Matrixにある部品と同じ意味の処理を、新しく書いていないか。
- 定数や上限値を、定義元から参照せずに直接書いていないか。
- 状態や理由の文字列リテラルを、定義元の型から取らずに書いていないか。
- 表示面（report / cli / chatgpt bundle）で、集計や判定をやり直していないか。
