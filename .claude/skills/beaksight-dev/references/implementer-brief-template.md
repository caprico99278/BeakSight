# 実装者・レビュー担当への指示書テンプレート

サブエージェントは、このスキルの内容も、ここまでの会話も知りません。
指示書に書かなかったことは、存在しないものとして扱われます。
禁止事項と報告形式は省略せず、毎回そのまま含めてください。

指示書は作業記録置き場に `<サブタスクID>-brief.md`（修正依頼なら `<サブタスクID>-fix-round-N-brief.md`）として保存し、同じ内容をAgentツールの `prompt` に渡します。
Agentツールでは `subagent_type: "general-purpose"` と `model: "opus"` を使い、`isolation: "worktree"` は指定しないでください（HEADから作業ツリーが作られ、未コミットの作業が含まれないため）。
指示書はWriteツールで書いてください（Bashのヒアドキュメントは、本文の引用符で壊れることがあります）。

安全に関わるサブタスクでは、次の行も「守ること」に加えてください。

- 実験で中継（proxy）やサーバを作る場合は、上流と接続先を127.0.0.1（とloopback）だけに限る。外部のホストへ中継する作りにしない（調査担当が、Chromium自身の外部への接続を中継してしまったことがあります）。
- Chromiumはheadlessだけ。REDとGREENは、テストの既定のChromium（`chrome-headless-shell`）と、CLIの起動の設定（`launchCliChromium`、`chrome.exe`）の両方で確かめる。
- 一時のテストのファイルをリポジトリに置いた場合は、終わったら必ず消し、消したことを報告する。

見えない文字（ゼロ幅の文字、向きを変える文字、U+2028 など）を扱うサブタスクでは、次の行も加えてください。

- 編集の道具やシェルで、バックスラッシュ u と 16 進 4 桁の表記を書くと、実際の見えない文字に置き換わることがある。コードは文字コードの数値（`String.fromCharCode(0x202e)` など）で組み立てるか、書いた後にファイルを文字コードで確かめる。記録や報告では「U+202E」の書き方にする。

````markdown
1. RED: <追加するテストと、期待する失敗>

# 受け入れ条件

# 守ること

- Git: `git commit`、`git push` は禁止です。作業ツリーやファイルをHEADや過去の状態に戻す操作（`git checkout`、`git restore`、`git reset`、`git stash`、`git switch`、`git clean`、`git worktree`、`merge`、`rebase`、`pull` など）も禁止です。使ってよいのは表示だけの `git status`、`git diff`、`git log`、`git blame`、`git show` です。コミットされていない作業が大量にあり、HEADに戻すとそれが失われるためです。
- 不具合が「前からあったものか」を確かめるために、HEADの状態に戻して試すことはしないでください。現在の状態で再現した事実だけを報告してください。
- テストを削除したり、条件を弱めたり、skipにしたりしてPASSさせないでください。
- 設計書のSSOT ownerとは別の場所に、同じ判断や変換を実装しないでください。
- 新しい関数・定数・型・状態や理由の文字列を書く前に、同じ意味のものが `src/`（テストなら `tests/` と `fixtures/`）にないかを検索してください。あれば、それを使ってください。それが変更してよいファイルの外にあって使えない場合は、複製を作らずに止まり、Blockerとして報告してください。
- 上限値やタイムアウト値などの数値を、定義元から参照せずに直接書かないでください。
- 共通部品の振る舞いを、呼び出す側で上書きしたり補正したりしないでください。振る舞いが合わない場合は報告してください。
- HTMLレポート・CLI出力・ChatGPT用バンドルに関わる場合: 件数の集計、ラベル、色、書式、文言を、表示する側で独自に持たないでください。指定された表示用モデル・カタログ・部品を使ってください。
- `src/**` にtarget固有の名前・domain・URL・selectorを書かないでください。
- 依存パッケージを追加・更新しないでください。実際の監査対象サイトにアクセスしないでください。
- 実装計画に `git add` や `git commit` の手順が書かれていても、実行しないでください。
- 実行していないコマンドやテストをPASSと書かないでください。

# 止まるべきとき（Blocker）

次の場合は、自分で回避策を考えて進めず、その時点で作業を止めて報告してください。

- 設計書・実装計画と実際のコードが食い違っていて、どちらに合わせるか判断が必要なとき
- 計画どおりのテストがREDにならない、または計画どおりの実装でGREENにならないとき
- 変更してよいファイル以外を変更する必要があるとき
- SSOTの第二ownerや安全性の不変条件違反が必要になりそうなとき

# 範囲外の不具合を見つけたとき

今回のサブタスクとは別の原因による不具合を見つけた場合は、修正せずに報告の「発見事項」に書いてください。
その不具合のせいで今回のサブタスクが進められない場合は、Blockerとして報告してください。
同じ意味の処理や定数が複数の場所に重複しているのを見つけた場合も、まとめる作業はせずに「発見事項」に書いてください（該当箇所の `パス:行` と、振る舞いに違いがあるかどうか）。

# 報告

作業の最後に、以下の形式で、意味の通る日本語で報告してください。
英語は、識別子・ファイル名・コマンド・固有名詞に限って使ってください。
結論を先に書き、「何を、どう変え、その結果どうなったか」が一度読んで分かるように書いてください。

<ここに report-templates.md の「実装者の報告」または「Blocker報告」の形式を貼り付ける>
````

## レビュー担当向け

````markdown
あなたはBeakSightリポジトリ（`C:\Develop\github-repo\BeakSight`）の独立レビュー担当です。
ファイルを一切編集しないでください。確認のためのテスト実行と、表示だけのGitコマンド（`git status`、`git diff`、`git log`、`git show`、`git blame`）は使ってかまいません。HEADに戻す操作、commit、pushは禁止です。

# レビュー対象

- 設計書: `<パス>`
- 実装計画: `<パス>` の <サブタスク>
- 変更ファイル: `<一覧>`
- 実装者の報告: `<パス>`

# 観点

1. 設計書・受け入れ条件どおりに実装されているか
2. SSOT ownerの重複、`src/**` へのtarget固有情報の混入がないか
3. 読み取り専用の安全性の不変条件を破っていないか
4. テストが実装の誤りを本当に検出できるか（弱いテスト、skip、削除がないか）
5. 報告されたPASSが、実際に再実行しても成立するか
6. 共通部品台帳（`doc/design/beaksight-shared-components.md`）やSSOT Owner Matrixにあるものと同じ意味の処理・定数・状態や理由の文字列を、新しく書いていないか
7. 表示に関わる変更なら、集計・ラベル・色・書式・文言を表示面ごとに持っていないか。HTMLへ値を入れる箇所がすべてエスケープを通っているか（`.claude/skills/beaksight-dev/references/ui-ux-ssot.md`）
8. 安全に関わる変更なら、本物のfactoryとGuardで、127.0.0.1の自前のサーバに対して実機の実験を行い、読み取りでない要求や記録されない要求が届く経路が残っていないかを確かめる（前のレビューで確かめた経路の再実行と、新しく考えられる経路）。修正の前からある経路でも、Criticalとして報告する。両方のChromium（テストの既定と、CLIの起動の設定）で確かめる
9. 決まりの変更によるテストの直しが、弱体化になっていないか（漏れを検出する条件が残っているか）

# 報告

意味の通る日本語で、次の形式で返してください。

- 総合判定: 承認 / 修正が必要
- 指摘一覧: 各指摘に 重大度（Critical / Important / Minor）、該当箇所（`パス:行`）、問題の内容、そう判断した根拠、期待する状態 を書く
- 再実行したコマンドと結果
- 確認できなかった点
````

- 文字列や正規表現に Unicode のエスケープ（とくに向きを変える文字や行の区切り）を書いたときは、Edit・Write のツールが目に見えない生の文字に変えて保存していないかを確かめる（2026-10-12 CCX-3 の教訓）。

- 改行コードの注意（2026-10-12 追記）: Git Bash の `sed -i` と、Edit ツールの書き換えは、CRLF のファイルを LF に変えることがある。CRLF のファイルを書き換えたら、最後に `tr -cd '\015' < file | wc -c` と行の数で、CR の数が行の数と同じことを確かめる。CRLF のファイルに `sed -i` を使わない。
- 書き換えの道具の注意（2026-10-13 追記）: PowerShell 5.1 の `String.Split(string)` は区切りの文字列を文字の集まりとして扱うので、ファイルの書き換えに使わない（JavaScript の `String.replace` と同じく使わない）。
- 取得の注意（2026-10-14 追記）: `npx <パッケージ>` は、そのパッケージが依存にないと、npm の一時の置き場所にダウンロードして実行する（T31e で `npx tsx` が取得された）。これは依存の追加と同じく、ユーザーの事前の承認が要る。`npx` は、`package.json` の依存にある道具（`vitest`・`tsc` など）だけに使い、ほかの道具は使わない。TypeScript を直接動かしたいときは、`npm run build` の後の `dist/` を `node` で動かす。
