# 日本語の書き方

報告と設計書の読み手は、BeakSightの前提知識は持っていますが、書き手の頭の中までは知りません。
一度読んで意味が取れない文は、読み手に「たぶんこういう意味だろう」という推測をさせ、その推測が設計の誤解につながります。
次の点を、書き終えたあとの見直しで確認してください。

## 1. 結論を先に書く

読み手が最初に知りたいのは「終わったのか、終わっていないのか」です。経緯は後に回します。

- 悪い例: 「テストを実行したところ、guardのテストで失敗があったため調査した結果、原因はタイムアウト設定にあることが分かったので、設定を修正して再実行し、PASSしました。」
- 良い例: 「T2は完了しました。`passive-request-guard.test.ts` の1件が失敗していましたが、原因はタイムアウト値の不足で、値を修正して再実行し、全件PASSしました。」

## 2. 1つの文に1つの内容

「〜し、〜したが、〜ので、〜した」と続く長い文は、どこが主張なのかが分かりにくくなります。
読点で3つ以上の内容をつないでいたら、文を分けてください。

## 3. 主語と述語を対応させる

- 悪い例: 「この修正は、closeが失敗した場合に再試行できる。」（修正が再試行するわけではない）
- 良い例: 「この修正により、closeが失敗した場合に再試行できるようになる。」

## 4. 英語の使い方

英語をそのまま使ってよいのは、次のものに限ります。

- コード上の識別子（`deriveRunStatus()`、`AuditConfig`、`PASSIVE_ACTIVE`）
- ファイル名、コマンド
- 固有名詞（Playwright、Vitest、Node.js）
- プロジェクトで定着している用語（SSOT、owner、Blocker、Finding、Evidence、PASS / FAIL、RED / GREEN、fixture）

識別子は、文中で何のことか分かるようにバッククォートで囲みます。
英単語を助詞でつないだだけの文は、日本語として意味が通りません。

- 悪い例: 「guardのphaseをretryしてcloseをdrainする。」
- 良い例: 「Guardの状態が閉じ処理中のままなら、閉じ処理を再試行し、実行中のタスクがすべて終わるのを待つ。」

## 5. 「対応しました」で終わらせない

「対応しました」「修正しました」「確認しました」だけでは、何をしたのかが伝わりません。
何を、どう変え、その結果どうなったかを書きます。

- 悪い例: 「指摘事項に対応しました。」
- 良い例: 「指摘1について、`discover-candidates.ts` の祖先要素の走査も共通の作業量上限に含めるよう変更しました。追加したテスト `shares ancestor budget` がPASSすることを確認しました。」

## 6. 事実と推測を分ける

実行して確かめたことと、そうだろうと考えていることを、文の形で区別します。

- 事実: 「`npm run verify` を実行し、全件PASSしました。」
- 推測: 「原因は、Contextを閉じる前にリスナーが解除されていないことだと考えられます（未確認）。」

## 7. 曖昧な言葉を避ける

「適切に」「うまく」「なるべく」「など」「いい感じに」は、判断を読み手に丸投げする言葉です。
設計書や指示書では、何をもって適切とするのかを具体的に書いてください。

- 悪い例: 「エラーを適切に処理する。」
- 良い例: 「タイムアウトした場合は `status: 'TIMED_OUT'` を返し、Safety Ledgerに記録する。例外は投げない。」

## 8. 重複した言い回しをしない

- 「〜を実施を行う」→「〜を実施する」
- 「まず最初に」→「最初に」
- 「〜することができる」→ 多くの場合「〜できる」で足りる

## 9. 見直しの手順

1. 最初の3行だけを読み、結論が分かるか。
2. 50字を超える文を探し、分けられないか。
3. 英単語が続く箇所を探し、日本語で言い換えられないか。
4. 「対応」「適切」「など」を探し、具体的に書けないか。
5. 確認していないことを、確認済みのように書いていないか。
