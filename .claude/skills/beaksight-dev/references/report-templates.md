# 報告・台帳の形式

報告は、読み手が次に何をすべきかを判断するための材料です。
うまくいったことより、終わっていないこと・確認できていないことのほうが読み手にとって重要なので、隠さずに書いてください。

---

## 実装者の報告

```markdown
# <サブタスクID> 実装報告

## 結論

完了 / 一部完了 / Blocker で停止
<1〜3文で、何ができて何ができていないか。>

## 変更したファイル

| パス | 変更の内容 |
| --- | --- |
| `src/...` | <何をどう変えたか> |

## TDDの記録

- RED: `<コマンド>` → 失敗（<失敗した理由。期待どおりの理由で失敗したか>）
- GREEN: `<コマンド>` → PASS（テスト数 N、失敗 0、終了コード 0）
- 関連する検証: `<コマンド>` → <結果>

## 受け入れ条件の確認

- [x] <条件> — <確認方法と結果>
- [ ] <条件> — <満たせなかった理由>

## 発見事項

<範囲外の不具合、設計書との小さな食い違い、気になった点。なければ「なし」。>

## 未実行項目

<なければ「なし」。あれば下の「未実行項目」の形式で。>
```

---

## Blocker報告

```markdown
# <サブタスクID> Blocker報告

## 止まった箇所

<手順の何番目で、どのファイルのどの処理に取り組んでいたときか。>

## 何が起きたか

<観察した事実。実行したコマンドとその出力の要点。推測は含めない。>

## なぜ進めないのか

<設計書・実装計画のどの記述と、実際のどの状態が食い違っているか。>

## 考えられる選択肢

1. <選択肢> — <その場合の影響>
2. <選択肢> — <その場合の影響>

（どれを選ぶかは設計者が決めます。実装者は選択肢を示すだけにしてください。）

## 停止時点の作業ツリーの状態

- 変更済みのファイル: <一覧。途中まで変更したものも含める>
- 追加したテストの状態: <RED / GREEN / 未実行>
```

---

## 設計者からユーザーへの報告

ユーザーには、次の順で報告します。短い作業なら、該当しない節は省いてかまいません。ただし「未実行項目」と「残っている課題」は、なければ「なし」と明記してください。

```markdown
## 結論

<何が終わり、何が終わっていないか。1〜3文。>

## 実施内容

- <サブタスクID>: <何をどう変えたか。結果>

## 設計の変更

<Blockerや既存不具合によって設計書を変えた場合、その理由と内容。変更した設計書のパス。なければ「なし」。>

## 検証結果

| コマンド | 結果 | テスト数 | 失敗数 |
| --- | --- | --- | --- |
| `npm run verify` | PASS | ... | 0 |

## 未実行項目

<なければ「なし」>

## 残っている課題

<未解決のBlocker、未修正の既存不具合（DEF-NNN）、ユーザーの判断が必要な事項。なければ「なし」。>
```

---

## 未実行項目

実行できなかったコマンド、テスト、Gateは、1件ずつこの形式で書きます。

```markdown
- コマンド: `<コマンド>`
  - 実行しなかった理由: ...
  - 影響: <これを実行しないことで、何が確認できていないか>
  - 完了を妨げるか: はい / いいえ
```

---

## 不具合台帳（`defects.md`）

```markdown
# 不具合台帳

## DEF-001: <現象を1行で>

- 状態: 登録済み / 設計中 / 実装中 / 修正済み
- 発見日: YYYY-MM-DD
- 発見した経緯: <どのサブタスクの作業中に、誰が見つけたか>
- 現象: <何が期待と違うか>
- 再現手順: <現在の作業ツリーで再現できるコマンドや条件>
- 影響範囲: <影響するモジュール、機能、Gate>
- 発生時期の推測: <`git log`・`git blame` の表示やコードを読んだ結果からの推測。HEADに戻しての確認は行わない。不明なら「不明」>
- 対応する設計: `<設計書のパスと節>`
- 対応するサブタスク: <ID>
- 検証結果: <修正後に実行したコマンドと結果>
```

---

## 進捗台帳（`progress.md`）への追記

サブタスクが1つ終わるたび、または状態が変わるたびに、末尾に追記します。過去の記述は書き換えず、訂正する場合も追記で行います。

```markdown
### YYYY-MM-DD <サブタスクID>: <状態>

- 内容: ...
- 判断（Ruling）: <設計者が下した判断と、その理由。誤っていた場合の影響>
- 検証: <コマンドと結果>
- 次の作業: ...
```
