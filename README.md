# BeakSight

BeakSight は、公開 Web サイトを読み取り専用で自動巡回し、機械的に判定できる異常を検出するツールです。
検出した異常と、その根拠の証跡（Evidence）を、構造化したデータとして書き出します。
書き出したデータは、後段の意味監査（例: ChatGPT への手動アップロード）に使えます。

固定の URL の一覧や、固定の DOM の selector に依存した E2E テストは、サイトを改修するたびに直す必要があります。
BeakSight は、開始の URL から、許可した Origin（`site.allowedOrigins`）の中でたどれるページを自動で見つけます。
人が公開サイトを巡回して確かめる作業のうち、機械的に判定できる範囲を、Playwright で自動化します。
BeakSight は、文章の自然さや配色の美しさのような、意味や美的な判断はしません。
パフォーマンス、アクセシビリティ、レイアウト、インタラクションなどの証跡を出力することに専念します。

設計の詳細は [doc/design/](doc/design/) を参照してください。

## 必要なもの

- Node.js 24（`package.json` の `engines` は `>=24 <25`）
- 依存パッケージ
- Playwright の Chromium（Chromium だけを使います。ほかのブラウザは入れなくてかまいません）

```bash
npm install
npx playwright install chromium
npm run build
```

CLI は、ビルドした `dist/cli/index.js` を Node.js で実行します。

BeakSight は、headless で実行するときも、Playwright に同梱の通常の Chromium（`channel: 'chromium'`）を、新しい headless の方式で使います。
これは `npx playwright install chromium` で入るもので、追加の準備は要りません。
headless の既定のブラウザ（`chrome-headless-shell`）を使わないのは、Windows では、そのブラウザが Ctrl+C を受けて終わってしまい、1回目の Ctrl+C で今のページを監査し終えられないためです（「[中断と再開](#中断と再開)」の「Ctrl+C で止める」）。

## 使い方

```bash
node dist/cli/index.js <コマンド> [オプション]
```

### コマンド

| コマンド | 内容 |
| --- | --- |
| `validate-config` | 設定を読み、誤りがないかを確かめます。監査は実行しません。ブラウザも起動しません。 |
| `run` | 設定を読み、監査を実行して、結果を出力先に書き出します。 |

### オプション

| オプション | 内容 |
| --- | --- |
| `--config <パス>` | 対象の設定のファイル。省略した場合の扱いは「[監査の対象の設定](#監査の対象の設定)」を参照してください。 |
| `--output <ディレクトリ>` | 出力先のディレクトリ。設定の `output.directory` を上書きします。 |
| `--headed` | ブラウザの画面を表示して実行します。設定の `browser.headed` を上書きします。使う前に「[headed で実行するときの注意](#headed-で実行するときの注意)」を読んでください。 |
| `--headless` | ブラウザの画面を表示せずに実行します。設定の `browser.headed` を上書きします。 |
| `--new` | 途中の Run があっても、続きから再開せずに、新しい Run を始めます（`run` のときだけ）。「[中断と再開](#中断と再開)」を参照してください。 |
| `--help` | 使い方を表示します。設定は読まず、監査も実行しません。終了コードは 0 です。 |

- `--headed` と `--headless` は、同時に指定できません。同時に指定すると、設定のエラー（終了コード 4）になります。
- `--new` は、`run` だけのオプションです。`validate-config` で指定すると、設定のエラー（終了コード 4）になります。`--new` は値を取りません（`--new=yes` のように値を付けると、設定のエラーになります）。
- 値を取るオプション（`--config`、`--output`）を2回以上指定すると、設定のエラー（終了コード 4）になります。後の値で上書きすることはしません。
- 知らないオプション、値のないオプション、余分な引数、知らないコマンドも、設定のエラー（終了コード 4）になります。このとき、使い方も表示します。
- `--help` は、ほかの引数を解析できれば、コマンドの有無によらず使い方を表示します。
- どちらのオプションも指定しない場合は、設定の `browser.headed` に従います。既定値は `false`（headless）です。

### 例

```bash
# 使い方を表示する
node dist/cli/index.js --help

# config/targets/ の中の、ただ1つの設定を確かめる
node dist/cli/index.js validate-config

# 設定のファイルを指定して確かめる
node dist/cli/index.js validate-config --config config/targets/example.json

# 監査を実行する（headless を勧めます）。途中の Run があれば、続きから再開します
node dist/cli/index.js run --config local/targets/<対象名>.json --headless --output artifacts

# 途中の Run があっても、続きから再開せずに、新しい Run を始める
node dist/cli/index.js run --config local/targets/<対象名>.json --headless --output artifacts --new
```

`validate-config` が成功すると、次のように表示します。

```text
設定に、誤りはありません。
対象: example
開始の URL: https://example.com/
```

## 中断と再開

監査（Run）が途中で止まっても、同じコマンドをもう一度実行すると、続きから監査します。監査を終えたページは、監査し直しません。
BeakSight は、ページの読み込みの間隔を空けるので（「[サイトへの負荷](#サイトへの負荷)」）、full audit には何時間もかかることがあります。最初からやり直すと、同じページを読み込み直し、サイトに余計な負荷をかけるためです。

### 自動の再開

`run` を起動すると、Run を始める前に、出力先（`output.directory`、または `--output`）の中から、同じ対象の最も新しい Run を探します。
その Run が途中で終わっていて、次の条件をすべて満たす場合は、新しい Run を始めずに、続きから再開します。

- 同じ対象（`target.id`）の Run のうち、最初の起動の開始が最も新しい Run であること。それより古い途中の Run は、再開しません。
- 実効の設定（設定のファイルに、既定値と CLI の上書きを適用した後の設定）が、完全に同じであること。`--headed`・`--headless` による上書きも比べます。ただし、出力先（`output.directory`、`--output`）は比べません。出力先は途中の Run を探す場所そのものなので、書き方が違っても（例: `artifacts` と `C:\path\to\BeakSight\artifacts`）、同じ出力先の途中の Run を再開します。
- BeakSight と Playwright の版が、途中の Run を始めたときと同じであること。

再開するときは、開始の行（`監査を始めます。`）の前に、次のように表示します。

```text
途中の Run（RUN-20261001000000。監査を終えたページ 3件）を、続きから再開します。最初から始めるには --new を付けてください。
```

続きから監査しない場合は、次のように表示します。

| 場合 | 表示 | 動き |
| --- | --- | --- |
| 最も新しい Run が、違反を検出した後の途中の Run | `途中の Run（RUN-20261001000000）は、安全の不変条件の違反を検出した後のため、新しいページを監査せずに、最後の処理だけを行います。` | 新しいページを監査せずに、最後の処理（結果のファイルの書き出し）だけを行います。 |
| 最も新しい Run の設定が違う | `設定が違うため、途中の Run（RUN-20261001000000）は再開しません（違う項目: crawl.maxPages）。新しい Run を始めます。` | 新しい Run を始めます。違う項目は5件まで示し、残りは件数（例: `ほか 2 件`）で示します。 |
| 再開のための保存を読めない Run がある | `途中の Run（RUN-20261001000000）の再開のための保存を読めないため、再開の対象にしません。` | その Run は再開しません。ほかに再開する Run がなければ、新しい Run を始めます。 |
| 最も新しい Run の版が違う | `途中の Run（RUN-20261001000000）は、版が違うため再開できません（BeakSight の版: 保存 0.1.0 → 今 0.2.0）。最初から始めるには --new を付けてください。` | 監査を始めずに終えます（終了コード 4）。 |

- 最も新しい Run を最後まで終えている場合は、何も表示せずに、新しい Run を始めます。
- 最も新しい Run が、最初の再開のための保存（robots.txt と sitemap.xml の取得の後）を書く前に止まった場合と、その Run の保存が壊れていた場合は、その Run を最も新しい Run として数えません。そのため、それより古い途中の Run を再開することがあります。
- 再開した Run は、Run の ID と Run のディレクトリを、そのまま使います。最後の処理（ページ間の Rule、Run の状態、結果のファイルの書き出し）は、再開の前と後のすべてのページで行います。結果は、中断しなかった場合と同じになります（時刻と、起動の記録を除きます）。
- 監査の途中だったページは、最初から監査し直します（そのページのディレクトリ `pages/<pageId>/` を消してから、監査します）。そのページの分だけ、サイトへの読み込みが重なります。
- 再開した起動でも、ページの読み込みの間隔は、前の起動の最後の読み込みの開始から数えて、`crawl.minNavigationIntervalMs` 以上空けます。サイトへの負荷の記録（`run.json` の `load`）も、前の起動の分から続けて数えます。

### 途中の Run になる場合と、ならない場合

| 前の起動の終わり方 | 次に同じコマンドを実行したとき |
| --- | --- |
| プロセスが途中で終わった（強制終了、停電、端末の再起動、2回目の Ctrl+C、Windows で端末のウィンドウを閉じた場合など） | 続きから監査します。 |
| 1回目の Ctrl+C で、今のページを終えてから止めた | 続きから監査します（止めたために監査しなかったページを、監査します）。 |
| 実行時間の上限（`crawl.maxRuntimeMs`）で止まった | 続きから監査します（上限のために監査しなかったページを、監査します）。 |
| サイトが応答しないため止まった（「[サイトが応答しないとき](#サイトが応答しないとき)」） | 続きから監査します（不調を検知したページから、監査し直します）。 |
| 安全の不変条件の違反を検出した | 新しいページは監査しません。最後の処理を終える前にプロセスが終わっていた場合は、最後の処理だけを行います。最後の処理を終えていた場合と、最後の処理で結果のファイルを書き出せなかった場合は、新しい Run を始めます（結果のファイルも再開のための保存の終わりも書けなかった場合は、再開することがあります。下の項目を参照）。 |
| 最後まで終えた（`COMPLETE`）、ページ数・深さの上限で終えた（`PARTIAL`）、`FAILED` で終えた | 再開しません。新しい Run を始めます。範囲を広げたい場合（`crawl.maxPages` を大きくするなど）も、新しい Run になります。 |

- 再開した起動で、実行の前の確認（PREFLIGHT）に失敗した場合（サイトに一時的につながらない場合など）は、それまでの監査を失わないよう、再開のための保存をそのまま残します。次に同じコマンドを実行すると、また続きから再開します。
- 実行の途中で、再開のための保存を書けなかった場合は、残りのページを監査せずに（理由 `CHECKPOINT_WRITE_FAILED` のスキップ）、確認できた範囲の結果を書き出します。保存は、最後に書けたものが残ります。次に同じコマンドを実行すると、そこから再開します。
- 止まった Run の結果のファイル（`run.json`、`report.html` など）は、止まった時点のものです。再開して最後まで終えると、全ページの結果で書き直します。
- 安全の不変条件の違反を検出した Run は、最後の処理で結果のファイルを書き出せなかった場合も、再開しない状態にします。違反の後に、監査を続けないためです。ただし、結果のファイルも、再開のための保存の終わりも書けなかった場合は、次に同じコマンドを実行すると、再開することがあります。その場合も、Guard と違反の確かめは同じく働きます。違反のない Run で結果のファイルを書き出せなかった場合は、再開のための保存を変えません。次に同じコマンドを実行すると、最後に書けた保存から再開し、結果のファイルを書き出し直します。
- 安全の不変条件の違反を記録してから、そのページの再開のための保存を書くまでの間にプロセスが終わった場合（2回目の Ctrl+C、停電など）は、違反は保存に残りません。次に同じコマンドを実行すると、そのページを最初から監査し直します。Guard と違反の確かめは同じく働くので、同じ違反が起きれば、そこで止まります。

### `--new`

`--new` を付けると、途中の Run を探さずに、新しい Run を始めます。

- 途中の Run のディレクトリは、消さずに残します。
- `--new` で始めた Run が、同じ対象の最も新しい Run になります。そのため、それより前の途中の Run は、その後も再開しません。
- 同じ出力先で別の Run が実行中の場合は、`--new` を付けても、新しい Run を始めません（終了コード 4）。

### Ctrl+C で止める

| 押した回数 | 表示 | 動き | 終了コード |
| --- | --- | --- | --- |
| 1回目 | `中断を受け付けました。今のページの監査を終えてから止めます。すぐに止めるには、もう一度押してください。` | 今のページの監査を、再試行を含めて最後まで行い、新しいページを始めません。残りのページを理由 `RUN_INTERRUPTED` のスキップにして、確認できた範囲の結果を書き出します。 | Run の状態のとおりです。ふつうは一部未完了（`PARTIAL`）の 2 です。 |
| 2回目 | `すぐに止めます。再開のための保存は、最後に監査を終えたページまで残っています。同じコマンドを実行すると、続きから再開します。` | すぐに止めます。結果のファイルは書き出しません。再開のための保存は、最後に監査を終えたページまで残ります。 | 5（中断） |

- どちらの場合も、同じコマンドを実行すると、続きから再開します。
- 3回目以降は、何もしません。
- SIGTERM と SIGHUP も、Ctrl+C（SIGINT）と同じに扱います。種類が違っても、合わせて数えます（1回目が Ctrl+C、2回目が SIGTERM でも、2回目として扱います）。
- Windows で端末のウィンドウを閉じると、OS が数秒でプロセスを終えます。そのため、今のページの監査を終えてから止まるとは限りません。その場合は、プロセスが途中で終わった場合と同じく、次に同じコマンドを実行すると、続きから再開します。
- 1回目の後は、今のページの監査が終わるまで待ちます。1つのページの監査は、ページの監査の期限（`crawl.overallPageTimeoutMs`）と再試行の回数の上限があるので、必ず終わります。
- 1回目を押したときに、残りのページがなかった場合は、そのまま最後まで終えた Run になります（`COMPLETE` になることもあります）。
- headed（`--headed`）の Run では、ブラウザの画面（タブやウィンドウ）を閉じたり、読み込みを停止したり、再読み込みしたりしないでください。止めるときは、端末で Ctrl+C を使ってください。
  - 画面を閉じると、安全の不変条件の違反（`CDP_SESSION_DETACHED`）として Run が止まり（`ABORTED_BY_SAFETY`、終了コード 3）、再開できないことがあります。
  - 停止、再読み込み、別の URL への移動は、多くの場合は、違反になりません。その場合も、そのページの監査は、失敗になることがあります。ただし、Interaction の確かめの途中などでは、安全の不変条件の違反として Run が止まり（`ABORTED_BY_SAFETY`、終了コード 3）、再開できないことがあります。

### 実行時間の上限は1回の起動ごと

- `crawl.maxRuntimeMs` は、1回の起動ごとの実行時間の上限です。再開した起動は、その起動の開始から数えます。止まっていた時間は数えません。
- 上限に達すると、新しいページの監査を始めません。残りのページを理由 `MAX_RUNTIME_REACHED` のスキップにして、確認できた範囲の結果を書き出します（一部未完了、終了コード 2）。
- 同じコマンドを実行すると、続きから再開します。full audit を、何回かの起動に分けて行うこともできます。
- `run.json` の `crawlLimits.maxRuntimeReached` は、最後の起動で上限に達したかを示します。

### サイトが応答しないとき

BeakSight は、サイトの不調（メンテナンス中で応答しない、接続できない、503 を返すなど）を検知したら、それ以上の読み込みを送らずに、再開できる状態で止まります。応答できないサイトに、読み込みを送り続けないためです。

- 対象は、BeakSight が自分で始めるページの読み込みです（Passive のデスクトップとモバイル、幅の走査の各幅、Interaction の各候補、robots.txt と sitemap.xml の取得）。ページが読み込む画像などの部品の要求と、許可 Origin の外への要求は、対象にしません。
- サイトの不調を検知したら、そのページの残りの読み込み（次のビューポート、幅の走査の次の幅、Interaction の次の候補、同じページの再試行）を始めません。ページの監査で検知した場合は、そのページを捨てて待ち、同じページを確かめ直します（待ちは 60 秒から段階的に延ばし、1 ページにつき最大 4 回。下の「段階的に確かめ直す」）。最後の確かめ直しでも不調なら、新しいページを始めずに止めます。

次の失敗だけを、サイトの不調とみなします。

| 失敗 | 例 |
| --- | --- |
| 読み込みの時間切れで、ページの応答（ヘッダ）を1つも受けていないもの | サーバが応答しない |
| ネットワークの層の失敗 | `net::ERR_CONNECTION_REFUSED`、`net::ERR_CONNECTION_RESET`、`net::ERR_NAME_NOT_RESOLVED`、証明書の失敗（`net::ERR_CERT_` で始まるもの）、本文の途中の切断（`net::ERR_CONTENT_LENGTH_MISMATCH`） |
| HTTP の status が 429、502、503、504 の応答 | メンテナンス中の 503。読み込みが終わった場合も、時間切れの場合も同じです |

次の失敗は、サイトの不調とみなしません。今までどおり、そのページの失敗として記録し、監査を続けます。

- 応答（ヘッダ）を受けた後の時間切れ（status が 429、502、503、504 の場合を除きます）。本文や部品の読み込みが遅いなど、そのページの重さによるものです。
- HTTP の status が 500 と、429 を除く 4xx の応答。そのページだけの問題のことが多いためです。
- `net::ERR_ABORTED`（ブラウザやページの都合で、読み込みが取り消されたもの）。

段階的に確かめ直す決まりは、次のとおりです。個々の要求だけがサーバ側で応答されない場合や、無応答が数分続く場合（サイト全体は止まっていない場合）に、起動し直さずに済ませるためのものです。

- ページの監査で不調を検知したら、そのページを捨てて（途中までの監査の結果は残しません）、待ちます。待つ時間は、1 回目の確かめ直しの前が 60 秒、2 回目が 2 分、3 回目が 4 分、4 回目が 8 分です（1 ページにつき最長で約 15 分。表示では秒で書きます: `60秒`、`120秒`、`240秒`、`480秒`）。待っている間は、サイトへ何も送りません。待つ時間と回数は変えられません（設定の項目にすると、途中の Run を続きから再開できなくなるためです）。
- 待っている間に Ctrl+C を押すと、待ちを打ち切り、確かめ直さずに止めます（再開できる状態で止まります）。待っている間に実行時間の上限（`crawl.maxRuntimeMs`）に達した場合も、確かめ直さずに止めます。待った時間は、実行時間に含めます。
- 待った後、同じページをもう 1 回、最初から監査します（通常の監査と同じです。読み込みの間隔も同じく守ります）。不調がなければ、その結果を残して、続きのページを監査します。Run の理由には何も残りません（捨てた試行の記録は、下の診断の記録に残ります）。
- 確かめ直しで通った後は、ページの読み込みの間隔（`crawl.minNavigationIntervalMs`）を、それまでの 2 倍に延ばして続けます（戻ったばかりのサイトへの負荷を下げるためです）。上限は設定の 8 倍です（既定の 5 秒なら 40 秒）。確かめ直しで通るたびに 2 倍にし、上限に達したら、それ以上は延ばしません。延ばした間隔は、その起動の間だけです。保存しないので、Ctrl+C で止めてから再開した次の起動は、設定の値から始まります。`run.json` の `load.minNavigationIntervalMs` は設定の値のままで、実際に待った時間は `load.pacingWaitMs` に表れます。
- 確かめ直しでまた不調なら、次の段階の待ちで待ってから、もう 1 回確かめ直します。4 回目の確かめ直しでも不調なら、下のとおり止めます。確かめ直しは、1 回の起動の中で、同じページにつき最大 4 回です。確かめ直しで通ったページとは別のページが、その後に不調になった場合は、そのページで 1 回目（60 秒）から確かめ直します。
- 前の起動で止まるきっかけになったページ（下の「同じページで止まり続けないために」）と、robots.txt と sitemap.xml の取得では、確かめ直しません。
- 確かめ直すときと、通った後に間隔を延ばすときは、実行中の表示に、次の行を出します（例は 1 回目と 2 回目の確かめ直しと、既定の 5 秒からの減速）: `サイトが応答しないため、60秒待ってから同じページを確かめ直します（1/4 回目。<ページの URL>）。`、`サイトが応答しないため、120秒待ってから同じページを確かめ直します（2/4 回目。<ページの URL>）。`、`確かめ直しで応答が戻ったので、ページの読み込みの間隔を 10秒 に延ばして続けます。`

止めたときの結果は、次のとおりです。

- 不調を検知したページ（最後の確かめ直しでも不調だったページ）は、途中までの監査の結果を残さずに、理由 `SITE_UNAVAILABLE` のスキップにします。再開のときに、そのページを最初から監査し直します。
- 残りのページも、理由 `SITE_UNAVAILABLE` のスキップにします。
- Run の理由（`run.json` の `incompleteReasons`）に、`SITE_UNAVAILABLE` を1件加えます。`detail` は、止めた試行で最初に検知した失敗です（例: `desktop:passive:TIMEOUT`、`mobile:passive:HTTP 503`。robots.txt と sitemap.xml の取得では `site-metadata:TIMEOUT` など）。
- Run の状態は一部未完了（`PARTIAL`）、終了コードは 2 です。`run.json` の `executions` の最後の `endReason` は `STOPPED_BY_SITE_UNAVAILABLE` です。CLI の結果には、止めたことを1行で表示します（「[CLI の表示](#cli-の表示)」）。
- robots.txt か sitemap.xml の取得で不調を検知した場合は、ページの監査を始めません（robots.txt で検知した場合は、sitemap.xml も読み込みません）。取得の結果は保存せず、再開のときに取得し直します。
- 同じ起動で、安全の不変条件の違反も検出した場合は、違反を優先します（`ABORTED_BY_SAFETY`。再開しません）。

サイトが戻ってから、同じコマンドを実行してください。不調を検知したページから、続きを監査します。

同じページで止まり続けないために、次の決まりがあります。

- 前の起動で止まるきっかけになったページが、次の起動でもまた不調になった場合は、確かめ直さずに、そのページを失敗（または一部未完了）の結果として残して止めます。次の再開では、そのページを監査し直さずに、続きのページを監査します。1つのページだけが、いつも応答しない場合のための決まりです。
- そのため、サイトが戻る前に再開すると、そのページは失敗として残ります。再開は、サイトが戻ってから行ってください。
- robots.txt と sitemap.xml の取得も同じです。前の起動がその取得で止まり、次の起動でもまた不調になった場合は、取得の失敗を記録して止めます。次の再開では、取得し直さずに、ページの監査へ進みます。

既知の限界: BeakSight が、ページの応答を受けたと分かるのは、ヘッダを受けたときではなく、本文の始まりを受けた後です。そのため、次のことがあります。

- ヘッダだけを送り、本文を読み込みの期限まで送らないページは、応答のない時間切れとみなし、サイトの不調として止まります。status が 503 などでも同じです。
- 本文の始まりが、読み込みの期限の直前（約 0.5 秒の間）に届いた場合も、同じく止まることがあります。
- どちらも、サーバが本文を返せていない状態なので、止めることは、サイトへの負荷の方針（「[サイトへの負荷](#サイトへの負荷)」）に合います。同じページで止まり続けることは、上の決まりで防ぎます。そのページのために、起動が最大2回余分にかかります。

ページの監査で不調を検知したときは、原因（サイト側か、BeakSight 側か）を調べるための診断の記録を、Run のディレクトリの `diagnostics/site-unavailable-<pageId>-<実行の番号>-<試行の番号>.json` に書きます（「[出力の構成](#出力の構成)」）。

- 書くのは、不調を検知したページを捨てたとき（1 回目と、不調だった各確かめ直しの、それぞれの試行）と、前の起動で止まるきっかけになったページを、また不調のため失敗の結果として残したときです。robots.txt と sitemap.xml の取得で止めたときは、書きません。
- `<実行の番号>` は、その Run の何回目の起動か（`run.json` の `executions` の何件目か）です。1から数えます。同じページが別の起動でまた止まった場合は、別のファイルになります。
- `<試行の番号>` は、その起動の中で、そのページを何回目に監査したかです。捨てた 1 回目が 1、確かめ直しが 2〜5 です。確かめ直しで通った場合は、不調だった試行のファイルだけが残ります。
- 中身は、そのページの監査の結果（`page`。捨てたページでは、出力の結果に残らない、その監査の結果です）と、ページ本体の要求の観察（`navigationDiagnostics`）です。観察は、ビューポート（デスクトップとモバイル）ごとに、Passive の読み込み（`passive`）のほか、幅の走査の各幅の読み込み（`stressWidths[]`。`width` は幅）と、Interaction の各候補の読み込み（`interactionCandidates[]`。`index` は候補の順の番号で、0 から数えます）ごとにあります。読み込みを始めなかった幅と候補は、並びに入りません。読み込みを始めなかったビューポートは `null` で、Passive の読み込みを始められなかったビューポートは `passive` が `null` です。観察を始められなかった場合は、`status` が `NOT_OBSERVED` で、`reason` に理由があります。
- 記録の形の版（`schemaVersion`）は `site-unavailable-diagnostic-schema/1.1` です。

ページ本体の要求の観察は、1つの読み込みの観察（`navigationDiagnostics.<ビューポート>.passive`、`navigationDiagnostics.<ビューポート>.stressWidths[].diagnostics`、`navigationDiagnostics.<ビューポート>.interactionCandidates[].diagnostics`）の `documentRequests[].hops[]`（リダイレクトでたどった要求も、同じ要求の続きとして並べます）の、次の2つの時刻で読みます。時刻は、UNIX エポックからのミリ秒です。

| 要求のヘッダを送った時刻（`requestHeadersSentAtMs`） | 応答のヘッダを受けた時刻（`responseHeadersReceivedAtMs`） | 読み方 |
| --- | --- | --- |
| あり | なし | 要求はネットワークへ送られましたが、応答がありませんでした。サイト側か、経路の問題です。 |
| なし | なし | 要求はネットワークへ送られませんでした。BeakSight 側か、接続の段階の問題です。 |
| なし | あり | ネットワークを通らずに応答を得ました（キャッシュなど）。 |
| あり | あり | 応答を受けました。`httpStatus` は、その応答の status です（例: メンテナンス中の 503）。 |

- 診断の記録は、結果のファイルではありません。原因を調べるための、付けたしの情報です。Run Status、件数、HTML レポート、ChatGPT 用のバンドルには入りません。書けなかった場合も、監査は今までどおり続けます。
- Run を最後まで終えたときの片付け（`checkpoint/` の中だけを消します）では、消えません。要らなくなったら、手で消してかまいません。
- ページ本体の要求の観察（`navigationDiagnostics`）には、要求と応答の header の中身（Cookie など）と、本文を記録しません。記録するのは、上の時刻、`httpStatus`、接続先の IP アドレスと port などです。
- そのページの監査の結果（`page`）には、出力のページの結果（`page.json`）と同じ network の Evidence が入ります。決まった一部の header の値を含みます。Cookie、`Set-Cookie`、`Authorization` などの機微な header の値は、`[REDACTED]` に置き換えます。

### 同時に実行できる Run

- 同じ出力先では、同時に1つの Run だけを実行できます。別の Run が実行中の場合は、再開も新しい Run もせずに、終了コード 4 で終えます。対象が違っても同じです。同じ対象の Run を2つ同時に動かすと、サイトへの負荷が倍になるためです。
- この決まりは、起動の間が空いている場合のものです。2つの起動をほぼ同時に行うと、ロックを作るまでの間に、両方が実行中の Run の確かめを通り、両方が Run を始めることがあります。同じ出力先で、2つの起動をほぼ同時に行わないでください。

```text
同じ出力先で、別の Run（RUN-20261001000000）が実行中です。その Run が終わってから実行してください。
```

- 実行中かどうかは、Run のディレクトリのロック（`checkpoint/run.lock`）で判断します。ロックは、実行中は1分ごとに更新します。次のどれかに当たるロックは、実行中の Run のものではなく、前の起動が途中で終わった印とみなします（その Run を再開するときは、ロックを作り直します）。
  - 端末を再起動した後である（ロックに記録した OS の起動の時刻が、今の OS の起動の時刻と120秒より大きく違う）。
  - ロックを作ったプロセスが、動いていない。
  - 最後の更新から、5分より長く経っている。
- 同じ Run を、同時に2回起動しないでください。2つの起動を、同じ Run に対してほぼ同時に行うと、両方が再開を始めることがあります（防ぎきれません）。
- 再開を始めようとしたときに、次のように表示した場合は、監査を始めずに終えます（終了コード 4）。

| 表示 | 意味 |
| --- | --- |
| `別のプロセスが、この Run（RUN-20261001000000）を実行しています。` | ほかのプロセスが、同じ Run を実行しています。 |
| `別のプロセスが、同時にこの Run（RUN-20261001000000）の再開を始めました。` | ほかのプロセスが、同時に同じ Run の再開を始めました。 |
| `再開のための保存を読み書きできませんでした（RUN-20261001000000）。` | 再開のための保存やロックを、読み書きできませんでした。技術的な詳細を、続けて表示します。 |

### 再開のための保存

- 再開のための保存は、`<Run のディレクトリ>/checkpoint/` にあります（「[出力の構成](#出力の構成)」）。robots.txt と sitemap.xml の取得の後と、ページの監査が1つ終わるたびに書きます。
- 電源が切れても壊れにくいよう、保存は、一時ファイルに書いてディスクへの書き込みを確定してから、名前を変えて置き換えます。1つ前の保存（`state.prev.json`）も残します。`state.json` が壊れていた場合は、`state.prev.json` から再開します（`state.prev.json` に載っていない、最後に監査を終えたページは、もう一度監査します）。
- 最後まで終えた Run では、`checkpoint/` に `state.json` だけを残します。同じ対象の最も新しい Run を知るためです。これを消すと、それより前の途中の Run を、再開することがあります。
- 保存のファイルは、編集しないでください。中身を確かめて、合わない保存は使いません。Run のディレクトリの名前を変えた場合も、その保存は使いません。
- 最後の処理の後に、保存の終わりを書けなかった場合は、`再開のための保存の終わりを、最後まで書けませんでした。次に同じコマンドを実行すると、最後の処理をもう一度行うことがあります。` と表示します。終了コードは、Run の状態のとおりです。
- 最後まで終えた Run の、使わない保存（ページの保存と `state.prev.json`）を消せなかった場合は、`終わった Run の再開のための保存の一部を消せませんでした（<パス>）。手で消しても問題ありません。` と表示します。終了コードは、Run の状態のとおりです。

### 端末の起動のたびに自動で続ける（Windows のタスク スケジューラ）

BeakSight は、自分では起動しません。再開は、同じコマンドを実行したときに行います。
端末にログオンするたびに、自動で続きを監査したい場合は、Windows のタスク スケジューラに、同じコマンドを登録します。
次の例の `C:\path\to\BeakSight` と `<対象名>` は、置き換えてください。

```powershell
schtasks /Create /TN "BeakSight <対象名>" /SC ONLOGON /TR "cmd /c cd /d C:\path\to\BeakSight && node dist\cli\index.js run --config local\targets\<対象名>.json --headless --output artifacts"
```

- 手で実行するコマンドと、オプションと値を同じにしてください（とくに `--headed`・`--headless`）。違うと、設定が違うので再開せずに、新しい Run を始めます。`--output` は、同じ出力先を指していれば、書き方が違ってもかまいません（例: `artifacts` と `C:\path\to\BeakSight\artifacts`）。違う出力先を指すと、そこには途中の Run がないので、新しい Run を始めます。
- 相対パス（`local\targets\...`、`artifacts`）は、リポジトリのディレクトリから見たものです。そのため、例では、`cd /d` でリポジトリのディレクトリに移ってから実行します。
- タスクの環境で `node` が見つからない場合は、`node` の代わりに、`node.exe` のフルパスを書いてください。
- headed で実行する場合（`--headed`）は、`/IT` を付けて、ログオンしているときだけ実行する設定にしてください。ログオンしていないときは、ブラウザの画面を表示できないためです。headless での実行を勧めます（「[headed で実行するときの注意](#headed-で実行するときの注意)」）。

```powershell
schtasks /Create /TN "BeakSight <対象名>" /SC ONLOGON /IT /TR "cmd /c cd /d C:\path\to\BeakSight && node dist\cli\index.js run --config local\targets\<対象名>.json --headed --output artifacts"
```

- 環境によっては、タスクの作成に、管理者として開いた PowerShell が必要です。
- **監査が最後まで終わったら、タスクを消してください。** 最後まで終えた Run は再開しないので、消さないと、次のログオンで新しい Run を始め、サイトをもう一度監査します。

```powershell
schtasks /Delete /TN "BeakSight <対象名>"
```

## 監査の対象の設定

監査の対象は、JSON の設定のファイルで指定します。
必須の項目は、`target.id` と `site` の2つです。

```json
{
  "target": { "id": "example" },
  "site": {
    "startUrl": "https://example.com/",
    "allowedOrigins": ["https://example.com"]
  }
}
```

- `target.id`: 対象の ID。空でない文字列です。
- `site.startUrl`: 巡回を始める URL。`http:` か `https:` の URL で、認証情報（`user:pass@`）を含められません。
- `site.allowedOrigins`: 巡回を許す Origin の一覧。空にできません。`site.startUrl` の Origin を含める必要があります。
- 知らない項目があると、設定のエラーになります。

### 既定値

書かなかった項目には、次の既定値を使います。設定のファイルに書いた値が、既定値に優先します。

| 項目 | 既定値 | 意味 |
| --- | --- | --- |
| `crawl.maxPages` | `500` | 監査するページの数の上限 |
| `crawl.maxDepth` | `20` | 開始の URL からのリンクの深さの上限 |
| `crawl.maxRuntimeMs` | `3600000`（60分） | 1回の起動ごとの実行時間の上限。この時間を過ぎたら、新しいページの監査を始めません（監査中のページは続けます）。再開した起動は、その起動の開始から数えます。上限で止まった Run は、同じコマンドで続きから再開できます（「[中断と再開](#中断と再開)」） |
| `crawl.navigationTimeoutMs` | `30000` | ページを開く処理の期限 |
| `crawl.overallPageTimeoutMs` | `60000` | 1つのページの監査の期限 |
| `crawl.resourceSettlingTimeoutMs` | `5000` | リソースの読み込みが落ち着くのを待つ期限 |
| `crawl.interactionTimeoutMs` | `3000` | Interaction の1つの候補を確かめる期限 |
| `crawl.minNavigationIntervalMs` | `5000`（5秒） | ページの読み込みの最小の間隔（ミリ秒）。前の読み込みの開始から、この時間以上空けて、次の読み込みを始めます。`1000` 以上にする必要があります。ただし、`site.allowedOrigins` がすべてループバックのアドレス（`127.0.0.1`、`[::1]`、`localhost`）の場合は、`0` 以上にできます。方針と、監査にかかる時間への影響は「[サイトへの負荷](#サイトへの負荷)」を見てください |
| `crawl.maxInteractionsPerPage` | `20` | 1つのページで、Interaction で確かめる候補の数の上限。`1` 以上 `100` 以下にする必要があります（`100` は、1つのページで見つける候補の数の上限です）。上限を超えた候補の扱いは「[サイトへの負荷](#サイトへの負荷)」を見てください |
| `crawl.allowedQueryParameters` | `[]` | URL の正規化で残すクエリの名前。一覧にないクエリは、URL から除きます |
| `browser.headed` | `false` | ブラウザの画面を表示するか |
| `browser.locale` | `"ja-JP"` | ブラウザのロケール |
| `browser.timezone` | `"Asia/Tokyo"` | ブラウザのタイムゾーン |
| `viewports.primaryDesktop` | `1440` × `900` | デスクトップのビューポート |
| `viewports.primaryMobile` | `390` × `844` | モバイルのビューポート |
| `viewports.stressWidths` | `[320, 390, 768, 1024, 1440]` | 幅の走査で調べる幅。デスクトップとモバイルの幅と同じものは、走査しません |
| `audit.performance` | `true` | パフォーマンスの Evidence を集めるか |
| `audit.accessibility` | `true` | アクセシビリティの Evidence を集めるか |
| `audit.interactions` | `true` | Interaction の段階を行うか |
| `audit.screenshots` | `true` | スクリーンショットを撮るか |
| `output.directory` | `"artifacts"` | 出力先のディレクトリ |

- 期限の値には、組み合わせの条件があります。たとえば、Interaction を行う場合は、`crawl.overallPageTimeoutMs` を `crawl.navigationTimeoutMs + 2 × crawl.interactionTimeoutMs` 以上にする必要があります。
- 条件に合わない値は、`validate-config` が英語の技術的な詳細で示します。

### `config/targets/` と `local/` の使い分け

- `config/targets/` には、Git で公開してもよい設定だけを置きます。`config/targets/example.json` は、例の値（`https://example.com/`）だけを持つ見本です。
- 顧客を特定できる実際の設定（実在のサイトの URL など）は、`config/targets/` に置かないでください。Git の管理の対象外の `local/` に置きます（例: `local/targets/<対象名>.json`）。
- `local/` の設定は、自動では選ばれません。必ず `--config` で指定します。

```bash
node dist/cli/index.js validate-config --config local/targets/<対象名>.json
```

### `--config` を省いたときの扱い

- 実行したときのカレントディレクトリの `config/targets/` の中（サブディレクトリを含む）から、`*.json` を探します。
- ちょうど1つだけ見つかった場合に、それを使います。0個か2つ以上の場合は、設定のエラー（終了コード 4）になります。
- `config/targets/` の中の設定は、`target.id` が互いに重なってはいけません。重なると、設定のエラーになります。この確かめは、`--config` で `config/targets/` の中のファイルを指定した場合にも行います。
- このとき、`config/targets/` の中のすべての `*.json` を読みます。どれか1つでも JSON として読めないか、`target.id` がない場合も、設定のエラーになります。選んだ設定に誤りがなくても、同じです。
- `--config` で `config/targets/` の外のファイルを指定した場合は、そのファイルだけを読みます。
- 設定のファイルの先頭の UTF-8 の BOM は、1つだけ取り除いてから読みます。UTF-8 の BOM 付きのファイル（例: Windows PowerShell 5.1 で `-Encoding UTF8` を付けて書いたファイル）も、そのまま使えます。
- UTF-16 などの、UTF-8 でないファイルは読めません。

## 終了コード

終了コードは、最終の Run Status と、Run の外で決まる結果（設定のエラー、Run を始められない、中断）だけで決まります。
サイトの Finding の件数（エラーが何件あるか）では決まりません。
エラーの Finding があっても、必要な確認をすべて終えていれば、終了コードは 0 です。

| 終了コード | 結果 | 意味 |
| --- | --- | --- |
| `0` | 完了（`COMPLETE`） | 必要な確認を、すべて終えました。`validate-config` の成功と、`--help` も 0 です。 |
| `1` | 失敗（`FAILED`） | 監査を実行できませんでした。結果のファイルを書き出せなかった場合と、想定していないエラーの場合も 1 です。 |
| `2` | 一部未完了（`PARTIAL`） | 一部の確認を終えられませんでした。結果は、確認できた範囲のものです。1回目の Ctrl+C で止めた場合、実行時間の上限で止まった場合、サイトが応答しないため止まった場合も、ふつうは 2 です（同じコマンドで、続きから再開できます）。 |
| `3` | 安全のため中止（`ABORTED_BY_SAFETY`） | 安全の不変条件の違反を記録したため、監査を中止しました。 |
| `4` | 設定のエラー（`CONFIG_ERROR`） | 設定のファイル、または CLI の引数に誤りがあります。 |
| `4` | Run を始められない（`RUN_UNAVAILABLE`） | Run を始めずに終えました。同じ出力先で別の Run が実行中の場合、途中の Run の版が違う場合、ほかのプロセスが同じ Run を実行している・同じ Run の再開を始めた場合、再開のための保存を読み書きできない場合です。結果のファイルは書き出しません（「[中断と再開](#中断と再開)」）。 |
| `5` | 中断（`INTERRUPTED`） | 2回目の Ctrl+C（または SIGTERM、SIGHUP）で、すぐに止めました。結果のファイルは書き出していません。再開のための保存は、最後に監査を終えたページまで残っています。同じコマンドを実行すると、続きから再開します。 |

## 出力の構成

`run` は、出力先のディレクトリの下に、Run ごとのディレクトリを作ります。
Run のディレクトリの名前は、Run の ID（`RUN-YYYYMMDDHHmmss`。開始の時刻の UTC）です。

```text
<出力先>/
  RUN-20260925010203/
    run.json                        Run の要約（Run Status、件数、Safety Ledger、実際に使った設定、起動の記録）
    audit.json                      全ページの結果と、すべての Finding
    report.html                     日本語の HTML レポート
    beaksight-audit-bundle.zip      ChatGPT 用のバンドル
    pages/
      PAGE-000001/
        page.json                   ページの結果（Evidence と Finding）
        visible-text.txt            ページの可視テキスト
        desktop/
          viewport.png              表示範囲のスクリーンショット
          full-page.png             ページ全体のスクリーンショット
        mobile/
          viewport.png
          full-page.png
        retry-1/                    再試行した場合の、前の試行のスクリーンショット
          desktop/
            ...
    checkpoint/                     再開のための保存（「中断と再開」）
      state.json                    Run の状態の保存（最後に監査を終えたページまで）
      state.prev.json               1つ前の state.json
      pages/
        PAGE-000001.json            監査を終えたページの保存
      run.lock                      ロック（実行中の Run の印）
    diagnostics/                    サイトの不調で止めたときの診断の記録（「サイトが応答しないとき」）
      site-unavailable-PAGE-000003-1-1.json   不調だったページの監査の結果と、ページ本体の要求の観察（ページと起動と試行ごと）
```

- JSON とテキストは、UTF-8（BOM なし）で、改行は LF です。
- JSON は、スキーマ（`schemas/`）で検証してから書きます。スキーマに合わない場合は、Run Status を `COMPLETE` にしません。
- `visible-text.txt` は、デスクトップの可視テキストから作ります。デスクトップにない場合はモバイルから作り、どちらにもない場合は書きません。
- 新しい Run を始めるときに、同じ名前の Run のディレクトリがすでにある場合は、別の Run の結果を書き換えないよう、監査を始めずに終えます（終了コード 1）。途中の Run を再開するときは、その Run のディレクトリを、そのまま使います。
- 出力先には、スクリーンショットや、サイトの可視テキストが入ります。`artifacts/` は、Git の管理の対象外です。

`checkpoint/` は、途中で止まった Run を、続きから再開するための保存です（「[中断と再開](#中断と再開)」）。

| ファイル | 中身 | 書く時期 |
| --- | --- | --- |
| `checkpoint/state.json` | Run の状態（巡回の記録、ID の採番、実効の設定、起動の記録、サイトへの負荷の記録など） | robots.txt と sitemap.xml の取得の後と、ページの監査が1つ終わるたびに、置き換えます。 |
| `checkpoint/state.prev.json` | 1つ前の `state.json` | `state.json` を置き換える前に、今の `state.json` をこの名前に移します。 |
| `checkpoint/pages/<pageId>.json` | 監査を終えたページの結果 | そのページの監査が終わったときに、1回だけ書きます。 |
| `checkpoint/run.lock` | ロック（プロセスの ID、OS の起動の時刻、ロックを取った時刻、最後に更新した時刻） | Run の開始と再開のときに作り、実行中は1分ごとに更新します。結果のファイルを書き出し、保存の終わりを書いた後に消します。 |

- 最後まで終えた Run では、`checkpoint/` に `state.json` だけが残ります。ページの保存（`checkpoint/pages/`。出力の `page.json` とほぼ同じ中身）と `state.prev.json` は、使わないので消します。
- 止まった Run（1回目の Ctrl+C、実行時間の上限）では、`run.lock` のほかのファイルが残ります。途中で終わった Run では、`run.lock` も残ります（次の起動で、古いロックと判定します）。
- 保存のファイルは、編集しないでください。

`diagnostics/` は、サイトの不調でページの監査を止めたときに書く、原因を調べるための記録です（「[サイトが応答しないとき](#サイトが応答しないとき)」）。結果のファイルではなく、`checkpoint/` の外にあるので、Run を最後まで終えた後も残ります。不調で止めたことがない Run には、ありません。

`run.json` の `executions` は、その Run の起動ごとの記録です。起動の順に、開始の時刻（`startedAt`）、終わりの時刻（`finishedAt`）、終わり方（`endReason`）を持ちます。中断せずに終えた Run では、1件です。

```json
"executions": [
  { "startedAt": "2026-10-01T00:00:00.000Z", "finishedAt": "2026-10-01T01:00:00.000Z", "endReason": "STOPPED_BY_RUNTIME_LIMIT" },
  { "startedAt": "2026-10-02T00:00:00.000Z", "finishedAt": "2026-10-02T00:30:00.000Z", "endReason": "INTERRUPTED_ABNORMALLY" },
  { "startedAt": "2026-10-02T09:00:00.000Z", "finishedAt": "2026-10-02T09:40:00.000Z", "endReason": "COMPLETED" }
]
```

| `endReason` | 意味 |
| --- | --- |
| `COMPLETED` | 下のどの止まり方でもなく、最後の処理まで行いました（Run の状態は問いません）。 |
| `STOPPED_BY_RUNTIME_LIMIT` | 実行時間の上限（1回の起動ごと）で、今のページを終えてから止まりました。 |
| `STOPPED_BY_SIGNAL` | 1回目の Ctrl+C などで、今のページを終えてから止まりました。 |
| `STOPPED_BY_SAFETY_VIOLATION` | 安全の不変条件の違反で止まりました。 |
| `STOPPED_BY_SITE_UNAVAILABLE` | サイトが応答しないため、残りのページを監査せずに止まりました。同じコマンドで再開できます（「[サイトが応答しないとき](#サイトが応答しないとき)」）。 |
| `INTERRUPTED_ABNORMALLY` | プロセスが途中で終わりました（強制終了、停電、2回目の Ctrl+C など）。終わりの時刻は、その起動の最後の保存の時刻です。 |

- `run.json` の `startedAt` は最初の起動の開始、`finishedAt` は最後の起動の終わりの時刻です。`environment`（実行の環境）は、最初の起動のものです。

## 結果の読み方

### CLI の表示

`run` は、実行中に、ページの監査が1つ終わるたびに、進み具合を1行で表示します。サイトへの負荷が上限の中に収まっていることを、実行中に数字で確かめるためです（「[サイトへの負荷](#サイトへの負荷)」）。

```text
進み具合: 監査を終えたページ 12件（発見したページ 85件、上限 50件）・ページの読み込み 284回・許可 Origin への要求 1,930件（直近1分 38件、1分あたり最大 61件）・許可 Origin の外 12件・経過 24分10秒
```

- 監査を終えたページ: 監査を終えたページの数です。一部未完了と失敗のページも含みます。結果の「監査したページ」（最後まで監査できたページだけの数）とは、別の数です。括弧の中は、これまでに発見したページの数と、ページの数の上限（`crawl.maxPages`）です。再開した Run では、再開の前に監査を終えたページも含みます（Run の全体の数です）。
- ページの読み込み: ページの読み込みの回数です。`run.json` の `load.navigationCount` と同じ数え方で、読み込みを始められなかったものも含みます（「[実績の確かめ方](#実績の確かめ方)」）。
- 許可 Origin への要求: 許可 Origin へ、ネットワークに送った要求の件数です。括弧の中は、直近の1分に終わった要求の件数と、1分あたりの最大です。
- 許可 Origin の外: 許可 Origin の外へ、ネットワークに送った要求の件数です。
- 経過: この実行を始めてからの時間です。1時間未満は秒まで、1時間以上は分まで示します（例: `1時間5分`）。再開した Run でも、その起動を始めてからの時間です。
- 再開した Run では、ページの読み込みの回数と、要求の件数も、再開の前の分を含みます（`run.json` の `load` と同じ数え方です）。

途中の Run を再開するときは、開始の行（`監査を始めます。`）の前に、再開の知らせを1行で表示します。監査を終えたページの数は、進み具合の行と同じ書き方で、再開の前に監査を終えたページの数です。ほかの知らせは「[中断と再開](#中断と再開)」を見てください。

```text
途中の Run（RUN-20261001000000。監査を終えたページ 3件）を、続きから再開します。最初から始めるには --new を付けてください。
監査を始めます。
対象: example
開始の URL: https://example.com/
```

`run` は、最後に次の項目を表示します。

- Run の状態（例: `完了（COMPLETE）`）
- 出力先（Run のディレクトリ）と、HTML レポートと ChatGPT 用のバンドルのパス
- ページの網羅（発見、監査、一部未完了、失敗、スキップのページの数）
- サイト品質の指摘の件数（エラー、警告、情報）と、安全の指摘の件数
- サイトへの負荷（ページの読み込みの回数と、許可 Origin への要求の件数と1分あたりの最大。「[サイトへの負荷](#サイトへの負荷)」）
- 実行の記録（実行の回数と、再開の回数）。`run.json` の `executions` の件数が実行の回数で、そのうち最初の起動の後の起動が再開です。中断せずに終えた Run でも、`実行: 1回、再開 0回` と表示します（「[中断と再開](#中断と再開)」）
- サイトが応答しないため止まった場合は、止めたことと、再開のしかた（「[サイトが応答しないとき](#サイトが応答しないとき)」）
- 未完了の理由がある場合は、その件数

たとえば、2回中断して、3回目の起動で最後まで終えた Run では、サイトへの負荷の行の次に、次の行を表示します。

```text
実行: 3回、再開 2回
```

サイトが応答しないため止まった Run では、実行の記録の行の次に、止めたことの1行を表示します。

```text
実行: 1回、再開 0回
サイトが応答しないため、監査を止めました（desktop:passive:TIMEOUT）。サイトが戻ってから、同じコマンドで続きから再開してください。
```

- この行は、この起動の終わり方（`run.json` の `executions` の最後の `endReason`）が `STOPPED_BY_SITE_UNAVAILABLE` のときだけ表示します。Run の理由では決めません。前の起動がサイトの不調で止まっていても、この起動がほかの終わり方（最後まで終えた場合など）なら、表示しません。
- 括弧の中は、最初に検知した失敗の技術的な詳細で、`run.json` の `incompleteReasons` の `SITE_UNAVAILABLE` の `detail` と同じです。その理由がない場合は、括弧を表示しません。

### HTML レポート

`report.html` は、ブラウザで開く静的な HTML です。
`page.json` やスクリーンショットへの相対リンクを持つので、Run のディレクトリごと扱ってください。
レポートは、次の節からなります。

1. 要約: Run の状態、ページの網羅、指摘の件数、上限、サイトへの負荷、実行の記録、未完了の理由、実行の環境
2. 重大な指摘: 重大度がエラーの指摘（カテゴリを問いません）
3. カテゴリ別の指摘: ネットワーク、JavaScript、リンク、DOM、フォーム、レイアウト、アクセシビリティ、パフォーマンス、ページ間、安全
4. インタラクション: 操作の候補ごとの結果
5. 安全: 安全のために止めた操作と、安全の不変条件の違反（「[Safety Ledger の読み方](#safety-ledger-の読み方)」）
6. ページの一覧: ページごとの状態、ビューポートごとの状態、スクリーンショット

要約の「実行の記録」には、実行の回数と再開の回数（CLI の実行の行と同じ値）と、起動ごとの一覧を示します。一覧の各行は、何回目の実行か、開始の日時、終了の日時、終わり方です。終わり方は、日本語のラベル（例: 「実行時間の上限で停止」）、`run.json` の `endReason` のコード、説明で示します（コードの意味は「[中断と再開](#中断と再開)」の表を見てください）。

`mailto:` や `tel:` などの URL と、安全のために止めた操作の URL は、リンクにせず、文字として示します。

### Run Status の意味

Run Status は、監査を最後まで行えたかを表します。サイトの品質の良し悪しを表すものではありません。

- `COMPLETE`: 必要な確認を、すべて終えました。サイトに問題があるかどうかは、Finding で確かめます。
- `PARTIAL`: 一部の確認を終えられませんでした。たとえば、上限（ページの数、深さ、実行時間）に達した場合や、期限を過ぎた場合、Ctrl+C で止めた場合です。理由は、レポートの要約の「未完了の理由」と、`run.json` の `incompleteReasons` にあります。
- `FAILED`: 監査を実行できませんでした。たとえば、実行の前の確認（PREFLIGHT）に失敗した場合や、Run のディレクトリを作れなかった場合です。
- `ABORTED_BY_SAFETY`: 安全の不変条件の違反を記録しました。違反を記録した後は、新しいページ、次のビューポート、次の Interaction の候補を始めません。残りのページは、理由 `SAFETY_VIOLATION_ABORT` のスキップになります。結果のファイルは、止めたことを含めて書き出します。

### Finding と Evidence

- Evidence は、ブラウザで観測した事実の記録です（ネットワーク、コンソール、DOM、レイアウト、色、パフォーマンス、アクセシビリティ、スクリーンショットなど）。各ページの `page.json` にあります。
- Finding は、Rule が Evidence から判定した指摘です。重大度（エラー、警告、情報、安全）、カテゴリ、Rule の ID（`ruleId`）、文言を持ちます。
- Finding は、根拠の Evidence を `evidenceRefs` で参照します。HTML レポートの指摘の表からは、Evidence（`page.json` の中の場所）とスクリーンショットへたどれます。
- 件数は、サイト品質（エラー、警告、情報）と安全を、分けて数えます。

### 幅の走査の結果

レイアウトは、デスクトップとモバイルのビューポートのほかに、`viewports.stressWidths` の幅でも調べます（幅の走査）。
既定値では、デスクトップ（1440）とモバイル（390）の幅を除いた、320、768、1024 の3つの幅を調べます。

- 幅の走査は、ページごとに、デスクトップのビューポートの監査の中で1回だけ行います。
- 走査の結果は、デスクトップのレイアウトの Evidence の中（`stressSweep`）に記録します。
- 走査で見つかったはみ出し（例: `DOCUMENT_HORIZONTAL_OVERFLOW`）の Finding は、ビューポートがデスクトップとして記録されます。
- そのため、HTML レポートの指摘の表では、ビューポートの欄が「デスクトップ」になります。どの幅で見つかったかは、文言の先頭（例: 「レスポンシブの幅 320 px の確認で、…」）で分かります。

### ChatGPT 用のバンドル

`beaksight-audit-bundle.zip` は、後段の意味監査のために、ChatGPT に手動でアップロードする ZIP です。次のファイルを含みます。

- `manifest.json`: 中のファイルの一覧（大きさと SHA-256）と、入れられなかったファイル（`omittedFiles`）
- `run.json`: 書き出した `run.json` そのもの
- `summary.json`、`findings.json`、`pages.json`、`evidence-index.json`: 要約、指摘、ページ、Evidence の索引
- `pages/<pageId>/page.json`: 各ページの結果（一次の Evidence）
- 指摘に関係するスクリーンショット（合計 64 MiB まで。超えた分は `omittedFiles` に書きます）

- 状態、理由、重大度などの値は、英数字のコードのままです。表示用の日本語のラベルは入れません。
- Finding の文言（日本語）は、そのまま入ります。
- ページの HTML などの、生の応答の本文は含めません。
- ただし、各ページの `page.json` には、ページの可視テキストと URL が入ります。

アップロードする前に、バンドルの中身が、ChatGPT に渡してよい内容かを確かめてください。

## 読み取り専用の保証の範囲

BeakSight は、サイトの状態を変える操作をしないように作っています。

- ページを観測する段階（Passive）では、ネットワークへのリクエストを `GET` と `HEAD` に限ります。ほかのメソッドのリクエストは、送る前に遮断し、記録します。
- WebSocket の接続は、遮断します。
- 許可 Origin の外へのページの移動は、遮断します。巡回でたどるのは、許可 Origin の中の通常のリンクだけです。
- Interaction（開閉のボタンなどの操作）は、ページを観測する環境とは別の、使い捨ての環境で行います。操作の前に通信を止め、操作の後の通信、ページの移動、ポップアップ、ダウンロード、WebSocket を遮断します。
- 送信のボタン、フォームに属する要素、ほかのページへ移動するリンク、ダウンロード、外部の Origin や特殊なスキーム（`tel:`、`mailto:` など）へ作用する要素は、操作しません。
- フォームの送信、ダウンロード、外部のアプリの起動は行いません。ブラウザの環境は、ダウンロードを受け付けない設定で作ります。

保証できない範囲もあります。

- サーバの側で副作用を持つ `GET` のエンドポイントがあっても、クライアントの側からは見分けられません。
- ページ自身が読み込む、ほかの Origin のリソース（画像、スクリプト、iframe など）への `GET` は、送られます。遮断するのは、許可 Origin の外へのページそのものの移動です。
- ページのスクリプトによる外部スキームへの移動は、止められません。headed でも headless でも、外部のアプリが起動する可能性があります。BeakSight は、この移動を検出したら、安全の不変条件の違反として Run を止めます（「[headed で実行するときの注意](#headed-で実行するときの注意)」）。

## サイトへの負荷

BeakSight は、監査の対象のサイトに、短い時間に多くの要求を送らないように作っています。
そのために、ページの読み込みの間隔を空け、1つのページの読み込み直しの回数に上限を置き、同じ起動の中で同じ画像や動画などを取り直さないようにします。
サイトの不調（応答がない、接続できない、503 などの応答）を検知したら、それ以上の読み込みを送らずに止めます（「[サイトが応答しないとき](#サイトが応答しないとき)」）。
実際に送った要求の数は、Run ごとに記録します。

### ページの読み込みの間隔

- BeakSight は、ページの読み込みを、前の読み込みの開始から `crawl.minNavigationIntervalMs` 以上空けてから始めます。既定は 5秒で、ページの読み込みは1分に12回までになります。
- この間隔は、Run の中のすべてのページの読み込みに使います。Passive の監査（デスクトップとモバイル。再試行を含む）、幅の走査、Interaction、robots.txt と sitemap.xml の読み込みが対象です。
- `site.allowedOrigins` にループバックでない Origin が1つでもある場合は、間隔を 1秒より短くできません。設定の誤りで、短い時間に多くの読み込みをしないためです。
- `site.allowedOrigins` がすべてループバックのアドレスの場合は、間隔を 0 にできます。ローカルの fixture での検証のための例外です。
- 間隔のために待った時間は、ページの監査の期限を消費しません。実行時間の上限（`crawl.maxRuntimeMs`）には含めます。
- サイトの不調で捨てたページを確かめ直して通った後は、この間隔を 2 倍（上限は設定の 8 倍）に延ばして続けます（「[サイトが応答しないとき](#サイトが応答しないとき)」）。延ばした間隔はその起動の間だけで、次の起動は設定の値から始めます。

### 1つのページの読み込みの回数

1つのページにつき、次の回数だけページを読み込みます。

| 段階 | 読み込みの回数 |
| --- | --- |
| Passive の監査 | 2回（デスクトップとモバイル。再試行した場合は、その分だけ増えます） |
| 幅の走査 | 幅ごとに1回（既定では 320、768、1024 の3回） |
| Interaction | 候補ごとに1回（デスクトップだけ。既定では最大 20回） |

- Interaction で確かめる候補は、1つのページにつき `crawl.maxInteractionsPerPage`（既定は 20）までです。上限を超えた候補は確かめません。そのページは、一部未完了（`PARTIAL`）になります。デスクトップの未完了の理由（`COLLECTOR_INCOMPLETE`）の技術的な詳細に、`interaction:limit:remaining=<残りの件数>` と記録します。
- BeakSight は、すべての読み込み（Passive、幅の走査、Interaction）で、Run 全体のキャッシュを使います。同じ起動の中では、画像、動画と音声、スタイルシート、スクリプト、フォントは、最初の1回だけネットワークから取り、2回目からはキャッシュから返します（ネットワークに送りません）。ふつうの利用者が、ブラウザのキャッシュを使いながらサイトを見て回るのと同じです。
- 文書（ページと iframe の HTML）は、サイトの今の状態を見るため、どの読み込みでも、毎回ネットワークから取ります。外部の iframe の文書も取りますが、その中の画像などは、読み込み直しでは、キャッシュになければ送りません。
- Passive の2回の読み込み（デスクトップとモバイル）では、キャッシュにないものは、許可 Origin の外のもの（外部のストレージの画像や動画、外部のサービスのスクリプトなど）も、ネットワークから取ります。
- キャッシュに入れるのは、`GET` で status が 200 の、画像、動画と音声、スタイルシート、スクリプト、フォントの応答のうち、読み込みが成功して終わったものだけです。本文の途中で接続が切れた応答（`net::ERR_CONTENT_LENGTH_MISMATCH` など）と、読み込みの途中で閉じたページの応答は、入れません。次の読み込みでは、ネットワークから取り直します。
- 動画と音声は、ブラウザがファイルの全体を範囲の指定（`Range: bytes=0-`）で求めます。この要求に、サーバがファイルの全体を status 206 で返した応答と、範囲の指定を無視してファイルの全体を status 200 で返した応答も、入れます。
- `Cache-Control: no-store` の応答、ファイルの一部だけを返した応答（ほかの `Range` の header を付けた要求の応答など）、16 MiB より大きい応答は入れません。合計は 256 MiB までで、超えた分は、最も前に使ったものから捨てます。
- キャッシュから動画を返すときは、要求に `Range` の header があっても、ファイルの全体を status 200 で返します。
- キャッシュは、ファイルに保存しません。起動ごとに空から始まり、起動の終わりに捨てます。
- キャッシュにないもので、許可 Origin の中への要求は、どの読み込みでもネットワークに送ります。キャッシュに入れない要求（XHR と fetch、ファイルの一部を求める `Range` の要求、`Cache-Control: no-store` の応答、16 MiB より大きい応答など）は、読み込みのたびに送ります。また、幅によって選ぶ画像が変わる場合（`srcset` など）は、Passive の2回で取っていない画像を、幅の走査の読み込みで取ります。
- 読み込み直し（幅の走査と Interaction）では、許可 Origin の外への要求（文書の読み込みを除く）は、キャッシュになければ送りません。外部のサービス（アクセス解析、広告など）への要求も、送りません。

### ページの先読み

- BeakSight は、speculation rules による先読み（prefetch と prerender）と、`<link rel="prerender">` による先読み（ほかのページの先回りの読み込み）を、Chromium の起動の設定で止めます。これらの先読みの要求は、BeakSight の読み込みの間隔と負荷の記録の外で起きるためです。監査に使うページは、BeakSight が自分で読み込むので、監査の結果は変わりません。
- `<link rel="prefetch">` による先読みは、止められません。その要求は、ページが読み込む画像などと同じく、Guard を通り、負荷の記録（`run.json` の `load`）に数えます。ページの読み込みの間隔（`crawl.minNavigationIntervalMs`）の対象ではありません。

### ページのアイコン

- BeakSight が使う Chromium は、ページのアイコン（favicon）を、自分で取りに行くことがあります。
- ページにアイコンの指定がない場合、Chromium は、Origin の直下の `/favicon.ico` を取りに行きます（例: `https://example.com/` のページなら `https://example.com/favicon.ico`）。この要求は、ふつうは止まりますが、まれにサイトに届くことがあります。その場合も、届くのは許可 Origin への `GET` の1件だけです。この要求は、負荷の記録（`run.json` の `load`）には数えません。
- ページがアイコンの URL を指定している場合は、その要求は、ページが読み込む画像などと同じく、Guard を通り、負荷の記録に数えます。読み込み直しでは、許可 Origin の外へは送りません。

### 制約

- 読み込み直しでは、外部のサービスのスクリプトがキャッシュから動いても、その通信は送りません。そのため、外部のサービスが作る部品（チャットのボタンなど）が現れないことがあります。Interaction の候補がそうした部品の場合は、候補が見つからず、確認できなかった（`NOT_VERIFIABLE`）になります。
- 幅の走査では、外部の iframe の中身が表示されないことがあります。そのため、外部の iframe によるはみ出しを見逃すことがあります。
- Run 全体のキャッシュは、URL だけで応答を見分けます。`Vary` の header は考えません。有効期限（`Cache-Control` の `max-age` など）も考えず、1回の起動の間は、同じ URL を同じ内容とみなします。
- Passive の2回の読み込みでは、キャッシュにない外部のサービスへの要求も送ります。そのため、1つのページにつき2回分が、アクセス解析などに記録されることがあります。
- 同じ起動の中の2ページ目からは、Passive の読み込みの速さ（パフォーマンスの値）が、画像などがキャッシュにある状態の値になります。キャッシュは起動ごとに空から始まるので、起動の最初のページだけは、キャッシュがない状態の値になります。中断した Run を再開した場合も、再開した起動の最初のページは、キャッシュがない状態で読み込みます。
- 1つのページのデスクトップとモバイルも、キャッシュを共有します。モバイルの読み込みは、デスクトップの読み込みで取った画像などを、キャッシュから使います。
- キャッシュから返した動画は、途中への移動（シーク）ができません（ファイルの全体を status 200 で返すため）。監査では、動画の途中へ移動しません。
- キャッシュから返した応答は、ページの結果の network の Evidence で、ネットワークから取った応答と見分けにくくなります。キャッシュから返した応答にも、status、header（元の応答の `date` を含みます）、大きさの値が入るためです。そのため、network の Evidence の大きさを、サイトから実際に取った量（転送量）の根拠として読まないでください。実際にネットワークに送った要求の数は、`run.json` の `load` で確かめてください（「[実績の確かめ方](#実績の確かめ方)」）。Finding の判定は、応答の status と失敗だけを使うので、キャッシュから返しても、Finding は変わりません。

### full audit での上限の選び方

この間隔では、ページの数が多いと、監査に長い時間がかかります。
既定の `crawl.maxPages`（500）のページは、既定の `crawl.maxRuntimeMs`（1回の起動ごとに1時間）では、1回の起動で監査を終えられません。
実在のサイトを広く監査する場合（full audit）は、`crawl.maxPages` と `crawl.maxRuntimeMs` を明示して選んでください。
`crawl.maxRuntimeMs` は1回の起動ごとの上限なので、上限で止まった Run は、同じコマンドを実行すると、続きから監査します（「[中断と再開](#中断と再開)」）。full audit を、何回かの起動に分けて行うこともできます。

目安は、次のとおりです。どれも推定です。

- 必要な時間は、少なくとも「ページの数 × 1つのページの読み込みの回数 × 間隔」です。
- 既定の設定で、Interaction で確かめる候補が上限の20件になるページは、読み込みが25回（Passive 2、幅の走査 3、Interaction 20）になります。間隔が 5秒なので、1つのページに少なくとも約125秒かかります。
- そうしたページばかりの場合、1時間に監査できるのは、約29ページ以下です。
- 例: 200ページを監査する場合は、200 × 25 × 5秒 = 25,000秒（約7時間）が目安です。実際の時間は、ページの読み込みと監査にかかる時間の分だけ長くなります。余裕を見て、`crawl.maxRuntimeMs` を `28800000`（8時間）にします。
- Interaction の候補が少ないページは、これより早く終わります。
- `crawl.maxRuntimeMs` を過ぎると、新しいページの監査を始めません。Run は一部未完了（`PARTIAL`）になり、理由は `MAX_RUNTIME_REACHED` です。同じコマンドを実行すると、続きから再開します。再開した起動の上限は、その起動の開始から数えます。
- `crawl.maxInteractionsPerPage` を小さくすると、時間は短くなります。ただし、上限を超えた候補は確かめず、そのページは一部未完了になります。
- `crawl.minNavigationIntervalMs` を短くすると、時間は短くなりますが、サイトへの負荷が増えます。

```json
{
  "target": { "id": "example" },
  "site": {
    "startUrl": "https://example.com/",
    "allowedOrigins": ["https://example.com"]
  },
  "crawl": {
    "maxPages": 200,
    "maxRuntimeMs": 28800000
  }
}
```

### 実績の確かめ方

実際の負荷は、次の3か所で確かめられます。どれも、同じ記録（`run.json` の `load`）の値を示します。

- `run.json` の `load`（ChatGPT 用のバンドルの `summary.json` の `load` も、同じ値です）
- HTML レポートの要約の「サイトへの負荷」（すべての項目）
- CLI の結果の1行（ページの読み込みの回数と、許可 Origin への要求。例: `サイトへの負荷: ページの読み込み 120回、許可 Origin への要求 3,400件（1分あたり最大 210件）`）

| 項目（`run.json` の `load`） | レポートの表示 | 読み方 |
| --- | --- | --- |
| `minNavigationIntervalMs` | ページの読み込みの最小の間隔 | 実際に使った設定の値（ミリ秒）。 |
| `maxInteractionsPerPage` | 1ページで監査する Interaction の候補の上限 | 実際に使った設定の値。 |
| `navigationCount` | ページの読み込みの回数（始められなかったものを含む） | 間隔を守るために数えた、読み込みの開始の回数。待った後に読み込みを始められなかった場合も数えるので、実際の読み込みの回数より多いことがあります。 |
| `pacingWaitMs` | 間隔のために待った時間の合計 | 間隔を守るために待った時間の合計（ミリ秒）。 |
| `requests.allowedOrigins` | 許可 Origin への要求 | ネットワークに送った要求の件数（`count`）と、1分あたりの最大（`peakPerMinute`。要求の終わった時刻で数えた、直近の60秒の件数の最大）。 |
| `requests.otherOrigins` | 許可 Origin の外への要求 | 許可 Origin の外へ、ネットワークに送った要求の件数と、1分あたりの最大。 |
| `requests.servedFromCache` | Run 全体のキャッシュから返した要求 | ネットワークに送らずに、キャッシュから返した要求の件数。 |
| `requests.withheldOtherOrigins` | 送らなかった、許可 Origin の外への要求 | 読み込み直しで、キャッシュになかったので送らなかった、許可 Origin の外への要求の件数。 |

- 要求は、ネットワークに送ったものを、終わった（完了した、または失敗した）時点で数えます。
- Guard が安全のために止めた要求と、キャッシュから返した要求は、`count` に数えません。Guard が止めた要求は、Safety Ledger に記録します。

## headed で実行するときの注意

**headless での実行を勧めます。** 既定値は headless です。
headed では、ブラウザの環境（Context）を作るたびに、ブラウザのウィンドウが開きます。そのため、実行中は、画面がほぼ使えません。
外部のアプリの扱い（下の項目）は、headed と headless で同じです。headless を勧めるのは、外部のアプリのためではありません。
実行中は、ブラウザの画面（タブやウィンドウ）を閉じたり、停止・再読み込みしたりしないでください。止めるときは、端末で Ctrl+C を使います（「[中断と再開](#中断と再開)」の「Ctrl+C で止める」）。

- ページのスクリプトが外部スキーム（`mailto:`、`tel:` など）へ移動しようとした場合、BeakSight はその移動を止められません。外部スキームへの移動は、ネットワークを通らないためです。
- BeakSight は、headless でも、headed と同じ通常の Chromium を使います。そのため、headed（`--headed`、または `browser.headed: true`）でも headless でも、メールのアプリや電話のアプリなどの、外部のアプリが起動する可能性があります。
- この移動の試みを検出した場合は、headed と headless を問わず、安全の不変条件の違反（`EXTERNAL_SCHEME_NAVIGATION_ATTEMPTED`）として記録します。その時点で、そのブラウザの環境を閉じます。Run は `ABORTED_BY_SAFETY`（終了コード 3）になります。止められない経路なので、外部のアプリが起動した可能性を隠さずに、Run を止めます。起動そのものは、防げません。移動の試みは、Safety の記録（外部スキームへの移動の試み）にも残します。
- ページのスクリプトが新しいウィンドウ（`window.open` や `target="_blank"` のリンク）で外部スキームを開こうとした場合は、この違反に加えて、`FRAME_CLASSIFICATION_FAILED` の違反も記録します。新しいウィンドウの移動は、どの frame の移動かを判定できないためです。
- サーバのリダイレクトによる外部スキームへの移動（3xx の `Location` が外部スキーム）は、ブラウザがたどる前に止めます。この経路は、止めて防げるので、headed でも headless でも違反にしません。記録の理由は `EXTERNAL_SCHEME_REDIRECT_BLOCKED` です。
- 外部のアプリの起動を避けたい場合は、headed と headless を問わず、`mailto:` や `tel:` の既定のアプリがない、隔離した環境（仮想マシンなど）で実行してください。

## Safety Ledger の読み方

Safety Ledger は、Guard（安全の確認の仕組み）が止めた操作と、安全の不変条件の違反の記録です。
要約は `run.json` の `safety` に、事象の一つ一つは各ページの `page.json` の安全の記録（Evidence）にあります。
HTML レポートでは「安全」の節に示します。

| 項目（`run.json`） | レポートの表示 | 読み方 |
| --- | --- | --- |
| `guardEnabled` | 安全の確認: 有効 / 無効 | Guard が有効だったか。 |
| `blockedActions` | 遮断した操作 | リクエスト、ナビゲーション、外部への作用、ポップアップ、ダウンロード、WebSocket の、遮断した件数。 |
| `blockedRequestsByMethod` | メソッドごとの、遮断したリクエスト | 遮断したリクエストの、メソッドごとの件数。 |
| `excludedInteractionCandidateCount` | 安全のため除外した Interaction の候補 | 安全のため、機械的に操作の対象から外した候補の数。 |
| `invariantViolationCount`、`invariantViolations` | 安全の不変条件の違反 | 違反の件数と、各違反のコードと内容。1件でもあれば `ABORTED_BY_SAFETY` になります。 |
| `recordTruncated` | 安全の記録 | 記録が上限に達したか。達した場合、遮断した件数は下限です。Run は `COMPLETE` になりません（`PARTIAL`）。 |

- 遮断した操作があることは、失敗ではありません。Guard が正しく止めた証拠です。
- 問題になるのは、不変条件の違反です。違反があると、Run は `COMPLETE` になりません。

レポートの「Safety の事象の一覧」は、次の種類の記録を示します（名前は `page.json` の安全の記録の項目の名前です）。

| 記録の名前 | レポートの表示 |
| --- | --- |
| `blockedRequests` | 遮断したリクエスト |
| `blockedNavigations` | 遮断したナビゲーション |
| `blockedWebSockets` | 遮断した WebSocket |
| `blockedExternalActions` | 実行しなかった外部への作用 |
| `excludedInteractionCandidates` | 除外した Interaction の候補 |
| `blockedInteractionRequests` | 操作中に遮断したリクエスト |
| `blockedInteractionNavigations` | 操作中に遮断したナビゲーション |
| `blockedPopups` | 遮断したポップアップ |
| `blockedDownloads` | 遮断したダウンロード |
| `blockedInteractionWebSockets` | 操作中に遮断した WebSocket |
| `externalSchemeNavigations` | 外部スキームへの移動の試み |

外部スキームへの移動の試みは、理由で見分けます。

- `EXTERNAL_SCHEME_NAVIGATION`: ページが移動を試みた記録です。止められない経路です。headed でも headless でも、外部のアプリが起動した可能性があります。そのため、安全の不変条件の違反（`EXTERNAL_SCHEME_NAVIGATION_ATTEMPTED`）も記録し、Run は `ABORTED_BY_SAFETY` になります。
- `EXTERNAL_SCHEME_REDIRECT_BLOCKED`: サーバのリダイレクトを、ブラウザがたどる前に止めた記録です。

## パフォーマンスの値（RUM/APM）について

BeakSight のパフォーマンスの値は、監査の実行の中で、ブラウザがページを開いたときに測った、合成の計測（Synthetic）の値です。

- 実際の利用者の環境で測った値（RUM）ではありません。値は、実行した環境やネットワークに左右されます。
- APM の値でもありません。Navigation Timing、Resource Timing、`Server-Timing`、`traceparent` などは、ブラウザから見える範囲の記録です。サーバの内部の記録（データベースの処理の時間など）は含みません。
- パフォーマンスの Finding（例: `POOR_LCP`）の重大度は、警告です。
- 観測できなかった値は、0 などで埋めずに「未観測」と示します。

## Windows PowerShell での日本語の表示

CLI の出力は、UTF-8 の日本語です。

- コンソールに直接表示する場合は、Windows PowerShell 5.1 と cmd.exe のどちらでも読めます。
- Windows PowerShell 5.1 で、出力をパイプやリダイレクトに渡すと、`[Console]::OutputEncoding` が既定（コードページ 932）のままの場合に、文字化けします。パイプやリダイレクトの前に、次のコマンドを実行してください。

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

- BeakSight は、コンソールのコードページを変えません。
- 結果は、UTF-8 の `report.html` と JSON（`run.json`、`audit.json`）で見ることも勧めます。

### ローカルでの検証の手順

1. Chromium を入れます（初回だけ）: `npx playwright install chromium`
2. 全体を確かめます: `npm run verify`
3. fixture の全体の監査を確かめます:

```bash
npx vitest run tests/integration/fixture-full-crawl.test.ts
```

fixture の全体の監査のテストは、次のことを行います。

- テスト用の fixture のサイト（`fixtures/site/full-crawl/`）を、ローカルのサーバで動かします。
- ビルドした CLI を別のプロセスで起動し、`--headless` で最後まで監査します。
- 既定の設定で、Run が `COMPLETE` になることを確かめます。わざと壊した箇所ごとに期待した Finding が出ること、安全の不変条件の違反がないこと、サーバに届いたリクエストが `GET` と `HEAD` だけであることも確かめます。

テストは、Chromium を headless だけで起動します。実在の外部のサイトにはアクセスしません。

### アーカイブのスクリプト

`tools/archive_beaksight.ps1` は、本番用のソースだけの ZIP を作ります。
依存パッケージ、生成物、テスト、fixture、ドキュメント、リポジトリのメタデータ、エージェントの作業ファイルは、含めません。

```powershell
powershell -ExecutionPolicy Bypass -File tools/archive_beaksight.ps1
```

出力先の既定は、環境変数 `BEAKSIGHT_ARCHIVE_OUTPUT_DIR` の値です。
設定していない場合は、リポジトリと同じ階層の `BeakSight-archive` フォルダです。
`-OutputDirectory` で指定することもできます。
